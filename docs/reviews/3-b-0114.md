## C — blocking

- **C1 — `tests/test_hermetic.py:229`: the new guard pins one twin, not both, so the twin that
  round 2 held this branch for can still be left behind silently.** The loop runs two child
  entries, `'import tests'` and `'import tests.test_00_home'`. The second imports the `tests`
  package first — Python cannot import `tests.test_00_home` without running `tests/__init__.py` —
  so the package guard strips `core.hooksPath` before `test_00_home` is ever reached, and
  `test_00_home`'s own `hermetic.strip_git_config(os.environ)` (`tests/test_00_home.py:31`) is
  masked. Nothing in this test can fail because of it.

  Reproduced both ways on this head, from this session (which carries `GIT_CONFIG_COUNT=4` with
  `core.hooksPath` at index 1):

  - delete `hermetic.strip_git_config(os.environ)` from `tests/__init__.py:26` →
    `python3 -m unittest tests.test_hermetic.OneBuilderTests.test_both_of_the_suites_entry_points_are_hermetic`
    → `FAILED (failures=1)` at `tests/test_hermetic.py:234`, `AssertionError: 'core.hookspath'
    unexpectedly found in [...] : import tests`. The guard works for this twin.
  - delete `hermetic.strip_git_config(os.environ)` from `tests/test_00_home.py:31` → the same
    test → `Ran 1 test in 0.432s` / `OK`. **Green with the twin broken.** And it really is broken:
    `python3 -m unittest discover -s tests -p "test_00_home.py"` with that same line gone →
    `FAILED (failures=1)` at `tests/test_00_home.py:51`. Note the test id in that run,
    `test_00_home.HomeIsHermetic...`, not `tests.test_00_home...` — `discover -s tests` loads the
    module **top-level** and never imports `tests/__init__.py`, which is exactly why two guards
    exist and exactly the mode this test does not cover.

  The comment at `tests/test_hermetic.py:214-215` ("Both are proved here from a child carrying all
  three, so neither twin can be left behind again") and `29276db`'s subject ("a test pins both")
  are therefore not true of `tests/test_00_home.py`. Blast radius today is the developer entry
  point only — `tools/run_tests.py:92-94` names modules package-qualified (`tests.test_00_home`) and
  its `child_env` goes through `hermetic.build`, so CI is covered twice over — but
  `discover -s tests` is the mode `tests/test_00_home.py:1` names as its reason to exist.

  The fix is one more child run in the same loop, after it. Append to
  `test_both_of_the_suites_entry_points_are_hermetic`:

  ```python
  # and the third entry point, the one tests/__init__.py cannot cover: `discover -s tests` loads
  # test_00_home top-level, so only its own guard runs. HomeIsHermetic asserts the same three.
  out = subprocess.run(['python3', '-m', 'unittest', 'discover', '-s', 'tests',
                        '-p', 'test_00_home.py'], cwd=root, env=base,
                       capture_output=True, text=True)
  self.assertEqual(out.returncode, 0, out.stderr)
  ```

  Verified here: under the same `base` this test builds (identity planted, `core.hooksPath`
  planted, `ASF_HOME`/`ASF_TESTS_HOME` popped) that child gives `rc = 0` / `OK` today, and it is
  the run shown above to go red the moment `tests/test_00_home.py:31` is removed. With it, the
  comment at `:214-215` becomes true as written.

## I — would change, will not block

- **I1 — `asf/harvest/lane.py:1320`: `:meth:`GhHost.merge`` names a class that does not exist.**
  The class is `GitHubHost` (`:1428`); `grep -rn "GhHost" asf tests` returns this docstring line
  and nothing else, so the cross-reference resolves nowhere. The sentence is also slightly off in
  substance — `squash_subject` is called at `:1352` *before* `host.merge`, so on a queue repo the
  subject is computed and then dropped by the early return at `:1516-1518`, rather than the merge
  "returning before this". `:meth:`GitHubHost.merge` ignores it on ``--auto``` says both.
- **I2 — `asf/harvest/lane.py:1527-1530`: the `--subject` fallback is silent, and the window it
  reopens is real if narrow.** When an old `gh` rejects the flag the merge is retried without it
  and the lane reports `landed` with no line saying the subject was dropped — so the trunk quietly
  carries a non-conforming subject and nobody can attribute it. That matters because the two
  protections are not symmetric: the merged-PR scan at `asf/evidence/evidence.py:983` does check
  the lane branch prefix (`lane_kind`), but the trunk-commit scan at `:972` has no such escape —
  it skips on `DOC_LANE_SUBJECT.match(subject)` **or** `docs_only(paths, dirs)` only. A document
  lane that touched one path outside `specs_dir`/`plans_dir`/`reviews_dir`, merged by a `gh` too
  old for `--subject`, is back at the bug this card names. The trade against round 1's I3 (a
  silent stall) is the right one and the docstring at `:1318-1323` is honest about the paths
  argument; one `lane.out(f'{b}: merged without --subject — this gh does not know the flag')`
  before the retry would make the degrade visible rather than inferred.
- **I3 — `asf/harvest/lane.py:1297`: one of the four alternatives in `SUBJECT_UNKNOWN_RE` is
  dead.** `flag provided but not defined` is Go's stdlib `flag` package, which prints the flag
  single-dashed (`flag provided but not defined: -subject`), while `_rejects_subject` (`:1301`)
  additionally requires the literal `'--subject'` in the same text. `gh` is cobra/pflag and says
  `unknown flag: --subject` — which is what `tests/test_harvest.py:1613` feeds it and what makes
  the test green — so nothing is wrong today; the alternative simply can never fire alongside the
  conjunct. Either drop it or relax the conjunct to `'subject' in err`.
- **I4 — `tests/test_dry_run.py:76` asserts byte-equality over a line carrying a wall clock, and
  it is red under load at every commit.** `asf/harvest/harvest.py:746` prints
  `gate: {count} modules, {time.monotonic() - started:.0f}s, {verdict}`; the module count is
  already redacted to `?`, the seconds are not, and two dry runs a second apart on a loaded host
  round to `2s` and `1s`. It cost this round a re-run and a full baseline. Not this branch's —
  the file is untouched — and the baseline proves it: `python3 tools/run_tests.py` at
  `origin/main` (`dcd27ad`, a detached worktree, since removed) gave
  `Ran 2635 tests in 1429.036s (90 module(s), 8 at a time)` / `FAILED (errors=5, failures=35,
  skipped=14)` / `red: test_doctor, test_install, test_sample_product, test_gitfixture,
  test_dry_run, test_e2e_lane` — the branch's red is a strict subset of the trunk's, and this
  branch turns 40 failures into 0. Worth its own Bug: normalise the duration the way the module
  count already is.
