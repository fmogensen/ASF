## C list

- **C1 — `asf/groom/groom.py:656-657`: the over-budget question's `why` text does not match
  §2.7's literal wording.** The spec (`docs/specs/f-0092.md:402-406`) and the plan (Step 3, "The
  line's `why` is §2.7's") both give the fenced example `9/3 sessions, $13.53/$10 over budget
  (product default): raise it (...)` — measures first, `over budget (<whose>)` second, a colon
  before the answers. The code builds `f"over budget ({whose}): {measures} — raise it (...)"`,
  producing `over budget (product default): 9/3 sessions, $13.53/$10 — raise it (...)` instead —
  reordered, and with an em dash where the spec has a colon. None of the new tests catch this
  because they use `assertIn` on the pieces rather than asserting the whole line, and
  `OverBudgetAnswerTests.write_prev` constructs its own fixture text matching the code's (wrong)
  order rather than the spec's. Fix: build `why` as
  `f"{measures} over budget ({whose}): raise it (...)"` so the rendered line matches the spec's
  fenced example exactly, and add one test asserting the full line text (not just substrings) so
  a future reorder is caught.

- **C2 — `tests/test_groom.py:534` (`OverBudgetAnswerTests`): the plan's named Acceptance test
  class does not cover Step 8.** The plan's Files section names only `OverBudgetQuestionTests`
  for T6, and its Acceptance fence is `python3 -m unittest -v
  tests.test_groom.OverBudgetQuestionTests` — the command that is meant to prove this Task's
  work. Half of Step 8's required sentences (the `budget <n>`/`budget <n> $<usd>` write
  behaviour, idempotency, `no:` closing the card, `budget soon` being skipped, and the
  adjudicator-attributed `auto` path) live instead in a second class, `OverBudgetAnswerTests`,
  that the plan never names and that the plan's own Acceptance command does not run. Running the
  Acceptance command exactly as the plan gives it proves only the question-rendering half of Step
  8, not the answer-application half. Fix: either fold `OverBudgetAnswerTests`'s methods into
  `OverBudgetQuestionTests` as the plan's Files section specifies, or, if the split is kept, get
  the plan amended to name both classes and update its Acceptance fence to run both — a plan's
  Acceptance command should prove the whole Task it is attached to.
