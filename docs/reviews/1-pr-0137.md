## C (blocking)

- **`asf/feeder/rows.py:853` — a Task lead whose Feature is not in the index crashes the whole
  feeder.** `feature = _task_feature(items, lead) if slice_ else None` (rows.py:852) returns `None`
  when the parent chain does not reach a Feature in `items`, and `in_build_stage(None)` raises:
  `in_build_stage` guards only its first use (`is_open(feature or {})`, rows.py:1450) and then
  dereferences the unguarded original on the same line (`feature.get('type')`). Line 853 is the
  only one of the four `in_build_stage` call sites that can pass `None` — the other three
  (rows.py:1390, 1487, 1538) pass a Feature off `ix.of_type` or an `or {}` fallback.

  This is reachable, not theoretical: `asf/views/index_reader.py:23` drops `removed:` cards from the
  index (`items = {k: v for k, v in raw['items'].items() if not v.get('removed')}`), while the
  `delivers:`/`delivered_by:` fields the slice pass wrote stay on the Task cards — nothing unwrites
  them. So a Feature retired by a reshape after its Tasks were cut into a delivery leaves Task
  leads whose Feature the index no longer has. Reproduced against the tree at HEAD:

  ```
  items = {'T-0001': {...'parent':'F-0001', 'delivers':['T-0001','T-0002']},
           'T-0002': {...'parent':'F-0001', 'delivered_by':'T-0001'}}   # no F-0001
  rows.candidates({'items': items}, product(), [])
  → AttributeError: 'NoneType' object has no attribute 'get'
    rows.py:1367 candidates → rows.py:853 delivery_rows → rows.py:1450 in_build_stage
  ```

  `candidates` is the whole feeder, so NEXT yields nothing for that product until a human hand-edits
  the record — every lane, not just the delivery.

  Fix: make the guard cover the whole expression, at rows.py:1450 —

  ```python
  def in_build_stage(feature):
      feature = feature or {}
      return (is_open(feature) and feature.get('type') == 'feature'
              and (feature.get('stage') or '').split(' ')[0] in BUILD_STAGES)
  ```

  Note what that alone buys: `in_build_stage({})` is `False`, so rows.py:853 `continue`s and the
  orphaned delivery gets no row — while `task_rows`' `delivered(…)` (rows.py:1043) still reads the
  lead as speaking for the members, so those Tasks go *silent* instead of crashing. Silent beats
  crashed, but the second half of the fix belongs with it: when `slice_` is true and
  `_task_feature` found no Feature, fall back to the F-0102 path (`slice_ = False`, so
  `code_stage` is decided by the lead's own `stage`) rather than dropping the delivery, or have
  `delivered()` return `False` for a lead whose Feature is gone so the members return to their own
  lane. Either keeps the Tasks buildable.

- **`asf/record/slice.py:171` — `started_tasks` counts a *retired* Task as started, and the
  delivery then waits on it for ever.** The module is consistent everywhere else that a card with
  `removed:` **or** `moved_to:` is retired — `free_tasks` (slice.py:153) and `deliverable_features`
  (slice.py:204) both check both, matching `asf/record/core.py:252-255`
  (`is_retired(meta)`: "A card with `removed:` or `moved_to:`: no stage, no Tasks, no session"). Line
  171 checks `m.get('removed')` only and omits `m.get('moved_to')`.

  Consequence: a Task moved away by a reshape (`moved_to:` set, state past `New`, a PR in its
  evidence so `idle()` does not exclude it) lands in `started`, so `deliveries` adds it to the
  lead's `after:` at slice.py:230-233. `hold_unlanded` then holds the delivery on it — and it can
  never clear, because `absorbers` (rows.py:377-386) resolves only `merged:` ids, not `moved_to:`,
  so the moved card is never read as landed and never read as absorbed. Reproduced against HEAD:

  ```
  # T-0001: state Active, moved_to T-0099, evidence names PR #11
  slice.free_tasks(metas, 'F-0001')     → ['T-0002', 'T-0003']
  slice.started_tasks(metas, 'F-0001')  → ['T-0001']        # retired, yet "started"

  # and through the feeder, with the after: that write produces:
  DELIVERY → CODE T-0002 | WAITS ON T-0001 | after: T-0001 has not landed
  DELIVERY → CODE T-0003 | WAITS ON T-0001 | after: T-0001 has not landed
  ```

  The delivery is deadlocked: no session ever launches, and no groom pass clears it.

  Fix: slice.py:171 — make it match its two siblings in the same file:

  ```python
  if m.get('type') != 'task' or m.get('removed') or m.get('moved_to'):
  ```

  Worth an acceptance test beside `MigrationTests` (test_feature_delivery.py:203): a half-built
  Feature one of whose Tasks was moved away does not gain an `after:` on it.

## I (non-blocking)

- **`asf/record/slice.py:39` — the `==` marker is false.** `BIG = 10 ** 9  # ==
  asf.views.index_reader.BIG`, but `asf/views/index_reader.py:15` is `BIG = 10 ** 6`. No behaviour
  differs (`_rank` uses it only as a sort sentinel above every real `rank:`), but this module leans
  on `==` comments as the mechanism that keeps its four mirrored constants honest — `DONE_STATES`
  (slice.py:37) and `BUILD_STAGES` (:38) both do check out against rows.py:133 and :147, and
  `PR_RE` (:135) against rows.py:161. Make it `10 ** 6`, or drop the claim.
- **`asf/record/slice.py:138` — `idle()` claims `== asf.feeder.rows.idle_branch`, and is not.**
  `rows.idle_branch` (rows.py:500) tests `type == 'task'`, `state == 'Active'`, `not blocked`, no PR;
  `slice.idle` tests `state == 'Active'`, `id not in busy`, no PR — no type check, no `blocked`
  check. For `free_tasks` the difference is absorbed (it filters `blocked` and type itself), but
  `started_tasks` (:177) uses `idle()` to *exclude*, so a **blocked** Active Task with no PR reads
  as idle there and is neither free nor started — invisible to the pass, and a migrated delivery
  gains no `after:` on it. Either state the delta in the docstring or give `idle()` the same
  `not meta.get('blocked')` clause and let `started_tasks` see it.
- **`asf/harvest/lane.py:1347` — `members_named` runs twice per held delivery branch.**
  `incomplete_refusal` already computed `(named, missing)` at lane.py:809 and threw `named`/`missing`
  away; line 1347 recomputes it for `f['incomplete']`. Each call is a `git log` subprocess
  (`_subjects`, lane.py:398-400). Have `incomplete_refusal` return the missing ids alongside the
  refusal, or hoist the one `members_named` call to the caller and pass the result in.
- **`asf/feeder/rows.py:660` — an `incomplete` hold escalates to adjudicate.** `INCOMPLETE` is not
  in `MECHANICAL` (lifecycle.py:1810, `(NAMING, COPIES)`), and the `same >= CORRECTION_ROUNDS`
  arm at rows.py:646 is tested *before* the new `elif` at rows.py:660 — so a delivery held three times on
  the same missing ids becomes `STALEMATE → ADJUDICATE` with the `adjudicate` brief. A run cap or a
  dead pid is a mechanical fact, not a dispute, and there is nothing for an adjudicator to rule on.
  Progress changes the finding and resets the count, so this only fires on three consecutive
  zero-progress runs — which is arguably the right place to stop and think, but it is worth being a
  deliberate choice with a test rather than a fall-through of arm order.
- **`asf/budget.py:76` — `source != 'item'` drops the multiplier further than intended.** A card
  that sets only `budget_usd` marks `source = 'item'`, so `sessions` — which came from the
  conventions, not the card — also loses its `× members`. Gate each on whether the card set *that*
  field rather than on `source`.
- **`tests/test_feature_delivery.py:272` — the tick-wiring test asserts on source text.**
  `source = open(tick_mod.__file__, encoding='utf-8').read()` then greps it, rather than running
  `run_step0` and observing that the pass did or did not write. It will pass against a
  syntactically-present but unreachable call, and it is the only cover for the description's "Runs
  each tick in the record step after plan-order". It also leaks the handle — the run emits
  `ResourceWarning: unclosed file …/asf/tick/tick.py`. Use a `with open(...)` at minimum; better,
  drive `run_step0` with the convention on and off and assert on `delivers:` in the record.
- **`tests/test_lane.py:866` — the restamp does the wrong replacement first.** Line 866 replaces the
  *first* `"started": "2026-09-21T00:00:00Z"` (the crashed run's own launch line), then :869
  rpartitions the already-modified text and replaces the last one too, so both records get
  restamped. The comment on :867-868 says the intent is "the last launch line is the answer's" —
  which is what :869 alone does. Drop the `.replace(…, 1)` on :866.
