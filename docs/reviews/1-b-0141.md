## C

**C1 — `asf/upgrade.py:205` (`held`), read at `asf/doctor.py:652` and `asf/views/status.py:300`:
`held()` takes no product, so the marker's *owner* reads "waiting on upgrade …" in its own
SCHEDULER and Cron rows — and the owner is the one product whose ticks are still running.**

This is the normal, intended state of the fix, not an edge: `waiting()` returns False for the
owner by design (`asf/upgrade.py:230`, "The owner's ticks go on — the owner drains and retries the
upgrade at its start"), and both new call sites are per-product (`scheduler_rows(cfg, product)`,
`cron_cell(cfg, product)`) yet ask a question that has no product in it. Reproduced against a
temp `ASF_HOME` with the incident's own shape — product `alpha` owns a fresh marker:

```
held():            waiting on upgrade to f5aa236 since 07:04 (owner alpha)
waiting('alpha'):  False
waiting('beta'):   True   (tick: waiting — upgrade to f5aa236 pending)
```

So `asf doctor --product alpha` leads its SCHEDULER section with YELLOW `upgrade  waiting on
upgrade to f5aa236 since 07:04 (owner alpha)` and `asf status` for `alpha` prefixes its Cron row
with the same sentence, while `alpha` is precisely the product that is ticking. The row's own
claim is false for the product it is a row about, which is the inverse of the defect the card
asks to fix and lands in the same diagnostic. `held`'s docstring already states the correct
contract — "the pending marker while it still holds **the other products'** ticks" — the code
just does not honour it.

Fix: give `held` the product, and return `None` for the owner.

```python
def held(product_name=None, now=None):
    data = read_pending()
    if data is None:
        return None
    if product_name is not None and data.get('owner') == product_name:
        return None  # the owner's own ticks are not the ones parked (upgrade.waiting)
    ...
```

then `upgrade.held(product.name)` at `asf/doctor.py:652` and `asf/views/status.py:300`. If the
owner's row should still say something, it must say the true thing — that this product owns the
pending upgrade and installs it at its next tick, and that the *other* products' ticks wait —
which is a different sentence and needs its own test. Either way, add a test asserting the owner
product's `scheduler_rows` and `cron_cell` do not claim the owner is waiting;
`tests/test_doctor.py:917` and `tests/test_views.py:228` both currently assert the label on a
product (`sample`, `p`) that is not the marker's owner, which is why neither caught this.

**C2 — `asf/upgrade.py:205-216`: `held()` reports two markers that `pending()` deliberately
drops, so the views announce a wait no tick is honouring.**

`held()` checks only `at` and the TTL; `pending()` (`asf/upgrade.py:172-202`) drops three more
kinds. Two of those diverge and produce a false "waiting" row. Reproduced against a temp
`ASF_HOME`:

```
probe1  operator marker, pid 999999 dead:  held(): True   pending(): False
        label: waiting on upgrade to aaaaaaa since 06:49 (owner operator)
probe2  marker dated 1 h in the future:    held(): True   pending(): False
```

probe1 is the case `pending()`'s dead-pid branch (`asf/upgrade.py:181-185`, "killed, it never
cleared its mark") exists for: an operator's `asf upgrade --wait` that dies without running its
`BaseException` cleanup (`asf/upgrade.py:510-513`) — SIGKILL, a crash, a reboot inside the TTL —
leaves a marker every tick correctly ignores, while the doctor now reports it. probe2 is
`pending()`'s `age < -60` branch (`:194`): a clock step leaves a future `at`, `pending()` clears
it, `held()` reports it forever.

Fix: reuse the same two guards, both of which are free (no git, no network, so `held()` stays a
view-cheap read):

```python
    pid = data.get('pid')
    if data.get('owner') is None and isinstance(pid, int) and pid > 0 and not _alive(pid):
        return None
    at = data.get('at')
    if not isinstance(at, (int, float)):
        return None
    age = (now or time.time()) - at
    if age > PENDING_TTL_S or age < -60:
        return None
    return data
```

The third divergence — `pending()`'s `_installed(data['sha'], …)` check (`:190`) — needs a `git
merge-base` call and does not belong in a view; leave it, but say so in the docstring so the next
reader does not take `held()` for `pending()` minus the writes.

**I2 — `asf/upgrade.py:492`: `refuses()` spends a `gh run list` call that `_install` then spends
again, and the tick still drains up to `drain_wait_s` for a target it already knows is refused.**
On the happy path (green head, floor clears) `ci_red` now runs twice per upgrade — once at `:492`,
once at `:539` — each a network call with `timeout=30`. Worse, when the refusal *does* fire, the
code prints "the other ticks run" and then falls straight into `drain(others, wait_s, …)` at
`:509` with `wait_s = upgrade.drain_wait_s()` (180 s by default, `asf/tick/tick.py:396`), burning
up to three minutes of every owner tick polling for a gap in which to run an install that
`_install` will refuse at `:539-541` anyway. Since the refusal is already known at `:493`, that
branch could return `DEFERRED` immediately, which would also make the doubled `ci_red` the only
remaining cost. I would restructure it; it wastes time rather than parking anyone, so not
blocking.

**I3 — `asf/upgrade.py:426`: `refuses(url, None)` reports "main's head is unreadable from <url>"
for a caller that merely passed no ref, and the refusal branch then clears that caller's own
valid marker.** With `owner` set and `ref=None`, `install()` never resolves the head (`:490`
resolves it only when `not owner`), so `refuses` sees a falsy ref and blames the remote; `:497`
then matches `wait.get('owner') == owner` and deletes a marker that was perfectly good. Not
reachable from the factory today — `asf/drift.py:157` only calls the upgrade when `is_behind`, and
always with a resolved `d.head` — and the old code also wrote no marker in this shape, so this is
a wrong message plus a new destructive clear on an unreachable path rather than a live bug. I
would resolve the head first (`ref = ref or remote_head(url, run)`, unconditionally) so the
distinction is real before it is reported.

**I4 — the card's narrative and the commit body disagree on the old TTL, and neither matches the
code.** The card says "the pending expiry becomes 10 minutes, not 30" and the incident line says
the marker "held the whole factory until its 30-minute expiry"; the commit body says "not 20"; the
code at `origin/main` was `PENDING_TTL_S = 20 * 60`. 10 minutes is what was asked for and 10
minutes is what landed, so nothing in the diff is wrong — but the card's 30 should be corrected in
the record, since the incident's own 21:44–22:10Z window is 26 minutes and cannot have been one
20-minute expiry either. Worth a line on the card; no code change.
