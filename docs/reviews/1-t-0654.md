## C — blocking

**C1 — `window_usd` resolution has four priority levels, not the spec's six; a learned per-kind value outranks a configured pool-wide one.**

`docs/specs/f-0138.md` §2: "`window_usd` resolution, per `(provider, window)`, first hit wins: the
operator's `quota_guards.window_usd[provider][window]`; **that kind's `five_h`** × the ratio; **the
pool-wide `quota_guards.five_h_usd`** × the ratio; **the learned per-kind `five_h`** × the ratio;
**the learned pool-wide `five_h`** × the ratio; `None`." Six distinct sources, in order:
configured-per-kind, configured-pool-wide, learned-per-kind, learned-pool-wide. Every configured
value must outrank every learned one.

`asf/workers/headroom.py:528-534` builds `window_usd` by seeding it from
`five_h_usd_by_provider` (learned) and then `.update()`-ing the operator's `quota_guards.window_usd`
on top, merging configured and learned into one dict keyed by provider. `_window_usd`
(`:254-268`) then checks `known.get('five_h')` — which may be either source — *before*
`self.five_h_usd`, the pool-wide figure. So when a provider kind has no explicit
`window_usd[<kind>]` entry but has learned samples, and the operator *has* set a pool-wide
`quota_guards.five_h_usd`, the learned per-kind figure wins — the opposite of the spec's order.

Reproduced directly:

```python
cfg = {'quota_guards': {'five_h_usd': 1000.0}}   # operator sets a pool-wide budget, no window_usd
# plan-small has 3 learned 5h intervals worth $2/run, giving a learned five_h of 50.0
table = headroom.table_from_config(cfg)   # with history_runs/read_samples mocked to that data
table.share('spec', 'Opus', 'plan-small', 'five_h')   # -> 4  (2.0*100/50.0, the LEARNED figure)
# spec order says the configured pool-wide 1000.0 should price it: 2.0*100/1000.0 -> 0.2
```

An operator who sets one pool-wide dollar figure expects it to hold for every kind that names no
override; instead a kind with enough traffic to be learned silently drops its price by 5× here,
with no config change and no visible cause. This is exactly the primitive Task 2 will consume
unmodified (§3's `share(...)` calls), so the mis-ordering is live from the moment placement starts
reading it.

**Fix** — stop blending configured and learned data into one `window_usd[provider]` dict.
In `table_from_config` (`:524-536`), keep the operator's `g.get('window_usd')` as its own dict
(no seeding from `five_h_usd_by_provider`), and pass the learned per-kind table through a second,
separate keyword (e.g. `learned_window_usd={provider: five_h for provider, five_h in
five_h_usd_by_provider(samples, runs).items()}`). In `CostTable.__init__`, store both; in
`_window_usd`, check in this order: `configured[provider][window]` →
`configured[provider].get('five_h') * ratio` → `self.configured_five_h_usd * ratio` (the plain
`quota_guards.five_h_usd`, not blended with the samples fallback) → `learned_window_usd[provider]
* ratio` → `self.five_h_usd * ratio` (today's already-learned-or-configured pool-wide fallback,
kept for the existing pool-wide back-compat path) → `None`.
