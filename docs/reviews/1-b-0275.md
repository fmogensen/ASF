## C list

### C1 — `asf/harvest/lane.py:2553-2558`: the green guard reads only what was written down, and nothing writes it for a naming-held branch

`reword_held`'s second condition answers "is there a green we remembered for this very head", not
the card's "any green required check on its head". Because neither writer of that memory can be
reached while a naming correction is pending (the evidence row above traces both), the ordinary
sequence is:

* pass 1 — the run is in flight: `ci_flight.verdict` defers (`lane.py:2560`), the head stands;
* pass 2 — that same run has completed, green on every required check. Nothing is in flight any
  more, there is no land request, and nothing was ever written down, so `reword_held` answers
  `''` and the reword force-pushes the green head away. The carry cannot give it back either:
  the old head's green was never remembered.

Which is the card's own signature with the land request removed — and the F-0203 guard makes it
*likelier*, not less, by holding the reword back until exactly the pass on which CI has just gone
green.

Reproduced at this head in a scratch module `test_c1_demo.py` (`Ran 9 tests … OK` — the new
case passes, i.e. the reword happens):

```python
class C1(RewordDefers):
    def test_a_run_that_completes_green_is_reworded_away_on_the_next_pass(self):
        old = self.push_commits([('tidy up', {'a.txt': 'a\n'})])
        self.held_for_naming(old)
        with mock.patch.object(ci_flight, 'run_in_flight',
                               return_value={'id': 4242, 'status': 'in_progress'}):
            self.one_pass()
        self.assertEqual(self.tip(), old)            # pass 1: deferred, in flight
        self.assertIsNone(tree_green.green_on(self.state_dir, self.PR, old))
        lines = self.one_pass()                      # pass 2: the run has completed, green
        self.assertIn(f'reword {self.B}: 1 subjects, trees identical — pushed', lines)
        self.assertNotEqual(self.tip(), old)         # the green head is gone
        self.assertIsNone(tree_green.carried(self.state_dir, self.PR, self.tip(),
                                             tree_green.tree_at(self.origin, self.tip()),
                                             ['gate']))
```

**The fix.** In `reword_held`, when `tree_green.green_on` answers None, ask the host for the
head's own checks — the one `pr_checks` read the gate already makes — and defer when every
required check concluded success, writing it down as the gate does so a later rewrite can carry
it back. In `asf/harvest/lane.py`, after line 2558:

```python

        if not why and number and head and host is not None:
            cls = f.get('class') or landing_class(self.product, f.get('files') or ())
            required, _unknown = host.merge_required(self.state_dir, cls, head)
            if required:
                state, _detail, checks = pr_checks(
                    host.slug, number, required, host.rerun_ids(), head=head,
                    attest_context=attestation.context(self.product))
```

One host read on a path that already makes one (`ci_flight.verdict`, two lines below), and it
closes the net the module's own docstring claims the first half keeps empty
(`asf/tree_green.py:9-19`). `merge_required`, `rerun_ids` and `remember_green` are
`GitHubHost`'s, not `FastForwardHost`'s, hence the `slug` guard. A read that cannot be made
(no PR host, an unreadable answer) must leave `why` as it is — the existing behaviour — not defer.

### C2 — `asf/merge_queue.py:2603-2612`: the carry is granted before the conflicts-with-trunk guard, so a conflicting PR is admitted as green

The carry block sits above the guard at `asf/merge_queue.py:2613`:

```python
        if state == 'pending':
            carry = tree_green.carried(...)
            if carry is not None:
                state, why, earned = 'green', '', True
        if state == 'pending' and not lane.conv.branch_kind(b) and conflicts_with_trunk(lane, n):
```

Setting `state = 'green'` makes that guard unreachable. Its whole premise is that GitHub starts
*no* `pull_request` CI on a PR that conflicts with the trunk — so such a PR's checks read
"(not started)", which is exactly the `pending` the carry now answers. The sequence is ordinary:
a non-factory PR with an `asf land` request goes green and is remembered
(`merge_queue.py:2659-2661`); the trunk moves under it and it now conflicts; its author amends a
message, giving a new head with a byte-identical tree and no checks at all. Before this diff the
queue wrote `red at <head> — conflicts with main — merge or rebase it` and recorded the red; now
it emits the PR into the batch as green and says nothing about the conflict. The pre-existing
"never started" promotion two lines above does *not* do this — `deploy.never_started` returns
`[]` when there are no runs at all (`asf/harvest/deploy.py:559`), so a conflicting PR fell
through to the guard.

Reproduced at this head, with the counterfactual (scratch modules `test_c2_demo.py` and
`test_c2_counter.py` — both pass):

**The fix.** Move the carry below the guard — a pure reorder, no new code. In
`asf/merge_queue.py`, cut lines 2603-2612 (the `if state == 'pending': … carry …` block) and
paste them immediately after the `conflicts_with_trunk` block that now ends at line 2620
(`continue`), so the order reads: never-started promotion → conflicts-with-trunk → carry →
red.
`tests/test_tree_green.py` gains the case: a non-factory land-requested PR, remembered green,
reworded to an identical tree, `conflicts_with_trunk` True → `out == []` and the line names the
conflict.

## I list (not blocking)

**I1 — the carry has no trunk-freshness bound, where every red verdict in the same file has one.**
`asf/merge_queue.py:2628-2637` and `asf/harvest/lane.py:4679-4697` both treat a red judged on a
merge ref from before the trunk moved as *no verdict* (`asf.stale_ref`); `tree_green.carried` will
carry a green for up to `KEEP_S` = 7 days (`asf/tree_green.py:36`) with no reference to the trunk
at all, so a green earned against trunk `S1` can admit a head that has never been tested against
`S2`. The baseline has the same hole for a head that was never reworded (a green is not re-earned
when the trunk moves), and on a queue product the batch ref's own run covers it — so this is not
a regression, but the asymmetry is worth a card, and the `--merge`/`--rebase` landing path
(`check_gate` returning `'ci'`, no batch) does not have the batch run to fall back on.

**I2 — a green carried onto a head is remembered as if that head earned it, so the chain never
ends.** `asf/merge_queue.py:2601` sets `earned = True` on a carry and `2659-2661` then writes the
new head down, which re-arms `KEEP_S` from the carry rather than from the run. The
`required`-superset guard (`tree_green.py:135`) bounds the damage, and the writer's choice is
deliberate (a long reword chain keeps working), but a content tree can hold a green indefinitely
across rewrites it never ran for. Contrast `2602-2607`, where the "never started" promotion
correctly leaves `earned` False — the same care, applied here, would remember the carry under the
*original* `at` instead of now.

**I3 — `tests/test_tree_green.py:20-21` imports two names it should not.** `NamingRepair` is
pulled into this module's namespace, so unittest collects its 5 tests here as well as in
`tests.test_lane` — that is why the module reports `Ran 19 tests` for the 14 it defines, and the
gate runs those 5 twice. `check_run` (line 21) is imported and never used. Fix: `from
tests.test_lane import LaneFixture, sh` and `from tests import test_lane`, then reference
`test_lane.NamingRepair` at lines 29-33; drop `check_run` from line 21.

**I4 — a permanent deferral is reachable, and says nothing about itself.** `reword_held`'s
docstring (`asf/harvest/lane.py:2538-2541`) says the reword "happens on a later pass, once the PR
has landed or its head moved for a reason of its own". For the land-request and in-flight reasons
that holds (the queue lands it; the run completes). For the green reason it need not: a head
remembered green by the queue whose `asf land` request is later withdrawn (`asf land --withdraw`)
keeps a naming refusal that blocks the lane's own landing and a memory that blocks the reword, and
nothing moves the head — so the branch sits for the remaining 7 days of `KEEP_S`, printing one
`reword <b>: deferred — … green on <head>` line a pass and nothing else. Worth either a bound on
how long that reason may defer, or a line that says the branch is stuck and why.

**I5 — the acceptance's "the squash subject is set at merge time instead" holds for a document
lane only.** `squash_subject` returns None for a code lane (`asf/harvest/lane.py:3979-3981`,
"whose subject is the host's to compose"), and a merge-queue member lands under
`merge-queue: #{pr} ({branch} @ {head})` (`asf/merge_queue.py:208`) with its own non-naming
subjects riding along on the trunk. `reword_held`'s docstring is careful to say "a document
lane's" (`lane.py:2539`), so the code is honest; it is the card's parenthetical that over-reaches
for a code branch, and a deferral that ends in a landing means the reword the naming refusal asked
for never happens at all. A question for the record, not this diff.

**I6 — small things.** `asf/tree_green.py:98` rebinds `rows`, already bound at `:93`, as the loop
variable (harmless — the outer `rows` is not read again — but one name for two lists in eight
lines); `:93-94` prunes this PR's rows by `KEEP_S` and then `:98-103` prunes every PR including
this one, so the first filter is redundant. `tree_at` is called with a bare `lane.repo` in
`asf/merge_queue.py:2605` and with `getattr(self.lane, 'repo', None)` in
`asf/harvest/lane.py:4432`/`4445` — two defences for one attribute. `carried_green`
(`lane.py:4425-4434`) replaces `checks` wholesale with its synthetic passes, so
`not_required_red` at `lane.py:4912` can no longer see a non-required red on the carried head and
its informational line is lost. `tests/test_tree_green.py:266`
`test_an_unreadable_file_remembers_nothing` asserts about `load` and `carried`, never about
`remember` — `test_an_unreadable_file_carries_nothing` is what it checks. `Carry` covers neither
`MAX_PER_PR` nor a `save` that raises (`tree_green.py:106-107`), both of which the module takes
trouble over. The writer's report says "`::Carry` (the store's own six)"; `Carry` defines five.
