## C — blocking

- **C1** `asf/env.py:538` (`'x-unmapped': _MAP` added to `PRODUCT_FIELDS`) breaks
  `tests/test_env.py:829-836` `PinnedReader.test_no_product_key_the_pinned_reader_would_refuse`.
  That test's own comment (`tests/test_env.py:830-832`) says exactly what happened: *"A new
  top-level ... key strands a product pinned to PINNED_SHA (its loader refuses it). Put a new
  switch under conventions.flags instead; drop the sha from tools/pinned-readers.txt only once no
  product runs it."* Neither `docs/specs/f-0129.md` nor `docs/plans/f-0129.md` mentions this
  conflict (grepped both, no hits on `pinned`/`PinnedReader` beyond the plan's unrelated
  `pinned together` at line 98), so this Task's own Step 4 lands a key the gate explicitly
  guards against, and ships with the gate red. The coder's own commit message for `8e02ea21d`
  documents finding this and names it "outside this Task's writes: and a coder's authority" —
  that is a `NEEDS OPERATOR`, not a thing to push past. Fix: do not land Step 4 until an operator
  rules on dropping `PINNED_SHA` from `tools/pinned-readers.txt` (an operational fact: whether any
  product still runs that pinned sha) or the design is amended to route `x-unmapped` around the
  pinned-reader guard, per the test's own suggestion (`conventions.flags`).
- **C2** `asf-heartbeat.sh` (repo root, new file) is in the diff against `origin/main` and outside
  `writes: asf/env.py, docs/products.example.yaml, tests/test_env.py`. It is a generic heartbeat
  daemon launcher, not Task 1 work — the factory's WIP auto-commit (`a34278d28`) picked it up from
  the coder's own session scaffolding. Fix: `git rm asf-heartbeat.sh` in a follow-up commit before
  this branch lands.
