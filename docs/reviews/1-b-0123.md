## C list

- `docs/plans/b-0123.md` (missing): there is no plan or spec, so "every Step" and "byte-identical tests" cannot pass on the table above. Fix: add the plan naming the Task ("a regular tick catches up a missed daily once") and its Steps (`_daily_clock_time`/`daily_catch_up_due`/`daily_catch_up_message` in `asf/tick/steps.py:195-227`, the call site in `asf/tick/tick.py:411-417`), and give the Acceptance as the two tests now at `tests/test_tick.py:605-646`.
- `asf/tick/steps.py:226-227`, `daily_catch_up_message`: the card's Description is explicit that "the tick log names the catch-up" with the literal shape `"daily: catching up — 06:00 run failed: <reason>"` — a message that says *why* the 06:00 run didn't succeed. The implementation prints `"daily: catching up — {hour:02d}:{minute:02d} run has not succeeded today"`, which never carries a failure reason at all (there is no code path anywhere in this diff that threads a reason from the failed run's process into the later tick that catches it up). Either the message needs a reason (which requires persisting one from the failed run — e.g. a line in the stamp/lock state read back here), or the plan this item is missing needs to record that the card's literal message was intentionally simplified and why; as written, the log line the card asked for is not the log line this ships.

## I list

- `asf/tick/steps.py:200-204`, `_daily_clock_time`: iterates `clocks:` and returns the first entry whose `steps:` contains `daily` and whose `at:` parses — silently falls through to `None` (no catch-up, ever) if a product's daily clock uses a different key shape (e.g. `every:` instead of `at:`, or `daily` combined with other steps in one clock). Not a bug against today's config shapes, but worth a line in the (still-to-be-written) plan's accepted-costs.
- The card's exact wording ("catches up on the next regular tick after its time, once") is satisfied because `daily_due` flips false the moment the catch-up stamps — but nothing stops a *third* tick later the same day from re-checking `daily_catch_up_due` too; it happens to be safe only because the stamp write is what makes it idempotent, not because the call site guards against a repeat. Worth naming as the actual idempotency mechanism in the plan rather than leaving it implicit.
