## C — must change

1. **`asf/harvest/lane.py:847` — the comment claims a fallback the code does not have.**
   The comment reads `# a guard never stops a landing on its own`, and the commit message
   repeats it as *"A config the guard cannot read holds nothing"*. It does not hold nothing.
   `cfg = {}` falls through to `host.guards_from_config({})`, which returns the **defaults**:

   ```
   cfg={} (the except fallback) -> guards {'load_per_core': 2.0, 'swap_pct': 85}
   judge(load 90/12, swap 87)   -> (True, 'host pressure load 90/cores 12, swap 87%')
   guards actually OFF would be {'load_per_core': None, 'swap_pct': None}
   ```

   Concretely: an operator who has turned the guard off (`host_guards: {load_per_core: 0,
   swap_pct: 0}`) and whose `config.yaml` also carries a malformed `worker_pool.env_passthrough`
   gets `ConfigError` → `cfg = {}` → the default 2.0/85 guards silently back on, and their
   landings held on a loaded host with nothing in the output saying the config was ignored.

   The *behaviour* is the right one — a host-freeze guard should fail to its defaults, not
   fail open — so the fix is the comment, not the code:

   ```python
   except (env.ConfigError, OSError, ValueError):  # unreadable: the default guards, not none
       cfg = {}
   ```

   and strike *"A config the guard cannot read holds nothing"* from the commit message's last
   paragraph (`git commit --amend` before the branch lands, or a follow-up commit saying so).

2. **`tests/test_lane.py:435` — the `how == 'ci'` passthrough is promised and untested.**
   `held_by_host`'s docstring (`asf/harvest/lane.py:840-841`) promises that an entry merging on
   its external CI's checks alone *"runs no suite here, so it goes on"*, and `lane.py:855`
   returns exactly those. Nothing tests it: the one new test has a single FF entry with
   `how == 'gate'`, and `grep` finds no other test naming host pressure in `tests/test_lane.py`.
   A regression to `return []` there would silently hold every external-CI PR under pressure
   and no test would notice. Add a case to `LaneRepo` alongside the new one: a PR entry whose
   `precheck` sets `f['how'] = 'ci'` (the `GitHubHost` fixture the neighbouring PR tests use)
   beside the FF entry, under `ASF_HOST_READING='90 12 87'`, asserting the `ci` branch still
   reaches `merge_prs` while the FF one waits at `lane.HOST_PRESSURE`.
