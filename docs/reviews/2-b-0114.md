## C — blocking

- **C1 — `tests/__init__.py:15`: the twin guard was left behind, so a bare `python3 -m unittest
  tests.<module>` is still red exactly as before the fix.** There are two hermetic guards for the
  suite, and the package's own docstring says so: `tests/test_00_home.py` for `discover -s tests`
  (its line 1), and `tests/__init__.py` for "`discover -t .`" — i.e. for every other entry point,
  since importing any `tests.<module>` imports the package first. Both already drop the operator's
  home (B-0043) and pin `ASF_HOST_READING`. The diff added `hermetic.strip_git_config(os.environ)`
  to the first one only (`tests/test_00_home.py:31`).

  It reproduces now, on this branch, from inside this session:
  `python3 -m unittest tests.test_install` → `FAILED (failures=12)`, at
  `tests/test_install.py:669` (`test_a_foreign_hook_is_not_touched_and_is_one_needs_operator_line`)
  and 11 more, with the diff `- <the operator's home>/.ASF/state/asf/githooks` / `+ .githooks`
  (the home spelled in full in the run's output, redacted here as round 1 redacted it) — the same
  failure text, and the same module, that round 1's I4 quoted. `tools/run_tests.py` is green only
  because it covers this twice over (`:85 child_env` builds each process's environment through
  `hermetic.build`, and `:40 HOME_MODULE` runs `test_00_home` first in each), and
  `python3 -m unittest -v tests.test_sample_product` — the one CI step that names a module
  directly — passes only because its fixtures happen to go through `hermetic.build`.

  The fix is one import and one call, and it must go at the **bottom** of the file, after the
  `ASF_HOME` lines: `asf.env` reads `ASF_HOME` at import time, which is why
  `test_00_home.hermetic_home` also imports `asf` only after setting it. Append to
  `tests/__init__.py`:

  ```python
  # B-0114: a session that runs the suite carries its own core.hooksPath in GIT_CONFIG_*, and git
  # applies it to every repo — a fixture repo this suite creates would report the caller's hooks.
  from asf import hermetic  # after ASF_HOME above: asf.env reads it at import

  hermetic.strip_git_config(os.environ)
  ```

  Proof that this is the whole fix: `probe-c1.py`, which does exactly those two lines before
  loading the module, turns the same 64 tests from `FAILED (failures=12)` to `OK`.

## I — would change, will not block

- **I1 — `asf/hermetic.py:15` is 138 characters.** The edit rewrapped lines 12-14 and left the
  tail of the old line 15 unwrapped, so `Then what the caller asks for: …PYTHONPATH``` now runs
  off the edge. `grep -rn ".\{111,\}"` over the package finds this line and one other
  (`asf/evidence/evidence.py:486`) in the whole tree, so it is an outlier, not the house style.
  Rewrap at the ~100 columns the rest of the module keeps.
- **I2 — the hermetic fix is a second card's work sitting on a doc-lane card.** `asf/hermetic.py`
  is production code for a defect whose symptom, cause and test are entirely unrelated to a spec/
  plan PR's landing; the only thing joining them is that B-0114's gate could not run without it.
  Round 1 said it "belongs to a card of its own". Landing it here means the record has no Bug for
  a hermeticity leak that cost two review rounds, and `git log asf/hermetic.py` will name B-0114
  for it forever. The `NEEDS OPERATOR` line below asks for the carve-out; the code itself is right
  and should not be reverted to get it.
- **I3 — the two guards are now three-line twins that must agree.** `tests/__init__.py:8-15` and
  `tests/test_00_home.hermetic_home` (`:15-33`) do the same three things in the same order, and
  C1 exists because one of them was edited and the other was not. Once C1 lands, having
  `hermetic_home` call the package's guard — or both call one `tests/hermetic.py` helper — removes
  the class of miss rather than this instance of it.
- **I4 — `core.hooksPath` has a third channel, and `strip_git_config` covers one.** git also
  hands a child `GIT_CONFIG_PARAMETERS` (what `git -c` exports to its own descendants) and honours
  `GIT_CONFIG_GLOBAL`. Probed here: `git -c core.hooksPath=/callers/githooks -c alias.probe=!…` in
  a fresh repo gives the alias's child
  `GIT_CONFIG_PARAMETERS='core.hooksPath'='/callers/githooks' …`, and a git run from inside that
  child resolves `/callers/githooks` as its hooks dir — `GIT_CONFIG_*` never appearing. I found no
  live path to it (`asf/snapshot.py:172`, the one `git -c core.hooksPath=` in the tree, points at
  `os.devnull`, so it spawns no hook), which is why this is an I and not a C. But
  `GIT_CONFIG_NOT_INHERITED` reads as "the keys a child never inherits", and for one of the two
  other channels it is not true. A line in the docstring naming the channel it covers would keep
  the next reader honest.
- **I5 — gate mode still hands a product's test command the operator's code-host credential.**
  The same `GIT_CONFIG_*` run this session carries holds `credential.https://github.com.helper`
  (a helper script that echoes `GH_TOKEN`; the value quoted nowhere in this review), and `GH_TOKEN`
  itself is in the environment — both reach a gate, because `mode='gate'` is documented to start
  from the whole base (`asf/hermetic.py:20-21`). That is a standing design choice, not this diff's
  regression. It is worth naming now only because the diff creates the exact mechanism the
  decision would use: one more entry in `GIT_CONFIG_NOT_INHERITED` strips the helper, and a gate
  that must fetch would then need it passed in deliberately.
- **I6 — `strip_git_config` lowercases the whole key, which is right for `core.hooksPath` and
  wrong for the next entry.** The docstring says "the way git compares a section and a key" —
  accurate, but git compares a *subsection* case-sensitively, so a future
  `credential.https://GitHub.com.helper` in the list would drop a key git considers different.
  `core.hooksPath` has no subsection, so nothing is wrong today; a half-line in the docstring
  ("no subsection here — those compare case-sensitively") fences it.
- **I7 — `GIT_CONFIG_VAR_RE` (`:46`) is the third copy of that regex.** `asf/redact.py:86`
  already carries `^GIT_CONFIG_(KEY|VALUE)_\d+$|^GIT_CONFIG_COUNT$` for B-0081, and
  `tools/smoke_isolated_session.sh:178` matches the prefix. One of them moving is a silent drift.
- **I8 — `strip_git_config` leaves `GIT_CONFIG_COUNT=0` when the base had a count and every pair
  was dropped.** `had` (`:90`) is there so a base with no git config gains none, but the mirror
  case — a base whose only pair was `core.hooksPath` — keeps a count of zero rather than no count.
  git reads both the same, and `build` overwrites it one line later (`:147`); the only caller that
  sees it is `tests/__init__.py`/`hermetic_home` on `os.environ`. Harmless, but the comment at
  `:93` reads as if both cases were handled the same way.

## Missed in round 1

- **M1 — round 1 blamed the host for a leak its own evidence named.** I4 concluded "the leak is

  red, which is where the real defect was.

  They were I, so this is not a demand: the merge-queue path still names no subject (`:1495-1497`),

## What was checked and held

- The suite's green is not a quiet host: it ran twice, once with this session's environment intact
  (the leaking pair present) and once under `env -i` with an operator-like home and
  `init.defaultBranch master`. Both `OK (skipped=14)`, 2715 tests, 89 modules.
- `strip_git_config` rewrites contiguously, which is the thing that would silently lose config if
  it were wrong: `tests/test_hermetic.py:75` pins `KEY_0`/`KEY_1` and `GIT_CONFIG_COUNT == '2'`
  with no `GIT_CONFIG_KEY_2` left behind, and `_git_config` (`:98`) re-derives `n` from the count
  that `strip_git_config` has just popped, so the append cannot collide with a stale index.
- The session spawner's own hook dir survives: `build` strips before it appends (`:146` then
  `:147`), so `asf/workers/runtime.py:367`'s `git_config=[('core.hooksPath', job.hooks_dir)]`
  lands on top — pinned by `tests/test_hermetic.py:67`, and by `test_session_identity` and
  `test_auth_env` (both green), which assert the pairs a session is given.
- `mode='worker'` needs no strip and gets one harmlessly: `worker_base` (`:114`) is an allow-list
  that keeps no `GIT_CONFIG_*` at all unless `worker_pool.env_passthrough` names one.
- The hook shim is unaffected: `asf/workers/githooks.py:43` finds a repo's own hooks with
  `env -u GIT_CONFIG_COUNT git config --get core.hooksPath`, which masks the pairs by dropping the
  count — it never depended on inheriting the key, and it runs inside the session, whose own
  `core.hooksPath` is still set.
- `git_config_pairs` cannot raise on a hostile environment: a non-numeric or negative
  `GIT_CONFIG_COUNT` reads as no pairs (`:71-76`), and a missing `KEY_n` is skipped rather than
  indexed — so `build` degrades to "no inherited config" instead of failing a gate.
