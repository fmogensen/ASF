## C list

### C1 — a git read that did not answer is read as "the branch proves nothing"

`asf/harvest/lane.py:1144-1145` (inside `proves_refusal`). Both reads take
`gitops.git(...).stdout` and never look at `.ok`. `gitops.git` (`asf/gitops.py:41-60`) returns
the shared `Result` dataclass, whose own docstring is explicit: `ok` false means the answer is
**Unknown**, with `stdout` defaulting to `''` — not "nothing there." Confirmed directly:

```
$ python3 -I probe.py          # gitops.git patched to return Result(False, reason='timeout')
kind: proves
no claim
add a trailer to one of your commits naming the line your tests prove, e.g.
  Proves: <S-id> line <n> — <the test path that proves it>
then push; the factory publishes the rewritten branch
```

A timed-out or transiently-failing `git log`/`git ls-tree` therefore reads as "this Task proves
nothing," refusing a branch whose commits may carry a perfectly good trailer — a correction round
bought for a network hiccup, with `hold_with_correction`'s round counter bumped toward
adjudication for it. The `ls-tree` half fails the opposite way: a non-zero `ls-tree` gives
`tree == []`, so every *valid* claim collects `no such test: <raw>` and the correction tells the
coder its test path is not on the branch when it is.

**The fix.** Capture both `Result`s and refuse nothing when either is Unknown:

```python
log = gitops.git(['log', ...], repo)
tree_r = gitops.git(['ls-tree', '-r', '--name-only', f'origin/{branch}'], repo)
if not (log.ok and tree_r.ok):
    return None   # a git read that did not answer is not evidence of a missing trailer
claims, tree = proves.parse(log.stdout), tree_r.stdout.split()
```

(`proves.claims_on_branch`'s injected callable returns text, not a `Result`, so `proves_refusal`
needs to read the range itself — the same single `git log --format=%B` over
`origin/<trunk>..origin/<branch>` `claims_on_branch` already runs.) Add a `ProvesRefusalTests`
case patching `lane.gitops.git` to an Unknown `Result` and asserting `assertIsNone`.

### C2 — the shipped-script test asserts a literal against itself

### C3 — `asf proves check` with no resolvable product exits 0 having checked nothing

`asf/rules/story_proof.py:81-83`: `product = _product(args)`; `ev = evidence.load(product=product)
if product else {}`. `_product` (`:70-77`) swallows `env.ConfigError` and returns `None` when no
`--product` is given and no default product is configured. With `ev == {}`, `violations`' every
`(ids_ev.get(iid) or {}).get('commit')` is falsy, so `lines == []` and `cmd_check` prints nothing
and returns 0 — **a green rule that read no evidence at all**. `cmd_show` already fails loud for
the same gap (`:109-112`, rc 2, "no product repo in hand"); `cmd_check` does not. The plan's own
P13 is explicit about the direction a rule should fail in: *"`${ASF_PRODUCT:?}` makes bash exit
non-zero with nothing on stdout, which `run_check` reports as a violation line — fail-loud, and
the right way round for a rule"* (`docs/plans/f-0040.md:38`) — that covers the shipped script's
own env-var guard, but `asf proves check` reached directly (no `--product`, no configured
default — any session running `asf proves check` ad hoc, not through the shipped script) has no
equivalent guard at all.

**The fix**, at `asf/rules/story_proof.py:81-83`:

```python
product = _product(args)
if not product:
    print('proves check: no product in hand — pass --product', file=sys.stderr)
    return 2
ev = evidence.load(product=product)
```

with a `StoryProofCmdTests` case asserting rc 2 and empty stdout when `_product` returns `None`.

### C4 — a claim whose commit or PR names no Task id is counted against no Task

`asf/rules/story_proof.py:52-53`: `[c for c in proven.get(sid) or [] if c.get('task') == iid]`.
`landed_proves` (`asf/evidence/evidence.py:1577, 1588`) sets each entry's `task` to the first
`T-` id its naming ids carry, falling back to `None` when there is none — and a Task landed
inside a delivery pull request whose title and branch name only the Feature (this repo's own
F-0102 cross-item delivery shape) stores its claim with `task: None`, while
`ev['ids'][<T-id>]['commit']` is still set from the member commit's own subject. Confirmed
directly: a claim with `task: None` and `sha` equal to the Task's own landing commit still
reports as

```
['task landed proving nothing T-1 (S-1) since 2026-09-20']
```

— a false violation for a Task whose claim is right there in the evidence, which `asf file-bugs`
turns into a Bug through the path every other rule violation already takes
(`asf/tick/file_bugs.py:145, 227`, over `violations`' own lines).

**The fix.** Fall back to the Task's own landing commit when the claim names no Task — a claim
on the same sha as the Task's landing is that Task's:

```python
landed_sha = (ids_ev.get(iid) or {}).get('commit')
task_claims = {sid: [c for c in proven.get(sid) or []
                     if c.get('task') == iid
                     or (not c.get('task') and c.get('sha') == landed_sha)]
               for sid in stories}
```

with a `StoryProofViolationsTests` case: a claim carrying `task: None` and the Task's own
`commit` sha is **not** a violation.
