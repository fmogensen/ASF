## C list

- C1 — `asf/workers/lifecycle.py:417-422` (`settled`): marks a correction settled off `r.get('ended')`
  alone, not `finished(r)` (this file's own `ended and end_reason == FINISHED` helper at
  `asf/workers/lifecycle.py:345-348`, already used for exactly this purpose by `landed()` and
  elsewhere). A crashed, stopped, or quota-exhausted adjudicate run — any `end_reason` other than
  `finished` — still sets `settled=True` forever for that hold, so `correction_rows`
  (`asf/feeder/rows.py:415-419`) permanently emits `WAITS ON merge` and never launches another
  `STALEMATE → ADJUDICATE` row over it, even though no ruling was ever actually delivered. Fix:
  gate on `finished(r)` (or `r.get('end_reason') == FINISHED`) in place of `r.get('ended')`.
- C2 — `asf/feeder/rows.py:78,415-419`: the card's Want is explicit — "`asf next` shows
  `WAITS ON merge: #773, #775`." `WAITS_MERGE` is the bare literal `'WAITS ON merge'`, and
  `correction_rows` sets `action=WAITS_MERGE` with no PR number ever appended;
  `action_cell` (`asf/feeder/render.py:61`) prints `row.action` verbatim, so `asf next` can never
  show a PR number for this row. `correction_rows` only receives the `corrections` dict (no
  `occupancy`/harvest data), unlike the PR-numbered `WAITS ON landing` sibling row
  (`asf/feeder/rows.py:460,472`, which reads `h.get('pr')` off harvest occupancy) — there is no
  plumbing from a PR number to this row at all. The new test (`tests/test_feeder.py:688-695`)
  only asserts `action.startswith(rows.WAITS_MERGE)`, so it does not catch this.
- C3 — `docs/plans/b-0128.md` (missing): no plan or spec exists on any branch, so "every Step" and
  "byte-identical acceptance tests" cannot be checked (rows above). Bugs of this shape get a plan
  in this repo's own practice (`docs/plans/b-0090.md`, `b-0092.md`, `b-0099.md`, `b-0101.md`,
  `b-0110.md`, `b-0115.md`, `b-0119.md`, `b-0120.md`) — add one naming this Task, with the
  Acceptance pointing at `tests/test_lifecycle.py:289` and `tests/test_feeder.py:688`, and state
  explicitly whether the PR-number half of the Want (C2) is in scope for this Task or a follow-up.

  implicit; worth a comment (or an explicit check) once C1 is fixed, so the invariant is
  self-evident rather than load-bearing by accident.
