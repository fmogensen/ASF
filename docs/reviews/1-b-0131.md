  about the console's allow list, though the card's Want opens with "`asf init` / tools/install.sh
  ends by offering the operator a reviewed allow list for the console". Fix: after the hooks line
  (`asf/init.py:318`), add `print(); print(console_perms.offer_text(product))` (mirroring
  `tools/install.sh`'s step 6 wording, "run one to write it: …"), so an operator who sets up or

  Add a test alongside `SampleProductTest`/`PackageTest` asserting `cmd_init`'s output contains the
  fixed rules, the same way `test_step_6_offers_the_console_permissions_and_writes_nothing`
  (`tests/test_install.py:1345`) checks the installer.

## I list

- `asf/console_perms.py:61-67` (`missing`) — dead code. `check_doctor` (`:108-124`) recomputes the
  same "not already present" set inline instead of calling it, and nothing else calls it either
  (`grep -rn "console_perms\.missing\b"` → only the definition). Either wire `check_doctor` through
  it (one source of truth for "what's missing") or drop it.
- `asf/console_perms.py:43-47` (`deny_rules`) — the deny pattern is
  `Bash(git push --force* origin <main>)`, a literal prefix match starting with `git push --force`.
  It is the card's own text verbatim ("a deny rule for `git push --force*` on the trunk"), but a
  differently-ordered command — `git push origin <main> --force` — would not match it and falls
  through to the normal allow rules. Worth a second deny rule (`Bash(git push origin <main> *--force*)`
  or equivalent) if Claude Code's own permission matching does not already normalize flag order;
  out of scope to verify here since it depends on the runtime's own matcher, not this diff.
- `asf/console_perms.py:35-40` (`allow_rules`) — the per-prefix push rules are built from
  `product.conventions.all_prefixes()`, which includes `legacy_prefixes()`
  (`asf/conventions.py:606-613`) as well as live ones. A retired prefix "is recognised but never
  minted" (`tests/test_conventions.py`'s own naming), so this allows pushing a branch name the
  factory will never create — harmless, but slightly broader than "lane branches" as the card
  states them.
- `docs/guide/operating.md:365-394` — the new section explains *why the console needs a list at
  all* well, but not why each individual rule is there one by one (e.g. it never spells out that
  `Bash(git worktree:*)` is for cleanup after a landed or abandoned branch, specifically). Minor;
  the six-line block plus the opening paragraph gets close enough that a reader can infer the rest.
