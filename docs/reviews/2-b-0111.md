## C — must change

1. **`asf/groom/inbox.py:83-85` — an unknown-header-shaped line that is never followed by a
   further confirmed header now leaks into the description instead of being dropped, when it is
   the *last* header before the body.** This is a regression round 1's head (`d0cf7f3`) did not
   have, introduced by this round's own fix for C1. The writer's own comment two lines above
   (`asf/groom/inbox.py:12`) names the exact case: "`after:` on a Task, say" — a real header
   intake does not read. Round 1's own test (`tests/test_inbox_shape.py:400-408`) only covers
   `after:` followed by more confirmed headers (`signature:`, `severity:`); nothing covers
   `after:` as the tail of the header block, immediately before body:

   ```python
   from asf.groom import inbox
   text = "# Checkout fails\nparent: E-0001\nafter: T-0001\nThe plan needs this to land first.\n"
   c = inbox.parse_inbox_file(text)
   # on round 1's head (d0cf7f3): c.headers == {'parent': 'E-0001'}
   #                              c.description == 'The plan needs this to land first.'
   # on this branch (452fa0f):    c.headers == {'parent': 'E-0001'}
   #                              c.description == 'after: T-0001\nThe plan needs this to land first.'
   ```

   Confirmed live against both revisions (`git show d0cf7f3:asf/groom/inbox.py` vs. the working
   tree) — a blank line between `after:` and the body line does not change the result.

   The C1 fixture and this one are genuinely indistinguishable by shape alone once nothing
   follows them: both are `[confirmed header] [word:-shaped line] [break]`, and the only way the
   current code tells them apart is whether a *further* confirmed header happens to come next —
   which is true for round 1's `after:` test and false for both this case and C1's. A shape-only
   lookahead cannot resolve this; the fix needs either (a) an explicit registry of known-but-
   unread header keys (`after:` at least, since the writer's own comment names it) that are
   always treated as headers regardless of what follows, leaving genuinely unknown `word: value`
   body lines to fall through untouched, or (b) some other signal beyond shape + lookahead. Add a
   test for `after:` as the last header line, no confirming header following, asserting it is
   dropped from `description` the way it already is when followed by more headers.
