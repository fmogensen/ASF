## C list

- **C1** `asf/tick/step_wave.py:1303` (`launch_now`) never reads the pause: it calls `screen(product, planned, items, running, held, seats, (host_held, host_why), s1_bypass_open, act=True, out=out, build=build, ctx=ctx)` with no `paused=`, and when `screen` returns any starting row it calls `_wave(...)` directly (`:1316`) — launching a session. `launch_now` is the wave clock's own launch path (`asf/tick/wave_clock.py`, `asf wave --product <p>`), installed by the scheduler on every product whose clocks carry a `wave` step and firing on its own ~60s period, independent of the product's tick lock. Confirmed live: `tests/test_wave_clock.py` has no mention of `pause` at all, and reading `launch_now` end to end shows no hold of any kind between `screen` and `_wave`. Under `asf pause`, a product with the wave clock installed (the default) keeps launching new sessions through this door — the one guarantee the whole card exists to deliver ("a pause starts nothing") does not hold for it. This is a second launching door PD12's re-grep missed (it only found `_wave`'s call sites inside `step_wave.py` itself at the old `:456,772`, which correspond to `launch` and `launch_now` both — the re-grep named the hits but the plan's analysis reasoned about only one of them). Fix: bind `paused = pause_mod.held(product)` beside the other reads in `launch_now`, pass it to `screen(...)`, and return 0 before reaching `_wave` the same way `launch()` does.
- **C2** `asf/tick/step_wave.py:890` (`would_start`) also calls `screen(...)` with no `paused=`. Verified directly: calling `screen()` the way `would_start` does, with a product that `pause.held()` returns a record for, yields `Screened.starts == True` for the launching row (reproduced with a standalone script against this tree). `would_start` is what `asf/views/status.py:387` (`ready_cell`, "Ready to launch N") and `asf/dwell.py:355,492` (`Facts.would_start`, `launchable_idle`) read. `screen`'s own docstring — edited by this diff — now claims "the operator's own launch pause … holding every row" is one of the checks the live wave and "the status cell's preview … run[ning] the same checks in the same order" both apply; for a launch pause that is false. Under a pause, `asf status`'s Ready-to-launch count stays unchanged (still counts the held rows as starting) and `asf.dwell`'s `launchable_idle` watchdog keeps firing `Finding`s for rows that are not idle at all — they are correctly held by the operator's own pause. Fix: bind `paused = pause_mod.held(product)` in `would_start` and pass it to `screen(...)`, matching `launch()`.
