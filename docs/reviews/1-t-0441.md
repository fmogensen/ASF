## C — must fix

**C1.** `asf/views/status.py`, `ready_cell` (and its feed, `_plan`) — the `Ready to launch` cell no longer
screens rows the way the wave actually will this tick, and the regression is invisible because the test
that caught it was deleted rather than adapted.

Before this diff, `ready_cell(root, product)` called `step_wave.would_start(product, root)`, whose
`screen()` (`asf/tick/step_wave.py:746-815`) walks the planned rows through approval holds (`held[row.item_id]`),
`trunkclose.closes_before_launch`, a host-pressure hold, the seat count (`room = seats - len(running)`,
`seats = r.sessions + extra` — the cloud lane's seats included), and the relaunch cap, and reported
anything it refused as "N held back (kind n, ...)". `_plan` replaces that with a bare
`feeder_rows.plan_rows(items, product, running, cap, **inputs)` (no `screen()` call anywhere in the new
path) and `cap = step_wave.capacity(product)` with no cloud `extra`. `tiers.select` (what `plan_rows` cuts
with) only ever applies the S1-lane cut and the raw seat count — it has no notion of an approval hold, a
closed-on-trunk item, host pressure, or the relaunch cap, all of which live only in `screen()`. So a row
that `would_start` would refuse this tick (held, host-pressure, relaunch-capped, or beyond the cloud-aware
seat count) now reads as "ready" on `asf status`, with no "held back" note at all — the opposite of what
F-0113 is about: a hold the operator can't see.

The old coverage of exactly this — `tests/test_views.py`'s
`test_the_ready_cell_counts_only_what_the_wave_would_start` (asserted `'0 (2 held back (held 1, relaunch
cap 1))'` by mocking `step_wave.would_start`) — is gone from this diff, not adapted to the new `Plan`
argument. Nothing in `docs/plans/replans/f-0113-8266efca4547.md`'s Steps 2 or 4 authorizes dropping this
behavior; Step 4 explicitly says the opposite ("every string it prints to the character"). The module
docstring was quietly edited to match the new, narrower behavior (dropping "held back" from the `Ready to
launch` bullet) rather than flagging the conflict.

Fix: either route `ready_cell` (or `_plan`) back through `step_wave.screen`/`would_start` so the held/host/
relaunch-cap/trunk-close/cloud-seat refusals are still named, or — if narrowing the cell's contract really
is this Task's intent — say so in the report and the plan, keep (don't delete) a test pinning the new,
narrower contract, and update the docstring to state the gap plainly rather than silently matching the
reduced behavior.

## I — not blocking
