## C list

### C1 — `_plan`'s screened plan is built from un-overlaid items, so `ready_cell` can again say "ready" for a row the wave will not launch

`asf/views/status.py:91` loads `items, _generated = ix.load(root)` and never applies
`asf.record.plan_order.overlay`. That `items` map feeds `rows`, `uncut` (`:95,98`), `gate`
(`:119`) **and** the `screened` computation (`:104-117`, via `gated_plan`/`host_hold`/`screen`).

Before this diff, `ready_cell` read `step_wave.would_start(product, root)`
(`asf/tick/step_wave.py:865-889`), which does apply the overlay unconditionally when
`product.repo_dir` is set (`step_wave.py:873-874`:
`items = plan_order.overlay(items, plan_order.trunk_reader(product))`), before calling
`gated_plan`/`screen` on the result. The real tick's launch path applies the same overlay too
(`step_wave.py:1147`, `:1282`). `_plan`'s hand-rolled reimplementation of `would_start` (added by
this diff to keep `ready_cell`'s output "to the character", per the code's own comment at
`:100-103` citing C1/I1 of an earlier round) copied every other step of `would_start`'s body —
`cloud_settings`, `cloud_readiness`, `split_hold`, `gated_plan`, `host_hold`, `host_mod`,
`s1_bypass_live`, `screen` — but dropped this one line.

**Failure scenario:** a product with `repo_dir` set, an open Task card
(`type: task`, `links: {plan: docs/plans/....md}`) that carries no explicit `after:` but whose
linked plan text implies a predecessor that has not landed. The real tick (which overlays items
before planning) derives the `after:` and holds the Task back. `asf status`'s `ready_cell`, going
through `_plan`'s un-overlaid `screened`, has no such `after:` on that item, plans it as
launchable, and reports it among the ready rows (or in the "N — first: ..." count). This is
exactly the bug class `ready_cell`'s own docstring and the test this diff deleted
(`tests/test_views.py`, old comment: "2026-10-04: status said 2 ready while the wave launched
0") exist to prevent — reopened here for any Task whose `after:` is derived rather than
explicit. It also makes the new `S1 gate` row (`gate` is built from the same un-overlaid `rows`
/ `uncut`) potentially name the wrong holder or miss/add an unworked S1 for the same class of
record.

No test in this diff exercises a `links: {plan: ...}` card, so nothing catches this; it is an
untested, silent behavior change for exactly the kind of record this feature is built to get
right.

**Fix:** mirror `would_start`'s guard — build a second, overlaid items map for the planning
calls, leaving `plan.items` (what `build_cell`/`decisions_cell` read) untouched, since those two
cells' pre-existing behavior never had the overlay and must not gain it now:

```python
from asf.record import plan_order
...
items, _generated = ix.load(root)
planning_items = (plan_order.overlay(items, plan_order.trunk_reader(product))
                  if product.repo_dir else items)
rows = feeder_rows.plan_rows(planning_items, product, running, cap, **inputs)
uncut = feeder_rows.plan_rows(planning_items, product, running, len(planning_items) + len(running or ()),
                              s1_first=False, **inputs)
...
planned, _dropped = step_wave.gated_plan(planning_items, product, running, seats, inputs, ...)
...
screened = step_wave.screen(product, planned, planning_items, running, ...)
```

### C2 — Step 1's `Plan` namedtuple and Step 2's `_plan` body do not match the plan text

Plan Step 1: `Plan = collections.namedtuple('Plan', 'product items rows inputs capacity inflight gate')`
(7 fields). Code (`asf/views/status.py:76`): 8 fields, `... gate screened`.

Plan Step 2: `_plan`'s whole body is `items`/`inputs`/`running`/`cap`/`rows`/`uncut`/
`tiers.gate(...)`, and "catches nothing (RD6) and writes nothing." Code
(`asf/views/status.py:79-120`) adds ~20 lines reimplementing `step_wave.would_start`'s screening
(`cloud_settings`, `cloud_readiness`, `split_hold`, `gated_plan`, `host_hold`, `host_mod`,
`s1_bypass_live`, `step_wave.screen`) to produce the new `screened` field.

This is not scope creep for its own sake: as established under C1, the plan's own RD4 claim that
dropping the overlay (and, read literally, Step 4's "`ready_cell` counts `plan.rows`") would
leave `ready_cell` printing "the same characters … today" does not hold — `plan.rows` is the
*unscreened* cut plan, not `would_start`'s `(row, starts, why)` triples, so counting it directly
would have changed `ready_cell`'s output (no held-back breakdown, no failing-to-spawn split).
The `screened` field is the correct fix for that gap and is itself well-tested
(`test_the_ready_cell_counts_only_what_the_wave_would_start`,
`test_the_ready_cell_counts_rows_failing_to_spawn`, both green). The finding is process, not
code: the plan document (`docs/plans/replans/f-0113-8266efca4547.md`) was never amended with an
RD covering this, so a reader of the plan alone would not learn that `_plan` now duplicates
`would_start`'s body, nor why. Not blocking on its own, but it is the same gap that let C1's
missing overlay line go unnoticed — a plan amendment documenting `screened` should also have had
to name every line `would_start` runs, which would have surfaced the missing overlay call.
Raised as I1 below for the operator; listed here only to explain why "every Step … implemented"
reads `fail` above.
