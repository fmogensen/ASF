## C

**C1 — `tools/install.sh:40-58`: the lock is checked, then released, then the package is swapped
unguarded — a tick that starts in that gap still tears exactly as B-0135 describes.**

The new Python block acquires `LOCK_EX | LOCK_NB` on `tick.lock`, and on success immediately does
`fcntl.flock(f, fcntl.LOCK_UN)` and `sys.exit(0)` — releasing the lock *before* the script returns
to `pipx install --force` two lines later. Nothing holds the lock across the install itself. A
tick launched by the scheduler in the window between that release and `pipx install --force`
finishing (a `pipx install` from a git ref clones and can run for several seconds) acquires the
now-free `tick.lock` in `asf.tick.tick.acquire_lock` and starts running against a package that is
mid-swap — the identical "half old, half new" `ImportError` the card exists to fix, just moved
from "a tick already running" to "a tick that starts during the install." The commit message's own
framing — "waits ... on the same tick.lock a running tick holds for its whole run ... before it
touches the package" — describes *waiting*, but what protects the install is *holding* the lock for
its duration, not checking it once beforehand. The fix: hold the same lock (or write a pending
marker the way `asf.upgrade.install`'s `write_pending`/`other_ticks` pair already does for the
tick's own self-upgrade path, `asf/upgrade.py:267-280`) across the `pipx install --force` call
itself, not just before it — e.g. keep `f` open and locked through the `pipx install` line, closing
it only after the install completes.

**C2 — `asf/tick/tick.py`: the second half of the Want — "the tick imports every step module up
front at start, so a swap mid-tick cannot mix versions" — is not in this diff at all.**

`_asf_step` (`asf/tick/tick.py:525-529`) still resolves each step's module with
`importlib.import_module(f'asf.tick.step_{step}')` at the moment that step runs, not at tick start.
This is the direct mechanism of the 2026-09-25 incident: `record` (and whatever else the tick had
already imported at process start) can be from the old package while `step_groom`, imported later
in the same process because it happens to run fourth, resolves from a package `pipx` has since
moved underneath it. C1's lock is the first of the two defenses the card asks for; this is the
second, and it is the one that would still catch a torn tick even when C1's race window is hit.
The fix: in `_run_steps` (or `cmd_tick`, before `_run_locked`), resolve every row's callable — e.g.
call `_asf_step(step)` for every `(step, 'asf', _)` in `rows` — before running any of them, so a
package swap mid-tick can no longer land between two of a single tick's own step imports.

**I2 — `asf/tick/tick.py`'s own doc comment overstates what "held" covers.** `Locks.__init__`
(`asf/tick/tick.py:295-297`, the class docstring above it) says a clock of command-steps-only takes
the product lock "briefly, waiting, around each record part" rather than for its whole run — so
`tools/install.sh`'s new comment, "the same lock a running tick holds for its whole run," is true
only for a clock that includes an `asf` step, not for one that doesn't. No `asf`-owned step is
dynamically imported by a command-only clock in the same run, so this doesn't reproduce the C2
symptom today — but it's worth tightening the install.sh comment so a future reader doesn't read
"whole run" as universal.
