## Context

`fix/B-0016` was routed to adjudication a sixth time as a reviewer/fixer stalemate "held 3 times
(conflict)", after [D-7850](D-7850.md), [D-7851](D-7851.md) and [D-7852](D-7852.md) had each ruled
that there is no open finding and that the hold lives in the branch's history. This session found
what D-7851 and D-7852 found: no review file on any ref, and the worktree left mid-`rebase` onto
`895539c` with four conflicted hunks in `asf/workers/spawn.py` — the fourth stray rebase the item
has produced. All three prior cards ended by handing the operator a cherry-pick rebuild finishing
in `--force-with-lease`; none of them tested whether a history rewrite was needed at all.

## Decision

**Open review findings: none — none upheld, none overruled.** Checked in this checkout, not
inherited: `git log --all --oneline --diff-filter=A -- docs/reviews/1-b-0016.md` returns nothing,
and so do the same queries for `docs/specs/b-0016.md` and `docs/plans/b-0016.md`. The round-1
review this session was told to answer has never existed on any ref, so there is no reviewer
reading and no fixer reading to choose between. Any finding raised against round 1 after this card
is out of time permanently: it is a new item against `main`, never a reopening of this loop.

**The fix stands as committed. No edit to it.** Every anchor re-checked against this checkout:
- `_repo_lock_path` — `asf/workers/spawn.py:139-140`, `.git/asf-worktree.lock` per repo.
- `_with_repo_lock` — `:143-161`; exclusive `fcntl.flock` at `:152`, one retry only when the error
  names `lock config file` at `:157`, unlocked in a `finally` at `:161`.
- `make_worktree` — `:164`; its whole `add` closure (fetch, takeover, held-branch reuse,
  reaped-branch arm, fresh branch) goes through that lock at `:215`.
- Pinned by `tests/test_workers.py:332` (eight concurrent adds all land) and `:350` (the retry runs
  the add path again over a half-made worktree).

That is exactly the "serialise worktree creation per repo (a lock dir or a per-repo mutex) and
retry once" the item asks for.

**The remedy does not need a force-push, and this is what changes.** D-7850, D-7851 and D-7852 all
concluded that only a history rewrite could clear the hold, because a plain rebase replays the
superseded `6fcb8df` on top of `4690ba0`. The first half is right; the conclusion does not follow.
Verified here by object id rather than by argument:

```sh
git merge-tree --write-tree origin/main origin/fix/B-0016   # exit 0 -> 3930e63
git rev-parse 3930e63:asf/workers/spawn.py                  # 44ee4df
git rev-parse origin/fix/B-0016:asf/workers/spawn.py        # 44ee4df  <- identical
git rev-parse 6fcb8df:asf/workers/spawn.py                  # 69b7fb3  <- not present
```

The merged tree's `spawn.py` is byte-identical to the branch tip's and is **not** the superseded
variant: the `-s ours` merge `59e8ebf` already settled that `6fcb8df`'s tree contributes nothing,
and merging preserves that decision where rebasing discards it. `git diff 3930e63
origin/fix/B-0016` is only `main`'s newer work arriving (F-0073/F-0074 specs, D-8050, `lifecycle`,
`check`), which is what landing on current trunk is supposed to look like. So B-0016 lands with a
plain non-fast-forward merge, which rewrites nothing, needs no lease, and depends on no local
state:

```sh
git fetch origin && git checkout main && git merge --no-ff origin/fix/B-0016 && git push origin main
```

**D-7850, D-7851 and D-7852 are affirmed on the finding and on the fix, and their handover form is
superseded.** The rebuild formula still works and stays valid as a fallback, but it is no longer
the recommended route: a rewrite is the larger and more dangerous of two remedies that reach the
same tree, and the merge is verifiable ahead of time by the four commands above.

**Adjudication stays refused for this item.** B-0016 is not disputed. Pushing to `main` is not a
session's to do under the standing rules, so the last step remains the operator's either way.

## Consequences

- B-0016 is **blocked on the operator for one merge**, not for a history rebuild. No review or
  adjudication round on `fix/B-0016` follows this card; a later `conflict` hold on it is answered
  by pointing here, not by starting a seventh session.
- Harvest still cannot land this branch, and that is a defect in harvest, not in the branch:
  `rebase_and_resolve` runs a plain `git rebase origin/{trunk}`
  (`asf/harvest/harvest.py:285`), which flattens merges, and aborts on the first file it does not
  own (`:290-292`, the `conflict in <file>` hold). **Any** branch that ever carries a merge commit
  is unharvestable for this reason, so this will recur on items unrelated to B-0016. It needs its
  own bug — a `--rebase-merges` rebase, or a merge fallback when `git merge-tree` exits 0 and the
  rebase does not converge. That is outside this branch's footprint and is not changed here.
- The routing defect D-7852 named is now demonstrated rather than predicted: it said "no review or
  adjudication round on `fix/B-0016` follows this card", and a sixth one followed anyway. A
  repeating `conflict` hold on the same file and the same sha pair is still routed to "adjudicate",
  which cannot clear it. Six sessions have each spent a cycle re-deriving one answer.
- No commit on this branch changes the fix. This card and the pointer added to
  `docs/reviews/1-b-0016-ruling.md` are the only files it touches.
- `BACKLOG_ID_RANGE` gives adjudication only the `S`, `T` and `B` bands (`7850-7899`). As with
  D-7850..D-7852 this card takes the next free id in the matching `D` band (`D-7850`, `D-7851`,
  `D-7852` here, `D-8050` on `main`). The missing `D` allocation is still the operator's to close.
