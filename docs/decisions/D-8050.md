## Context

`fix/B-0053` was held three times as `unpushed work: not pushed: 1 uncommitted file(s), 8 unpushed
commit(s)` and sent back to a correction session each time, which is what put it at the round cap.
No review was ever filed against it — there is no `docs/reviews/1-b-0053.md` on any branch, and
the card still reads `fix_rounds: 1` — so the stalemate was never a reviewer disputing the fix with
a fixer; it was the same mechanical verdict three times, against work that was already correct and
already on origin.

## Decision

**The B-0053 fix stands as written. No edit to it.** Checked against the checkout: the workflow's
trigger is `on: push: branches: [main]` with `pull_request:` kept
(`.github/workflows/tests.yml:7-10`), which is exactly what the card's `## Fix` asks for, and
`tests/test_workflow.py` pins both halves. `asf/env.py:105` is a hand-written YAML-subset parser,
not a YAML 1.1 one, so the `on:` key survives as the string `'on'` and the test reads what it
claims to read. Limiting push to the trunk costs the record nothing: the only consumer of branch
runs, `evidence.ci_green_runs`, already reads `--branch {product.main}` only
(`asf/evidence/evidence.py:633`). This finding is settled and does not come back in a later round.

**The hold was the defect, and it is fixed here.** `health.push_gap` and `lifecycle.gather` counted
`origin/<branch>..HEAD` by sha. Harvest rebases a branch onto the trunk in its own throwaway
worktree (`harvest.rebase_and_resolve`, called at `harvest.py:381`) *after* the session pushed it,
which drags every commit the trunk has gained into that range and gives the session's own commits
new shas. On this branch it counted 10: nine that are already on `origin/main`, and one — the fix —
whose patch is already on `origin/fix/B-0053`. Both commits have patch-id `00d73bef1b1c…`; `git
cherry origin/fix/B-0053 HEAD origin/main` marks the fix `-`, already upstream. The count is now
`lifecycle.unpushed_commits`: above `origin/<main>`, and by patch rather than by sha.

**This was a livelock, not a slow session.** No move the session was allowed to make could bring
the old count to zero — a plain push of a rebased branch is rejected non-fast-forward (verified:
`git push --dry-run` → `! [rejected] … (non-fast-forward)`), and the standing rules forbid a force.
Every correction round could only re-report the same failure.

## Consequences

- `asf/workers/lifecycle.py` gains `unpushed_commits`; `gather` and `health.push_gap` both use it.
  A branch harvest rebased whose work is on origin now reads pushed, so harvest gates and lands it
  instead of health sending another correction. Work genuinely committed after the rebase is still
  counted — pinned by `tests/test_lifecycle.py::UnpushedAfterARebaseTest`, four tests including the
  raw-sha count of 2 that caused this.
- B-0053 itself needs no further session. Harvest lands from the **local** ref
  (`harvest.py:375`, `git rev-parse <branch>` in the product repo), which is `751fd7b` — the fix
  rebased onto current `main`, and the only commit in `origin/main..fix/B-0053`.
- `origin/fix/B-0053` stays at the pre-rebase `8256485` until harvest moves it. That is harmless:
  its patch is identical, and `push_branch` (`harvest.py:346`) force-with-leases the branch as a
  matter of course.
- The asymmetry that made this unescapable is left standing for the operator: harvest may
  force-with-lease a worker branch, a session may not force its own. See the NEEDS OPERATOR note
  in this session's report.
