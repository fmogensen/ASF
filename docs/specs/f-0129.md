# F-0129 — the product file says what is wrong with it, and one command fixes what it can

One unknown key in `~/.ASF/products/<p>.yaml` stops the whole install. `load_product` refuses the
file on the first problem `validate_product_text` finds, every command that loads a product raises
`ConfigError`, and `asf doctor` prints exactly one row — `config RED` — and nothing else: no repo
row, no scheduler table, no clue which key, no command to run. The operator's only route is to
open the file and guess which of their keys the schema still knows. The first customer install
paid that cost, and paid it with a hand-made file where the keys were not typos but *homes*: a
secrets store, CI budgets, runner pools, a spec/plan approval policy — written where an earlier
release, or a reasonable guess, put them.

Two things the card asks for are already true in the checkout, and the design below is cut to what
is not:

- **The prod-view crash is closed.** B-0095 landed: `prod.render` reads a list-shaped
  `customer_paths` and an empty one (P5), and a map- or string-shaped one is refused at *load*
  with its line and its shape. What is left of the card's last bullet is the opposite failure
  (P4): `ci:` and `deploy_sha:` carry **no** declared shape, so `ci:` written as a list loads
  clean and is then silently ignored by every reader — a product with no gate, no provider and no
  deploy, and nothing anywhere saying so.
- **Three of the four homeless keys now have homes**: `ci.budgets`, `ci.pool`, `credentials` and
  `approvals`/`approval_signals` are all declared fields (P6). So for those the failure is a
  *spelling* — `ci_budgets` for `ci.budgets` — and the fix is a suggestion, not a new schema.

And the guide already holds the map this card wants in code: an *Old keys, and where they went*
table, eleven rows, saying for each old spelling what replaced it and whether it is still read
(P7). Nothing reads that table but a person.

After this change: `asf config check --product P` prints one row per key the schema does not know
as written — its line, the current key it maps to, or that it has no home — and exits non-zero only
when the file does not load as it stands. `asf config migrate --product P` rewrites the renames and
moves every unknown key under `x-unmapped:` with a comment, keeping a timestamped backup, refusing
to write a file that would not load or that would change a value the factory already reads; a
second run writes nothing. `asf doctor`, the `NEEDS OPERATOR` line and `asf upgrade`'s row all name
`asf config check`. And the guide's table becomes the code's table, with a test that they cannot
drift apart.

### In

- **`asf/product_config.py`** — the one place that knows what an old product-file key is called
  now: the rename table, the check, and the line-based rewrite. It reads the schema from
  `env.PRODUCT_FIELDS`/`NESTED_FIELDS` (never a second copy of the key list) and the file's text
  through `env`'s own `_match_key`/`_strip_comment`, so it cannot disagree with the reader about
  what a key line is.
- **`asf config check --product P`** — one row per key the schema does not know as written: its
  line, its class (`renamed`, `retired`, `no home`, `shape`, `duplicate`), the current key it maps
  to or the note, and whether `asf config migrate` fixes it. Exits **1 only when the file does not
  load as it stands** — an advisory about a still-read old spelling keeps a working install green.
- **`asf config migrate --product P`** — writes. It acts on exactly two classes: a key in the
  rename table becomes its current key (renamed in place, or moved into its new section), and an
  **unknown** key's whole block moves under `x-unmapped:` with a comment naming why. It keeps
  `<file>.bak.<UTC stamp>`, prints what it did, and a second run finds nothing and writes nothing.
- **Three refusals in `migrate`, each of which leaves the file untouched**: a rewrite whose text
  would not validate; one that loses a leaf value; one that changes a value the factory already
  reads (P19 — a migration may only make an *ignored* key start being read). Anything needing a
  human decision — a rename whose target is already set, a wrong shape, a duplicate key — is
  reported and left alone, and the rest of the file is still migrated.
- **`x-unmapped:`** — a declared top-level key of shape *a map*, whose contents nothing checks and
  nothing reads. It is what makes "never drop a key" possible at all: without it, the parked keys
  would refuse the load they were parked to permit.
- **A declared shape for `ci` and `deploy_sha`** — a map, or (for `ci`) the bare word `none`. A
  list-shaped `ci:` stops being a silently ignored block and becomes a named finding at load (P4).
- **The pointer, in all three places a load failure surfaces**: `cli.needs_operator_line`, the
  doctor's `config` row, and `asf upgrade`'s per-product row all name
  `asf config check --product <p>`.
- **A `config keys` doctor row, advisory** — how many keys are parked under `x-unmapped:` and how
  many old-but-read spellings are still in the file, with the command. A parked key nothing ever
  mentions again is a lost key with extra steps.
- **The guide**: *Old keys, and where they went* is split into a product-file table (one row per
  key, machine-checked against the code table) and an operator-config table (prose, as now);
  `product-config.md` gains `x-unmapped:` and the two commands; `troubleshooting.md` gains the row
  for a refused product file; `products.example.yaml` documents `x-unmapped:`.

### Out

- **A YAML library, and a round-trip rewrite.** `migrate` never regenerates the file: it splices
  lines. A round-trip through the reader would drop every comment in the file, and comments are
  where the keys this card is about have been kept (D3).
- **Migrating `config.yaml`.** Its deprecated keys are all still read, so an old one costs nothing
  today, and it is machine-wide: one command that rewrites the file every product shares is a
  different blast radius from one that rewrites a product's own. `check` names them from the
  guide's prose; nothing rewrites them (D6).
- **Moving a retired-but-parsing key.** `conventions.task_heading` parses, is a `Conventions`
  field, and nothing reads it. Parking it would change nothing for the better. `check` says
  *retired*; `migrate` leaves it (D7).
- **Coercing a shape.** A `customer_paths` written as a map holds information a list cannot
  (`web: apps/web` — which key was the name?), and guessing wrong silently redefines what
  customer-visible means. `check` prints the shape and the line; the operator edits (D8).
- **`--all`.** One product per invocation. `asf upgrade`'s table already names the per-product
  command for each product it found, and that is where an operator meets several at once.
- **`--apply`.** `asf config check` *is* the dry run (D5), so a second dry-run mode on `migrate`
  would be a third spelling of the same output.
- **A new card id for a homeless key.** Ids come from `asf new` or a session's range (P20); a code
  table of ids that this session invented would be a record that does not exist. The note's card
  slot exists and ships empty (D10).
- **Checking keys deeper than the schema does today** (P2). `groom.nonsense` is not refused now
  and is not refused after this; widening the checked depth would refuse files that load today,
  which is this card's failure mode, not its fix.
- **`asf init`'s writer, and the record's schema.** `asf config migrate` edits an existing product
  file in place; `asf init` writes a new one; `asf schema-migrate` migrates the record. None of the
  three learns about the others.

| # | Chosen | Against | Why |

| D3 | A line-based splice that keeps every byte it does not move | load, transform, dump | there is no dumper (P11) and writing one is a larger change than this card; and a dump would drop the file's comments — the very place a hand-made file's homeless keys have been surviving. A splice also makes the diff `migrate` prints small enough to read |
| D4 | Unknown keys are **parked**, under a declared `x-unmapped:` that nothing reads | commented out in place, or left where they are and the load made tolerant | commenting out is dropping a key with an audit trail, and it leaves the file's shape a lie. Making the load tolerant of unknown top-level keys would lose the typo check that catches `customer_path` today. | D6 | `check` reports `config.yaml`'s old keys from the guide's prose; nothing rewrites that file | migrate both files under one command | every documented `config.yaml` rename is still read (P7), so the file loads and the factory behaves — there is no RED to clear. And it is the machine's file, not the product's: rewriting it on `--product P` would edit state every other product shares |
| D7 | `migrate` touches exactly two classes — renames, and unknown keys | also retire, coerce shapes, and resolve collisions | the file refuses to load because of the second class and misbehaves because of the first; those are the two the card names, and both are decidable from the table with no guessing. A shape coercion or a collision resolution is a guess about intent, and a wrong guess here changes what the factory does to a repo |
| D8 | A wrong shape is reported with its line and the shape wanted, never rewritten | coerce a scalar to a one-item list, a map to its keys | `customer_paths: apps/web/**` → `[apps/web/**]` looks safe and `customer_paths: {web: apps/web}` does not, and one rule cannot be right for both. The report is already the whole diagnosis: the key, the line, `must be a list` |
| D9 | Two suggesters: the rename table (authoritative — `migrate` acts on it) and a best-effort *did you mean* (`check` prints, `migrate` never acts) | one fuzzy matcher | a table row is a fact about this project's history; a close match is a guess (P17). The slot is in the table's shape, so filling one later is a one-line data change, not a redesign |
| D11 | `migrate` refuses to write unless the new text validates, keeps every leaf, and changes no value the factory already reads | write, then tell the operator to check | the file being edited is the one that decides what the factory does to a repo, and the operator running this command is by definition not sure what their keys mean. | D12 | The backup is `<file>.bak.<UTC stamp>`, written only when something changes | a single `<file>.bak`, or no backup | a single `.bak` is overwritten by the second run — which, on a bad first migration, is exactly when the original is wanted. Making them equal by test means a future rename cannot land in one and miss the other, and it is why the code table needs no docstring repeating the notes |
| D15 | The doctor's parked-keys row is **not required** | required, so a parked key keeps the doctor red | a parked key is a *decision owed*, not a broken install — the product works, the key does nothing. ## The design

### `asf/product_config.py` — the map, the check, the rewrite

```python
"""asf.product_config — what an old or hand-made product file's keys are called now.

``~/.ASF/products/<p>.yaml`` is refused whole on one unknown key (:func:`asf.env.load_product`),
which is right — a typo must not be read as a new feature — but leaves an operator whose file was
written for an earlier release, or by hand, with a RED doctor and no route (F-0129). This module is
the route:

- :func:`findings` — one row per key the schema does not know as written: renamed, retired, no
  home, a wrong shape, a duplicate. Read-only; ``asf config check`` prints it.
- :func:`rewrite` — the same file with the renames applied and every unknown key parked under
  ``x-unmapped:``, comments and untouched lines byte for byte. ``asf config migrate`` writes it.

The current keys come from :data:`asf.env.PRODUCT_FIELDS` and :data:`asf.env.NESTED_FIELDS`, never
a second copy (D2), and the text is cut on ``env``'s own key and comment primitives, so this module
and the reader cannot disagree about what a key line is (D3).
"""
```

The three tables. `RENAMES` is the machine half of the guide's *Old keys* table and is asserted
equal to it (D14):

```python
#: old dotted key -> the dotted key it is now. Every row is also a row of the product-file table
#: in ``docs/guide/product-config.md`` (:class:`tests.test_product_config.TheGuideTableAndTheCodeTableAgree`).
RENAMES = {
    'ci.deploy_workflow': 'deploy_sha.workflow',
    'conventions.harvest_gate': 'conventions.harvest.gate',
    'conventions.branches_per_tick': 'conventions.harvest.branches_per_tick',
    'conventions.gate_timeout_s': 'conventions.harvest.gate_timeout_s',
    'conventions.test_command': 'ci.test_command',
    'conventions.ci_workflow': 'ci.workflow',
    'conventions.ci_dev_job': 'ci.dev_job',
    'conventions.deploy_workflow': 'deploy_sha.workflow',
}

#: old dotted key -> why nothing reads it any more. Reported, never moved (D7): a key the schema
#: still parses and nobody reads costs nothing where it sits.
RETIRED = {
    'conventions.task_heading': 'not read: the evidence pass finds a plan\'s tasks by its '
                                '`## Task N` … `#### Task N` headings',
}

#: a key with no home in the schema -> (the note, the card that decides it or None). An unknown
#: key needs no row here to be parked; a row is how a key the factory has *considered* says so.
#: The card slot ships empty: an id comes from ``asf new``, never from this table (D10).
HOMELESS = {}
```

The finding, and what produces it:

```python
#: One key the schema does not know as written. ``kind`` is 'renamed' | 'retired' | 'no home' |
#: 'shape' | 'duplicate'; ``now`` is the current dotted key, or '' when there is none; ``fixable``
#: is whether :func:`rewrite` acts on it (D7).
Finding = collections.namedtuple('Finding', 'line key kind now detail fixable')


def current_keys():
    """Every dotted key the schema declares, derived from ``env.PRODUCT_FIELDS`` and
    ``env.NESTED_FIELDS`` (D2) — ``{'main', 'ci', 'ci.budgets', 'capacity.batch', …}``."""


def suggestion(key):
    """The current key a hand-made ``key`` most likely meant, or '' — a close match over
    :func:`current_keys` (``customer_path`` → ``customer_paths``), then the dotted reading of an
    underscored one (``ci_budgets`` → ``ci.budgets``, ``release_window_days`` →
    ``release.window_days``). A guess: ``check`` prints it, ``rewrite`` never acts on it (D9)."""


def findings(text):
    """Every :class:`Finding` in a product file's text, sorted by line.

    Renames and retirements come from the tables; the unknown and wrong-shaped keys come from
    ``env.validate_product_text`` — the same list that refuses the load — so ``check`` can never
    disagree with the loader about whether the file is loadable. A key that is unknown *and* has
    no rename row is 'no home': its note and card from :data:`HOMELESS` when it has a row, else
    :func:`suggestion` and the ``asf inbox`` line."""
```

The rewriter. One block per key, taken with the comment lines directly above it, spliced whole:

```python
def blocks(text):
    """The file as ``[(dotted key, first line, last line, indent)]`` for every key line, with the
    comment lines directly above a key counted as part of its block — a comment is the operator's
    note on the key it sits over, and a move that left it behind would strand it."""


def rewrite(text, now=None):
    """``(new_text, [(Finding, what was done)])`` — the renames applied and every unknown key
    parked, with everything else byte for byte.

    A rename whose target sits in another section moves the block there, re-indented, creating the
    section when it is absent. A parked key's block moves under ``x-unmapped:`` (appended when
    absent) behind one comment line naming the key and why it is there. Nothing else moves.

    Three refusals, each raising :class:`asf.env.ConfigError` and leaving the caller with the
    original text (D11):

    - the new text does not validate (``env.validate_product_text``),
    - a leaf value of the old text is not in the new one, under its old dotted key or its new,
    - a value the factory already read changed (:func:`effect`).

    A key needing a human decision is skipped, never guessed: a rename whose target is already
    set, a duplicate key (the reader keeps the last value — P18), a wrong shape."""
```
