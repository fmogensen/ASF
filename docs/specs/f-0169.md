# F-0169 — the cause key stops naming the messenger

The card says the gate signature `--- test_tick_steps: FAILED (rc N)` is red 3.5 times a week, 7 of
7 runs over 14 days. Both numbers are real; the reading they add up to is not. The gate ledger
(`<state dir>/gates.jsonl`) and the kept output of each red gate (`logs/harvest-gate-red.log`) say
what those 7 rows actually were:

| ledger rows | branches | the test that failed |
| --- | --- | --- |
| 1 (09-25 21:50Z) | `fix/B-0125`, `fix/B-0127` | `tests.test_tick_steps.HarvestStepTests.test_finished_fix_branch_lands_through_the_tick` |
| 6 (09-26 01:46Z → 03:23Z) | `fix/B-0131` | `tests.test_tick_steps.PrsStepTests.test_harvested_and_at_trunk_branches_are_not_candidates` |

Two defects, on two branches' work in progress, which the gate correctly refused. One of them was
re-gated six times by six successive ticks while it stayed unfixed, and each re-gate appended
another row. `rank` counts rows (`asf/scorecard/diagnose.py:118`: `c['red'] += 1 if red else 0`), so
one unresolved red became six, and 2 became 7.

Neither defect is in `tests/test_tick_steps.py` as it stands. The module is green at `2184462be` —
98 tests in 28 s under plain `unittest`, 101 in 28 s under `tools/run_tests.py` — so there is
nothing in it for this card to fix. What is broken is the reporting, in two independent places.

**The signature names the module, never the test.** `harvest.first_failing_line`
(`asf/harvest/harvest.py:778`) returns the first line of the gate's output matching `FAIL_LINE_RE`
(`:707`). The sharded runner prints its own banner *before* the module's output
(`tools/run_tests.py:233`):

```
--- test_tick_steps: FAILED (rc 1)          <- \bFAILED\b matches here, and the scan stops
======================================================================
FAIL: test_harvested_and_at_trunk_branches_are_not_candidates (tests.test_tick_steps.PrsStepTests…)
```

So the signature can never be more specific than a module name. This is not a near miss: **all 23
red gates in the ledger carry a banner, and not one names a test** — 5 distinct signatures, all of
the form `--- <module>: FAILED (rc 1)`. `tests/test_tick_steps.py` carries 98 tests across a dozen
classes, and every failure in any of them lands in one cause key. The card that key files names no
test, no class and no assertion, so a session that picks it up has nothing to act on. That is why
this card arrived shaped as "a module is red 3.5 times a week" rather than "this test failed twice".

**A re-gate of the same red counts again.** Six rows for `fix/B-0131` are six runs of one defect.
The per-week rate is therefore *gate executions that were red*, not *distinct reds* — a single
unfixed branch inflates it by however many ticks pass before it is sent back. (The bisection's
targeted re-runs are not part of this: the 6 full gates on `fix/B-0131` wrote 6 ledger rows and the
6 `only:` re-runs between them wrote none. Only the full landing gate appends.)

Counting occurrences instead of rows, over the card's own window:

| signature | rows | rows/week | occurrences | occ/week |
| --- | --- | --- | --- | --- |
| `--- test_dry_run: FAILED (rc 1)` | 12 | 6.00 | 8 | 4.00 |
| `--- test_tick_steps: FAILED (rc 1)` | 7 | **3.50** | 2 | **1.00** |
| `--- test_conventions: FAILED (rc 1)` | 2 | 1.00 | 1 | 0.50 |
| `--- test_migrate: FAILED (rc 1)` | 1 | 0.50 | 1 | 0.50 |
| `--- test_watch: FAILED (rc 1)` | 1 | 0.50 | 1 | 0.50 |

3.50 reproduces the card exactly. 1.00 is under the 3.0 threshold — and `test_dry_run` stays over it
at 4.00 across eight separate branches, which is what tells us this counts recurrence and does not
merely suppress it.

This card fixes the two reporting defects, and then pays the bill they leave behind: once a
signature names a test, the key `gate:--- test_tick_steps: FAILED (rc N)` stops existing, and
`diagnose.metric` answers `0.0` for a `gate:` key it cannot find (`:159`). `moved(3.5, 0.0, 0.2)` is
True, so this card's own verify would write "moved — 3.5 before, 0 after" and close it on a number
nothing measured. §3 makes that impossible.

### In

1. `first_failing_line` prefers a **specific** failing line over the gate runner's own bookkeeping,
   and falls back through the module banner to the bare verdict.
2. `_sig_class` reduces a unittest failure header to its dotted test id, so the cause key is the
   test.
3. `rank` counts a red signature once per `(signature, branch set, UTC day)` and reports gate
   executions separately; the gate cause's detail names both numbers.
4. every new ledger line and `gates` event records the **signature scheme** its `line` was chosen
   under; a line written before this card reads as scheme 1.
5. `verify` refuses to call a `gate:` cause *moved* when the scheme changed under it, and records
   `scheme changed` with the before-number and no after-number.

### The choices

| # | chosen | against | why |
| --- | --- | --- | --- |
| C1 | three tiers in `first_failing_line`: a specific line beats the module banner, which beats the bare verdict | one extra `continue` that skips the banner | tested and rejected: a module killed by the gate timeout prints `--- m: no summary (rc -9)` and then the runner's `FAILED (errors=1)`. Skipping the banner returns the bare verdict — *less* specific than today. The banner must outrank it, not be dropped. |
| C2 | the banner is matched by its own pattern, not through `FAIL_LINE_RE` | reusing the existing match | P4: a `no summary` banner matches no part of `FAIL_LINE_RE`, so a tier keyed off that match never sees it and the killed-module case falls straight to the bare verdict again. |
| C3 | the dotted-id reduction lives in `_sig_class` | in `first_failing_line` | the gate stays generic — it reports the line its product's test command printed. All signature *shaping* (hex, digits, the 80-char cut) is already in one function, and putting it there re-classes stored rows with no migration. |
| C4 | the key is the dotted test id alone | the whole `FAIL: <name> (<id>)` header | the header is ~130 chars and `_sig_class` cuts at 80 (P5), which would truncate mid-id and could collide two tests of one class sharing a long prefix. The id alone is 68 chars for the worst case here and is already the canonical name — it is exactly what `python3 -m unittest` takes back. |
| C5 | an occurrence is `(signature, branch set, UTC day)` | `(signature, branch set)` over the whole window | a branch red, sent back, fixed wrong, and red again a week later is genuinely two occurrences, and the pair alone collapses them into one. The day bound keeps that recurrence visible. It over-counts a branch re-gated across midnight — conservative in the safe direction: it never hides a red. |
| C6 | `red` becomes occurrences, and a new `red_runs` keeps the executions | replacing `red` outright | P8's detail sentence reads "N of M runs red". With `red` alone it would say "2 of 7", which is false — all 7 executions were red. Both numbers are kept so the sentence can be true. |
| C7 | the scheme is an integer on the gate event | inferring the change from the signature's shape | shape-sniffing is a guess that breaks the next time either function changes. One integer, bumped deliberately, is the record — and it generalises: every future signature change is handled honestly instead of silently closing every open gate card. |
| C8 | `Cause` gains an 8th field with a default, and stays `frozen=True` | passing `facts` into `file_causes`; dropping `frozen` | all 8 construction sites are positional (P9), so a defaulted trailing field is source-compatible, and a default is legal on a frozen dataclass — the decorator is not touched. `file_causes` takes causes, not facts; threading facts in would widen a signature for one field the cause already knows. |
| C9 | `scheme changed` is a terminal verdict that does **not** reopen | reopening under the new key | the loop cannot know which new key replaces a dead one — a reopen would re-file the same unactionable module-level card. The card gets the truth in its History and stops; if `tests.test_tick_steps.*` genuinely recurs it crosses the threshold under its own name and files its own card, naming the test. |
| C10 | both filing sites write `scheme` — `file_causes` and the reopen at the tail of `verify` | recording it in `file_causes` alone | the reopen rewrites `state[key]` whole (`asf/scorecard/loop.py:383-386`), so a `scheme` left off there drops the freshly filed cause into the no-scheme fallback, and the next verify closes it the ordinary way — this card's own defect, one cycle later. The reopen records the window its new `baseline` was read over, so the entry's scheme and its number always come from the same reading. |

## The design

### `asf/harvest/harvest.py` — the gate reports the cause, not the messenger

Two patterns beside `FAIL_LINE_RE`, and one rewritten scan.

```python
#: The gate runner's own per-module banner (``tools/run_tests.py``): it names the red module but
#: never the red test, and it is printed *before* that module's output — so a scan for the first
#: failing line stops on it and the signature can never be more specific than a module (F-0169).
#: Tier 1: better than a bare verdict, worse than anything naming a test.
RUNNER_BANNER_RE = re.compile(r'^--- \S+: (?:FAILED|no summary) \(rc -?\d+\)$')
#: A test command's closing verdict with no cause in it. Tier 2: the last resort that is still
#: a failure line, for a red that named nothing else (a hook leak, a bare ``FAILED``).
BARE_VERDICT_RE = re.compile(r'^FAILED(?: \(.*\))?$')


def _fail_tier(line):
    """How specific a failing ``line`` is: 0 names a cause, 1 names only the module, 2 names
    neither, None is not a failure line at all. ``RUNNER_BANNER_RE`` is tried *before*
    ``FAIL_LINE_RE`` and not through it: a ``no summary`` banner matches no part of that pattern."""
    if RUNNER_BANNER_RE.match(line):
        return 1
    if BARE_VERDICT_RE.match(line):
        return 2
    return 0 if FAIL_LINE_RE.search(line) else None


def first_failing_line(text):
    """The most specific failing line of ``text`` — the first of the lowest tier
    (:func:`_fail_tier`); the last non-blank line when none failed."""
    lines = [l.strip() for l in (text or '').splitlines() if l.strip()]
    best = None
    for l in lines:
        tier = _fail_tier(l)
        if tier is None:
            continue
        if best is None or tier < best[0]:
            best = (tier, l)
        if tier == 0:
            break
    return best[1] if best else (lines[-1] if lines else 'no output')
```

A product whose test command is not this runner is unaffected: its failing line is tier 0 already
and the scan still stops on the first one (`tests/test_x.py::test_y FAILED` stays itself).

`gate_files` and `red_modules` are untouched — the files a red gate names and the modules it lists
are separate questions, already answered from the whole output.

### `asf/harvest/harvest.py` — the scheme is on the record

```python
#: Which rule chose a gate's ``line``. Bumped whenever :func:`first_failing_line` or
#: :func:`asf.scorecard.diagnose._sig_class` changes what a red gate is keyed on, because every
#: ``gate:`` cause key changes with it and a number taken under one scheme cannot be compared with
#: a number taken under another (F-0169). 1: the first ``FAIL_LINE_RE`` line, which on this repo's
#: sharded runner was always the module banner. 2: the most specific failing line, keyed on the
#: dotted test id.
SIGNATURE_SCHEME = 2
```

`record_gate` writes it into the entry:

```python
entry = {'at': ..., 'seconds': seconds, 'branches': list(branches), 'sha': sha, 'ok': ok,
         'line': line, 'signature_scheme': SIGNATURE_SCHEME}
```

Everything else about `record_gate` stands, including P10's rule that a ledger write which fails is
printed and never raised.

### `asf/metrics/metrics.py` — the stream carries it through

`SCHEMAS['gates']` gains one optional key, so an old ledger line validates unchanged (P12):

```python
'signature_scheme': (('num', 'null'), None),   # which rule chose `signature` (F-0169)
```

and `gates_from_ledger` passes it on, `None` where the line predates it:

```python
ev = {..., 'signature': None if signature is None else str(signature)[:120],
      'signature_scheme': rec.get('signature_scheme')}
```

`natural_key` is not touched (P13), so re-reading a ledger appends nothing twice.

### `asf/scorecard/diagnose.py` — the key is the test, and a recurrence is counted once

```python
#: A unittest failure header — ``FAIL: <name> (<dotted id>)``. The dotted id alone is the cause:
#: it is canonical, it is what ``python3 -m unittest`` takes back, and it fits the 80-char cut
#: where the whole header does not (F-0169 C4).
UNITTEST_FAIL_RE = re.compile(r'^(?:FAIL|ERROR): \S+ \(([\w.]+)\)$')
#: The signature scheme a gate event with no ``signature_scheme`` was written under.
SCHEME_1 = 1


def _sig_class(sig):
    """A gate's failing line as one cause key: a unittest failure header as its dotted test id,
    then digits and hex dropped — one test, one class."""
    s = str(sig or '').strip()
    m = UNITTEST_FAIL_RE.match(s)
    if m:
        s = m.group(1)
    s = re.sub(r'\b[0-9a-f]{7,40}\b', '', s)
    return re.sub(r'\s+', ' ', re.sub(r'\d+', 'N', s)).strip()[:80] or 'unknown'
```

In `rank`, the gates loop counts occurrences into a set and executions into `red_runs`:

```python
    occurrences = {}
    for g in facts.gates:
        if not score.in_window(g.get('ts'), start, end):
            continue
        red = g.get('conclusion') != 'success'
        name = f"gate:{_sig_class(g.get('signature'))}" if red else 'gate:green'
        c = jobs.setdefault(name, {'name': name, 'minutes': 0.0, 'runs': 0, 'red': 0,
                                   'red_runs': 0, 'scope': PRODUCT})
        c['minutes'] = round(c['minutes'] + score._num(g.get('seconds')) / 60, 1)
        c['runs'] += 1
        if red:
            c['red_runs'] += 1
            # C5: one branch set, one day, one signature is one red however many ticks re-gate it.
            occurrences.setdefault(name, set()).add(
                (tuple(sorted(map(str, g.get('branches') or ()))), str(g.get('ts'))[:10]))
    for name, seen in occurrences.items():
        jobs[name]['red'] = len(seen)
```

`ci-job:` entries get `red_runs` equal to their `red` at their own `setdefault`, so the one detail
sentence serves both and a forge CI run — one per commit, each already distinct — is counted exactly
as it is today.

`metric` is not touched: it reads `c['red']` (P7) and inherits the occurrence count. That is the
number the card's acceptance is measured on.

The gate cause's detail names both numbers, so it can no longer read "2 of 7 runs red" about seven
red runs:

```python
            re_gated = ('' if c.get('red_runs', c['red']) == c['red'] else
                        f" over {c['red_runs']} red gate runs (a re-gate of the same branch's "
                        f"unresolved red counted once)")
            out.append(Cause(
                c['name'], PRODUCT, per_week, t['ci_red_per_week'], 'red runs/week',
                f"CI {c['name']} is red {per_week:g} times a week",
                f"{c['red']} of {c['runs']} runs red over {days} days{re_gated}, "
                f"{c['minutes']:,.0f} runner minutes; threshold {t['ci_red_per_week']:g}/week.",
                scheme=(max(schemes(facts, start, end), default=None)
                        if c['name'].startswith('gate:') else None)))
```

with the scheme read off the window's own red gates:

```python
def schemes(facts, start, end):
    """Every signature scheme the red gates in ``[start, end)`` were written under — empty when the
    window holds no red gate to ask. A gate event with no ``signature_scheme`` predates F-0169 and
    reads as scheme 1."""
    return {int(g.get('signature_scheme') or SCHEME_1) for g in facts.gates
            if score.in_window(g.get('ts'), start, end) and g.get('conclusion') != 'success'}
```

One helper, not two: "the scheme of this window" is `max(schemes(...), default=None)` at both its
call sites (the cause above, the reopen in §5), and "does this window still speak scheme *n*" is
`n in schemes(...)`. A second function wrapping the first would be one more thing to keep in step.

`Cause` gains the field, defaulted so every existing positional construction stands (P9, C8):

```python
@dataclasses.dataclass(frozen=True)          # frozen stands (P9) — the field is added, not the decorator changed
class Cause:
    key: str
    scope: str
    value: float
    threshold: float
    unit: str
    title: str
    detail: str
    #: For a ``gate:`` cause, the signature scheme its reading was taken under; None otherwise.
    #: Carried into the cause's state entry so a later verify can tell a real fall from a key that
    #: stopped existing because the gate started naming causes differently (F-0169).
    scheme: int | None = None
```

### `asf/scorecard/loop.py` — a key that stopped existing is not a win

`file_causes` records the scheme on the entry (P14 grows by one key):

```python
        state[cause.key] = {'n': 1, ..., 'card': None, 'verdict': None, 'log': [],
                            'scheme': cause.scheme}
```

and `verify`, between reading the two numbers and judging them, checks that the after-window still
speaks the scheme the reading was filed under:

```python
        filed_scheme = entry.get('scheme')
        if key.startswith('gate:') and filed_scheme is not None:
            after_schemes = diagnose.schemes(facts, landed, landed + span)
            if after_schemes and filed_scheme not in after_schemes:
                # C9: the key cannot recur under a scheme that no longer writes it, so `after` is a
                # 0 nothing measured. Record that, and do not reopen — the loop cannot know which
                # new key replaced this one.
                line = (f"- {as_of[:10]} scorecard: {key} scheme changed — {_fmt(before)} before, "
                        f"no comparable reading after (the gate's signature scheme moved from "
                        f"{filed_scheme} to {max(after_schemes)}; this key is no longer written)")
                enqueue_fn(entry['target'], {'kind': 'history', 'card': iid,
                                             'marker': entry['marker'], 'line': line})
                entry['log'].append(line[2:])
                entry.update(verdict='scheme changed', verified=as_of[:10], before=before,
                             after=None)
                done.append((key, 'scheme changed'))
                continue
```

An entry with no `scheme` (filed before this card) is left to the ordinary comparison — there is
nothing on the record to compare schemes with, and inventing one would change old verdicts.

`file_causes` is not the only place an entry is written. The **reopen** at the tail of `verify`
(`asf/scorecard/loop.py:383-386`) rewrites `state[key]` whole for a cause that didn't move, and a
`scheme` left off there would put a freshly filed gate cause straight into the no-scheme fallback
above — the silent close this card exists to stop, reintroduced one verify later. The reopen carries
the scheme of the window its new `baseline` was read over, which is the after-window it just
measured:

```python
            state[key] = {'n': n, ..., 'baseline': after, ...,
                          'verdict': None, 'log': entry['log'], 'reopens': iid,
                          'scheme': (max(diagnose.schemes(facts, landed, landed + span), default=None)
                                     if key.startswith('gate:') else None)}
```

So every entry the loop writes after this card carries a `scheme` — `None` only for a non-`gate:`
cause, or for a `gate:` cause whose window held no red gate to ask (P-none), which the clause above
already treats as "nothing to compare" rather than as a change.

The docstring's list of verdicts grows to name the fourth: `moved`, `didn't move`, `dropped`,
`scheme changed`.

### What this card does to its own verify

F-0169's own entry was filed under scheme 1 with `baseline: 3.5`, and gains no `scheme` key
retroactively — so the clause above does not fire for it, and it is judged the ordinary way against
a key that no longer exists: 3.5 before, 0.0 after, `moved`. That verdict is *arithmetically*
correct — the module-level key really does stop being written, which is the point of the card — but
it is not evidence that any test got less flaky. The honest reading, recorded here so the reviewer
and the verify both have it:

- `gate:--- test_tick_steps: FAILED (rc N)` reads 0 after landing because it is retired, not because
  a defect was fixed. The card's acceptance is met, and that is what meeting it means.
- what replaces it, over the same 14 days, is two keys at 0.5/week each —
  `gate:tests.test_tick_steps.PrsStepTests.test_harvested_and_at_trunk_branches_are_not_candidates`
  and `gate:tests.test_tick_steps.HarvestStepTests.test_finished_fix_branch_lands_through_the_tick`.
  Both are under 3.0, and either would file a card naming one test if it recurred.

## Stories

- S: A red gate's signature names the test that failed, not the module that carried it — `first_failing_line` ranks a specific failing line above the runner's `--- <module>: FAILED (rc N)` banner, and ranks that banner above a bare `FAILED (…)` so a module killed by the timeout still names its module — acceptance: `python3 -m unittest -v tests.test_harvest.GateSignatureTests`
- S: A unittest failure header becomes one cause key — `_sig_class` reduces `FAIL: <name> (<dotted id>)` to the dotted id, which fits the 80-char cut where the header does not, while a stored scheme-1 banner row still classes exactly as it does today so no history is migrated — acceptance: `python3 -m unittest -v tests.test_scorecard.GateOccurrenceTests tests.test_harvest.GateSignatureTests`
- S: Re-gating one unresolved red is one red — `rank` counts a red signature once per `(signature, branch set, UTC day)` and keeps the executions in `red_runs`, so the card's own window reads 1.0/week instead of 3.5 while `test_dry_run`'s eight separate branches still read 4.0/week, and the cause's detail names both numbers rather than claiming 2 of 7 runs were red — acceptance: `python3 -m unittest -v tests.test_scorecard.GateOccurrenceTests`
- S: The rule that chose a gate's signature is on the record — `harvest.SIGNATURE_SCHEME` is written into every new ledger line and carried through the `gates` stream as an optional field, so a line written before this card reads as scheme 1 and no stored event is invalidated or re-appended — acceptance: `python3 -m unittest -v tests.test_harvest.GateLedgerTests tests.test_metrics.GateStreamTests`
- S: A cause key that stopped existing is not read as a win — `verify` records `scheme changed` with the before-number and no after-number for a `gate:` cause whose after-window speaks only a newer scheme, and does not reopen it, while a genuine fall to zero and an entry with no scheme on it are both still judged the ordinary way; both sites that write an entry record the scheme — the first filing and the reopen of a cause that didn't move — so a reopened gate cause is still readable a cycle later instead of falling back to the ordinary comparison — acceptance: `python3 -m unittest -v tests.test_scorecard.SchemeChangeTests tests.test_scorecard.VerifyTests`
