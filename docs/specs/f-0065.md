# F-0065 — measure the fence before anyone stands behind it

A worker session today is fenced by one thing: the directories the launch path hands it.
`build_command` renders `-p --permission-mode bypassPermissions --add-dir <d>… --settings <file>`
(`asf/workers/runtime.py:98-110`), the mode's default is `bypassPermissions`
(`asf/workers/runtime.py:27`), and the grants come from the product's `job_grants` plus the row's
own (`asf/workers/spawn.py:703-708`). The harness's own help calls `--add-dir` *"Additional
directories to allow tool access to"* — tool access, not read access. So the only fence the factory
has is a grant, and the grant is a write grant. That is the card's first sentence, and it is true.

The harness has a second fence — sandbox mode — and nobody here has measured it. That matters more
than it sounds, because a worker session is not a session in a repository. Its cwd is a worktree
under the operator's state directory, while its gitdir is `<repo>/.git/worktrees/<job>` and its
object store is `<repo>/.git/objects` — both **outside** cwd. Its `origin` is an HTTPS URL at the
code host. Its `core.hooksPath` is a directory under the state dir (`asf.workers.githooks.ensure`),
so every `git commit` execs a script outside cwd. Its `$HOME` is its own, seeded, with
`<home>/.local/bin/asf` a symlink to the operator's CLI and `ASF_HOME` pointing back at the
operator's `~/.ASF` (`asf/workers/runtime.py:250-271`, `:363-390`). And its environment is an
allow-list of six names plus `LC_*` (`asf/hermetic.py:63-66`) — no proxy variable, no CA bundle,
unless the operator names one in `env_passthrough`.

Turn a filesystem-and-network fence on around that and the first thing that breaks is not the
browser engine. It is `git commit`.

This Feature does not build the fence. It **measures** it: for a coder, a reviewer and a prober, in
real sessions, which of the factory's tools break under sandbox mode and exactly what each role must
be granted to work. The output is a document with one table per role and a settings block per role,
and the launch-path card adopts it. Every line of code this Feature writes is throwaway.

## 1. Decisions

### 1.1 In

- **A probe set, one line per probe** (§2.1, §2.2) — fourteen probes covering the five tool classes
  the card names (version control over HTTPS, the code host's API, dependency installation, the
  browser engine, a product's development server) *and* four more the card does not name, which the
  preconditions above say break first: the worktree's own gitdir and object store, the commit hook
  path, the factory CLI under the session's HOME, and the approvals hook's write to the operator's
  state dir — plus the one file a prober session exists to write. Each probe prints
  `PROBE <id> <ok|refused|error> <one line>` and nothing else.
- **The pair discipline** (§2.3) — no cell of any table is filled from one run. Every "must be
  granted" claim is two runs of the same probe: refused without the grant, `ok` with it. A single
  green run is not evidence, because under `-p` *"settings files that fail validation are silently
  ignored"* (the harness's own help for `-p`): a mistyped sandbox key produces a session with no
  fence at all, in which every probe passes and the table reads as a clean bill of health.
- **A negative control in every table** (§2.3, §3.4) — two probes (`P00` a write outside every
  grant, `P01` egress to a host no grant names) that **must** read `refused`. A table whose control
  rows read `ok` is refused by the collector and never reaches the document.
- **The permission-mode question, measured first** (§3.5) — whether the fence survives
  `bypassPermissions`, the launch path's own default. If it does not, that single row is the most
  expensive finding in the spike, because it means the adopting card changes `permission_mode` for
  every role before it changes anything else.
- **A throwaway fixture product** (§2.4) — the dependency step, the development server on a loopback
  port and the headless-browser script live in a fixture the harness creates, not in any real
  product. The factory's own repository has none of those three tools, so without a fixture three of
  the card's five classes cannot be probed at all.
- **The environment's own hole** (§3.9) — `hermetic.WORKER_ALLOW` is
  `('PATH', 'LANG', 'TERM', 'TMPDIR', 'USER', 'SHELL')`. If the sandbox's network fence works by
  proxy, the variables that make a proxied egress work are exactly the ones the worker environment
  strips. The egress rows are therefore probed twice more: with and without those names in
  `env_passthrough`.
- **Three tables and three settings blocks** (§2.6, §2.7) — coder, reviewer, prober, each with its
  own probe set, its own verdicts and its own settings block, in `docs/research/sandboxed-worker-shell.md`.
- **An adoption list** (§2.8) — the section the launch-path card's author reads: what must change in
  the launch path for these settings to be deliverable per role, named by file and function, with
  the measurement behind each one.

### 1.2 Out

- **No file under `asf/` changes, and no test joins the suite.** The spike's whole footprint is
  `docs/research/sandboxed-worker-shell.md` and `tools/spike/f-0065/**`. A per-role settings file is
  a change to `asf/workers/spawn.py` and `asf/workers/runtime.py`; shipping it here would ship
  unverified plumbing *ahead of* the numbers that justify its shape, and the card says the launch-path
  card adopts the table.
- **Nothing is minted in the record.** No Bug for a tool the fence breaks, no Rule, no Decision card.
  The adoption list (§2.8) names each one as a line for the launch-path card's author, who mints it
  with an id from their own range.
- **No new metrics stream and no session record.** `metrics.STREAMS` is a closed, validated set, and
  these sessions are launched by hand rather than by the tick, so the pool never sees them. The raw
  evidence is the harness's own log files (§4).
- **The cloud lane is not measured.** `asf/workers/cloud.py` runs a session off this host, inside a
  fence this factory does not own and cannot set. The document stamps the one platform it measured
  and says so in as many words; a second platform is the adopting card's problem, not a silent
  generalisation here.
- **`--restricted` is not measured.** The harness carries a second, stronger fence — it removes the
  command-running tools outright and *"refuses bypassPermissions"*. A role that cannot run `git` is
  not a coder, a reviewer or a prober, so it is named here and left alone.
- **No probe writes at the far end.** No push that lands a ref, no pull request, no package
  published, no row in any shared system. §2.1 says how each probe reaches full authentication and
  full TLS without a side effect.
- **The document is not a contract.** It is findings, in `docs/research/`, with a stamp and a
  platform. It does not define a setting the factory must keep; it says what was true on one host on
  one day at one runtime version.

## 2. The design

### 2.1 The probe set

One script, `tools/spike/f-0065/probe.sh`. It runs inside a session (the brief tells the session to
run it) and it runs on the host unsandboxed, which is the control column. Each probe prints exactly
one line:

```
PROBE <id> <ok|refused|error> <at most one line, no secret value>
```

`refused` is the fence saying no; `error` is the probe itself broken (a missing binary, no fixture)
and is never read as a finding. The script's exit status is always 0: a probe that stops the script
loses every row after it.

| id | probe | the reach it needs | role |
| --- | --- | --- | --- |
| P00 | **control:** write a file at `$HOME/.f0065-control` | a write outside every grant | all |
| P01 | **control:** a TLS connection to a host no grant names | egress to an ungranted host | all |
| P02 | edit a tracked file in the worktree | a write inside cwd | coder, reviewer |
| P03 | `git commit -s --allow-empty` | a write to `<repo>/.git/worktrees/<job>` and `<repo>/.git/objects`, plus exec of the hook dir under the state dir (P5, P8) | coder, reviewer |
| P04 | `git ls-remote origin` | DNS + TLS to the code host, a read of `<repo>/.git` | coder, reviewer |
| P05 | `git push --dry-run origin HEAD:refs/heads/<scratch>` | the same, plus the credential helper's own shell exec reading `$GH_TOKEN` (P6) | coder, reviewer |
| P06 | the code host's API CLI, its rate-limit endpoint | TLS to the API domain, a read of the CLI's config under the session HOME (P7) | coder, reviewer |
| P07 | the factory CLI: one read-only view | exec of `<home>/.local/bin/asf` (a symlink out of the worktree) and a read of `$ASF_HOME` (P7) | all |
| P08 | a `Bash` call the approvals matrix classifies, so the hook writes its ledger row | a write under `$ASF_HOME/state/<product>` by a hook, not by the model (P14) | all |
| P09 | the product's test command | exec, a `TMPDIR` write, and a temporary git fixture with its own `hooksPath` | coder, reviewer |
| P10 | dependency installation inside the session | TLS to the package registry, a write to the package cache under HOME, a write in the worktree | coder |
| P11 | the headless browser engine: launch it, load `about:blank`, exit | exec of the engine from its cache under HOME, its own child processes and its own inner sandbox | coder |
| P12 | the development server: bind a loopback port, fetch it in the same session, stop it | a loopback bind and a loopback connect | coder |
| P13 | read the brief from the state dir and write the named side file | a read under `<state>/<product>/briefs`, a write at the one path the brief names | prober |

`P08` is the probe with the worst failure mode and the reason it is in the set. The approvals hook
fails **closed**: if the fence refuses the hook's own append, the hook does not merely lose a row —
it can refuse the call that triggered it, and a session whose every classified call is refused is a
session that does nothing and reports nothing. That is a table row, not a surprise for the adopting
card to find in production.

### 2.2 The harness

Four files under `tools/spike/f-0065/`, none of them imported by anything in `asf/`:

| file | what it does |
| --- | --- |
| `probe.sh` | §2.1. Takes a role name and runs that role's probes only. |
| `fixture.sh` | Creates the throwaway fixture product (§2.4) and prints its path. Idempotent; a second run reuses it. |
| `session.sh <role> <variant>` | Launches **one real session**: the role block rendered by `roles.block` plus the brief's tail telling it to run `probe.sh`, on stdin; `--settings settings/<role>.<variant>.json`; `--permission-mode` from the variant; `--add-dir` per the variant's grants; cwd the fixture worktree; the stream-json log to `<state>/spike/f-0065/<role>.<variant>.jsonl`, whose path is the one thing it prints on stdout. |
| `collect.py` | Reads every log, pulls the `PROBE` lines out of the assistant's own tool results, pairs the variants, and prints the three tables as markdown. Refuses a table whose `P00`/`P01` rows are not `refused`. |

`settings/<role>.<variant>.json` is the settings file per pair leg. The variant vocabulary is fixed:

| variant | what it is |
| --- | --- |
| `off` | no fence — the control column, and the leg that proves the probes themselves work |
| `bare` | the fence on, nothing granted |
| `grant-<n>` | `bare` plus exactly one grant (§2.5) |
| `mode-bypass`, `mode-default` | the fence on and nothing granted, under each permission mode (§3.5) |
| `grant-net`, `grant-net-passthrough` | the network grants, without and with the proxy/CA names in `env_passthrough` (§3.9) |

A pair is two legs that differ in exactly one thing, read for the same probe id.

### 2.3 The pair discipline, stated once

A row of any table is filled only when both legs exist in the logs:

```
P05 refused under <role>.bare      →  the reason string, verbatim, capped to one line
P05 ok       under <role>.grant-2  →  the grant that leg added, and nothing else
```

`collect.py` prints `unpaired` in the verdict column when one leg is missing, and `unpaired` is not
a finding — it is work left. The document carries the count of unpaired rows in its stamp, so a
partial spike is legible as partial instead of reading as a complete table with quiet gaps.

The two control rows are checked before anything else is printed. `P00 ok` or `P01 ok` in a leg
whose settings say the fence is on means the settings file was ignored (P11); `collect.py` exits
non-zero naming the leg, and the document gets no table from that run.

### 2.4 The fixture product

`fixture.sh` builds, under the state dir and outside every repository:

- a git repository with one commit, an `origin` pointing at a bare repository beside it (so `P03`'s
  commit and a local ref negotiation work with no host involved) — the code-host probes `P04`–`P06`
  use the **real** product's remote, read-only, because the question is reach to that host;
- a package manifest with exactly one dependency, so `P10` fetches from a real registry into a
  temporary cache and nothing is installed into any real tree;
- a development server: one script that binds a loopback port and answers one path (`P12`);
- a headless-browser script: launch, load `about:blank`, print the engine's version, exit (`P11`).

The engine's own download happens in `fixture.sh`, i.e. **outside** the session, deliberately: that
is what P10 says the tick already does for `worktree_setup`, and separating it tells the adopting
card which half of "dependency installation" needs a grant at all.

### 2.5 The settings template

One file per pair leg, filled from §3.10's reading of the harness's own settings surface. The
template carries the *slots*, not guessed key names (D2):

```jsonc
// tools/spike/f-0065/settings/coder.grant-2.json — every <…> filled from §3.10, never guessed
{
  "permissions": { "defaultMode": "<the mode §3.5 proves keeps the fence>" },
  "<the sandbox key>": {
    "<the enable key>": true,
    "<the filesystem grant key>": [
      "<repo>/.git",              // P5: the gitdir and the object store
      "<state>/<product>",        // P8, P13, P14: hooks, briefs, the ledger
      "<home>/.local/bin",        // P7: the factory CLI symlink
      "$TMPDIR"                   // P9: the suite's own fixtures
    ],
    "<the network grant key>": [
      "<the code host>",          // P04, P05
      "<the host's API domain>",  // P06
      "<the package registry>"    // P10
    ],
    "<the loopback key>": true    // P12
  }
}
```

Each leg adds exactly one entry over `bare`, so the pair that turns a row from `refused` to `ok`
names one grant and not a bundle. A grant that turns out to be unnecessary is a row in the table
too, in the "not needed" verdict — an over-granted fence is the failure this card exists to avoid.

### 2.6 The three tables

One table per role, generated by `collect.py`, with these columns:

| probe | needed by the role | under the bare fence | what must be granted | the pair |
| --- | --- | --- | --- | --- |
| `P03 git commit` | yes | `refused` — <the fence's own reason, one line> | the gitdir and the object store under `<repo>/.git` | `coder.bare` / `coder.grant-1` |

`needed by the role` is read off the role's own boundaries, not guessed: the coder builds and pushes,
the reviewer reads, runs the gate and writes one review file, the prober *"is read-only … writes the
readings file and nothing else, restarts nothing and reaches only what the brief grants"*
(`asf/roles/asf-prober.md`). The prober's table is expected to be the short one, and if it is not,
that is the finding.

### 2.7 The document

`docs/research/sandboxed-worker-shell.md`:

1. **The stamp** — the host OS and version, the runtime version, the date, the commit of this branch,
   the number of sessions launched, and the count of unpaired rows (§2.3).
2. **What the fence is** — the settings surface as §3.10 read it, with the one sentence about P11
   that explains why every row is a pair.
3. **Three tables** (§2.6), each opening with its two control rows.
4. **Three settings blocks** — the minimal working file per role, the real one, with every host and
   path written generically (`<the code host>`, `<state>`, `<repo>`) and no account name or machine
   path anywhere in it.
5. **The adoption list** (§2.8).
6. **The deletion** — the one line that says `tools/spike/f-0065/` is throwaway and names the card
   that removes it.

### 2.8 The adoption list

The section the launch-path card is written from. One row per change the measurements show is needed,
each naming the file and the function, and each citing the probe that showed it:

| what must change | where | the measurement behind it |
| --- | --- | --- |
| a settings file per role, not per pool | `asf/workers/spawn.py:598-606` (`settings_file`), `:721` | three different settings blocks in §2.7 |
| the permission mode the fence survives | `asf/workers/runtime.py:27`, `asf/workers/spawn.py:715-716` | the permission-mode pair (§3.5) |
| the grants the fence needs that `job_grants` does not carry | `asf/workers/spawn.py:703-708` | every `grant-<n>` leg that flipped a row |
| the names a proxied egress needs in the environment | `asf/hermetic.py:63-66`, `worker_pool.env_passthrough` | the environment-hole pair (§3.9) |
| the hook's behaviour when the fence refuses its own ledger write | `asf/hooks.py`, `asf/approvals.py` | `P08` |

Nothing in that table is minted as a card by this session (§1.2).

## 3. Acceptance tests

Every fence below runs from the repository root. The three that launch real sessions cost money and
need the account's credentials; §4 says which line the operator sees when they are absent.

### 3.1 The probe script runs, on the host, unsandboxed

```bash
bash tools/spike/f-0065/fixture.sh
bash tools/spike/f-0065/probe.sh coder | tee /dev/stderr | grep -c '^PROBE '
# every applicable probe prints exactly one PROBE line; no line reads ' error '
bash tools/spike/f-0065/probe.sh coder | grep ' error ' && echo 'FAIL: a probe is broken, not refused' || echo 'ok'
```

### 3.2 The controls are the controls

```bash
# unsandboxed, the two control probes MUST read ok — they are what a fence turns over
bash tools/spike/f-0065/probe.sh prober | grep -E '^PROBE P0[01] ok '
```

### 3.3 A real session runs and its probes come back

```bash
log="$(bash tools/spike/f-0065/session.sh prober off)"   # the script prints its log path
python3 -c "import json,sys; \
 lines=[json.loads(l) for l in open(sys.argv[1]) if l.strip()]; \
 res=[l for l in lines if l.get('type')=='result'][-1]; \
 print(res['subtype']); \
 print(sum(1 for l in lines if 'PROBE ' in json.dumps(l)), 'lines carry a PROBE result')" "$log"
# prints: success, then a non-zero count
```

### 3.4 The fence is proved on, and a table without it is refused

```bash
bash tools/spike/f-0065/session.sh prober bare
python3 tools/spike/f-0065/collect.py --role prober --require-control
# the two control rows read 'refused'; exits 0
python3 tools/spike/f-0065/collect.py --role prober --leg off --require-control; echo "rc=$?"
# the control rows read 'ok' in an unsandboxed leg, so the collector refuses it: rc=1
```

### 3.5 The permission-mode pair

  overwrites its own file and no other.
- **`<state>/spike/f-0065/fixture/`** — untracked: the fixture product, its bare remote, its

- **What is *not* written:** no card in any record, no row in any metrics stream, no session record
  in the pool (these sessions are launched by hand, so `asf/workers/lifecycle.py` never sees them),
  no change under `asf/` or `tests/`, and no ref pushed to the code host (D5).
- **Secrets:** no probe prints a token. `P05` and `P06` authenticate through the existing helper and
  the existing environment variable and print only the status. `asf.workers.runtime.mask` is the
  shape to follow for anything a probe's output carries into a file.

NEEDS OPERATOR: launching a real session spends money and needs the account's runtime credential.
`session.sh` refuses with `NEEDS OPERATOR: no runtime credential in this environment — set the
account's auth_env (<var>) and re-run: bash tools/spike/f-0065/session.sh <role> <variant>` when
none of `asf.workers.runtime.RUNTIME_AUTH_VARS` is set, rather than launching an unauthenticated
session and reporting its failure as a finding.

NEEDS OPERATOR: `P04`–`P06` reach the real code host read-only with the token the product's
`conventions.auth_env` already provides. Without it those three rows come back `error`, not
`refused`, and the coder and reviewer tables are incomplete in exactly that way — the stamp says so.

## Stories

Eleven Stories, in the order the design builds them: the instrument first (the probe set, the fixture, the settings surface, the launcher), then the two measurements that prove the fence is on and survives the launch path's own default, then one table per role, then the document. That is the order of the spec's own sections, and the order the plan's seven Tasks were cut from.

Each acceptance line below is one physical line of plain text, without backticks, on purpose. The record's reader is line-anchored (`asf.record.idcheck.CHECKBOX`) and blanks every inline code span before it parses a declared Story (`CODE_SPAN`, applied by `_prose` ahead of `declared_stories`), so a wrapped line reaches the minted card truncated and a line whose command lives inside backticks reaches it with the command missing. The commands are therefore bare, and each one is a line of section 3 above.
