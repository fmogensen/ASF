# F-0128 — the half of `decide_feature: auto` that is missing is the bound, not the policy

The card was written on 2026-09-24 against a factory in which `decided:` on a Feature was set only
by a human. That factory is four days gone. On the same day the card was filed, `be3cfdefc`
landed the approval classes `decide_feature`/`decide_bug`, the `decide_by_approval` policy, the
two example yamls and the guide rows; four hours later `3cc3741b8` ruled on the other half and
took it back out. So of the card's proposal, everything except one bullet is already on the trunk,
and re-specifying it would be re-writing code that works.

The bullet that is not there is the third one — *crosses no other approval class that is not
`auto` … so a pricing/payments/legal Feature still goes to the operator batched*. It was built
once, as keyword recognisers over a card's **title**, and it was removed by name: on the first
customer install **For you** read `379 for you`, mostly parity Stories whose titles contained the
word *payment* or *credentials*. The ruling in `3cc3741b8` is explicit — *deciding a card crosses
no approval class; the approvals hook guards the work* — and `tests/test_groom_policy.py:496` holds
it shut. Reading intent out of prose is settled, and this spec does not reopen it.

What is left, then, is the difference between *inferring* that a Feature is a money Feature and an
operator **declaring** it. A product already declares what a class recognises — `approval_signals:`
with `paths:` and `commands:` — and that mechanism never fires on a card nobody declared. This
spec adds the one declared field a Feature actually carries, `area:`, as a third recogniser key,
and hangs the bound off it. An operator who runs `decide_feature: auto` and writes
`approval_signals.spend_money.areas: ['billing']` gets exactly the card's sentence: every eligible
Feature decided by rule, the billing ones left as one operator question in one table. An operator
who declares nothing gets today's behaviour unchanged, and **For you** stays at zero.

The second thing missing is smaller and more embarrassing: the card's acceptance sentence has never
been run end to end. Every piece is unit-tested in isolation; no test starts from a record and a
product file, runs a gated groom, and asserts that the cards come out `decided: true` **and** that
the feeder then offers `CARD → SPEC` for them. That sentence becomes one test file.

And the guide is wrong. `docs/guide/product-config.md:592-597` still tells an operator that "a card
whose title reads as money, security, production, customer data or legal … is answered by nobody
but you" and that "an auto-filed Bug is exempt from the title recognisers". Neither has been true
since `3cc3741b8`. An operator turning on `decide_feature: auto` reads that paragraph to find out
what will be left for them, and it describes a bound that does not exist.

## The design

### 1. `approval_signals.<class>.areas` — a third declared recogniser (`asf/approvals.py`)

`signals()` accepts one more key. Its validation set becomes `{'paths', 'commands', 'areas'}` and
its per-class dict gains `'areas': list(spec.get('areas') or [])`. Every other key still raises
`ConfigError` naming the offending keys, unchanged.

`recognisers()` lists them beside the others, so `asf approvals` prints them in its `recognisers`
column and `check_doctor` counts a class with only declared areas as recognised, not blind:

```
words += [f'signal area: {a}' for a in spec.get('areas') or []]
```

A new function, shaped on `path_class` (P12):

```python
def area_class(product, area):
    """``(class, level)`` of the first class in catalogue order whose declared
    ``approval_signals.<class>.areas`` matches ``area`` (case-insensitive fnmatch) and whose level
    is not ``auto``, or ``None``. The two classes the groom itself reads (``decide_feature``,
    ``decide_bug``) are skipped: an area declared under them would bar the card from the policy
    those classes switch on (D5)."""
```

It fails soft the way `path_class` does — a `ConfigError` out of `signals()` is caught and read as
"no declared areas", since a groom that cannot parse the config must still render a file.

What it looks like when it is there, in a product yaml:

```yaml
approvals:
  groom: auto
  decide_feature: auto
  spend_money: human-now
approval_signals:
  spend_money:
    paths: ['billing/*']
    areas: ['billing', 'pricing', 'payments*']
```

and in `asf approvals`:

```
class          level      from    read by  recognisers
spend_money    human-now  default hook     signal path: billing/*; signal area: billing; signal area: pricing; signal area: payments*
decide_feature auto       yaml    groom    the groom's decide_by_approval policy, over undecided Features
```

### 2. The bound reads it (`asf/groom/policy.py`)

`BARRED` is untouched — it keeps its one `new_epic` row and its documented purpose (F-0031 extends
it as data). `barred()` gains a second clause after the `BARRED` loop, reached only when the answer
under test is a decide:

```python
def barred(answer, item, product):
    ...
    for key, predicate in BARRED:
        if predicate(answer, typed) and str(approvals_map.get(key, '')).lower() != 'auto':
            return key
    if answer.field == 'decided' and answer.value is True and typed.get('area'):
        from asf import approvals          # local: the module-level rule (P16)
        hit = approvals.area_class(product, str(typed['area']))
        if hit is not None:
            return hit[0]
    return None
```

The `level_of` call inside `area_class` is what applies the "that is not `auto`" half, so a product
that maps `spend_money: auto` is not barred by its own declaration — the same rule `path_class`
follows.

A card with no `area:` is never barred, which is what exempts auto-filed Bugs without a special
case: the Bug filer writes `signature:`, `count:` and `last_filed:`, never `area:`.

When it is there, a groom file line reads:

```
- [ ] F-0131 Usage-based pricing for teams — undecided 5d → answer: ____ (barred: approvals.spend_money)
```

and `run_policy_pass` returns it in `barred_count`, `digest.render_digest` lifts it into **For you**
as `NEEDS OPERATOR: F-0131 — undecided 5d; approvals.spend_money is not auto.`, and
`step_wave._operator_owned` keeps it off the adjudicate session's list (P14) — all three through
code that already exists and needs no edit.

### 3. The end-to-end acceptance (`tests/test_decide_feature_auto.py`)

One new file, no production code. It builds a temp record with an `E-0001` that is open and
decided, and under it:

- `F-0001`, undecided, no spec, no area → decided by rule, and `CARD → SPEC` on the next pass;
- `F-0002`, undecided, stage `spec-approved`, no plan → decided, and `STARVED → PLAN` (D10);
- `F-0003`, undecided, `area: billing`, with `spend_money: human-now` declared over `billing` →
  **not** decided, and a `NEEDS OPERATOR` line in the day's digest;
- `F-0004`, undecided, under an Epic that is itself undecided → not decided;
- `F-0005`, undecided, superseded by a decided card → closed, not decided;
- `B-0001`, undecided, with `decide_bug` left at `human-now` → not decided.

It runs `cmd_groom` once with `approvals: {groom: auto, decide_feature: auto, spend_money:
human-now}`, then asserts against the **record on disk** (typed field plus History line), against
`groom/<date>-digest.md`, and against `feeder.rows.candidates` over the reindexed record. It runs
`cmd_groom` a second time for the same date and asserts nothing further is applied — the idempotence
`apply_groom_answers` promises.

### 4. The guide and the example (`docs/guide/product-config.md`, `docs/products.example.yaml`)

The stale paragraph at `product-config.md:592-597` is replaced with what the bound is now: a new
Epic, plus any class the product has declared `areas` for. The auto-filed-Bug sentence goes with
it — an auto-filed Bug carries no `area:` and needs no exemption. The `approval_signals` example
block gains `areas:`, and the `decide_feature` row gains the sentence P17 says is missing: it does
nothing unless `approvals.groom: auto` is also set. `docs/products.example.yaml` gets the same
`areas:` line in its commented `approval_signals` block and a pointer on the `decide_feature` line.

No new record state, no new `~/.ASF` state, no schema change, no new command, no migration.
