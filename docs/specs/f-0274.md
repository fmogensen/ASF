# F-0274 — the Feature went quiet, and the row that was meant to speak stepped aside

`asf next` drops every Task row of a Feature that has a live session of its own. A replan, a
spec-amend or a correction on the Feature puts its id in `busy` (`inflight_ids`, `:332`), and
`_one_feature_rows` returns before `task_rows` is reached (`asf/feeder/rows.py:1513`) — unless the
stories-first gate holds the Feature, which is the card's one exemption and stays one
(`needs_stories`, `:1514`; P15, C12). Seen 2026-10-07 on a product: F-0003's
rank-1 decided Task T-37153 had no row at all while `replan-f-0003` **and its correction** sat in
needs-input, and nothing in the table said why.

Half of that is already closed. The hotfix F-0285 landed `held_feature_row` and the
`FEATURE → HELD` row on 2026-10-07 at 23:43 (`73d7a2a71`), hours after the card was filed and
without the card's spec: a held Feature now gets one non-launching row, `WAITS ON <job> (<kind>)`,
whose reason names the open Tasks it holds. For a Feature whose session is *only* a session, the
card is served.

The other half is not, and it is exactly the shape the card saw. `held_feature_row` steps aside
when the occupancy names the Feature under `review`, `landing` or `corrections`
(`asf/feeder/rows.py:1602`) — deferring to the row it expects those to produce. For a correction
that row can never be produced: `correction_rows` drops every correction whose item is busy
(`:984`), and `held_feature_row` is only ever reached *because* the Feature is busy (`:1513`). So
the guard fires precisely when the thing it defers to has already stepped aside too, and the
Feature, with every one of its open Tasks, leaves the table in silence. Measured in this worktree
(P3): the Feature and all four of its open Tasks have **zero** rows.

Nothing notices. The factory has a counter for the one other silence it has been bitten by —
`orphaned_pushed`, and the `pushed work` row of `asf doctor` (P9) — and none for this one. The
card went a day unseen for want of that row.

### In

1. **One guard, over what is actually drawn.** `held_feature_row` steps aside for exactly one
   reason — another row already speaks for the Feature — and that is read from the rows already
   drawn (`spoken`), not guessed from occupancy keys. `spoken` is threaded from `_candidates`
   through `feature_rows` and `_one_feature_rows`.
2. **The silence is counted.** `rows.silent_features(index, rows, occupancy, inflight)` — every
   Feature in build with an open Task whose work has no row anywhere — and one `silent work` row
   in `asf doctor`, off the same draw of the plan the `pushed work` row already uses.
3. **The regression**, from the card: a Feature in build whose own session runs *and* carries a
   correction keeps one row that names what holds it and which Tasks wait, and the counter is
   empty once it does.

### Out

- **The Task rows are not restored.** One row for the Feature, naming the Tasks it holds, is the
  shape F-0285 landed and the shape this card keeps: N rows that all say "waits on the same
  session" is the noise the held row was written to avoid. The card asks for a reason, and the
  reason is one line.
- **No change to `correction_rows`, `lane_rows` or `pushed_rows`.** A correction on a busy item
  getting no row is deliberate — one session per branch — and this card does not make it a row. It
  stops the *Feature* from going silent because of it.
- **No new invariant in `asf/invariants.py`** (P12): a missing row has no subject to drop, and the
  counter is a `doctor` row, like `pushed work`.
- **No refusal and no hold.** The `silent work` row is a label. Nothing is blocked, nothing is
  filed, no card is minted by it.
- **`holder_of` keeps reading occupancy only.** With a fixture that passes `inflight` and no
  occupancy the row degrades to `WAITS ON a session (session)`; in the tick every live item is in
  `occupancy['busy']` as `session <job> running` (`asf/workers/lifecycle.py:1451`), so the row
  names the job. An `inflight` fallback is plumbing for a case the factory does not have.
- **The `review`/`landing` keys are not kept as a belt.** P6 proves them unreachable and P8 proves
  they never had `lane_rows` to defer to; `spoken` covers the reachable case (a Feature a lane or
  correction row really spoke for) and leaves the later `pushed_rows` row to the id it skips.
- **Nothing read about the session's state.** Running, needs-input, or finished-unharvested all
  hold the Feature the same way; the row says who holds it, not how it is doing.
- **The `needs_stories` gate arm is not touched** (P15). The card names it as the one exemption
  and it stays one: a Feature the stories-first gate holds draws its Task rows while its own
  `spec-amend` runs, because those Tasks still build. Such a Feature has no row of its own and no
  held row, and it is not silent either — its Tasks speak for it, and the counter reports total
  silence only (C5). `spoken` is not threaded into that arm (C12).
- **Each Task's own wait is not carried onto the held row.** The four Tasks of P17 all said
  `WAITS ON replan F-0090`; the held row says that once, as `WAITS ON <job> (<kind>)`, and names
  the ids it holds (C13).
- **No new command, no new state file, no new convention, no operator question.**

## The design

### 1. The guard — `asf/feeder/rows.py`

```python
def held_feature_row(items, feature, occupancy, spoken=()):
    """The one non-launching row of a Feature its own session holds (F-0274): ``WAITS ON <job>
    (<kind>)``, naming the open Tasks it holds. None when it holds no open Task, or when a row
    already drawn speaks for the Feature (``spoken``: the ``item_id`` of every row drawn before
    :func:`feature_rows` — a correction's, a lane's, a branch's, a groom's).

    ``spoken`` is the rows, never the occupancy. A Feature is only held here because it is busy,
    and :func:`correction_rows` drops every correction whose item is busy, so a ``corrections``
    key is not a row and a Feature that stepped aside for one left the table in silence with every
    one of its open Tasks (the live case: a product's F-0003, 2026-10-07, its replan session and
    the correction on it both in needs-input). ``review``/``landing`` need no test either: such a
    Feature is subtracted from ``busy`` before :func:`feature_rows` sees it (``docs_waiting``), and
    :func:`pushed_rows` draws its ``PUSHED → LAND`` row."""
    fid, occ = feature['id'], occupancy or {}
    if fid in set(spoken or ()):
        return None
    held = [t['id'] for t in ix.feature_tasks(items, feature) if is_open(t)]
    ...
```

The rest of the body is unchanged. The one call is the `else` arm of `if fid in busy:`, and the
`gate` arm above it is untouched (C12):

```python
    gate = needs_stories(items, product, f)
    if fid in busy:
        if gate and word in BUILD_STAGES and not plan_carrier(f) and not replan_mod.pending(f):
            # the Feature's own spec-amend session is running: its Tasks still build
            out.extend(task_rows(items, product, f, busy, running, landed_shas))
        else:
            # F-0274: the Feature's Task rows are held while its own session runs — say so, on
            # one row, rather than every open Task vanishing from the table with no reason
            row = held_feature_row(items, f, occupancy, spoken)
```

`spoken` is threaded, with the same default, through the two functions above it:

```python
def feature_rows(items, product, busy, running, landed_shas=None, occupancy=None, spoken=()):
def _one_feature_rows(items, product, f, busy, running, landed_shas, occupancy, spoken=()):
```

— both `_one_feature_rows` calls in `feature_rows` pass it on (the blocked branch included), and
the one call site in `_candidates` gives it the rows drawn so far:

```python
    rows += feature_rows(items, product, (busy - docs_waiting) | tasks_spoken, running,
                         landed_shas, occ, {r.item_id for r in rows})
```

Nothing else in the module changes. The new row cannot double up with a later one: both
`unverified_rows` (`:2588`) and `pushed_rows` (`:2590`) are already given every drawn `item_id` to
skip, which is how the landed `FEATURE → HELD` row already behaves.

### 2. The counter — `asf/feeder/rows.py`, beside `orphaned_pushed`

```python
def silent_features(index, rows, occupancy, inflight):
    """Every Feature in build whose work has no row at all — the invariant ``asf doctor`` counts
    (``silent work``); ``[]`` whenever the feeder speaks for it.

    A decided, open Feature whose stage word is in :data:`BUILD_STAGES`, that has at least one
    open Task, where no row in ``rows`` is the Feature's or one of those Tasks', and where nothing
    live or waiting to land holds one of those Tasks (:func:`live_ids` and the occupancy's
    ``waiting_landing``): work in flight is shown by the lane and the sessions, and a Task left to
    the lane never had a row here (:func:`task_rows` rows a New Task only).

    A live session on the **Feature** is no excuse: that is exactly when its Tasks vanish, and
    :func:`held_feature_row` is the row that must then speak (F-0274)."""
```

Returns the sorted Feature ids. It reads `items_of(index)`, `ix.of_type`, `ix.feature_tasks`,
`is_open`, `BUILD_STAGES` and `live_ids` — all already in the module.

It needs no arm-by-arm knowledge of `_one_feature_rows`, because it reads the drawn rows: the
`gate` arm's Task rows count as rows (P15), and so does the `PLAN → CODE` resume row `branch_rows`
draws for every Active Task of a held Feature (P16). What is left to count is a Feature whose open
Tasks are the ones `task_rows` owns and whose held row did not speak — the card's case.

### 3. The doctor row — `asf/doctor.py`

```python
def silent_work_line(silent):
    """``(ok, detail)`` for the silent-work invariant: red while a Feature in build with open Tasks
    has no row in ``asf next`` at all (:func:`asf.feeder.rows.silent_features`)."""
```

green: `silent work: every Feature in build with open Tasks has a row`
red: `silent work: 1 Feature in build whose open Tasks have no row — asf next says nothing about
them: F-0003`
(the first eight ids, then `+N`, as `pushed_work_line` does).

`check_pushed_work` becomes `check_plan_silence(product)`, same body up to the draw, yielding
`[(label, ok, detail)]`: `('pushed work', *pushed_work_line(orphaned_pushed(...)))` then
`('silent work', *silent_work_line(silent_features(...)))`. `[]` when there is no record yet; on an
unreadable plan, the one row it yields today, unchanged:
`('pushed work', None, f'pushed work: cannot draw the plan — {e}')`. The call site (`:1701`)
becomes:

```python
    for label, ok, detail in check_plan_silence(product):
        rows.append((label, False, ok, detail))
```

### 4. What it looks like when it is there

The card's Feature, its replan session and the correction on it both in needs-input:

```
earlier  PLAN → CODE      T-37153 WAITS ON replan F-0003     (and one such row per open Task)
before   (no row for F-0003, and none for T-37153 or any other open Task)
after    FEATURE → HELD   F-0003  WAITS ON replan-f-0003 (replan)
                          F-0003 is held by replan-f-0003 (replan): its open Task(s) T-37153,
                          T-37154 wait for it
```

The `earlier` line is the card's "a Task that showed `WAITS ON X`": the row each open Task carried
while the `reshape:` sat unanswered. `before` is what it turned into when the replan session took
it up and a correction landed on the Feature beside it (P17) — the invisibility the card reports.
`after` is one row that says the same thing once, and names every Task it holds.

and `asf doctor`, had the row not been there:

```
silent work   1 Feature in build whose open Tasks have no row — asf next says nothing about
              them: F-0003
```

Once the row is drawn, that line reads `silent work: every Feature in build with open Tasks has a
row`, and the `pushed work` row beside it is byte-identical to today's.
