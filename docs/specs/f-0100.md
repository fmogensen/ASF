# F-0100 — the savings pass, and the measurement it needs first

D-0050 says every saving the factory can see becomes a card with a number behind it. The card
names six signals and the card each one files. Five of the six can be read off the streams the
record already writes. One thing none of them can be read against:

> First measurement to build, because the record cannot yet answer it: minutes and dollars **per
> landed change**, per kind.

That is the true state of the record today. `metrics/sessions` knows what a session cost
(`minutes`, `usd`, `in_tokens`, `turns`) and `metrics/ci` knows what a CI run cost, but nothing
in the record says **which work reached the trunk**. The fact exists — `harvest.mark_harvested`
writes `harvested: <sha>` onto the run in the session registry
(`asf/harvest/harvest.py:194`, read by `asf/workers/lifecycle.py:246`) — and it never crosses
into the record. Nor does the gate: the landing gate runs in a detached process with no record
clone (`asf/tick/step_harvest.py`), so how long it ran and what it said is in nobody's stream.

So this spec is in two halves. The first builds the two measurements the card's signals stand
on — **a landing** and **a gate run** — as two streams beside `ci`, `sessions` and `ticks`. The
second is the pass itself: six detectors over the streams, run as a part of the `daily` step
before the rollup renders the page, each filing one card that carries the reading, the window,
the expected move in percent and the measurement that will prove it — and a `## Savings` block on
the scorecard that re-reads each filed card's own measurement and says **kept** or **reverted**.

Everything below is against this branch's base, `2c39ede`.

## 1. Decisions

### 1.1 In

- **`metrics/landings`** — a new stream. One event per run that landed: the job, the lane branch,
  the kind, the item, the sha, timed by the **trunk commit's own committer date**. Written by the
  record step's backfill out of the session registry, which already is that step's other source
  (`metrics.sessions_from_registry`).
- **`metrics/gates`** — a new stream. One event per landing gate: when it started, how many
  seconds it ran, the branches under it, green or red, and — on red — the first failing line as a
  **signature**. Fed by a new append-only ledger `~/.ASF/state/<product>/gates.jsonl`, written by
  the two places a landing gate runs (`harvest.land_ff`, `harvest.gate_groups`), read by the same
  backfill.
- **`asf/savings/landed.py`** — the join, and the card's first measurement: one row per landed
  change carrying its sessions, rounds, session-minutes, gate-minutes, dollars and input tokens,
  and `per_kind()` over those rows — the median minutes, median dollars, median gate minutes and
  mean rounds **per landed change, per kind**.
- **`asf/savings/signals.py`** — the card's six signals, one detector each, each returning the
  same `Signal`: the class, the subject it names, the reading, the window, the threshold, the
  expected move in percent, and the measurement that re-reads it.
- **`asf/record/propose.py`** — file or bump a card keyed on its typed `source:`, in the
  `file_bugs` shape, at the level `approvals.level_of(product, 'propose_improvement')`. It belongs
  to the record, not to either pass that calls it (§1.4).
- **`approvals.CLASSES`** gains `propose_improvement`, default `groom` — the class F-0091's spec
  names, in the words that spec names it in (§1.3, P15).
- **`asf savings`** — the command: compute, print the class table, propose. `--day`, `--window`,
  `--json`, `--dry-run`.
- **The `daily` step's fourth part**, `savings`, between `file-bugs` and `rollup`
  (`asf/tick/step_daily.py:154`) — the cards it files are in the index the rollup then reads.
- **The scorecard** gains a `## Cost per landed change (7 days)` table, a `landing cost` row in
  the waste table, and a `## Savings` block: card, class, expected, baseline → now, verdict.
- **`conventions.savings`** — one typed dict field with documented defaults: the window, the
  landings floor and the six thresholds.
- **`SCHEMAS['ticks']`** gains `steps` and `product` — the two keys `tick.write_tick_line`
  already writes and the schema does not declare (P6). Signal 4 reads `steps`; it may not read an
  undeclared key.
- **`tests/test_savings.py`**, and the additions named in §3 to `test_metrics`, `test_harvest`,
  `test_tick_steps`, `test_conventions` and `test_cli`.

### 1.2 Out

- **Rewriting an event already on disk.** `append_event` is keyed and append-only
  (`metrics.py:290`): a `sessions` event written the tick a session ended is never revisited, and
  the landing it earns an hour later could not be written onto it (P3). That is *why* a landing is
  its own event and not a field on the session. No existing stream changes shape.
- **Backfilling landings that predate this change.** Every landing the registry still carries is
  recovered — its time comes from the trunk commit, which is still there (§2.1). A landing whose
  run the registry has forgotten, or whose sha is no longer in the trunk, is not invented: it is
  skipped, and the pass says how many it skipped.
- **A card the pass files acting on anything.** The pass measures and proposes. Nothing it writes
  stops a launch, changes a model, splits a suite or edits a brief. The card it files is work for
  a session to plan, exactly like any other Feature.
- **Filing a Bug.** A savings card is a Feature. Defects already have a filer — `file-bugs`,
  three sources, `auto` by default — and the two must not cross: a red gate files a Bug today at
  two in 24 hours, and signal 6 files a *failure-class* Feature at three in seven days (§1.4).
- **Changing `file_bugs`.** Its three sources, its thresholds and its `auto` default are
  untouched. The `gates` stream is a fourth source nobody added to it.
- **Deciding the six cards' content.** Each card names the reading, the window, the expected move
  and the measurement. What to *do* about it — which preamble fact to add, how to split the suite,
  which model to route to — is the spec session that picks the card up. A proposal that wrote the
  fix would be a plan, not a proposal.
- **Vendor model names.** Signal 5's card names the model id as the record already carries it
  (`sessions.model`), in the card's body, in the operator's record. No id is written into a
  tracked file of this repo (`tools/check_generic.sh`).
- **A page of its own.** F-0091's `improve/<date>.md` is that page and this pass does not write a
  second one. The savings pass's output is the scorecard's two new sections and the cards.
- **The weekly `improve` pass itself.** F-0091 is specced and planned and is not in the tree
  (P15). This spec does not build it, re-specify it, or wait for it (§1.4).

### 1.4 The choices

| Choice | Chosen | Against | Why |
|---|---|---|---|
| What "a landed change" is | one **run whose registry record carries a `harvested` sha** — a lane that reached the trunk | a merged PR; a trunk commit naming an item; a card reaching Done | The three alternatives each drop work the factory paid for. A trunk commit is one commit of a lane that may have taken six sessions; a card reaching Done can happen by a groom. The harvested run is the unit the factory actually spends against, and it is the unit the gate gates. |
| Where the landing's **time** comes from | the trunk commit's committer date for the harvested sha (`git show -s --format=%cI`) | the run's `ended`; a new `harvested_at` written into the registry | The registry's mark carries no time (P5) and the sessions that earned the landing ended before it. The commit date is the moment the change entered the trunk, it is exact, and — decisively — it is **still there for every landing already marked**, so the measurement answers the question on the day it lands instead of a week later. |
| A landing the trunk cannot confirm | skipped, counted, and named in the pass's output — never written | write it with the session's `ended`; write it with `ts: null` | A sha that is not in the trunk did not land there (a superseded branch, a rewritten history). The registry keeps the record, so a landing skipped because the fetch was stale is written by the next tick that can see the sha. Nothing is lost by waiting and something is invented by guessing. |
| Landing as its own stream, not a field | a `landings` event | `landed: true` on the `sessions` event | The session's event is written the tick the session ends; the landing happens later, and an event on disk is never updated (P3). A `landed` field would read `false` for ever. This is not a preference — it is the only shape the writer allows. |
| Gate runs into a stream of their own | `metrics/gates` | a `ci` event with a `source: gate` key | Folding a local gate into `ci` silently changes three readings that already exist — the runner-minutes row, its "useful %", and `file_bugs.ci_signatures`, which would start filing a Bug for a red the correction already handed back to its session. A stream of its own has one writer and two readers and changes nothing that is already true. |
| How the gate's numbers leave the detached process | an append-only `gates.jsonl` in the state dir, read by the record step's backfill | `ctx.event('gate', …)`; the existing `harvest.json` | The gate has no record clone and no `ctx` (P9), and `harvest.json` is a status file rewritten each run — a ledger of one is not a ledger. An appended line beside `sessions.jsonl` is the pattern `mark_harvested` already uses in the same directory. |
| Where a combined gate's minutes go | split evenly over the branches under it | charged whole to each branch; charged to the first | `compute_costs` already splits a CI run's minutes over the items it names (`metrics.py:356`) — the same rule, so the two tables add up the same way. Charging it whole would make one gate over six branches read as six gates. |
| When the pass runs | a **part of the `daily` step**, before `rollup` | its own step with its own stamp (the shape F-0091 chose for `improve`) | The card says the `daily` step, and the code says why that is right here: the savings block and the landing table are rendered by `cmd_rollup`, which is the *next part of the same step*, and a card filed by an earlier part is in the index the rollup reads (P2). A separate step would render yesterday's proposals. The two objections to a part — it cannot be run alone, it cannot be timed — are answered by `asf savings` and by `run_part`'s own per-part line (P1). |
| What decides filing | `approvals.level_of(product, 'propose_improvement')`, default `groom` | reusing `file_bug`; a `savings.autofile` switch | `file_bug` is `auto` and is about defects; a pass that proposes work must not ride into the record on it. The approval matrix is the one file an operator widens, and the three levels are exactly the three ways a proposal can be handled: filed, put to the groom, or held for a person. |
| Who owns the filer | `asf/record/propose.py` — beside `record/ids.py`, which it uses | `asf/savings/propose.py`; `asf/improve/propose.py`, imported from here | Filing a card keyed on `source:` is a record primitive, not a property of whichever pass proposes. Naming it after neither pass is what lets F-0091's `improve` and this pass file through one writer, in one shape, with one set of tests — whichever of the two lands first. |
| The relationship to F-0091 | **no dependency either way.** This spec builds the measurements, the six signals, the daily cadence and the scorecard block; F-0091 builds the weekly pass, its page and its own four classes. The two pieces both need — `propose_improvement` and the `source:` dedupe — are specified here in the exact words F-0091's spec uses, so the second to land finds them already there | making this Feature wait for F-0091; re-specifying `improve` here | F-0091 is planned and unbuilt (P15); blocking on it would leave the card's measurement unbuilt too. Duplicating its pass would be worse. Naming the shared pieces identically, in a module owned by neither, costs the second lander one import. |
| The dedupe key's shape | `source: savings:<class>:<subject>` — the subject is the kind, the step or the signature the card names | `savings:<class>` alone | Four of the six signals can fire for more than one subject at once: two brief kinds over the ratio, two steps slow. One card per class would rewrite the same card with a different subject every day. |
| Signal 5's threshold | the median **× a ratio** (default 1.5), not the bare median | the card's literal "above the median" | Half of the kinds are above the median of the kinds by construction, every day, for ever — the bare median cannot be a threshold, only a ranking. A ratio makes it the outlier test the card means. Signal 1's "by 2×" is already written that way and keeps its 2.0. |
| A floor under the pass | `min_landings` (default 5) in the window: below it the pass reads, prints and proposes nothing | no floor | A median over two landings is not a reading, and a factory's quiet week must not file six cards about itself. | The expected move | computed, not chosen: `round(100 × (reading − threshold) / reading)` — the move that brings the reading back to its own threshold | a per-class constant; a human estimate at filing | The card asks for "the expected move in percent", and a number the pass can defend is one it derived from the two numbers already on the card. A constant would be a guess, and a guess in a field named *expected* is what makes the savings block worthless. |
| How the savings block re-reads a card | by re-running the card's own detector, named in its typed `measurement:` | parsing the card's prose; storing a shell command | The detector is the measurement. A card that names its class is re-read by one dict lookup, and a class the code no longer has is reported as `unmeasurable` rather than silently green. |
| The verdicts | `open` (the card is not closed), `kept` (closed, reading at or below target), `reverted` (closed, reading above target) | the card's two, with a third `slipped` band between target and baseline | The card asks for kept or reverted, and a third band would only move the argument to where its edges are. `open` is not a verdict, it is the absence of one, and the block says so. |
| Signal 6 against `file-bugs` | 3 occurrences in **7 days** files a **Feature** (the invariant that would end the class, F-0087); `file-bugs` keeps filing its **Bug** at 2 in 24 hours for the defect | let `file-bugs` cover it; make signal 6 file a Bug too | Two different claims about one red: *this build is broken* (a Bug, today) and *this class of red keeps costing us, and an invariant would end it* (a Feature, this week). The gate stream is not a `file_bugs` source, so neither filer sees the other's trigger. |
| Where the savings numbers live | typed fields on each card (`baseline`, `target`, `expected_pct`, `measured`, `verdict`), read back out of `index.json` | a `savings/history.jsonl`; a fourth stream | The index already carries every typed and machine field (P2), so the scorecard block costs the rollup nothing it does not already read. A ledger would be a second copy of numbers the cards must carry anyway. |
| `ticks.steps` in the schema | declared, as `list` with `[]` and `str|null` for `product` | read it as the undeclared key it is today | Signal 4's whole input is that key. A metric standing on a field the schema would reject (P6) is one `metrics append` away from a stream the validator disagrees with. Declaring the two keys the writer already writes is two lines and makes the reading legitimate. |

## 2. The design

### 2.1 `metrics/landings` — one event per landed change

Schema, joining `SCHEMAS` in `asf/metrics/metrics.py`, and `'landings'` joining `STREAMS`:

```python
'landings': {
    'ts': (('str',), REQ),                 # the trunk commit's committer date, UTC
    'job': (('str',), REQ),                # the run that landed
    'sha': (('str',), REQ),                # the sha it landed at
    'branch': (('str', 'null'), None),     # the lane branch — the join key
    'kind': (('str',), MATCH),             # session_kind(record): spec | plan | code | fix | …
    'item': (('str', 'null'), MATCH),      # the card it landed for
    'item_reason': (('str', 'null'), None),
},
```

`natural_key('landings', ev)` is `(ev['job'], ev['sha'])` — a job lands once at one sha, and a
combined gate landing six branches at one sha is six events, one per job.

`validate` gains a third branch before its `ticks` arm (P7): `kind` falls back to
`session_kind`'s mapping and must be in `KINDS`; `item` is matched exactly as a `sessions` event's
is; `ts` is required rather than `TS`, because a landing's time is never "now".

`metrics.landings_from_registry(product, items=None, known=(), state_path=None, repo=None)`
returns the events, beside `sessions_from_registry` and reading the same registry:

1. For every run in `lifecycle.runs(registry)` with a `harvested` sha that is not
   `harvest.SUPERSEDED` and whose `(job, sha)` is not in `known` (the shas the stream already
   holds).
2. `ts = _git(repo, 'show', '-s', '--format=%cI', sha)` → `iso(parse_ts(...))`. `None` (the sha is
   not in this repo) → skipped, counted as `unconfirmed`.
3. `kind = session_kind(record)`, `branch = record.get('branch')`, `item` as `session_event` takes
   it (`ID_RE`, and in the index or left to the matcher).

`cmd_backfill` calls it after the sessions loop, prints `landings appended: n` and, when any were
skipped, `landings unconfirmed: n (sha not in the trunk — retried next tick)`.

### 2.2 `metrics/gates` — one event per landing gate

**The ledger.** `harvest.record_gate(state_dir, branches, sha, ok, seconds, line)` appends one
line to `~/.ASF/state/<product>/gates.jsonl`, the same directory and the same append-only shape as
`mark_harvested` (`harvest.py:194`):

```json
{"at": "2026-09-24T06:41:12Z", "seconds": 412.7, "branches": ["spec/F-0100", "worker/T-0078"],
 "sha": "9f3c1ab…", "ok": false, "line": "FAILED (failures=1) tests.test_tick.RecordStepTests"}
```

Two callers, the two places a landing gate runs (P10):

- `land_ff` (`harvest.gate: per-branch`) — one line per branch gated.
- `gate_groups` (combined) — one line per `product_gate` call, so a bisect writes one line per
  group it gated. It takes a new `ledger=None` keyword, and `land_combined` passes
  `lambda branches, ok, seconds, line: record_gate(state_dir, branches, …)`; `None` writes
  nothing, which is what every existing test passes.

`seconds` is `time.monotonic()` around the `product_gate` call, and `line` is the first failing
line `product_gate` already returns — the same text the correction carries back to the session.

**The stream.**

```python
'gates': {
    'ts': (('str',), REQ),                    # when the gate started
    'seconds': (('num',), REQ),
    'branches': (('list',), REQ),
    'sha': (('str', 'null'), None),
    'conclusion': (('str',), REQ),            # 'success' | 'failure'
    'signature': (('str', 'null'), None),     # the first failing line, truncated to 120
    'items': (('list', 'null'), None),
},
```

`natural_key('gates', ev)` is `(ev['ts'], tuple(ev['branches']))`. `validate`'s gates arm checks
`conclusion` against `('success', 'failure')`, `seconds >= 0`, and that every entry of `branches`
is a string. `metrics.gates_from_ledger(product, known=())` reads the ledger, skips a line already
in the stream, and truncates the signature.

### 2.3 `asf/savings/landed.py` — the join, and the card's first measurement

```python
@dataclasses.dataclass(frozen=True)
class Landed:
    job: str; branch: str; kind: str; item: str | None; sha: str; ts: str
    sessions: int; rounds: int
    minutes: float; usd: float | None; in_tokens: int | None
    gate_minutes: float; gates: int
```

`landed_changes(landings, sessions, gates)` — pure, over three event lists:

- One `Landed` per landing event.
- Its sessions are every `sessions` event with the same `branch` and `ts <= landing.ts` (the lane's
  own rounds: the worker, its corrections, its reviews and its fixes). A landing with no branch
  falls back to the events with the same `item` and kind.
- `minutes`, `usd`, `in_tokens` are the sums over those, `None`-safe (`usd` stays `None` when no
  session carried one, never `0.0`); `rounds` is `max(round or 1)`; `sessions` is their count.
- `gate_minutes` is `Σ (g.seconds / 60) / len(g.branches)` over every `gates` event whose
  `branches` contains the lane branch and whose `ts <= landing.ts` — a combined gate's minutes
  split over what it gated, as CI minutes are split over the items they name.

`per_kind(rows)` → `{kind: {'landings': n, 'minutes': median, 'usd': median, 'gate_minutes':
median, 'rounds': mean, 'in_tokens': median}}`, plus an `all` row. Medians through
`statistics.median` over the non-`None` values (P16); a cell with nothing in it is `None`, printed
as `—`, and never `0`.

This is the card's named measurement: **minutes and dollars per landed change, per kind.**

### 2.4 `asf/savings/signals.py` — the six signals

```python
@dataclasses.dataclass(frozen=True)
class Signal:
    cls: str                # the class, one of the six below
    subject: str            # the kind / step / signature it names ('' when the class has one)
    reading: float          # what was measured
    threshold: float        # what it is measured against
    window_days: int
    expected_pct: int       # round(100 * (reading - threshold) / reading)
    title: str              # the card's title, with the number in it
    sentence: str           # one line: the reading, the window, and what the card would change
    evidence: list          # the rows behind the reading, one line each

    @property
    def over(self): return self.reading > self.threshold
```

`signals(streams, conv, day)` returns every class's `Signal`, over the threshold or not; the pass
proposes the ones that are over, and prints the rest with their distance. All six read the window
`conv.savings['window_days']` (default 7) ending at `day`.

| # | Class | The reading | Threshold (default) | The card it files |
|---|---|---|---|---|
| 1 | `brief_tokens` | per brief kind: the median `in_tokens` of that kind's sessions, over the median of all sessions in the window | `preamble_ratio` 2.0 | a preamble card for that kind (F-0022): the runner already knows what the session is discovering |
| 2 | `gate_minutes` | the median `gate_minutes` per landed change, all kinds | `gate_minutes_max` 20.0 | a gate card — *split the suite by footprint* when `conventions.harvest_gate` is `combined`, *one gate per tick* (B-0040) when it is `per-branch`; the reading says which |
| 3 | `rounds` | per kind: the mean `rounds` per landed change; the subject is the kind that rounds most | `rounds_per_landing` 1.3 | a brief card for that kind: what the session had to guess |
| 4 | `step_duration` | per tick step: the median `seconds` over the last day, over its median across the window | `step_duration_ratio` 1.5 | a step card naming the step |
| 5 | `model_spend` | per kind: the median `usd` per landed change, over the median of the per-kind medians | `spend_ratio` 1.5 | a routing card; the body names the cheapest `sessions.model` whose landings of that kind were green in the window |
| 6 | `failure_class` | per `gates.signature`: how many times it was seen in the window | `failure_class_count` 3 | a failure-class card (F-0087's list): the invariant that would end the class |

Signal 4's input is the `steps` list on each `ticks` line (P6): `{step: [seconds, …]}` grouped
over the window, today's median against the window's. A step seen fewer than three times in the
window is not read.

Signal 5 names the cheapest model by re-reading the same landings: for each `sessions.model` that
appears on a landed lane of that kind, its median `usd` per landed change. A kind whose landings
all ran on one model proposes nothing — there is no cheaper model to name.

**The floor.** With fewer than `conv.savings['min_landings']` (default 5) landings in the window,
classes 2, 3 and 5 read but do not propose; the pass prints
`savings: 3 landings in 7 days — under the floor of 5; nothing proposed from the landing join`.
Classes 1, 4 and 6 do not read the landing join and are unaffected.

### 2.5 `asf/record/propose.py` — file or bump a card by its `source:`

```python
def propose(root, canonical, source, fields, body, date, level='auto', product=None, out=print)
```

The `file_bugs` shape exactly (P12), with `source` in place of `signature`:

- **`auto`** — `find_open_by_source(canonical, source)`: an item that `core.is_open` and whose
  typed `source:` matches.
  - Found, `last_seen` is today → `'skipped'`, nothing written.
  - Found → write typed `measured`, `last_seen`, `expected_pct`, `rank`, append one `## History`
    line `- <date> savings: <class> <before> → <reading> (<n> landings)` → `'bumped'`.
  - Not found → `ids.mint_id(root, canonical, 'feature')` and `ids.write_new_item(...)` with the
    typed fields of §4 and an `## Acceptance` whose one line is the number that closes it →
    `'filed'`.
- **`groom`** (the default) — one file per proposal in `conventions.intake_dir`, named
  `savings-<class>-<subject>.md`, carrying the same body and `parent:`. An intake file already
  there for that key is overwritten with the new number, so the groom never sees two. Nothing
  under `features/` is touched.
- **`human-now`** — nothing is written and one line is printed per proposal:
  `NEEDS OPERATOR: savings proposes <class> (<sentence>) — widen approvals: propose_improvement in products/<p>.yaml`

`propose_improvement` joins `approvals.CLASSES` as

```python
ActionClass('propose_improvement', 'filing a card an improvement pass proposes', 'groom',
            ('savings',)),
```

and `new.SETTABLE['feature'] |= {'source'}` so the same field can be written by hand.

### 2.6 `asf savings` — the command

```
asf savings [--product P] [--day YYYY-MM-DD] [--window N] [--json] [--dry-run]
```

1. Resolve the product and the record through `cli.resolve_record` (so the first line is
   `record: <path>`).
2. Read the four streams for the window; build `landed_changes` and `per_kind`.
3. Print the per-kind table, then one line per class: the class, its subject, the reading, the
   threshold and `over` or its distance.
4. Propose every class that is over, ranked by `expected_pct` descending — `rank` on the card is
   the position × 10, so the board sorts them the way the pass does.
5. Re-measure every open card carrying a `savings:` source and write back `measured`, `last_seen`
   and `verdict` (§2.8).
6. `do_index(root)` once, when anything was written.
7. One last line: `savings <day>: 14 landed changes, 6 class(es) read, 2 over — 1 filed, 1 bumped`.

`--dry-run` does 1–3 and prints; it writes nothing and proposes nothing. `--json` prints the
readings and the per-kind table as JSON instead of the tables.

**A waste row**, `landing cost`: `14 landed in 7 days — median 44.0 min, $1.90`, with the note
`gate 6.9 min per landing (threshold 20.0)`.

**The savings block**, from the index (P2) — every item carrying a `source:` that starts
`savings:`:

```markdown
## Savings

| Card | Class | Expected | Baseline → now | Target | Verdict |
|---|---|---|--:|--:|---|
| F-0104 | gate_minutes:all | −54 % | 43.2 → 38.1 min | 20.0 | open |
```

`now` is the card's own detector re-read this run; `verdict` is `open` while the card is open,
