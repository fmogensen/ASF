# F-0269 — one test rolled a bad die, and the job says the product is broken

The card says `ci-job:tests (3.13)` is red 36.5 times a week — 73 of 961 runs over 14 days, 8,930
runner minutes. The number is real. What it names is not a defect: it is one matrix leg of one job
that runs **278 test modules and ~9,800 tests** in one step, ~340 times a day across the trunk and
every lane branch's pull request, and that goes red whole when any one of those tests rolls badly
once.

Read from the forge in this session, the six most recent red rows of that job (and of its 3.12
twin) are six different modules and five different causes:

| run | leg | `red:` module | what failed | reproducible? |
| --- | --- | --- | --- | --- |
| 37432074961 | 3.13 | `test_lifecycle` | `git clone` racing a detached `gc --auto` repack of the fixture's bare origin | no — **B-0403**, already carded |
| 37437245426 | 3.13 | `test_install` | `test_the_known_issues_page_names_the_clean_install_jobs`: `'install-clean-linux' not found` in the generated known-issues page | **yes** |
| 37438636186 | 3.13 | `test_install` | the same assertion, 12 minutes later on the next trunk push | **yes** |
| 37534521291 | 3.13 | `test_groom_publish` | `test_a_record_that_is_not_a_checkout_is_left_alone`: `filecmp` reported `['index.json']` differing | no — an mtime race |
| 37535104921 | 3.13 | `test_mechanical` | `push_from_elsewhere` (`tests/test_lifecycle.py:2955`): `fatal: failed to copy file to '…/.git/objects/38/4b6b…': No such file or directory` | no — the B-0403 race in a third fixture shape |
| 37551456319 | 3.12 | `test_tick` | `StaleRowCadenceTests…stales_at_40m`: `None != 'STALE since 23:42 — no fresh record in 40m'`, in a run that started at 00:20Z | no — a day-boundary clock flake |

Four of the six are non-reproducing races. One of them is a Bug the product has already filed and
whose own test names this very run (`tests/test_lifecycle.py:3451-3458` quotes run 37432074961).
Two are one deterministic defect, counted twice because the trunk took two pushes before anyone
could fix it. Not one of the six is specific to Python 3.13; the leg that caught each was a coin
flip, which is why the same reading files a second card for `tests (3.12)`.

So the cause key names the messenger — F-0169's complaint, now on the CI side of the same ledger —
and no session handed this card has a test, a module or an assertion to act on. What the product
*can* act on is the rule underneath the number: **this suite treats "a test failed once" and "the
product is broken" as the same event**, and the factory already disagrees with that everywhere
else. `asf.tick.flaky` exists precisely for the other reading — *"A product whose CI retries its
end-to-end tests passes a run a flaky test only survived on a retry. The run is green; the flake is
still there, printed in the reporter's summary"* — reads the flake out of the log, counts it, and
files one Bug per flaky test, S1 once it recurs. Every part of that is built. The one product whose
CI never retries anything, and therefore never feeds it, is this one.

This card closes that gap in the one place both the hosted job and every local gate share:
`tools/run_tests.py`.

### The arithmetic this card is measured on — stated before the design, not after

73 of 961 runs red is a **7.6 % red share**. The acceptance asks for fewer than 3 red runs a week
over the two weeks after landing; at the run volume the same 14 days hold (961 runs for this one
leg), 3 a week is a red share of about **0.4 %** — eighteen times better than today, and a bar no
suite of ~9,800 tests re-run ~340 times a day has ever cleared by fixing tests one at a time.

What the design below removes is the non-reproducing share: four of the six sampled reds, and every
future red of that kind. On that mix the reading falls from 36.5 to roughly 12 red runs a week — a
threefold fall, past the card's own *"must fall by 20 %"* verification clause, and **not** below 3.
What is left is a trunk that takes a genuine, reproducible red now and then (rows 2 and 3 above)
and keeps taking it on every push until it is fixed — each one its own Bug, filed by P5's pass,
none of them this card's to pre-empt.

Two things would close the remaining gap, and neither is a product change this card may make: read
the cause as a **share** rather than an absolute count (the threshold is a count, so it tightens by
itself every time the factory gets faster), or stop re-running the whole suite on each of ~120
trunk pushes a day. Both are the factory's own measurement and cadence, both are an operator's
call, and both are *Out* below — a spec that moves this number by shrinking its denominator is
exactly what the card's verification clause exists to catch.

### In

- **A second pass over the red modules, in `tools/run_tests.py`.** When the pool and the serial
  tail have drained and `1 ≤ len(red) ≤ retry_max`, the red modules are run once more, the same way
  they were run the first time — one `python -m unittest` per module through the same pool at the
  same `--shards`, each with a **fresh** `ASF_TESTS_HOME`. A module's second result replaces its
  first in `results`, so the summary, the counts, the `red:` line and the exit status are all taken
  from the final attempt.
- **A module red once and green on the retry is *flaky*, not red**, and the run's exit status does
  not count it.
- **The flaky block**, printed after the summary, in the exact shape the factory already reads
  (P8) — an `N flaky` head and one line per flaky test:

  ```
  1 flaky
    tests/test_groom_publish.py:140:1 › GroomPublishTests.test_a_record_that_is_not_a_checkout_is_left_alone
  ```

  The file and line come from the first `File "…"` frame inside the tests package in that test's
  own traceback; the title is `<Class>.<test>` read off the `FAIL:`/`ERROR:` line's dotted name. A
  module whose first attempt never reached a summary at all (a crash, a collection error) has no
  test to name and is reported as `tests/<module>.py:1:1 › <module>: no summary (rc N)`.
- **A `retry:` progress line** before the second pass, naming the modules it re-runs, so a reader
  of the log always sees that a second attempt happened and over what.
- **Two flags and two constants**: `--retry N` (default `RETRY = 1`) and `--retry-max N` (default
  `RETRY_MAX = 4`). `--retry 0` is today's behaviour exactly.
- **`tests/test_run_tests.py`** — three new case classes, and **`tests/test_flaky.py`** — one, all
  named in *Acceptance tests*.

### Out

- **Any edit to `.github/workflows/tests.yml`.** The `tests` step and the hermetic re-run both
  already call the runner, so both legs get the second pass with no workflow change (P1). The job's
  other steps run plain `python3 -m unittest` (the sample product, the installer, the README run,
  the goldens) and get nothing from this card — and none of the six sampled reds came from them:
  each one ended on the runner's own `red: <module>` line.
- **Trimming the matrix** — running 3.13 only on the trunk, or only nightly. It would halve this
  job's runs, and with them its red count, without a single test getting better; the card would
  read green for a reason that is not health. The 8,930 runner minutes the card prints beside the
  reading *are* worth a card (two legs of ~9,800 tests on every push of every lane branch), and
  this spec does not mint one.
- **The cause key, the threshold, and how a red job is counted.** Re-keying CI causes by root cause
  is already specified under F-0149 (`ci-step:`); counting one unresolved red once is F-0169's rule
  for gates. Neither is re-opened here, and this card must not: `metric` has to keep answering
  `ci-job:tests (3.13)` for two more weeks or the loop's own verification never reads it, and a
  card that re-reads the number that filed it is not a fix.
- **Fixing the five sampled defects.** B-0403's remaining fixture shape, the `filecmp` mtime race,
  the day-boundary clock assumption and the generated known-issues page are four Bugs, not this
  card's design. What this card changes is that the first three become *filed, counted* flakes with
  a test name on them instead of one anonymous red job among 961.
- **A new state file, a new stream field, a new tick pass, a new config key, or any edit to
  `asf/tick/flaky.py`.** The runner prints a block the existing parser already accepts; the
  existing state file counts it; the existing filer cards it (P8).
- **Retrying inside a module** (re-running the one failing test rather than its module). The
  runner's unit of work is a module in its own process, and a per-test retry inside the child would
  mean the runner writing its own unittest result handler — a far larger change for a narrower
  signal.
- **`bug_title`'s hardcoded `'Flaky e2e: '` prefix** where its signature side is the configurable
  `sig_prefix()` (`asf/tick/flaky.py:104-110` against `:55-58`). Under this product's default the
  two agree, so nothing here depends on it; it is a latent inconsistency for another card.

### The choices

| # | The choice | Chosen | Against | Why |
| --- | --- | --- | --- | --- |
| D1 | Where the retry lives | In the runner, on by default | A flag only the CI step passes | A CI-only retry would drop the card's number while every worker's own gate kept eating the same flakes — and the gate's half of this ledger (F-0159, F-0169: 23 red gates, every signature a module banner) is the same failure mode. One place, both callers (P1, P6). |
| D2 | How many extra attempts | One | `--retry 2`, or until green | Two independent dice rolls is what tells a race from a defect. A test that needs a third roll is not flaky, it is broken, and it should stay red. |
| D3 | How the red modules are re-run | As a second pass through the same pool, at the same `--shards` | Each red module alone, serially | Re-running the red set through the pool is what the harvest's bisect already does with `ASF_GATE_MODULES` (P7), it reuses `run`'s own loop, and it claims nothing a solo attempt cannot deliver: the pool's exact composition at the moment of the first failure can never be reproduced anyway. |
| D4 | The retry's `ASF_TESTS_HOME` | A fresh one per attempt | Re-use the first attempt's home | The first attempt died somewhere; whatever it left in its home is debris, and a retry over that debris tests the debris. A fresh home is one `os.path.join` and keeps the second attempt as hermetic as the first (P6). |
| D5 | What stops a retry storm | `--retry-max`, default 4 red modules | Retry every red module, however many | Five red modules out of 278 is a broken suite, not a flake storm, and a second pass over all of them would double a five-minute job to say what the first already said. Over the bound: no second pass, and the `retry:` line says so. |
| D6 | Where the flake is written down | The `N flaky` block the existing pass parses | A JSON artifact, a new stream field, a new tick pass | Everything needed is built (P8) and nothing else in the tree can name a module (P4, P5). The block costs one printed section and buys one counted Bug per flaky test, with the existing S1 escalation at three flakes in seven days or two on the trunk. |
| D7 | Where the block is printed | After the summary's two lines, last | Between `Ran …` and the verdict | `parse` reads the *last* `Ran`/verdict pair in a process's output and the harvest's gate reader scans for the first failing line; printing after both leaves every existing reader of this output untouched. |
| D8 | A flake's exit status | 0 | Non-zero, with the flake named | A flake that still fails the job changes nothing — and the factory's own answer to "the run is green, the flake is still there" is a counted Bug, not a red check (P8). A module red *twice* is still red, with both attempts' output in the log. |

## The design

Everything is inside `tools/run_tests.py` except the cases that prove it.

**`run()` (`tools/run_tests.py:272-323`) gains a third phase.** The pool loop and the serial tail
are untouched. When they have drained:

1. `red = [m for m, rc, out in results if rc != 0 or parse(out)[2] != 'OK']` — the same predicate
   `summary` and the exit status already use (P6).
2. No second pass when `retry == 0`, when `red` is empty, or when `len(red) > retry_max`; in the
   last case the `retry:` line says `retry: skipped — N red module(s) over the bound of M`.
3. Otherwise `retry: <modules>` is printed and those modules are re-run through the same pool loop,
   each at `os.path.join(homes, module + '#2')`, with the same `run_modules` and the same `finish`
   (so a module red twice streams its second output exactly as it streamed its first).
4. Each re-run module's entry in `results` is **replaced**, in place. The module count in the
   summary therefore stays the number of modules the suite ran, and `Ran N tests` is the final
   attempt's count for every module.
5. For a module that was red and is now green, one flake row is collected: `(file, line, title)`.
6. The flaky rows are printed after `summary(...)`, as `f'{len(rows)} flaky'` and one
   `f'  {file}:{line}:1 › {title}'` per row, before the hook-leak check (which is unchanged).

**Reading the flake's identity** is one new pure function, `flaky_rows(module, output)`:

- Split the first attempt's output on `FAIL:`/`ERROR:` lines. Each carries the dotted name in
  parentheses — `FAIL: test_x (tests.test_groom_publish.GroomPublishTests.test_x)` — whose last two
  dotted parts are the title `GroomPublishTests.test_x`.
- Inside that block, the first `File "<path>", line <n>,` frame whose path is under the tests
  package gives the file and line; the file is reported relative to the repo root
  (`tests/test_groom_publish.py`), so the key is stable wherever the checkout lives (P11).
- A block with no such frame falls back to `tests/<module>.py:1`. An output with no block at all —
  the module never reached a summary — yields the single row
  `(f'tests/{module}.py', 1, f'{module}: no summary (rc {rc})')`.
- Pure: it takes the module name, the return code and the text, and returns rows. It is unit-tested
  on the real outputs quoted in the table above.

**What a reader sees** when one module flakes in a 278-module run:

```
--- test_groom_publish: FAILED (rc 1)
======================================================================
FAIL: test_a_record_that_is_not_a_checkout_is_left_alone (tests.test_groom_publish.GroomPublishTests.test_a_record_that_is_not_a_checkout_is_left_alone)
…
retry: test_groom_publish

Ran 9818 tests in 352.004s (278 module(s), 4 at a time)

OK (skipped=18)

1 flaky
  tests/test_groom_publish.py:140:1 › GroomPublishTests.test_a_record_that_is_not_a_checkout_is_left_alone
```

The job is green. The next `asf file-bugs` reads that block out of the run's log, counts the test
in `state/<p>/flaky.json`, and files one Bug named after it — and the second time the same test
flakes on the trunk, that Bug is S1 (P8).

**`build_parser`** gains `--retry` (`type=int, default=RETRY`) and `--retry-max`
(`type=int, default=RETRY_MAX`), both passed through `main` into `run`. `run`'s signature gains
`retry=RETRY, retry_max=RETRY_MAX` after `only`, so every existing caller — the workflow's two
steps, the harvest's gate, `--touched` — gets the default without an edit.

## Records

- **Nothing new is persisted.** No new state file, no new stream field, no new config key, no card
  written by this change.
- **The run's log** gains, per run that had a red module: one `retry: …` line, and — only when a
  module went green on its second attempt — one `N flaky` block of one line per flaky test, after
  the summary. A run with no red module is byte-identical to today's.
