# F-0127 — a declared setup command, and freshness read off the worktree instead of guessed before it exists

A product with dependencies cannot use a worker worktree as git leaves it: `pnpm install`, `make
deps`, a codegen step must run before the session can build or test anything. The card asks for two
things — a product **declares** that command, and the spawner **runs it in every fresh worktree**.

Most of that is already in the tree, and the design below is cut to what is not:

- **The declaration exists and is validated.** `conventions.worktree_setup` is a contract field
  defaulting to nothing, and a value that is not a command string is refused with the key's name
  (P1, P2).
- **The spawner runs it, under the session's own environment.** `run_worktree_setup` runs the
  command in the new worktree under `runtime.build_env` in worker mode — the allow-list, the
  account's HOME, no operator secret — logs it masked, and on a failure or a timeout removes the
  worktree and refuses the launch (P3, P4). It runs before the id range and the brief, so a refused
  launch leaves no ledger line and no reserved ids (P5). Eight tests over it pass in this checkout.
- **One place decides *fresh*, and it decides wrong.** `spawn` reads `fresh = not
  os.path.exists(own_path)` **before** `make_worktree` runs, and runs the setup only when that
  boolean holds (P6). `make_worktree` reclaims a stale orphan — trashing the tree and pruning it out
  of git — and then creates a **brand-new checkout at the same path** (P7). For that launch `fresh`
  is False: the path did exist a moment earlier. The setup never runs, and a session is handed a new
  checkout with no dependencies, with nothing in the record saying so.

The fix is to stop asking the clock and ask the worktree. After this change a worktree carries its
own record that the product's setup command ran in it — a small JSON file in the tree's **git admin
dir**, which `git worktree remove`/`prune` deletes together with the tree — and the spawner runs the
setup exactly when the worktree it is about to hand over does not carry that record for the command
the product declares now. A fresh tree never has one; a reclaimed-and-recreated path never has one;
a reused tree that already installed its dependencies has one and is left alone. And the guide that
documents what a product declares gains the key, with when it runs, what a failure does, and the one
requirement the command must meet.

### In

- **A worktree records its own setup.** `spawn.setup_marker_path` / `setup_done` / `_record_setup`:
  a JSON file `asf-setup` in the worktree's git admin dir (P9) holding the command verbatim, the
  UTC time, and the seconds it took. `setup_done(worktree, command)` is True only when the marker
  parses and names **exactly** the command the product declares now.
- **The marker is written by `run_worktree_setup` on success, and read by it before it runs
  anything.** A worktree that already carries the marker for this command returns None — nothing
  runs, nothing is logged, no `setup_s` on the record (P11).
- **`spawn` stops guessing.** `own_path` and `fresh` go; every non-cloud launch calls
  `run_worktree_setup` and lets the marker decide. The reclaimed-and-recreated path (P7) gets its
  setup, because its new admin dir carries no marker.
- **A changed command re-runs the setup** in a worktree set up by the old one — the tree is not set
  up for what the product declares now.
- **`docs/guide/product-config.md` documents the key**: a row in the `## Conventions` table and a
  short subsection under it — when it runs, the environment it runs under, that a failure refuses
  the launch and removes the worktree, the 900 s timeout, the log path, that a reused worktree keeps
  its install and does not re-run it, that a changed command does, that the command must therefore
  be **idempotent**, and one line on what a cloud lane does with it (P12).

### Out

- **Running anything on this host for a cloud session** (D9). The local tree of a cloud run is a
  branch-publishing tree; the command reaches the CI job and the routine session by the two paths
  P12 names, and neither is this card's.
- **A configurable timeout.** `WORKTREE_SETUP_TIMEOUT_S` stays a constant at 900 s (D10).
- **A doctor row, a metrics event or an `asf` command over the marker.** The marker is evidence on
  disk that a test and an operator can read; a view over it is adjacent scope and its own card.
- **Re-running setup for any reason other than the marker** — a lockfile that changed under the
  tree, a deleted `node_modules`, a clock. The card's unit is the worktree, and the product's
  command is what knows whether its own install is current.
- **An invariant over it.** `asf/invariants.py` has three scopes — `record`, `feeder`, `lane` — and
  none of them is the spawn; a fourth scope for one check is a change to the invariant surface, not
  to this card.
- **Touching `make_worktree`'s placement logic, the reaper's verdicts, or the `spare` rule.** This
  change adds one file inside an admin dir and deletes two lines of guessing; the six paths a
  worktree can be placed by and the cap that reaps them are untouched.
- **A migration.** There is nothing to migrate: a worktree already on disk carries no marker and
  runs the command once more, on its next reuse (D4).

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | Freshness is a record the worktree carries | a `fresh` boolean threaded out of `make_worktree` | `make_worktree` places a worktree by six paths, two of which reuse and four of which create (P7), and the one that is broken today *creates* at a path that already existed. A boolean returned from there would be right until the seventh path is added; a marker is the answer to the question the session actually depends on — *are this tree's dependencies installed?* — and it is checkable afterwards, by a test and by an operator, where a boolean is gone the moment it is read |
| D2 | The marker lives in the worktree's **git admin dir** | the worktree root, or the product's state dir | The root is refused by P8: an untracked file there makes `safety` call every worktree dirty for ever, so no worktree is ever reaped again — and it would sit in the session's own `git status`. A state-dir file has a lifecycle nobody maintains: every removal path would have to delete it, and the one that forgets leaves a stale marker that skips the setup of a new tree. The admin dir *is* the worktree's lifecycle (P10): prune and remove delete it with the tree, so the reclaimed path — the defect this card fixes — has no marker by construction |
| D3 | The marker holds the command **verbatim**, and the check is string equality | a hash of it, or a bare `done` flag | An operator who edits `worktree_setup` has changed what a worktree needs; a flag cannot tell, and a hash cannot be read back. The text is what the operator wrote and what the log names, and it is not a secret — it is the product file's own line, already on disk in plain text |
| D4 | A worktree with no marker runs the setup once, reused or not | treat a worktree that already exists as set up, as today | That is exactly the guess this card removes, and it is wrong for the trees most likely to need it. The cost is one extra run of an idempotent command per worktree already on disk, once; the alternative keeps the defect alive for every worktree that predates the change |
| D5 | The command must be idempotent, and the guide says so | leave it unsaid | D4 runs it once in a tree that may be half-installed, and a changed command runs it in a tree the old one installed. Every plausible command (`pnpm install`, `make deps`, a codegen step) already is; a product whose is not must learn it from the contract, not from a broken worktree |
| D6 | The marker is checked **inside** `run_worktree_setup` | a `needs_setup(...)` guard at the call site in `spawn` | The function already owns "declares no command → None, nothing ran"; adding "already set up → None, nothing ran" keeps one decision in one place and keeps `setup_s is None` meaning exactly *no setup ran on this launch* on the ledger (P11) |
| D7 | A marker that cannot be written is not a failed launch | raise `SpawnError` | The setup did run and the tree is good. The cost of a missing marker is one repeat on the next launch in that tree; refusing the session instead would trade a working worktree for a `NEEDS OPERATOR` over a state file |
| D8 | A tree whose `_admin_dir` is `''` counts as **not** set up | count it as set up | `make_worktree` returns only linked worktrees git made, so the case is unreachable in practice (P9). On an unreachable path the safe answer is to run an idempotent command again, never to hand a session a tree that may hold no dependencies |
| D9 | The cloud arm still runs nothing here | run the setup in a cloud run's local worktree | Nothing is built on this host for a cloud session: the tree exists so a fresh branch can be published from it (P12). Running a dependency install for a machine that will never use it costs minutes a tick and gigabytes a worktree |
| D10 | No config key for the timeout | `conventions.worktree_setup_timeout_s` | 900 s is a constant no product has reached, and the card asks for the command to run, not for a knob over it. When one needs longer it is a one-line change with its own card, and a key minted now is a contract to keep for ever |
| D11 | No new field on the session record | record the marker path, or `setup: skipped` | The ledger says what a launch did; the marker says what the worktree holds. Those are two records with two lifetimes, and duplicating one onto the other gives the fold a field it must then keep true |
| D12 | The key is documented in `product-config.md`'s `## Conventions` | `operating.md`, or the example file's comment alone | `product-config.md` is where a product declares a convention, and its table of "the ones that matter most" is where a reader looks for one (P14). The example file's commented line is a reminder, not a contract: it does not say what environment the command gets, what a failure does, or that reuse skips it (P15) |
| D13 | The guide prose is pinned by a test | assert nothing about the docs | "A test nobody can run is not acceptance" — and the file already has guide-prose tests reading the checkout (P16), so the clauses an adopting product depends on have a home |

## The design

### `asf/workers/spawn.py` — the worktree's own record

One import (`json`) joins the module's list (P18), and three functions go beside
`run_worktree_setup`:

```python
#: The worktree's own record that the product's setup command ran in it: a JSON file in the
#: worktree's **git admin dir** (``<repo>/.git/worktrees/<name>/asf-setup``), never in the tree.
#: An untracked file in the tree would read as uncommitted work for ever, and no worktree would be
#: reaped again (:func:`asf.workers.worktrees.safety`); the admin dir is deleted with the tree by
#: ``git worktree remove`` and ``git worktree prune``, which is what makes a recreated path count
#: as fresh (F-0127, D1/D2).
SETUP_MARKER = 'asf-setup'


def setup_marker_path(worktree):
    """``worktree``'s setup marker, resolved through the tree's own ``.git`` file
    (:func:`_admin_dir`) so a suffixed admin dir resolves to its own; '' when there is none."""
    admin = _admin_dir(worktree)
    return os.path.join(admin, SETUP_MARKER) if admin else ''


def setup_done(worktree, command):
    """Whether ``command`` has already run in ``worktree``: its marker parses and names exactly
    this command.

    This is what *fresh* means (F-0127). A worktree with no marker has not been set up, whatever
    its path held before the launch — a reclaimed orphan is a new checkout at an old path, and the
    old admin dir went with the old tree (D1/D2). A marker naming a different command is a tree the
    product's current command has not run in (D3). An unreadable or malformed marker, or a tree
    with no admin dir, is not set up: running an idempotent command again is the safe answer, and
    handing a session a tree that may hold no dependencies is not (D8)."""
    path = setup_marker_path(worktree)
    if not path:
        return False
    try:
        with open(path, encoding='utf-8') as f:
            return json.load(f).get('command') == command
    except (OSError, ValueError, AttributeError):
        return False


def _record_setup(worktree, command, took_s):
    """Write the marker: the command verbatim, the UTC time, the seconds it took. Returns the path,
    or '' when it could not be written — which is not a failed launch (D7): the setup did run, and
    the only cost of a lost marker is one repeat in that worktree."""
    path = setup_marker_path(worktree)
    if not path:
        return ''
    try:
        with open(path, 'w', encoding='utf-8') as f:
            json.dump({'command': command, 'at': pool_mod.now_iso(), 'took_s': took_s},
                      f, sort_keys=True)
    except OSError:
        return ''
    return path
```

`run_worktree_setup` gains the check at the top and the write at the end; its middle — the
environment, the masking, the log, the failure — keeps every line it has (P3, P4):

What this changes, launch by launch:

| the launch | today | after |
| --- | --- | --- |
| a new worktree at a path nothing held | setup runs | setup runs, and the marker is written |
| an ended run's worktree reused for a correction | skipped (`fresh` False) | skipped (the marker names the command) |
| a **stale orphan reclaimed and recreated at the same path** | **skipped — the session gets no dependencies** | setup runs: the new admin dir has no marker |
| a worktree of another job that holds the branch | skipped (`worktree != own_path`) | skipped when that tree's marker names the command, run when it does not |
| a reused worktree after the operator edited the command | skipped | setup runs: the marker names the old command |
| a worktree already on disk when this change lands | skipped | setup runs once, then the marker is there (D4) |
| a cloud run's local worktree | nothing runs here | unchanged (P12, D9) |

### `docs/guide/product-config.md` — the key where a product declares it

One row in the `## Conventions` table:

| key | default | meaning |
| --- | --- | --- |
| `worktree_setup` | none | a shell command run in every fresh worker worktree before its session starts — the dependency install or codegen the product's gate needs. Must be idempotent — see below |

and a subsection under that table:

> #### `worktree_setup` — the command a fresh worktree needs
>
> Each worker session gets its own git worktree, and git gives it a checkout and nothing else: no
> `node_modules`, no virtualenv, no generated sources. `worktree_setup` is the one command that
> makes such a checkout buildable, and the factory runs it in the worktree **before** the session
> starts, so no session ever has to.
>
> - It runs in the **worktree**, under the environment the session itself will have: the worker
>   allow-list, the account's own HOME, the product's `auth_env` — never the operator's
>   environment, and never a value the tick happens to carry (see operating.md, Safety).
> - Its output goes to `~/.ASF/state/<product>/briefs/<job>.setup.log`, with every `auth_env`
>   value masked.
> - It gets **900 seconds**. A failure or a timeout **refuses the launch and removes the
>   worktree** — a tree without its setup is never handed to a session, nor reused as though it
>   had one — and names the log; the same failure twice in a row is a `NEEDS OPERATOR` telling you
>   which key to fix.
> - It runs **once per worktree**: the worktree records the command that ran in it, and a worktree
>   reused by a later session — a correction on the same branch, say — keeps the install it
>   already has. A worktree the factory recreates gets the command again, and so does one whose
>   recorded command is not the one the product declares now.
> - So **make it idempotent.** `pnpm install`, `make deps` and a codegen step already are. A
>   command that fails when its work is already done will refuse a relaunch.
> - A session that runs **off this host** (`lane: cloud`) never runs it here: the command is handed
>   to the run that needs it — the CI job gets it with its brief, a routine session is told to run
>   it first.

## Acceptance tests

The marker, on its own: it resolves through the tree's own `.git` file, an absent one is *not set
up*, one naming this command is, one naming another is not, a truncated or non-JSON one is not, a
tree with no admin dir is not — and a worktree that has been set up still has a **clean**
`git status --porcelain`, so the reaper can still reap it (P8, D2):

```bash
python3 -m unittest -v tests.test_worker_isolation.WorktreeSetupMarker
```

**The card's own test** — the spawner runs it in every fresh worktree, including the one that is
fresh at a path that already existed: a stale orphan at the job's own path is reclaimed, the new
checkout gets the setup, its marker names the command, and the record carries `setup_s`. Without
the fix this test fails on a session launched into a tree with no dependencies:

```bash
python3 -m unittest -v tests.test_worker_isolation.WorktreeSetupAfterReclaim
```

Once per worktree, and again when the command changes: a first launch runs it and writes the
marker; a second launch in the same worktree runs nothing, logs nothing and records no `setup_s`;

## Records

- **The setup marker** — `<repo>/.git/worktrees/<name>/asf-setup`, one JSON object,
  `{"at": "<UTC>", "command": "<the command, verbatim>", "took_s": <float>}`, written by
  `_record_setup` after a successful run and by nothing else. It is the worktree's own answer to
  *has the product's setup run here?* It is **not** in the worktree's tree, so it never shows in a
  session's `git status` and never blocks the reaper (P8); it is removed with the worktree by `git
  worktree remove` / `git worktree prune`, which is what makes a recreated path fresh (P10).
- **The setup log** — `~/.ASF/state/<product>/briefs/<job>.setup.log`, stdout then stderr, every
  `auth_env` value masked. Written per launch that runs a setup; a launch the marker skipped writes
  none, and leaves the previous one in place.
- **`setup_s`** on the session's ledger line in `sessions.jsonl` — the seconds the setup took, on
  launches that ran one. A skipped setup, a product with no command and a cloud launch write no
  such field (P11), so the field keeps its one meaning.
- **The refusal** — a failed or timed-out setup writes no ledger line, reserves no id range and
  writes no brief (P5); the worktree is trashed; the wave logs `spawn failed: worktree_setup
  \`<command>\` failed in <worktree> (<why>) — log: <path>`, and a second identical failure becomes
  `NEEDS OPERATOR … — fix \`<command>\` (conventions.worktree_setup in products/<product>.yaml),
  then relaunch` (P4, P13).
- **`docs/guide/product-config.md`** — the `worktree_setup` row in the `## Conventions` table and
  the subsection under it.
- **Nothing in the product repo's tree, and no new state file.** No config key, no schema change,
  no record card, no metrics event, no migration. A product that declares no `worktree_setup` is
  bit-for-bit unaffected: `run_worktree_setup` still returns at its first line.

## Stories

- S: A worktree records the setup that ran in it — `asf-setup` in its git admin dir, holding the command verbatim, and `setup_done` reads it as the one definition of *fresh*: absent, unreadable, or naming another command means not set up, and a set-up worktree's `git status` stays clean so the reaper can still reap it — acceptance: `python3 -m unittest -v tests.test_worker_isolation.WorktreeSetupMarker`
- S: The spawner runs the product's setup in every fresh worktree by asking the worktree instead of whether its path existed — so the reclaimed-and-recreated path gets its setup instead of handing a session a checkout with no dependencies, a reused worktree keeps its install and records no `setup_s`, an edited command runs again, and the cloud arm still runs nothing on this host — acceptance: `python3 -m unittest -v tests.test_worker_isolation.WorktreeSetupAfterReclaim tests.test_worker_isolation.WorktreeSetupRunsOnce tests.test_worker_isolation.WorktreeSetup tests.test_cloud`
- S: The product-config guide documents the declaration — the `worktree_setup` row in the conventions table and the subsection saying where it runs, its log, its timeout, that a failure refuses the launch and removes the worktree, that it runs once per worktree, that it must be idempotent, and what a cloud lane does with it — acceptance: `python3 -m unittest -v tests.test_readme.WorktreeSetupProseTests`
