# F-0348 — a Task whose predecessor is already written waits for a merge, not for the work

An `after:` edge is satisfied only when the item it names is **Done** — its pull request merged
(`asf/kernel/decide.py:1536`, `edge_open`). Until then the dependent Task is forced back to New
(`_apply_waits`, `:1551`), takes no seat, and its spell is recorded under the wait class `after`
(`asf/kernel/waits.py:22`).

That rule is right about one thing and wrong about another. It is right that a Task must not
start before the surface it builds on exists — the plan's order exists because the first
successor whose coder found its predecessor's surface missing wrote nothing
(`asf/record/plan_order.py:6-9`). It is wrong that the surface only exists once the trunk holds
it. The moment the predecessor's session has pushed, its surface is on origin, on a branch, with
a pull request open over it — and everything between that push and the merge is review, CI,
auto-merge and the merge train. On this factory that is the larger half of a Task's life, and the
successor spends all of it in a wait class, while a seat sits free.

This card closes that gap: **a dependent Task starts on its predecessor's branch instead of
waiting for its merge.** Its branch is cut from that branch's head, its pull request is opened
against that branch, its review reads its own change and nothing else, and when the predecessor
lands, the Task's own commits are replayed onto the trunk and its pull request is retargeted
there. Nothing merges into anything but the trunk, and no stacked pull request lands before the
branch under it.

The kernel already does this once, for documents: with `config.plan_on_approve` a Feature's plan
session launches on its spec's **approved, unmerged** pull request and reads the spec off the spec
branch (`decide.early_plans`, `:1788`; the brief block `briefs.EARLY_SPEC`, `:45`). F-0348 is the
same move for code, where the predecessor is not read but built on, so the branch — not just the
brief — has to point at it.

## 1. Decisions

### 1.1 In scope

- One new fact pair: `Item.stack` (the stack a card is on, off its machine block) and `PR.base`
  (the branch GitHub holds the pull request against, already read and discarded today).
- One new launch pass, `decide.stacked_builds`, modelled on `early_plans`: a Task or Bug held New
  by exactly one open `after:` edge whose predecessor has **pushed** launches on a free seat with
  its base set to the predecessor's branch and head.
- `Launch.base` / `Launch.base_sha` threaded to the host: the branch is cut from and rebased onto
  `origin/<base>` rather than the trunk, the brief says so, and the session's footprint gate
  diffs against the base.
- The stacked pull request: opened against the base branch (`OpenPR.base`, which already exists
  and is always `''` today), never auto-merged while its base is not the trunk.
- The unstack: when the predecessor reaches Done, one `Retarget` action moves the pull request to
  the trunk and the branch is replayed `--onto origin/<trunk>` from the recorded fork point, so
  the predecessor's commits are not carried twice.
- The teardown: a predecessor that is archived, reset, reverted or parked takes its stack down —
  the stacked card goes back to waiting, and nothing of it is merged.
- Two knobs under `kernel.stack`, with the floor being today's behaviour, and one new machine key
  (`kernel_stack`) in the keys the kernel owns.
- `tests/kernel/test_stacked_builds.py` and `tests/test_stacked_worktree.py`.

### 1.2 Out of scope

- **Changing what an `after:` edge means.** `edge_open` still holds until Done or retired; the
  card is still New; `blocked_count`, the `after` wait class and the wait ledger are untouched.
  The stack is a *launch* that happens while the item waits, exactly as `early_plans` launches a
  plan while its Feature is Landing. Nothing below re-derives a state (D1).
- **Stacking more than one level** by default (`max_depth: 1`, D5) and **stacking on more than
  one predecessor** at all (D6).
- **Document lanes.** A spec's or a plan's predecessor is read, not built on, and
  `plan_on_approve` already covers it. Only the build lanes stack (D3).
- **Merging a stacked pull request into its base branch.** Nothing but the trunk is ever a merge
  target (D9).
- **Any new landing path.** A retargeted pull request lands through the same review, auto-merge,
  merge train and still-needed gate as every other one.
- **Reordering a plan.** The stack follows the `after:` edges the plan already minted
  (`asf/record/plan_order.py`); it never infers an order of its own.

### 1.4 The choices

| # | chosen | against | why |
| --- | --- | --- | --- |
| D1 | a separate launch pass (`stacked_builds`), the card staying New and the `after:` edge staying open | releasing the edge in `edge_open`/`_apply_waits` so the Task becomes Ready | Releasing the edge would make the hold invisible: `blocked_count` (`:1569`), the `after` wait class, the breach targets and the still-needed gate all read "nothing waits on this" the moment a stack starts, and a Task would also be launchable by the ordinary path with the trunk as its base. P3's precedent keeps every one of those honest and puts the whole feature behind one pass. |
| D2 | stack only on a predecessor that has **pushed** — its session ended and its branch is on origin with an open pull request (Review or Landing) | stacking on a Building predecessor the moment its session starts | A Building predecessor's branch head moves under the stack on every commit, and by construction the two Tasks' `writes` overlap, which is exactly what the file-overlap hold exists to stop (`decide.py:1672-1674`). Waiting for the push costs the little that is left of the predecessor's session and buys a base that only a fix round moves. |
| D3 | build lanes only (a Task or a Bug; `_kind` returning a build kind) | every lane, specs and plans included | A document predecessor is *read*, not built on, and the kernel already starts a plan on an unmerged spec by handing its brief the spec branch and head (P3) — no second branch needed. A spec branch is also not a base anything can be cut from without carrying the document into the code pull request. |
| D4 | the base is the predecessor's **branch**, and the fork point is its head sha at cut time, recorded on the card (`kernel_stack: <branch>@<sha>`) | recording nothing and deriving the fork point later with `git merge-base` | After the predecessor merges, its branch is deleted by the repository's own setting, and a merge base that cannot be read is a replay that cannot be done: the unstack would have to rebase the whole branch onto the trunk and would replay the predecessor's commits on top of their own squashed merge. The recorded fork point makes the unstack `rebase --onto origin/<trunk> <fork>` — the Task's own commits, exactly once — and it survives the branch's deletion, a reaped worktree and a relaunch. |
| D5 | `max_depth: 1` — a stack on a stack waits | unbounded chains | Each level adds a replay that can conflict and a base that can be torn down, and the failure is not local: level 3 is rebuilt whenever level 1 is archived. Depth 1 is the whole of the card's measured win (the predecessor's review-and-land time) at one replay's risk; the operator raises the knob once the records show the first level landing clean. |
| D6 | a card with **two or more** open edges never stacks | a base branch that merges several predecessors together | Git has one base. Merging the predecessors into a synthetic base would be a branch the factory owns, lands and cleans up, and it would put other Tasks' changes into this Task's pull request diff — so the review would no longer read the Task's own change (P6). Such a card waits, as it does today. |
| D7 | the stack is never rebased while it is live: a predecessor head that moves is left alone until the base lands | rebasing the stacked branch onto its base's new head every tick | A rebase of a branch a session may be holding is the one thing `make_worktree` refuses to hand over (`spawn.py:678-681`), and the stacked pull request's diff is against the base ref as GitHub holds it *now*, so a moved base is already visible to the review, and a verdict keyed to the old tree no longer holds (`verdict_holds`). The one case that needs an act — the base no longer merges — arrives as `PR.conflicting` and is the existing conflict path. |
| D8 | a stacked pull request is never auto-merged or merged while `PR.base` is not the trunk; the hold is stripped from the plan with a note, exactly as high risk is | letting GitHub merge it into the base branch, which is what an unheld `EnableAutoMerge` would do | A merge into the predecessor's branch puts the Task's change into the predecessor's pull request, where it was never reviewed and where the still-needed gate never measured it; the Task's own pull request would then close as empty. P11 is the shape for holding a landing without inventing a state. |
| D9 | one `Retarget` action, applied by the kernel, when the predecessor is Done | relying on GitHub to retarget the pull request when the base branch is deleted | GitHub's retarget fires only if the base branch is deleted on merge, which is a repository setting no product file states; and it leaves the branch itself unreplayed, so the pull request would show the predecessor's commits as its own. An explicit action is a fact the kernel can see (`PR.base` next tick) and re-issue idempotently. |
| D10 | a predecessor that is archived, reset, reverted or parked tears the stack down: the card's `kernel_stack` is cleared and its branch is archived and cut fresh on the next launch | leaving the stack on a base that is gone | `archive_and_reset` already exists for a branch that cannot land (`ports.py:1540`), and a stack whose base was rewritten is that case: its fork point is on no branch, so its replay is not defined. Tearing it down loses nothing — the work is on `archive/<branch>` and the card waits as it did before the stack. |
| D11 | `enabled: true`, `max_depth: 1` | off by default | The card is operator-approved for 0.3, and depth 1 with D2's push gate is the conservative floor: nothing stacks until a predecessor has pushed, nothing lands out of order, and the one behaviour change a product can meet is a Task starting a review-and-land earlier. A product that wants today's behaviour sets `enabled: false`, and S-135960 pins that the floor is exactly what the trunk does now. |
| D12 | the stacked session's footprint gate diffs against `origin/<base>` (a new `ASF_BASE` in the worker env), not the trunk | leaving the gate on the trunk | On a stacked branch `origin/<trunk>...<head>` is the predecessor's paths *plus* the Task's, so every stacked push would be refused for paths outside its own `writes` (P9) — a refusal the session cannot fix. The base diff is the Task's own change, which is what the footprint means. |

## 2. The design

### 2.1 The fact: what a stack is, and where it is written down

Two fields, both read-only to `decide`:

- `model.Item.stack: str` — the card's machine key `kernel_stack`, in the form
  `<base-branch>@<fork-sha>`, '' when the card is not stacked. Written by the kernel through
  `record.write_fields` when a stack starts (D4), cleared when it is torn down or retargeted. Two
  helpers beside it, pure: `stack_of(item) -> (branch, sha)` and `is_stacked(item)`.
- `model.PR.base: str` — `baseRefName` as GitHub reports it, filled in `ports._open_pr` from the
  field `PR_FIELDS` already asks for (P5). `pr.base and pr.base != product.main` is the one test
  for "this pull request is stacked", and it is GitHub's own answer, not a guess.

`kernel_stack` joins `ports.KERNEL_KEYS` (P12), so `card_fields` round-trips it and a card the
kernel no longer stacks does not keep a stale key.

### 2.2 The stacked launch

A new pure function in `decide`, wired exactly where `early_plans` is (`:440-444`), after
`_launches` and on the seats it left free:

```
stacked = stacked_builds(facts, config, judged, states, parked, launches) if config.stack else []
launches += stacked
```

`stacked_builds` walks the items in `launch_order` and, for each, requires all of:

1. the item is a Task or a Bug whose kind is a build kind (D3), visible and not parked;
2. its derived state is New and `open_edges` holds **exactly one** id (D6);
3. that predecessor is a work item on the record, not parked, not Stuck, and its own derived
   state is Review or Landing — so its session has ended and its work is on origin (D2);
4. the predecessor has an open, non-conflicting pull request whose branch is under the product's
   work prefix, and whose `base` is the trunk — that is the depth check (D5: a predecessor whose
   own pull request is stacked is not a base);
5. the item has no live session, no open pull request of its own, and no stack already recorded
   (one that *does* have a stack recorded is not this pass's business — it is launched by the
   ordinary path, since the card is only New while the edge is open and `judged[iid].branch`
   carries its branch);
6. the WIP cap and the seat count allow it, with the same two guards `early_plans` uses
   (`open_prs(judged, on_pr) > cap` and `free <= 0`);
7. the item's `writes` do not overlap any Building item's (the ordinary launch guard, applied
   here too).

It then emits, per item, in order:

- `A.NoteStack(item_id, base_branch, base_sha)` — the record write (`kernel_stack`), so a
  relaunch, a reaped worktree and the unstack all read the same fork point off the card;
- `A.Launch(kind, item_id, branch, base=base_branch, base_sha=base_sha)`.

`Launch` grows the two fields (defaults `''`), and `apply.Launch` passes them to the port with
the row; `describe` says `… stacked on <base> @<sha[:9]>`, and the plan's `notes` carry one line
per stacked item so the tick prints it.

### 2.3 The worktree, the brief and the gate

`ports._spawn` passes `base`/`base_sha` on the `pool.Row`; `spawn.spawn` reads them and:

- `make_worktree(product, job, branch, …, base=row.base)` — the one fresh-cut site (P7) takes
  `origin/<base>` instead of `origin/<main>`, and `_rebase_onto_trunk` (renamed
  `_rebase_onto_base`, with `base` defaulting to `product.main`) rebases a fresh stacked branch
  onto `origin/<base>`. `_checkout_branch` takes the same argument. No literal moves: the value
  comes from the launch, which got it from `conventions` (P14).
- `runtime.Job(..., base=row.base or product.main)` (P8) — so both remote runtimes already tell
  the session "checked out on branch `<branch>` (base `<base-branch>`)" with no change to either.
- the worker env gains `ASF_BASE=<base-branch>`, and `asf pre-push` reads it:
  `prepush.added_paths(repo, sha, f'origin/{os.environ.get("ASF_BASE") or trunk}')` (D12, P9).
  An unresolvable base is already "not checked", never a refusal (`cli.py:210`).
- the brief gains one block, `briefs.STACKED` — the peer of `EARLY_SPEC` (P3):

  > ## Your branch starts on `<base-branch>`, not on the trunk
  >
  > `<predecessor id>` is written and pushed but not merged. Your branch is cut from
  > `origin/<base-branch>` at `<sha>`, so its surface is already here: build on it. Do not merge
  > or cherry-pick the trunk or `<base-branch>` into your branch, and commit nothing that belongs
  > to `<predecessor id>` — your pull request is opened against `<base-branch>` and holds your
  > change only. Your footprint is diffed against `origin/<base-branch>`.

  Its `cut from origin/{main}` line is rendered from the launch's base too, so the brief and the
  branch cannot disagree.

### 2.4 The pull request, and the landing hold

`open_pr_action(it, branch, session)` takes the base from the item's stack: `A.OpenPR(it.id,
branch, base_branch, …)` when `it.stack` names one and the predecessor is not yet Done, `''`
otherwise (P4). `ports.open_pr` already honours it, so the whole of the GitHub side is the base
string.

The landing hold is a new clause in the same place the high-risk hold is applied (P11,
`decide.py:860-864`):

```
stacked_held = {p.number for p in facts.prs
                if not p.merged and p.base and p.base != facts.main_branch}
actions[:] = [a for a in actions
              if not (isinstance(a, (A.EnableAutoMerge, A.MergePR)) and a.pr in stacked_held)]
```

with one note per held item — `stacked: waits for <base-branch> (<predecessor id>) to land` — so
the item reads Landing, its CI and review run as usual, and nothing merges it anywhere (D8). A
stacked pull request is therefore never `behind` the trunk in a way the merge train acts on: the
train reads `pr.behind` against its own base, and the retarget below is what brings it to the
trunk.

### 2.5 The unstack: the predecessor lands

When the predecessor reaches Done (its pull request merged and not reverted — `landed`), the
stacked item's `after:` edge closes by itself (`edge_open`) and the card becomes Ready. On that
same tick, for each item whose `stack` names a branch whose predecessor is now Done:

1. `A.Retarget(pr, '')` — the pull request's base becomes the trunk; the port is
   `github.retarget(pr, base)` (`gh pr edit <n> --base <trunk>`), idempotent, and a pull request
   GitHub already retargeted (its base is the trunk) is skipped on the facts, not on an error
   (D9).
2. `A.NoteStack(item_id, '', '')` — the card's `kernel_stack` is cleared; the stack is over.
3. The branch is replayed on its next touch. `make_worktree` is given the fork point as well, and
   a branch whose recorded fork point is not an ancestor of `origin/<trunk>` is rebased
   `--onto origin/<trunk> <fork>` — its own commits only, never the predecessor's, which the
   trunk now holds as the merge of the predecessor's pull request. A conflict is aborted and
   handed to the existing conflict path (the item's pull request goes `conflicting`, and the
   rebase round is the one that already exists), never left in the worktree (P7, `spawn.py:946`).
   The replay is published the way every launch-time rebase is (`lifecycle.publish`, `:953`), so
   the session that follows starts on the branch origin holds.
4. From there the item is an ordinary Task with an ordinary pull request against the trunk: the
   review verdict on the replayed tree, auto-merge, the train, the gate.

If instead the predecessor is **archived, reset, reverted or parked** (D10): `A.NoteStack(item_id,
'', '')` clears the stack, `A.ArchiveAndReset` is issued for the stacked item's own pull request
with the reason `its base <base-branch> was rebuilt`, and the card waits on its edge again — which
is exactly where it would have been without the stack.

### 2.6 The knobs

```yaml
kernel:
  stack:
    enabled: true     # a Task whose one open after: edge names an item that has pushed starts on
                      # that item's branch instead of waiting for its merge (false: it waits)
    max_depth: 1      # how many levels deep a stack may go; 1 = never stack on a stacked branch
```

In `settings.SPEC` as `'stack': {'enabled': (True, bool), 'max_depth': (1, int)}`, carried onto
`model.Config` as `stack` and `stack_max_depth` by `ports.config` (`:2446-2455`), and documented
in `docs/products.example.yaml` beside `launch:`. `enabled: false` restores the trunk's behaviour
whole: no `NoteStack`, no stacked launch, no base on any `Launch` or `OpenPR`, no hold — the pass
returns `[]` before it reads an item.

## 4. Records

What the change writes down, and nothing more:

| where | what | written by | cleared by |
| --- | --- | --- | --- |
| the card's machine block, `kernel_stack: <base-branch>@<fork-sha>` | the stack a card is on and the fork point its replay uses | `A.NoteStack` through `record.write_fields` (P12); the key joins `ports.KERNEL_KEYS` | `A.NoteStack(id, '', '')` at the retarget or the teardown |
| the pull request on GitHub, `baseRefName` | the durable statement that this pull request is stacked, read back as `PR.base` every tick | `ports.open_pr(branch, base, …)` (P4) | `A.Retarget(pr, '')` |
| the session ledger row (`state/<product>/sessions.jsonl`), `base` and `base_sha` | which base this run was cut from, for a relaunch and for the reaper's ancestry checks | `spawn.spawn`'s record dict | nothing — a run's row is history |
| the wait ledger (`state/<product>/kernel-waits.jsonl`) | the `after` spell **ends** with a `building` row at the stacked launch; this is the card's measure, and it needs no new counter (P13) | `waits.record`, unchanged | — |
| the tick's own lines | `STACK <item> on <base-branch> @<sha>` at the launch, `STACK RETARGET <item> #<pr> -> <trunk>` at the unstack, and `stacked: waits for <base-branch> (<id>) to land` as the held item's note | `Plan.notes` and `apply.describe` | — |
| `metrics/events/<day>.jsonl` in the record clone | one `stacked-start` and one `stacked-land` event per stack, each naming the item, the predecessor, the base branch and the fork point | the kernel step's `ctx.event` | — |

No new state file, no new ledger, and no row the kernel does not already own.

## Stories

Six Stories: the fact, the launch, the host side, the pull request, the unstack, and the knobs
with the records. Each is **declared** below as a `### S-…: <title>` heading with its acceptance
lines under it, with ids from this session's range `S:135955-136004` — that heading is what
`asf.record.idcheck.declared_stories` reads and what `asf.record.plan_tasks` mints the card from,
so a cited id with no declaration is a phantom and the plan citing it is refused whole.

Each acceptance line is one physical line of plain text with no backticks, on purpose: the reader
is line-anchored (`asf.record.idcheck.CHECKBOX` matches a single line) and `_prose` replaces every
inline code span with one space before parsing, so a wrapped line reaches the minted card
truncated and an identifier inside backticks reaches it missing.

Nothing below is true on the trunk today except the lines that say an existing behaviour is
unchanged, which are the facts this change relies on rather than adds.

### S-135955: the stack as a fact — the card's own key and the pull request's base

Design §2.1 (D4; P5, P12). Two read-only fields and two pure helpers. The card says which branch
the work was cut from and at which sha; GitHub says which branch the pull request is open
against. Neither is inferred.

- [ ] a card with no stack key reads as not stacked, with an empty base and an empty fork point
- [ ] a card whose stack key names a branch and a sha reads back both, in that order
- [ ] a stack key with no sha after the separator reads as not stacked, because a fork point that is not recorded cannot be replayed
- [ ] a stack key whose sha is not a hex sha reads as not stacked
- [ ] the stack key is one of the machine keys the kernel owns, so reading a card's kernel fields returns it
- [ ] writing an empty stack removes the key from the card rather than storing an empty value
- [ ] a pull request fact carries the base branch GitHub reports for it
- [ ] a pull request whose base is the trunk is not stacked, and one whose base is another branch is
- [ ] a pull request read with no base field at all is not stacked
- [ ] the base field is filled from the same GitHub reply the change id is already hashed from, with no second read

### S-135956: the stacked launch — one open edge, a predecessor that has pushed, a free seat

Design §2.2 (D1, D2, D3, D5, D6; P1, P2, P3). The pass that starts the dependent Task. It
launches on the seats the ordinary pass left free and it changes no state: the card is New and the
edge is open before it and after it.

- [ ] a Task held New by one open edge whose predecessor is in Review launches, on the predecessor's branch, at the head origin holds for it
- [ ] the same Task with the predecessor in Landing launches too
- [ ] the launch carries the predecessor's branch as its base and the predecessor's head as its fork point
- [ ] a record write of the stack accompanies the launch, so the fork point is on the card before the session starts
- [ ] the card stays New and the edge stays open on the tick that launches the stack
- [ ] the count of items waiting on the predecessor is unchanged by the stack
- [ ] the wait ledger shows the item's after spell ending with a building row, and no new wait class
- [ ] a predecessor still Building does not get stacked on
- [ ] a predecessor that is New or Ready does not get stacked on
- [ ] a predecessor that is Stuck does not get stacked on
- [ ] a predecessor whose pull request conflicts with its own base does not get stacked on
- [ ] a predecessor that is parked does not get stacked on
- [ ] a predecessor whose own pull request is stacked does not get stacked on at the default depth
- [ ] raising the depth knob lets a stack on a stacked branch launch
- [ ] a card with two open edges never stacks, whatever state its predecessors are in
- [ ] a card whose one open edge names an id the record does not hold never stacks
- [ ] a Feature, a Story and an Epic never stack
- [ ] a spec and a plan launch never carry a base, because only build lanes stack
- [ ] a card that already holds a live session is not launched a second time by the pass
- [ ] a card that already has an open pull request of its own is not launched by the pass
- [ ] a card whose writes overlap a Building item's writes is not launched by the pass
- [ ] the pass launches nothing when no seat is free
- [ ] the pass launches nothing while the open-pull-request cap is exceeded
- [ ] the pass launches nothing on a paused product
- [ ] two stackable Tasks on one predecessor both launch when two seats are free
- [ ] the pass is a pure function of the facts, the config and the plan so far, and returns the same launches for the same arguments

### S-135957: the branch cut from the base, the brief that says so, and the footprint gate that follows it

Design §2.3 (D12; P7, P8, P9, P14). The host's half. One base value reaches the cut, the rebase,
the brief and the gate, so none of them can disagree with the others.

- [ ] a launch with a base cuts its fresh branch from the base branch on origin, not from the trunk
- [ ] a launch with no base cuts from the trunk, exactly as it does today
- [ ] a fresh stacked branch is rebased onto its base branch, never onto the trunk
- [ ] a stacked branch already on origin is not rebased onto the trunk by the launch
- [ ] a worktree reused for a stacked branch checks the branch out without recutting it from the trunk
- [ ] the session's environment carries the base branch
- [ ] the pre-push footprint check diffs the pushed head against the base branch when the environment names one
- [ ] that diff holds the Task's own paths only, so a stacked push whose paths are inside its footprint is not refused
- [ ] the same check diffs against the trunk when no base is named
- [ ] a base the repository cannot resolve leaves the footprint unchecked rather than refusing the push
- [ ] the brief names the base branch, the fork point and the predecessor card
- [ ] the brief tells the session not to merge or cherry-pick either the trunk or the base into its branch
- [ ] the brief's cut-from line names the base branch, never the trunk, for a stacked launch
- [ ] a cloud session's own checkout line names the base branch as its base
- [ ] no branch prefix, document path or trunk name is written as a literal by any of this, so the conventions check stays green

### S-135958: the pull request opened against the base, and never merged into it

Design §2.4 (D8, D9; P4, P6, P11). The pull request is the Task's own change, reviewed on its own
diff, and it cannot land anywhere but the trunk.

- [ ] a stacked item's pull request is opened against its base branch
- [ ] an unstacked item's pull request is opened against the trunk, as it is today
- [ ] a stacked item whose predecessor is already Done has its pull request opened against the trunk
- [ ] the pull request's files are its diff against its base, so the file-overlap rule sees the Task's own paths
- [ ] auto-merge is never enabled on a pull request whose base is not the trunk
- [ ] a merge of a pull request whose base is not the trunk is never planned, even when it is green, approved and clean
- [ ] the held item reads Landing and carries a note naming the base branch and the predecessor it waits for
- [ ] the hold is applied to the plan, so the actions the tick applies hold no merge of a stacked pull request
- [ ] a review is still launched for a stacked pull request once its checks are green
- [ ] a changes-requested verdict on a stacked pull request opens a fix round on its own branch, with the base unchanged
- [ ] a red check on a stacked pull request is judged exactly as it is on any other
- [ ] the merge train never selects a pull request whose base is not the trunk
- [ ] the still-needed gate reads a stacked pull request exactly as it reads any other

### S-135959: the unstack — retargeted to the trunk, replayed onto it, torn down when the base is rebuilt

Design §2.5 (D4, D7, D9, D10). The one moment the stack ends. Either the predecessor lands, and
the Task's commits are replayed onto the trunk and its pull request moved there, or the
predecessor's branch is rebuilt, and the stack goes away with nothing merged.

- [ ] a predecessor reaching Done produces one retarget of the stacked pull request to the trunk
- [ ] the same tick clears the stack key on the stacked card
- [ ] a pull request GitHub already holds against the trunk is not retargeted again
- [ ] the retarget is idempotent, so two ticks in a row plan at most one
- [ ] a retargeted pull request is landed by the ordinary path, with no hold left on it
- [ ] the branch is replayed onto the trunk from its recorded fork point, so the predecessor's commits are not replayed
- [ ] the replayed branch holds exactly the Task's own commits over the trunk
- [ ] a replay whose fork point is already an ancestor of the trunk does nothing
- [ ] a replay that conflicts is aborted and never left in the worktree
- [ ] a replay that conflicts leaves the item on the existing conflict path, not on a new one
- [ ] a replay that moves the branch is published, so the session that follows starts on the head origin holds
- [ ] a predecessor whose branch is archived and reset tears the stack down
- [ ] a predecessor whose merge was reverted tears the stack down
- [ ] a predecessor that is parked tears the stack down
- [ ] a teardown names the base branch as the reason the stacked item is rebuilt
- [ ] a teardown merges nothing and leaves the card waiting on its edge, exactly where it would have been without the stack
- [ ] a stacked item whose base branch is gone from origin and whose predecessor is not Done is torn down rather than left on a base that cannot be read

### S-135960: the knobs, the records, and a product that stacks nothing behaving exactly as today

Design §2.6 and §4 (D11; P13). The floor and the measure. With the knob off the trunk's behaviour
is unchanged to the action; with it on, every stack leaves a record a person can read afterwards.

- [ ] the two keys are in the kernel settings with the documented defaults
- [ ] a value of the wrong type under the block refuses the product load, naming the key
- [ ] an unknown key under the block is a warning, not an error
- [ ] the documented product file carries the block and still validates clean
- [ ] the configuration reader fills both fields on the config the kernel decides with
- [ ] with the knob off, a Task held by one open edge whose predecessor has pushed stays New and nothing launches
- [ ] with the knob off, no launch and no pull request carries a base
- [ ] with the knob off, the plan for a fixed set of facts is identical to the plan the trunk produces for them
- [ ] the new actions are in the applier's order, so a plan carrying them sorts
- [ ] the record write of a stack is applied before the launch that depends on it
- [ ] the stack start logs one line naming the item, the base branch and the fork point
- [ ] the unstack logs one line naming the item, its pull request and the trunk
- [ ] one event is written when a stack starts and one when it ends, each naming the item, the predecessor, the base branch and the fork point
- [ ] a dry run writes no card field, no event and no pull request, and prints the stacks it would start
- [ ] a blind tick starts no stack and retargets nothing
- [ ] a state directory that cannot be written leaves the tick green and the launch unchanged
