# F-0111 — the install a hook names

On 2026-09-24 a customer product's operator ran `asf-live hooks install --product <p>` from the
pinned live install — a pipx install made with `--suffix live`, sitting beside an editable dev
`asf` on the same machine. The product's `pre-push` is the product's own, so the command refused,
which is right. What it then told the operator to add was

```
"<operator home>/.local/bin/asf" redact --pre-push --product <p>
```

— the *dev* install's entry point, not the live one's. Following that line ties a customer
product's push gate to a working checkout that moves under it: the thing the live install exists
to prevent. The cause is one line: `asf.hooks.runnable_asf` resolves `asf` off `PATH`
(`shutil.which('asf')`), and `PATH` answers with whichever install is first, never with the one
that is running.

The same resolution writes the git hook bodies and the Claude Code settings commands, so the bug
has a second half that has not been seen yet only because nobody has installed hooks twice from a
suffixed install: neither recogniser knows the spelling such an install would write. A hook whose
line says `asf-live redact --pre-push` reads as *foreign* to the very command that wrote it, and a
settings entry whose command says `asf-live hook approvals` reads as *absent*, so the next run
refuses and the doctor goes red on hooks asf itself put there.

After this change, every command asf writes into a hook file or a settings file names the entry
point of the install that ran the write; the recognisers read back every form asf can write; a
hook asf wrote whose entry point has gone or points at a checkout is repaired by the next
`hooks install`, never downgraded by one; and the doctor's `redaction-hooks` row says out loud when
a product's gate is wired to an editable install.

### In

- **One resolver that answers with the running install.** `hooks.running_asf()` walks three routes
  in order and returns the entry point *and the route that found it*, so the install summary and
  the doctor can say which one answered.
- **Every written command comes from it** — the git hook body, the foreign-hook refusal line, and
  the settings command (P2), all three.
- **Both recognisers read back every form asf can write**, including a suffixed basename
  (`asf-live`) and the module forms, so a second `hooks install` from the same install changes
  nothing and never appends a second settings entry (P4, P5, P6, P7).
- **Repair, without downgrade.** A hook or settings entry that *is* asf's but names an entry point
  that has gone, or names an editable install while the running install is not one, is rewritten
  by `hooks install`. Two usable non-editable installs never overwrite each other, so alternating
  `asf` and `asf-live` runs cannot flap a hook file.
- **The doctor says it.** `redaction-hooks` flags a hook whose named entry point is missing, and a
  hook that names an editable install — unless the product *is* the factory's own source, where an
  editable install is what the product is (P16).
- **The operator-facing text follows**: the two refusal lines, the troubleshooting rows that quote
  them (P14), and the `product-config.md` line.

### Out

- **`asf init`'s bare `exec asf redact --pre-push` templates (P15).** They belong to the record repo
  and deliberately resolve at hook-run time, so an operator who moves install can move the record
  with it. The recogniser keeps accepting the bare form; nothing about it changes here.
- **A second console script name in `pyproject.toml`.** The suffix is pipx's, made at install time
  by whoever installs; the package has no business declaring `asf-live`.
- **Running the named `asf` to ask what it is.** The doctor reads files (P18) and never executes a
  path it found in a hook — a doctor that executes what a hook file names is a worse problem than
  the one it diagnoses.
- **Making `PATH` unreachable.** It stays the last route and the last resort: it is the only one
  that can name another install, and the new doctor row is what catches that (see D4).
- **Rewriting a foreign hook.** D10 of F-0075 stands: no hook file asf did not write is ever
  edited. This card only changes the *path inside the line it prints* for the operator to add.
- **Changing what `asf redact` does, or the hook's four-line shape.** Only the first word of the
  `exec` line changes.
- **Teaching the upgrade path about hooks.** A `pipx reinstall` that keeps the same bin path leaves
  every hook valid; one that does not is the missing-entry-point case, which the doctor now names
  and `hooks install` now repairs.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | `sys.argv[0]` is the first route, when its basename looks like an `asf` entry point and it is an executable file | the script beside `sys.executable` first | `argv[0]` *is* the entry point the operator invoked — `~/.local/bin/asf-live`, a stable symlink pipx recreates — and it is the shortest true answer to "which install is running". The venv's internal script is one indirection further from what the operator typed |
| D2 | The basename test is a name shape (`asf` plus any pipx suffix), never "any executable file" | accepting whatever `argv[0]` holds | `argv[0]` is `pytest` under the suite and `asf/cli.py` under `python -m asf.cli`; a resolver that wrote either of those into a hook would break every push. The shape test is also what keeps P13's fifteen call sites green |
| D3 | The second route — `dirname(sys.executable)/asf` — fires only when the script's shebang names that same interpreter *and* the distribution visible to this process resolves to the running package | taking the script whenever it exists | P12: from a clock snapshot the running package is a `PYTHONPATH` shadow, and the venv's script is a different install. Writing a snapshot-era path into a product's push gate outlives the snapshot and refuses every push |
| D4 | `PATH` stays, last | dropping it and refusing instead | it is today's answer and the only one available to a checkout run through `PYTHONPATH` with no entry point of its own; refusing there would take hooks away from a working setup. It is also the only route that can name a foreign install, which is exactly why the doctor gains the row that names one |
| D5 | The `<python> -m asf.redact` module form is recognised but never written | writing it as a fourth route, which cannot fail | a hook is read by operators; a two-word interpreter line is the least legible form of the four, and an install with no entry point at all is rare enough to be worth one refusal. P11/P4 keep the form working for anyone who writes it by hand |
| D6 | One helper (`prefer_entry`) decides "is the running entry point better than the one written", and both the git-hook repair and `merge` call it | letting `merge` keep its unconditional replace (P6) | with two installs on one machine an unconditional replace turns every run into a rewrite, so a dev-install tick would quietly re-point a live product's hooks. Same question, one answer, two call sites |
| D7 | "Better" means: a missing or non-executable entry point loses to any usable one, and an editable install loses to a non-editable one. Otherwise the written one is kept | preferring the running install always | it makes repair monotone: no pair of installs can flap a hook file, and running the doctor or a tick from a checkout can never downgrade a product's gate |
| D8 | Editability is read from `direct_url.json` under the shebang interpreter's site-packages, and an unreadable answer is `None` | inferring it from the path (`/checkout/` in the string), or from the running install's own editability | P18 makes it a two-file read with no execution; a path heuristic is a guess about someone else's layout. `None` never turns a row red — the doctor states what it could not read and stays green |
| D9 | The editable finding is suppressed when `is_factory_repo(product)` (P16) | flagging every editable hook | ASF's own factory runs from a checkout by design; a row that is permanently red on the factory's own product teaches operators to ignore it |
| D10 | The new tests live in two new modules (`tests/test_hooks_entry.py`, `tests/test_hooks_recognise.py`), not in `tests/test_install.py` | one more class in `test_install.py` | `test_install.py` is already the module all fifteen injecting sites live in (P13), and every Story here would write it. Two new modules let the recogniser Story and the writing Stories land in either order; the plan still sequences the two Stories that share `test_hooks_entry.py` |

## The design

### `asf/hooks.py` — the resolver

```python
#: The console-script name `[project.scripts]` declares (`pyproject.toml:18-19`). A pipx install
#: made with `--suffix <s>` exposes it as `asf<s>` in the bin dir and keeps this name inside the
#: venv (F-0111 P3), so either spelling may be written and both must be read back.
ENTRY_POINT_NAME = 'asf'

#: What an `asf` entry point may be called: the declared name with any pipx suffix appended.
#: Never `asf/cli.py` (what `python -m asf.cli` leaves in `argv[0]`) and never an interpreter.
ENTRY_NAME_RE = re.compile(r'^asf[A-Za-z0-9._+-]*$')

Entry = collections.namedtuple('Entry', 'path route')
```

`running_asf(argv0=None, executable=None, which=shutil.which)` → `Entry` or `None`. `argv0`
defaults to `sys.argv[0]`, `executable` to `sys.executable`; both are parameters so each route can
be driven from a test. The routes, in order:

| route | what it takes | when it counts |
| --- | --- | --- |
| `argv0` | `sys.argv[0]`, made absolute (a bare name resolved through `which`) | its basename matches `ENTRY_NAME_RE`, does not end `.py`, and the path is an executable file |
| `venv` | `os.path.join(dirname(abspath(executable)), ENTRY_POINT_NAME)` | it is an executable file, its `#!` line names `executable` or its realpath, and `same_install()` |
| `path` | `which(ENTRY_POINT_NAME)`, absolute | it is an executable file |

`same_install()` — the `asf-factory` distribution this process can see resolves to the package this
process is running: `importlib.metadata.distribution('asf-factory')`, then either
`locate_file('asf/__init__.py')` is the same file as `asf.__file__`, or its `direct_url.json` is
editable with a url path equal to `drift.factory_root()` (P17). False when the distribution cannot
be found, and false for a `PYTHONPATH` shadow — which is the snapshot case D3 exists for (P12).

`runnable_asf(which=shutil.which, argv0=None, executable=None)` keeps its `(path, refusal)`
contract and its name, so P2's three writers and P13's fifteen call sites are untouched in shape.
It returns `running_asf(...)`'s path, or one of two refusals:

- nothing answered:
  `NEEDS OPERATOR: this asf install has no entry point to name (argv[0] <argv0>, none beside <executable>, none on PATH) — pipx install asf-factory`
- a route answered with a path that is not an executable file: today's line, unchanged
  (`<path> is not an executable asf — no hook is written naming it; pipx install asf-factory`).

`install`'s summary line gains the route and the path it resolved, so a run from the wrong install
is visible without opening a hook file: `hooks: … ; entry: <path> (argv0)`.

### `asf/hooks.py` — reading back what asf writes

`is_git_hook_ours(text, name)` accepts exactly these, and the test table in
`tests/test_hooks_recognise.py` is the contract:

| form | example |
| --- | --- |
| bare name (P15, `asf init`'s) | `exec asf redact --pre-push` |
| quoted absolute path | `exec "/opt/p/bin/asf" redact --pre-push --product p` |
| **suffixed basename, quoted or not** | `exec "/opt/p/bin/asf-live" redact --pre-push --product p` |
| module form, either module | `exec "/v/bin/python3" -m asf.redact --pre-push`, `… -m asf.cli redact --pre-push` |
| not ours | `exec /opt/p/bin/asfmt redact-all --pre-push`, `echo "asf redact --pre-push"` inside a string, a `#` comment |

The expression becomes three branches — an entry-point basename followed by `redact --<name>`, or
`-m asf.redact --<name>`, or `-m asf.cli redact --<name>` — each anchored to a word boundary at
the left so a longer command name (`asfmt`) cannot match a shorter one. `hook_entry(text, name)` is
new beside it: the command the matched line names, unquoted — the entry-point path, or the
interpreter for a module form — used by the repair rule and by the doctor.

`_is_ours(command, name, product)` widens the same way: `(^|/)asf<suffix>? hook <name>` or
`-m asf.cli hook <name>`, with the existing `--product <p>` tail and its `$` anchor. P7 makes the
doctor's `approvals-hook` row correct by the same edit.

### `asf/hooks.py` — repair without downgrade

```python
def entry_point_source(path):
    """('editable', <checkout>) | ('installed', <site-packages>) | None — what install the entry
    point at ``path`` belongs to, read from files only (D8). ``None`` when it cannot be told."""
```

It reads `path`'s first line for `#!<interpreter>`, takes that interpreter's prefix, and globs
`lib/python*/site-packages/asf_factory-*.dist-info/direct_url.json` (and `lib/*/site-packages/…`,
for a layout that spells it otherwise). `dir_info.editable` true → `('editable', url path)`; a
dist-info without it → `('installed', dir)`; an unreadable or absent one, a `#!/bin/sh` wrapper, or
a module-form line → `None`.

```python
def prefer_entry(written, running):
    """True when ``running`` should replace ``written`` in a command asf already wrote (D6, D7):
    a missing or non-executable ``written`` loses to any usable ``running``; an editable
    ``written`` loses to a non-editable ``running``; an unknown or equal pair keeps ``written``."""
```

In `ensure_git_hooks` it becomes a third upgrade beside `init_hook_upgrade` and
`staged_check_upgrade` (P8): when the hook is ours and `prefer_entry(hook_entry(text, name),
entry)` is true, the file is rewritten with `_git_hook_body` and the summary says
`repaired <path>: <old> → <new>`. In `merge` it gates the in-place replacement (P6): a matching
entry whose command asf should not replace is left exactly as it is, and still counts as found, so
no second entry is appended.

### `asf/doctor.py` — the row that names a checkout

`check_redaction_hooks` keeps its shape and gains one branch per hook that is ours:

```python
entry = hooks.hook_entry(text, name)
source = hooks.entry_point_source(entry) if entry else None
if entry and not _usable(entry):
    problems.append(f'{path} names {entry}, which is not an executable asf')
elif source and source[0] == 'editable' and not is_factory_repo(product):
    problems.append(f'{path} names an editable install ({source[1]})')
```

The remedy the detail ends with becomes
`— asf hooks install --product <p>, run from the install the hook should name`. When the product
*is* the factory (D9) the green detail says so: `pre-commit, pre-push in <n> repos (editable
install: this product is the factory's own source)`. A `None` source adds nothing — neither a
problem nor a claim.

### The operator-facing text

`docs/guide/troubleshooting.md:43` (the `not on PATH` row) is replaced by the new refusal and its
remedy; `:45`'s quoted line keeps its shape, and a new row covers the two new findings
(`names <path>, which is not an executable asf`, `names an editable install (<checkout>)`), each
with the same remedy: rerun `asf hooks install --product <p>` *from the install you want named*.
`docs/guide/product-config.md:635` and `docs/guide/getting-started.md:64` gain the same sentence in
one clause: the hook names the install that ran the command.

## Records

Nothing new is written to the record, to `~/.ASF` or to any ledger. What changes is what asf writes
into files it already owns, and what it says about them:

- **Each git hook `asf hooks install` writes** — `<git-path hooks>/pre-commit` and `/pre-push` of
  `repo_dir` and `backlog_dir` — whose third line now names the entry point of the install that ran
  the command. An existing hook of asf's is rewritten only under D7, and the run says so:
  `repaired <path>: <old entry> → <new entry>`.
- **Each settings command** — `<repo>/.claude/settings.json` and every worker account's own
  `settings.json` — same rule, same helper. A run that keeps a command it should not replace writes
  no file at all (`_write_merged` already returns early when the merge is a no-op).
- **The `hooks install` summary line**, which gains `entry: <path> (<route>)` — the record of which
  install did the writing, readable without opening a hook file. `rc` stays 0/2 as it is.
- **The two refusal lines**, one of them new text (the one P14's test and
  `docs/guide/troubleshooting.md:43` quote), both still one `NEEDS OPERATOR:` line each.
- **The doctor's `redaction-hooks` detail**: two new problem strings and one new green clause. The
  row's name, position and `required` flag are unchanged, so every consumer of the doctor table
  reads it as before.
- **`docs/guide/troubleshooting.md`, `docs/guide/product-config.md`,
  `docs/guide/getting-started.md`** — the quoted lines and one clause about which install a hook
  names.
- No migration and no new config key. An operator with a single install sees one difference: the
  path in the hook is now the one they invoked, which for them is the same path `PATH` gave.
