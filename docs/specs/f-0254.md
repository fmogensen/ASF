# F-0254 — first in ASF's line, last at the runner

On 2026-10-06 (on 0.1.195) a product session asked for a PR in first — `asf land --priority` — and
then watched its required jobs sit queued for the heavy runner class for 40 minutes while six
lower-rank PR runs sat queued ahead of it. The session force-cancelled the six by hand, and the
priority PR's jobs started within the minute.

Round D (#13) had already made that PR's own run S1: first in the start queue, and never a relief
candidate (`relief: exempt <branch> — asf land --priority request, never cancelled`). Both halves
hold. Neither reaches the runner, because the host hands runners out first-in-first-out to jobs it
already holds, and ASF's line only decides what it *starts*. A run the host already has is past
the only lever the start queue owns.

The relief that is meant to be that second lever did run for the priority PR — and passed over
every one of the six. Measured below (P3): each of the six was its PR's *first* run on its head,
and relief exempts a first run on purpose — *"held before its start, never cut"* — because a cut
first run is a red mark on a PR for no defect of its code. So the exemption that protects an
ordinary PR from relief is exactly what left the priority PR waiting, and the hand cancel the
session fell back to is the behaviour this card has to make automatic and safe.

This card is: **while a priority PR's required jobs are queued for a runner class, the queued
lower-rank PR runs competing for that class are *held* — cancelled through `asf/run_cancel.py`,
recorded as `held_for` that PR, capped, re-dispatched the moment the priority PR has its runners
or stops being priority, and counted as the factory's own doing rather than as the PR's red.**
A hold is not a relief cancel: it takes nothing that is running, it throws away no sunk minute,
and it is undone without a hand retrigger — which is what earns it the right to touch a first run.

### In scope

- Which PRs the queue preempts for: an `asf land --priority` request's PR, and a goal-ranked PR
  (its item at rank 1 of the record's order), while a *required* job of its run is queued for a
  runner class.
- What a hold is and what it may take: queued lower-rank PR runs competing for that class, never a
  batch, trunk, in-progress or runner-holding run, never an S1/hotfix/priority run, never a
  CI-changing PR — and, unlike a relief cancel, a first run is fair game.
- The cap (`ci.queue.max_held`), the gate (`ci.queue.priority_preempt`), and the hold's own stop
  condition.
- The record a hold writes (`held_for` on the existing relief record), and the re-dispatch it is
  released by — the priority PR's required jobs having runners, **or** that PR no longer being a
  priority PR (landed, closed, request withdrawn, rank moved).
- How a held run reads afterwards: the cancel cause, the visible-reds class, and the PR's
  first-pass green.

### Preconditions the work depends on

- `asf/run_cancel.py` stays the one way the factory cancels a run: a queued run is force-cancelled
  (a plain `gh run cancel` on it is a no-op) and read back, and an accepted cancel the run does not
  confirm is said, never taken as done. The hold calls `_cancel_run`, which calls it; it adds no
  second cancel path.
- The `relief` list keeps its shape and its five readers (P6). A record written before this change
  carries no `held_for` and must keep behaving exactly as it does today.
- `priority(item, items, branch, product=...)` stays the one answer to where a branch's work sits
  in the line, and `_item_of_run` the one answer to which item a run is for.
- `_starved_jobs`, `_required_names`, `_job_labels`, `label_classes` and `saturation` stay as they
  are: the hold asks the same questions about the same host reads and adds no new `gh` call beyond
  the `live_jobs` reads the relief pass already makes for the same runs.
- The merge queue drops a request from `land-requests.json` when its PR lands (`drop_request`), so
  `land_priority` going False is already the record of "it landed or was withdrawn".

### Out of scope

- **The start queue's order.** A goal-ranked PR is protected by the hold; it does **not** become
  S1 in the line, is not exempt from the ceiling or the fit, and keeps its `RANKED` priority
  everywhere else. Reordering the line for rank 1 is a different card.
- **The S1 relief, the trunk relief and the escalation.** They keep their candidate sets, their
  thresholds, their first-run exemption and their right to cancel an in-progress run. A
  `land --priority` PR keeps being served by them as it is today (P2); the hold is an additional
  pass over what they pass over, never a replacement, and removes no power the priority PR has now.
- **Runs that hold a runner.** A queued run with a job already on a runner is the escalation's
  business, where the sunk minutes are weighed. The hold never takes one (C3).
- **Merge-queue batches.** Never held, priority or not: the batch is the trunk's next sha and a
  cancel costs the whole chain a re-cut. The existing exemption lines stand.
- **The host's hand-out order.** ASF cannot ask GitHub for a runner. This card removes rival
  claimants for the next freed runner; it does not reserve one (`ci.reserve` is that, and is
  untouched).
- **Relief's own unboundedness (P4).** The relief loop's stop condition is wrong for candidates
  that hold nothing, and this card does not fix it there: the hold gets a stop condition and a cap
  of its own, and relief keeps the behaviour (and the tests) it has. A card for `_fits` as a stop
  condition can follow.
- **`own_cancel_causes`, `reds_window` and the other scorecard knobs.** Defaults unchanged; the new
  class is counted under the configuration the product already has.

## The design

Everything is in `asf/ci_queue.py`, `asf/ci_cancels.py` and `asf/metrics/reds.py`, plus the two
new `ci.queue` fields. No new state file, no new `gh` call shape, no new cancel path.

### 2. The hold (C1, C3, C4, C5)

`relieve_trunk` gains one loop after its `s1_runs` loop, sharing the same `q`, `src`, `listed` and
`now` — so no extra host read:

```python
for r, item, why in priority_prs(product, items, pr_runs.values()):
    owner = f'priority PR run {r.get("databaseId")} ({item}, {why})'
    n += preempt_for_priority(product, q, src, items, listed, now, r, out, dry_run,
                              owner=owner, wait_s=s1_wait_min(product) * 60)
```

```python
def preempt_for_priority(product, q, src, items, listed, now, target, out, dry_run, owner,
                         wait_s):
    """Hold the queued lower-rank PR runs competing for the runner classes a priority PR's
    required jobs are waiting on.

    The host hands each freed runner to a queued job it can serve, not to the oldest (P5), so a
    priority PR that is first in ASF's line is still last at the runner behind enough queued
    rivals. Cancelling a rival that holds no runner frees nothing — it removes a claimant for the
    next one, which is the only lever ASF has over a run the host already holds.

    A candidate is a ``pull_request`` run of the PR workflow whose **every** job is still queued
    (nothing on a runner, nothing sunk — C3), which queues a job a runner able to take one of the
    starved jobs could serve, and whose ``(prio, record_rank key)`` is strictly behind the
    priority PR's. Never a batch, a trunk run, an S1, hotfix or priority run, or a CI-changing
    PR — the relief's own exemptions, each printed as it is today. A *first* run is a candidate
    (C4): a hold is undone, and the three things that made cutting one wrong are removed with it.

    Lowest priority first, newest first within it, until no competing queued job is left or
    ``ci.queue.max_held`` records are outstanding for this PR. Each is cancelled through
    :func:`_cancel_run` (:mod:`asf.run_cancel`: a queued run is force-cancelled and read back),
    claimed ``held``, and recorded in ``relief`` with ``held_for``. Nothing when the classes are
    not saturated (:func:`saturation`), when no required job is starved, or under a dry run.
    The number held."""
```

The shape, in order — each step is the relief pass's own, reused:

| Step | What | Reused from |
| --- | --- | --- |
| 1 | `priority_preempt` off, or `max_held` 0 → nothing, no host read | new |
| 2 | `_starved_jobs(product, src.live_jobs(tid), created, now, wait_s, headSha)` — a required job queued past `s1_wait_min`; none → nothing | `:3717` |
| 3 | `_fits(want, idle)` → nothing: a runner is already there for each starved job | `:3993` |
| 4 | `saturation(q._runners, q.pool, classes)` below `relief_saturation` → one line, nothing (P13) | `:4025-4037` |
| 5 | outstanding `= [rec for rec in q.data['relief'] if rec.get('held_for') == tid]`; at `max_held` → one line, nothing | new |
| 6 | candidates: the relief scan's own filters, plus *every job queued* and *strictly lower rank* | `:4041-4135` |
| 7 | order: `(group, -created, -id)` — lowest priority first, newest first | `:4133` |
| 8 | cancel while a competing queued job is left and the cap is not reached | new stop (C5) |
| 9 | `claim_cancel(..., 'held', now, for_run=tid)`, then the record with `held_for` | `:4179-4191` |

"Strictly lower rank" is one comparison, not a new order:

```python
def behind(prio, item, items, their_prio, their_item):
    """True when ``(prio, item)`` sits after ``(their_prio, their_item)`` in the queue's own
    order: a lower priority, or the same priority and a later :func:`record_rank` key. Equal rank
    is never behind — a goal-ranked PR never holds another run of its own Feature."""
```

### 3. The record, and the re-dispatch (C5, C6)

The record is a relief record with one more field — so `rerun_ids`, `sweep`, the TTL and
`STUCK_MAX_S` drops, `stuck_lines` and `_rerun_cancelled` all read it with no change (P6):

```python
rec = {'id': rid, 'kind': kind, 'item': item, 'prio': prio, 'label': label, 'workflow': wf,
       'at': _iso(now), 'branch': r.get('headBranch'), 'sha': r.get('headSha'),
       'attempt': _attempt(r), 'held_for': tid, 'held_branch': target.get('headBranch'),
       'held_why': why}
```

`held_for` is the priority PR's **run id** (what `started` needs), `held_branch` its branch (what
`land_priority` needs once the run is gone from the listing) and `held_why` the reason it was
protected, for the line. `trunk_id`/`trunk_sha` are **not** set: a held record is not a trunk
record, and P7's `rec.get('for') is None` arm must not claim it. `started(rec)` gains one arm,
first:

```python
def started(rec):
    if rec.get('stall'):
        return None, 'its stalled step'
    if rec.get('held_for') is not None:
        r = held_started(rec)
        return None if r is None else (r, 'priority PR')
    ...
```

```python
def held_started(rec):
    """The priority PR's run once the hold is over: its required jobs are all on runners, or it
    has left the queue or the listing (:func:`s1_started`'s own reading, reused) — **or** it is
    no longer a priority PR: its ``asf land --priority`` request is gone (it landed, or was
    demoted) and its item is no longer goal-ranked. None while the hold stands."""
```

Then `_rerun_cancelled` re-runs it as it re-runs every relief record: through the queue, at the
priority re-read from the record each ask, `gh run rerun` unless the workflow changed on the trunk
since (then a fresh dispatch once admitted), with the refusal counting, the `stuck` state and the
drops all unchanged. **No hand retrigger anywhere on the path** — which is the acceptance.

Design §3 (*The record, and the re-dispatch*) — `held_for`/`held_branch`/`held_why` on the
existing relief record, `held_started` as `started`'s first arm, and `_rerun_cancelled` doing the
re-dispatch it already does for every relief record (C5, C6; P6, P7). Acceptance is the third
fenced block of `## Acceptance tests`. The land arm is the one `s1_started` has not got (P7): a
priority PR that lands through the merge queue without its own run ever getting a runner would
otherwise leave its holds waiting on a run that will never start.

- [ ] while the priority PR's required job is still queued the held record is kept and nothing is re-run
- [ ] once that required job is on a runner the held run is re-run through the queue at the record's own priority and the record leaves relief
- [ ] the record is released the same way once the priority PR's run has left the queue statuses
- [ ] the record is released the same way once the priority PR's run is gone from the listing
- [ ] the record is released once the priority PR's land request is dropped and its item is no longer goal-ranked, while that run and its required job are both still queued
- [ ] a held record is not read by the trunk arm: with the trunk run queued it is not re-run as though the trunk had started
- [ ] rerun_ids carries the held run's id, so the lane waits for the re-run instead of handing the branch back on the cancelled check
- [ ] a held branch whose workflow changed on the trunk since the hold gets a fresh dispatch instead of a replay
- [ ] sweep drops a held record whose branch can no longer start, together with its rerun entry
- [ ] a relief record written before this change, carrying no held_for, is read exactly as it is read today
