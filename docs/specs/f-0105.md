# F-0105 — the landing gate runs on the product's CI, not on the operator's machine

The harvest gate is the product's whole test suite, and today it runs in a throwaway worktree on
the same host as up to eight worker sessions. On 2026-09-23 a gate that takes about 95 s alone took
15–25 minutes; `tests.test_cutover` ran `tools/cutover.sh` about every 13 s for more than thirteen
of them, and `gate_timeout_s` had to be raised to 1800. Since 989b775 a slow gate no longer blocks
the wave, but landing latency is still gate time, and every second of it is CPU taken from the
sessions doing the work.

The product already has a CI that runs exactly this suite on hardware nobody else is using. This
spec moves the landing gate there, under a product switch, and keeps the per-module timings that
say which module is worth trimming next.

Operator direction (2026-09-23): speed and cost first.

### In

* A product switch that moves the fast-forward landing gate onto the product's own CI, default off.
* Pushing the combined head as a gate ref, waiting for that ref's workflow run across ticks, landing
  the **gated sha itself** on green and holding on red — with the red branch's correction carrying
  the same failing line and files the local gate gives it today.
* Cleaning gate refs: the ones this factory is done with, and the ones it left behind.
* `NEEDS OPERATOR` when the product names no workflow, or names one that never starts on the ref.
* Per-module timings kept from **either** gate, and the slowest modules named in the daily rollup.

### Out

* **Any change to the default.** `gate_where` defaults to `local`; a product that does not set it
  behaves exactly as it does today, down to the transcript. Every Story below is inert on the trunk
  until an operator turns it on, which is what makes them safe to land in sequence.
* **The PR landing mode.** `merge: queue` already gates a batch ref on CI for PR products (P8) and
  is untouched. This card is the fast-forward mode's missing half, and it borrows that module's
  shape without changing it.
* **Stacking gates.** At most one gate in flight per landing class. `merge_queue.inflight` exists
  and could be copied later; doing it now would double the states to test for a throughput problem
  nobody has measured yet. Named in Records as a follow-up.
* **Trimming `tests.test_cutover`.** This card makes it *visible* — the card's own words are "the
  first to look at". Which module to trim, and how, is the card that the first rollup naming it
  files.
* **Changing what a worker session runs.** P23's brief rule stays true and stays as it is. The
  approvals guard that stops a session running the product's full suite on an external-CI product
  (`asf/approvals.py:875-877`, `:968`) is likewise untouched: it keys off the PR landing mode, and
  widening it is a different decision about sessions, not about the gate.
* Raising, lowering or removing `gate_timeout_s`. It bounds a local gate; a CI gate has its own
  clock (D6) and the local one keeps its meaning for products still on `local`.

## The design

### 1. The switch — `asf/conventions.py`

One scalar field and one map registration.

```python
#: ``harvest.gate_where``: where the landing gate's suite runs — ``local`` (this host, in a
#: throwaway worktree: :func:`asf.harvest.harvest.product_gate`) or ``ci`` (the product's own
#: CI, on a pushed gate ref: :mod:`asf.ci_gate`). Orthogonal to ``harvest.gate``, which says how
#: many gates a tick runs, not where any of them runs.
DEFAULT_GATE_WHERE = 'local'
GATE_WHERE_VALUES = ('local', 'ci')
```

`HARVEST_KEYS` gains `'gate_where': 'gate_where'` (`:182-183`); `Conventions` gains
`gate_where: str = DEFAULT_GATE_WHERE` beside `harvest_gate` (`:669`); `MAP_CONVENTIONS` gains
`'ci_gate'` (`:321-322`); and a value outside `GATE_WHERE_VALUES` is a shape finding, not a silent
default. `docs/products.example.yaml:81-86` gains the key under the `harvest:` block it already
documents, and `docs/guide/product-config.md:23`/`:79` gain its row.

### 2. The workflow trigger — `.github/workflows/tests.yml`

P10 is the reason nothing would run. One line, on the existing workflow — never a second workflow
file (P12):

```yaml
on:
  push:
    branches: [main, 'gate/**']
  pull_request:
```

The B-0053 comment above it is extended, not replaced: a push to a *worker* branch is in-progress
work and still starts nothing; a gate ref is the opposite — it is a candidate trunk, and gating it
is the only reason it exists. The existing comment already carries the same exemption for
`merge: queue`'s batch ref (`docs/products.example.yaml:79-80`).

### 3. The gate itself — `asf/ci_gate.py` (new)

A sibling of `asf/merge_queue.py`, built on its shape (P8) and reusing its two pure functions where
they fit. Module state: `state/<product>/ci-gate.json` — `{"gates": {"<class>": {ref, sha, cut_at,
members: [...], split: [[...],[...]] | null}}}`, at most one gate per landing class (Out).

```python
DEFAULTS = {'ref_prefix': 'gate/', 'run_wait_min': 10, 'timeout_min': 120}
```

`settings(conv)` reads `conv.map_of('ci_gate')` over those, per-key, exactly as
`merge_queue.settings` does. `enabled(conv)` is `str(conv.gate_where).strip().lower() == 'ci'`.

**`cut(lane, group, cls, st)`** — the combined head, pushed. Identical to today's first half:
`combined_head` (P3) in a throwaway worktree, every conflict through the existing `hold` → `send_back`
path, so a conflicting branch still goes back on the same tick with the same words. Then the head is
pushed once as `<ref_prefix><stamp>-<sha9>` over `lane.guarded` (P21), the gate is written to the
state file, and every member goes `WAITING_CI` with `gate <ref> cut, waiting for CI`. **No test
process is started.** Under `lane.dry_run` the function prints what it would cut and returns before
the worktree is made (P9).

**`judge(lane, gate, st)`** → `(state, why, detail)`, in this order, borrowing `merge_queue.judge`'s
ladder:

| verdict | when | what happens |
| --- | --- | --- |
| `moved` | a member's head moved, or it is no longer `WAITING_CI` on this ref | drop, delete the ref, the rest re-cut next pass |
| `stale` | the ref is gone from origin, or moved off the gated sha, or the trunk moved to a sha the gate does not contain | drop, delete the ref if it is still ours, re-cut next pass |
| `no-run` | no run of `conventions.ci_workflow` on the ref, age < `run_wait_min` | `WAITING_CI`, `gate run not started yet` |
| `no-workflow` | no `ci_workflow` configured, **or** no run after `run_wait_min` | §4 — `NEEDS OPERATOR`, drop, delete the ref |
| `pending` | the run exists and has not concluded | `WAITING_CI`, `gate run <id> <status>` |
| `timeout` | still pending past `timeout_min` | drop, delete, re-cut — unknown, never red, never a correction (D6) |
| `unknown` | the run concluded `cancelled`, `timed_out` or `skipped` | as `timeout` |
| `red` | the run concluded anything else non-`success` | §3.1 |
| `green` | the run concluded `success` | §3.2 |

The run is found with one `H.gh_json(['run', 'list', '-R', slug, '--workflow', <ci_workflow>,
'--branch', <ref>, '--limit', '20', '--json', 'databaseId,status,conclusion,createdAt,headSha'])`
— `ci_flight.run_in_flight`'s exact read shape (`asf/ci_flight.py:47-51`), narrowed to the run whose
`headSha` is the gated sha, newest first. The slug is `lane.slug or lane_mod.repo_slug(lane.product)`
(P5): a fast-forward lane has none, and this is the one thing it needs one for.

**3.1 Red.** One `H._gh(['api', f'repos/{slug}/actions/runs/{run_id}/jobs'])` names the failed job;
one `H._gh(['api', f'repos/{slug}/actions/jobs/{job_id}/logs'])` fetches its log (D7). Over that
text, unchanged: `H.first_failing_line`, `H.gate_files`, `H.red_modules` (P17). Then

* the **trunk-alone** read (D4): the newest completed `push` run of the same workflow on
  `origin/<trunk>` at the current trunk sha. Red there → every member `WAITING trunk-red`, the ref
  dropped, nobody blamed — the same outcome `gate_one_set` reaches today through `red_on_trunk`, and
  the same words.
* one member left → `send_back(lane, f, 'gate', <first failing line>, <files>)`, the lane's existing
  path, so the session gets the correction it gets today plus the run's URL in the text.
* more than one → split (D5): the halves are written to the gate's `split` and the first is cut on
  the next pass; the second waits. Each half is cut **on the trunk alone**.
* a log that could not be read degrades the text to `gate red: <job> — <run url>` and the files to
  `()`. The verdict is unaffected.

**3.2 Green.** `land(lane, gate)` — `MERGING` on every member with the gate sha, one
`gitpush.push(['-q', 'origin', f'{sha}:refs/heads/{trunk}'], refs_only=True)` after re-reading that
the trunk is still an ancestor of it (D3), `MERGED` at that sha, member branches deleted, the gate
ref deleted, `lane.results[branch] = 'landed'`. This is `push_set`'s tail (P2) and
`merge_queue.land`'s body; the trunk moving under the push is not an error — the next pass reads the
gate as `stale` and cuts it again.

**3.3 The sweep.** Once per pass, `clean(lane, st)` lists `origin` refs under `ref_prefix` and
deletes every one the state file does not claim, newest `ORPHANS_PER_PASS`-bounded (`lane.py:237`),
through `lane.ref_push(':refs/heads/<ref>', …, done=lambda: lane.ref_gone(ref))` (P21) — a tick that
died between the push and its state write leaves exactly this, and without the sweep those refs
accumulate and keep starting runs forever.

### 4. `NEEDS OPERATOR` — the line and the row

Two causes, one line (D9):

* `gate_where: ci` and `conventions.ci_workflow` unset →
  `NEEDS OPERATOR: product <name> gates on CI but names no conventions.ci_workflow — set it to the workflow that runs the suite (e.g. tests.yml), or set harvest.gate_where: local`
  Nothing is cut; every entry `WAITING_CI`.
* a ref pushed and no run after `run_wait_min` →
  `NEEDS OPERATOR: no <workflow> run started on <ref> within <n> min — add the gate ref prefix to the workflow's push triggers`
  The ref is deleted and the members are `WAITING_CI`; the next pass cuts again and says it again
  until a person acts, which is correct — nothing is lost, nothing lands.

The line is printed through `lane.out` and the cause is written to the state file as
`{"needs_operator": {"why": …, "at": …}}`, read back by `ci_gate.needs_operator_line(product)` and
surfaced as a doctor row by `doctor.check_ci_gate`, in the shape of `check_gate_speed` and
`check_ref_pushes` (P22) — a `NEEDS OPERATOR` that only ever appeared in one tick's output is a
`NEEDS OPERATOR` nobody sees.
