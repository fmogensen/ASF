# F-0267 — the queue head was a batch that did not exist

On 2026-10-07 a product's CI queue stood at the head of its line on an entry nobody could start.
A PR run — run 37532396976 on `cloud/T-0484` — had been cancelled as starvation relief for a
higher-priority run and queued to re-run. The host then went offline: `gh run rerun` was refused
three times, the fresh dispatch that follows the third refusal was refused too, and the record
was marked `stuck`. It then sat in `ci-queue.json`'s `relief` for over three hours, its
`rerun:cloud/T-0484` entry at the head of the line the whole time, while the status row read

```
CI START STUCK batch run 37532396976 (batch) on cloud/T-0484 for 204 min — …
```

with no merge-queue batch anywhere on the product.

The lie and the hold are the same defect. The queue decides a candidate run's `kind` by
elimination — *not a PR run, not a trunk push, therefore a batch* — and then overwrites its item
with the literal string `batch`. A product that does not declare a batch workflow of its own runs
all three kinds out of one workflow file, so every push run on every ordinary branch is a "batch"
(P1, P2). And a record labelled `batch` is invisible to the two passes that would have cleared
it: the stale sweep looks at `kind == 'pr'` records only (P4), and the per-minute start pass
starts `kind == 'pr'` entries only (P5). The record's only remaining reader was the 30-minute
stuck retry, and its only remaining bound the 24-hour TTL (P7) — so the entry kept its place, and
its three heavy runners, against every start behind it (P6).

This card is: **a run's kind is read, never inferred; a branch run is a branch run everywhere the
queue sizes, sweeps and starts; and a record the queue has given up on holds no place in the line
and leaves it on a bound measured in minutes, not a day.**

### In scope

- The kind a relief or stall record is written with, and the item it carries: one classifier, used
  by the relief candidate scan and by the step-silence watch.
- A non-trunk `push` run of a shared workflow being handled as the branch run it is — in the
  relief order, in the runner fit, in the starvation guard, in the stale sweep and in the
  per-minute start pass.
- A relief record the queue has given up on (`stuck`): it keeps no place in the line while it is
  stuck, and it leaves the file on a bound of its own.
- The lines all of that prints: the cancel line, the `asf ci queue` row, the status clause, the
  doctor's `ci runners` row, the drop line.

### Preconditions the work depends on

- The queue file keeps its shape: `relief` a list of records each carrying `id`, `kind`, `item`,
  `branch`, `sha`, `workflow`, `at`, and `entries` a map keyed `pr:<branch>` / `rerun:<branch>` /
  `trunk:<branch>` (`load` normalises both, `asf/ci_queue.py:1732-1733`). A file written before
  this change still carries `kind: 'batch'` records; they must be read, not crashed on.
- `_batch_ref` stays the record of what a merge-queue batch ref is (P12), and a batch run on one
  stays exempt from relief altogether.
- `priority(item, items, branch, product=...)` stays the one answer to "where does this branch's
  work sit in the line", and `_item_of_run` the one answer to "which item is this run for".
- Relief keeps its existing candidate *set*: this card relabels and re-sorts candidates, and
  cancels no run that is not a candidate today.

### Out of scope

- **`RELIEF_TTL_S`.** The 24-hour backstop for a record nothing ever started stays as it is; this
  card adds a tighter bound on the one path that reaches it in practice (`stuck`), and does not
  touch the other.
- **The refusal counting itself.** `RERUN_REFUSALS_MAX` 3, the fresh-dispatch fallback and the
  30-minute retry are the right shape and are not re-opened; what changes is what the record
  costs the line while they run, and when they stop.
- **The `started` claim a refused re-run leaves behind.** `admit` moves an entry to `started`
  before the `gh run rerun` that is then refused, and that claim expires on its own at `PICKUP_S`
  (3 min, P7). Three minutes is not the 204 the card is about; a separate card may reclaim it.
- **Why the host refused.** `gh` being offline, rate-limited or 503 is the host's business; the
  queue's business is not to hold a line on it. The refusal reason stays on the record and in the
  line, verbatim, as it is today.
- **Cancelling push runs at all.** Relief cancels a non-trunk push run today (P2 measures the
  cancel) and still will. Whether a branch with no PR should hold heavy runners is a different
  question, for a different card.
- **`cancel_duplicate_pushes`.** It already has its own correct rule for a push run a PR run
  covers, and it writes no relief record (it is never re-run). Untouched.
- **The merge queue.** No batch is cancelled, rebuilt or re-run differently by this card; the only
  change a real batch sees is that `item` falls back to `'batch'` instead of being overwritten
  with it.

## The design

Everything is in `asf/ci_queue.py`, plus three rows for the new timing (`asf/config_keys.py`,
`docs/config.example.yaml`, and the `TUNABLES` map).

### 1. `run_kind` — the one classifier (C1, C2)

```python
#: the kinds a run of a watched workflow can be: the trunk's own push run, a PR run, a
#: merge-queue batch, and a push (or dispatch) on an ordinary branch
TRUNK_KIND, PR_KIND, BATCH_KIND, PUSH_KIND = 'trunk', 'pr', 'batch', 'push'
#: a run of one branch's work: sized, swept, guarded and started alike (:func:`fit_applies`,
#: :func:`starved`, :func:`sweep`, :func:`start_admitted`)
BRANCH_KINDS = frozenset({PR_KIND, PUSH_KIND})


def declared_batch_workflow(product):
    """``ci.queue.workflows.batch`` when the product declares one of its own — a workflow whose
    non-PR runs are batches by declaration — else None. The bare ``ci.workflow`` fallback is not
    a declaration: it is the same file the PR and trunk runs use (F-0267)."""


def run_kind(product, branch, event, workflow):
    """What a run of a watched workflow is, read off the run and the product's declarations:

    * ``trunk`` — a ``push`` run on the product's trunk branch;
    * ``pr`` — a ``pull_request`` run of the PR workflow;
    * ``batch`` — a run on a merge-queue batch ref (:func:`_batch_ref`), or a non-PR run of a
      batch workflow the product declares for itself (:func:`declared_batch_workflow`);
    * ``push`` — everything else: a push or dispatch on an ordinary branch, in a file the
      product also runs its PR runs from.

    Never by elimination: before F-0267 every non-PR, non-trunk run of the batch workflow was a
    ``batch``, and with no ``ci.queue.workflows`` declared that is every push run on every
    branch — one of them held a queue head for 204 min as a batch that did not exist.
    """
```

The relief candidate scan (`:3954-3958`) becomes one call and one `continue`:

```python
kind = run_kind(product, branch, ev, wf)
if kind == TRUNK_KIND:
    continue                                # a trunk run is never cancelled
```

and the grouping (`:3988-3991`):

```python
if kind == BATCH_KIND:
    group, label, item = 3, 'batch', item or 'batch'    # C4: a fallback, not an overwrite
else:                                       # the line's order reversed: other, ranked, S2
    group = {OTHER: 0, RANKED: 1}.get(prio, 2)
```

`_stall_kind(product, run)` becomes `run_kind(product, run.get('headBranch'), run.get('event'),
run.get('workflow'))`, keeping its `trunk` arm as the classifier's own.

**What changes on the wire.** A push run on `cloud/T-0484` under a shared workflow is now
`kind: 'push'`, `item: 'T-0484'`, `label` and `prio` its branch's own, and it is cancelled in its
item's tier rather than behind every batch — a push run of a ranked item goes before an unranked
PR run's, which is what the module's stated order has always said ("PR runs of branches the
record has no item for, then of the record's ranked items, then of S2 items, then batch runs").
The cancel line reads `cancelled queued push run 37532396976 (T-0484, Task) — main run 900 …`.
A declared batch workflow's runs, and merge-queue batch refs, are untouched.

### 2. A push run is a branch run everywhere (C3)

| Site | Today | After |
| --- | --- | --- |
| `fit_applies` (`:2132-2138`) | `kind in ('pr', 'batch')` | `kind in BRANCH_KINDS \| {BATCH_KIND}` |
| `ceiling_applies` (`:2141-2147`) | `kind == 'batch'` | unchanged — the ceiling is the batch step's gate |
| `starved` (`:2183-2190`) | `kind != 'pr'` → never starved | `kind not in BRANCH_KINDS` → never starved |
| `start_admitted`'s filter (`:4200`) | `entries[k].get('kind') == 'pr'` | `entries[k].get('kind') in BRANCH_KINDS` |
| `sweep`'s branch backfill (`:3458`) | `rec.get('kind') != 'pr'` → skip | `kind not in BRANCH_KINDS` → skip |
| `sweep`'s record arm (`:3488`) | `rec.get('kind') == 'pr'` | `rec.get('kind') in BRANCH_KINDS` |
| `sweep`'s "no open PR" drop (`:3497-3499`) | every record in the arm | `pr` records only; a `push` record with no PR is kept and judged by its runs |
| `sweep`'s newest-record map (`:3481`) | `pr` records | every `BRANCH_KINDS` record |

The remaining drops in that arm — a draft PR, a superseded head, a newer run covering the sha, a
later attempt running already, a newer record for the same branch and sha — apply to a `push`
record exactly as they do to a `pr` one; they read the listing and the record, not the PR.

The entry a `push` record places is keyed `rerun:<branch>` as every re-run entry is, and
`start_admitted` now starts it: `has_pr` is already True for every `rerun:` key, so the entry
takes the ordinary `_start_run` path, and a refused start is the existing one loud `START FAILED`
line that drops the entry, the `started` claim and the relief record together.

### 3. A record the queue has given up on holds no place in the line (C5, C6)

**Parking.** `_rerun_refused` already writes `rec['stuck'] = {'since', 'tried', 'why'}` when both
the re-run and the fresh dispatch are refused. It now also parks the record's entry:

```python
def park(entries, key, why, now):
    """Mark the line entry ``key`` parked: it cannot start whatever is free, so it sets nothing
    aside, is never the head and never the status row's head — and it keeps its ``since``, so
    its place in line is waiting for it when it can start again."""
    e = entries.get(key)
    if e is not None:
        e['stuck'] = {'at': _iso(now), 'why': why}
```

and `Queue.admit` clears it on the key it is asked about (`e.pop('stuck', None)` beside the
`e.update(...)` at `:2683`): a record asking for its start is, by definition, no longer parked.

**Reading it.** `decide` gains the class:

```python
def parked(order, entries):
    """The keys of entries the queue has given up on starting (:func:`park`)."""
    return frozenset(k for k in order if (entries.get(k) or {}).get('stuck'))
```

- `skip = ceiling_held(...) | parked(order, entries)` — so a parked entry sets nothing aside in
  `shortfall`, is passed over by `head_of`, and never takes `backfill`'s room;
- `if key in skip:` splits — a parked key answers
  `parked — its cancelled run could not be re-run (stuck 45 min); it holds no runners`, every
  other skipped key keeps `ceiling_reason`;
- `Queue._mark_head` takes the parked keys as `skip` too, so `head_since` moves to the entry
  behind and the head guard's clock belongs to something that can actually start;
- `_status_clause` names the first unparked decision as the head (`line.decisions` already
  carries every entry; the parked ones are printed by `asf ci queue` in line order with their
  parked reason, and by the status row through `stuck_lines`, which is unchanged).

### 4. And it leaves the line on a bound (C7, C8)

```python
#: a cancelled run the queue could neither re-run nor start fresh for this long is dropped: the
#: refusals are not going to stop, and a dead record is a red row and a place in a line (F-0267)
STUCK_MAX_S = 2 * 60 * 60
TUNABLES = {..., 'STUCK_MAX_S': 'ci.stuck_max_s'}
```

`_rerun_cancelled`'s per-record head (`:3144-3147`, beside the TTL drop) gains:

```python
stuck = rec.get('stuck') if isinstance(rec.get('stuck'), dict) else None
if stuck and _age(stuck.get('since'), now) > tunable('STUCK_MAX_S'):
    out(f"ci queue: drop {_rerun_key(rec)} — cancelled {rec.get('kind')} run {rid} "
        f"({rec.get('item')}) on {rec.get('branch') or '?'} could not be re-run or started "
        f"fresh for {int(_age(stuck.get('since'), now) // 60)} min (last: {stuck.get('why')}); "
        f"{_then(rec)}")
    entries.pop(_rerun_key(rec), None)
    continue
```

where `_then(rec)` is `the branch's next push runs fresh` for a `push` record and
`its open PR starts again from the lane` for a `pr` one (P11). The record and its entry leave
together, as every other drop in that loop already does. `ci-cancels.json`'s claim stays (C8), so
the run still reads as "cancelled by relief" and not as a host cancel or a verdict.

Once the record is gone, `stuck_lines` returns nothing for it, the doctor's `ci runners` row goes
green again, and the Capacity row's clause loses the clause it had carried for hours.

## Records

- **`<state>/<product>/ci-queue.json` → `relief[]`** — each record's `kind` is now one of `pr`,
  `push`, `batch` (a `trunk` run is never recorded: it is never cancelled), and its `item` is the
  item its branch or title names, with `'batch'` only as the fallback for a batch run that names
  none. The fields are otherwise unchanged; a record written before this change keeps its
  `kind: 'batch'` and is read as one.
- **`<state>/<product>/ci-queue.json` → `entries{}`** — a parked entry carries
  `stuck: {at: <iso>, why: <text>}` beside its existing `since`/`kind`/`item`/`prio`/`label`/
  `workflow`/`run`/`sha`. The key cleared by the next `admit` of that key. No new entry key shape:
  a push run's held re-run is `rerun:<branch>` as every other is.
- **`<state>/<product>/ci-cancels.json`** — unchanged, and explicitly *not* withdrawn when a stuck
  record is dropped (C8): the run was cancelled by relief and still reads that way.
- **`asf/config_keys.py`** — one row, `'ci.stuck_max_s': (NUM, 1, None)`, beside
  `ci.stuck_retry_s`; **`docs/config.example.yaml`** — one commented row under the `ci:` block,
  `stuck_max_s: 7200   # a stuck cancelled run is dropped after this long` (P10: the suite fails
  without it).
- **stdout / the operator's three screens** — the relief cancel line and the `STUCK` line now
  name `push run <id> (<item>, <label>)`; `asf ci queue` prints a parked entry with
  `parked — … ; it holds no runners` and its head row names an entry that can start; the doctor's
  `ci runners` red row and the Capacity row's stuck clause both clear when the record is dropped,
  instead of standing until the next day.
- **What is no longer written** — no relief or stall record naming `batch` for a run that is not
  one; no `CI START STUCK batch run …` on a product with no batches; no queue head, status head
  or set-aside claim belonging to a record the queue has already given up on; and no stuck record
  older than `STUCK_MAX_S`.

## Stories

- S-65654: A run's kind is read, never inferred — one `run_kind(product, branch, event, workflow)` over `trunk`/`pr`/`batch`/`push`, where `batch` means a merge-queue batch ref or a batch workflow the product declares for itself, called by both the relief candidate scan and `_stall_kind`, with a batch's `'batch'` item demoted from an overwrite to a fallback, so a push run on an ordinary branch of a shared workflow is recorded as the branch run it is, under the item its branch names — acceptance: `python3 -m unittest -v tests.test_ci_queue.ARunsKindIsReadNotInferred`
