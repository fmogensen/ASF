# F-0109 — `install.sh`: the half only the operator can run, and the hooks step that never asked

Epic: E-0001 — ASF 0.1 — a working factory. Branch: `spec/F-0109`.

The card was written on 2026-09-24, installing ASF for the first customer product off the README
path. Two of its three findings are still true in this checkout; one was ruled out of the
installer on the same day.

What has changed since the card: the package is no longer installed under a suffix — step 1 is
one `pipx install --force git+<url>@<ref>` as the command `asf`, held across the product's tick
lock (`tools/install.sh:94-125`) — and B-0131's step 6 landed, so the console's own allow list is
now *offered*, never written, and the operator runs `asf console-permissions install` themselves
(`tools/install.sh:192-197`, `asf/console_perms.py:26-33`). Neither of those touches the two
findings below.

**Finding 1 — the script is one command with two owners.** Step 1 is a network install of a
package from a git URL. A Claude Code session in auto mode is refused it by the runtime's own
classifier, and the session cannot grant itself the rule that would allow it — that refusal is
the runtime's, upstream of the approval matrix, and nothing in this repo can clear it. So today
the whole script belongs to a human at a terminal, including steps 3-6, which are ordinary `asf`
commands a session runs every day. The operator cannot install from a phone or the web, and a
session told to install gets as far as step 1 and stops with nothing done.

**Finding 3 — step 3 writes tracked files without asking.** `asf hooks install` puts `pre-commit`
and `pre-push` into `git rev-parse --git-path hooks` of `repo_dir` and `backlog_dir`
(`asf/hooks.py:173-216`, `:66-84`). When a repo sets `core.hooksPath` at a directory it versions
— `.githooks/`, the convention this factory itself recognises (`asf/hooks.py:52`) — that
directory *is* the hooks directory, and the install writes and upgrades tracked files in it
(`asf/hooks.py:196-213`). Those paths are `touch_security` in the approval matrix
(`asf/approvals.py:132-137`), which every product has at `human-now` unless it says otherwise, and
`asf hooks install` is itself `touch_amendable_set` to a session (`asf/approvals.py:152`). The
approvals hook governs a session (an `ASF_JOB` in the environment) and nothing else, so an
install run from the operator's own console is ungoverned: the matrix says human-now, the script
asks nobody, and the product's working tree comes back dirty.

After this change the script has a named seam. `--package-only` is the operator's half,
`--no-package` is the half a session can run, and the default still runs both for a human at a
terminal. Off a tty the package half is never attempted silently: the exact command the operator
must run is printed, and everything a session may still do is done. And no install writes a
tracked file in a product's repo without a person answering for it — on a tty by answering the
question, off one by re-running with `--approve` — with the question and its answer in the
approvals ledger beside every other hold.

## Decisions

### In

- **The seam, as two flags on `tools/install.sh`.** `--package-only` runs steps 1-2 and stops.
  `--no-package` skips step 1 entirely — no `pipx`, no network, no lock wait — and runs steps 2-6.
  Neither given: both halves, exactly as today. The flags may appear anywhere after the script
  name; `<product>` and `[ref]` keep their positions (`tools/install.sh:36-37`).
- **The tty rule.** The package half needs a person. With no controlling terminal and no `--yes`,
  the default form does not run step 1: it prints one `NEEDS OPERATOR` line carrying the operator
  command verbatim, then — when `asf` is already on PATH and, if `[ref]` was given, already at
  that ref — carries on with steps 2-6 and exits non-zero at the end. A session therefore
  finishes everything it is allowed to finish and names the one thing it is not.
- **`--yes`** (or `ASF_INSTALL_YES=1`) is the standing answer for a machine with no terminal: it
  lets the package half run without a tty and answers step 3's question `yes`. It is never the
  default, and it is not what a session is given.
- **The ref check on the session half.** `--no-package` with a `[ref]` compares that ref against
  `asf --version`'s own release and commit (`asf/cli.py:118-127`): a mismatch is a `NEEDS
  OPERATOR` line naming the operator half, and the session half does not run against a package
  that is not the one asked for.
- **`asf hooks install --dry-run`** — the plan, one row per target it would touch:
  `<kind> <action> <tracked|untracked> <path>`, `kind` one of `git-hook` / `repo-settings` /
  `account-settings`, `action` one of `write` / `upgrade` / `already ours` / `left (not ours)`.
  Writes nothing, exits 0 whatever the rows say. It is the same walk `install` performs, factored
  into `hooks.plan(product)` so the two can never disagree.
- **The gate, in `asf/hooks.py` and not in the shell.** A planned row whose path is tracked by its
  own repo (`git -C <repo> ls-files --error-unmatch -- <path>`) and whose action would change the
  file (`write` or `upgrade`) is approval-bearing: its class is `touch_security` and its level is
  the product's own (`approvals.level_of(product, 'touch_security')`, `asf/approvals.py:586`).
  At `auto` it is written as today. At `groom` or `human-now` it is withheld unless `--approve`
  was given. Every caller inherits the gate — the script, an operator's own `asf hooks install`,
  and `asf install` when F-0107 lands.
- **A withheld row never withholds anything else.** The approvals hook in each worker account's
  settings file is written first and is never gated (those files live under an account's home and
  are tracked by nothing): no install may leave a worker session running without the guard that
  refuses human-now actions — `asf/hooks.py:302-334`'s own discipline, kept. Untracked git hooks,
  untracked repo settings and every other row are still written. The call returns rc 3 — distinct
  from rc 2, a foreign hook the operator must merge by hand — with one `NEEDS OPERATOR` line per
  withheld path and the one command that writes them.
- **The question, when there is a terminal.** Step 3 runs the plan first and prints it. With
  approval-bearing rows and a readable `/dev/tty`, it asks once — `write them? [y/N]` — and reads
  the answer from `/dev/tty`, never from stdin, which under `curl … | bash` is the script itself.
  `y` re-runs the step with `--approve`; anything else leaves the rows withheld.
- **A withheld step 3 is not a failed step.** It prints `install: WITHHELD step 3: <n> tracked
  hook file(s) in <repo> — <the command>` rather than `FAILED`, and steps 4-6 run as they do
  after any other step-3 outcome (`tools/install.sh:138-145`). The exit status is still non-zero:
  the install is incomplete until a person answers.
- **The ledger.** A withheld step records one hold through `approvals.ask` — item `install`, class
  `touch_security`, level from the matrix, job `$ASF_JOB` or `install`, tool `hooks install`,
  subject the sorted withheld paths (`asf/approvals.py:712`). `--approve` appends the matching
  `resolved granted` line (`asf/approvals.py:639`) before it writes, so the ledger carries both
  halves of the answer. `asf approvals list` shows it and `asf approvals resolve
  install/touch_security granted` is the other way to answer it.
- **The docs.** The README's Install block and `docs/guide/getting-started.md` §2 name the two
  halves and who runs each. `docs/guide/upgrading.md` says the same of a re-run.
  `docs/guide/troubleshooting.md`'s installer table gains the new `NEEDS OPERATOR` and `WITHHELD`
  lines, and the install path links its existing
  [Retiring a pre-ASF scheduler](../guide/troubleshooting.md) section, so the operator meets that
  step before `asf scheduler install` rather than after.

### Out

- **Retiring the product's pre-ASF clocks.** The operator ruled on 2026-09-24 that this is the
  product's own migration step, not the installer's — it is out of F-0108 and out of this card.
  ASF already removes no job it did not install, `tools/cutover.sh` already boots out the declared
  pre-ASF job and files the plists under `~/.ASF/state/<product>/retired/<date>/`, and the guide
  already documents it (`docs/guide/troubleshooting.md:153-200`). This card adds one link from the
  install path to that section and no code: the installer never boots out a job.
- **`asf install`** — the Python command F-0107 specifies. This card cuts the seam in the shell
  where it already exists and leaves the move to Python to that card (see Preconditions).
- **The runtime's auto-mode classifier.** Nothing in this repo can allow a session the `pipx`
  step; this card makes the refusal anticipable and routes around it, it does not try to clear it.
- **Writing the console allow list.** B-0131's offer stands as it is: shown in full, written by
  the operator (`asf/console_perms.py:1-33`).
- **A foreign git hook.** Already refused, and left untouched (`asf/hooks.py:206-208`). The new
  gate is about *asf's own* hook landing in a tracked file, not about overwriting someone else's.

### Preconditions

- `tools/install.sh` is the one-product installer, steps 1-6 as its header describes, with the
  record-and-continue discipline for steps 3-6 (`tools/install.sh:138-213`).
- `tests/test_install.py:1669` `InstallScriptTest` already runs the script end to end on a stubbed
  `PATH` (stub `pipx`, stub `asf`, temp `HOME`/`ASF_HOME`) — the harness every acceptance test
  below extends. Its existing cases stay green unchanged.
- The approval matrix, its levels and its ledger are in place (`asf/approvals.py`), `touch_security`
  is `human-now` by default and carries the tracked-hook glob (`asf/approvals.py:132-137`), and
  the hook governs only a session (`asf/approvals.py:926-1012`).
- An open hold whose item is not a card is inert for the wave: `touch_security` is a session
  refusal (`asf/approvals.py:1014-1018`), so `step_wave.groom_owned` does not add its item to the
  groom's (`asf/tick/step_wave.py:203-212`). The `install` hold is read by `asf approvals list`
  and by nothing else.
- F-0107 keeps `tools/install.sh` as the bootstrap and moves steps 2-6 into `asf install`. The
  flag names this card adds (`--package-only`, `--no-package`, `--yes`, `--approve`) are the ones
  that card passes through, so the seam survives the move; `hooks.plan` and the gate move with
  `asf/hooks.py`, which that card does not touch.

### Choices

| choice | against | why |
| --- | --- | --- |
| Split the script with flags | document who runs which half and change no code | the card offers either; the doc alone leaves a session stopping dead halfway through a run it was told to do. The flags make the two halves separately runnable, and the doc then has something true to describe |
| The gate lives in `asf/hooks.py` | the gate lives in `tools/install.sh` | the shell is one caller of three (the operator's own `asf hooks install` and F-0107's `asf install` are the others). Putting it at the writer covers all of them and keeps the plan and the write from disagreeing |
| "Tracked, and would change" is the trigger | gate every git-hook write | an untracked `.git/hooks/pre-commit` is machine state, not the product's source: gating it would put a question in front of every ordinary install, and a question everyone answers `y` teaches nobody anything |
| `touch_security`, the class the matrix already has | a new `install_hooks` class | the paths are already `touch_security` (`asf/approvals.py:132-137`); a second class for the same files would let one product answer the same question two ways |
| Withheld is rc 3 and a `WITHHELD` line | reuse rc 2 / `FAILED` | rc 2 is "a foreign hook — merge one line by hand". "Answer the question and re-run" is a different act, and the operator reading the summary must be able to tell them apart |
| Ask on `/dev/tty`, never stdin | read the answer from stdin | under `curl … | bash` stdin is the script; a read there consumes the script's own remaining bytes. `/dev/tty` is the only honest prompt on that path |
| No tty and no flag: print the operator command, then run what can be run | refuse the whole script | a session that does steps 2-6 and names step 1 leaves one human act; a refusal leaves the whole install undone and the human doing six |
| The hold's item is the literal `install` | attach it to the card being worked on, or write no hold | an install is not a card's doing. `install/touch_security` is typable, inert for the wave (Preconditions), and puts the question where every other approval question lives |
| Only the package half appends to `install.log` | append on every invocation | `asf release-readiness` counts those lines as installs by hand (`tools/install.sh:126-129`); splitting one install into two invocations must not read as two |

## The design

### 2.1 `tools/install.sh` — the flags and the two halves

Argument parsing (`tools/install.sh:36-37`) becomes a loop: the first two non-flag words are
`<product>` and `[ref]`; `--package-only`, `--no-package`, `--yes` and `-h|--help` are flags in any
position; anything else is a usage error, exit 2. `--package-only` with `--no-package` is a usage
error too. The header comment gains the two halves and who owns each.

```
step                                     --package-only   --no-package   default
1 pipx install (under the tick lock)           run           skipped       run*
  install.log line                             written       skipped       written*
2 config preconditions                         run           run           run
3 hooks install (gated, §2.4)                  skipped       run           run
4 scheduler install + read-back                skipped       run           run
5 doctor against the baseline                  skipped       run           run
6 console-permissions offer                    skipped       run           run
```

`*` unless there is no controlling terminal and no `--yes` (§2.2).

The baseline doctor read before step 1 (`tools/install.sh:77-80`) stays where it is on both
halves: on `--no-package` it is the baseline for a package that did not move, which is exactly the
comparison step 5 wants. `--package-only` ends with `say` naming the session half verbatim:
`bash tools/install.sh <product> <ref> --no-package` (and the `curl … | bash -s -- …` form of the
same line).

`--no-package` asserts what step 1 would have guaranteed, before step 2:

- `asf` on PATH, else `NEEDS OPERATOR: asf is not installed — the operator runs: <the
  --package-only command>`, exit 2;
- when `[ref]` was given, `asf --version` parsed as `<release> (<commit>)`
  (`asf/cli.py:118-127`): the ref matches when it equals the release, or when it and the printed
  commit share a prefix of at least the shorter one's length. A mismatch is `NEEDS OPERATOR: asf
  is <release> (<commit>), not <ref> — the operator runs: <the --package-only command>`, exit 2.

It never opens the tick lock: nothing it does replaces the package.

### 2.2 No terminal, and the default form

The script has a terminal when `/dev/tty` is readable. Without one, and without `--yes`, the
default form (neither flag) does not run step 1. It prints

```
install: NEEDS OPERATOR: step 1 installs the package and needs a terminal — run:
install:   bash tools/install.sh <product> <ref> --package-only
install: then this session can finish with: bash tools/install.sh <product> <ref> --no-package
```

and then behaves as `--no-package` for the rest of the run — including that section's two asserts,
whose failure ends it at exit 2 with nothing else attempted. When they pass, steps 2-6 run, their
own failures are recorded as usual, and the final exit is non-zero with the package step named in
the summary as the outstanding one. `--package-only` without a terminal is the same refusal with
no half left to run: the message, exit 2. `--yes` overrides all of this and runs step 1 as today.

### 2.3 `hooks.plan(product)` and `asf hooks install --dry-run`

`asf/hooks.py` gains `plan(product, which=shutil.which)` → a list of rows
`(kind, action, tracked, path)`:

- one `git-hook` row per (`repo_dir`, `backlog_dir`) × (`pre-commit`, `pre-push`), the action
  decided exactly as `ensure_git_hooks` decides it today (`asf/hooks.py:195-213`): absent →
  `write`; present and upgradable → `upgrade`; present and ours → `already ours`; present and
  foreign → `left (not ours)`;
- one `repo-settings` row for the product repo's `.claude/settings.json` when any rule declares a
  hook, `write` when `merge` would change the file, else `already ours`;
- one `account-settings` row per worker account, the same way.

`tracked` is true when the path lies inside a repo and `git -C <repo> ls-files --error-unmatch --
<path>` exits 0; `repo` is `repo_dir` / `backlog_dir` for the first two kinds and is never
consulted for an account file (always false). A repo that is not a git repo yields the refusal
row `ensure_git_hooks` already produces (`asf/hooks.py:191-194`), `tracked` false.

`register` (`asf/hooks.py:397-410`) gains `--dry-run` and `--approve` on the `hooks` subcommand.
`--dry-run` prints the rows as a table and exits 0; `--approve` is §2.4. `--dry-run --approve`
together is a usage error. Nothing else about the subcommand changes.

### 2.4 The gate

`install()` (`asf/hooks.py:302-334`) takes `approve=False` and, in this order:

1. writes the approvals hook into every worker account's settings — ungated, unchanged;
2. computes `plan(product)`;
3. splits it: `gated` = rows with `tracked` true and action in (`write`, `upgrade`), when
   `approvals.level_of(product, 'touch_security') != 'auto'` and `approve` is false; `writable` =
   every other row;
4. performs `writable`, exactly as today, refusals and all;
5. when `gated` is non-empty, records the hold (§2.6) and returns rc 3 with the summary, then one
   line per withheld path:
   `NEEDS OPERATOR: <path> is tracked in <repo> and the matrix has touch_security at <level> — asf hooks install --product <p> --approve`;
6. else returns the rc it returns today (0, or 2 with the foreign-hook refusals).

With `approve=True` the gated rows are written with the rest, and the grant is recorded before the
write. rc 2 and rc 3 can both be owed in one call: the foreign-hook refusal lines and the withheld
lines are both printed, and the rc is 3 (a question a person can answer outranks a note about a
file nobody will touch).

A session cannot reach `--approve`: `asf hooks install` in a Bash command is already
`touch_amendable_set` to the hook, which is `human-now` and not grantable
(`asf/approvals.py:151-153`, `:97-102`). Nothing new is needed for that, and nothing here weakens it.

### 2.5 Step 3 asks

Step 3 (`tools/install.sh:146`) becomes:

```
asf hooks install --product <p> --dry-run     # printed in full
  no approval-bearing row  -> asf hooks install --product <p>            (as today)
  a terminal, no --yes     -> the rows, then "write them? [y/N] " read from /dev/tty
                               y -> asf hooks install --product <p> --approve
                               else -> withheld
  --yes                    -> asf hooks install --product <p> --approve
  no terminal              -> withheld
```

"approval-bearing row" is read from the plan the same way §2.4 reads it, so the script asks
exactly when the command would withhold. A withheld step 3 prints the `WITHHELD` line of §2.1 and
is carried in a second list beside `FAILED`; the closing summary prints both, and the exit is
non-zero when either is non-empty.

### 2.6 The record of the question

Withholding appends, once per call, through `approvals.ask` (`asf/approvals.py:712`):

```json
{"event":"refused","hold":"install/touch_security","item":"install","class":"touch_security",
 "level":"human-now","job":"install","tool":"hooks install",
 "detail":"2 tracked hook files would be written: <repo>/.githooks/pre-commit, <repo>/.githooks/pre-push",
 "subject":"<the same paths, sorted, comma-joined>","ts":"<utc>"}
```

`ask` is what is called, not `refuse`, so a hold a person already resolved `dropped` for these same
paths is not asked again (`asf/approvals.py:700-722`). `--approve` appends
`{"event":"resolved","hold":"install/touch_security","resolution":"granted","ts":"<utc>"}` before
it writes. `job` is `$ASF_JOB` when the environment carries one, else the literal `install`.

### 2.7 The docs

- **`README.md:16-27`** — the Install block becomes three lines plus one sentence: the operator
  runs the `--package-only` line in a terminal; everything after it, including a re-run to
  upgrade, works as `--no-package` from the product's own Claude Code session.
- **`docs/guide/getting-started.md:47-72`** — §2 gains the halves table of §2.1, the sentence that
  step 1 cannot be run by a session in auto mode and why, and one line before step 4 linking
  [Retiring a pre-ASF scheduler](troubleshooting.md): a product that had its own clocks retires
  them first, and ASF never boots out a job it did not install.
- **`docs/guide/troubleshooting.md:9-20`** — the installer table gains: `step 1 … needs a
  terminal`, `asf is not installed`, `asf is <release> …, not <ref>`, `<path> is tracked in
  <repo> …` and the `WITHHELD step 3` summary line, each with the one command that clears it. The
  `Hooks and the redaction gate` section (`:39-47`) gains `asf hooks install --dry-run` as the way
  to see what a hooks install would touch before it touches it.
- **`docs/guide/upgrading.md`** — the re-run is the same two halves.

## Acceptance tests

Every block is runnable from a checkout of this repo.

The seam: the two flags, what each half runs, the no-tty default, the ref check and the single
`install.log` line. The tty cases open a pty with `pty.openpty()` and hand the slave to the child
as stdin/stdout/stderr under `start_new_session=True`, so `/dev/tty` inside the script resolves to
it:

```bash
python3 -m unittest -v tests.test_install.InstallScriptSeamTests
```

The plan: one row per target, the action each target is in, and `tracked` true only for a path its
repo versions — a repo with `core.hooksPath` at a tracked `.githooks/` against one with the
default `.git/hooks`:

```bash
python3 -m unittest -v tests.test_install.HooksPlanTests
```

The gate: a tracked write withheld at `human-now`, written at `auto`, written under `--approve`;
the approvals hook in every account written either way; the untracked rows written either way;
rc 3, and rc 3 winning over a foreign hook's rc 2:

```bash
python3 -m unittest -v tests.test_install.HooksApprovalTests
```

The question in the script: asked on a pty and answered `y` then `n`, never asked without one,
`--yes` answering it, and the `WITHHELD` summary that does not stop steps 4-6:

```bash
python3 -m unittest -v tests.test_install.InstallScriptHooksApprovalTests
```

The ledger rows the two outcomes write, and the `dropped` hold that is not asked twice:

```bash
python3 -m unittest -v tests.test_approvals.InstallHoldTests
```

The install path as the docs describe it — both halves named in the README and the guide, every
new `NEEDS OPERATOR` and `WITHHELD` line in the troubleshooting table, and the pre-ASF link:

```bash
python3 -m unittest -v tests.test_readme.InstallHalvesTests
```

Nothing that ran before this card stops running — the existing end-to-end script cases, the hooks
and console-permissions cases, and the approvals matrix:

```bash
python3 -m unittest -v tests.test_install.InstallScriptTest tests.test_install.HooksTest \
    tests.test_install.GitHookTests tests.test_install.ConsolePermissionsTest tests.test_approvals
```

The fences:

```bash
bash tools/check_conventions.sh
bash tools/check_generic.sh
```

The whole suite, as CI runs it:

```bash
python3 tools/run_tests.py
```

## Records

- **`~/.ASF/state/<product>/approvals.jsonl`** — one `refused` line per withheld hooks install and
  one `resolved granted` line per `--approve`, as §2.6 (`asf/approvals.py:598-648`). This is
  operator state, not the record: no card, no event, no `metrics/*.jsonl` line.
- **`~/.ASF/logs/install.log`** — unchanged in shape (`<utc>\t<product>\t<ref>`), written by the
  package half only, so one install is one line however it was split
  (`tools/install.sh:126-129`).
- **The git hooks** — `pre-commit` and `pre-push` in `repo_dir` and `backlog_dir`, written as
  today when they are untracked, and only after an answer when they are tracked. A file that is
  not asf's is still never written (`asf/hooks.py:206-208`).
- **The settings files** — the approvals hook in each worker account's settings, and the rule
  hooks in the product repo's `.claude/settings.json`; the first is never withheld.
- **Printed output** — the plan table, the step lines, one `NEEDS OPERATOR: <what> — <the
  command>` per human act (no terminal for step 1; `asf` absent or at the wrong ref; each withheld
  tracked path), and the closing summary's two lists, `FAILED` and `WITHHELD`.
- **The product's clocks and the pre-ASF ones** — unchanged by this card: the installer installs
  ASF's own clocks and removes nothing (`tools/install.sh:148-171`).
