# F-0338 — a trunk nobody ran is not a green trunk

The main safety net (`asf/kernel/mainline.py`) is the one reader of the trunk's own CI. It reads
the newest commits (`Facts.main`, `ports.py:1311-1350`, fifteen of them), gives each a verdict on
the required checks, and acts on **the newest commit that has one**: green, nothing; red, a
revert of the single candidate or a Bug for a fix session (`mainline.py:176-208`).

That design has one silent state, and this card names it: **a commit with no verdict is skipped,
and a trunk where *every* read commit has no verdict produces no action, no record and no line**
(`red_spell`, `mainline.py:74-86`, returns `None`; `judge` then returns `([], None)`). The tick
prints nothing. `asf kernel status` shows nothing. The net is not watching the trunk — it is
watching a window in which nothing finished, and silence from it reads exactly like a green
trunk.

The way the trunk gets into that state is ordinary, not exotic. This repo's `tests` workflow
groups its runs by event and ref, with `cancel-in-progress` off on the trunk
(`.github/workflows/tests.yml:21-27`): a run that has started finishes and gives its verdict,
while a run still **queued** is cancelled the moment a newer push joins its group. On a trunk
taking landings faster than one suite takes to run, the queued run of nearly every commit is
cancelled by the commit after it. GitHub reports those as `conclusion: cancelled`, which is no
verdict either way — and nothing re-runs a cancelled run on the trunk (the kernel's one re-run
path, `A.Rerun`, is a PR's, `actions.py:65-72`). So the verdict the net acts on drifts further
and further behind the head, and the candidate set of the next red (`commits[i:j]`) grows with
it, until a red names a dozen candidates and no change can be reverted.

Two things follow, and they are this card:

1. **A cancelled run is no verdict, said out loud and pinned by tests.** Today this holds by
   construction — `cancelled` is in neither `RED_CONCLUSIONS` (`model.py:50-51`) nor
   `GREEN_CONCLUSIONS` (`mainline.py:32`) — and nothing tests it. It is also the property with
   the worst failure mode in the whole module: were a cancelled trunk run ever read as red, the
   net would open a revert PR against an innocent landed change and send its item back to Ready
   (`revert_action`, `mainline.py:139-157`). A property that expensive to lose is a property with
   its own tests.
2. **A trunk with no verdict gets one.** Once more than `kernel.mainline.max_pending` commits
   above the newest judged commit hold no finished required run, the kernel dispatches **one**
   `workflow_dispatch` run of the trunk's workflow on the newest head. A dispatch is in its own
   concurrency group (`github.event_name` is part of the group,
   `.github/workflows/tests.yml:26-27`), so a push cannot cancel it; and a non-`pull_request`
   event is never the docs-only fast path (`tests.yml:43-47`), so it runs the full suite and
   posts exactly the required check names. The net gets a verdict on the head, and the next red
   has one or two candidates instead of twelve.

## Decisions

### Preconditions — measured in this worktree at `55d9ec2f1`, 2026-10-10

Each line below was run from the repo root; the script is in this spec's Acceptance tests
(`the preconditions, re-measured`) so a reviewer can replay it.

* **P1 — a cancelled required run already reads as no verdict, and nothing tests it.**
  `mainline.verdict` returns `pending` for a required check completed `cancelled`, for one still
  `in_progress`, and for one never reported at all. A `cancelled` beside a `failure` is still
  `red` (the failure decides), and a `cancelled` beside a `success` is `pending` (the cancel is
  not a green). `grep -c cancel tests/kernel/test_main_landing.py` is **0**: the module that
  covers `mainline.py` has no cancelled case at all, and `test_verdicts`
  (`test_main_landing.py:258-262`) pins only green, red and one unreported check.
* **P2 — a trunk of commits with no verdict is a silent no-op.** Seven commits whose required
  runs were all cancelled, sitting over one green commit, give `judge` → `actions=[]`,
  `record=None`. No action, no `Plan.main`, no `MAIN RED` line, nothing in the tick's summary.
* **P3 — there is no `kernel.mainline` block.** `sorted(asf.kernel.settings.SPEC)` is
  `['briefs', 'dor', 'floor', 'gate', 'github', 'idle_alarm', 'install', 'intake', 'landing',
  'launch', 'main_move', 'models', 'resolve', 'review', 'risk', 'stuck', 'tick', 'waits',
  'watch']` — nineteen sections, no `mainline`.
* **P4 — nothing in the kernel can dispatch a run.** The `Config` fields naming the trunk are
  `['main_red_revert']` alone; no action class in `asf/kernel/actions.py` has `Dispatch` in its
  name; `RealGitHub` has no method with `dispatch` in its name. The kernel's three run writes are
  `rerun` (`ports.py:1467-1474`), `rerun(cancel=True)` and `cancel_run` (`ports.py:1499-1500`).
* **P5 — the trunk's own workflow would refuse a dispatch.** `.github/workflows/tests.yml`
  declares `on: {push: {branches: [main]}, pull_request:}` (`:7-11`) and **no
  `workflow_dispatch:`**. `gh workflow run tests.yml --ref main` is refused by GitHub for a
  workflow without that trigger. `asf.trunk_red.dispatch` (`trunk_red.py:313-328`) already
  dispatches `ci_queue.workflow_for(product, 'trunk')` the same way, so this precondition is
  missing for that module too, and it fails there the same way: one refusal line per tick.
* **P6 — the facts the judge would read are already there, every tick.** `Facts.main`
  (`model.py:374`) is read unconditionally (`facts.py:160-176`); `Facts.ci_runs`
  (`model.py:378`, `CIRun` at `model.py:138-148` with `run_id`, `head_sha`, `branch`, `event`)
  is read before the PRs (`facts.py:191-204`) and carries each queued or running workflow run's
  event. `Check.status` is GitHub's (`queued`, `in_progress`, `completed`) and `conclusion` is
  set only when completed (`model.py:151-166`).
* **P7 — the record holds no Story for F-0338**, and this session's block is
  `S:122755-122804`.

* **The trigger the dispatch needs**: `workflow_dispatch:` in `.github/workflows/tests.yml`'s

### Out

* **Changing `verdict`, `red_spell`, `red_checks` or any red behaviour.** Not one line of the red
  path moves. S-122755 pins what `verdict` already does (P1); the dispatch is reached only where
  `red_spell` returns `None` (D3), so a red trunk plans exactly what it plans today.
* **Re-running a cancelled trunk run.** `gh run rerun` on a cancelled run is a different write
  with different failure modes (`asf.ci_queue._rerun_cancelled` has a whole refusal ladder for
  it, `ci_queue.py:350-353`), and it re-runs the old sha. The net wants a verdict on the **newest
  head**, which a fresh dispatch gives directly.
* **Anything about the trunk's workflow beyond its trigger.** No concurrency group, no job, no
  matrix and no required check name changes. The dispatch is designed around the groups as they
  are (D6).
* **`asf.trunk_red`, `asf.trunk_watch`, `asf.ci_queue`.** The host-side trunk watch dispatches
  for its own reasons (a stall alarm, a suspected trunk red, a six-hourly floor) off its own
  state file. This card adds the kernel's reason; the two never need to agree, and P5's fix makes
  both work. No state file, no cadence and no suspicion logic is shared, read or moved.
* **A new wait class, breach or Stuck.** A verdict-less trunk is not an item and owns no card;
  it has a plan record and a tick line, which is what every other trunk fact has.
* **Making `Facts.ci_runs` distinguish "unread" from "empty".** `read_runs` returns `[]` for a
  port that cannot read, a rate-guarded port and a failed read alike (`facts.py:191-204`), as
  `open_heads=None` does not (`model.py:379`). The dispatch is designed not to need that
  distinction (D5): the in-flight checks on the newest head, which come from `Facts.main` and are
  always read, are what make it at most one run.
* **A second dispatch, a retry or a cadence.** One run per threshold crossing, and nothing until
  that run's checks say something. A dispatch `gh` refuses is one `FAILED` line in the apply log
  (`apply.py:494-511`) and the next tick decides afresh.

### Preconditions the work depends on

1. `Facts.main` is read every tick and is `[]` when unreadable (`facts.py:160-176`), so an
   unread trunk plans nothing — the dispatch needs no extra guard for a blind tick.
2. `Check.status` is `completed` only for a run that finished, and `conclusion` is set only then
   (`model.py:151-166`). "A run that can still give a verdict" is exactly `status != 'completed'`.
3. `mainline.judge` is pure — facts and config in, actions and one record out (`mainline.py:1-27`)
   — and `decide` appends its actions untouched unless they are a `Rerun` already planned
   (`decide.py:427-433`). A new action class needs no change in `decide`.
4. `apply` dispatches on the action class's own name and logs `describe(action)`; one action's
   failure never stops the rest (`apply.py:494-511`). `targets()` returns `[]` for an action with
   no PR, so the staleness guard is a no-op for this one (`apply.py:470-481`).
5. `RealGitHub._write` raises `PortError` on a refused `gh` call and is the one path every kernel
   write takes, including under the mutation guard (`ports.py:1438-1441`).
6. `ci_queue.workflow_for(product, 'trunk')` answers with `ci.queue.workflows.trunk`, else
   `ci.workflow`, else `None` (`ci_queue.py:768-775`), and `product.main` is the trunk branch.
7. `settings.problems`/`settings.read` are generic over `SPEC`: a new section with an `int` key
   is validated, defaulted and documented with no reader change (`settings.py:208-377`).
8. A non-`pull_request` event is never the docs-only fast path (`tests.yml:43-47`), and the
   gathering job keeps the names the trunk's ruleset requires (`tests.yml:12-17`), so a
   dispatched run reports `tests (3.12)` / `tests (3.13)` on the trunk head like a push run.
9. On the trunk, `cancel-in-progress` is `${{ github.event_name == 'pull_request' }}` — false —
   and the group carries the event (`tests.yml:26-27`): a dispatched run is in its own group and
   no push cancels it.

## The design

### 1. `asf/kernel/mainline.py` — the no-verdict head, and the one run that answers it

Three readers, all pure, and one new branch in `judge`. Nothing above them moves.

```python
def in_flight(commit, config):
    """Whether a required check on ``commit`` has a run that can still finish — any status short
    of ``completed`` (:class:`asf.kernel.model.Check`). A verdict is coming for this commit, so
    nothing is dispatched for it (and the run a dispatch starts is what makes the dispatch
    at most one: its checks land on this commit)."""
    return any(c.status != 'completed' for c in commit.checks if _required(c.name, config))


def unjudged(facts, config):
    """The trunk's commits with no verdict above the newest one that has a verdict (newest
    first): every commit whose required checks hold no finished run — a run cancelled by a newer
    push, one never reported, one still going. Every read commit when none has a verdict; empty
    when the trunk is unread, or its newest commit has one."""
    out = []
    for c in facts.main or []:
        if verdict(c, config) != 'pending':
            return out
        out.append(c)
    return out


def dispatching(facts):
    """Whether a ``workflow_dispatch`` run on a sha the trunk reads is queued or running
    (``Facts.ci_runs``): the kernel's own last dispatch, before its checks reached the commit.
    An unread run list is empty and holds nothing back (F-0338 D5)."""
    shas = {c.sha for c in facts.main or []}
    return any(r.event == DISPATCH_EVENT and r.head_sha in shas for r in facts.ci_runs or [])
```

The judgement itself, and the one line of `judge` that reaches it:

```python
#: the ``CIRun.event`` of a run the kernel asked for (``gh workflow run``), never a push's
DISPATCH_EVENT = 'workflow_dispatch'


def dispatch(facts, config):
    """``(actions, record)`` of a trunk with no verdict: one
    :class:`~asf.kernel.actions.DispatchMain` on the newest commit once more than
    ``config.main_max_pending`` commits above the newest judged one hold no finished required
    run (:func:`unjudged`) and nothing is already coming for that head
    (:func:`in_flight`, :func:`dispatching`). ``([], None)`` while the knob is off, the trunk is
    unread, or the lag is inside the bound."""
    if not config.main_max_pending:
        return [], None
    waiting = unjudged(facts, config)
    if len(waiting) <= config.main_max_pending:
        return [], None
    head, why = waiting[0], '%d commits with no verdict' % len(waiting)
    if in_flight(head, config) or dispatching(facts):
        return [], {'sha': head.sha, 'kind': PENDING,
                    'action': 'waits on the run in flight (%s)' % why}
    a = A.DispatchMain(head.sha, why)
    return [a], {'sha': head.sha, 'kind': PENDING, 'action': A.describe(a)}


def judge(facts, config):
    spell = red_spell(facts, config)
    if spell is None:
        return dispatch(facts, config)      # <- was: return [], None
    ...                                     # the red path, unchanged
```

`RED, PENDING = 'red', 'pending'` are the record's two kinds; every record the red path returns
gains `'kind': RED` (`mainline.py:184-208`, four of them, one key each). The module docstring
gains the two paragraphs this spec opens with: that a cancelled run is no verdict and never a
red, and that a lag past the knob is answered by one dispatched run on the newest head.

### 2. `asf/kernel/actions.py` and `asf/kernel/apply.py` — the action, and its one write

```python
@dataclasses.dataclass
class DispatchMain:
    """Dispatch one ``workflow_dispatch`` run of the trunk's workflow on the trunk: the main
    safety net has no verdict to act on and ``why`` says what it is missing. ``sha`` is the
    newest head the kernel judged — GitHub dispatches on a ref, whose tip may have moved since
    (F-0338 D7), so it names the decision, not the run's head. Idempotent on the world it was
    decided from: the run it starts puts the required checks in flight on the trunk's head, and a
    head with a check in flight is never dispatched for."""
    sha: str
    why: str = ''
```

`describe` gains one line — `'dispatch a trunk run on %s: %s' % (action.sha[:9], action.why)` —
and `apply` one handler beside `CancelRun` (`apply.py:384-385`):

```python
    def DispatchMain(self, a):
        return self.ports.github.dispatch_main(a.sha)
```

The handler's return is the note the apply log prints after `describe` (`apply.py:506-509`), so
one tick reads `dispatch a trunk run on 9f31ab0c1: 6 commits with no verdict — tests.yml on
main`. `apply`'s module docstring gains that clause in the sentence that already lists
`CancelRun` (`apply.py:49`).

### 3. `asf/kernel/ports.py` — `dispatch_main`, and the knob into `Config`

```python
    def dispatch_main(self, sha=''):
        """Dispatch the trunk's workflow on the trunk: ``gh workflow run <wf> --ref <trunk>``,
        the workflow from :func:`asf.ci_queue.workflow_for` ``trunk`` — the call
        :func:`asf.trunk_red.dispatch` makes. A ``workflow_dispatch`` run is in its own
        concurrency group, so a push to the trunk never cancels it, and it is never the
        docs-only fast path: it reports the required checks on the trunk's head. ``sha`` is the
        head the kernel judged, for the line it returns only. :class:`PortError` when the product
        declares no trunk workflow, or when ``gh`` refuses."""
        from asf import ci_queue
        wf = ci_queue.workflow_for(self.product, ci_queue.TRUNK_KIND)
        if not wf:
            raise PortError('no trunk workflow to dispatch: ci.workflow is unset')
        self._write(['workflow', 'run', wf, '--ref', self.product.main, '-R', self.slug],
                    'dispatch %s on %s' % (wf, self.product.main))
        return '%s on %s' % (wf, self.product.main)
```

The `Ports` protocol comment (`ports.py:137-147`) gains
`def dispatch_main(self, sha='') -> None: ...` under the GitHub port, beside `rerun`.

### 5. `asf/kernel/loop.py` — `MAIN PENDING` beside `MAIN RED`

```python
def main_line(main):
    """``MAIN RED <sha> -> <action>`` of :attr:`Plan.main`, or ``MAIN PENDING <sha> -> <action>``
    when the record is a trunk with no verdict (``kind: pending``,
    :func:`asf.kernel.mainline.dispatch`). A record written before that key existed reads as

```

`loop.py`'s module docstring (`:17`) gains the second line beside the first. Nothing else reads
the record: `summarize` copies it (`loop.py:97`) and `print_summary` prints it
(`loop.py:203-204`).

### 6. `.github/workflows/tests.yml` — the trigger a dispatch needs

```yaml
on:
  push:
    branches: [main]
  pull_request:
  # F-0338: the kernel's main safety net (asf.kernel.mainline) and the trunk watch
  # (asf.trunk_red) both dispatch this workflow on the trunk when nothing finished on it — a
  # workflow_dispatch run is in its own concurrency group below, so a push never cancels it, and
  # it is never the docs-only fast path, so it reports the required checks on the trunk's head.
  workflow_dispatch:
```

No job, group or name changes: the group expression already carries `github.event_name`
(`:26-27`), so a dispatch run groups as `tests-workflow_dispatch-refs/heads/main` on its own.

### What it looks like when it is there

A trunk taking landings faster than the suite runs, six commits deep with every queued run
cancelled by the push after it:

```
kernel tick: done 41, landing 2, review 3, ready 5, LIMBO 0
MAIN PENDING 9f31ab0c1 -> dispatch a trunk run on 9f31ab0c1: 6 commits with no verdict
dispatch a trunk run on 9f31ab0c1: 6 commits with no verdict — tests.yml on main
```

The next tick, the dispatched run's checks are in flight on that head:

```
MAIN PENDING 9f31ab0c1 -> waits on the run in flight (6 commits with no verdict)
```

and the tick after it finishes, the net is reading a verdict on the head again — green, and
silent; or red, with one or two candidates, and the revert or the Bug it has always filed. A
cancelled run never reads as either, and no landed change is ever reverted for one.

## Records

Nothing is written to the record: no card is minted, no state moves, no field is set, no note is
appended, no Bug is filed, no branch is touched, no file is created outside the new test module.
The change writes exactly three things, and two of them are read-only:

* **One plan record per tick with a verdict-less trunk** — `Plan.main`, as it is already written
  for a red one (`actions.py:262-291`): `{'sha': <the newest head>, 'kind': 'pending', 'action':
  <the one line>}`. It is carried into the tick's summary (`loop.py:97`) and the state file the
  loop keeps, exactly as the red record is, and no reader needs to change: `main_line` prints
  whichever kind it finds (D8).
* **One tick line** — `MAIN PENDING <sha> -> dispatch a trunk run on <sha>: N commits with no
  verdict`, or `… -> waits on the run in flight (N commits with no verdict)` while a run that can
  answer is going (D9). Plus the apply log's own line, which carries the port's note: `dispatch a
  trunk run on <sha>: … — <workflow> on <trunk>`.
* **One `workflow_dispatch` run on GitHub**, the only outward write: the trunk's workflow on the
  trunk ref, appearing in the repo's run list with `event: workflow_dispatch` and posting the
  required check names on the trunk's head. It is what the next tick reads back, both as
  `Facts.ci_runs` (queued or running) and as the head's own checks.

A dispatch GitHub refuses writes nothing at all: `_write` raises, `apply` logs one `FAILED` line
and keeps going (`apply.py:503-505`), and the next tick decides the same trunk afresh.

## Stories

Five Stories, one per section of `## The design` as the design groups them: the judge (§1, split
into the cancelled verdict it pins and the threshold it adds), the guards that keep it to one run
(§1's three conditions), the action-applier-port path (§2, §3), and the knob with its record, its
line and its trigger (§3-§6). Each is **declared** below as a `### S-…: <title>` heading with its
acceptance lines under it, with ids from this session's block `S:122755-122804` — that heading is
what `asf.record.idcheck.declared_stories` reads and what `asf.record.plan_tasks` mints the card
from, so a cited id with no declaration is a phantom and the plan citing it is refused whole.

Each acceptance line is one physical line of plain text with no backticks: the reader is
line-anchored (`asf.record.idcheck.CHECKBOX` matches a single line) and inline code spans are
replaced by one space before parsing, so a wrapped line reaches the minted card truncated and an
identifier inside backticks reaches it missing.

Everything below is false on the trunk today except the lines of S-122755, which pin behaviour
that already holds and that no test covers (P1) — those are the facts the rest relies on.

### S-122755: a cancelled trunk run is no verdict — never red, never green, and never a revert

Design §1 (D1; P1). Acceptance is the first fenced block of `## Acceptance tests`. The property
is the one whose loss is most expensive in the module — a cancelled run read as red reverts a
landed change and sends its item back to Ready — and today nothing covers it.

- [ ] a required check completed cancelled reads as pending, not red and not green
- [ ] a required check still queued reads as pending
- [ ] a required check still in progress reads as pending
- [ ] a required check the rollup never reported reads as pending
- [ ] a cancelled required check beside a failed one reads as red, so a cancel never hides a verdict
- [ ] a cancelled required check beside a green one reads as pending, so a cancel is never a green
- [ ] a commit whose every required run was cancelled is never a revert and never a Bug
- [ ] a trunk whose newest commit was cancelled over a green commit plans nothing against that green
- [ ] cancelled commits above a red commit leave the red's candidate set exactly the commits from the red back to the last green
- [ ] a cancelled run on a commit is never counted as a red check of that commit
- [ ] a cancelled required check is never rerun by the main safety net

### S-122756: more than max_pending commits with no finished required run dispatch one trunk run on the newest head

Design §1 (D1, D2, D6, D7). Acceptance is the second fenced block. The count is the lag of the
verdict behind the head, the bound is strict, and the answer is one run on the newest commit.

- [ ] the commits with no verdict are read newest first, stopping at the newest commit that has one
- [ ] a verdict-less commit below the newest judged commit is not counted
- [ ] every read commit counts when no commit in the window has a verdict
- [ ] exactly max_pending commits with no verdict dispatch nothing
- [ ] one more than max_pending commits with no verdict dispatch one run
- [ ] the dispatch names the newest commit's sha
- [ ] the dispatch carries why it fired, naming how many commits have no verdict
- [ ] the plan holds exactly one dispatch action, never one per commit
- [ ] a run cancelled by a newer push, a run never reported and a run still going all count towards the bound
- [ ] the trunk's record for the tick carries the newest sha, the pending kind and the action's own line
- [ ] a trunk whose newest commit has a verdict dispatches nothing whatever sits below it

### S-122757: at most one run in flight for the trunk, and none while the net has a verdict to act on

Design §1 (D3, D4, D5). Acceptance is the third fenced block. Four guards, and the first of them
is what makes the dispatch idempotent without any state of its own.

- [ ] a newest commit with a required check still queued dispatches nothing
- [ ] a newest commit with a required check still in progress dispatches nothing
- [ ] the tick that waits on a run in flight still records the trunk, naming the run it waits on
- [ ] the checks a dispatched run puts on the newest head stop the next tick from dispatching again
- [ ] a queued workflow_dispatch run on a sha the trunk reads stops a second dispatch
- [ ] a queued push run on the trunk is not a dispatch in flight and never stops the dispatch by itself
- [ ] an empty run list never stops the dispatch
- [ ] a trunk whose newest judged commit is red plans the red's own action and no dispatch
- [ ] a trunk waiting on a main-red Bug or a revert plans no dispatch
- [ ] a trunk whose newest judged commit is green and whose lag is inside the bound plans nothing
- [ ] the knob unset dispatches nothing however long the lag
- [ ] the knob at zero dispatches nothing however long the lag
- [ ] an unread trunk plans nothing and never raises

### S-122758: the action, the applier and the port that runs the trunk's workflow on the trunk

Design §2 and §3 (D6, D7; P4, P5). Acceptance is the fourth fenced block. One action, one
handler, one `gh` call.

- [ ] the action carries the sha the kernel judged and the one line of why
- [ ] the action describes itself in one line naming the short sha and the reason
- [ ] applying the plan calls the port exactly once
- [ ] applying the plan writes nothing to the record and moves no item's state
- [ ] the apply log line carries the port's own note, naming the workflow and the trunk branch
- [ ] a port that refuses the dispatch leaves one failed entry in the result and the rest of the plan applied
- [ ] the port runs the trunk's workflow on the trunk ref through the repo slug
- [ ] the port takes the workflow from the product's trunk workflow convention
- [ ] the port refuses with a port error when the product declares no trunk workflow
- [ ] the port refuses under the dry-run mutation guard like every other kernel write
- [ ] the staleness guard never skips a dispatch, since it targets no pull request

### S-122759: the knob, the MAIN PENDING line, and the trigger a dispatch needs

Design §3, §4, §5 and §6 (D8, D9, D10, D11; P3, P5). Acceptance is the fifth fenced block. The
knob is readable, documented and reaches the judge; the tick says what it did; and the trunk's
workflow accepts a dispatch at all.

- [ ] the kernel settings hold a mainline section whose max pending defaults to five
- [ ] a product file setting the knob is read back as given
- [ ] a knob of the wrong type is a named error against its dotted key and the load is refused
- [ ] the documented block in the settings module names the mainline section and its default
- [ ] the example product file documents the mainline section and its default
- [ ] the product's knob reaches the config the judge reads
- [ ] a knob of zero reaches the config as off
- [ ] the tick line for a pending trunk reads MAIN PENDING with the sha and the action
- [ ] the tick line for a red trunk still reads MAIN RED with the sha and the action
- [ ] a trunk record carrying no kind at all still prints as MAIN RED
- [ ] the trunk's workflow declares the workflow dispatch trigger
- [ ] the trunk's workflow still fires on a push to the trunk only, and on pull requests
- [ ] the trunk's workflow still groups its runs by event, so a dispatched run is its own group
