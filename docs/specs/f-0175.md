# F-0175 — the CI log stops and nothing says so

A product's `metrics/ci` stream ends on 09-21, the day its pre-ASF collector was retired. The
groom policy `decide_or_close_ci_red` reads that stream, so it answers CI-red Bugs off a log that
stopped a week ago — or, for the five Bugs filed after the last recorded run, answers nothing at
all. Nobody was told. The tick kept running, `asf doctor` kept printing green, and the only
symptom was five open Bugs that the groom never touched.

The card asks for three things. Read against this checkout, the first is **most of the way there
already and nobody can see it working**, and that is the whole shape of this card:

> `run_step0` calls `cmd_backfill(days=1, workflow=ci_workflow(product))` **every tick**, for
> every product whose `ci.provider` is not `none` (`asf/tick/tick.py:96-99`). ASF already
> collects trunk CI runs itself.

So the defect is not that the collector is missing. It is that the collector it has cannot close a
gap, pays for every run twice, and is completely silent about both — and that the two readers
downstream of it treat "the log stopped" as "the trunk has been quiet". Three measurements, taken
in this checkout (P1, P2, P3, P9), say it exactly:

| measured | what it means |
| --- | --- |
| `days_back('2026-09-29', 1) == ['2026-09-29']` — the listing asks the host for `created>=<today>` | a tick that misses a midnight never learns yesterday's runs, and a collector that is down for eight days leaves an eight-day hole **that no later pass will ever fill** |
| 40 runs listed → **40** `gh api …/jobs` calls; the same pass again, with all 40 already in the stream → **40** again | `append_event` is first-write-wins on `(run, attempt)`, so every one of those 40 fetches is thrown away |
| a pass that collected nothing: `rc=0`, printed `''` | a misconfigured workflow name, an unset `repo_slug`, an unauthenticated `gh` and a genuinely quiet trunk are one and the same output |

And downstream, run here (P9):

```
newest fact is 10d old; ci_red_days=7
answer: Answer(word='no: green since bbbbbbbbb', field='removed', …)
```

The policy closes a CI-red Bug on a ten-day-old green while its own window is seven days. The
failure branch of `decide_or_close_ci_red` is bounded by `ci_red_days`; the closing branch is
bounded by nothing.

This card makes the pass incremental against the record's own watermark, cached against the runs
the record already holds, and loud; gives `doctor` a row that goes RED when the newest trunk fact
outlives the cadence the facts themselves show; and bounds the policy on the newest fact rather
than on one branch of it.

### In

- **A collecting pass with a window of its own.** `cmd_backfill` with no `--days` reads the
  record's own newest trunk fact and asks the host from that day forward, floored at
  `CI_CATCH_UP_DAYS` (14) before today. The tick stops passing `days=1` and passes nothing, so a
  tick that missed a midnight — or a week — closes the hole on its next pass (P2). `--days N`
  keeps working, unchanged, as the operator's override.
- **A pass that does not buy what the record already owns.** `ci_from_api` takes the
  `{(run, attempt)}` the stream already holds and skips the per-run `jobs` and `pr_info` fetches
  for those runs. The **listing** is untouched — all runs still reach `by_branch`, so `superseded`
  is bit-for-bit what it is today (P5), and a run already recorded could not have been improved
  anyway (P4).
- **A pass that says what it did, every time, including nothing.** One `ci:` line per pass naming
  the window, how many runs were listed, how many the record already held, how many were fetched,
  how many were appended, and the newest fact after it — or, when the listing was empty, *which*
  of P6's causes it was: the host did not answer, the product names no `repo_slug`, or the window
  genuinely held no run of that workflow.
- **`gh_lines_answered(args, timeout)` → `(lines, answered)`**, with `gh_lines` a two-line wrapper
  over it. The one thing P6 cannot currently distinguish — "the host said nothing" from "the host
  said there is nothing" — becomes one boolean, and every existing `gh_lines` caller is untouched.
- **`metrics.ci_facts(root, conv, limit=None)`** — the trunk half of the `ci` stream, **newest
  first**, at most `limit`, day files read newest-first so a caller wanting one timestamp does not
  parse a year of jsonl. It becomes the **one** parser of those facts:
  `groom.trunk_ci_runs` is reduced to reversing it, with the same `parse_iso`, the same
  `conv.is_trunk` filter, **no workflow filter** (P8) and therefore the same tuple the policy
  reads today.
- **A `ci facts` doctor row**, required, for any product with CI to collect: the age of the newest
  trunk fact against `ci_stale_factor ×` the cadence the facts themselves show, never RED before
  24 h. A product with no fact at all and a CI provider is RED with a row that names the pass.
- **One new convention: `conventions.ci_stale_factor`** (int, default 3) — the N of "N× the CI
  cadence", documented in `docs/guide/product-config.md`.
- **One window in `decide_or_close_ci_red`, on the newest fact.** The guard that today bounds only
  the failure branch moves to cover both, unchanged in value (`ctx.ci_red_days`) and unchanged in
  its six shipped outcomes (P11).

### Out

- **Moving the collection into the `health` or `prs` step.** The card names those two; the pass
  already runs, in step 0, before the `groom` step that reads its output (`STEPS = ['record',
  'health', 'groom', …]`). Moving it would buy nothing, would put the write *after* `do_index`
  instead of before it, and would leave a second collector to retire. D1.
- **A new state file for the watermark.** The record's own stream is the watermark (D3).
- **Changing the `ci` event schema, `natural_key`, `append_event`'s first-write-wins, or
  `validate`.** The facts are the right facts; nobody is collecting them reliably. F-0070's
  `stall`/`stall_step` work and F-0158's `'updated'` status are untouched.
- **Filtering the doctor row or `trunk_ci_runs` by workflow.** `trunk_ci_runs` has never filtered
  by workflow (P8) and a doctor row that did would go RED on a product with two CI workflows while
  the policy read facts happily from the other. The row measures exactly what the policy reads.
  A workflow name that matches nothing (P7) still surfaces — as facts that stop arriving.
- **Filing a Bug when the facts go stale.** `doctor` reports; `file-bugs` files. A row that is RED
  for a week is a row the operator sees on every `asf doctor`, and the card asks for a row.
- **Answering *why* collection stopped for the first customer** (P21). The pass line will name it
  on the next tick; this card does not guess it now.
- **Retiring or reading the legacy collector's output.** The stream it wrote is already in the
  record and stays there; nothing re-imports it and nothing deletes it.
- **`ci.provider` validation, or a doctor row for a missing `repo_slug`.** Both are causes the
  pass line now names; neither grows its own check here.
- **The `sessions`, `landings`, `gates` and `ticks` streams.** `cmd_backfill` collects all five;
  only the `ci` half changes.
- **Rate limiting, retry or a budget on the listing call.** One listing plus (now) only the
  uncached runs' jobs is strictly less than today's traffic. A cap belongs to whoever measures one.

## The design

### `asf/metrics/metrics.py` — the pass, its window, its cache, and the one parser

Three constants, beside `STREAMS`:

```python
#: How far back one collecting pass reaches when the record gives it no watermark, or when the
#: watermark is older than that (D2). A gap longer than this is skipped — and said out loud.
CI_CATCH_UP_DAYS = 14
#: The newest trunk facts the cadence is measured over (D7).
CI_CADENCE_SAMPLE = 20
#: The cadence assumed until there are three facts to measure one from (D7).
DEFAULT_CI_CADENCE_H = 24
```

`ci_facts` — the one parser (D10), newest first:

```python
def ci_facts(root, conv, limit=None):
    """The trunk's finished CI runs off the record's ``metrics/ci`` stream, **newest first**, at
    most ``limit`` of them: ``{'ts': datetime, 'sha': str, 'jobs': {name: conclusion}}``.

    The one reader of the stream's trunk half (D10): :func:`asf.groom.groom.trunk_ci_runs`
    reverses it for the policy and :func:`asf.doctor.check_ci_facts` measures its age, so neither
    can come to hold a different idea of what a trunk CI fact is. A run on any branch but
    ``conv.main`` is left out; a job listed twice in one run keeps its last conclusion.

    Day files are read newest first and the read stops as soon as ``limit`` facts are in hand — a
    caller that wants one timestamp does not parse the whole stream.
    """
```

It parses with `asf.tick.stale.parse_iso`, imported inside the function (P19), so the datetimes the
policy already compares are the datetimes it gets today.

`ci_watermark(root, conv)` → the `YYYY-MM-DD` of `ci_facts(root, conv, limit=1)`, or `None`.

`ci_window(root, conv, days=None, day=None)` → `(since, floored)`:

- `days` given (the operator's `--days N`) → `days_back(day or today(), days)[0]`, `floored=False`.
- else the watermark's day, unless it is more than `CI_CATCH_UP_DAYS` before today, in which case
  the floor day and `floored=True`.
- no watermark → the floor day, `floored=False` (a first pass is not a skipped gap).

Re-listing the watermark's own day is deliberate: that day is the only one the stream may hold
partially, and `append_event` makes the overlap free.

`ci_runs_held(root, days)` → `{(run, attempt)}` from `read_stream(root, 'ci', days)` — what the
pass must not fetch again (D4).

`gh_lines_answered(args, timeout=300)` → `(lines, answered)`; `gh_lines` becomes
`return gh_lines_answered(args, timeout)[0]` (D5).

`ci_from_api` gains three keyword arguments, all defaulting to today's behaviour:

```python
def ci_from_api(days, workflow, batch_prs, items, repo_slug=None, product=None, conv=None,
                since=None, held=(), report=None):
```

- `since` (a day string) overrides `days` for the listing.
- the listing is unchanged and `by_branch` is still built from **every** listed run (P5).
- `fresh = [r for r in runs if (r['id'], r.get('run_attempt') or 1) not in held]`; `jobs_of` is
  mapped over `fresh`, `pr_info` is consulted for `fresh`, and events are built for `fresh` only.
- `report`, when a dict is passed, is filled with
  `{'since', 'listed', 'held', 'fetched', 'answered'}`.

`cmd_backfill` builds the window, the held set and the report, and prints one line per pass (D6):

```
ci: 2026-09-21..2026-09-29 — listed 61, held 47, fetched 14, appended 14; newest 2026-09-29T08:12:04Z (23m)
ci: 2026-09-15..2026-09-29 — the host did not answer (gh); newest 2026-09-21T14:02:11Z (8d)
ci: 2026-09-15..2026-09-29 — no run of workflow 'ci' in the window; newest 2026-09-21T14:02:11Z (8d)
ci: 2026-09-15..2026-09-29 — the product names no repo_slug; no trunk fact in the record
ci: 2026-09-15..2026-09-29 — reached back 14d; runs before 2026-09-15 are not collected
```

The last is printed *in addition*, when `floored` is true. The `ci appended: N` / `ci exists: N`
counters `put` already prints are untouched — they are shared with four other streams.

`--days` becomes `type=int, default=None` and its help says "default: from the newest trunk CI run
the record holds".

### `asf/doctor.py` — the `ci facts` row

| age past the limit | `(True, False, 'newest trunk CI run 8d ago (a1b2c3d4e, cadence 41m, red past 24h) — CI facts are not being collected')` |

## Stories

- S: The collecting pass reaches back to the record's own newest trunk fact instead of to midnight, floors a gap at 14 days, never fetches the jobs of a run the stream already holds, and says what it did on every tick — the window, the runs listed, held, fetched and appended, the newest fact after it, and which of the five silent causes an empty listing was — with `metrics.ci_facts` as the one parser of the stream's trunk half that `groom.trunk_ci_runs` now reverses — acceptance: `python3 -m unittest -v tests.test_metrics.CollectingPass tests.test_metrics.Backfill`
- S: `asf doctor` grows a required `ci facts` row that reports the age of the newest trunk CI fact and goes RED when it outlives `ci_stale_factor ×` the cadence the facts themselves show — never before 24 hours, and never at all for a product with no CI to collect — acceptance: `python3 -m unittest -v tests.test_doctor.CiFactsRow`
- S: `decide_or_close_ci_red` answers nothing off a fact older than its own window: the bound that today covers only the failure branch moves onto the job's newest run and covers the close too, so a ten-day-old green no longer closes a CI-red Bug under a seven-day window — acceptance: `python3 -m unittest -v tests.test_groom_policy.FactPolicyTests`
