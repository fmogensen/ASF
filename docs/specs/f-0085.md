# F-0085 — The groom answers itself (D-0049): rules as code, an adjudicate session for the rest, a digest to the operator

Parent: E-0001 — ASF 0.1 — a working factory. Stage: card → spec.

The card, as the requirement: *implements D-0049 for the `asf` product (and any product whose yaml
sets `approvals.groom: auto`)*. Three parts, named by the title: **rules as code** — the groom
questions a rule can answer, answered by code; **an adjudicate session for the rest** — the
questions no rule reaches, given to one session; **a digest to the operator** — what is left, and
what was done in their absence, as one thing to read instead of a questionnaire to fill.

Today `asf groom` writes `groom/<date>.md`: eight sections of `- [ ] <id> <title> — <why> → answer:
____` lines, and `--apply` reads yesterday's file back. Every `____` is a person. A day nobody
fills it in is a day nothing is decided, and the sections grow. This card closes the loop: the
`____` is filled by a policy, by a session, or by nobody — and when it is nobody, that is said out
loud in one line rather than left as a blank in a file nobody opened.

This changes code under `asf/` and `tests/` in this repository. It does not change any card in any
record; it changes what writes to them.

## 1. Decisions

### In

- A **policy pass** in `asf groom`: four named policies (§2.2) that answer a groom question from
  the record alone, write the answer as a typed field with a History line attributed to the
  policy, and are gated on `approvals.groom: auto`.
- A **suppression pass**: a groom question about an item the feeder already has a row for, or that
  a live session already holds, is not asked of anyone (§2.3).
- One new answer verb, `unblock <id>` (§2.4), because the `blocked on a Closed item` section has no
  answer word today.
- A **`GROOM → ADJUDICATE` feeder row** (§2.5) and a new brief kind `groom` (§2.6): one session per
  groom day, for every question the policies did not answer.
- The session's deliverable: an **answers file** in the product's state dir, applied by the next
  `groom --apply` (§2.6). The session writes nothing to the record and nothing to the product repo.
- A **digest** `groom/<date>-digest.md` in the record (§2.7), derived from the cards' History, plus
  a `Groom` row in `asf status`.
- One `groom_answer` event per applied answer in `metrics/events/<day>.jsonl` (§4).
- New config: `approvals.groom`, a `groom:` block in the product yaml, and
  `conventions.branch_prefixes.groom` (§2.1).

### Out

- **The eight sections themselves.** `build_groom_sections` and `GROOM_SECTIONS` keep their present
  shape, wording and order. This card decides who answers them, not what is asked.
- **The approval matrix as a whole.** `approvals` has no reader in the package today; this card
  adds the first one, for the single key `approvals.groom`. Making the other classes (`spend_money`,
  `new_epic`, …) refuse at the hooks is F-0031 and stays there. §2.8 is the one place the other
  classes are consulted, and it consults them read-only.
- **A product whose yaml does not set `approvals.groom: auto`.** Unset, or `groom`, or `human-now`:
  every behaviour in this card is off and `asf groom` writes exactly the file it writes today. The
  default is off — a factory does not start deciding by upgrade.
- **Teaching `asf.workers.spawn` a second repository.** See D4.
- **Rule cards.** The policies are not `rules/R-nnnn.md` cards. See D2.
- **Changing what `asf stale` reports.** `stage_limits.undecided_close` is read by `stale.py` today
  and reported; this card makes a policy act on the same limit. The report is unchanged.
- **Back-filling.** The policy pass answers the questions in the run it is in. It does not walk
  previous `groom/<date>.md` files.

### Choices

| # | Choice | Chosen | Against | Why |
| --- | --- | --- | --- | --- |
| D1 | What "the groom answers itself" may decide | Only answers that are **reversible from the record**: a typed field with a History line. Never a delete, never a file move, never a card's prose | A free hand over the record | Every answer this card writes is one `frontmatter.write_typed` and one History line — the same edit an operator's `yes` makes today. An answer that was wrong is visible in History and undone the same way. Nothing new becomes irreversible |
| D2 | Where the policies live | Python in a new `asf/groom/policy.py`, one function per policy, a table binding it to a groom section | `rules/R-nnnn.md` cards with `check:` scripts, run by `asf rules check` | The rules engine reports **violations** — a check exits 1 and prints a line. A policy must return *an answer for one card*, with a field, a value and a reason. That is a different signature and a different lifecycle. Reusing the rules engine would mean a check script that writes to the record, which is exactly what `rules.py` is not |
| D3 | How a policy's answer reaches the card | The existing answer grammar: the policy writes `→ answer: controller: <word>` into today's file, and the same run applies it through `apply_groom_answers` | A private write path straight to `frontmatter.write_typed` | One applier, one grammar, one place that knows how an answer becomes a field. The groom file stays the readable record of what was answered and by what. P3's `controller:` prefix exists for precisely this |
| D4 | Where the adjudicate session writes its answers | `~/.ASF/state/<product>/groom/<date>.answers`, in the groom answer-line grammar, picked up by the **next** tick's `groom --apply` | The session commits to the record in a record worktree | P6: `make_worktree` knows one repo. Teaching it a second is a change to the launch path, which every kind rides — a large blast radius for one kind's convenience. And the record already has exactly one writer, the tick (P4). Keeping it that way costs one tick of latency and buys no new way for the record to be written concurrently |
| D5 | One session for the whole list, or one per question | One per groom day, for every open question | One `GROOM → ADJUDICATE` row per unanswered card | The card says "an adjudicate session for the rest" — singular, for the remainder. One per question floods the pool on the first run against a record with a long-ignored groom. Judging a list together is also better judgement: the duplicates and the starvation cases inform each other |
| D6 | The row's `item_id` | The **oldest** open question's card id | A synthetic id for the groom day | `briefs.build.item_line` falls back to `Backlog item: none (<why>)` for an id the index does not carry, and that first line is the only one a session registry reads. A real card keeps the registry, the preamble and `asf sessions` honest. The job name carries the date instead (D7), so the session is still one-per-day |
| D7 | The job name | `groom-<date>`, via a per-kind override in `step_wave.job_name` | `groom-<item_id>`, the default | Two groom days whose oldest question is the same card would produce the same job name, the same branch and a worktree collision. The date is what makes a groom session unique |
| D8 | The cap on relaunching | At most `groom.adjudicate_attempts` (default 2) sessions per groom date, counted from the ledger. Past the cap the remaining questions go to the digest under `NEEDS OPERATOR` | No cap; or the feeder's `attempt_limit` | A session that ends without writing its answers file must not be relaunched forever — that is the failure mode `STALEMATE → ADJUDICATE` exists to stop elsewhere. `attempt_limit` counts per *item*, and D6 makes the item drift as questions get answered, so it cannot serve here |
| D9 | Where the digest lives, and whether it is regenerated | `groom/<date>-digest.md`, **fully regenerated** from the cards' History on every groom run | Appended to as answers arrive; or a section of `groom/<date>.md` | `cmd_groom` rewrites `groom/<date>.md` wholesale, so anything hand-added there is lost (the same reason F-0002's D5 put its notes in a separate file). A regenerated digest is derived state over typed intent — the constitution's §6 shape — which makes it idempotent, and makes "the digest lies" a diff rather than an argument |
| D10 | What a policy may never answer | Anything whose answer would cross an action class the product maps to `human-now` (§2.8). Today that is one case: an inbox card inferred as an Epic, against `approvals.new_epic` | Policies bounded only by their own conditions | The approval matrix is the operator's statement of what they keep. A groom that auto-decides a new Epic while the yaml says `new_epic: human-now` has quietly overridden it. The same bound holds for the session: what a policy may not answer, the adjudicator is not asked |
| D11 | The defaults for the four policies | Deliberately timid: exact-duplicate overlap `0.95` (the section's own threshold is `0.6`), recurring-bug count `2`, starvation at the existing `stage_limits.undecided_close` (`14d`) | Thresholds tuned to clear the most questions | A policy that is wrong is a card closed or decided without anyone asking. The first version should answer the questions that are not questions and hand over everything else. The thresholds are config, so an operator who watches the digest for a fortnight can loosen them |
| D12 | What the session may not do | It writes one file, in the state dir, in the answer grammar. It commits nothing, to either repository. Its worktree is an ordinary product-repo worktree it does not write to | Giving it the record, or giving it no worktree | D4. An ordinary worktree costs one `git worktree add` and needs no change to the launch path. The template says, in as many words, that the repository is not its work |

## 2. The design

### 2.1 Config — the new keys

In `~/.ASF/products/<name>.yaml`, added to `docs/products.example.yaml`:

```yaml
approvals:
  groom: auto            # auto | groom | human-now — the one key this card reads.
                         # unset or anything but `auto`: every behaviour below is off.

groom:
  # the four policies' thresholds. A policy whose key is absent uses the default shown.
  duplicate_overlap: 0.95      # close_exact_duplicate: title overlap at or above this
  recurring_bug_count: 2       # decide_recurring_bug: auto-filed Bug seen this many times
  adjudicate_attempts: 2       # D8: groom sessions per groom date before the operator is asked
  policies:                    # a policy named here with `off` never runs
    close_exact_duplicate: on

conventions:
  branch_prefixes:
    groom: groom               # the groom session's throwaway branch
```

`groom` joins `env.PRODUCT_FIELDS` as `_MAP` (P7), and `Product.groom` is a property beside
`Product.approvals`. `groom_auto(product)` in `asf/groom/policy.py` is the single gate:
`str((product.approvals or {}).get('groom', '')).lower() == 'auto'`.

Nothing else in the package reads `groom:`. A product with no `groom:` block and
`approvals.groom: auto` gets every default.

### 2.2 The policy pass — rules as code

New module `asf/groom/policy.py`. A policy is a function
`policy(item_id, rec, canonical, derived, ctx) -> Answer | None`, where `Answer` is a dataclass
`(word, field, value, why)`; `None` means "no rule reaches this one". `ctx` carries the run's date,
the thresholds and the `now` clock, so no policy reads the wall clock or the config itself.

`POLICIES` binds section keys to policies, in the order they are tried:

| Policy | Section | Answers when | Word written | Reason line |
| --- | --- | --- | --- | --- |
| `unblock_on_closed` | `blocked_closed` | always — the blocker's `state` is `Closed` | `unblock <blocker>` | `blocker <id> is Closed` |
| `close_exact_duplicate` | `dupes` | overlap ≥ `duplicate_overlap`, same `type`, same `parent`, and the **younger** card is `state: New`, `decided != true`, childless, named in no `blockedBy`, and has no branch in `links` | `no` | `duplicate of <id> (overlap 0.97)` |
| `decide_recurring_bug` | `auto_bugs` | the Bug has a `signature` and `count >= recurring_bug_count` | `yes` | `auto-filed, seen <n> times` |
| `close_on_starvation` | `undecided14` | the card is older than `stage_limits.undecided_close`, still `decided != true`, childless, named in no open item's `blockedBy`, and no session in the ledger ever ran on it | `no` | `undecided <age>, starvation policy` |
| — | `inbox`, `undecided3`, `no_stories`, `no_tasks` | never — new intent, and two questions with no answer word | — | — |

Every policy is skipped when §2.8 bars it, and when `groom.policies.<name>` is `off`.

The pass runs inside `cmd_groom`, after `process_inbox` and before `build_groom_sections`, in four
steps:

1. build the sections once, to get the questions;
2. suppress (§2.3);
3. for each surviving line, try its section's policy. An `Answer` is rendered into the line as
   `→ answer: controller: <word>` and collected;
4. apply the collected answers through `apply_groom_answers` against the file just written (D3),
   so the History line is
   `- <date> groom: <field> → <value> (controller, <policy>)`.

`apply_groom_answers`'s `who` becomes `(controller, <policy name>)` when the `controller:` prefix is
followed by a known policy name, and keeps `(controller, starvation policy)` for a hand-written
one — the existing string stays valid.

The pass is idempotent: a policy whose answer is already the card's value writes nothing
(`apply_groom_answers` already returns early on an unchanged field), so a second `asf groom` on the
same date changes no card and produces the same digest.

### 2.3 The suppression pass

A question the factory is already acting on is asked of nobody. `suppress(sections, index, inflight)`
drops a line when:

- a live session in `sessions.jsonl` holds that item; or
- `asf.feeder.rows.candidates()` emits a launching row for that item.

The suppressed line is not deleted — it is rewritten as
`- [x] <id> <title> — <why> → answer: (spoken for: <ROW KIND>)`, so the groom file still shows the
question and says who has it. A `[x]` line carries no `→ answer: <word>`, so `apply_groom_answers`
(which matches on `→ answer: <text>`) parses it and finds no known word, and changes nothing.

This is what keeps a `Features without Stories` line from reaching an adjudicator while a
`CARD → SPEC` session is already writing that Feature's spec — two writers, one card.

### 2.4 The new answer verb

`_parse_answer` gains one case, before the fallthrough:

```
ANSWER_UNBLOCK = re.compile(r'^unblock\s+([A-Z]-\d{4})$', re.IGNORECASE)
```

returning `('unblock', '<ID>')`. `apply_groom_answers` handles `unblock` as its one non-scalar
field: it reads the card's `blockedBy`, removes the id, and writes the remainder (or removes the
field when the list empties). The History line is
`- <date> groom: blockedBy → <remaining, or (none)> (controller, unblock_on_closed)`.
An id not in `blockedBy` is a no-op, which keeps `--apply` idempotent.

### 2.5 The feeder row

In `asf/feeder/rows.py`:

```
GROOM_ADJUDICATE = 'GROOM → ADJUDICATE'
```

`groom_row(index, product, busy, groom_state)` returns at most one `Row`:

- `tier=2`, `kind=GROOM_ADJUDICATE`, `brief_kind='groom'`;
- `item_id` = the oldest open question's card (D6), `feature_id` = `feature_of` that card, or `''`;
- `branch` = `branch_for(product, 'groom', <date>, default='groom/')`;
- `reason` = `"<n> groom questions no rule answers, oldest <id> (undecided <age>)"`.

`groom_state` is the one fact the feeder cannot derive from `index.json` (P5): it is passed in by
the caller, as `{'date': ..., 'open': [ids], 'oldest': id, 'attempts': n}`. `step_wave` fills it
from the record clone's newest `groom/<date>.md` — counting the `- [ ] … → answer: ____` lines that
remain — and from the ledger's `groom-<date>` jobs. A caller that passes no `groom_state` gets no
row, which keeps every existing feeder test and `asf next` unchanged.

The row is emitted only when: `groom_auto(product)`, `open` is non-empty, no live session holds
`groom-<date>`, and `attempts < groom.adjudicate_attempts` (D8). It sorts after the stalemate and
branch-housekeeping rows and before new Feature work, in tier 2.

### 2.6 The brief

`groom` joins `briefs.build.KINDS`, `DEFAULT_MODELS` (`HEAVY` — this is judgement), and
`ID_RANGE_KINDS` (it may mint a Decision card for a ruling that deserves one). A new template
`asf/briefs/templates/groom.md` uses only names `briefs.build.context` already provides, plus two
new ones the row carries: `groom_file` and `answers_file`.

What the template tells the session, in the house's imperative voice:

- the groom file to read, and the open questions listed in the preamble;
- **for each open question, one of**: an answer word from the grammar (`yes`, `no`, `rank <n>`,
  `parent <id>`, `S1|S2|S3`, `unblock <id>`) with one sentence of why; or the literal
  `NEEDS OPERATOR: <the question> — <your recommendation>`. Never "noted", never a question back;
- write them, and nothing else, to `{answers_file}` — one line per question, in the exact grammar
  `- [ ] <id> <title> — <why> → answer: <word>`, prefixed `adjudicator:` instead of `controller:`;
- **the repository is not your work.** Do not commit, do not push, do not edit a card. The tick
  applies what you write (D4, D12);
- the four that are never yours (licence, money, security, customer-visible) go to
  `NEEDS OPERATOR`, matching `adjudicate.md`'s rail.

`apply_groom_answers` learns the `adjudicator:` prefix beside `controller:`, attributing
`(adjudicator, <job>)`. `step_daily` passes `~/.ASF/state/<product>/groom/<date>.answers` to
`cmd_groom` as a second answers source, applied after the previous groom file and before the policy
pass; the file is renamed to `<date>.answers.done` once applied, so it is applied once.

`step_wave.job_name(brief_kind, item_id)` gains `KIND_JOB_KEY = {'groom': <the groom date>}` — for
the `groom` kind the job is `groom-<date>` (D7).

### 2.7 The digest

`asf/groom/digest.py` renders `groom/<date>-digest.md` on every `cmd_groom` run, derived (D9) from
the cards' `## History` lines for `<date>` plus the day's remaining open questions:

```markdown
# Groom digest <date>

3 answered by rule · 5 ruled by the adjudicator · 2 spoken for · 1 for you

## Answered by rule
- B-0031 decided → true — decide_recurring_bug: auto-filed, seen 3 times
- F-0077 removed → groom <date> — close_on_starvation: undecided 21d
- S-0140 blockedBy → (none) — unblock_on_closed: blocker T-0091 is Closed

## Ruled by the adjudicator (groom-<date>)
- F-0081 decided → true — the card names a real gap; ranked behind F-0079

## Spoken for
- F-0012 no Stories — CARD → SPEC is writing its spec

## For you
- NEEDS OPERATOR: E-0004 — the inbox card reads as a new Epic, and approvals.new_epic is human-now.
  Recommendation: fold it under E-0001 as a Feature.

— generated by asf groom@<sha> <HH:MM>
```

The stamp line is `asf.cli.stamp('groom')`, the same one every generated table carries. A `For you`
section that is empty prints `(none)`; a digest with nothing in any section is still written, so
"the groom ran and there was nothing" is distinguishable from "the groom did not run" (§6 of the
constitution).

`asf status` gains one row, `Groom`, filled from the newest digest:
`<date>: 3 by rule, 5 ruled, 1 for you` — or `not_configured('approvals.groom')` when the product
does not set it, matching the view's "never a bare —" rule.

### 2.8 The approval bound

`barred(answer, item, product)` in `asf/groom/policy.py` returns the action class when an answer
would cross one the product maps to anything but `auto`. One mapping today:

| The answer | The class | Consulted key |
| --- | --- | --- |
| `yes` on a card whose `type` is `epic` | a new Epic | `approvals.new_epic` |

A barred question is answered by no policy, is not put to the session, and goes to the digest's
`For you` as a `NEEDS OPERATOR` line naming the key that barred it. The table is data, so F-0031
extends it without touching the groom.

## 3. Acceptance tests

All from the repository root, stdlib only (P8). The whole suite must stay green:

```bash
cd "$(git rev-parse --show-toplevel)"
git config --global user.name ci; git config --global user.email ci@localhost
python3 -m unittest discover -s tests
```

**T1 — the gate.** A product without `approvals.groom: auto` behaves exactly as today: no policy
runs, no line is suppressed, no digest is written, no row is emitted.

```bash
python3 -m unittest -v tests.test_groom_policy.GateTests
```

**T2 — the four policies.** One test per policy for the answering case and for the nearest
non-answering case (overlap just under the threshold; a Bug at count 1; a card one hour short of
`undecided_close`; a blocker that is `Active`, not `Closed`).

```bash
python3 -m unittest -v tests.test_groom_policy.PolicyTests
```

**T3 — an answer becomes a field and a History line, and only that.** After a policy pass, the
card's typed field holds the value, `## History` carries
`- <date> groom: <field> → <value> (controller, <policy>)`, and every other card in the fixture is
byte-identical to before the run.

```bash
python3 -m unittest -v tests.test_groom_policy.PolicyPassTests.test_answer_writes_one_field_one_history_line_and_nothing_else
```

**T4 — idempotent.** Running `asf groom` twice on the same date leaves the cards byte-identical
after the second run and renders the same digest.

```bash
python3 -m unittest -v tests.test_groom_policy.PolicyPassTests.test_second_run_same_date_changes_nothing
```

**T5 — `unblock`.** `_parse_answer('unblock S-0140')` returns `('unblock', 'S-0140')`; applying it
removes that id from `blockedBy` and leaves the others; applying it twice is a no-op.

```bash
python3 -m unittest -v tests.test_groom.AnswerParsingTests tests.test_groom_policy.UnblockTests
```

**T6 — suppression.** A Feature with no Stories for which `candidates()` emits `CARD → SPEC` is
rendered as a `- [x] … (spoken for: CARD → SPEC)` line, is not answered by a policy, and is not
among the open questions the feeder counts.

```bash
python3 -m unittest -v tests.test_groom_policy.SuppressionTests
```

**T7 — the approval bound.** With `approvals.new_epic: human-now`, an inbox card inferred as an
Epic is answered by no policy, does not appear in the row's open list, and appears in the digest's
`For you` section as a `NEEDS OPERATOR` line naming `approvals.new_epic`.

```bash
python3 -m unittest -v tests.test_groom_policy.ApprovalBoundTests
```

**T8 — the feeder row.** Given a `groom_state` with two open questions, `candidates()` emits one
`GROOM → ADJUDICATE` row whose `item_id` is the oldest, `brief_kind` is `groom` and branch is
`groom/<date>`. It is not emitted when: the product is not `auto`; `open` is empty; a live session
holds `groom-<date>`; attempts have reached the cap. Called with no `groom_state`, the feeder emits
exactly the rows it emits today.

```bash
python3 -m unittest -v tests.test_feeder.GroomRowTests
```

## 4. Records

**Cards (in the product's record).** One typed field write and one `## History` line per applied
answer, through the existing `frontmatter.write_typed` / `append_history_lines` path:

```
- 2026-09-22 groom: decided → true (controller, decide_recurring_bug)
- 2026-09-22 groom: removed → groom 2026-09-22 (controller, close_on_starvation)
- 2026-09-22 groom: blockedBy → (none) (controller, unblock_on_closed)
- 2026-09-22 groom: rank → 40 (adjudicator, groom-2026-09-22)
```

**Files.**

| Path | Written by | Shape |
| --- | --- | --- |
| `<record>/groom/<date>.md` | `cmd_groom` | as today, plus `controller: <word>` answers and `- [x] … (spoken for: …)` lines |
| `<record>/groom/<date>-digest.md` | `cmd_groom` | §2.7, regenerated every run |
| `~/.ASF/state/<product>/groom/<date>.answers` | the groom session | answer lines, `adjudicator:` prefixed |
| `~/.ASF/state/<product>/groom/<date>.answers.done` | `cmd_groom` | the same file, renamed once applied |
| `~/.ASF/state/<product>/sessions.jsonl` | `spawn` | one launch line, `job: groom-<date>`, `kind: groom` |

**Events** — `<record>/metrics/events/<day>.jsonl`, appended by the tick's `ctx.event` through the
sink `step_daily` now passes to `cmd_groom`:

```json
{"kind": "groom_answer", "item": "B-0031", "section": "auto_bugs", "field": "decided",
 "value": "true", "by": "rule:decide_recurring_bug"}
{"kind": "groom_answer", "item": "F-0081", "section": "undecided3", "field": "rank",
 "value": "40", "by": "adjudicator:groom-2026-09-22"}
{"kind": "groom_open", "count": 1, "barred": 1}
```

plus the `launch` event `step_wave` already appends for the groom session
(`brief_kind: groom`).

**Printed.** `cmd_groom`'s last line gains the pass's counts, so the tick log carries them:
`groom <date>: applied 4, inbox 1 card(s), by rule 3, spoken for 2, open 1 — <the section counts>`.
