# F-0260 — the factory tells the operator to write in a file nothing ever reads

The `NEEDS OPERATOR` row ends in a promise: *answer its `inbox:<file>` line in
`groom/<today>.md` (the next tick applies it)*. The operator does exactly that, in the one
checkout they have, and three things happen, none of them the promise.

**The answer is written where no tick can see it.** The operator edits `groom/<today>.md` in their
record checkout (`backlog_dir`). The tick works in its own clone, which it fetches and
`reset --hard`s to `origin/<trunk>` at the head of every record step
(`asf/tick/shadow.py:69-81`), and reads the operator's checkout for exactly one thing — the
`origin` url (`asf/tick/shadow.py:57-58`). An uncommitted line in the operator's working tree is
not on origin, so it is not in the clone, so there is nothing for the applier to apply. The
applier itself is not the bug: `_groom` has read the previous day's file *and today's own* since
v0.1.210 (`asf/groom/groom.py:1265-1277`), and `tests/test_groom_adjudicate_reach.py:173` proves
it. It reads the right file in the wrong repository.

**The edit then jams the one thing that kept the operator's view honest.** `sync_operator_checkout`
fast-forwards that checkout to origin after every tick push, and refuses on a dirty tree
(`asf/tick/shadow.py:221-224`). Its return value is read by nobody (`asf/tick/tick.py:310`), it
runs inside `finish` — *after* `[step:record] … ok=yes` has already been printed and after
`record_health.record(ok=True)` has already been written (`asf/tick/tick.py:632-633`, `:645-647`)
— so the tick says `record ok` and means it, about a step whose last act silently stopped
working. The checkout then drifts: 28 commits in about an hour on 2026-10-06.

**And `asf status` blames the factory for it.** The Stale row reads `metrics/ticks` and
`index.json` *out of that checkout* (`asf/views/status.py:244-251`, `:329-345`). Frozen checkout,
frozen clock: the row reads `STALE since <HH:MM> — no fresh record in 1h` while every tick in that
hour landed. The one artifact built to survive a broken record step — `record-health.json`,
local, never git-tracked (`asf/tick/record_health.py:1-9`) — says `ok`, because the record step
was fine.

**Then the hand `groom --apply` mints ids that are already taken.** `mint_id` claims on origin
only for `asf new` or a worktree (`asf/record/ids.py:93-94`); every other caller — the groom's own
intake at `asf/groom/inbox.py:357`, `file_bugs`, `flaky`, `plan_tasks`, `policy` — falls through to
`max_n + 1` read from the working tree (`asf/record/ids.py:76-87`, `:103`), stepping over only the
claim blocks the *local* mirror happens to hold, with no fetch (`asf/record/ids.py:104`). On a
checkout 28 commits behind, that is a stale top. Measured in this checkout (P9): the three ids it
mints are the three already on origin. And the push that follows reports success while throwing
them away — `_resolve_by_ownership` takes origin's side for every conflicted card
(`asf/tick/shadow.py:184-189`), which for an add/add collision means origin's Bug wins and the
operator's three Bugs are gone, under one line that says `origin moved — re-derived onto
origin/main and pushed`.

So this card is four seams, in the order a tick meets them: **carry the operator's answered line
to the record so the promise is true; make a refused sync a refusal the operator can read, with
its drift and its remedy, rather than a line under `record ok`; mint every id through the one
allocator, with a floor origin agrees with; and never discard a card inside a successful push
without saying which.**

## Decisions

throwaway repositories, using the production functions unchanged); the rest are the files read at

### In

* **The operator's answered line is carried, every tick, out of the record checkout into the
  state dir** as `<state dir>/<product>/groom/<date>.operator.answers`, and applied in the clone
  by the machinery that already applies an adjudicate session's answers (P15). The checkout is
  read — `git show HEAD:groom/<date>.md` and the file on disk — and never written, never
  committed, never pushed from.
* **`_ANSWERS_FILE_RE` in `asf/groom/answers.py` is widened to the shape
  `asf/groom/groom.py:1141` already accepts**, and the date comes from the regex's group rather
  than a suffix slice (P16, P17).
* **`sync_operator_checkout` returns why it refused, not just that it did** — a small record
  `(moved, why, behind, paths)` — and its lines name the drift and the record-relative paths
  that block it instead of the checkout's absolute path (P5, and F-0200's P13: no machine path).
* **A refused sync is a `NEEDS OPERATOR` line, an event, a `record-health.json` field and the
  Stale row's own words.** Said again every tick while it holds, pure over the checkout's state,
  with no ledger and no marker — the shape `stuck_s1_lines` already uses.
* **`[step:record] … ok=yes` stays `yes`.** The derivation did succeed; the sync is reported
  beside it, never as its exit code (see D4).
* **Every `mint_id` in a record checkout with an `origin` and claims on goes through
  `idclaim.claim_one`** — the `claim or worktree` gate goes (P10).
* **The claim's floor, and the local fallback's top, are read from `origin/<trunk>`'s tree**, not
  from a working tree that may be behind it (P9), after one fetch.
* **A push that discards a card to resolve an add/add collision names each one it discarded**, in
  one line and one `NEEDS OPERATOR`.

### Out

* **Changing the `NEEDS OPERATOR` row's words** (`asf/groom/inbox.py:562-565`). The promise it
  makes becomes true; rewording a line that is about to be correct is churn, and the row's
  record-relative path and `QUESTION_MAX` folding are F-0200's, tested there.
* **Committing or pushing anything from the operator's checkout, on the tick's behalf.** The
  tick's one write to that checkout stays a `--ff-only` merge of a clean tree on the trunk
  (B-0042's rule, `asf/tick/shadow.py:196-230`). Carrying a *copy* of the answered line into the
  state dir needs no write at all, which is why it is the mechanism chosen (D1).
* **Clearing the operator's local edit for them.** It is their tree. The refusal names the paths
  and the exact command; whether the edit is dropped is theirs to decide (C2).
* **Making a refused sync fail the record step.** `asf/tick/tick.py:648-652` (B-0083) stops every
  later step after a failed record, so a dirty operator checkout would stop the whole factory —
  a strictly worse failure than the one this card is about (D4).
* **Widening `approvals.groom: auto`.** The carry sits inside `apply_pending_answers`, behind the
  same gate (P17). On a `groom: manual` product nothing the groom decides applies itself, and an
  operator's answer is no different; named as C1, not fixed here.
* **Retiring the local-only mint path.** A record with no `origin`, or a product with
  `conventions.flags.id_claim: off`, keeps today's behaviour — with the origin floor where there
  is an origin to read (D7). `BACKLOG_ID_RANGE` is untouched: a job's claimed block still wins
  over everything, as `asf/record/ids.py:88-92` has it.
* **Repairing ids already collided.** `B-0268`–`B-0270` on the live record are an operator
  decision, not a migration: three Bugs were filed and lost (P12) and only a person knows what
  they said. The change makes the next one impossible and makes this one loud; it does not go
  back.
* **`asf groom --publish`, or any new subcommand** (P20). The carry runs inside the tick, where
  the promise was made. A command the operator must remember to run is the defect, restated.

### Choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | **The tick copies the answered lines out of the operator's checkout into `<date>.operator.answers` in the state dir, and the existing applier applies them in the clone.** | Committing and pushing `groom/<date>.md` from the operator's checkout; or having the tick's clone read that checkout as a second source of record truth. | The answers file is already the carrier for a hand-written answer the tick must apply, already carried out of a repository the tick does not own, already applied in the clone and published from there (P15). Reusing it needs no write to the operator's tree, so B-0013's rule survives intact, and the answer lands on origin as a factory commit from the clone — the same path an adjudicate session's answer takes. Pushing from the operator's checkout would mean the tick commits in a tree whose other contents it knows nothing about; `publish_changes` exists precisely because that is hard to do safely (P4), and doing it from a background tick is worse than doing it from a console command. |
| D2 | **A line is carried when its answer slot is filled (`not unanswered(answer)`) and the checkout's own `HEAD` copy of that file does not already carry that exact line.** | Carrying every answered line in the file; or diffing against `origin/<trunk>`. | `HEAD` is the comparison that isolates exactly the operator's uncommitted edit, with no fetch and no network. Carrying every answered line would re-carry the whole day's history of rule answers each tick; they are already on origin and already applied, so the work is wasted and the file churns. `origin/<trunk>` is the wrong side: a checkout 28 commits behind would call every line on origin "new". |
| D3 | **The carry writes nothing when every answered line it found is already in some `<date>.operator.answers` or `.done`/`.superseded` beside it.** | Writing the file every tick and letting `--apply`'s idempotence absorb it. | The operator's edit stays in their tree after the answer lands (the sync is still refused, C2), so the naive carry would write and apply the same file on every tick, forever — a state dir that grows and a `groom:` line that says `answers applied` about nothing. Idempotence makes it harmless, not free. |
| D4 | **A refused sync never changes `[step:record]`'s `ok=`.** It is reported in four places beside it: one `NEEDS OPERATOR` line, one event, one `record-health.json` field and the Stale row. | `ok=no` for the record step; or a new step. | `ok=no` on `record` triggers B-0083 (`asf/tick/tick.py:648-652`): nothing after a stale record runs. A dirty file in the operator's checkout would then stop the wave, the harvest and the daily — the factory halted by an edit it was never meant to care about. The record step's `ok` means "the index was re-derived", and it was. What the card asks for is that `record ok` stop being *the whole log line*, and that is what the four reports do. |
| D5 | **The `NEEDS OPERATOR` line is pure over the checkout's state, said again every tick, with no ledger and no marker.** | A once-only line, or a marker file that suppresses it. | `stuck_s1_lines` settled this for the same shape of problem (its C7): a row an operator must act on is said until the state it describes is gone, because the tick that said it once may be the tick nobody read. The state here — behind by N, refused for this reason — is one `git status` and one `rev-list --count` away, which is what `sync_operator_checkout` already runs (P5). |
| D6 | **Every mint in a checkout with an `origin` claims on origin: the `claim or worktree` gate goes.** | Leaving the gate and only fixing the floor. | The floor fix alone closes the measured incident (one stale writer) and leaves the race the claim mechanism was built for: two writers that read the same origin top in the same second both mint the same next id, and nothing refuses either. The gate also contradicts the module's own first line — "one allocator, shared by `new`, groom's inbox intake and `file-bugs`" (`asf/record/ids.py:1-2`) — while three of those three callers are on the other side of it (P10). One allocator means one allocator. The cost is named as C4. |
| D7 | **The floor is `max(the working tree's top, origin/<trunk>'s top)`, read after one fetch, in both the claim path and the local fallback.** | Trusting `idclaim.top` alone; or refusing to mint at all on a checkout behind origin. | `idclaim.top` knows only *claimed* blocks, and every id minted before this change has no claim ref — so on this record it is 0 for most prefixes and would re-mint history. Reading origin's own tree is the authoritative floor and it is one `ls-tree`. Refusing to mint was rejected because it turns a recoverable staleness into a dead command: the groom's intake would stop filing cards the moment a checkout fell behind, which is exactly when the factory is least able to tell anyone. |
| D8 | **The add/add case gets its own branch in `_resolve_by_ownership`, which returns the paths it discarded; the push prints them and the tick raises one `NEEDS OPERATOR`.** | Printing a line for every path the resolver touched; or aborting the push on add/add. | Four tests assert the push prints exactly one line on a modify/modify resolution (P19), and they are right to: nothing is lost there — the hand side's typed fields are kept and the derivation re-runs. add/add is the one shape where a whole card goes away, the stages already tell them apart (P13), and the operator needs the id to re-file. Aborting would leave the clone's own lines unpushed to protect a card that collided because it was minted wrong — the wrong trade once D6 makes the collision impossible. |
| D9 | **`_ANSWERS_FILE_RE` is widened to `asf/groom/groom.py:1141`'s shape and the date is taken from its group.** | A second regex just for the operator's file; or naming the file `<date>.answers` and risking a collision with the adjudicator's. | Two regexes for one file name is how P16 happened. The `half` segment is already in the applier and already turned into an adjudicator job name (`asf/groom/groom.py:1282-1286`), so `operator` reads through unchanged and the attribution says who answered. Sharing the plain `<date>.answers` name would mean the operator's answer and an adjudicate session's answer for the same day silently overwrite one another. |
| D10 | **The refusal lines name the checkout as `the record checkout` plus the record-relative paths that block it, never its filesystem path.** | Keeping the absolute path, which is what the line prints today. | The line goes into the tick log, and its fields go into an event in the record (`asf/tick/tick.py:249-257`), which is tracked and published. F-0200's P13 is the standing rule — a file is named record-relative, never by machine path — and `stuck_s1_lines` already obeys it for the same operator. A path tells the operator nothing they do not know; `behind 28, groom/2026-10-06.md` tells them what to do. |
| D11 | **The Stale row says the checkout is the stale thing, and keeps saying `STALE`.** | Suppressing the row when the sync is the cause; or a new row. | The row's job is "the numbers you are reading are old", and they are — 28 commits old. What was wrong was the cause: it read as the tick failing. Suppressing it would make a frozen board look current, which is worse than a wrong reason. `record_health.line` is already consulted first and already returns the sentence the row prints (P8), so the field goes there and the row needs one branch. |
| D12 | **Five Story ids from this session's `BACKLOG_ID_RANGE` (`S:60054-60103`): S-60054–S-60058.** | Minting four-digit ids that `plan_tasks.STORY_ID_RE` would match. | The range is the only id source this session has, and the record refuses an id no claim covers at land. The consequence is known and recorded: `plan_tasks.STORY_ID_RE` is `\bS-\d{4}\b` (`asf/record/plan_tasks.py:29`), so a five-digit Story does not link from a Task's `stories:` line — already named in `docs/specs/f-0258.md` D11 and `docs/plans/f-0208.md:54`. It is a Bug of its own and nowhere near this footprint. |

### Consequences, named not fixed

| # | Consequence |
| --- | --- |
| C1 | **On a product with `approvals.groom: manual`, the operator's answer in today's file still waits for a hand `asf groom --apply`.** The carry lives inside `apply_pending_answers`, which returns 0 before doing anything under a manual gate (P17). This is consistent — under `manual` no groom decision applies itself — but it means the `NEEDS OPERATOR` row's promise is true only under `auto`. The row cannot tell, because `stuck_s1_lines` is pure over the intake directory and takes no product approval. Widening it is a card about the row, not about the carry. |
| C2 | **The operator's checkout stays dirty, and so stays un-fast-forwarded, until they clear it themselves.** The answer lands on origin from the clone (D1); the local edit that produced it is still an edit. So the `NEEDS OPERATOR` line goes on being said — correctly — after the answer has been applied, and the board the operator reads goes on being 28 commits old until they act. The line names the drift and the command, which is the whole remedy available to a factory that may not touch that tree. |
| C3 | **A `groom/<date>.md` the operator edited for any other reason is read by the carry too.** Any filled answer slot `HEAD` does not carry is carried, whatever the operator meant by it — there is no draft state in that file. This is the same contract the file has always had for the adjudicator and for the rule pass: a filled slot is an answer. A half-written answer is applied, or refused by `parse_answer`'s grammar and left changing nothing (`asf/groom/inbox.py:585-600`). |
| C4 | **Every auto-filed card now creates a claim ref on origin.** `file_bugs`, `flaky`, the groom's intake, `plan_tasks` and `replan` all mint, and under D6 each mint is one `fetch` plus one create-only `push` plus one more `fetch` under `refs/asf/ids/*` (`asf/record/idclaim.py:146-176`). That is new network per card filed, in the tick's own clone where it was previously free, and `refs/asf/ids/*` grows by one ref per id ever minted rather than one per job block. Both costs are bounded and visible; neither is measured here, and a product that cannot pay them has `conventions.flags.id_claim: off` (`## Out`). |
| C5 | **A mint now fails where it used to succeed offline.** `claim_one` raises `ClaimError` when origin is unreachable, and `mint_id` turns that into `SystemExit` (`asf/record/ids.py:97-99`). Under D6 that reaches callers that never had it: an offline tick's `file_bugs` can no longer file. The tick already treats an offline step as its own named case (`asf/tick/network.py`, `_reason`'s `offline` marker at `asf/tick/tick.py:869-876`), so the failure is legible, but it is a new way for a card not to be filed. The plan should decide whether an unreachable origin falls back to the local path or refuses; this spec names it rather than choosing for a seam it cannot measure here. |
| C6 | **The three Bugs already lost stay lost** (`## Out`). Nothing in the record says they existed: the push that dropped them reported success (P12), so there is no event, no refused-write finding and no commit carrying their text. |
| C7 | **A card discarded add/add is named by id, not recovered.** The `NEEDS OPERATOR` line says which ids the push dropped and that they must be re-filed; the content is in the operator's reflog and nowhere the factory can read. Recovering it automatically would mean re-minting under a fresh id and rewriting the card's own `id:` field inside a rebase — a writer this card does not build. |

## The design

### 1. `asf/groom/answers.py` — the operator's answer, carried

Two existing functions widen and one is new.

`_ANSWERS_FILE_RE` becomes the shape `asf/groom/groom.py:1141` already accepts, and the date is
read from its group everywhere (D9, P16, P17):

```python
#: The applier's own shape (``asf.groom.groom.ANSWERS_FILE_RE``): ``<date>.answers`` and
#: ``<date>.<who>.answers``. One regex for the scanner and the applier, or a file is appliable
#: and invisible (F-0260 P16).
_ANSWERS_FILE_RE = re.compile(r'^(?P<date>\d{4}-\d{2}-\d{2})(?:\.(?P<half>[a-z]+))?\.answers$')
```

`pending_answers_files` returns `(path, date)` pairs, and `apply_pending_answers` uses the
`date` it is given instead of slicing `'.answers'` off the basename — which for
`2026-10-06.operator.answers` gave `2026-10-06.operator` and made the `_newest_applied`
supersede comparison nonsense.

`carry_checkout_answers(product, out=print)` is new, and sits beside `carry_staged_answers` at
`asf/groom/answers.py:103`:

```python
def carry_checkout_answers(product, out=print):
    """The operator's own answer, written by hand into ``groom/<date>.md`` in the record
    checkout, copied into the state dir as ``<date>.operator.answers`` — where the tick's
    applier reads it (:func:`apply_pending_answers`), in the clone, and publishes the card from
    there.

    The `NEEDS OPERATOR` row tells the operator to answer in that file and says the next tick
    applies it (``asf.groom.inbox.stuck_s1_lines``). The tick's clone is reset to origin every
    run and reads this checkout for nothing but its ``origin`` url, so an uncommitted line in it
    reached no tick at all (F-0260). This is the one thing the tick reads out of that tree, and
    it reads it: nothing here writes, commits or pushes in the operator's checkout.

    A line is carried when its answer slot is filled and the checkout's own ``HEAD`` copy of the
    same file does not carry it verbatim (D2) — exactly the operator's uncommitted edit, with no
    fetch. Nothing is written when every such line is already in a file beside it, applied or
    not (D3). Returns the paths written."""
```

Its body is four reads and one write:

* `product.backlog_dir`, skipped when it is unset, is not a checkout, or resolves to the record
  clone itself (the same three guards `sync_operator_checkout` opens with).
* for each `groom/<date>.md` in the checkout, `git show HEAD:groom/<date>.md` (missing → the
  empty string: a groom file the operator has not committed at all is all new).
* the lines of the working-tree file that `_LINE_TOKEN_RE`/`_CONFLICT_TOKEN_RE` recognise, whose
  answer is `not unanswered(answer)`, and which the `HEAD` text does not contain verbatim.
* the lines already carried, read off every `<date>.operator.answers*` in the state dir's `groom`
  directory (D3); when the remainder is empty, nothing is written.
* `<state dir>/<product>/groom/<date>.operator.answers`, those lines, one per line.

`apply_pending_answers` gains one call, immediately after `carry_staged_answers(product, out=out)`:

```python
    carry_staged_answers(product, out=out)
    carry_checkout_answers(product, out=out)   # the operator's own, from the record checkout
```

so the file is in the state dir before the loop that applies pending files reads it, on the same
tick. `cmd_groom(answers_file=…)` then applies it against the clone's `groom/<date>.md` for its
section context (`asf/groom/groom.py:1282-1286`), attributes it to `groom-operator-<date>`, and
`publish_changes` pushes the card from the clone. One line out, the shape the others use:

```
groom: carried 1 answered line from the record checkout — groom/2026-10-06.md
groom: answers 2026-10-06 applied — groom 2026-10-06: applied 1, inbox 0 card(s), …
```

### 2. `asf/tick/shadow.py` — a sync that says why, in words with no machine path

`sync_operator_checkout` returns a record instead of a bool:

```python
#: What one attempt at the operator's checkout came to. ``moved``: it was fast-forwarded.
#: ``why``: ``None``, or one of ``'off-trunk'``, ``'local-changes'``, ``'merge-refused'``.
#: ``behind``: how many commits of ``origin/<trunk>`` it lacks. ``paths``: the record-relative
#: paths that block it, sorted, capped at :data:`SYNC_PATHS_MAX` — never the checkout's own
#: filesystem path (F-0260 D10).
Sync = namedtuple('Sync', 'moved why behind paths detail')
```

The three refusal lines lose `{repo}` and gain the drift (D10):

```
record: the record checkout is not fast-forwarded — 28 behind, on a detached HEAD, not main
record: the record checkout is not fast-forwarded — 28 behind, local changes: groom/2026-10-06.md
record: the record checkout is not fast-forwarded — 28 behind, merge refused: <git's last line>
```

Each keeps the literal `not fast-forwarded`, which `tests/test_operator_checkout_sync.py:81`
asserts (P18). `paths` comes from the `git status --porcelain --untracked-files=no` the function
already runs — its own output, parsed for the path column, which is already record-relative.

`_resolve_by_ownership` returns the paths it discarded rather than `True` (D8):

```python
    added_both = []      # add/add: origin's card wins and the local one is gone (F-0260 D8)
    for rel in conflicted:
        if rel != 'index.json':
            ...
            if base is None and ours is not None and theirs is not None:
                added_both.append(rel)
```

and `push` prints one more line, only when that list is non-empty, so the four exact-output tests
at `tests/test_tick.py:209-362` stay green (P19):

```
tick: 3 card(s) discarded by the rebase — origin already holds these ids: B-0268, B-0269, B-0270
```

Its signature changes from `-> bool` to `-> list | None` (`None` for the conflicts it still
refuses), and `push` gains one `discarded` list it returns alongside its bool — or carries on
`out`, which is what the tick reads. The plan picks one; the acceptance test asserts the line and
the ids, not the return shape.

### 3. `asf/tick/tick.py`, `asf/tick/record_health.py`, `asf/views/status.py` — the four reports

`commit_and_push` keeps the sync's answer:

```python
    ctx.checkout_sync = shadow.sync_operator_checkout(ctx.product, out=print)
```

and, when it refused, the tick says so once, as a `NEEDS OPERATOR` with the exact command (D5):

```
NEEDS OPERATOR: the record checkout is 28 commits behind origin and the tick cannot fast-forward
it — local changes in groom/2026-10-06.md; the board every read view shows is that old —
`git -C "$(asf prod --record-dir)" status --porcelain && git -C "$(asf prod --record-dir)" log --oneline HEAD..origin/main`
```

read-only, so harvest runs it itself and the park already carries the answer (B-0042). The event
carries the same fields and no path outside the record (D10):

```python
    ctx.event('record_checkout_stale', why=sync.why, behind=sync.behind, paths=sync.paths)
```

`record_health.record` takes one more argument and stores one more field:

```python
def record(product, ok, reason=None, checkout=None, now=None):
    """... ``checkout`` is the operator checkout's sync refusal (``asf.tick.shadow.Sync``) or
    ``None``: a record step that landed but could not carry its push into the checkout the read
    views read (F-0260). It is kept whatever ``ok`` says, because the two are independent."""
```

and `line` says it when the record step itself is fine:

```
CHECKOUT 28 BEHIND since 10:41 — local changes: groom/2026-10-06.md (12 ticks)
```

`stale_cell` needs one branch: `record_health.line` is already the first thing it reads and
already returns the sentence the row prints (P8), so the row stops saying `no fresh record in 1h`
about a factory that ticked twelve times and starts saying which tree is behind (D11).

Because `record` is called from `asf/tick/tick.py:645-647` — inside the step loop, before the
sync runs — the checkout field is written by a second call from `finish`, after
`commit_and_push`, with the `ok` the step row already carried. The plan decides whether that is a
second `record(...)` call or an `update(product, checkout=…)`; the acceptance test asserts the
file's contents and the row, not the call count.

### 4. `asf/record/ids.py` — one allocator, and a floor origin agrees with

Two changes, both in `mint_id`.

The gate goes (D6):

```python
    if idclaim.has_origin(root) and _claims_enabled(root):
        who = claimant or os.environ.get('ASF_SESSION') or os.environ.get('ASF_JOB') or 'asf new'
        try:
            return idclaim.claim_one(root, prefix, who, floor=max(max_n, origin_top(root, prefix)))
        except idclaim.ClaimError as e:
            raise SystemExit(f"new: {prefix}-id claim on origin failed: {e}") from None
```

`claim` and `worktree` stay parameters — `claim` because `asf new` still passes it and the
worktree refusal below still reads it, `worktree` because the `BACKLOG_ALLOW_MINT` refusal at
`asf/record/ids.py:100-102` is unchanged for a record with no origin.

`origin_top` is new, and is also the floor the local fallback uses:

```python
def origin_top(root, prefix, remote='origin'):
    """The highest number ``origin/<trunk>``'s tree holds for ``prefix`` — the floor a mint must
    clear whatever the working tree says.

    ``record_top`` reads the checkout, and a checkout behind origin reads a lower top: on
    2026-10-06 a record 28 commits behind minted B-0268, B-0269 and B-0270, each already a card
    on origin (F-0260 P9). One ``fetch`` and one ``ls-tree``; 0 when there is no origin, no
    trunk, or the fetch fails — a floor that cannot be read is no floor, never a refusal."""
```

and the fallback's claim mirror is read after that same fetch, so the "step over a claimed block"
guard stops being as stale as the checkout (P11):

```python
    n = max(max_n, origin_top(root, prefix)) + 1
```

`BACKLOG_ID_RANGE` is untouched and still returns before any of this
(`asf/record/ids.py:88-92`): a job's claimed block is the one thing that already cannot collide.
