# F-0193 — every check was green and the pages were still not fit to read

On 2026-09-25 one product's legal pages — contact/DSA, cookies, DPA, privacy, terms — went
through code review, went through CI, and went live. Every gate the factory has was green. The
operator then read them:

> those legal documents has not been proff read with the eyes of an enduser

Nothing was broken. That is the whole finding. A code reviewer reads a **diff**, against a
**plan**, for the checks in `reviews.CHECKLIST['code']` — writes-footprint, steps implemented,
tests byte-identical, tests green, gate green, no secret printed. Not one of those six questions
is *"would the person this page is for understand it, believe it, and find it complete?"* The
diff was correct. The page was not finished.

This factory has already reached for this once, and the reach fell short in a way worth naming
precisely, because it is the reason this card is not a one-line change.
`asf.customer_content` (P1) makes the **code** reviewer carry one extra table row, `read as the
customer` (P2, P3). That row is real and it works for what it catches — a bracketed `[legal: …]`
note, a TODO, a placeholder. But it asks the wrong reviewer at the wrong moment:

* the reviewer is a **code** reviewer, mid-diff, with five other rows to answer and a `writes:`
  footprint to police. The row is the eighth item on their list, not their job;
* the artefact is a **diff**. The row's own text asks for the rendered page (P3) but the session
  it asks is the one whose entire brief is the diff, and the review it writes is filed against
  the diff's own head;
* the verdict is **binary and buried**: one `pass`/`fail` cell among seven. There is no place in
  it for *"this is shippable but the cookie table reads like a spec"*, so everything either
  blocks or vanishes.

So F-0193 does not strengthen the row. It **moves the question to its own reviewer**: a second
review of the same head, by a session whose only brief is to be the product's target user reading
the finished pages, and whose findings come back in the two shapes a content reader actually
produces — **MUST FIX** (this cannot ship) and **SHOULD FIX** (this should be better).

Three properties hold the cost down, and each is a design constraint, not an aspiration:

1. **The routing is deterministic; only the reading is an LLM's.** Whether a branch needs an
   enduser review is a glob match over its changed files. Whether the gate opens is a verdict
   already on disk. No model decides whether the gate applies.
2. **Nothing new parses a verdict.** The enduser review writes the same check table every other
   review writes, and its MUST FIX list *is* the C list the existing grammar already reads (P8,
   D4) — verified in this checkout, both ways, including the case where the reviewer contradicts
   their own table.
3. **One question, one owner.** Where the enduser gate is on, the code reviewer stops owing the
   `read as the customer` row (D3). The factory does not pay two reviewers for one question, and
   a product that has not turned this on keeps today's behaviour byte for byte (P14).

And because the incident was a **deploy** — the pages were live before anybody read them — the
gate is in both places the card names: the landing, and the dispatch of every deploy target.

### In

- **`asf/enduser.py`** — one new module, the single owner of this card's vocabulary: the
  classification (`applies`, `legal`), the config readers (`audience`, `legal_paths`, `policy`),
  the persona render (`brief_section`), the review's identity in the store (`slug`), the state
  reader (`state`), the ledger (`record`, `rows`, `covered`), the two refusal texts
  (`deploy_refusal`, `legal_line`) and the doctor rows (`findings`). It sits beside
  `asf.customer_content` and borrows its `matches`/`paths`/`touched` rather than reimplementing
  glob matching (P1).
- **`audience:`** — a new product-config field, a scalar (`PRODUCT_FIELDS['audience'] = _STR`),
  documented in `products.example.yaml`: one or two sentences naming who the product's pages are
  for. It is the persona the enduser brief takes, and its presence is what turns the gate on
  (D2).
- **`conventions.customer_content.legal_paths`** — globs, beside `paths`. Implicitly customer
  content whether or not `paths` also covers them (D6), and the trigger for the operator's
  signature (D8).
- **`conventions.customer_content.enduser`** — `none` | `required`, the same two words
  `REVIEW_POLICIES` already uses (P6 neighbour: `conventions.py:202`). Unset, it is derived
  (D2); set, it wins, so a product can name either state explicitly.
- **`reviews.KINDS` gains `'enduser'`, and `CHECKLIST['enduser']`** — five mechanical rows, one
  per thing the card names the reviewer must check, plus two standard rows. The card's MUST FIX
  / SHOULD FIX arrive as the C and I lists the grammar already reads (D4, P9).
- **`asf/briefs/templates/enduser.md`, and `'enduser'` in `build.KINDS`** — the review brief
  whose reviewer is the audience, not the diff: it names the rendered pages, the persona, the
  check table, and the two lists.
- **A second review of the same head, sequenced after the first.** `lane.facts` gains
  `f['enduser_required']` and `f['enduser']`; `next_state`'s T3/T4 block gains **T4e** (the code
  review approved but the enduser review has not: stay in REVIEW, asking for the enduser round)
  and **T5e** (the enduser review reads changes: BACK, `kind=enduser`). The lane record's REVIEW
  entry gains `kind`, which `occupancy['review']` passes through and `lane_rows` turns into
  `brief_kind='enduser'` (P11).
- **The ledger `state/<product>/enduser.jsonl`** — one append-only row per enduser verdict the
  lane acts on, carrying the PR number and the trunk sha it landed as. It is what makes the
  deploy gate and the `asf prod` column possible at all, since neither has a branch to read
  (D7, P14).
- **`deploy.enduser_refusal(product, f, env)`** — one loud line, at the two call sites
  `marker_refusal` already occupies (P13): a candidate carrying a customer-content landing the
  ledger does not cover does not dispatch, to any target.
- **`approvals` gains `merge_legal_content` and `deploy_legal_content`** — the first read by
  `precheck` through `merge_class` (P12), the second by the deploy pass; both default
  `human-now`, both `operator=True`, both released by `asf approvals resolve`.
- **`asf prod`'s State column names the enduser state** of every NOT LIVE and ON PROD row whose
  landing touched customer content, and `—` for one that did not.
- **`asf doctor`'s `customer content` section** gains this card's advisory rows: the gate's
  derived state, `legal_paths` with no approvals class reachable, an `audience` that is missing
  while `enduser: required` is set explicitly.

### Out

- **No third landing class.** `landing_class` keeps its two values. P5 is the reason: eight call
  sites branch on `== DOCS` for the CI start class, re-gating, conflicts, batching and the
  spec/static check, and none of them is about review. The classification is orthogonal and
  lives beside the landing class, exactly as `f['customer']` already does (P4, D1).
- **No new verdict grammar, no MUST FIX parser, no second verdict word.** P9 was measured, not
  assumed: the C heading carries it. `asf.reviews` and `asf.evidence.review` gain no regex.
- **No kind dimension in the review store.** P7's key is untouched; P8's composed slug is what
  separates the two reviews, and it was verified isolating in both directions.
- **The `read as the customer` row is not deleted, not reworded, and not weakened.** It yields
  only where the enduser gate is actually on and actually covers the branch (D3). A product with
  no `audience:` keeps every assertion in `tests/test_customer_content.py` (P20) — that file is
  not edited by this card.
- **The marker gate is not touched.** `refusal`, `tree_hits` and `marker_refusal` keep first
  claim: a branch that adds a `[legal: …]` note still goes BACK before any reviewer is launched,
  and no enduser session is spent on a page with a placeholder still in it. The two gates
  compose; the cheap one runs first.
- **No retro-block of history.** A product turning this on does not have its deploy frozen by
  trunk commits that predate the ledger (D7). The floor is mechanical and needs no operator sha.
- **No enduser review of a diff that touches no customer content**, and no enduser review as a
  replacement for the code review. It is strictly additional, strictly second, and strictly
  scoped to the pages.
- **Nothing about rendering.** The brief *asks* the reviewer to read the page as published and
  names the product's `app_host` when it has one; the factory does not build, serve, screenshot
  or crawl the site, and no acceptance test here runs a browser.
- **No new session kind in `metrics`/`tokens`.** The enduser reviewer's job name keeps the
  `review` prefix, so `KIND_PREFIXES` classes it as `review` and no stream schema moves (P18,
  D9).
- **No `asf enduser` subcommand.** The only operator surfaces are the ones the card names:
  `asf prod`, `asf doctor`, and `asf approvals` for the signature.
- **`STORY_ID_RE`'s four-digit shape is not fixed here** (P21).

| D9 | `merge_class` returns `merge_legal_content` **before** `merge_amendable_set`. | Leaving the existing order and appending. | `merge_class` returns the first match (P12). The two sets are disjoint in practice — the factory's own rules are not customer legal text — but where they did overlap, the operator's signature on legal text is the stricter and the more specific claim, and it is the one whose absence is a published legal document nobody agreed to. |
| D10 | The prod view's enduser cell is driven by `conventions.customer_content.paths ∪ legal_paths`, not by `product.customer_paths`, and reads `—` for a row that is customer-*visible* but not customer-*content*. | Using `product.customer_paths` — which is literally what the card's description names, and what the view's own rows are already filtered by. | P15: they are two different lists and both are right about different things. `customer_paths` includes an API (`apps/api/**` in the shipped example) — code a customer's requests reach, not a page a customer reads. An enduser reviewer cannot proofread an API route, and a gate that demanded it would be asking for a reading nobody can perform. The view keeps its existing row filter unchanged (P14) and the new cell is honest about the narrower question it answers. |
| D11 | The enduser review runs **after** the code review approves the same head, never in parallel. | Launching both reviewers at once on the same head. | A head the code review sends BACK is about to be rewritten, and every page the enduser reviewer read is then history — the whole cost, thrown away, and the ledger row bound to a head that no longer exists. Sequencing costs latency on a branch that was going to land anyway and saves the entire second session on every branch that was not. It is the same trade the factory made last week for heavy CI (`ci.heavy_after_review`, `7fbbfdba9`), and it keeps `occupancy['review']` to one launch row per item, which is what `lane_rows` is built for (P11). |
| D12 | The ledger row is written by the **lane, at the transition it acts on the verdict** (the enduser review approved this head), carrying the PR number and, once merged, the trunk sha. | Deriving coverage at deploy time by re-reading the review store. | The store is keyed by branch, and a branch is deleted after it lands; the deploy pass has a trunk sha and nothing else (P13). The PR number is the key `asf prod` already uses to identify a customer-visible landing (P14), so one row serves the deploy gate, the view and the audit, and the fact is written once, by the code that knew it. |

## The design

### §1 The classification — `asf/enduser.py`, the pure half

`enduser.py` is pure functions over plain lists for everything but the ledger, in the shape of
`asf.customer_content` and `asf.size`: no `Product` construction of its own, and glob matching
borrowed, never reimplemented (P1).

```
paths(conv)          -> customer_content.paths(conv) + legal_paths(conv), de-duplicated
legal_paths(conv)    -> the customer_content.legal_paths globs ([] unset)
audience(product)    -> product.audience, stripped ('' unset)
policy(product)      -> 'required' | 'none'
applies(product, files) -> [f for f in files if matches(paths(conv), f)]   # the label
legal(product, files)   -> [f for f in files if matches(legal_paths(conv), f)]
enabled(product)     -> policy(product) == 'required'
```

`policy` resolves in one documented order, and `asf doctor` prints which arm fired:

1. `conventions.customer_content.enduser` when it is `none` or `required` — the operator said so;
2. else `required` when `audience(product)` is non-empty **and** `paths(conv)` is non-empty;
3. else `none`.

The classification a caller acts on is `enabled(product) and applies(product, files)`. The
name the factory already uses for it is `customer_content.KIND`, `'customer-content'` (P2) — no
second string is minted for the same class.

`legal_paths` is inside `paths` by construction (D6), so `legal(...)` is a subset of
`applies(...)` and a page cannot take a signature without being read.

### §2 The review kind — the checklist, the slug, the brief

**`reviews.KINDS`** becomes `('spec', 'plan', 'code', 'enduser')`, and `CHECKLIST['enduser']` is
five mechanical rows — one per thing the card names — and two standard ones:

```
mechanical:
  'every touched page was read in full, as published, not as a diff'
  'no leaked internals: no id, TODO, placeholder, spec wording or internal note on any page'
  'no missing fact the audience needs to act on this page'
  'every link resolves, and every cross-page fact agrees'
  'plain language: no unexplained jargon, no sentence the audience cannot follow'
standard:
  'a reader of the stated audience would find this page complete and believable'
  'the page says what the product actually does'
```

These are what `reviews.required('enduser')` returns, and `covers` (P6) lets the brief's own
shorter wording of each count as the row, so a reviewer who writes `leaked internals: none` has
answered row two.

**The identity.** `enduser.slug(item)` is `f'{str(item).lower()}-enduser'`. Everything else
follows from P8 with no new code: the brief names
`conventions.review_path(enduser.slug(item), n)`; the health pass files it with
`review_store.take(store, conv, wt, branch, enduser.slug(item), remote_sha)`; the lane reads it
with `review_mod.review_at(repo, conv, f'origin/{b}', enduser.slug(item),
reviews.required('enduser'), store=…)`. Rounds, head-binding and `is_current` all work as they
already do, for the same reason they work for the code review.

**The brief** is `asf/briefs/templates/enduser.md`, and `'enduser'` joins `build.KINDS`. Its
context adds `audience`, `pages` (the touched customer-content files, `SHOW_HITS`-capped in
`customer_content.describe`'s style) and `app_host` (the product's own live URL, or the empty
string). Every one of those is a context key, so a typo is a test failure (P18). The brief says,
in the house voice:

* **who you are** — the `audience` sentence, verbatim from the product config, and the
  instruction that this is the only perspective in the brief: you are not reviewing a diff, a
  plan or a footprint, and the code review has already passed;
* **what to read** — each page in `pages`, whole, as published; the rendered page where
  `app_host` gives one, the rendered source top to bottom otherwise; never only the changed
  lines;
* **what to look for** — the five mechanical rows, each as a question a reader asks: internals
  that leaked, a fact you would need and cannot find, a link that goes nowhere, a claim that
  contradicts another page, a sentence you cannot follow;
* **the two lists** — `### C — MUST FIX`, numbered, each with `file:line` (or the page and the
  sentence) and the exact change; `### I — SHOULD FIX` for everything that should be better and
  will not block. `none` under MUST FIX is the shape that approves (D4, P9);
* **the standing review rule, unchanged** — the review never touches the branch: write the file
  in the worktree, commit nothing, push nothing; the factory files it (`review.md`'s own rule,
  and the reason it exists).

The enduser reviewer's job name keeps the `review` prefix (P18, D9): `metrics` and `tokens` gain
nothing, and the session shows up as a review in every stream that already counts reviews.

### §3 The landing gate — two transitions in the one place the lane decides

`lane.facts` gains two fields, next to the `f['customer']` it already computes (P4):

```
f['enduser_required'] = bool(enduser.enabled(product) and enduser.applies(product, f['files']))
f['enduser_legal']    = enduser.legal(product, f['files'])
f['enduser']          = review_at(..., enduser.slug(item), reviews.required('enduser'), store=…)
                        with 'current' set exactly as f['review']['current'] is
```

`f['enduser']` is read only when `f['enduser_required']` and the code review already reads
approved for the current head — D11's sequencing, expressed as not paying for the read until it
can matter.

The T3/T4/T5 block (P10) gains two arms, both inside the existing `s in (PR_OPEN, REVIEW)` branch
and both pure:

* **T4e** — the code review is current and APPROVED, and `f['enduser_required']`, and
  `f['enduser']` is not a current APPROVED review: the branch stays in (or enters) REVIEW with
  `round <n> wanted (enduser): <why>`, where `<why>` is `no enduser review yet`, `<path> predates
  the head`, or `<path> reads <verdict>`. This arm sits **after** `incomplete(f)` and **before**
  the fall-through to `review_reason`, so a branch still owing a code round is never diverted.
* **T5e** — `f['enduser']` is current and reads CHANGES: `BACK`, `kind=enduser`. The correcting
  session's brief is the correction brief it already is, answering a C list that happens to be
  written MUST FIX. `overruled` and `review_answered` (T5a/T5b) apply unchanged — an adjudicated
  ruling on this head answers the enduser review exactly as it answers the code review.
* **T4** proper — GATE — now requires both: the code review approved (and `not incomplete(f)`)
  **and** (`not f['enduser_required']` or the enduser review approved the same head).

`Lane.set(f, REVIEW, reason, result='waiting', round=rnd, review_kind='enduser')` writes the kind
on the lane record. `occupancy['review'][item]` carries it through as `kind` (defaulting to
`'review'`, so every existing reader is unaffected), and `lane_rows` emits
`brief_kind=h.get('kind') or 'review'` — one launch row, the right template, no new row kind
(P11).

**D3's yield**, in one place: `customer_content.review_section(conv, files)` returns `''` when
`enduser.enabled(product) and enduser.applies(product, files)`, and `lane.incomplete(facts)`
returns False under the same condition. `review_section`'s signature takes the product (or the
resolved flag) to answer this; `has_customer_row` and `CHECK_ROW` are untouched, and a product
with no `audience:` reaches neither new branch (P20).

**The ledger row** is written at the transition that acts on the verdict: when T4e is satisfied —
the enduser review of this head reads APPROVED and the branch goes to GATE — the lane appends one
row to `state/<product>/enduser.jsonl` (§4, Records). It is written once per (item, branch, head);
a re-entry after a head move writes a new row for the new head. When the lane reaches MERGED it
stamps that row with the trunk sha it landed as (`method=` already tells it which sha that is:
the pushed sha for a fast-forward, the merge commit for a PR).

### §4 The deploy gate — one loud line, at the two places that must agree

`enduser.covered(product, repo, deployed, candidate)` answers the deploy pass's only question:
*which customer-content landings in `deployed..candidate` does the ledger not cover?*

```
1. landings = deploy's own first-parent walk of `deployed..candidate`, as prod.py's
   `_landings` does it — (sha, parents, subject, pr) — and, for each, its changed files
   against the first parent (`_changed`).                                          [P14]
2. keep the landings whose changed files match enduser.paths(conv).
3. drop every landing older than the floor: the earliest ledger row's own landing, or
   `customer_content.enduser_from` when the operator set one.                       [D7]
4. a landing is covered when a ledger row approves it by trunk sha or by PR number.
5. return the uncovered ones, newest first.
```

Steps 1 and 2 are the read `prod.py` already performs; the walk lives in one place and both
callers use it, since the alternative is two first-parent walks that can disagree about what a
landing is.

`deploy.enduser_refusal(product, f, env)` returns one line or None, and is called at exactly the
two sites `marker_refusal` occupies (P13), immediately after it — the marker gate keeps first
claim (Out):

```
DEPLOY prod DISPATCH REFUSED — `a1b2c3d4e` would ship 2 customer-content landing(s) no
enduser review approved: #487 the cookie page, #491 terms and DPA; nothing deploys to prod
until each is reviewed (asf prod names them)
```

and, when the walk cannot be read at all, the same refusal `marker_refusal` already makes for an
unreadable tree — *not deployed to `<env>` unchecked*. `view_line` returns it in place of
*"the next tick dispatches"*, so the view and the tick never disagree (P13's own reason).

The gate applies to **every** environment and named target the card names — prod, dev and each
target — because the incident was a site target, not the app.

### §5 Legal content and the operator's signature

Two new `ActionClass` entries, both `default='human-now'`, both `operator=True`, both
`grantable=True`:

| class | covers | read_by | parks |
| --- | --- | --- | --- |
| `merge_legal_content` | landing a branch that changes the product's legal pages | `('harvest',)` | True |
| `deploy_legal_content` | deploying a sha that ships a legal-page change | `('harvest',)` | True |

`merge_class(product, files)` gains one arm, **before** the amendable-set arm (D9): when
`enduser.legal(product, files)` is non-empty, return `('merge_legal_content', <first matched
file>)`. Everything else in `precheck` is already written (P12) — the level lookup, the
`is_granted` check, the `dropped` path, the `ask`, the `wait(..., 'held')` line, and the release
under `merge: auto`. The lane prints `held <branch>: merge_legal_content (human-now) —
site/legal/terms.md`, and `asf approvals resolve <item>/merge_legal_content granted` releases it.

The deploy side asks the same way, from the deploy pass: when the uncovered-landing check passes
but the candidate's `deployed..candidate` window carries a legal-path landing, the pass asks
`deploy_legal_content` for that sha and prints one held line instead of dispatching. The hold key
is the sha, not the item — a signature on legal text is about the text, and the thing being
shipped here is a sha.

Both classes appear in `asf approvals`' printed matrix with their recognisers, as
`merge_amendable_set` and `merge_routine_pr` already do (`approvals.py:1302-1303`).

### §6 The views and the doctor

**`asf prod`.** `_check_rows` already has, per row, the landing's sha and PR number (P14). Each
row whose landing touches `enduser.paths(conv)` gains its state as a clause on the existing State
cell — the column count does not change:

```
| Target | What | State | PR |
| prod | the cookie page | NOT LIVE — merged, prod `a1b2c3d4e` lacks it · enduser ✗ | #487 |
| prod | terms and DPA | NOT LIVE — merged, prod `a1b2c3d4e` lacks it · enduser ✓ r2 | #491 |
| site | the pricing copy | live since 14:02 · enduser ✓ r1 · legal: signed | #486 |
| prod | the retry backoff | NOT LIVE — merged, prod `a1b2c3d4e` lacks it | #492 |
```

`enduser ✓ r<n>` for an approving ledger row, `enduser ✗` for a customer-content landing with
none, `legal: signed` / `legal: waits` where a legal path is in it, and **no clause at all** for
a row that is customer-visible but not customer-content (D10 — the last row above is an API
change, in the view's rows as it is today and silent on a question it cannot be asked). A product
with the gate off gets no clause anywhere, so `asf prod`'s output is byte-identical for it.

**`asf doctor`.** `enduser.findings(product)` appends to the existing advisory `customer content`
section (P17), never a new one:

* green — `enduser: required (audience set, 2 path glob(s), 1 legal glob) · 14 approvals on the
  ledger`, and which arm of `policy` decided;
* red — `enduser: required` is set explicitly but `audience:` is empty: the brief has no persona
  to take, so the gate holds every customer-content landing with no reviewer who can clear it;
* red — `legal_paths` is set but both legal approval classes resolve to `auto`: the operator
  asked for a signature and configured it away;
* amber — the product deploys, `audience:` is set, and `customer_content.paths` is empty: nothing
  is classified, so the gate never fires.

## Records

**The ledger — `<state dir>/<product>/enduser.jsonl`**, append-only, one JSON object per line,
read by the deploy gate, `asf prod` and `asf doctor`:

| field | what |
| --- | --- |
| `at` | ISO stamp, `now_iso()` |
| `item` | the card id the branch answers for |
| `branch` | the lane branch |
| `head` | the head sha the enduser review approved (the binding `is_current` already checks) |
| `round` | the enduser round that approved it |
| `path` | `conventions.review_path(enduser.slug(item), round)` — where the review reads from |
| `pages` | the customer-content files the branch touched |
| `legal` | the `legal_paths` files among them (`[]` when none) |
| `verdict` | `approved` — only an approval is recorded; a CHANGES verdict is the lane's BACK row |
| `pr` | the PR number, or `null` in fast-forward mode |
| `trunk_sha` | stamped at MERGED: the sha the branch landed as (`null` until then) |

A row is written once per (item, branch, head); a head move writes a new row rather than editing
one. Nothing ever rewrites or deletes a row, so the file is the audit trail for *"who signed off
that this page was fit to read, and against what text"*.

**The review file** — `docs/reviews/<n>-<item>-enduser.md` in the worktree, filed by the health
pass into `<state dir>/reviews/<item>-enduser/<branch key>/<stamp>-r<n>-<head>.md`. Never
committed to the branch (P8, and `review.md`'s standing rule).

**The lane record** — the REVIEW entry on the run line in `state/<product>/sessions.jsonl` gains
`kind: 'enduser'` while the enduser round is the one being asked for. No new ledger, as the lane's
own rule requires; a reader that does not know the field sees the REVIEW state it already knew.

**The approvals ledger** — `state/<product>/approvals.jsonl` gains rows for
`merge_legal_content` (keyed `<item>/merge_legal_content`) and `deploy_legal_content` (keyed
`<sha>/deploy_legal_content`), through the existing `ask`/`resolve` path. No new file.

**The events already emitted stay as they are.** The enduser session is a `review` in the
`sessions` stream (P18, D9); its BACK is a correction of kind `enduser`, counted where every
other correction kind is counted. No stream schema moves.

**The config the operator writes** — documented in `docs/products.example.yaml`:

```yaml
# who the product's customer-facing pages are written for. The `enduser` review takes this
# persona; setting it is what turns the end-user review gate on.
audience: >
  A small-business owner with no legal or technical training, reading in their second
  language, deciding whether to trust this service with their customers' data.

conventions:
  customer_content:
    paths: [site/content/**, site/app/legal/**]
    legal_paths: [site/app/legal/**]     # implicitly customer content; takes the operator's signature
    enduser: required                    # none | required; unset, derived from audience + paths
```
