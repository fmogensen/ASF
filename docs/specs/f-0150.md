# F-0150 — the third verdict, and the record of what the factory learned from it

The scorecard loop already closes most of its circle. It measures, it files one card per cause over
threshold, and `verify_weeks` after that card lands it reads the same number again and writes
`moved` or `didn't move` onto the card — a card that did not move is reopened with both numbers.

Two things are missing, and they are the two halves of the same gap.

The first is that the loop has no way to say a change made things **worse**. `loop.moved` is a
boolean: a number that fell by a fifth is `moved`, and *everything else* — a number that sat still,
and a number that doubled — is `didn't move`. Both get the same treatment: a reopened card saying
"find the cause it missed". But a cause whose number rose after the card landed is not a miss; it is
a regression, and the honest response is to take the change back out, not to try again on top of it.

The second is that none of this is written down where a human can read it. The verdict is a History
line on one card in one product's record. The factory learns "filing a card against `lead-time` made
lead time worse" and keeps that lesson nowhere — the next cause over threshold is filed as if the
first had never happened.

This card is both: a third verdict `got worse`, which opens a **revert card naming the commits that
landed the change** and both readings; and an **adoption or reversion Decision** — a real `D-nnnn`
card in the target's record — carrying the two readings that justify it. `didn't move` is untouched.

### In

- **A `reverts=` shape on `loop.card_text`** — the revert card: it names the landing commits, both
  readings, and asks for the change to be taken back out.
- **`facts.children(items)`** — `facts._children` made public, so the revert card can resolve a
  Feature's landing commits through `facts.landing_commits` without a git call.
- **A third queue kind, `'decision'`, drained by `loop.drain`** — minted as a real `D-nnnn` in the

- **A `state=` keyword on `ids.write_new_item`** — one defaulted parameter, no caller changed.

### Out

- **The loop does not perform the revert.** It opens the card that asks for one. The loop touches no
  git repository, and nothing here reverts a commit (D9).
- **`didn't move` is unchanged** — same History line, same reopen card, and **no Decision** (D8).
- **No new setting.** `got worse` is measured with the same `min_move` the card is verified against
  (D2).
- **No change to `diagnose`** — no new cause, no new threshold, no change to `metric`.
- **No new CLI command or flag**, no new approval class (P15), no new module (P18).
- **No cross-product write.** A Decision for another target is queued and minted by *that* product's
  own drain, exactly as an inbox card is (P10).

## The design

### 1. The third verdict — `asf/scorecard/loop.py`

`moved` is left alone. Beside it:

```python
def direction(before, after, min_move):
    """The verdict on one cause: ``'moved'`` (the number fell by ``min_move``), ``'got worse'``
    (it rose by the same), ``"didn't move"`` (neither), or ``None`` when a reading is missing.
    A zero that stayed zero moved; any rise off zero got worse."""
    if before is None or after is None:
        return None
    if before <= 0:
        return 'moved' if after <= 0 else 'got worse'
    if after <= before * (1 - min_move):
        return 'moved'
    if after >= before * (1 + min_move):
        return 'got worse'
    return "didn't move"
```

`verify` replaces its two lines of verdict logic with one call and branches three ways. The History
line keeps its exact shape — only the word between the key and the dash changes:

```
- 2026-09-23 scorecard: failure:dead pid got worse — 1 before, 2.5 after (2 weeks each side of landing 2026-09-08)
```

and then:

- **`moved`** — enqueue an adoption Decision for `entry['target']`. Nothing else changes: no card is
  filed, and `state[key]` keeps its terminal `verdict` as it does today.
- **`didn't move`** — byte for byte what it does now (D8).
- **`got worse`** — resolve the landing commits (§2), file the revert card with them and both
  readings, replace `state[key]` with the `#n+1` entry exactly as the reopen path does, and enqueue a
  reversion Decision.

The `#n+1` entry the revert path writes carries one extra key beside the reopen path's `reopens`:
`reverts: <card id>`, so the state file says which of the two a re-filed cause came from.

### 2. The revert card — `card_text(..., reverts=…)`

`reverts` is `{'card', 'landed', 'before', 'after', 'weeks', 'commits'}` — `commits` a list of shas,
possibly empty. The title becomes `Revert <card>: <title>`; the inserted paragraph is:

```
F-0009 landed 2026-09-08 and this number got worse, not better: 1 before, 2.5 after, over 2 weeks
each side. Take it back out: the commits that landed it are 74df364ab, 9c1a2b3de. Reverting is the
default here — if it should stand instead, say why on this card and close it.
```

and, when nothing could be traced, the last sentence of the first line is
`the record has it landed without a traceable commit, so the commits must be found by hand.`
(`facts.UNTRACEABLE`, P5 — the wording is not re-invented here).

The Acceptance line the revert card carries is the one that can actually be checked:

```
- [ ] failure:dead pid reads at most 1 runs/week again over 2 weeks after the revert lands
```

The commits are resolved in `verify`, not in `card_text`, so `card_text` stays pure:

```python
shas = list(c.get('landing_shas') or []) or facts.landing_commits(iid, cards, facts.children(cards))
```

`facts._children` is renamed to `facts.children` and its one internal caller (`attribute_prod`,
P5) updated. No alias is kept — one name, two callers.

### 3. The Decision — a third queue kind

`verify` enqueues, for the target that owns the card:

```python
{'kind': 'decision', 'card': iid, 'key': key, 'n': n, 'verdict': word,
 'marker': f'scorecard-decision: {key} #{n}',
 'title': f'Adopted {iid}: {entry["title"]}',      # 'Reverting {iid}: …' for got worse
 'before': _fmt(before), 'after': _fmt(after), 'unit': entry['unit'],
 'weeks': cfg['verify_weeks'], 'landed': c['landed'][:10], 'commits': shas}
```

`drain` gains the branch that writes it. It mints through the shared path (P7), writes the card
`Closed` (D5), and is idempotent on the marker the same way the inbox branch is — a `decisions/`
card already carrying `scorecard-decision: <key> #<n>` is skipped:

```python
elif e.get('kind') == 'decision':
    by_id = by_id if by_id is not None else load_cards(root)
    if _decision_has(root, e['marker']):
        continue
    try:
        canonical = ...                      # load_items + canonicalize, as ids.mint_id expects
        new_id = mint_id(root, canonical, 'decision')
    except SystemExit as why:                # a root that cannot mint today: it waits (D10)
        out(f'scorecard: decision for {e["card"]} not minted — {why}')
        left.append(e)
        continue
    write_new_item(root, canonical, 'decision', new_id, {'title': e['title']},
                   body, date, why='scorecard: ' + e['verdict'],
                   acceptance=[...], state='Closed')
    n_decisions += 1
```

The body is the two readings and what they were read against:

```
The scorecard loop verified F-0009 against the cause it was filed for, failure:dead pid.

Reading: 1 runs/week over the 2 weeks before it landed on 2026-09-08, 2.5 runs/week over the 2
weeks after. The number got worse by more than the 20 % the loop verifies against, so the change
is being taken back out; the revert is asked for on its own card.

Landed by 74df364ab, 9c1a2b3de.

scorecard-decision: failure:dead pid #1
```

The adoption body is the same shape with "The number moved … so the change stands."

Immediately after minting, `drain` appends a History line to the card the Decision decides — this is
the link back, and it is written here rather than queued because only here is the id known:

```
- 2026-09-23 scorecard: adopted as D-0007 — 2 before, 0.5 after
```

Finally, when `n_decisions` is non-zero, `drain` calls `do_index(root)` once before it returns (D6),
and its summary line names the third count:

```
scorecard: wrote 1 card(s), 2 History line(s) and 1 Decision(s) into the record
```

`drain`'s return value becomes `(cards, lines, decisions)`. Its two callers are both inside `daily`
and ignore the value; `RecordTests` asserts on it and is updated.

### 4. `ids.write_new_item(..., state='New')`

One defaulted keyword, used at the one line that sets the state (P8):

```python
meta['state'] = state
```

Every existing caller keeps its behaviour by default.

### What it looks like when it is there

A cause is filed. Its card lands. Two weeks later the loop reads the number again and it has gone
up by more than a fifth. That day's tick prints its usual scorecard line, and the record gains three
things in one commit: a revert card in the inbox naming `F-0009`, both readings and the two commits
that landed it; a History line on `F-0009` saying the number got worse and that `D-0007` records it;
and `decisions/D-0007.md`, `Closed`, holding the two readings and the sentence that the change is
coming back out. `index.json` and `F-0009`'s backlinks are current in that same commit.
