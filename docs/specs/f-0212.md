# F-0212 — a hold on a command that writes nothing

2026-09-25/26, a product's T-0157 was held `touch_security` (human-now) on this:

```
git config core.hooksPath && ls -la $(git config core.hooksPath 2>/dev/null || echo .git/hooks) 2>&1 | head -30
```

It prints a config value and lists a directory. It writes nothing. The hold sent T-0157 round
STALEMATE → ADJUDICATE several times.

**Half of this is already fixed, and the half that is fixed is fixed for the wrong reason.**
Hotfix `06bcc0042` (2026-09-24 07:07:10 +0200, a day before the T-0157 holds) narrowed the
recogniser from `git config core\.hooksPath\b` to a pattern that demands *something after the
key*, on the argument that a value means a set. Run against this checkout the card's exact command
now passes — but only because `_run_text` drops the read-only `ls` that the command substitution
sits inside (`asf/approvals.py:436-468`). The substitution is never read. Change `ls -la` to
`stat -c %a` and the hold comes back.

The demand for "something after the key" is not git's grammar, and measured over this checkout it
is wrong in both directions at once:

| Written | Today | What it is |
| --- | --- | --- |
| `git config core.hooksPath 2>/dev/null` | **HELD** | a read. The `2` of a split `2>` satisfies `[^\s;&\|)]`. |
| `git config core.hooksPath > /tmp/p` | **HELD** | a read whose output is captured. |
| `git config --local core.hooksPath 2>/dev/null` | **HELD** | a scoped read. |
| `git config core.hookspath /tmp/h` | **passes** | a set. Git config keys are case-insensitive. |
| `git -C /repo config core.hooksPath /tmp/h` | **passes** | a set. `\bgit\s+config` wants adjacency. |
| `git config --file .git/config core.hooksPath /tmp/h` | **passes** | a set. `--file` is not in the flag group. |

Three false holds and three real evasions, from one regex trying to be a parser. The card's rule
is the right one and it is a rule about *grammar*, not about trailing characters: **`git config
<key>` with no value, and `--get`/`--get-all`/`--list`/`-l`, is a read and never a security write;
only a set — `git config <key> <value>`, `--add`, `--unset`, `--unset-all`, `--replace-all` — of a
guarded key is one.** This spec replaces the two regexes with a predicate that reads the command as
tokens and applies that rule.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | **A predicate over tokens — `_sets_guarded_config(command)` — consulted from `_command_matches`, with both regexes deleted.** | A third, cleverer regex (e.g. excluding `2`/`>`/`#` from the trailing character class). | The bug is not that the regex is too loose or too tight; it is that "is there a character after the key" is not the question. Git's answer depends on a flag set, a positional count, and flags that swallow their own argument (`--file <path>`) — three things a character class cannot see, which is exactly how P4's six rows split three each way. Every widening of the character class adds another evasion (`#`, `\|&`, a tab) and still leaves `git -C` and the casefold hole open. P7 already settled that a command-shaped question gets a predicate in this module. |
| C2 | **The predicate reads the raw `command`, not `_run_text(command)`.** | Reading `_run_text`, as the pattern table does. | P3: `_run_text` deletes read-only simple commands whole, which is why the card's command is judged by accident today. A `git config` set is never inside a read-only simple command, so there is nothing for `_run_text` to save the predicate from — and `_simple_commands`, which the predicate calls itself, already strips heredoc bodies, which is the one thing `_run_text` was protecting against. Same choice `_pushes_trunk` makes, for the same reason. |
| C3 | **Guarded keys are one module-level frozenset, casefolded, with exactly one member: `core.hookspath`.** The key read off the command is compared `.casefold()`. | Keeping the key inline; widening to `core.fsmonitor`, `core.editor`, `core.pager`, `credential.helper` and the other keys that execute something. | P5 makes the casefold non-optional: without it `git config core.hookspath /tmp/h` disables every hook and is waved through, today. A frozenset is where the next key goes, but adding one now would hold commands that are not held today — a new refusal the card did not ask for, landing on sessions with no warning. The card's words are "core.hooksPath and the like"; "the like" is a future card with its own measurement, not a guess made inside this one. |
| C4 | **A read flag decides, and a set is then either a write flag or two positionals.** Read flags: `--get --get-all --get-regexp --get-urlmatch --list -l --name-only --get-color --get-colorbool`. Write flags: `--add --unset --unset-all --replace-all`. Otherwise: two or more positionals after `config` = key and value = a set; one = a read. | Deciding on positional count alone; a single "is it a write" flag list with no read list. | `--get core.hooksPath` has one positional and `--unset core.hooksPath` has one too — the count alone cannot separate them, so the flags must be named. Naming *both* directions, with the read list winning, is what makes the default safe in the right direction: a `git config` form nobody listed and nobody can name a read flag in, carrying a key and a value, reads as a set. |
| C5 | **Flags that take the next token consume it: `--file -f --blob --type -t --default`.** | Ignoring them, as the old regex's `--\S+` group effectively did. | P4's third evasion. Without this, `git config --file .git/config core.hooksPath /tmp/h` has `.git/config` as its first positional, so the key looks like `.git/config` and the set is waved through. With it, the key is `core.hooksPath` and it holds. |
| C6 | **`git`'s own globals are walked past before `config` is required**, the same three lines `_pushes_trunk` uses, and `argv[0]` is matched by `os.path.basename`. | Requiring `git config` adjacent, as both regexes do. | P4's second evasion: `git -C /repo config core.hooksPath /tmp/h` is the form a factory session actually writes, because a worker works in a worktree and reaches into another checkout by `-C`. `/usr/bin/git` is the same program. |
| C7 | **Unbalanced quotes → `True`.** | `False`; raising. | P7's words: the safe side. A command the tokeniser cannot read is one whose `git config` the predicate cannot rule out, and the cost of the two sides is not symmetric — a false hold is a STALEMATE round, a false pass is an unheld hooks-path write. Pinned by a case in the acceptance table so it is a decision and not an accident. |
| C8 | **`--edit`/`-e`, `--remove-section` and `--rename-section` stay out.** | Holding them too. | None of them names a key, so none can be attributed to a guarded one without holding every `git config --remove-section <anything>`. They pass today and they pass after; this is a stated, tested-nowhere gap and not a regression. Named here so a reviewer reads it as a decision. |
| C9 | **`git -c core.hooksPath=/tmp/h <cmd>` stays out**, and so does a set hidden in a command substitution inside a read-only simple command (`ls $(git config core.hooksPath /tmp/h)`). | Extending the predicate to git's one-shot `-c`; adding `(`/`)` to `_OPERATORS`. | Both pass today, so neither is a regression, and neither is a `git config` read/write question — `-c` is a different surface (it disables hooks for one command without writing anything, which is `--no-verify`'s shape, not `git config`'s), and `(` in `_OPERATORS` would change `_simple_commands` under `_pushes_trunk` and `full_suite_command` too, which is a rewrite of shared machinery the card does not ask for. Both are named in this session's report so the observation is not lost. |
| C10 | **One Story, one Task.** | Splitting "reads pass" and "sets hold" into two. | They are two directions of one predicate in one function. Two Tasks would write the same two files, so their footprints could not be disjoint and the second would wait on the first for no gain — and landing either half alone is worse than landing neither: the reads-only half deletes the regexes and leaves the hooks path unguarded, the sets-only half keeps the three false holds the card was filed about. |

## The design

One file changes: `asf/approvals.py`. Four module-level frozensets and one predicate go in beside
`_pushes_trunk`; two regexes come out of `_COMMAND_PATTERNS`; one branch goes into
`_command_matches`.

**The tables**, beside `_GIT_READS` and `_REDIRECTS` (`asf/approvals.py:429-433`):

```python
#: The ``git config`` keys whose *setting* is a security write: the hooks path decides which hooks
#: run at all, so a session that sets it turns off the checks it is meant to pass. Casefolded —
#: git config keys are case-insensitive in section and variable name, and `git config
#: core.hookspath <p>` is the same write as `core.hooksPath` (asf.hermetic stores them this way
#: for the same reason). Reading one is a read: see :func:`_sets_guarded_config`.
_GUARDED_CONFIG_KEYS = frozenset(('core.hookspath',))

#: ``git config`` flags that take the next token as their own argument — never the key, never the
#: value. `git config --file <path> <key> <value>` is a set of `<key>`, not of `<path>`.
_CONFIG_VALUE_FLAGS = frozenset(('--file', '-f', '--blob', '--type', '-t', '--default'))

#: ``git config`` flags that make it *write* the key they carry.
_CONFIG_WRITE_FLAGS = frozenset(('--add', '--unset', '--unset-all', '--replace-all'))

#: ``git config`` flags that make it *print*: git writes nothing, whatever else is on the line.
_CONFIG_READ_FLAGS = frozenset((
    '--get', '--get-all', '--get-regexp', '--get-urlmatch', '--list', '-l', '--name-only',
    '--get-color', '--get-colorbool'))
```

**The predicate**, after `_drop_redirections` (it uses it):

```python
def _sets_guarded_config(command):
    """True when one of ``command``'s own ``git config`` invocations *sets* a key in
    :data:`_GUARDED_CONFIG_KEYS`. Reading one writes nothing and is never
    ``touch_security``: a bare ``git config core.hooksPath``, a ``--get``, a ``--list``/``-l``,
    whatever redirection or compound it sits in (F-0212 — a product's Task was held on
    ``git config core.hooksPath && ls -la $(...)``, which prints a value and lists a directory).
    A set is a write flag, or a key with a value after it. Each simple command is split off the
    compound (:func:`_simple_commands`), so a heredoc body quoting a set is data, and each is
    read past ``git``'s own globals, so ``git -C <dir> config`` counts. Unbalanced quotes: True,
    the safe side, as in :func:`_pushes_trunk`."""
    if 'config' not in command:
        return False
    try:
        argvs = _simple_commands(command)
    except ValueError:                      # unbalanced quotes: refuse, the safe side
        return True
    for argv in argvs:
        argv = _drop_redirections(argv)     # `2>/dev/null` says where output goes, not what runs
        if not argv or os.path.basename(argv[0]) != 'git':
            continue
        i = 1
        while i < len(argv) and argv[i].startswith('-'):
            i += 2 if argv[i] in ('-C', '-c') else 1
        if i >= len(argv) or argv[i] != 'config':
            continue
        flags, positional, rest, j = set(), [], argv[i + 1:], 0
        while j < len(rest):
            if rest[j] in _CONFIG_VALUE_FLAGS:
                j += 2                      # the flag's own argument, never the key or the value
                continue
            (flags.add(rest[j]) if rest[j].startswith('-') else positional.append(rest[j]))
            j += 1
        if flags & _CONFIG_READ_FLAGS or not positional:
            continue                        # git prints; it writes nothing
        if not (flags & _CONFIG_WRITE_FLAGS or len(positional) >= 2):
            continue                        # a key on its own: git prints its value
        if positional[0].casefold() in _GUARDED_CONFIG_KEYS:
            return True
    return False
```
