# F-0331 — an install that lost a clock must not exit 0

`asf scheduler install` boots a clock out and bootstraps it back in two calls with nothing between
them (`asf/scheduler.py:926-927`):

```python
    _launchctl(['bootout', f'gui/{_uid()}/{label}'])  # not loaded yet is the ordinary case
    rc, _out, err = _launchctl(['bootstrap', f'gui/{_uid()}', path])
```

A `bootout` of a job whose process is running returns as soon as launchd has signalled it, not
when the service has left the domain — the product's own guide already says so: *"on launchd it
boots out and reloads each tick job, which ends a tick that is running at that moment"*
(`docs/guide/upgrading.md:125`). The `bootstrap` on the next line therefore arrives while the old
job is still being reaped, launchd refuses it, and the clock the command was run to install is
gone. Nothing in the command notices: the refusal is one line in the middle of four clocks' output
and **the command still exits 0** (P2).

That is the card, step for step: an install at about 18:55Z while a tick had been running since
18:37Z, four clocks bootstrapped and the tick clock not among them, a product with no tick clock
for five minutes, and nothing that said so until a second install at 19:00Z — when no tick was
running — loaded it.

The gap is not that the install ends a running tick. That is documented, and nothing is lost: the
next tick resets its clone and derives again. The gap is that the install then **does not look**,
and tells its caller it succeeded. Its two sibling command paths both already look at their own
result (`:1473`, `:1504`), and `asf scheduler status` already exits 1 for exactly the state this
install exits 0 on (`:1627-1628`).

* **P1 — the bootout's result is discarded, and nothing is read back between the two calls.**
  `_launchd_install` (`asf/scheduler.py:914-932`) writes the plist, returns early for a paused
  clock, then issues `bootout` without binding its return value and `bootstrap` immediately after.
  Measured, a first install of one clock (nothing loaded, the stub's `bootout` exits 3):


  The comment on `:926` is right that a failed bootout is the ordinary case on a first install. It
  is also the reason a *successful* one — launchd held a job, and it is now winding down — is not
  distinguished from it.
* **P2 — a refused bootstrap is one line among many, and the command exits 0.** The card's product
  file as the card describes it (a tick clock, `batch`, `daily`, and the `wave` clock the tick's
  `wave` step adds), with the stub refusing exactly the tick's bootstrap the way launchd does
  (`Bootstrap failed: 37: Operation already in progress`):

  ```
  scheduler: bootstrap asf.sample.tick failed (Bootstrap failed: 37: Operation already in progress)
  scheduler: wrote <tmp>/home/Library/LaunchAgents/asf.sample.batch.plist
  scheduler: bootstrapped asf.sample.batch
  scheduler: wrote <tmp>/home/Library/LaunchAgents/asf.sample.daily.plist

  scheduler: wrote <tmp>/home/Library/LaunchAgents/asf.sample.wave.plist
  ```

  This is the card's output, shape for shape: the clocks that came back are `batch`, `daily` and
  `wave` (plus `ci-queue` on a product with a CI queue), and the one that did not is named only in
  a line that says `failed` four lines up. The clock reads back **not loaded**, it carries **no
  pause record** — so nothing meant it to be unloaded — and the exit status is **0**.
* **P3 — the race, modelled, and the wait that closes it.** A stub that models launchd's own
  semantics — `bootout` of a live job returns at once and the service stays in the domain until
  the process is reaped, a `bootstrap` of a label still in the domain fails 37 — against today's
  code, and then against a bounded poll of `status(label)` between the two calls:

  ```
  --- state before: running
  --- today: rc = 0
  scheduler: wrote <tmp>/home/Library/LaunchAgents/asf.sample.tick.plist
  scheduler: bootstrap asf.sample.tick failed (Bootstrap failed: 37: Operation already in progress)
  --- today: read-back 1: loaded = True
  --- today: read-back 2: loaded = True
  --- today: read-back 3: loaded = False

  --- with the wait: rc = 0
  scheduler: asf.sample.tick is running now — the bootout ends this tick
  scheduler: wrote <tmp>/home/Library/LaunchAgents/asf.sample.tick.plist
  scheduler: bootstrapped asf.sample.tick
  --- with the wait: gone = True after 0.155s
  --- with the wait: loaded after = True
  ```

  Today the label launchd still holds for the first two reads is the **old** job, exiting; once it
  is reaped the product has no tick clock at all. With the wait the bootstrap lands first time.
  The whole wait was 0.155 s of the stub's model; on a real host it is bounded by launchd's own
  `ExitTimeOut` (20 s by default), after which the process is killed and the service leaves.
* **P4 — `status(label)` already carries both facts the wait needs, and no pid.** `status` →
  `_launchd_status` → `parse_print` (`asf/scheduler.py:1175-1192`, `:1134-1172`) returns
  `loaded` and `state`, and the captured sample `tests/fixtures/launchctl-print.txt` has
  `state = running`. It has **no** `pid =` line, so a line naming the pid of the job this install
  is about to end cannot be written from the reader the product has (D6).
* **P5 — the two sibling command paths already fail on their own output; install is the only one
  that does not look.** `_cmd_pause_resume` ends `return 1 if any('failed' in line for line in

  command returns 1 for a clock that is not loaded and not paused (`:1627-1628`). The install tail
  (`:1630-1643`) prints its lines and returns `0 if job_kind == 'launchd' else 3` without reading
  one of them.

  gone cannot notice its own
  absence.

### Out

| Out | Why |
|---|---|
| Refusing to install while a tick is running, or draining first | The guide already licenses the interruption and nothing is lost by it (`docs/guide/upgrading.md:125`), the operator ran the command on purpose, and the drain machinery that exists (`upgrade._drain_and_hold`) costs a bounded wait on the whole floor plus a pause record per clock — far more than this card asks. An install that ends a tick and says so is right; one that silently loses the clock is the defect |

### Preconditions the work depends on

* `scheduler.kind` is `launchd`. Every line of this change is behind that: the wait and the retry
  are in `_launchd_install`, and the read-back is behind `job_kind == 'launchd'` so a cron or
  `none` kind still prints its lines and returns 3.
* A paused clock is meant to be unloaded. `_launchd_install` returns before the bootout for one
  (`:921-925`), and the read-back never counts one (`pause_record`), exactly as
  `install._clocks_not_loaded` does today (`asf/install.py:385-389`).
* `launchctl print` is the authority on whether launchd holds a label. The wait and the read-back
  are both `status(label)`, which is the reader `asf scheduler status`, `asf doctor` and
  `asf install`'s step 8 already trust.
* The retired labels an install boots out on purpose (`retire_candidates`, `:1635-1640`) are never
  read back: they are gone because the product file no longer declares them.
* `tools/rollback.sh` reads the cutover's manifest. The `scheduler_install` row must be written
  whether or not the clock loaded, because the plist is on disk either way (P8).

## The design

One module carries the change (`asf/scheduler.py`); `asf/install.py` loses a predicate body to it;
`tools/cutover.sh`, `asf/config_keys.py`, `docs/config.example.yaml`, two guide files and
`tests/test_scheduler.py`'s stub and argv pin follow.

### 1. The wait — `asf/scheduler.py`

`asf/scheduler.py:51-58` imports no `time`; the signature below needs one (`import time`, in its
alphabetical place beside `subprocess` and `sys`).

```python
#: An install waits this long (seconds) for a booted-out job to leave launchd before it
#: bootstraps the new one: the job's process gets SIGTERM, and launchd kills it at its own
#: ExitTimeOut (20 s by default), so the service is gone well inside this bound. Config
#: ``scheduler.bootout_wait_s`` over it (F-0331 D2).
BOOTOUT_WAIT_S = 30
#: how often the wait looks — one ``launchctl print`` a poll (``scheduler.bootout_poll_s``)
BOOTOUT_POLL_S = 0.5


def wait_unloaded(label, limit_s=None, poll_s=None, sleep=time.sleep, clock=time.monotonic):
    """Poll until launchd no longer holds ``label``: ``(True, waited_s, polls)`` once it is gone,
    ``(False, waited_s, polls)`` when the bound passed with the label still there. ``polls`` is
    how many times it slept — zero means the label was already gone and the caller says nothing
    (F-0331 D11).

    ``launchctl bootout`` returns when launchd has signalled the job, not when the service has
    left the domain, and a ``bootstrap`` of a label still in it is refused (``37: Operation
    already in progress``) — which is how an install run during a running tick left the product
    with no tick clock (F-0331). ``sleep`` and ``clock`` are injected so a test spends no real
    seconds."""
```

It reads before it sleeps: the first `status(label)` happens at once, so the ordinary bootout of
an idle job costs one `launchctl print` and no seconds. Both bounds read through `tunable()`, so
the constant is the default and the config key is over it.

### 2. The install — `_launchd_install`, rewritten around the wait

```python
def _launchd_install(job):

    ...                                     # the plist and the log dir, unchanged (:916-920)
    record = pause_record(label)

```

`insert(0, …)` and not `append`: `lines` is built at `:920` as `[f'scheduler: wrote {path}']`, and
the running-now line is about the job that is *already* there — it reads before the line that says
what this install wrote, which is the order P3 measured and the order both illustrations below
print.

and the retry, which is the only new branch in the bootstrap itself:

```python
def _bootstrap_with_one_retry(label, path):
    """Bootstrap ``path``; a refusal gets one more bounded wait and one more try (F-0331 D3)."""
    rc, _out, err = _launchctl(['bootstrap', f'gui/{_uid()}', path])
    if rc == 0:
        return [f'scheduler: bootstrapped {label}']
    # `refused`, not `failed`: _cmd_host's exit status sniffs these lines for `failed` (:1504),
    # and a retry that succeeded must not read as a failure (F-0331 D3)
    lines = [f'scheduler: bootstrap {label} refused ({err.strip() or rc}) — retrying once']
    wait_unloaded(label)
    rc, _out, err = _launchctl(['bootstrap', f'gui/{_uid()}', path])
    lines.append(f'scheduler: bootstrapped {label} (retried)' if rc == 0 else
                 f'scheduler: bootstrap {label} failed again ({err.strip() or rc})')
    return lines
```

A first install of a clock nothing holds prints exactly the two lines it prints today: `before` is
`{'loaded': False}`, there is no running-now line, the `bootout` fails as it always did, no wait is
entered, and the bootstrap succeeds first time. One thing *is* different, and it is a pin this
change amends rather than preserves: the `before = status(label)` is one more `launchctl print`,
and `tests/test_scheduler.py:473-478` counts every call —


### 3. The read-back, and the exit status — `cmd_scheduler`'s install tail

One module function, which `asf/install.py` then shares (D5):

```
NEEDS OPERATOR: clock(s) not loaded after install: asf.sample.tick — nothing ticks sample on it; `asf scheduler install --product sample` again (between ticks), then `asf doctor --product sample` for what launchd says
```

— exit 1. The product still has no tick clock for the moment, which no command can promise
otherwise; what has changed is that the operator, `asf install`'s step 8, the upgrade and the
cutover all learn it from the command itself.

A paused clock is unchanged and is not a failure: `scheduler: asf.sample.tick paused since … — not
loaded; asf scheduler resume … to start it`, exit 0.

So is the ordinary case — an install between ticks, which is what an upgrade and a cutover do. The
bootout of an idle clock leaves the domain before the wait's first look, so no wait line is printed
(D11) and the output is the two lines per clock it is today:

```
scheduler: wrote <home>/Library/LaunchAgents/asf.sample.tick.plist
scheduler: bootstrapped asf.sample.tick
```

— exit 0. One `launchctl print` per clock before the bootout and one after the installs is the
whole cost of the change on that path.
