# F-0264 — the operator said revert it, and the factory landed it anyway

An operator ruling is the one instruction in this factory that no cap, no round count and no
verdict may outrank. `asf correct <item> --why …` at the round cap exists precisely because every
other guard has been spent: a person has read the branch and said what must happen to it. The
lane's own docstring says so — "An operator ruling (`asf correct` at the cap) always does [turn a
landing wait BACK] — a CI wait on a head the ruling is there to change is no reason to hold it".

On 2026-10-06 it did not. On a product's T-42278 an operator ruling was recorded at
`23:01:39Z`, the lane reworded the branch's commit subjects at `23:01:56Z` — seventeen seconds
later, a naming reword, no session, trees identical — and the next pass read the branch as
`PUSHED → LAND`. The ruling was never carried out. The pull request would have landed a reverted
feature carrying a `Proves:` claim, and the only row the factory showed for the item was
`WAITS ON landing: PR #42278 lane WAITING_CI: required checks pending`: not a word about the
ruling, not a word about why nothing was launching.

Three independent causes, all live on `main` at `5a6b035`, and **each one alone is enough to lose
the ruling** — the measurements below show that fixing any one of them still loses it. This card
is: all three, plus the two places that must stop hiding a correction that has no session.

## Decisions

### In

1. **The lane and `occupancy` read a pending correction item-wide, scoped to the branch** — one
   new `lifecycle.pending_on_branch`, used at `lane.branch_facts` and at the three
   `pending_correction` reads inside `occupancy` that decide `back` and `correction_turns_back`.
2. **A lane-made head move does not answer a correction** — `head_at` is carried across the
   lane's own rewrites, so the ruler `correction_turns_back` uses stays the moment a *session*
   last left the head.
3. **An adjudication's overrule never outranks a later operator ruling** — a guard inside
   `lifecycle.overruling`, so every caller gets it, and the lane's T5a' (`f['ruled']`,
   `rulings.reraised_only`) held by the same fact.
4. **`asf land --withdraw` neither drops nor hides a pending correction** — pinned by test; the
   `WAITING` record it leaves is a landing wait like any other and goes BACK.
5. **A pending correction with no launch row names its cause** — one feeder helper, read by
   `asf next`'s rows and by a new `asf status` cell: live session, lane state, cap, parked.
6. **The regression replay** of the 2026-10-06 sequence, expecting a `FIX → CORRECT` row.

### Out

- **No change to who may write a correction.** `asf correct` keeps its surface; this card changes
  only which readers see one and when it counts as answered.
- **No change to `pending_correction`'s own "answered" rule.** A run of the item started at or
  after the correction still answers it, adjudicate runs still do not (B-0128), and a quota-dead
  run still does not. This card changes the *lane's* second ruler (`head_at`), not that one.
- **No new round, cap or relaunch counting.** A ruling turns the branch BACK; what the correction
  round cap then does with it is untouched.
- **No item-wide BACK.** A correction pending on branch *X* of an item never turns branch *Y*
  back. Item-wide is how the correction is *found*; branch-scoped is how it is *applied*.
- **No change to the lane's rewrites themselves.** The reword, restack, sign-off and copy-drop
  keep running, keep their guards and keep their archives; only their effect on `head_at` changes.
- **No `asf land --withdraw` behaviour change.** The withdraw keeps dropping the request and
  holding the PR out; the correction simply survives it, which it already does — the test is the
  deliverable, not a code change.
- **No new operator command.** Every cause this card names becomes visible in `asf next` and
  `asf status`; nothing new must be typed to see it.

### Choices

## The design

### 1. `lifecycle.pending_on_branch` — the item's correction, scoped to one branch

New in `asf/workers/lifecycle.py`, beside `pending_correction` and `correction_of`:

```python
def pending_on_branch(path, item, branch, run=None):
    """The pending correction a session on ``branch`` of ``item`` must answer: the newest
    :func:`pending_correction` across *every* run of the item (not only the branch's newest
    run — F-0264) whose correction names ``branch``, or names no branch and sits on a run
    whose branch is ``branch``, or names neither. ``None`` when there is none.

    The item park (:func:`item_park`) is not here and never is: it speaks for the item, and
    the feeder's PARKED row speaks for it — a park has no session to go back to. A run a
    branch or job park holds (:func:`scoped_park_of`) is skipped for the same reason.

    With no ``item`` (an adopted or foreign branch no card claims) it answers
    ``pending_correction(run, path)``: that branch's own run is all there is to read."""
```

It is the one read for "what does this branch owe a session". `correction_of` keeps its own job —
the feeder's item-wide row, park folded in — and is unchanged.

**`asf/harvest/lane.py:1742`**, in `branch_facts`, becomes:

```python
'correction': lifecycle.pending_on_branch(self.path, item, b, run),
```

— one read, no `if run else None` arm (C3 puts the fallback inside).

**`asf/workers/lifecycle.py`, in `occupancy`**, the three reads over a branch's run become the
same call. The loop already has `item` and `branch` in hand:

```python
corr = pending_on_branch(path, item, branch, run)
...
if state == lane_mod.BACK and not landed(run) and not corr:
...
if lane_mod.correction_turns_back(rec, corr):
    continue
...
elif landed(run) or corr or lands_nothing(run):
    continue
```

With fix 2 in place this is what closes the chain P7→P8: the branch's landing wait is no longer
a wait, the item leaves `landing`/`waiting_landing`, `rows.occupied` stops holding it, and
`correction_rows` emits the `FIX → CORRECT` row it already wanted to (P8).

### 2. `head_at` survives the lane's own rewrites

`lane.head_since` grows one argument and one clause:

```python
def head_since(prev, head, now, lane_heads=()):
    """When a *session* last left ``head`` on the branch (a lane record's ``head_at``):
    ``prev``'s own while the head has not moved — or while ``head`` is one the lane itself
    built (``lane_heads``, and the chain ``prev`` carries): the lane's reword, restack,
    sign-off and copy-drop change the sha without answering anything, and a correction must
    not read as answered because of one (F-0264). A record from before ``head_at`` existed,
    its ``at``; else ``now``."""
    prev = prev or {}
    if head and (prev.get('head') == head
                 or head in set(prev.get('lane_heads') or ()) | set(lane_heads or ())):
        return prev.get('head_at') or prev.get('at') or now
    return now
```

`Lane.record` feeds it the pass's own rewrites and persists the chain:

```python
#: how many of the lane's own rebuilt heads one record keeps (F-0264): enough to explain the
#: current head through a pass that rewords, drops copies and signs off in turn
LANE_HEADS_MAX = 20
...
built = tuple(f.get('lane_built') or ())
rec['head_at'] = head_since(f.get('prev'), f.get('head'), now, built)
chain = (tuple(prev.get('lane_heads') or ()) + built) if rec['head_at'] != now else ()
chain = tuple(dict.fromkeys(h for h in chain if h))[-LANE_HEADS_MAX:]
if chain and f.get('head') in chain:
    rec['lane_heads'] = list(chain)
```

`f['lane_built']` is appended to at the two push sites of P11, each one line:

- `Lane._repair_naming`, where it already does `f['head'] = new` (`asf/harvest/lane.py:2715`);
- `Lane.publish_rebuilt`, where it already does `f['head'] = new` (`:2954`) — which carries
  `drop_copies`, `rebase_onto_trunk` and `repair_signoff`;
- `Lane.normalise_commits`, where it already does `f['head'] = new` (`:2901`).

```python
f.setdefault('lane_built', []).append(new)
```

Nothing else reads `lane_built`. A session's push leaves it empty, `head_at` becomes `now`, the
chain is dropped (C6), and the branch's `head_at` means again what it always meant.

`correction_turns_back` itself is **unchanged** — its `since = rec['head_at']` is now the right
ruler. Its docstring gains the one sentence that says so, and names F-0264.

What this makes true, in the acceptance's words: a lane-made head move after the ruling does not
answer it; a session run started at or after the ruling does (`pending_correction`'s own rule,
untouched), and so does a head that session pushed (`head_at` moves to that push's pass).

### 3. An adjudication's overrule never outranks a later operator ruling

New in `asf/workers/lifecycle.py`:

```python
def later_operator_ruling(path, item, at):
    """The pending operator ruling on ``item`` written at or after ``at``, or None: a
    :func:`pending_correction` carrying ``operator_ruling`` on a run no branch or job park
    holds. The one correction no verdict and no adjudication outranks (F-0264) — a person read
    the branch and said what must happen to it."""
```

and in `overruling`, immediately after `run = ruled[-1]`:

```python
if later_operator_ruling(path, item, run.get('started') or ''):
    return None   # F-0264: a ruling an operator overruled afterwards does not stand
```

In `lane.branch_facts`, the same fact holds T5a' back, so neither arm of the review's
ruling-answers-it path can reach GATE:

```python
f['overruled'] = lifecycle.overruling(...)
if not f['overruled'] and not lifecycle.later_operator_ruling(
        self.path, item, ''):          # a pending ruling outranks a standing one too (T5a')
    f['ruled'] = rulings_mod.reraised_only(...)
```

The `at=''` read is deliberate: T5a' cites a *standing* ruling with no run to date from, so any
pending operator ruling on the item outranks it.

### 4. `asf land --withdraw` neither drops nor hides a pending correction

No code change (C13). What must hold, and what the test pins:

- after `cmd_land(--withdraw)` the stored correction is byte-identical — `land-withdrawn.json`
  and the dropped request are the only writes;
- the `WAITING` record `_wait` leaves (`merge queue: withdrawn (asf land --withdraw)`) keeps the
  record's `head_at`, because the head did not move (`head_since`'s first clause);
- `WAITING` is in `LANDING_WAITS`, so `correction_turns_back` turns the branch BACK on the next
  pass, and `occupancy` reports the item in neither `landing` nor `waiting_landing`.

### 5. A pending correction with no launch row names its cause

New in `asf/feeder/rows.py`:

```python
#: why a pending correction got no launching row (F-0264) — one of four, never nothing
CAUSE_LIVE = 'live session'
CAUSE_LANE = 'lane'
CAUSE_CAP = 'cap'
CAUSE_PARKED = 'parked'

def correction_cause(items, item_id, occupancy, attempts=None, product=None):
    """``(cause, text)`` for a pending correction on ``item_id`` that launches nothing, or
    ``None`` when none is pending. Four causes, read off facts the feeder already has
    (F-0264) — never a bare ``WAITS ON landing``:

    * :data:`CAUSE_PARKED` — the correction carries ``parked``, or a branch/job park holds its
      run (``occupancy['parks']``): a person releases it (``asf unpark``);
    * :data:`CAUSE_LIVE` — a run of the item is live (``occupancy['busy']`` from
      :func:`asf.workers.lifecycle.inflight`): the session it is waiting for is running;
    * :data:`CAUSE_LANE` — a lane state holds the item and is not one a correction turns back
      (``PUSHED``, ``QUEUED``, ``MERGING``, ``PARKED`` — P10), named with its state and PR;
    * :data:`CAUSE_CAP` — the item is at or past ``attempt_limit`` and an adjudication already
      ended on this same card (:func:`_capped`'s ``adjudicated``): a card edit, a ruling or an
      unpark moves it.

    ``text`` is one line, operator-facing, and always names the correction's kind and ``at``."""
```

Read at three sites:

- **`pushed_rows`** — before its three existing arms, so the correction wins the row's action:

  ```python
  cause = correction_cause(items, iid, occ, attempts, product)
  if cause:
      action = f'{WAITS_CORRECTION}: {cause[1]}'
  elif iid in waiting:
      ...
  ```

  with `WAITS_CORRECTION = 'WAITS ON correction'` beside the other `WAITS_*` constants. The row
  stays non-launching (`PUSHED → LAND`) and gains `waits_on=cause[0]`.

- **`bug_rows`** — its `b['id'] in busy` arm asks `correction_cause` first, so a decided S1/S2
  Bug with a held correction says so instead of `WAITS ON landing`.

- **`asf status`** — a new cell in `asf/views/status.py`:

  ```python
  def held_corrections_cell(product, root=None):
      """``Held corrections``: every pending correction that launches nothing, with the cause
      :func:`asf.feeder.rows.correction_cause` names (F-0264) — never a silent ruling.
      Silent (None) when every pending correction has a launching row."""
  ```

  registered in `render`'s cell list between `Parked` and `Quota 5h/7d`, rendered like
  `parked_cell`: `"<n> — <item> [<cause>]: <text>; … (+k more) · `asf next` shows the row"`.

### 6. What it looks like when it is there

The 2026-10-06 sequence, replayed: the operator ruling at `23:01:39Z` is found by
`pending_on_branch` on the review run's branch though it sits on the coder job (fix 1); the
reword at `23:01:56Z` leaves `head_at` at `22:30:00Z`, where the coder's push left it (fix 2);
`correction_turns_back` answers True; the lane writes `BACK kind=review`; `occupancy` reports no
landing wait for the item; and `asf next` shows

```
FIX → CORRECT  T-42278  would launch   review, round 2, operator ruling
```

instead of `PUSHED → LAND  T-42278  WAITS ON landing: PR #42278 lane WAITING_CI`. Had the
adjudication's overrule still been in play, `overruling` would have answered None (fix 3) and
the review would not have reached GATE.

## Records

- **`<state>/<product>/sessions.jsonl`, the lane record on the branch's run** — one new key,
  `lane_heads`: the list of heads the lane itself built since a session last left one, newest
  last, at most `LANE_HEADS_MAX = 20`, written only while the current head is one of them and
  absent otherwise. `head_at` keeps its meaning but changes its truth: it is now the moment a
  *session* last left the head, not the moment the sha last changed.
- **The lane's own lines** (stdout, and the tick log) — unchanged for every rewrite. The one new
  line is the transition the fix makes possible:
  `lane: <branch> WAITING_CI → BACK (kind=review)`, where before it read
  `lane: <branch> WAITING_CI → WAITING_CI (…)` or a PUSHED → LAND row with no reason at all.
- **`asf next`** — a `PUSHED → LAND` or `BUG → FIX` row whose action is
  `WAITS ON correction: <cause text>` and whose `waits_on` is one of `live session`, `lane`,
  `cap`, `parked`, in place of `WAITS ON landing: …`. Plus the row this card exists for:
  `FIX → CORRECT` in the item's severity tier, launching.
- **`asf status`** — one new cell, `Held corrections`, one line, silent when there is none:
  `<n> — <item> [<cause>]: <text>; … · `asf next` shows the row`.
- **No new file, no new state file, no new command.** `land-withdrawn.json`, the correction
  records, the parks and the review files are all read as they are.
- **What is no longer written** — a `GATE … overruled by <job>'s ruling` record while an operator
  ruling is pending; a `head_at` stamped by the lane's own reword, restack, sign-off or copy-drop;
  and a `WAITS ON landing` row for an item whose correction is waiting for nothing.
