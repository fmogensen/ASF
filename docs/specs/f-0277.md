# F-0277 — the trunk had already moved, and the factory was reading last hour's answer

A Task's PR landed through the merge queue. The queue *fast-forwards* the trunk to the green batch
sha and only then asks the host to mark the member PRs merged (`asf/merge_queue.py:1964-2024`:
"MERGING on every member first, MERGED at that sha after — then close what the host did not mark
merged"), so for a few seconds the trunk is ahead of the PR list by construction. The host caught
up within seconds, as it normally does. The factory did not: 40 min later the card still read
`PR #1046 OPEN / rule: in-flight`, Active, because `state/<product>/cache-prs.json` was 46 min old
and still held that row as OPEN. The Feature's next Task waited behind it.

Two halves of the answer are already on the trunk, both naming this card. The PR cache is keyed on
the trunk's sha as well as its age (`asf/evidence/sources.py:28-80`, `asf/evidence/evidence.py:388-405`):
a landing moves the trunk, so the list read before it is stale at once. And `evidence.queue_landed`
reads the queue's own `merge-queue: #<n> …` subjects off the trunk and keeps those numbers out of
`open_prs` (`asf/evidence/evidence.py:1390-1404,1465-1473`). `tests/test_pr_cache_trunk.py` pins both.

Neither half reaches the two places that produced the row the card quotes, and this was measured in
this worktree, not inferred:

- **The Task's state never reads `open_prs`.** The `in-flight` rule is
  `lambda ev: bool(ev.branch or ev.pr_state)` (`asf/evidence/closing.py:120`). `open_prs` alone
  derives New (P3), so the landed `queue_landed` exclusion cannot move a single Task. The field that
  does move it, the plan row's `pr_state`, is chosen by
  `open_pr = next((p for p in cand_prs if p.get("state") != "CLOSED"), None)`
  (`asf/evidence/evidence.py:804-810`) — which asks the PR list and nothing else, so a row still
  reading OPEN yields `pr_state: 'OPEN'`, `Active`, `rule: in-flight`, and the ingest line
  `PR #1046 OPEN` verbatim (P4, P5, P6). The queue had already deleted the branch
  (`asf/merge_queue.py:2018`), which is why the card's row names a PR and no branch: `pr_state`
  was the whole hold.
- **The lane's occupancy reads the cache file raw.** `lifecycle.ended_prs(state_dir)` opens
  `cache-prs.json` and counts only the rows that already say MERGED or CLOSED — with no age check
  and no trunk read at all (`asf/workers/lifecycle.py:1374-1392`). An hour-old OPEN row for a PR the
  trunk carries returns `{}` (P7), so `pr_ended` is None (P8), `occupancy` keeps the lane record
  live, and the Feature's next Task waits — until the next evidence pass rewrites the file, about
  45 min later. The trunk key does not help here: nothing in this path asks the trunk.

So the card's own symptom is still reachable on the trunk as it stands. This card finishes the
sentence the landed halves started: **a PR the trunk carries as landed is landed, whatever a PR list
read before the landing still says** — in the one field a Task's state is derived from, and in the
one map the lane releases an item by.

### In

1. **One fact, read once** — `trunk_watch.landed_prs(commits)` → `{pr number: sha}`: every PR the
   trunk's own commit subjects name as landed, by `pr_of` (P11's three forms). Pure; the caller reads
   the trunk. `evidence.queue_landed` becomes `set(trunk_watch.landed_prs(commits))` — same name,
   same callers, same landed tests (P18), one rule instead of a narrower second one (P12).
2. **The Task's own state** — `evidence.chosen_pr(cand_prs, merged, landed)` →
   `(number, pr_state, merged_sha)`, the plan row's three PR fields as one pure decision: a merged
   candidate first, then one the trunk carries as landed — read as `MERGED` at the trunk's sha — then
   the newest not-CLOSED one. `facts()` reads the trunk's commits once above the plan-row block (P14)
   and the row block becomes one call. The Task then settles on `landed-green` (`PR #1046 merged
   (bc62d611)`, Closed) instead of `in-flight` (`PR #1046 OPEN`, Active).
3. **The lane's release** — `lifecycle.ended_prs(state_dir, landed=())`: the cached MERGED/CLOSED
   rows as today, plus every number in `landed` as `{'state': 'MERGED', 'head': <cached head or
   None>}`, whatever that number's cached row says. `step_wave.occupancy` reads the trunk's
   first-parent subjects once (P13) within `TRUNK_LANDED_DAYS` and hands their numbers over. No
   readable trunk → `landed={}` → today's behaviour, byte for byte.
4. **The regression**, from both sides: the incident replayed as the plan row and the Task's derived
   state, and as the lane record that held the Feature's next Task.

### Out

- **No change to the trunk-keyed PR cache.** P1 is landed and pinned; this card neither re-keys it,
  re-times it, nor touches `PR_TTL`/`EVIDENCE_TTL` (P16). The hole is not that the cache is too old:
  it is that two readers never ask the trunk at all.
- **No new `gh` call, no new network read, no new state file.** Both new reads are `git log` on a
  repo the pass already has, one per pass.
- **No change to `closing.RULES` or to the rule order.** `landed-green`/`landed` already outrank
  `in-flight` (P15). This card feeds the rules the fact they are missing; it does not restate them.
- **No change to the tick's cadence.** The card observes that the record and PR steps run about
  every 45 min. Running them oftener would shorten the window, not close it; reading the trunk
  closes it. The clocks are untouched.
- **No change to `cache-prs.json`'s shape or to who writes it.** `ended_prs` keeps reading a plain
  list of rows; `landed` arrives as an argument, never as a field in the file.
- **Nothing inferred from an absent branch.** A deleted lane branch (P17) is not read as a landing.
  Only a PR number the trunk's own subject names is landed here.
- **No change to `_close_if_open`, its retries, or the queue's own lane records.** The host-side
  catch-up is already correct and already fast; the defect is on the reading side.
- **No change to `asf check`, the invariants or the feeder's rows.** The feeder reads `occupancy`
  and nothing else (`asf/workers/lifecycle.py:1412-1420`); once it releases the item the next-Task
  row follows with no new code.
- **A PR the trunk does not name is untouched.** An open PR stays open, a closed one stays closed,
  and a PR whose landing is older than `TRUNK_LANDED_DAYS` is left to the cache: a lane record still
  naming a PR from two days ago is a stall the watchdog owns, not a landing race.

## The design

### 1. The fact — `asf/trunk_watch.py`

Beside `pr_of`, over the rows `first_parent` and `evidence.main_commits` both produce:

```python
def landed_prs(commits):
    """``{pr number: sha}`` — every PR the trunk's own commit subjects name as landed, by
    :func:`pr_of` (``merge-queue: #<n> …``, ``… (#n)``, ``Merge pull request #<n> …``). The fact
    that outranks a PR list read before the landing: the merge queue fast-forwards the trunk and
    the host marks the PR merged after, so for a moment — and for as long as a cached copy of the
    list lives — the trunk is ahead (F-0277).

    ``commits``: ``{'sha', 'subject'}`` rows (:func:`first_parent`) or ``(sha, subject, …)``
    tuples (:func:`asf.evidence.evidence.main_commits`), newest first; the newest wins. Pure."""
```

and in `asf/evidence/evidence.py`, `queue_landed` keeps its name and its callers:

```python
def queue_landed(commits):
    """The PR numbers the trunk carries as landed (:func:`asf.trunk_watch.landed_prs`)."""
    from asf import trunk_watch
    return set(trunk_watch.landed_prs(_commit_rows(commits)))
```

### 2. The Task's own state — `asf/evidence/evidence.py`

```python
def chosen_pr(cand_prs, merged, landed):
    """``(number, pr_state, merged_sha)`` — the PR a plan's Task row is derived from, or
    ``(None, None, None)``.

    A candidate the PR list says MERGED first, at its ``merged`` sha; then one the trunk already
    carries as landed (``landed``: :func:`asf.trunk_watch.landed_prs`), read as ``MERGED`` at the
    trunk's sha whatever the list still says — a PR list read before a merge-queue landing says
    OPEN, and ``pr_state`` is the only PR field the Task's ``in-flight`` rule reads, so a stale row
    is 40 min of a landed Task kept Active (F-0277); then the first candidate that is not CLOSED,
    at its own state."""
```

The row block (`:803-813`) becomes:

```python
number, pr_state, merged_sha = chosen_pr(cand_prs, merged, landed)
rows.append({"id": tid, "cand": cand, "branch": br, "pr": number,
             "pr_state": pr_state, "merged_sha": merged_sha,
             "landed_no_branch": landed_doc and not br})
```

with `commits = main_commits(product)` hoisted above the plan-row loop (P14), `landed =
trunk_watch.landed_prs(commits)` beside it, and `:928`'s read replaced by the hoisted name. The
local `landed` the row block already uses for "a report says this Task is done" is renamed
`landed_doc` in the same change, so the two never read as one.

### 3. The lane's release — `asf/workers/lifecycle.py` and `asf/tick/step_wave.py`

```python
def ended_prs(state_dir, landed=()):
    """``{number: {'state', 'head'}}`` of every PR that is over: the rows the evidence pass last
    saw MERGED or CLOSED on its cache, plus every number in ``landed``
    (:func:`asf.trunk_watch.landed_prs`) as MERGED, whatever its cached row says — the trunk
    carries the merge, and the cache is a copy of an older answer (F-0277). ``{}`` when there is
    no cache and ``landed`` is empty."""
```

The trunk's entry is written last and wins (C8); it keeps the cached row's `headRefOid` when the
cache holds one, else None (C9). `occupancy` is unchanged: `pr_ended` reads MERGED, the branch goes
on `dead_branches`, `landed[item]` is set from the lane record's own sha, and the item leaves both
`busy` and `waiting_landing` (P9).

```python
#: how far back the wave step reads the trunk for landed PR numbers (:func:`occupancy`)
TRUNK_LANDED_DAYS = 2


def trunk_landed(product):
    """``{pr number: sha}`` the trunk carries as landed within :data:`TRUNK_LANDED_DAYS`
    (:func:`asf.trunk_watch.landed_prs` over :func:`asf.trunk_watch.first_parent`); ``{}`` when
    git cannot read it — unknown is never "not landed"."""
```

and `occupancy(product)` passes it:

```python
return lifecycle.occupancy(path, ended=lifecycle.ended_prs(os.path.dirname(path),
                                                           landed=trunk_landed(product)),
                           on_origin=lambda branches: on_origin(product, branches))
```

### 4. What it looks like when it is there

The incident, at the first pass after the landing instead of 40 min later — the card's row:

```
before   T-0485   Active   in-flight   PR #1046 OPEN
after    T-0485   Closed   landed-green   PR #1046 merged (bc62d6117)
```

and the Feature's next Task, which had been waiting on the lane record rather than on the card:

```
before   T-0660   WAITS ON T-0485   T-0485 is in flight (PR #1046)
after    T-0660   LAUNCH
```

Nothing is read, written or printed differently for a PR the trunk does not name, for a product
whose repo cannot be read, or on a second pass over the same trunk.

## Records

- **The card** — a Task whose PR the trunk carries derives `Closed` on `landed-green` with the
  evidence line `PR #<n> merged (<sha9>)`, in the first record pass after the landing instead of
  the one after the PR cache is next rewritten. The line it replaces, `PR #<n> OPEN` under
  `rule: in-flight`, is no longer written for a landed PR.
- **The Feature's delivery row** — the next Task's `WAITS ON <landed task>` row goes the same pass,
  because `occupancy` releases the item (`landed[item]` set, the branch dead) instead of holding it
  until the next evidence pass.
- **No new file, no new state file, no new command, no new convention, no new event kind.**
  `cache-prs.json` keeps its shape and its writer; `landed` is an argument, never a field in it.
- **No new `gh` call.** Two `git log` reads on a repo each pass already has: one hoisted inside
  `facts()` (P14 — the same read, earlier), one added in the wave step, bounded by
  `TRUNK_LANDED_DAYS`.
- **What is no longer written** — the 40-minute window in which the record says a landed Task is
  in flight and the lane says its item is busy, while the trunk carries the merge and the host has
  already marked the PR merged.
