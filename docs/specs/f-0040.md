# F-0040 — the claim, the refusal, and the tick

A Story card is required to carry an acceptance list: `asf check` fails a Story without one
(`asf/record/check.py:155`, `ACCEPTANCE_ITEM_RE` at `:15`). Nothing in the factory ever ticks a
box on that list. Every Story acceptance line in this record is `- [ ]`, including the lines of
Stories whose Tasks are Closed and whose code has been on the trunk for weeks. The state the
board shows for a Story comes from its Tasks' branches and merges (`asf/record/ingest.py:293`),
which says *a Task finished*, never *the criterion it existed for is now proven*.

That is the criteria-have-evidence gate with its evidence half missing. A Task lands green — the
gate ran the product's whole test command — and no row anywhere records *which test* turned
*which acceptance line* from a hope into a fact. The verdict is real; the evidence for the
specific claim is an opinion.

This spec adds the missing half as one short claim a builder writes, one refusal that will not
land a Task without it, and one pass that turns the claim into a tick:

```
Proves: S-1234 line 2 — tests/test_count.py::test_tabs
```

Written as a git trailer on the Task's commits, lifted into the pull-request body by the tick's
`prs` step, refused at the landing by `harvest.lane_refusal` before either merge lane sees the
branch, and read back by `asf ingest`, which ticks line 2 of S-1234's `## Acceptance` and writes
one History line naming the Task, the test and the sha.

This changes code under `asf/`, `tests/`, one brief template and one new file under `rules/`. It
mints one rule card in the record, through `asf new rule` — never by an id written here.

## 1. Decisions

### 1.1 In

- **`asf/proves.py`** — a new top-level module: the claim grammar, the parser, the validator, the
  acceptance-bullet reader and the idempotent tick. Pure functions over text, with git injected
  as a callable where a branch must be read (§2.1).
- **The carrier is a commit trailer** (D1): `Proves: <S-id> line <n> — <test path>` on the Task's
  own commits. The pull-request body carries the same lines, put there by the tick, not typed by
  the session (§2.4).
- **The coder brief asks for it by name** (§2.3): `templates/coder.md` gains the requirement,
  `build.context` gains `{proves}` — the Task's Stories with their acceptance bullets *numbered*,
  so the builder never has to count them — and the common `REPORT` block gains a `proves:` line
  in the shape the adjudicate-only fields already use.
- **The refusal** (§2.5): `harvest.lane_refusal` gains a third kind, `proves`. It sits at
  `asf/harvest/harvest.py:1297`, above both merge lanes — a claimless Task branch is never marked
  `harvest: pr` for the merge queue and never fast-forwarded onto the trunk. It is handed back to
  its session as a correction, exactly as the `merge` and `naming` refusals are.
- **The evidence** (§2.6): `evidence.discover` gains `proves` — the claims that have *landed*,
  from merged pull-request bodies and from `Proves:` trailers on the trunk.
- **The tick** (§2.7): `asf ingest` turns `- [ ]` into `- [x]` on the claimed acceptance line of
  the claimed Story, and writes one `## History` line per newly proven line.
- **The rule and its check** (§2.8): `asf proves check` and the shipped script
  `rules/story-proof.sh`, reporting every landed Task whose Stories are still unproven. The rule
  card is minted with `asf new rule` when the work lands (D9), not named here.

### 1.2 Out

- **Running the test.** The claim names a test; the gate that runs it is the product's test
  command, which already ran over the whole branch before it landed
  (`asf/harvest/harvest.py:416`). This card proves *which line* the green run bought. A per-claim
  test invocation is a second test run for every landing, and is not this card (D6).
- **A convention key to switch it off.** On by default, no yaml (D8).
- **Un-ticking.** Nothing this card writes ever turns `- [x]` back into `- [ ]` (D7).
- **The Feature's and the Bug's acceptance lists.** A Bug carries a signature, not Stories; a
  Feature's acceptance is the sum of its Stories'. The claim names a Story and only a Story.
- **A Task with no `stories:`.** It is not refused at the landing — the coder cannot fix a Task
  card that is outside its footprint. It is the plan's defect, and the rule check reports it
  (D5).
- **Reviews.** Whether a reviewer must check the claim is F-0053's subject (machine-readable
  reviews). Here the claim is checked by the landing and by the rule, both mechanical.

### 1.3 Preconditions

- The record's Story cards carry an `## Acceptance` list, which `asf check` already requires
  (`asf/record/check.py:155`). A Story whose list is empty can be claimed against by no line
  number, and its Task's branch is refused until the Story is fixed — which is the correct
  outcome and is why that check exists.
- The Task card carries `stories:` — the plan mints it that way, and `asf check` already fails a
  building Feature whose Story no Task lists (`asf/record/check.py:193`).
- `run_product_harvest` has the record's index (`items`) and the product's `backlog_dir`. It has
  both today: `items` is a parameter the tick fills, `backlog_dir` is a field of the product in
  hand. **Without `items` there is no refusal** (D4) — a missing index must never stop every
  landing in the factory.
- **The one-time cost.** Coder sessions that are in flight when this lands were briefed before
  the requirement existed. Their branches are refused once, with a correction naming the exact
  trailer to write; `git commit --amend --trailer` or one empty commit clears it. That is one
  correction round per in-flight Task, paid once, and it is the mechanism working, not a
  regression. The brief change (S-18751) and the refusal (S-18752) must land in that order.

### 1.4 The choices

| # | Question | Chosen | Against | Why |
| --- | --- | --- | --- | --- |
| D1 | Where the builder writes the claim | A `Proves:` git trailer on the Task's commits; the tick lifts it into the pull-request body | The coder writing the pull-request body itself | **A coder may never open a pull request** — it is one of the six standing rules in every brief (`asf/briefs/preamble.py:39`), and the `prs` step opens it after the session has ended. The only text a builder controls is its commit messages. A design that asks for a claim in a body the builder cannot write is a gate that can only be failed |
| D2 | What `line <n>` counts | The nth bullet of the card's `## Acceptance` list, 1-based | The line number in the card file | A file line moves when a History line is appended, and ingest appends History on nearly every pass. The bullet ordinal is stable under everything but an edit to the acceptance list itself — and an edit to the acceptance list *should* invalidate a claim against it |
| D3 | How strict the validator is | Every claim on the branch must resolve, and there must be at least one | One good claim is enough; the rest are warnings | A malformed claim is a typo whose cost is silence: the line it meant to tick stays open and nobody looks again. The session that wrote it is the cheapest place to fix it, and it is still running when the refusal lands |
| D4 | What happens when the record is unreadable | No refusal; the rule check is the backstop | Refuse, fail closed | This is the opposite of the approvals hook's fail-closed rule (`asf/approvals.py`, D7 there) and deliberately so: that hook governs *one tool call*, this gate governs *every landing in the factory*. A missing `index.json` that stopped all landings would be an outage; a missing `index.json` that stops the tick is one the operator already sees |
| D5 | A Task that lists no Story | Not refused at the landing; reported by the rule check against the Task | Refused like any other | The Task card is not in the coder's `writes:`, so the correction would ask a session for something it is forbidden to do — a refusal loop that can only end in the round cap. A Task with no Story to prove is a defect of the plan that minted it, and belongs in the rule's violation list where the Bug filer can see it |
| D6 | Whether the claim's test is run | No — only resolved as a path in the branch's tree | Run the named test, per claim, at the gate | The branch's whole test command already ran green in the harvest worktree; running one node of it again proves nothing new and doubles the gate for every Task. What the gate *can* cheaply add is that the path is real — which is the whole of the "a test nobody can run is not acceptance" failure mode |
| D7 | Whether a tick can be reversed | Never. `- [ ]` → `- [x]` only, once, and an already-ticked line is left alone | Re-derive the whole acceptance list from current evidence each pass | Every other ingest field is derived and so reversible; this one is a *historical* fact — a test proved a line at a sha. Withdrawing the claim later does not un-prove it. Deriving it afresh would also mean an acceptance list that silently un-ticks when an old pull request scrolls out of the 300-PR window |
| D8 | Whether a product can switch the gate off | No key; on for every product | `conventions.proves_required: true` | F-0024 already ruled on this shape (`docs/specs/f-0024.md:105`): "An empty default is why the F-0031 gate has never fired." A gate an operator must switch on is a gate nobody switches on. The rule card carries `enforced:`, which is the honest switch the factory already has |
| D9 | Where the rule lives | The check script ships here (`rules/story-proof.sh`); the rule card is minted into the record with `asf new rule` when the work lands | Writing an `R-nnnn` id into this spec | The precedent is F-0023's D10 (`docs/specs/f-0023.md:157`): an id is never invented in a document and a ruling is never a commit in this repo. What this repo ships is the mechanism and its check |
| D10 | Where the parser lives | `asf/proves.py`, a new top-level module | `asf/record/`, `asf/evidence/`, `asf/harvest/` | Four callers in three packages read it — harvest, the tick's `prs` step, evidence and the CLI. Under any one of them it would be an upward import from the other three. Top-level and pure is `asf/approvals.py`'s and `asf/redact.py`'s shape |
| D11 | How the module reaches git | Not at all: a `git` callable is injected where a branch must be read | `subprocess` inside the module | `asf/harvest/pr_hygiene.py:134` (`branch_verdict(branch, git=None, …)`) is the pattern this repo already uses, and it is what makes the branch-reading half testable without a fixture repo in the unit test |
| D12 | The dash in the grammar | `-`, `–` or `—`, any of them, with surrounding space optional | An em dash, exactly | A refusal for typing a hyphen is a refusal that teaches nothing. The parts that carry meaning — the id, the number, the path — are strict |

## 2. The design

### 2.1 The claim and its parser — `asf/proves.py`

```python
#: A claim, as written on a commit or in a pull-request body. The id shape is the record's own
#: (any prefix, four digits) — which prefix means Story is the record's to say, not this
#: module's: `validate` resolves the id and rejects anything that is not a Story.
CLAIM_RE = re.compile(
    r'^[ \t>*-]*Proves:[ \t]*(?P<story>[A-Za-z]+-\d{4})[ \t]+line[ \t]+(?P<line>\d+)'
    r'[ \t]*[-–—]+[ \t]*(?P<test>\S.*?)[ \t]*$', re.M | re.I)


@dataclasses.dataclass(frozen=True)
class Claim:
    story: str      # upper-cased
    line: int       # 1-based, the nth bullet of the Story's ## Acceptance
    test: str       # as written: a path, optionally `path::node`
    raw: str        # the line as found, for the refusal text


def parse(text):
    """Every claim in ``text``, in first-seen order, duplicates collapsed."""


def bullets(body):
    """The ``## Acceptance`` bullets of a card body, in order — what ``line <n>`` counts (D2).
    The same bullet shape ``asf.record.check.ACCEPTANCE_ITEM_RE`` requires of a Story, and the
    same one ``asf.tick.step_prs.acceptance`` reads."""


def card_bullets(root, item):
    """:func:`bullets` of the card ``root/<folder>/<id>.md`` names; ``[]`` when it is unreadable.
    ``item`` is an index entry — the ``folder``/``id`` pair ``step_prs.card_relpath`` uses."""


def validate(claims, task, items, root, tree=None):
    """``(good, problems)`` for one Task's claims. ``problems`` are one-line strings naming the
    claim and what is wrong with it, in the order found:

    * ``no claim``          — ``claims`` is empty
    * ``unknown story``     — the id is not in ``items``, or is not a Story
    * ``not this Task's``   — the Story is not in the Task's ``stories:``
    * ``no such line``      — ``n`` is outside ``1..len(card_bullets(...))``
    * ``no such test``      — ``tree`` is given and the path before ``::`` is not in it

    ``good`` is the claims with no problem; a Task passes the gate when ``problems`` is empty
    and ``good`` is non-empty (D3)."""


def claims_on_branch(git, trunk, branch):
    """The claims on ``origin/<branch>`` above ``origin/<trunk>``, read with the injected ``git``
    callable (D11): one ``git log --format=%B`` over that range, parsed."""


def tick(body, line_no, note):
    """``(new_body, changed)`` — flip the ``line_no``-th ``## Acceptance`` bullet from ``- [ ]``
    to ``- [x]`` and leave every other character of the body alone. ``changed`` is False when the
    bullet does not exist or is already ticked: the tick is idempotent and never reverses (D7).
    ``note`` is the text the caller appends to ``## History``; this function does not write it."""


def render(claims):
    """The ``## Proves`` block a pull-request body carries — one bullet per claim, the same text
    the trailer had."""
```

No `subprocess`, no `os` beyond reading a card path, no product convention: the branch-reading
half takes the `git` callable its caller already has (D11).

### 2.2 The grammar, written where a human reads it

One line, anywhere in a commit message, conventionally as a trailer:

```
fix(T-0123): the parser reads a Proves trailer

Proves: S-18750 line 1 — tests/test_proves.py::ParseTests::test_trailer
Proves: S-18750 line 3 — tests/test_proves.py::ParseTests::test_duplicates_collapse

Signed-off-by: …
```

A Task may prove several lines, of several of its Stories, across several commits: the claims of
the whole branch are one set (`claims_on_branch`).

### 2.3 The brief asks for it — `templates/coder.md`, `build.py`

`asf/briefs/build.py:242` (`context`) gains one key:

```python
'proves': facts['proves_lines'] or '(this Task lists no Story — say so in the report)',
```

and `asf/briefs/preamble.py:249` (`collect`) gains the fact behind it — for each id in the
Task's `stories:`, the Story's acceptance bullets, numbered:

```
S-18750 the claim and its parser: 1 `tests/test_proves.py::ParseTests` passes;
        2 a malformed claim is a problem, not a silent skip
```

The builder never counts bullets itself, which is the whole reason the preamble exists
(`asf/briefs/preamble.py:1-20`: the facts are generated, never discovered).

`templates/coder.md` gains one paragraph, before `Final message:`:

```markdown
PROVES — the acceptance lines your tests tick: {proves}
Before the push, every line above that your tests now prove carries a trailer on its own line in
one of your commit messages:

    Proves: <S-id> line <n> — <the test path that proves it>

`<n>` is the number above, not a line of the card file. The test path must exist on this branch.
A Task that proves nothing is refused at the landing and handed straight back to you, so write
the trailer with the commit, not after it.
```

and the common `TAIL` (`asf/briefs/build.py:63`) gains one `REPORT` field, in the shape the
adjudicate-only fields already use:

```
proves: <code only — the Proves: trailers you wrote, one per line; or none — <why>>
```

### 2.4 The pull request carries it — `asf/tick/step_prs.py`

`title_and_body` (`asf/tick/step_prs.py:158`) gains the block between the card's acceptance
checkboxes and the closing line:

```markdown
Card: [T-0123](…)

## Acceptance
- [ ] the parser reads a Proves trailer

## Proves
- S-18750 line 1 — tests/test_proves.py::ParseTests::test_trailer

Opened by the tick from `worker/T-0123`.
```

built from `proves.claims_on_branch(git, product.main, branch)` with the step's own `_git`
(`asf/tick/step_prs.py:45`). A branch with no claim still gets its pull request opened — the
refusal is harvest's, in one place (§2.5), and a pull request nobody opened is a Task nobody can
correct. The block is simply absent, and its absence is what the reviewer and the rule see.

This is the half the card names literally: *the pull-request body carries `Proves: …` for every
acceptance line its tests prove.* It is generated from the branch rather than typed, because of
D1.

### 2.5 The refusal — `asf/harvest/harvest.py`

`lane_refusal` (`asf/harvest/harvest.py:800`) gains its third kind. The signature grows by three
optional arguments the one call site (`:1297`) already has in hand:

```python
def lane_refusal(repo, trunk, branch, item, conv=None, items=None, root=None):
    """… and a Task branch that proves nothing: a lane branch may not land unless its commits
    name the acceptance line its tests tick (F-0040). Skipped — never refused — when ``items``
    or ``root`` is missing, when the item is not a Task, or when the Task lists no Story (D4,
    D5): the rule check is the backstop for both."""
```

After the `merge` and `naming` checks:

```python
card = (items or {}).get(item) or {}
if not (root and card.get('type') == 'task' and card.get('stories')):
    return None
claims = proves.claims_on_branch(lambda *a: sh(['git', *a], cwd=repo).stdout, trunk, branch)
tree = sh(['git', 'ls-tree', '-r', '--name-only', f'origin/{branch}'], cwd=repo).stdout.split()
good, problems = proves.validate(claims, card, items, root, tree)
if problems:
    return 'proves', (…)
```

and the call site passes what it has:

```python
refusal = lane_refusal(repo, trunk, branch, item, conv, items, product.backlog_dir)
```

The refusal text is a correction, not a verdict — it names the Story, its numbered bullets and
the exact trailer to write:

```
no acceptance line proved: this Task lists S-18750, whose acceptance is
  1 `tests/test_proves.py::ParseTests` passes
  2 a malformed claim is a problem, not a silent skip
add a trailer to one of your commits naming the line your tests prove, e.g.
  Proves: S-18750 line 1 — tests/test_proves.py::ParseTests::test_trailer
then push; the factory publishes the rewritten branch
```

Because `lane_refusal` runs at `:1297` — above the approvals class, above `mark_session(harvest=
'pr')` at `:1313` and above `land_ff`/`land_combined` at `:1320` — **both** merge lanes refuse
it. A product whose `landing` is `pull-request` never has the branch handed to its merge queue
(`asf/harvest/harvest.py:616`); a product whose landing is fast-forward never has it pushed to
the trunk. That is the card's "the merge queue refuses it", in the one place where this factory
decides a landing.

### 2.6 The evidence — `asf/evidence/evidence.py`

`discover` (`asf/evidence/evidence.py:386`) gains one key, `proves`, holding only claims that
have **landed**:

```json
"proves": {
  "S-18750": [
    {"line": 1, "test": "tests/test_proves.py::ParseTests::test_trailer",
     "task": "T-0123", "pr": 412, "sha": "9f1c2ab…", "source": "pr"},
    {"line": 3, "test": "tests/test_proves.py::TickTests",
     "task": "T-0124", "pr": null, "sha": "0b77de4…", "source": "commit"}
  ]
}
```

Two sources, both already fetched or one cheap call away:

1. **Merged pull requests.** `pr_list` already asks `gh` for `body`
   (`asf/evidence/evidence.py:192-194`); a PR whose `state` is `MERGED` and whose
   `mergeCommit.oid` is an ancestor of the trunk contributes its body's claims. `task` is the
   Task id among the PR's id tokens (`id_tokens`, `:768`).
2. **Trailers on the trunk.** One `git log --format=%H%x1e%B --grep=^Proves: origin/<main>`,
   bounded by the same `--since=record_since(product)` window `main_commits` uses
   (`asf/evidence/evidence.py:726`). `task` is the id token in the commit's subject — which
   `commits_name_item` (`asf/harvest/harvest.py:669`) guarantees every landed lane commit has.

The second source is what makes the tick work for a product that lands by fast-forward and has
no pull requests at all — this one.

### 2.7 The tick — `asf/record/ingest.py`

After the state passes and before `do_index`, `cmd_ingest` (`asf/record/ingest.py:221`) runs one
pass over the Story cards:

```python
for iid, rec in canonical.items():
    if rec['meta'].get('type') != 'story':
        continue
    for claim in (ev.get('proves') or {}).get(iid) or []:
        body, changed = proves.tick(body, claim['line'], …)
```

One read, one `frontmatter.render` write per Story that changed — the same body-writing shape the
History append already uses at `asf/record/ingest.py:163`. For every line newly ticked, one
History line:

```markdown
## Acceptance
- [x] `tests/test_proves.py::ParseTests` passes
- [ ] a malformed claim is a problem, not a silent skip

## History
- 2026-09-24 12:30 ingest: proved line 1 — T-0123, PR #412 (tests/test_proves.py::ParseTests::test_trailer)
```

Idempotent by construction (D7): a bullet already `- [x]` is left alone and writes no History
line, so a second ingest in the same minute changes nothing. A claim whose line does not exist —
because the Story's acceptance list was rewritten after the Task landed — ticks nothing and is
what the rule check reports.

### 2.8 The rule and its check

```
asf proves check [--product P] [--json]
```

One violation line per landed Task whose Stories are not proven, in the `<what> <where> <since>`
shape `asf/rules/rules.py:9` expects (the rule id is prefixed by the runner, so the script
never carries one):

```
task landed proving nothing T-0123 (S-18750) since 2026-09-20
claim names a line S-18750 has no more S-18750 line 7 (T-0124) since 2026-09-22
task lists no story T-0125 since 2026-09-21
```

Exit 1 with violations, 0 without — the contract `run_check` reads
(`asf/rules/rules.py:131-142`). `asf file-bugs` turns the lines into a Bug as it does for every
other rule (`asf/tick/file_bugs.py:145`), which is how a landing that slipped through a merge
queue comes back as work.

The shipped script, `rules/story-proof.sh` — the core rules directory `asf/rules/rules.py:43`
and `asf/hooks.py:38` both already name:

```bash
#!/usr/bin/env bash
# F-0040 — every landed Task ticks the acceptance line its tests prove.
exec asf proves check --product "${ASF_PRODUCT:?}"
```

The rule card itself is minted into the record when the work lands (D9), never by an id written
here:

```bash
asf new rule --title "A Task's landing ticks the Story acceptance line its tests prove" \
  --set check=rules/story-proof.sh --set scope=product --set enforced=true
```

`asf proves show <T-id>` prints one Task's claims and their problems — the same `validate`
output the refusal prints, available before the push.

## 3. Acceptance tests

Each block runs from the repository root.

### 3.1 The parser, the validator, the tick

```bash
python3 -m unittest -v tests.test_proves
```

Covers: the trailer parsed off a commit message with a `Signed-off-by:` after it; a claim in a
pull-request body under a `## Proves` bullet; all three dashes and no dash (D12); duplicates
collapsed in first-seen order; a line that says `Proves` but names no id, no line or no test
parsed as nothing; `bullets()` over a card body with `- [ ]`, `- [x]` and a non-acceptance
section between them; `card_bullets` returning `[]` for an unreadable path; each of `validate`'s
five problem kinds by name, and a Task with one good claim and one malformed one rejected (D3);
`tick` flipping exactly the nth bullet and leaving the rest of the body byte-identical, twice in
a row with the second a no-op (D7), and on a line that does not exist; `claims_on_branch` with a
stub `git` callable, asserting the one `git log` range it asks for.

### 3.2 The brief

```bash
python3 -m unittest -v tests.test_briefs
```

Covers: `{proves}` rendered for a Task whose two Stories have three acceptance bullets between
them, numbered 1-based per Story; a Task with no `stories:` rendering the stated fallback rather
than an empty string; `templates/coder.md` naming `Proves:` and the `REPORT` block carrying
`proves:` — with the existing test that every placeholder in every template is a key of
`context` still passing, which is what makes a typo here a red test instead of a brief that ships
`{proves}` literally (`asf/briefs/build.py:158`).

### 3.3 The refusal

```bash
python3 -m unittest -v tests.test_harvest
```

Over the git fixture (`tests/gitfixture.py`), a new `ProvesRefusalTests`: a Task branch whose
commits carry no trailer is refused with kind `proves` and never reaches `land_ff` or the
`harvest: pr` mark; the correction text names the Story and its numbered bullets; the same branch
with a valid trailer lands; a claim naming a Story the Task does not list, a line past the end of
the list, and a test path not in the branch's tree are each refused with their own reason; a
branch whose item is a Bug, a branch whose Task lists no Story (D5), and a call with `items=None`
(D4) are each *not* refused; and the two existing refusals (`merge`, `naming`) still fire first.

### 3.4 The pull-request body

```bash
python3 -m unittest -v tests.test_tick_steps
```

Covers: `title_and_body` carrying a `## Proves` block with one bullet per claim on the branch,
below the card's `## Acceptance` checkboxes; the block absent, with no stray heading, when the
branch has no claim; and the `gh pr create` argv unchanged otherwise.

### 3.5 The evidence

```bash
python3 -m unittest -v tests.test_evidence
```

Covers: `discover()['proves']` keyed by Story id, from a merged pull request's body and from a
`Proves:` trailer on a trunk commit; an **open** pull request's claim absent (a claim is not

## 4. Records

**On the branch, by the builder** — one `Proves: <S-id> line <n> — <test path>` trailer per
proven line, in the commit that proves it. Nothing else is asked of the session, and its
`REPORT` repeats them under `proves:`.

**In the pull request, by the tick** — a `## Proves` block in the body `step_prs` opens, one
bullet per claim (§2.4).

**In the session ledger, on a refusal** — the existing `correction` field and round counter of
`asf.workers.lifecycle.hold` (`asf/workers/lifecycle.py:626`), with `kind: proves`. No new state
file, no new ledger field.

**In the record, by ingest** — on the Story card: the claimed `## Acceptance` bullet turned
`- [x]`, and one `## History` line per newly proven line:

```
- 2026-09-24 12:30 ingest: proved line 1 — T-0123, PR #412 (tests/test_proves.py::ParseTests::test_trailer)
```

**In the record, by the groom** — one Bug per standing violation, through the existing
`asf file-bugs` path (`asf/tick/file_bugs.py:145`). No new filing mechanism.

**In the record, once, by hand** — the rule card, minted with the `asf new rule` command of §2.8
when this lands. Its id comes from `asf new`, never from this document.

**Not written.** No new machine-block key on the Story — the tick is the visible record and the
History line is its detail. No new metrics stream: how many acceptance lines are proven is a
count over the record, which the PARITY table already reads. No new convention key (D8). No
change to what the gate runs, to `index.json`'s shape, or to any card's typed fields.

## Stories

- S: The claim and its parser — `asf/proves.py` reads `Proves: <S-id> line <n> — <test>` off any text, counts acceptance bullets, validates a Task's claims against the record, and ticks a bullet idempotently — acceptance: `python3 -m unittest -v tests.test_proves`
- S: The coder brief requires the trailer — the template names it, `{proves}` numbers the Task's Story acceptance lines, and the REPORT block carries `proves:` — acceptance: `python3 -m unittest -v tests.test_briefs`
