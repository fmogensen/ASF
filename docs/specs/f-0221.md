# F-0221 — a row that fires on a healthy factory is not a signal

The `Stale` row is the first row of `asf status` (`asf/views/status.py:520`) and the one an
operator reads before any other: it is the row that says *do not trust the numbers below me*. On
2026-09-27 it fired on healthy ticks all day.

Its fallback clause (`asf/views/status.py:221-245`) is:

```python
age_s = (datetime.datetime.now(datetime.timezone.utc) - when).total_seconds()
if age_s <= 2 * _record_period_s(product):
    return None
return f"STALE since {ix.local_stamp(generated, '%H:%M')} — no fresh record in {ix.span(age_s)}"
```

`when` is `index.json`'s `generated` in the operator's checkout, and `_record_period_s`
(`:211-218`) is the record clock's `every:` — 5m, so the threshold is 10 minutes. Both halves of
that comparison are wrong about the thing they are measuring.

**The numerator measures more than the record's age.** `generated` is stamped early in the tick,
at `[record:index]`. It reaches the operator's checkout only at the tick's very end: `finish`
commits and pushes the record clone and *then* calls `shadow.sync_operator_checkout`
(`asf/tick/tick.py:236-237`), after every step including `harvest`. So at the moment `asf status`
runs, the freshest `generated` the checkout can possibly hold is the one tick N stamped at its
start, and its visible age is

```
(the rest of tick N after [record:index])  +  (the idle before tick N+1)  +  (tick N+1 so far)
```

**The denominator measures only the idle.** `2 × 5m` budgets two clock periods and nothing for
the tick itself. The middle term of that sum is already 5 minutes of `StartInterval`, so the
budget is spent before the tick has run a single step. Any tick longer than about 5 minutes trips
the row.

The day's own stretches, from `metrics/ticks/2026-09-27.jsonl` on the operator's host:

| stretch | length | what it was |
|---|---|---|
| 13:10 | 13.3m | a healthy tick |
| 14:01 | 12.4m | a healthy tick |
| 22:56 | 29.6m | a healthy tick |
| 23:18 | — | `tick: waiting — upgrade to 2a02de5 pending` |

Four STALE rows, four healthy states. And the last is worse than a false positive: the factory was
deliberately parked while an upgrade drained the running ticks (`asf/upgrade.py:23-27`, B-0141),
and the row that exists to say *why the table is old* said the one thing that was not true. The
`Cron` row knew — `cron_cell` (`asf/views/status.py:413-416`) already prefixes
`upgrade.held_label(marker)` for exactly this case — while the row above it called it a stall.

A row that fires on nearly every tick is read as noise, and then the one real stall is read as
noise too. This Feature makes the threshold measure the cadence the tick actually has, reads "a
tick finished a record" from the record the tick writes about itself, and lets an upgrade hold
name itself.

## Decisions

**In scope**

- The threshold becomes `2 × (the record clock's interval + the last record tick's own
  `duration_s`)`, read from `metrics/ticks`.
- "A tick finished a record" is read from the `metrics/ticks` line of a tick whose `record` step
  ran and landed — the stamp written at the tick's *end* — and not from `index.json`'s
  `generated` alone.
- While an upgrade marker holds this product's ticks, the row names the hold
  (`upgrade.held_label`) instead of saying STALE.
- STALE remains for the case it was built for: no tick finished a record inside that window.
- A test case beside the existing ones in `tests/test_tick.py`, and a replay of the 2026-09-27
  day as a fixture.

**Out of scope**

- `record_health.line` and its first clause (B-0124). A record step that *failed* already has its
  own local stamp, its own text (`record failed: <reason> (<n> ticks)`) and its own tests
  (`tests/test_tick.py:378-420`); it stays first and is not touched. This Feature changes only
  the fallback that runs when the record step is not reporting a failure.
- The `Cron` row. It already names a pending upgrade (B-0141) and keeps doing so, unchanged; this
  Feature does not move that clause or share code with it beyond calling the same two public
  functions, `upgrade.held` and `upgrade.held_label`.
- Every other row of `asf status`, and `asf doctor`'s SCHEDULER section.
- The tick's own timing, the clocks block, `StartInterval`, and the shape of `metrics/ticks`. No
  new field is written anywhere: every number this row now reads is already on disk.
- Making the tick faster, or splitting `record` off the clock that also runs `harvest`. The row's
  job is to describe the cadence the operator has, not to have an opinion about it.
- A cap on the threshold (see D6).

**Preconditions**

- Every tick appends one line to `metrics/ticks/<day>.jsonl` in the record clone
  (`asf/tick/tick.py:634-646`), carrying `ts` (stamped at `tick_line` time, i.e. the tick's end),
  `duration_s` (`round(sum(r['seconds'] for r in ran), 1)`), `product`, and `steps` — a list of
  `{'step', 'ok', 'seconds'}` (`asf/tick/tick.py:479`).
- That file is in the record repo, so it travels in the same push as `index.json` and arrives in
  the operator's checkout through the same `shadow.sync_operator_checkout` call
  (`asf/tick/tick.py:237`). The row therefore never needs a signal `index.json` does not already
  have — only a better-stamped one.
- `duration_s` is nullable in the stream's schema (`asf/metrics/metrics.py:135`:
  `('num', 'null')`), so the reader must treat a missing or `None` duration as "no measurement".
- `upgrade.held(product_name)` (`asf/upgrade.py:208-231`) is the read-only "is this product's
  tick parked" question: it already drops a dead operator's wait, a future `at` and an expired
  TTL, and it already returns `None` for the marker's *owner*, whose ticks go on by design.
  `upgrade.held_label(data)` (`:233`) is its sentence.
- `_record_period_s` (`asf/views/status.py:211`) already falls back to
  `DEFAULT_RECORD_CLOCK_S = 300` for a product with no clocks, an unreadable clocks block, or a
  record clock on `at:` rather than `every:`. Unchanged.
- `render` wraps every cell in `try/except` (`asf/views/status.py:543-545`), so a row that raises
  costs its own cell and not the table. This is a safety net, not a licence: the new reader
  catches its own `OSError`/`ValueError` and returns `None`.

**Choices**

| # | Choice | Against | Why |
|---|---|---|---|
| D1 | The threshold is `2 × (interval + last record tick's `duration_s`)` | Keep `2 × interval`, but raise the constant to 3× or 4× | A constant multiple is a guess at the tick's length, and the tick's length is *measured and written down every time it runs*. The day's stretches run 12m to 30m; any constant that covers 30m calls a 10-minute stall healthy, and any constant that catches a 10-minute stall fires on the 30-minute tick. The formula tracks whatever cadence the product actually has, including one that changes when its clocks block does. |
| D2 | The freshness signal is the newest `metrics/ticks` line whose `steps` carry a landed `record`, falling back to `index.json`'s `generated` | Keep `generated` as the only signal | `generated` is stamped at `[record:index]` and read at the tick's end, so its age carries the whole of tick N as dead weight before the clock has ticked once (the numerator problem above). The tick line's `ts` is stamped at the tick's end — the same moment the operator's checkout is synced — so it measures the idle and nothing else. `generated` stays as the fallback because it is the signal that exists when `metrics/ticks` cannot be read, and because the row must still work on a checkout that has one but not the other. The row takes whichever of the two is fresher, never the older. |
| D3 | A tick counts as "finished a record" only when its `steps` carry an entry `{'step': 'record', 'ok': True}` | Count any tick line | A `dispatch`-clock tick that runs `health, groom, wave, prs, harvest, batch` (`docs/products.example.yaml:393-395`) finishes no record and refreshes no `index.json`; counting it would let a product whose record clock is dead read as fresh forever off its other clock. A tick whose record step *failed* is likewise not a finished record — and `record_health.line`, the first clause, is the row that speaks for that case. |
| D4 | The duration term comes from that same line | Average the last N durations; or take the maximum of the day | The tick that will run next is the one most like the tick that just ran. A mean lags a product whose cadence just changed (a new clocks block, a repo that grew), and a daily maximum lets one pathological tick silence the row for the rest of the day. One line, and the reader is a single `max()` over at most two small files. |
| D5 | No tick line readable, or `duration_s` absent/`None`/negative → the duration term is `0`, i.e. exactly today's `2 × interval` | Invent a default duration; or return no row when the metrics cannot be read | With a zero duration term the formula *is* the current expression, so a checkout without `metrics/ticks` — a fresh clone, a product whose first tick has not landed, a day file that is corrupt — keeps today's behaviour and today's tests, and no case gets quietly less protection than it has now. Returning no row would be worse than the bug: an unreadable metrics directory would silence the stall detector altogether. |
| D6 | No upper cap on the threshold | Cap it at, say, 30 minutes | A cap reintroduces the exact false positive this Feature removes, for the exact product that suffers it worst: the 29.6m tick would be called stale by a 30-minute cap. A slow factory's stall genuinely does take longer to be certain about — with a 30-minute tick, two clock periods and two ticks is ~70 minutes, and a row that fired sooner would be guessing. The row that catches a *fast* failure is `record_health.line`, which fires on the first failed record step regardless of any duration. |
| D7 | The hold is tested with `upgrade.held(product.name)` — so the marker's owner is not held | Read the marker directly with `read_pending` | The owner's ticks go on: the owner is the product that drains and installs the upgrade (`asf/upgrade.py:212-215`). If its record really has gone quiet, that is a stall and must read as one. This is the same reasoning, and the same function call, that `cron_cell` settled on for B-0141; two rows disagreeing about whether a product is parked would be its own defect. |
| D8 | The hold replaces the row's text only when the age has already crossed the threshold | Name the hold whenever a marker is pending | `Stale` is a row that says nothing at all when nothing is wrong (`render` drops a `None` cell, `asf/views/status.py:546`). A held product whose last record is still fresh has nothing wrong with its record, and the `Cron` row already names the hold for the operator who wants to know why nothing is starting. The hold speaks in this row only in the moment it would otherwise have lied. |
| D9 | The text is `<held_label> — no fresh record in <span>` | `HELD — …`; or `upgrade.held_label` alone | The card asks for `upgrade.held_label` instead of STALE, and `held_label` already opens with `waiting on upgrade to <sha7> since <HH:MM> (owner <p>)` — a sentence that cannot be misread as a stall and needs no prefix invented for it. The age clause stays because the age is this row's subject: the operator still wants to know how old the table below is, and now learns that the reason is a parked factory rather than a broken one. |
| D10 | `since` in the STALE text names whichever signal was freshest | Keep naming `generated` always | The sentence is `STALE since <time> — no fresh record in <span>`, and `<span>` is now computed from the freshest signal. Naming a different, older timestamp in the same sentence would make the two halves contradict each other. |
| D11 | The reader reads the newest two day files, not the whole stream | `metrics.read_stream(root, 'ticks')` | `read_stream` globs and parses every day the record has ever held — for one row, on every `asf status`, to answer a question about the last few minutes. Two files cover the only edge that matters, a tick just after midnight whose predecessor is in yesterday's file. |
| D12 | The 2026-09-27 replay is a fixture built from the stretches above, not the operator's raw file | Commit `metrics/ticks/2026-09-27.jsonl` as it stands on the host | The operator's day file is on a host this branch cannot read, and the standing rule is that no worker account name or machine path enters the product. A fixture that carries the four stretches, their durations and the upgrade wait proves everything the replay is for, is readable by the next person, and stays green when the host is gone. Its rows are specified below so the operator can drop a scrubbed real file in its place if they prefer. |
| D13 | It stays in `asf/views/status.py` | A new module for the cadence read | One row, one reader of about fifteen lines, sitting next to the `_record_period_s` helper it pairs with. A module earns its own file when a second caller appears; `stale_cell` is the only caller. |

**The footprint this needs** (the writes the Tasks minted from these Stories will declare):
`asf/views/status.py`, `tests/test_tick.py`, `tests/fixtures/ticks/2026-09-27.jsonl`.

## The design

### 1. `asf/views/status.py` — the cadence reader (new)

Two private helpers beside `_record_period_s` (`:211`), which is unchanged.

```python
#: how many day files of ``metrics/ticks`` the Stale row reads: today's and yesterday's, so a
#: tick a few minutes after midnight still finds the tick before it (D11)
STALE_TICK_DAYS = 2


def _last_record_tick(root, product):
    """``(ts, duration_s)`` of the newest ``metrics/ticks`` line in the operator's checkout that
    says a tick *finished a record* — its ``steps`` carry a landed ``record`` entry (D3) — or
    ``None`` when no such line is readable.

    ``ts`` is stamped when the tick ends (:func:`asf.tick.tick.tick_line`), the same moment the
    push reaches this checkout (:func:`asf.tick.shadow.sync_operator_checkout`), which is why it
    is a truer "the record is this old" than ``index.json``'s ``generated`` (D2). ``duration_s``
    is that tick's own length, and is ``None`` when the line does not carry one (D5).
    """
```

Its body: glob `<root>/metrics/ticks/*.jsonl`, sort by name, keep the last `STALE_TICK_DAYS`,
parse each line, and keep those for this product — `product` equal to this product's name, or
absent/`None`, which is the stream schema's own default (`asf/metrics/metrics.py:138`) and the
shape a record repo serving one product writes. Of those, keep the ones whose `steps` hold
`{'step': 'record', 'ok': True}`, and return the one with the greatest parseable `ts`. Every
`OSError`, `ValueError` and shape surprise is caught and reads as "no line".

```python
def _stale_after_s(product, duration_s):
    """The age past which the record table is stale: twice one full cadence — the record clock's
    idle plus the tick that follows it (D1). ``duration_s`` ``None`` or negative contributes
    nothing, so a checkout with no readable cadence keeps the old ``2 x`` the clock (D5)."""
    duration = duration_s if isinstance(duration_s, (int, float)) and duration_s > 0 else 0
    return 2 * (_record_period_s(product) + duration)
```

### 2. `asf/views/status.py` — `stale_cell`

The first clause and the `index.json` guards are untouched. What changes is what the age is
measured from, what it is measured against, and what is said when it is exceeded.

```python
def stale_cell(root, product):
    """B-0124: the record step's own health first (:func:`asf.tick.record_health.line`) — ...
    [first paragraph unchanged] ...

    F-0221: the fallback then judges the tick's real cadence. The age is taken from the freshest
    thing in the checkout that says a tick finished a record — a ``metrics/ticks`` line stamped at
    a tick's end, or ``index.json``'s ``generated`` when there is none (D2) — and the threshold is
    twice one full cadence, the record clock's idle plus the last tick's measured ``duration_s``
    (D1). Past it, a pending upgrade that parks this product's ticks names itself instead of
    being called a stall (D8, D9); otherwise no tick finished a record in that window, and the row
    says STALE. ``None`` (no row) when nothing says the table is stale."""
    from asf import upgrade
    from asf.tick import record_health
    from asf.views import index_reader as ix
    line = record_health.line(product)
    if line:
        return line
    if not root or not os.path.exists(os.path.join(root, 'index.json')):
        return None
    try:
        _items, generated = ix.load(root)
    except (OSError, ValueError, KeyError):
        return None
    when = ix.parse_ts(generated)
    if when is None:
        return None

    last = _last_record_tick(root, product)
    duration_s = last[1] if last else None
    freshest, stamp = when, generated
    if last is not None:
        tick_when = ix.parse_ts(last[0])
        if tick_when is not None and tick_when > freshest:
            freshest, stamp = tick_when, last[0]        # D2: never the older of the two

    age_s = (datetime.datetime.now(datetime.timezone.utc) - freshest).total_seconds()
    if age_s <= _stale_after_s(product, duration_s):
        return None
    marker = upgrade.held(getattr(product, 'name', None))
    if marker is not None:                              # D7, D8
        return f"{upgrade.held_label(marker)} — no fresh record in {ix.span(age_s)}"
    return f"STALE since {ix.local_stamp(stamp, '%H:%M')} — no fresh record in {ix.span(age_s)}"
```

### 3. What the row reads like when it is there

A product on `record every: 5m` whose last record tick took 13.3m — the 13:10 stretch — has a
threshold of `2 × (300 + 798) = 36.6m`, and its record is at most a cadence old. **No row.** The
table below it is trusted, correctly, for the first time that day.

The same product with nothing having finished a record since 22:56, read at 00:05:

```
| Metric | Now |
|---|---|
| Stale | STALE since 22:56 — no fresh record in 1h |
```

And parked on the upgrade at 23:18, read at 23:36 — the case that read STALE on the day:

```
| Metric | Now |
|---|---|
| Stale | waiting on upgrade to 2a02de5 since 23:18 (owner asf) — no fresh record in 18m |
| ... | |
| Cron | waiting on upgrade to 2a02de5 since 23:18 (owner asf); asf.record waiting (exit 0) |
```

Two rows, one story, and neither of them the word STALE.

A product whose record step is failing is unchanged, because the first clause still owns it:

```
| Stale | STALE since 03:01 — record failed: offline (2 ticks) |
```

### 4. `tests/fixtures/ticks/2026-09-27.jsonl` — the day, replayable (new)

One line per tick, the stream's own shape (`asf/metrics/metrics.py:134-139`), carrying the four
stretches of the evidence and nothing that names a host or an account (D12). The rows the replay
needs — `ts` UTC, `duration_s` seconds, and a `steps` list whose `record` entry is `ok`:

| `ts` | `duration_s` | `steps` carry a landed `record` | the stretch it stands for |
|---|---|---|---|
| `2026-09-27T13:10:00Z` | 798.0 | yes | the 13.3m tick |
| `2026-09-27T14:01:00Z` | 744.0 | yes | the 12.4m tick |
| `2026-09-27T14:20:00Z` | 60.0 | **no** (`dispatch` steps only) | D3: finishes no record |
| `2026-09-27T22:56:00Z` | 1776.0 | yes | the 29.6m tick |
| `2026-09-27T23:18:00Z` | 1.0 | **no** (the tick exited on the hold) | the upgrade wait |

The test reads it, and for each `ts` asks the row what it would have said a realistic moment
later — the same clock arithmetic the day had — with `index.json`'s `generated` set to the tick's
*start* (`ts - duration_s`), which is where `[record:index]` stamps it.

## Records

**Rows**

| Where | What |
|---|---|
| `asf status`, `Stale` | unchanged when the record step failed: `STALE since <HH:MM> — record failed: <reason> (<n> ticks)` |
| `asf status`, `Stale` | unchanged in shape when the record really is old: `STALE since <HH:MM> — no fresh record in <span>`, now computed from the freshest of the two signals and the measured cadence |
| `asf status`, `Stale` | new: `waiting on upgrade to <sha7> since <HH:MM> (owner <product>) — no fresh record in <span>` |
| `asf status`, `Stale` | new absence: no row at all through a tick whose length is within the cadence the product has just measured — the four rows of 2026-09-27 |
| `asf status`, `Cron` | unchanged: it keeps its own `upgrade.held_label` prefix (B-0141) |

**Files**

| Path | What |
|---|---|
| `metrics/ticks/<day>.jsonl` | read only. No field is added, no line is written, no line is rewritten. The row is a new reader of a stream the tick has always written. |
| `index.json` | read only, as before; still the fallback signal, and still the only one on a checkout without metrics. |
| `~/.ASF/state/<product>/record-health.json` | untouched — the first clause's file, read through `record_health.line`. |
| `~/.ASF/state/upgrade-pending.json` | read only, through `upgrade.held`. The row never writes, clears or expires a marker; `pending` is the one that does, and it is not called here. |
| `tests/fixtures/ticks/2026-09-27.jsonl` | new. Five tick lines standing for the day's four stretches, with no host name, no account and no path (D12). |

**Events**

None. This Feature adds no event, no `NEEDS OPERATOR` line and no metric: it changes what one
read-only cell of one table says. The events that already describe the cases it reports —
`asf/upgrade.py`'s `tick: waiting — upgrade to <sha7> pending` on the held tick's own stdout, and
the record step's `RECORD STALE — offline` — are unchanged and remain the primary record.

**What is never written**

No product repository file changes. No worker account name and no machine path enters the tree:
the fixture carries UTC timestamps, durations, step names and the product's own name only, and
`bash tools/check_generic.sh` is part of the acceptance set above.
