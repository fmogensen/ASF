# F-0226 — the row that lands a document, named for what it does

A spec PR the lane sends BACK for merge conflicts comes back to a session that must **land the
approved spec as written**. The row `asf next` prints for it is

```
| Tier | Row | Item | Feature | Action |
|---|---|---|---|---|
| 2 | STARVED → SPEC | F-0092 | F-0092 | would launch spec on spec/F-0092 |
```

— measured this session against the live shape (a Feature at `spec-approved`, `spec on
spec/F-0092 (review r1 APPROVED)`, a `landing-gate` correction on `spec/F-0092`). Every word of
it says *a spec is about to be written*: the row is the same `STARVED → SPEC` a spec nobody is
moving gets, and the action is the same `would launch spec on <branch>` a fresh `CARD → SPEC`
gets. Nothing in the row says the branch already carries an approved spec, that the document is
not to be touched, or that git — not a writer — is what stopped it.

The brief the session then receives says the same thing at the top:

```
Why this session exists: STARVED → SPEC — the lane held it (landing-gate), round 1: the spec cannot land as it stands
```

`it` is the branch, unnamed. `cannot land as it stands` is true of a conflict, of a red gate, of a
branch carrying code beside its document and of a branch that is not a lane branch at all — the
one sentence covers five different refusals and distinguishes none of them. The session does the
right thing anyway, because the correction text underneath it is explicit (`Land the existing
approved spec on the trunk from spec/F-0092 … and don't rewrite it`), but the row and the Why
line are what a *reader* sees, and they read as a duplicate spec session. A product session read
them exactly that way and asked for the launch to be stopped as a duplicate (a product's F-0092,
PR #842).

The work is already correct. This card is the label: the row is named `BACK → REBASE` — the lane
state that caused it, and the git operation that answers it — the refusal's own cause is recorded
as one word when the refusal is written, and that word goes into the Action cell and into the
brief's Why line. No launch, no hold, no cap and no brief template changes.

### In

- **A row kind of its own — `BACK → REBASE`** — for the landing-gate row of P1, both documents, in
  place of `STARVED → SPEC` / `STARVED → PLAN`. `_doc_row`'s genuinely starved rows (P2) keep
  their name; the goldens do not move.
- **Every kind-keyed set the row belongs to today, extended with the new kind** so the rename
  changes what the row is *called* and nothing else: `LANE_LAUNCH_KINDS['BACK']` (P6, without
  which the row stops launching), `NEW_DOC_KINDS` (P7), `HELD_KINDS['features']` and thereby
  `BUDGET_HELD_KINDS` (P8), `CAPPED_KINDS` (P9).
- **The refusal's cause recorded as one word** — a `why` key on the `landing-gate` correction,
  from a closed vocabulary, written by both producers (P3) at the point each already knows it.
- **That word in the two places a reader looks**: the Action cell of the NEXT table, and the
  brief's Why line — which follows from the row's `reason` (P5), so the `reason` is rewritten to
  name the branch, the cause, and the fact that the document is landed, not written.
- **The prose brought into line** (P12): two guide passages that enumerate the row kinds, one
  that enumerates what `feeder.hold: features` holds, and the five docstrings that describe this
  row's path.

### Out

- **Every launch decision.** No row starts or stops launching, no cap moves, no hold is added or
  removed, no seat changes hands. P6–P9 are in scope *because* they are what keeps that true; if
  the plan finds itself changing which rows launch, it has left the card.
- **The brief template.** `brief_kind` stays `spec` / `plan`, so the session still gets
  `templates/spec.md` or `templates/plan.md` with the landing-gate correction appended (P5), and
  its job name stays `spec-<id>` / `plan-<id>`. That the template is the *write a spec* template,
  redirected only by the correction text underneath it, is a real wart — a `spec-land` /
  `plan-land` template would say the job once instead of contradicting itself — but it changes
  the job name, the `ONE_PUSH_KINDS` membership and `correction_text`'s gate, and it is a
  different card. **Recorded here so the reviewer sees it was found and left**; no id is minted
  for it by this session, which mints Story ids only.
- **The correction text itself.** `land_spec.adopt`'s sentence and `send_back`'s note keep their
  bytes; the `why` key is written *beside* the text, never parsed out of it. The card adds no
  prose-parsing anywhere — P11's `_CHECKS_RED_RE` is the precedent for a *suffix*, not for how
  the cause is obtained.
- **`why_not_as_is`'s verdict.** Which branches can land as they stand does not change: the same
  six refusals, the same order, the same sentences. Only their names are added.
- **The lane's own rebase.** `send_back` already rebases a conflicting branch itself and returns
  `'rebased'` without a session when that works (`asf/harvest/lane.py:2873-2894`); the rows this
  card labels are the ones where that did not work. Untouched.
- **`asf next`'s two goldens** (P2). They contain no landing-gate row, so they must come out
  byte-identical — that is the fence that the rename hit the right site.
- **`CONFLICT → REBASE`.** A Task's PR that no longer merges, with the `rebase` brief. Same verb,
  different job; see C2.
- **The dry-run line.** `dry_run` prints `would launch <job> <item> <row.action>` from the raw
  `action`, not the cell; it gains the new `state`/`action` words through `worker_row` (P10) and
  needs no edit.
- **Any new config key, file or event.** One kind constant, one correction key, one row field,
  four set memberships, two writers, two readers, eight prose passages.

## The design

One new kind constant, one correction key, one `Row` field, four set memberships, two writers,
two readers, eight prose passages. Five source files, two guide files, five test modules.

### 1. The vocabulary — `asf/feeder/rows.py:124`

Beside `LANDING_GATE`, the closed set of causes a landing-gate correction may name (C6), and the
sentences `why_not_as_is` already returns for each:

```python
#: the causes a :data:`LANDING_GATE` correction may name in its ``why`` — the refusal that stopped
#: the document, as one word the row and the brief print (F-0226). A correction written before
#: this vocabulary existed carries none, and the row says nothing rather than guessing (D5).
LANDING_WHY = ('conflict', 'gate red', 'more than documents', 'not a lane branch',
               'nothing past the trunk', 'lane refusal', 'not on origin')
```

and the kind itself, beside `STARVED_PLAN`:

```python
#: the landing-gate row of a spec or plan branch the lane refused (:func:`correction_rows`): the
#: branch is in lane state BACK and the answer is a rebase, not a new document. Not
#: ``STARVED → SPEC``, which is a document nobody is writing (F-0226).
BACK_REBASE = 'BACK → REBASE'
```

### 2. The producers name the cause — `asf/tick/land_spec.py`, `asf/harvest/lane.py`

The suffix becomes the one thing computed per kind, with P11's red-checks case unchanged beside

```python

        why = f' ({row.hold_why})' if row.hold_why else ''
        return f"{R.LAUNCH} {row.brief_kind} on {row.branch} — land it as written{why}"
    m = _CHECKS_RED_RE.match(row.correction or '') if row.brief_kind == 'correct' else None
    red = f" — against the red check(s): {m.group(1)}" if m else ''
    return f"{R.LAUNCH} {row.brief_kind} on {row.branch}{red}"
```
