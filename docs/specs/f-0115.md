# F-0115 — the worker's allow list is the gate's own registry

A worker session is told, in its brief, to run the product's own checks before it pushes. It then
asks the runtime to run `bash tools/check_conventions.sh` and the runtime asks for approval —
there is nobody to ask, so the call is refused and lands in the result's `permission_denials`.
The session does the only honest thing left: it reports the check "left out", prints
`NEEDS OPERATOR`, and pushes a branch with the repo's own lint unverified.

The evidence the card carries (`~/.ASF/logs/jobs/asf/plan-f-0041.jsonl`, 2026-09-24 04:0x) has six
Bash calls in `permission_denials`, among them `bash tools/check_conventions.sh` three times and
`printenv | grep -iE 'backlog|ASF'` — while `bash tools/check_generic.sh`, run in the same
session, was allowed. One of the two scripts the gate runs has a rule and the other does not,
because the rules are a hand-kept list and the gate is not.

This session reproduced it live. `printenv BACKLOG_ID_RANGE` was refused here with *"the following
parts require approval"*; `python3 -c "import os; print(os.environ.get('BACKLOG_ID_RANGE'))"` was
allowed and printed the value. So the refusal is an **ask with no one to answer it** — the absence
of an allow rule, not a deny rule — and on the command it does refuse it protects nothing, because
the same bytes come back through the interpreter next to it.

The fix is one seam: the commands the gate runs become a registry with two readers — the gate that
runs them and the allow list that permits them — so a lint added to the registry is allowed the day
it is added, with no second edit and nobody to remember it.

## Decisions

### In scope

1. **One registry for the gate's commands.** `asf.harvest.harvest.gate_commands(conv, asf_repo)`
   returns the argv list `product_gate` runs, in order, with the environment assignments its
   leading `NAME=value` tokens lift out. `product_gate` stops building that list inline and calls
   it. Nothing about what the gate runs changes.
2. **The worker's allow list is derived from that registry.** `asf/workers/worker_perms.py`, new,
   turns each gate command into one `Bash(<command>:*)` rule, adds `conventions.pre_push_check`
   (the command every code brief names as the one that must pass before a push), and omits any gate
   command the approvals hook would refuse as a full suite.
3. **The settings file ASF passes as `--settings` is composed, not copied.** The operator's own
   `worker_pool.settings_file` is read first and the derived allow rules are merged **over** it,
   `asf.console_perms.merge`'s discipline exactly: append what is missing, keep existing entries
   and their order, touch no other key. The composed object is written to
   `asf.env.state_dir(product)` and that path is what `build_command` receives. The operator's own
   file is never edited and no rule of theirs — allow or deny — is ever removed.
4. **`printenv` is allowed, and so is `grep`.** Two rules, `Bash(printenv:*)` and `Bash(grep:*)`,
   so the card's own evidence command (`printenv | grep -iE …`) runs. `printenv` also joins
   `asf.approvals._READ_ONLY_PROGRAMS`, where it belongs and is missing.
5. **A rule ASF allows that the composed object also denies is a doctor row.** In the runtime a
   deny beats an allow, so ASF must not pretend its allow rule won. `worker permissions` names, by
   name, every derived rule that the composed settings still refuse, and the file the deny came
   from.
6. **`asf worker-permissions offer --product <p>`** prints the composed list in full before any
   session runs — `console_perms.offer_text`'s discipline, for its reason: a confirmation of a list
   has to be of the actual list.

### Out of scope, and why

- **The per-role deny rules, the role guard, and the secret-path `Read` denies.** Those are
  F-0062 §2.7's, and F-0062 has not landed (`asf/workers/worker_settings.py` does not exist; P8).
  This spec ships the *allow* half under a name F-0062's own plan already reserves
  (`asf worker-permissions`, `docs/plans/f-0062.md:52`), in a module shaped so F-0062's
  `deny_rules(product, launch)` and its per-role split drop in beside `allow_rules` later.
- **Removing `printenv` from F-0062's planned deny list.** F-0062 §2.7 calls that deny "the single
  highest-value rule in the list", on the ground that `build_env` puts live credentials in the
  session's environment (`asf/workers/runtime.py:276`, `:283`) and `printenv` prints them. The
  ground is sound; the conclusion is not, and this spec records why (C6) rather than deleting a
  rule that is not in the code yet. F-0062 keeps the decision that is its to make.
- **Masking the session transcript.** The exposure F-0062 names is real and this spec does not
  close it: `asf/workers/runtime.py:354`'s `mask` is applied to the worktree-setup log
  (`asf/workers/spawn.py:854-856`) and to nothing else, and the session's own `.jsonl` is the
  detached child's stdout fd, with no ASF process in the pipe (P10). It is also **pre-existing and
  not widened here** — `bash -c 'echo $GH_TOKEN'` and the `python3 -c` this session ran both reach
  the same values today, under no rule at all. It wants its own Bug card, not a clause in this one.
- **`env`.** `env FOO=1 <anything>` is a command launcher: one `Bash(env:*)` rule would allow
  every command in the product. `printenv` cannot run a program. The card's `env | grep` shape is
  served by `printenv | grep`, which is what its own evidence used.
- **`worker_pool.permission_mode`.** Untouched. The derived rules are what a non-bypass mode reads
  and are inert under `bypassPermissions`, so the fix holds whatever the operator has set and
  needs no config change to take effect.
- **The gate's own behaviour.** `gate_commands` is an extraction. The bisection path (`only`), the
  per-command timeout, the red-module parse and the timing line are all unchanged, and
  `tests.test_harvest`'s existing gate cases are the proof.

### The choices

| # | chosen | against | why |
| --- | --- | --- | --- |
| C1 | One registry function, `gate_commands(conv, asf_repo)`, with the gate and the allow list as its two readers | exporting `ASF_GATE_SCRIPTS` and letting `worker_perms` re-derive the `bash tools/<x>.sh` argv itself | two derivations of one list drift, and the second one would have to spell `tools/…\.sh` inside `asf/`, which `check_conventions.sh` forbids (P11). One function, one spelling, one place to add a lint. |
| C2 | The allow list is computed at launch from the registry | a generated file checked into the repo, or a list in the product yaml | the card's requirement is that "a new lint is allowed the day it is added"; anything an operator or a commit has to refresh is the hand-kept list under another name. |
| C3 | Merge over the operator's `worker_pool.settings_file`, write the result under `state_dir`, pass that path | editing the operator's file in place, or replacing it | the operator's deny rules are theirs and a factory that rewrites them is a factory nobody trusts with a token. `merge` already has the discipline and the tests (P6). |
| C4 | A gate command that `full_suite_command` matches gets **no** rule | allowing every gate command unconditionally | allowing what the approvals hook then refuses is worse than either alone: the session gets past the runtime and is stopped by the hook, and the two refusals read as one flaky fence. `pre_push_check` is the slice a session is meant to run, and the hook is documented never to refuse it (P12). |
| C5 | `Bash(<command>:*)`, one rule per command, no exact-match twin | emitting both `Bash(cmd)` and `Bash(cmd:*)` | `console_perms` has used the `:*` form alone for every rule since B-0131 and it covers the bare command; two shapes per command double the list the operator reads in `offer` for nothing. |
| C6 | `printenv` is allowed | keeping it refused as a credential fence, per F-0062 §2.7 | the fence does not hold and its cost is real. `python3 -c "import os; print(os.environ)"` and `bash -c 'echo $GH_TOKEN'` are unrestricted today, and this session proved the first of them live while `printenv` was refused. What the rule bought was a session that cannot see its own `ASF_SESSION` or `BACKLOG_ID_RANGE` and reports `NEEDS OPERATOR` instead. The exposure belongs at the transcript, which is where this spec files it (Out of scope) rather than pretending a command name is a boundary. |
| C7 | `grep` is allowed too | `printenv` alone | the card's own evidence is `printenv \| grep -iE 'backlog\|ASF'`, and the runtime judges each side of a pipe against the rules separately — `printenv` alone leaves that exact call refused. `grep` has been on this repo's read-only register since F-0042 (P9) and the `Grep` tool already gives a session the same reach. |
| C8 | `env` stays out | symmetry with `printenv` | `env NAME=value <program>` runs a program. A single `Bash(env:*)` rule is a rule that allows everything. |
| C9 | A doctor row names a derived rule the composed object still denies | trusting the merge, or stripping the operator's conflicting deny | a deny beats an allow in the runtime, so a composed file can carry both and refuse anyway. | C10 | `offer` only — no `install` subcommand | `console_perms`' `offer`/`install` pair | the console's list is written by hand into a file the operator owns; the worker's is composed by ASF at every launch, so there is nothing for an operator to install. `offer` is the read of what the next session will get. |

## The design

### 1. One registry for the gate's commands (`asf/harvest/harvest.py`)

```python
def gate_commands(conv, asf_repo, only=None):
    """``(cmds, env)``: every command the gate runs for ``conv``, in the order it runs them, and
    the environment assignments lifted out of the test command's leading ``NAME=value`` tokens
    (:func:`command_env`).

    The product's test command first, then — on asf's own repo, and only when this is not a
    bisection's targeted re-run (``only``) — one ``bash tools/<name>.sh`` per
    :data:`ASF_GATE_SCRIPTS`. This is the one list: :func:`product_gate` runs it and
    :mod:`asf.workers.worker_perms` permits it, so a lint appended to
    :data:`ASF_GATE_SCRIPTS` is allowed in every worker session with no second edit.
    """
    cmds, extra = [], {}
    if conv.test_command:
        cmd, extra = command_env(shlex.split(str(conv.test_command)))
        cmds.append(cmd)
    if not only and asf_repo:
        cmds += [['bash', os.path.join('tools', name + '.sh')] for name in ASF_GATE_SCRIPTS]
    return cmds, extra
```

`product_gate`'s first six lines become the call, and nothing after them moves:

```python
    env = gate_env(tmp)
    cmds, extra = gate_commands(conv, asf_repo, only)
    env.update(extra)
    if only:
        env[ONLY_VAR] = ' '.join(only)
```

The `elif`/`if not only` inversion is the same condition read the other way round (P1): with `only`
set the old code took the `if only:` branch and never appended the scripts, and the new code
appends nothing for the same reason. `ASF_GATE_SCRIPTS`' docstring gains one sentence — that it is
read by the worker allow list too, so the next person to append to it knows what else moves.

### 2. The worker's allow list (`asf/workers/worker_perms.py`, new)

Built on `console_perms`' shape (P6), with `allow_rules` split into the two halves the card names —
what the gate runs, and what a session needs to diagnose itself.

```python
"""asf.workers.worker_perms — F-0115: the rules a worker session is launched with.

A worker session has nobody to answer an approval prompt: a Bash call with no allow rule is
refused, recorded in the result's ``permission_denials``, and reported by the session as a check
"left out" — so its branch lands with the repo's own lint unverified. The rules are therefore
derived, never kept by hand: :func:`gate_allow_rules` reads
:func:`asf.harvest.harvest.gate_commands`, the same list the gate itself runs, so a lint added to
the registry is allowed the day it is added.

:func:`settings` merges those rules **over** the operator's own ``worker_pool.settings_file`` —
`asf.console_perms.merge`'s discipline: append what is missing, keep every existing entry and its
order, touch no other key. The operator's file is never written to and no rule of theirs is ever
removed; where one of theirs denies what this module allows, the runtime's deny wins and
:func:`check_doctor` says so by name.
"""

#: What a session needs to read its own situation, and nothing that can run a program.
#: ``printenv`` prints variables and cannot execute (``env NAME=v prog`` can, and is not here);
#: ``grep`` has been on :data:`asf.approvals._READ_ONLY_PROGRAMS` since F-0042, and the card's own
#: evidence is ``printenv | grep`` — the runtime judges each side of a pipe on its own.
SELF_DIAGNOSIS = ('Bash(printenv:*)', 'Bash(grep:*)')


def rule_for(argv):
    """One ``Bash(<command>:*)`` rule for ``argv`` — ``shlex.join``'s spelling, so the rule reads
    exactly as the gate invokes it (C5)."""


def gate_allow_rules(product):
    """One rule per command the gate runs for ``product`` (:func:`harvest.gate_commands`, with
    ``asf_repo`` from :func:`harvest.is_asf_repo` over the product's checkout), plus
    ``conventions.pre_push_check`` — the command every code brief names as the one that must pass
    before a push. A command ``asf.approvals.full_suite_command`` matches is left out: the
    approvals hook refuses it whatever the runtime allows, and two fences on one command read as
    one flaky fence (C4). Order: the gate's own, then ``pre_push_check``; each rule once."""


def allow_rules(product):
    """:func:`gate_allow_rules` then :data:`SELF_DIAGNOSIS`, deduped, order kept."""


def settings(product, operator=None):
    """``operator`` (the object read from ``worker_pool.settings_file``, or ``{}``) with every
    rule of :func:`allow_rules` present exactly once in ``permissions.allow`` — every unrelated
    key, and every deny rule, untouched."""


def path(product, wp):
    """``<state_dir>/worker-settings.json``, rewritten only when it differs from what is there;
    the path :func:`asf.workers.spawn.spawn` gives ``Job(settings_file=…)``. ``wp`` is the worker
    pool block: its ``settings_file`` is read through :func:`asf.workers.spawn.settings_file`, so
    a configured path that does not exist still refuses the launch (P5)."""


def denied_anyway(product, wp):
    """Every rule of :func:`allow_rules` that the composed object's ``permissions.deny`` also
    matches — in the runtime a deny beats an allow, and a rule in both refuses (C9)."""


def offer_text(product, wp=None):
    """Every rule the next session will get, in full, one per line, the gate's own marked with the
    command they came from — `console_perms.offer_text`'s discipline (C10)."""
```

Three notes on what is deliberately *not* there:

- **No `FIXED_ALLOW`.** Every rule is derived or named for one reason (`SELF_DIAGNOSIS`, two
  entries, each with its own sentence). The moment a rule needs a fixed tuple, it needs a card.
- **No `deny_rules`.** F-0062 §2.7 owns those (Out of scope). `settings` reads and preserves a
  deny list; it writes none.
- **No `tools/` literal, no `.claude/` literal.** The gate's script paths arrive from
  `harvest.gate_commands`, which spells them by `os.path.join`, and the composed file goes to
  `env.state_dir(product)` — so this module needs no exemption from `check_conventions.sh` (P11),
  and the one lint the card is about passes over the code that fixes it.

### 3. What `--settings` points at (`asf/workers/spawn.py`)

One line at the `Job` construction (`asf/workers/spawn.py:933`):

```python
-                          settings_file=settings_file(wp), hooks_dir=hooks_dir,
+                          settings_file=worker_perms.path(product, wp), hooks_dir=hooks_dir,
```

`settings_file(wp)` keeps its signature, its `FileNotFoundError` and its tests — it becomes
`worker_perms.path`'s reader of the operator's half rather than `spawn`'s only answer. A pool with
no `settings_file` configured now gets a composed file carrying only ASF's derived rules, where it
used to get `--settings` not at all: that is the case the card's evidence is from, and it is the
whole point.

### 4. `printenv` on the read-only register (`asf/approvals.py`)

```python
 _READ_ONLY_PROGRAMS = frozenset((
     'grep', 'egrep', 'fgrep', 'rg', 'ag', 'ls', 'cat', 'head', 'tail', 'wc', 'less', 'more',
     'stat', 'file', 'diff', 'cmp', 'cut', 'tr', 'nl', 'echo', 'printf', 'pwd', 'true', 'test',
-    'basename', 'dirname', 'realpath', 'readlink', 'which', 'jq',
+    'basename', 'dirname', 'realpath', 'readlink', 'which', 'jq', 'printenv',
 ))
```

One token, and it belongs: `printenv` reads the environment and writes nothing but through a
redirection, which is the exact contract the set's docstring states. It is not `env` (C8), which is
absent for the reason `sed` and `awk` are. What it fixes is the hook's second-order reading of a
command: `printenv | grep -iE 'backlog|ASF'` stops being a *run* in `_run_text`, so an item id or a
set name inside that grep pattern is text the session searched for, never a command it ran — the
same false refusal F-0042 fixed for `grep`.

### 5. The doctor row (`asf/doctor.py`)

One row, next to `console permissions` (P7):

```python
    from asf.workers import worker_perms
    ok, detail = worker_perms.check_doctor(cfg, product)
    rows.append(('worker permissions', True, ok, detail))
```

Green: `<n> rule(s) derived, every one allowed`. Red, and it names the rule and the file:
`Bash(bash tools/check_conventions.sh:*) is denied by worker_pool.settings_file — drop that deny
rule or a session cannot run the gate's own lint`. A pool with no worker accounts configured
returns `(True, 'no worker pool')` and the row says so — the doctor never turns red over a
product that has no sessions.

### 6. `asf worker-permissions offer` (`asf/cli.py`, `asf/surface.py`)

A parser in the shape `console_perms.register` uses (`asf/console_perms.py:154-163`): one
positional `worker_permissions_command` with the single choice `offer`, and `--product`. The
surface row (P14):

```python
    'worker-permissions': ("print the rules a worker session is launched with", None, None),
```

`None` effect and `None` flag: it reads and writes nothing.

### 7. The documentation

- `docs/config.example.yaml:79`'s `settings_file` comment gains a clause: the file is the
  operator's own rules, and ASF merges its derived allow list over it at every launch — it is no
  longer the whole of what a session gets.
- `CHANGELOG.md` — one line under the release, naming F-0115.
