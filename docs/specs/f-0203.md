# F-0203 — a run nobody lets finish

2026-09-26, a product's S1 PR #858 — the only thing standing between the trunk and prod — had its
CI run superseded four times in about forty minutes:

```
36258895126 → 36260038746 → 36261357776 → 36261437904 → 36262385912
```

The last supersede, 18:23Z, was a factory rebase onto a trunk that had moved (`#848` had merged at
20:02): all five of the branch's commits re-dated `20:22:51`, and not one byte of the branch's own
change different. Every supersede throws away the required jobs that were queued or had started
and sends the PR back to the end of the runner queue. Five runs, forty minutes, **zero verdicts** —
and the relief work spent cancelling other products' runs to clear a lane for this one was spent on
a run that was then thrown away too.

The waste is not the compute. It is that a push with nothing new in it takes the PR's place in the
queue away from itself, so the one thing the operator needed — does this S1 pass — never arrived.

Half of this is already fixed. `fbbadd432` narrowed the launch rebase to the three things a rebase
alone clears, on the measurement that **25 of 57 superseded runs on that product's PRs came from
the launch rebase alone, the branch's own changes byte-identical**
(`asf/workers/spawn.py:614-641`). What is left is the rule that measurement implies and nothing in
the tree yet states: **the factory never re-pushes a PR branch while that branch has a CI run in
flight, unless the push is the only thing that can make the PR mergeable.** This spec is that rule:
one reader, one verdict, five call sites, and the update moved from mid-run to merge time.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | **One new module, `asf/ci_flight.py`: the reader and the verdict, nothing else.** `run_in_flight(product, branch)` → `{'id', 'status'}` or `None`; the three exception constants; `verdict(...)` → `''` or the deferral line. | Putting it in `asf/capacity.py` beside `ci_runs_in_flight`; putting it in `asf/harvest/lane.py`; putting it in `asf/ci_queue.py`. | Both `asf/workers/spawn.py` and `asf/harvest/lane.py` must consult it, and spawn imports neither lane nor ci_queue today — routing the rule through either would be a new edge from the launch path into the landing machinery. `capacity` is about *how many* sessions and runs a host may have, which is a different question from *may this push go*. A module with two functions and no state is cheaper to read than either intrusion. `ci_queue` is imported lazily inside `urgent()` (C5), the way this tree already reaches heavy modules. |
| C2 | **The guard sits at the five sites that rewrite-and-push with no new content, never in `lifecycle.publish`.** | One guard in `publish`, the single funnel every factory push goes through. | P4: `publish` is also how a session's real work reaches origin. A guard there would defer the commits a session just made because a run from the *previous* head was still going — losing the work's only route to origin and re-creating B-0056 from the other end. "One place" is the wrong instinct when the one place serves two different meanings. The five sites are enumerable, and each already has a deferral path to hang this on (P3). |
| C3 | **Three named exceptions, and the push goes only for one of them.** `CONFLICT` — the PR does not merge cleanly into the trunk; `RED` — a required check is red on this very head and this push is its repair; `STRICT` — the host requires an up-to-date branch and every required check is green. Anything else, with a run in flight, defers. | A single boolean `needed=True` at each call site; deferring everything unconditionally. | The card names (a) and (b); `RED` is (b) read at the sign-off site and `STRICT` is (b) read at the merge site, and they are not the same test. A bare boolean hides which argument a site is making, so the S1 rule (C4) could not distinguish them, and the line could not say why a push went. Deferring unconditionally would strand a conflicting PR for ever: its in-flight run is against a head that cannot land, so waiting for it buys nothing. |
| C4 | **For an S1 or hotfix branch, only `CONFLICT` survives.** `RED` and `STRICT` are refused while a run is in flight; the repair or the update happens on the next pass, after the run has concluded. | Treating S1 like everything else; refusing every exception including `CONFLICT`. | This is the card's "for S1/hotfix PRs, never rebase mid-run", and it has a real bite: an S1 whose sign-off check is red today gets its trailer repair pushed at once and its run discarded, when the operator's one question is whether the code is green. One run's latency buys that answer. `CONFLICT` still survives because a conflicting PR cannot merge at any point — its run is already worthless, and for an S1 that is the most urgent thing on the branch. |
| C5 | **"S1 or hotfix" is `ci_flight.urgent(branch, severity=None, item=None, items=None)`, delegating to `ci_queue.priority` when the record is at hand.** The branch-name `hotfix` test and the `severity == 'S1'` test are the two the launch site can make from `pool.Row` alone (P7); with `items`, the answer is `ci_queue.priority(item, items, branch=branch)[0] == ci_queue.S1` and nothing else. | A second severity test written out in `ci_flight`; passing `items` down into `spawn`. | P7: the tree already has one definition of this tier and every feeder row is ordered by it. A copy would drift. `spawn` has no record index and should not gain one to answer a question its Row already carries. |
| C6 | **At launch the rebase and its publish are skipped together; the session starts on the branch as origin holds it.** | Rebasing the worktree and deferring only the publish, so the session still works on the trunk it must land on. | Tempting and strictly cheaper in runs — but `trunk_rebase_needed`'s own docstring says why the publish is immediate: so the session's own pushes are fast-forwards. A rebased, unpublished head makes the session's first push a non-fast-forward, and "told to push the same branch, never a force, a session did the one thing left and merged its own stale remote" is B-0056 — eight branches, 13 to 20 commits of tangle each. The brief does now cover that refusal (`pushed: rebased <sha> — the factory publishes`), but buying one CI run with a fresh route into B-0056 is not a trade this card asked for. A branch behind its trunk needs no rebase to be reviewed, tested or landed — `trunk_rebase_needed` says so — and the two reasons that are deferred here (`merge commits`, `copies of trunk commits`) are the lane's own `drop_copies` to clear, which defers with the same guard (C7). |
| C7 | **`drop_copies` (T13c) defers with the launch rebase, and for the same run.** | Letting the lane rebuild the branch on the next pass anyway. | Otherwise the guard is theatre: the launch defers, and the lane pass minutes later rebuilds the branch on the trunk and pushes it — the same supersede, one call site over. The two sites are one decision about one branch and must answer alike. |
| C8 | **`repair_signoff` (T13s) passes `RED` and goes through; `repair_naming` (T13n) passes nothing and defers.** | Deferring both; letting both through. | A sign-off repair exists only because the sign-off check is *already red on this head*: the run in flight is going to conclude red whatever else it says, so waiting for it wastes the wait as well as the run, and the PR cannot merge until the trailers are there. A naming reword is different — the subjects are wrong, the trees are identical (`repair_naming` asserts that before pushing), and the branch was going nowhere until its CI concluded. It waits. |
| C9 | **The update moves to merge time as one lane step, `update_for_merge`, and only where the host demands it.** In `merge_prs` (P10), before `MERGING`: when `protected_strict` is true, the PR is behind `origin/<trunk>`, and the checks are green, the branch is rebased once in a throwaway worktree (`H.rebase_and_resolve`) and published (`H.push_branch`) — this pass merges nothing, the branch returns to `WAITING_CI` at its new head, and the next green pass merges it. | Leaving the update out and trusting the deferral; doing it in `GitHubHost.merge` via the host's own "Update branch". | Without it the deferral can livelock: a host with `strict` on refuses to merge a branch that is behind, and every push that would bring it up to date is exactly what the guard defers — the PR would sit green and unmergeable for ever. One rebase, once, at the end, on a head whose checks are green is the whole of the card's "prefer *update at merge time*". It is dormant on this product (P6: no branch protection), which is why it is proved against a faked payload and a real git repo rather than against the forge. |
| C10 | **`protected_checks` splits into one `_protection()` read of the cached payload, with `protected_checks` and `protected_strict` as its two thin readers; a cache entry with no `strict` key is a miss.** | A second `gh` call for `strict`; returning a dict from `protected_checks` and moving its callers. | P6: it is one payload, already fetched, already cached for an hour — a second call would be a second round trip for a field that arrived in the first. Treating a `strict`-less entry as stale is what stops an hour-old pre-upgrade cache from answering "not strict" for a trunk that is. `protected_checks`' signature and its callers do not move. |
| C11 | **The line is the card's, with the verb of the site in front: `<what> deferred: <branch> CI in flight (run <id>)`.** `what` is `rebase` (launch, `drop_copies`), `reword`, `sign-off` or `update`. | The card's literal `rebase deferred:` at every site; one generic `deferred:`. | The card fixes the clause that matters — which branch, that CI is in flight, and which run, so an operator can open it. A reword that says `rebase deferred` is a false statement about what the factory was about to do, and the lane's existing lines already name their verb (`reword {b}: deferred — …`). One format constant, four verbs. |
| C12 | **No new lane state, no new record field, no new command, no doctor row.** A deferral leaves the branch exactly where it stands and is retried by the next pass; it is a line, and nothing else. | A `DEFERRED_CI` state; a `deferred:` mark on the lane record; a doctor row counting deferrals. | A deferral is not a state of the branch — the branch is in `PUSHED`/`GATE`/wherever it was, its head unmoved, and the next pass re-asks the same question against fresh facts. This is exactly how `repair_naming` already defers for a live session or a lease race. The effect is measurable where it already is: `metrics.py`'s `superseded` flag per run (`asf/metrics/metrics.py:1714`) is the number this card is trying to move. |

### In, and out

**In.** `asf/ci_flight.py` — `run_in_flight`, `Flight`, `urgent`, the three exception constants and
`verdict`; the guard at five sites — `spawn._rebase_onto_trunk` (P1), `Lane.repair_naming`,
`Lane.drop_copies`, `Lane.repair_signoff` (P3) and the new `update_for_merge` in `merge_prs` (P10);
`lane._protection` / `protected_strict` off the one cached payload (C10); `severity` threaded from
`pool.Row` through `spawn.make_worktree` to the launch guard; `Lane.flight`; the deferral line.

**Out, deliberately.**

* `lifecycle.publish` itself (C2) — and with it every push that carries a session's own commits.
* `asf/harvest/harvest.py`'s `harvest_branch` rebase-and-`push_branch` (`:579`, `:624`). It is the
  record repo's landing and the fast-forward path; on a product repo "a product repo's lane
  branches live on its origin, pushed by the sessions" and the lane owns their lifecycle
  (`asf/harvest/harvest.py:697-701`). The branch it pushes has no PR yet — it prints the
  `gh pr create` line immediately after. Named here so it is not read as an oversight.
* The CI start queue's own supersede, dedupe and relief passes (`asf/ci_queue.py`). This card stops
  the factory from *causing* supersedes; what the queue does with the ones that happen is its own.
* Cancelling a run the factory is about to supersede anyway. A cancel is not cheaper than a
  supersede and the host already does it; the card asks for the push not to happen.
* Any change to what `trunk_rebase_needed` returns (P2). Its three reasons and its test stand
  exactly as they are; this card only decides what to do with them when a run is in flight.
* Widening the guard to a branch with no open PR, or to a run of a workflow that is not
  `ci.workflow`.

## The design

### 1. `asf/ci_flight.py` — the reader and the verdict

```python
"""asf.ci_flight — may the factory re-push this branch right now?

A factory push that carries no new content — a rebase onto a moved trunk, a reword, a sign-off
trailer, a rebuild that drops trunk copies — supersedes whatever CI run the branch has going.
The run's queued and started jobs are thrown away and the PR goes back to the end of the runner
queue. A product's S1 PR #858 was superseded four times in forty minutes that way and never once
reached a verdict (F-0203).

So: while a branch has a run in flight, such a push waits — unless the push is the only thing
that can make the PR mergeable at all (:data:`CONFLICT`, :data:`RED`, :data:`STRICT`), and for an
S1 or hotfix branch unless it is :data:`CONFLICT`. Nothing here decides *whether* a rewrite is
wanted; each call site has already decided that. This module answers only *now, or next pass*.

A session's own push is never asked about: it carries the work, and :func:`asf.workers.lifecycle.
publish` is its route. The guard sits at the rewrite sites, never in the funnel they share.
"""

#: the PR does not merge cleanly into the trunk — its run is against a head that cannot land
CONFLICT = 'conflicting'
#: a required check is red on this very head, and this push is its repair
RED = 'a required check is red on this head'
#: the host requires an up-to-date branch and every required check is green (merge time only)
STRICT = 'the host requires an up-to-date branch'
#: the exceptions an S1 or hotfix branch admits while a run is in flight (F-0203 C4)
URGENT_EXCEPTIONS = (CONFLICT,)

CI_FLIGHT_TIMEOUT_S = 30
#: the one line a deferred rewrite writes, whatever the site (F-0203 C11)
DEFER_FMT = '{what} deferred: {branch} CI in flight (run {run})'


def run_in_flight(product, branch, run=None, timeout=CI_FLIGHT_TIMEOUT_S):
    """The newest run of the product's ``ci.workflow`` on ``branch`` the host has not completed:
    ``{'id': <int>, 'status': <str>}``, else None — nothing in flight, no ``ci.workflow`` or
    ``repo_slug`` configured, or a failed, timed-out or unparsable ``gh``. Read with the
    product's own login (:func:`asf.ci_pool._gh_env`), the seam and the discipline of
    :func:`asf.capacity.ci_runs_in_flight` (P5). Never raises."""


def urgent(branch, severity=None, item=None, items=None):
    """True when this is an S1 or hotfix branch — :func:`asf.ci_queue.priority`'s tier 0, which
    is the tree's one definition of it (C5). With ``items`` the answer is that function's;
    without, it is ``hotfix`` in ``branch`` or ``severity == 'S1'``, the two a ``pool.Row``
    carries."""


def verdict(product, branch, what, needed=None, severity=None, item=None, items=None,
            flight=None):
    """``''`` when the rewrite may be pushed now, else the one line it is deferred with.

    ``what`` is the verb the line names (``rebase``, ``reword``, ``sign-off``, ``update``);
    ``needed`` is the exception the site is claiming, or None. With no run in flight the answer is
    always ``''`` — this is the only question asked, and the ``gh`` read behind it is the only
    cost added to a pass with nothing in flight.

    |  run in flight | urgent | ``needed`` | verdict |
    | --- | --- | --- | --- |
    | no  | —   | —                    | push |
    | yes | no  | None                 | **defer** |
    | yes | no  | CONFLICT/RED/STRICT  | push |
    | yes | yes | CONFLICT             | push |
    | yes | yes | RED/STRICT           | **defer** |
    """


class Flight:
    """The per-pass reader a caller holds: one :func:`run_in_flight` per branch asked about,
    remembered for the pass. A test substitutes any object with the same ``read(product,
    branch)``."""

    def read(self, product, branch): ...
```

### 2. `asf/workers/spawn.py` — the launch rebase asks first

`make_worktree(product, job, branch, kind=None, severity=None, flight=None)`, and `spawn()` passes
`severity=row.severity`. `_rebase_onto_trunk(path, branch, main, kind=None, severity=None,
product=None, flight=None)` gains one gate between reading `remote_sha` and rebasing:

```python
    why = trunk_rebase_needed(path, main) if remote_sha else 'a fresh branch'
    if remote_sha and why:
        needed = ci_flight.CONFLICT if why == CONFLICT_REASON else None
        line = ci_flight.verdict(product, branch, 'rebase', needed=needed, severity=severity,
                                 flight=flight)
        if line:
            print(line, file=sys.stderr)   # the launch's own channel, as its other lines
            return                          # the session starts on the branch origin holds (C6)
```

`CONFLICT_REASON` names `trunk_rebase_needed`'s third string as a constant so the two do not drift;
its other two reasons (`merge commits above the trunk`, `copies of trunk commits above the trunk`)
claim no exception and so wait for the run (C6, C7). A branch not on origin (`not remote_sha`) is
never asked: rebasing it pushes nothing.

### 3. `asf/harvest/lane.py` — the three rewrites, and the update

`Lane.__init__` gains `self.flight = None` beside `self.ci_queue`, filled on first use with
`ci_flight.Flight()` (P9: a test sets it instead).

```python
    def ci_deferred(self, f, what, needed=None):
        """The deferral line for a rewrite of ``f``'s branch (:func:`asf.ci_flight.verdict`),
        said and returned; '' when the push may go. The branch is left exactly where it stands —
        no state, no mark, retried next pass (C12)."""
```

* **`repair_naming` (T13n)** — after the `guarded` check and before `fresh_trunk()`:
  `if self.ci_deferred(f, 'reword'): return DEFERRED`. It joins the live-session and lease-race
  deferrals already there (P3).
* **`drop_copies` (T13c)** — beside the existing live-session deferral:
  `if self.ci_deferred(f, 'rebase'): return None`, the same `None` a live session returns.
* **`repair_signoff` (T13s)** — `if self.ci_deferred(f, 'sign-off', needed=ci_flight.RED): return
  None`. For a non-urgent branch this never defers; for an S1 it does (C4, C8).
* **`merge_prs`** — `update_for_merge(lane, f, number)` between `host.recheck` and `MERGING`:

```python
def update_for_merge(lane, f, number):
    """The one rebase this card allows, at the one moment it is safe: the host requires an
    up-to-date branch (:func:`protected_strict`), the PR is behind origin/<trunk>, and every
    required check on it is green. The branch's own commits are replayed onto the trunk in a
    throwaway worktree (:func:`asf.harvest.harvest.rebase_and_resolve`) and pushed over a lease on
    the head read before it (:func:`asf.harvest.harvest.push_branch`); this pass merges nothing
    and the branch goes to WAITING_CI at its new head, for the next green pass to merge (C9).
    True when it updated; a conflict is send_back's, and an S1 with a run still in flight defers
    (C4). None of it runs for a trunk with no strict protection — every product here today."""
```

### 4. The protection payload read once (C10)

```python
def _protection(slug, trunk, state_dir, now=None):
    """``{'checks': (…), 'strict': bool}`` from ``repos/<slug>/branches/<trunk>/protection/
    required_status_checks``, cached per ``<slug>@<trunk>`` for :data:`REQUIRED_TTL_S`. An entry
    with no ``strict`` key was written before F-0203 and is a miss, not a False."""


def protected_checks(slug, trunk, state_dir, now=None):
    """The trunk's branch-protection required checks (unchanged signature and result)."""
    return _protection(slug, trunk, state_dir, now)['checks']


def protected_strict(slug, trunk, state_dir, now=None):
    """True when the host requires a branch to be up to date before it merges."""
    return _protection(slug, trunk, state_dir, now)['strict']
```

## Acceptance tests

Four blocks. The first is a new file; the rest extend the classes that own each site today (P12),
and every one runs with no `gh` and no network — `run_in_flight` is either inert (P8) or faked
through a `Flight` with the same `read(product, branch)`.

**The reader and the verdict.** `tests/test_ci_flight.py` — `RunInFlight`: a faked `gh run list`
returning two not-completed runs on the branch gives the newest with its id and status; one
returning `[]` gives `None`; a product with no `ci.workflow`, one with no `repo_slug`, a `gh` that
exits non-zero, one that times out and one that prints garbage each give `None` and raise nothing
(P5, P8). `Urgent`: `hotfix/x` is urgent on its name alone, `severity='S1'` is urgent, `'S2'` and
`None` are not, and with `items` the answer is `ci_queue.priority`'s for an `S1` card, a `hotfix`

## Records

| What | Where | What it says |
| --- | --- | --- |
| **The deferral line** | stdout of the lane pass; stderr of a launch | `<what> deferred: <branch> CI in flight (run <id>)`, with `what` one of `rebase`, `reword`, `sign-off`, `update`. The run id is the host's, so an operator can open the run that was protected. |
| **The launch-rebase line already there** | stderr of a launch | Unchanged when nothing is in flight: the rebase happens and `lifecycle.publish` says `published <branch> at <sha>` as today. |
| **`landing-required-checks.json`** | `state/<product>/landing-required-checks.json` | The existing per-`<slug>@<trunk>` entry gains a `strict` key beside `at` and `checks` — one bool, from the payload already fetched. An entry written before this card has no `strict` and is re-read once (C10). No new file, no migration. |
| **The lane record** | `state/<product>/sessions.jsonl`, the `lane` field | **Nothing new.** A deferral does not move the branch: its state, head and reason are exactly what they were, and the next pass re-decides. `update_for_merge` writes only states that already exist — `WAITING_CI` at the new head, or `BACK` on a conflict. |
| **What is not written** | — | No new lane state, no `deferred:` mark, no new config key, no command, no doctor row, no schema change, no metric of its own — the effect is read off `metrics.py`'s existing per-run `superseded` flag (C12). |

## Stories

- S: The one reader and the one verdict — `asf/ci_flight.py` with `run_in_flight(product, branch)` returning the newest not-completed run of `ci.workflow` on the branch as `{'id', 'status'}` (and `None`, never an exception, for no CI, no slug, a failed, timed-out or unparsable `gh`), `urgent()` as `ci_queue.priority`'s tier 0 read from a `pool.Row`'s own fields when the record is not at hand, the three exception constants `CONFLICT`/`RED`/`STRICT`, and `verdict()` implementing the full table including an S1 or hotfix branch admitting only `CONFLICT` — acceptance: `python3 -m unittest -v tests.test_ci_flight`
- S: A launch never re-pushes a branch whose run is in flight — `spawn.make_worktree`/`_rebase_onto_trunk` taking the row's `severity` and consulting the verdict before it rebases, so a branch carrying trunk copies or a merge keeps its head byte-identical and un-re-dated while its run finishes, a branch that does not merge cleanly into the trunk is still rebased at once (S1 included), an S1 carrying copies defers, a fresh branch off the trunk is never asked, and with nothing in flight the rebase and its publish are exactly what they are today — acceptance: `python3 -m unittest -v tests.test_workers.LaunchRebaseDefersMidRun tests.test_workers.TestSpawn`
- S: The lane's three content-free rewrites wait for the run, except the one the merge cannot do without — `repair_naming` (T13n) and `drop_copies` (T13c) deferring with `reword deferred:` / `rebase deferred:`, pushing nothing and archiving nothing, the branch's lane state and head untouched and the next quiet pass doing the work as before; `repair_signoff` (T13s) claiming `RED` and pushing at once because the check it repairs is already red on that head — unless the branch is S1, which defers; and every existing repair test unchanged because a product with no `ci.workflow` is never asked — acceptance: `python3 -m unittest -v tests.test_lane.RewritesDeferMidRun tests.test_lane.NamingRepair tests.test_lane.SignoffRepair tests.test_lane.TrunkCopiesDropped`
- S: The update happens once, at merge time, and only where the host demands it — `_protection()` reading `strict` and the required checks from the one cached payload with `protected_checks`/`protected_strict` over it and a `strict`-less entry counting as a miss, and `update_for_merge` in `merge_prs` rebasing a green PR onto the trunk exactly once and returning it to `WAITING_CI` at its new head when the host requires an up-to-date branch, doing nothing at all when it does not, deferring for an S1 whose run is still in flight, and sending a conflicting rebase BACK with its files — acceptance: `python3 -m unittest -v tests.test_lane.UpdateAtMergeTime`
