# F-0061 — the rule bites at the tool boundary, not at the next tick

A rule in this factory is a card with a `check:` script. The check runs on a clock
(`asf/rules/rules.py`), prints one line per place the product broke the rule, and `asf file-bugs`
turns each line into a Bug. Every part of that works. What it cannot do is *stop* the call: by the
time the check runs, the blanket `git add -A` has already staged another session's file, the
`git stash` has already taken work off a stack four worktrees share, and the session that did it
has ended. The rule is a report, and the report arrives after the damage.

The runtime already has the boundary this needs. A `PreToolUse` hook sees the tool name, the tool
input and the session's cwd before the call runs, and an exit status of 2 refuses it and hands its
stderr back to the model. `asf` already installs one: `approvals` (F-0031 §2.3), the human-now
matrix, written into every worker account's own settings file so that every session is bound by it
whether or not it is in a product repo. `asf/hooks.py` already carries the whole installer — the
`hook:` frontmatter field, `declared_hooks`, the idempotent `merge`, `asf hook <name>` — and
`asf.workers.githooks` already carries the git-hook half.

What is missing is everything the installer was built to install. `hooks.RULES_DIR`
(`asf/hooks.py:40`) names a top-level `rules/` directory this repository has never shipped, so
`declared_hooks` returns `[]` on every run and `asf hooks install` writes exactly zero rule hooks.
And the one place it would write them to if it had any — the product repo's own
`.claude/settings.json` — is an untracked file in the canonical checkout, while every worker
session runs with `cwd` set to a *worktree* (`asf/workers/runtime.py:7`). An untracked file does
not follow a worktree. A rule hook installed today would bind the operator's console and no worker
session at all, which is the opposite of this card's title.

This Feature ships the directory, the hooks in it, and the two wiring changes that make an
installed hook actually run inside a worker session.

## 1. Decisions

### 1.1 In

- **`rules/` in this repository** (§2.1) — the core rule directory `asf.rules.rules.core_rules_dir()`
  and `asf.hooks.RULES_DIR` both already name. One `R-nnnn.md` card per rule, each with `id:`,
  `title:`, `check:` and the third field this card asks for, `hook:`; one `r<nnnn>.sh` script
  beside it per hooked rule. The core band `R-0001`–`R-0099` is reserved for it.
- **Rule hooks go where every session reads them** (§2.2) — `install` writes the declared rule
  hooks into each worker account's own settings file (`hooks.account_settings_path`), *product-less*,
  exactly as it already writes `approvals`; each hook resolves its product from `ASF_PRODUCT` at run
  time. The product repo's `.claude/settings.json` keeps getting the same entries too, for the
  operator's console.
- **`asf hook <name>` finds a core script** (§2.3) — a fourth resolution step after the record's and
  the cwd's `tools/checks/<name>.sh`: `<core rules dir>/<name>.sh`. Without it a core card's `hook:`
  installs a command that resolves to nothing and exits 0 — an unenforced rule that reports itself
  as enforced.
- **The hook contract, in one place** (§2.4) — `asf/rules/hookcall.py`: read the call JSON from
  stdin, answer with `allow` (0) or `refuse` (2, the reason on stderr), fail *closed* on any
  exception but say it was the hook that broke and not the rule (the `HOOK_ERROR_LINE` shape
  `asf/approvals.py:860-863` already uses), and append one `refused-rule` record to the product's
  `approvals.jsonl`. Every hook script is four lines of `bash` that `exec`s a python entry point
  built on it.
- **Seven core rules** (§2.5–§2.11), six of them hooked:

  | id | rule | event | tool |
  | --- | --- | --- | --- |
  | R-0001 | a stage names its files | `PreToolUse` | `Bash` |
  | R-0002 | the stash stack is shared — never touch it | `PreToolUse` | `Bash` |
  | R-0003 | a session pushes its own branch, never the trunk | `PreToolUse` | `Bash` |
  | R-0004 | a card is minted from the range the session was given | `PreToolUse` | `Write`/`Edit`/`MultiEdit` |
  | R-0005 | a session does not open a pull request; a lane's body carries its lines | `PreToolUse` | `Bash` |
  | R-0006 | a card written is a card checked | `PostToolUse` | `Write`/`Edit`/`MultiEdit` |
  | R-0007 | a session ends with nothing uncommitted and nothing unpushed | `Stop` | — |

- **A fixture session that fires every refusal** (§3, T8) — one test that drives each hook's real
  entry point with the real call JSON the runtime sends, in a real git fixture, and asserts the rc
  and the first line of the reason. This is the card's first acceptance, and it is the test that
  would have caught every wiring hole above.
- **The measure** (§2.12) — `asf doctor` gains a `rule-hooks` row (the accounts whose settings are
  missing a declared rule hook, the shape `hooks.approvals_missing` already has), and
  `asf rules hooks` prints the installed-vs-declared table plus the `refused-rule` count per rule
  over a window. That count going to about zero as violations go to about zero is the card's fourth
  acceptance, read off one table.

### 1.2 Out

- **Nothing is minted in any product record.** The core cards are source files in this repository,
  not record cards; they carry no `epic:`, no state and no groom. A product that wants the *check*
  half of a core rule on its clock adds its own one-line `R-` card pointing at the same basename,
  which `asf.rules.rules.resolve_script` (`asf/rules/rules.py:66-73`) already falls back to. That
  adoption is per-product operator work and is out of this Feature.
- **The card's "a commit whose message lacks the item id" refusal is not built.**
  `asf.workers.githooks`'s `commit-msg` already *rewords* such a subject to `<kind>(<ID>): …`
  before the product's own hook sees it, and never blocks (`asf/workers/githooks.py:13-17`). A
  refusal on top of a silent fix is strictly worse: it turns a solved problem into a retry loop.
  Recorded here, with its owner named, rather than dropped silently.
- **The approvals matrix is not touched.** `touch_production`, `touch_amendable_set` and the rest
  keep their classes, their levels and their holds. R-0003 covers the one shape the classifier
  structurally cannot see (§2.7); it does not re-decide anything the matrix decides.
- **No new metrics stream.** `metrics.STREAMS` is a closed set with a validating schema
  (`asf/metrics/metrics.py:41`, `:116`); the refusal record goes to the product's existing
  `approvals.jsonl` ledger, which is where `approvals.refuse` already writes and where `asf rules
  hooks` reads it back from.
- **No `SessionStart`, `UserPromptSubmit` or `PreCompact` hook.** `hooks.EVENTS` is
  `('PreToolUse', 'PostToolUse', 'Stop')` and stays as it is.
- **The hooks never redact, never rewrite and never fix.** A hook answers allow or refuse. The
  redaction gate keeps its own git hooks (F-0075) and is unchanged.

## 2. The design

### 2.1 `rules/` — the core rule directory

New, at the root of this repository. Generic: no path, no account, no product name in any file —
every path a script needs comes from the environment or the product config, which is the same
constraint `core_rules_dir`'s docstring already states.

```
rules/
  README.md          the core band R-0001–R-0099, the card shape, how a product adopts a check
  R-0001.md … R-0007.md
  r0001.sh … r0007.sh          (six: R-0007's Stop hook has one too; no script for an unhooked card)
```

A card:

```markdown
---
id: R-0001
type: rule
title: a stage names its files
check: tools/checks/r0001.sh
hook: [PreToolUse]
---
A blanket stage in a worktree commits whatever else is in the tree — another item's file left by
a rebase, a scratch file, a second session's edit in a shared checkout. Name what you are
committing: `git add <path> …`.
```

`type: rule` and `check:` are what `rules.py`'s `partition` reads off a record card
(`asf/rules/rules.py:96-110`); `hook:` is what `declared_hooks` reads (P3). The hook name is the
id in check-script form — `R-0001` → `r0001` — which is already `declared_hooks`'s rule and is
why the scripts are named that way rather than by slug.

`rules/README.md` states the band (D11) and the two halves: the `hook:` half binds from this
directory on `asf hooks install`; the `check:` half binds only through a product's own record card
of the same basename (§1.2).

### 2.2 `asf/hooks.py` — where the rule hooks are written

`install` changes in one place. Today (`asf/hooks.py:311-333`) `rule_hooks` go to
`repo_settings` and `approvals` goes to each account. After:

```python
rule_hooks = declared_hooks(rules_dir)
accounts = pool.accounts_from_config(cfg or env.load_config())
for account in accounts:
    # product-less: one account's settings serve every product its sessions run for; each
    # hook resolves the product from ASF_PRODUCT (D1, PD5's reason, now for rule hooks too)
    _write_merged(account_settings_path(account),
                  [('PreToolUse', 'approvals')] + rule_hooks, asf_path, None)
```

and the existing `_write_merged(repo_settings, rule_hooks, asf_path, product.name)` stays exactly
as it is (D2). `merge` and `_is_ours` already handle both the product-less and the `--product`
command forms (`asf/hooks.py:249-275`), so a rule hook present in both files is recognised, updated
in place and never duplicated — running `install` twice still changes nothing.

The summary line gains the count:

```
hooks: 6 rule hooks in <repo>/.claude/settings.json; approvals + 6 rule hooks in 3 worker accounts; pre-commit, pre-push in 2 repos
```

The `rule_hooks and not product.repo_dir` refusal (`asf/hooks.py:326-329`) is now a refusal about
the *repo* copy only: the account copy is written first, so a product with no `repo_dir` still
leaves every worker session hooked. This is the same "every hook that can be written is written
before anything is refused" rule the docstring already states.

`approvals_missing` gains a sibling, `rule_hooks_missing(accounts, declared, repo_dir=None)`,
returning `[(account, [name…])]` — the doctor row in §2.12. It is a read: an unreadable settings
file counts as missing, exactly as `approvals_missing` treats it.

### 2.3 `asf/hooks.py` — `asf hook <name>` finds a core script

`check_script` gains the fourth root (D3):

```python
def check_script(name, product_name=None, cwd=None):
    """The first of: the record's tools/checks/<name>.sh, the cwd's, then the core rules/<name>.sh
    that ships with asf — so a core rule card's hook resolves without a product copying a file."""
    if not re.match(r'^[A-Za-z0-9_.-]+$', name):
        return None
    ...
    for root in roots:
        path = os.path.join(root, *CHECKS_DIR.split('/'), f'{name}.sh')
        if os.path.isfile(path):
            return path
    from asf.rules import rules
    core = os.path.join(rules.core_rules_dir(), f'{name}.sh')
    return core if os.path.isfile(core) else None
```

Order matters and does not change: a product that puts its own `tools/checks/r0001.sh` in its
record still overrides the core one, which is the override `resolve_script` gives the check half.
`ASF_CORE_RULES_DIR` therefore redirects both halves at once, which is what the tests use.

`cmd_hook` is otherwise unchanged: `BUILTIN` still shadows, stdin is still inherited by the
`bash` child, and the script's rc is still the rc the runtime reads. A name that resolves nowhere
still exits 0 — but §2.12's doctor row now makes that state visible instead of silent.

### 2.4 `asf/rules/hookcall.py` — the contract every hook script shares

New module. One entry point, one refusal shape, one ledger write.

```python
CALL = 'the call the runtime sent: {tool_name, tool_input, cwd, hook_event_name}'
HOOK_ERROR_LINE = 'rule hook {rule} broke ({why}) — the call is refused; this is the hook, not you'

def run(rule, decide, stdin_text=None, environ=None, out=sys.stderr):
    """The rc the runtime reads: 0 lets the call through, 2 refuses it and feeds ``out`` back to
    the model. ``decide(call, ctx)`` returns None to allow, or the refusal lines to print."""
```

`ctx` carries what every rule needs and none of them should re-derive: the product
(`env.load_product(environ['ASF_PRODUCT'])`), the job and item (`ASF_JOB`, `ASF_ITEM`), the call's
`cwd`, whether that cwd is a linked worktree (`_in_worktree`'s `.git`-is-a-file test,
`asf/record/ids.py:25-29`), and whether it is inside the product's `backlog_dir` or `repo_dir`.

The four rules of `run`:

1. **`ASF_JOB` unset → 0, before anything else** (D12). Not a factory session.
2. **`decide` returns `None` → 0.** Nothing recorded; a hook that allows is silent.
3. **`decide` returns lines → 2**, the lines on `out`, and one record appended to
   `<state>/<product>/approvals.jsonl` (D6):
   `{"event": "refused-rule", "rule": "R-0001", "item": …, "job": …, "tool": …, "detail": <the
   command or path, first 120 chars, redacted>, "ts": …}` — no `hold` key, so nothing parks and
   nothing is relaunched on it.
4. **Any exception → 2** with `HOOK_ERROR_LINE` (D5), and the error recorded for the operator the
   way `approvals.record_hook_error` already records one. A refusal is never mistaken for a rule
   violation: `event` is `rule-hook-error`, and `asf rules hooks` counts it in its own column.

Every refusal prints in the shape the model already reads from `approvals`: what was refused,
why, and what to do instead.

```
REFUSED git add -A — a stage names its files (R-0001)
  a blanket stage in a worktree commits whatever else is in the tree: another item's file, a
  scratch file, another session's edit.
  instead: git add <the paths you changed>
  This is not a question for a person: do not print NEEDS OPERATOR for it.
```

Each `rules/r000N.sh` is then the shim (D4):

```bash
#!/bin/bash
# written by hand, shipped with asf — the hook half of R-0001 (F-0061)
exec python3 -m asf.rules.hooks.r0001
```

and each `asf/rules/hooks/r000N.py` is a `decide` and a `hookcall.run(...)` call in `__main__`.

### 2.5 R-0001 — a stage names its files

`PreToolUse`, `Bash`. Refuses, in any simple command of the compound
(`approvals._simple_commands`, which already splits off `&&`, `;`, `|` and strips heredocs, so
`main` in a commit message never counts):

- `git add` with `-A`, `--all`, `--no-ignore-removal`, or a path argument of `.`, `:/`, `*` or the
  repo toplevel;
- `git commit` with `-a`, `--all`, or a bundled short flag containing `a` (`-am`, `-sam`);
- `git stage` in the same shapes (the alias).

Allowed: `git add <path>…`, `git add -p`, `git add -u <path>` (`-u` with no path is a blanket over
tracked files and is refused), and `git add` inside a `.git`-less fixture directory — the rule only
binds a worktree or a repo checkout (`ctx.in_worktree or ctx.in_repo`).

### 2.6 R-0002 — the stash stack is shared

`PreToolUse`, `Bash`. The stash stack belongs to the *common* `.git` directory, so every worktree
of a repo — and every session in them — pushes and pops the same stack. A `git stash pop` in one
session can take another session's work.

Refuses `git stash` and `git stash push|save|pop|apply|drop|clear|branch|create|store` in a
worktree. Allows the read-only verbs `list` and `show`.

The refusal names the way out, because there is one:

```
REFUSED git stash — the stash stack is shared across every worktree of this repo (R-0002)
  another session can pop what you pushed, and you can pop theirs.
  instead: set work aside with a WIP commit — git commit -s -m "wip(<ITEM>): …" — and reset it
  later; or, if you must stash, git stash push -u -m "<a tag only you use>" and recover it with
  git stash apply <sha>, never pop.
```

`-m` with a tag is still refused by default; `rules.r0002.allow_tagged: true` in the product's
conventions lets the tagged `push -u -m` form through for a product whose operator wants it. That
key is the only configuration any rule in this card takes.

### 2.7 R-0003 — a session pushes its own branch, never the trunk

`PreToolUse`, `Bash`. The complement of `touch_production` (D7). `approvals._pushes_trunk` reads
refspecs off the argv, so it catches `git push origin main` and misses every shape where the
destination is implied rather than written:

- `git push` with no refspec at all, from a checkout whose `HEAD` is the trunk, or whose upstream
  (`branch.<name>.merge`) is the trunk;
- `git push origin HEAD` / `git push origin @` from the trunk;
- `git push --force`, `-f`, `--force-with-lease` and `--mirror` **to any branch** — a force-push is
  refused for every branch, not only the trunk, because the standing rule is that a lane branch is
  never force-pushed and the lane rebases it (B-0056);
- `git push --delete` / `:<branch>` of the trunk.

The hook reads the cwd's branch and upstream with `git -C <cwd> rev-parse --abbrev-ref HEAD` and
`git -C <cwd> config --get branch.<b>.merge`, with `hermetic.GIT_HOOK` stripped from the
environment first — the same guard `hooks.git_hooks_dir` already takes (`asf/hooks.py:69-77`), so
an inherited `GIT_DIR` from an enclosing git hook never answers for another repo.

Explicit trunk refspecs are **left to the matrix**: `decide` returns None for them, and the
refusal text for the shapes it does catch names `touch_production` as the owner of the rest, so the
model is never told two different stories about the same command.

### 2.8 R-0004 — a card is minted from the range the session was given

`PreToolUse`, `Write` / `Edit` / `MultiEdit`. Refuses a write whose `file_path` (or
`notebook_path`) is a *new* file matching `<backlog_dir>/<folder>/<PREFIX>-<NNNN>.md` for a
`TYPES` folder (`asf/record/core.py`), in a worktree, when either:

- `BACKLOG_ID_RANGE` names no range for that prefix and `BACKLOG_ALLOW_MINT` is unset, or
- the id is outside the range it names.

This is `mint_id`'s rule (`asf/record/ids.py:32-36`) at the tool boundary, for the path that never
reaches `mint_id`: a session writing the card file itself (D8). An `Edit` of a file that already
exists is not a mint and is allowed; so is any write outside the record's card folders.

```
REFUSED writing tasks/T-0900.md — T-0900 is outside this session's id range (R-0004)
  this session holds T:30550-30599. Two worktrees minting from the same counter collide, and the
  record carries two cards with one id.
  instead: asf new --type task --title "…" — it mints from the range for you.
```

### 2.9 R-0005 — a session does not open a pull request

`PreToolUse`, `Bash`. Two shapes, one card:

- A worker session (`ASF_JOB` set, and the job is not a lane job) running `gh pr create`,
  `gh pr merge`, `gh pr ready` or `git push` with `-o merge_request.*`: refused outright. The
  standing rule in every worker brief is that the session pushes its branch and ends there; the
  lane opens and lands the PR.
- A **lane** job running `gh pr create` whose `--body` / `--body-file` is missing a line its lane
  requires: refused with the missing lines listed. What a lane requires comes from the product's
  conventions (`conventions.lane.pr_body_lines`, a list of literal lines or `/regex/` forms,
  empty by default — an empty list means nothing to check and the rule allows every body). This
  is the one half of this card that is configuration rather than a constant, because what belongs
  in a PR body is a product's policy, not the factory's.

`--body-file -` and a heredoc body are both read: the hook resolves `--body-file` against the
call's cwd and reads it, and falls back to allowing with a recorded `rule-hook-error` when the
file is not there yet (a body written by a later command in the same compound).

### 2.10 R-0006 — a card written is a card checked

`PostToolUse`, `Write` / `Edit` / `MultiEdit`. When the touched `file_path` is inside the
product's `backlog_dir`, run `asf check --product <p> <file_path>` and, if it reports errors,
print them (D9). rc is always 0: `PostToolUse` fires after the write, and a refusal there cannot
undo it.

The output is the check's own lines, prefixed once:

```
R-0006 asf check tasks/T-0900.md
  T-0900 state: New is not one of: New, Ready, Doing, Review, Done
  T-0900 epic: E-0009 does not exist
  fix these before you commit — the record's pre-commit refuses them anyway.
```

The check runs with a 20 s timeout and prints nothing when it is clean, so a session editing
twenty cards sees twenty silences and one report. A timeout or a crash is a `rule-hook-error`
record and a one-line note, never a wall of text.

### 2.11 R-0007 — a session ends clean

`Stop`. No tool input; the hook reads the session's worktree from the call's `cwd`, the branch
from `git -C <cwd> rev-parse --abbrev-ref HEAD`, and the trunk from the product's conventions,
then calls `workers.health.push_gap(cwd, branch, main)` (D10). When it says not pushed, the hook
refuses the stop with the gap and *what is in it*:

```
REFUSED finishing — not pushed: 2 uncommitted file(s), 1 unpushed commit(s) (R-0007)
   M asf/hooks.py
  ?? rules/r0008.sh
  1 commit above origin/spec/F-0061
  a result with uncommitted or unpushed work is a failed session (B-0051) and comes back to you
  as a correction.
  instead: git add <paths>; git commit -s -m "spec(F-0061): …"; git push origin spec/F-0061
```

The file list is `git status --porcelain` capped at 20 lines with `… and <n> more`, and it is run
through `asf.redact` before it is printed, so no account name and no machine path is fed back into
a transcript.

The refusal is **once per session**: a second `Stop` with the same gap allows, and records
`rule-stop-repeat`. A `Stop` hook that refuses forever is an unkillable session, and the one thing
worse than an unpushed branch is a session that cannot end. The one-shot state is a file under
`<state>/<product>/hooks/stop/<ASF_SESSION>`, removed by the session reaper with the rest of the
job's state.

### 2.12 The measure

Two reads, no new stream (§1.2).

**`asf doctor`** gains a `rule-hooks` row, beside the existing `approvals-hook` one: red when
`hooks.rule_hooks_missing` is non-empty, naming each account and the hooks it lacks, with the one
line that fixes it (`asf hooks install --product <p>`). It is also red when a declared hook's
script resolves nowhere (`check_script` returns None) — the silent-exit-0 state §2.3 exists to
prevent.

**`asf rules hooks [--product P] [--days N] [--json]`** prints one table:

```
== RULE HOOKS  6 declared, 6 installed in 3 accounts, 0 unresolved
rule    event         installed  refused(7d)  errors(7d)  violations(7d)
R-0001  PreToolUse    3/3                  4           0               0
R-0002  PreToolUse    3/3                  1           0               0
R-0003  PreToolUse    3/3                  0           0               0
R-0004  PreToolUse    3/3                  2           0               0
R-0005  PreToolUse    3/3                  0           0               0
R-0006  PostToolUse   3/3                  —           1               3
R-0007  Stop          3/3                  6           0               2
```

`refused` counts `refused-rule` records in `approvals.jsonl`; `errors` counts `rule-hook-error`;
`violations` counts Bugs `asf file-bugs` opened for that rule id in the window — the after-the-fact
number the card's fourth acceptance is about. The reading the card asks for is that the
`violations` column falls to about zero while `refused` stays non-zero: the rule is being enforced
at the boundary instead of reported after it. A run with both columns at zero and `installed` at
`0/3` is the failure this table exists to make impossible to mistake for success.

## 4. Records

**Files, in this repository**

- `rules/README.md`, `rules/R-0001.md`…`R-0007.md`, `rules/r0001.sh`…`r0007.sh` — the rule set as
  source. These are the record of *what the rules are*: a rule with no card here is not a rule.

**Files, per worker account**

- `<account settings>` (`hooks.account_settings_path`) gains one `PreToolUse` entry per declared
  `PreToolUse` rule, one `PostToolUse` entry, one `Stop` entry, beside the `approvals` entry
  already there. Merged in place; no other key is touched.
- `<product repo>/.claude/settings.json` gains the same entries with `--product <p>`.

**Rows, per product**

- `<state>/<product>/approvals.jsonl` — the existing ledger, two new `event` values:
  - `refused-rule` — `{event, rule, item, job, tool, detail, ts}`, no `hold` key, so nothing parks.
  - `rule-hook-error` — `{event, rule, job, why, ts}`, the hook broke and refused the call.
  - `rule-stop-repeat` — `{event, rule, job, ts}`, a `Stop` refusal not repeated (§2.11).
- `<state>/<product>/hooks/stop/<session>` — the one-shot marker for R-0007, removed with the
  job's state.

**Rows, in the record**

- None written by this Feature. Bugs for a *check* violation keep arriving the way they already do,
  through `asf file-bugs`, for products that adopt a core rule's check half.

**Events the console sees**

- `asf doctor`: the `rule-hooks` row (§2.12).
- `asf rules hooks`: the table (§2.12).
- `asf hooks install`: the summary line now counts rule hooks in accounts as well as in the repo.
