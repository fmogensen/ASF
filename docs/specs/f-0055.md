# F-0055 — an instrument, not another test

Three tools in this factory *judge*. `match.match_event` decides which card an event belongs to
(`asf/record/match.py:170`) — get it wrong and a session's cost lands on the wrong Feature, which
is the number the scorecard exists to report. `rules.run_check` decides whether the product broke
a rule (`asf/rules/rules.py:126`) — get it wrong and a Bug is filed against clean code, or a real
violation passes. `build.brief` decides which brief a row gets, by one line of kind detection
(`asf/briefs/build.py:495`) — get it wrong and a spec session runs on a coder's template.

Each of the three has tests. Every one of those tests is *editable*: when a change makes one red,
the honest repair and the dishonest one look identical in the diff, and the suite cannot tell them
apart. So there is no number anywhere in this factory that says how well the matcher matches. It
is the exact hole F-0021 D5 already refuses to paper over — its `## Not measured` section names
*prompt evals* as a thing 0.1 has no instrument for (`docs/specs/f-0021.md:127`), and cites the
prior art's own rule: *an eval that does not exist is worse than no eval*.

An eval is not a test. A test asserts a contract and is edited when the contract legitimately
changes. An eval is a measurement instrument: frozen, scored as a rate, and compared between a
candidate and an incumbent. A task edited after a failure is no longer a measurement — it is a
reading taken with a bent ruler. Everything below exists to make that edit either impossible in
one commit, or visible as a new instrument.

## 1. Decisions

### 1.1 In

- **`evals/`** in this repo: `manifest.json` (the lever roster), `exemptions.json`, `README.md`,
  and one directory of task files per lever. Tasks are JSON, one per file, one assertion each.
- **The lever** — the unit that is measured and reported on. Three families: `matcher` (one
  lever), `brief-kind` (one lever), and `rule:<R-nnnn>` (one lever per *enforced* rule in the
  product's live rule index, so the roster grows when the record does).
- **`asf/evals/`** — `set.py` (load, validate, hash), `adapters.py` (three adapters, one per
  family), `run.py` (score, append the stream), `freeze.py` (the pre-commit refusal), and
  `asf evals run | check | hash | --pre-commit` on the CLI beside `asf rules`.
- **Must-fire and must-not-fire pairs.** Every lever carries at least one task of each polarity,
  which is the card's "at least two tasks per judged tool" in its strong form: a lever with two
  must-fire tasks measures only half an instrument.
- **The set hash** — `sha256` over the canonical bytes of the whole set, plus a per-lever hash
  over that lever's tasks. Computed on every read, recorded in every reading, never stored in a
  file. A changed set is a new instrument; two readings are comparable only when the hashes match.
- **A daily reading**, scored by the tick's daily step (`asf/tick/step_daily.py:26`) into a new
  `evals` metric stream, and rendered as a `## Evals` section of `metrics/daily/<day>.md` — one
  line per lever, passed over total, with the hashes and the exempt count.
- **The exemption** — `evals/exemptions.json`. A lever the set has no pair for scores as `exempt`,
  and is counted on the daily line. A lever with no pair *and* no exemption entry is `unrecorded`:
  the daily line names it and `asf evals check` exits 1, so it cannot land quietly.
- **The freeze** — `asf evals --pre-commit` in `.githooks/pre-commit`, refusing a commit whose
  staged set touches both a lever's tasks and that lever's own source. `asf hooks install` writes
  the same line into a product's `pre-commit` and upgrades one it already wrote.
- **One extraction**: `build.detect_kind(row)` — the line at `asf/briefs/build.py:495` becomes a
  named function, because a lever needs one entry point to measure.
- **`tests/test_evals.py`** — the machinery's own tests, and the coverage and determinism gates.

### 1.2 Out

- **Any judgement a model makes.** A brief's quality, a review's verdict, a spec's fitness: none
  of them has a right answer a JSON file can hold, and an instrument stamped on a lever it does
  not cover is the exact defect F-0021 D5 refuses. `## Not measured` keeps naming model judgement,
  and this Feature's arrival does not let it stop.
- **A candidate-versus-incumbent harness.** The card asks for the instrument and the daily rate.
  Comparing two versions of a tool over one frozen set is what the instrument makes *possible*;
  it is a separate card, and nothing here is shaped to prevent it — a reading already carries the
  set hash and the per-lever rate, which is everything a comparison needs.
- **Scoring the model-router, the feeder's tier assignment, or the groom's decisions.** Judged,
  arguably; not named by the card. They become levers by an entry in `manifest.json` and a
  directory of tasks — the runner needs no change — and until they do they are `## Not measured`.
- **Changing what the three judged tools *do*.** `match_event`, `run_check` and the kind detection
  keep their behaviour to the byte. The one change to any of them is the extraction of §1.1's
  `detect_kind`, which is a rename of a line.
- **A rule check's own correctness as a *shipped* artefact.** This repo ships no rule card and no
  core check script today (`core_rules_dir()` points at a `rules/` that is not here,
  `asf/rules/rules.py:56`); enforced checks live in each product's record. So the rule-check
  adapter ships with the `sample/` product's tasks as its proof, and every real product's rule
  levers are discovered from its own index at run time, scored the same way, and exempt until that
  product's record carries a pair.
- **Blocking a commit that edits a task alone.** The hook refuses the *pair* of changes, as the
  card says. A lone task edit stays legal and is caught by the other half: the set hash changes,
  so the reading is published against a new instrument and no trend crosses the boundary. Naming
  this hole out loud is the point — see the choice row.
- **`--no-verify`.** The standing rules already forbid it; the refusal names the two commits to
  make instead, so there is nothing to escape.

### 1.4 The choices

| Choice | Chosen | Against | Why |
|---|---|---|---|
| What a "lever" is | the judged surface reported on one line: `matcher`, `brief-kind`, `rule:R-nnnn` | one lever per *function*; one lever for "rules" as a whole | The card asks for "per lever" on the daily line and "at least two tasks per judged tool", so lever and judged tool are the same unit. One lever for all rules would let ten scored checks hide one with no task — the very silence acceptance #4 forbids. |
| Task file format | JSON, one task per file | YAML; one file holding a lever's whole set; a card in the record | JSON is stdlib, and this repo is stdlib-only (`index.json`, `fake_script.json` are the precedent). One file per task makes the freeze's diff exact: the hook can name *which* task moved, and a task's git history is its own. |
| Where the set lives | `evals/` at the repo root | `tests/evals/`; `docs/evals/` | Under `tests/` it inherits the suite's culture — a red thing you edit — which is the one property an eval must not have. The card names `evals/`, and a top-level directory is the readable statement that this is not the suite. |
| Whether the set hash is stored | computed on read, recorded in each reading | a generated `evals/SET_HASH` file; a line in the manifest | A stored hash is a second source of truth that goes stale, and keeping it fresh means a commit that changes a task also changes the hash file — which the freeze would then have to exempt. Computed, it cannot disagree with the set. |
| What makes two readings comparable | equal set hash *and* equal lever hash | a version integer someone bumps | A number someone remembers to bump is a number someone forgets. The hash changes exactly when the bytes do, which is exactly when the instrument changed. |
| A lever with no pair | scored `exempt` with a reason and a card id in `evals/exemptions.json`, counted on the daily line; `unrecorded` and a non-zero `asf evals check` when there is no entry | dropping it from the report; failing the run | Acceptance #4: it *lands*, with a recorded, counted exemption. Failing the run would mean a product could not add an enforced rule until it had written evals, which stops work; dropping it is the silence. Recorded is quiet, unrecorded is loud. |
| Which gate the unrecorded lever fails | `asf evals check`, run by `tests/test_evals.py::CoverageTests` for this repo's own levers, and reported on the daily line for a product's | the pre-commit hook | A product's rule index is not readable from this repo's pre-commit, and a hook that fails on another repo's state is a hook that fails at random. The suite covers what this repo owns; the daily line covers what it does not. |
| What the freeze refuses | a staged set intersecting both `evals/<lever>/**` and that lever's `implements:` globs | any commit touching `evals/**`; any commit touching both directories regardless of lever | Per-lever is the honest unit: a matcher fix and a new rule-check task are unrelated and must not block each other. Refusing every task edit would make adding a task as hard as bending one. |
| The manifest is not frozen | `manifest.json` and `exemptions.json` may change beside a tool | freezing them too | Renaming a lever or widening its globs *must* travel with the tool, or the roster and the code disagree for one commit. Neither file holds a task, so neither can be bent to make a failure pass. |
| A lone task edit | allowed, and caught by the hash boundary | refusing it in the hook | The card asks the hook for the task-and-tool pair. A lone edit is caught where it should be: the reading lands under a new set hash, and §2.6's renderer prints an instrument change instead of a trend. Stated here so no one reads the hook as a complete freeze. |
| How a rule check is scored | through `rules.run_check` over a temporary record root | a second runner in the adapter | The contract being measured *is* `run_check`'s — exit codes, timeout, missing-script handling. A second implementation would measure the adapter's reading of the contract, not the contract. |
| A check that says neither (broken, timed out) | the task **fails**, with `got: broken` | scored as no-fire; excluded from the total | A check that cannot answer is not evidence either way, which is precisely a failed measurement. Excluding it would let a check that always times out score 100 %. |
| Polarity per lever | at least one must-fire and one must-not-fire | two tasks of any polarity | The card says "must-fire and must-not-fire pairs". A rule check that violates on everything scores perfectly on must-fire tasks alone; the pair is what makes the reading mean anything. |
| Where the daily line goes | a `## Evals` section of `metrics/daily/<day>.md` | a row in `## Waste`; a new file; `asf scorecard`'s output | That file is titled *Factory scorecard `<day>`* — it is the daily scorecard the card names. `## Waste` is about spend, and a per-lever table does not fit one row. |
| Which day a reading is rendered under | the day its events were appended; the rollup renders yesterday, as it does for every other stream | rendering today's reading in yesterday's rollup | Every other section of that file reads the streams for the day it names (P7). A section that reached forward one day would be the only one, and would read as today's reading in yesterday's file. |
| Where in the daily step | `evals` first, before `stale` and `rollup` | after `rollup` | Running it first means a hand-run `asf metrics rollup <today>` in the same tick sees the reading. The parts are independent (P8), so order costs nothing else. |
| One event per lever, or one per run | one per lever per run | one event carrying every lever | A per-lever event is what makes "per lever" a query rather than a parse, and a lever added later needs no schema change. |
| `detect_kind` extracted | yes, as `build.detect_kind(row)` | measuring `normalize_kind` alone | `normalize_kind` takes a string; the *detection* is the choice of which of the row's two fields to read, and that choice is the thing that can be wrong. Measuring the string normaliser would score the easy half. |
| The adapters' purity | pure over the task's `given`, no clock, no network; the rule adapter's only side effect is a temp tree it removes | letting a task name a real path | A task that reads the working tree is a task whose answer changes with the tree, which is not an instrument. `tests/test_evals.py::DeterminismTests` scores the whole set twice and demands identical outcomes. |

## 2. The design

### 2.1 `evals/` — the set

```
evals/
  README.md              why this is not the suite; how to add a lever; why a task is never edited
  manifest.json          the lever roster
  exemptions.json        the levers with no pair, each with a reason and the card that will add one
  matcher/
    001-branch-id-token.json
    002-branch-token-of-another-item.json
    ...
  brief-kind/
    001-row-brief-kind-wins.json
    002-unknown-kind-refuses.json
  rules/
    R-0001/              one directory per enforced rule id; the sample product's, in this repo
      001-violates.json
      002-clean.json
```

`manifest.json` — the roster. One entry per lever this repo owns; a `rule:<id>` lever with no
entry is discovered from the product's index (§2.4) and inherits the `rules` family's defaults.

```json
{
  "levers": [
    {
      "id": "matcher",
      "adapter": "matcher",
      "judges": "asf.record.match.match_event",
      "implements": ["asf/record/match.py"],
      "tasks": "matcher"
    },
    {
      "id": "brief-kind",
      "adapter": "brief-kind",
      "judges": "asf.briefs.build.detect_kind",
      "implements": ["asf/briefs/build.py"],
      "tasks": "brief-kind"
    },
    {
      "id": "rules",
      "adapter": "rule-check",
      "judges": "asf.rules.rules.run_check",
      "implements": ["asf/rules/rules.py", "rules/*", "tools/checks/*"],
      "tasks": "rules/{rule}",
      "family": true
    }
  ],
  "min_tasks": 2,
  "require_both_polarities": true
}
```

A task file — the whole vocabulary:

```json
{
  "id": "matcher/002-branch-token-of-another-item",
  "lever": "matcher",
  "expect": "no-fire",
  "why": "a PR body that merely cites a Decision belongs to the work, not to the ruling",
  "given": {
    "items": {"F-0012": {"type": "feature", "folder": "features"},
              "D-0292": {"type": "decision", "folder": "decisions"}},
    "branch": "worker/f-0012-thing",
    "body": "as [[D-0292]] says"
  },
  "want": {"ids": ["D-0292"]}
}
```

`expect` is `fire` or `no-fire`. `want` states the *firing condition* — never the outcome — so the
two polarities read the same input grammar: this task passes when the matcher does **not** return
exactly `D-0292`. `why` is required and is printed beside a failure; a task with no `why` is a
reading nobody can interpret, and the loader refuses it.

### 2.2 `asf/evals/set.py` — load, validate, hash

```python
@dataclasses.dataclass(frozen=True)
class Task:
    id: str
    lever: str
    expect: str            #: 'fire' | 'no-fire'
    why: str
    given: dict
    want: dict
    path: str              #: repo-relative, for the freeze and for a failure line

@dataclasses.dataclass(frozen=True)
class Lever:
    id: str
    adapter: str
    judges: str
    implements: tuple      #: globs, repo-relative
    tasks: tuple           #: Task, in path order
    exempt_reason: str = ''   #: from exemptions.json; '' when not exempt
    exempt_card: str = ''

@dataclasses.dataclass(frozen=True)
class Set:
    levers: tuple
    root: str
    set_hash: str          #: 12 hex
```

`load(root='evals') -> Set` reads the manifest, then every `*.json` under each lever's `tasks`
directory in sorted path order, then `exemptions.json`. It raises `EvalError` naming the file and
the key for: an unknown `adapter`; an `expect` that is neither word; a missing `why`, `given` or
`want`; a `lever` field disagreeing with the directory; a task under no lever's directory; a
duplicate task `id`; an exemption for a lever that has a pair.

`set_hash(levers)` / `lever_hash(lever)` — `sha256` over, per task in path order, the task's
repo-relative path and the canonical bytes of its JSON (`json.dumps(obj, sort_keys=True,
separators=(',', ':'))`), plus the manifest entry's own canonical bytes; first 12 hex characters.
Canonicalising rather than hashing the raw file means a reformat that changes no assertion does
not fake a new instrument, while any change to a value does. The set hash folds every lever's
hash, in lever-id order, the same way.

### 2.3 `asf/evals/adapters.py` — three adapters

Each adapter is one function, `fires(given, want) -> (bool, detail)`. The scorer, not the adapter,
compares against `expect`; an adapter that raised anything but `Broken` is a *fail* whose detail
is the exception's first line, so a task that cannot be run is never a pass.

**`matcher`** — pure, no I/O:

```python
ids, reason = match.match_event(given['items'], **kwargs_of(given))
fired = set(ids) == set(want['ids']) and (want.get('reason') or '') in (reason or '')
```

`kwargs_of` passes only `match_event`'s own keywords (`task`, `branch`, `pr`, `title`, `body`,
`files`, `prs`, `pr_info`, `prefixes`); anything else in `given` is a loader error, not a silently
ignored key. `want.ids` may be `[]` — with `expect: fire` that is the assertion that a branch is
attributed to nothing, which is a real must-fire.

**`brief-kind`** — pure. `given.row` is a dict, passed to `detect_kind` through a tiny stand-in
carrying the two attributes it reads (`brief_kind`, `kind`), so a task never has to build a feeder
`Row`. `want` is `{"kind": "coder"}` or `{"error": "no brief template"}`; the second fires when
`BriefError`'s message contains the text — which is how a must-fire task proves the detector
*refuses* an unknown kind rather than guessing one.

**`rule-check`** — the one adapter that touches a filesystem, and only a temporary one:

1. a temp directory becomes the record root: `given.files` is `{relpath: contents}`, written
   verbatim; `given.index` is written as `index.json` (the card under test, with its `check:`), and
   `given.scripts` is `{relpath: contents}` written mode `0o755`;
2. `rules.run_check(root, rule)` is called with `BACKLOG_ROOT` and the cwd set to that root, the
   caller's `ASF_RULE_CHECK_TIMEOUT` replaced by the task's `given.timeout_s` (default 10), and
   the git-hook variables stripped as `hermetic.GIT_HOOK` names them — a check run from inside a
   pre-commit must not read this repo's index;
3. `(violations, broken)` decides: `broken` non-empty → `Broken(broken[0]['line'])`, which the
   scorer records as a **fail** with `got: broken`, whichever polarity was expected; else
   `fired = bool(violations)` and every string in `want.lines_contain` must appear in some
   violation line;
4. the temp tree is removed whether or not the check answered.

A real product's rule lever names no `scripts` and no `files` of its own script: `given.files` is
the fixture the check is pointed at, and the script comes from the product's record through
`resolve_script`. This repo's `sample/` tasks ship both, which is what makes the adapter provable
here (§3.4).

### 2.4 `asf/evals/run.py` — the reading

```python
def score(eval_set, product=None, record_root=None) -> Reading
```

`Reading` is `(set_hash, levers)` where each `LeverReading` is
`(lever, lever_hash, passed, total, exempt, exempt_reason, unrecorded, failures, seconds)` and a
failure is `(task_id, why, expected, got, detail)`.

The roster scored is the manifest's own levers, **plus** one `rule:<id>` lever per enforced rule
when a record root is given: `rules.load_rules(root)` → `rules.partition` → the enforced list
(P2), each looking for `evals/rules/<id>/` in this repo and then in the record's own `evals/`, so a
product carries its rule tasks where its rule cards are. A lever with fewer than `min_tasks`
tasks, or missing a polarity, is not scored:

| The lever | `exempt` | `unrecorded` | `passed` / `total` | On the daily line |
|---|---|---|---|---|
| has a pair | false | false | as scored | `18/19` |
| has no pair, has an `exemptions.json` entry | true | false | `0` / `0` | `exempt — <reason> (<card>)` |
| has no pair, has no entry | true | **true** | `0` / `0` | `UNRECORDED — no eval task, no exemption` |

`asf evals run [--product p] [--json]` prints one line per lever and the totals, appends one
`evals` event per lever (§4), and exits 1 when any task failed or any lever is unrecorded — so the
command is usable as a gate as well as a reading. `asf evals check` scores nothing: it loads the
set, applies the coverage rule, and exits 1 on an unrecorded lever, naming it. `asf evals hash`
prints the set hash and each lever's.

Printed shape:

```
== EVALS set 7f3a1c9d0b42 — 18/19 passed, 1 lever exempt, 0 unrecorded
matcher        9/9   a41c8e02b7d1
brief-kind     4/4   0c9b12ff5a63
rule:R-0001    5/6   3de7104c8b9a
  FAIL rules/R-0001/004-nested-case  expected no-fire, got fire
       why: a path inside a vendored directory is not the product's own
rule:R-0002    exempt — filed as B-0130, no fixture yet (0/0)
```

### 2.5 The stream

`STREAMS` gains `'evals'` (`asf/metrics/metrics.py:41`) and `SCHEMAS` the entry of §4. No key uses
`MATCH`: a reading is about an instrument, not about a card, so the matcher is not asked to
attribute the events that measure it. `asf metrics append evals '<json>'` therefore validates and
appends with no index read.

### 2.6 The daily line

`render_daily` (`asf/metrics/metrics.py:715`) gains a section, after `## Waste`:

```markdown
## Evals

set 7f3a1c9d0b42 — 18/19 tasks passed (95 %), 1 lever exempt, 0 unrecorded

| Lever | Passed | Total | Rate | Lever hash | Note |
|---|--:|--:|--:|---|---|
| matcher | 9 | 9 | 100 % | a41c8e02b7d1 | |
| brief-kind | 4 | 4 | 100 % | 0c9b12ff5a63 | |
| rule:R-0001 | 5 | 6 | 83 % | 3de7104c8b9a | 004-nested-case: expected no-fire, got fire |
| rule:R-0002 | 0 | 0 | — | — | exempt — filed as B-0130, no fixture yet |
```

Three rules the renderer keeps:

- **No reading for the day** → the section is one line, `no eval reading for <day>`. It is never
  omitted: a missing instrument is the thing that has to stay visible.
- **A rate is never printed for an exempt lever** — `—`, not `100 %`. A lever with no task has not
  passed anything.
- **An instrument boundary is printed, never crossed.** When the day's events carry more than one
  `set_hash`, or the previous day's hash differs, the section's first line reads
  `instrument changed 4b2e77a10c33 → 7f3a1c9d0b42 — readings before and after are not comparable`
  and no rate is compared across it. A trend that spans two hashes is the defect this Feature was
  written to prevent, so the renderer refuses to draw one.

`step_daily.parts` gains `('evals', lambda: evals_run.daily(product, root))` **first** in the list
(`asf/tick/step_daily.py:26`); it reports `daily: evals ok — 18/19 passed, 1 exempt` through the
step's existing one-line-per-part shape, and a failing reading does not stop `stale`, `rollup` or
`scorecard` (P8).

### 2.7 The freeze

`asf evals --pre-commit` (`asf/evals/freeze.py`), the third gate in `.githooks/pre-commit`:

```python
def refusals(staged, eval_set):
    """One refusal per lever whose tasks and whose own source are both in ``staged``."""
```

- `staged` is `git diff --cached --name-only --diff-filter=ACMRD -z`, repo-relative — `D` included,
  because deleting the task a change would have failed is the cheapest way to bend the set.
- a lever's task paths are the files under its tasks directory; its tool paths are its
  `implements` globs, matched with `fnmatch` per path segment as `ci.matches` already does.
- `manifest.json` and `exemptions.json` are in neither set (§1.4), so a lever rename travels with
  the tool it renames.
- the refusal, on stderr, exit 1:

```
pre-commit: refused — an eval task and the tool it measures in one commit

  lever matcher
    task  evals/matcher/002-branch-token-of-another-item.json
    tool  asf/record/match.py

An eval is a measurement instrument: a task edited in the same commit as the tool it measures is
no longer a measurement of it. Commit them apart, tool first:

  git reset evals/matcher/002-branch-token-of-another-item.json
  git commit -s -m "<the tool change>"
  git add evals/matcher/002-branch-token-of-another-item.json
  git commit -s -m "<what the set now measures, and why>"
```

The hook returns 0 at once when `ASF_HOOK_RUNNING` is set (P9) and when `evals/manifest.json` is
absent, so a checkout without the set is not blocked. It reads the index and never the working
tree, and never runs a task: the freeze is a path question, and a pre-commit that scored the set
would put a rule check's subprocess in front of every commit.

**A product's hook.** `hooks._git_hook_body` (`asf/hooks.py:86`) becomes two commands for
`pre-commit` — `asf redact --pre-commit` then `asf evals --pre-commit` — and loses its `exec`;
`pre-push` is unchanged. `is_git_hook_ours` (`:92`) already matches on the `redact` line, so an
installed hook is still recognised as asf's; a new `evals_gate_upgrade(text, name)` beside
`staged_check_upgrade` appends the evals line to a `pre-commit` that is ours and lacks it, so
`asf hooks install` upgrades rather than refusing (P11, D10). A hook that is not asf's is still
left untouched, and its `NEEDS OPERATOR` line now names both commands.

## 3. Acceptance tests

All run from the repo root.

### 3.1 The set loads, or says exactly why

```bash
python -m unittest tests.test_evals.SetLoadTests -v
```

Covers: the shipped `evals/` loads, every task's `lever` agrees with its directory, and every
task carries `why`, `given` and `want`; each malformed task — unknown adapter, `expect: maybe`,
missing `why`, a duplicate id, a `given` key `match_event` does not take, a stray `*.json` under
no lever — raises `EvalError` naming the file and the key; an exemption for a lever that *has* a
pair is an error, so an exemption cannot outlive the gap it recorded.

### 3.2 The set hash is the instrument's identity

```bash
python -m unittest tests.test_evals.SetHashTests -v
```

Covers: the hash is stable across two loads of the same bytes and across a reformat of a task file
that changes no value; changing one character of one task's `want` changes that lever's hash and
the set hash; adding a task to one lever changes that lever's hash and the set hash and leaves the
other levers' alone; deleting a task changes both; the hash is 12 hex characters and is recorded
in no file in the tree (the test greps `evals/` and `asf/` for it).

### 3.3 The matcher and the kind detector are measured

```bash
python -m unittest tests.test_evals.MatcherLeverTests tests.test_evals.BriefKindLeverTests -v
```

Covers, for each of the two levers: the shipped set carries at least one must-fire and one
must-not-fire task; the whole lever scores `passed == total` against today's code — the number the
instrument exists to report, and a red one here is a real defect in the tool, not in the test; a
task's outcome is unchanged when the adapter is handed the same `given` twice; `detect_kind` reads
`brief_kind` before `kind` and refuses an unknown kind with `BriefError`; and a deliberately bent
task (built in the test, not in `evals/`) is scored as a failure carrying its `why`, its
`expected` and its `got`.

### 3.4 A rule check is measured through its own contract

```bash
python -m unittest tests.test_evals.RuleLeverTests -v
python -m unittest tests.test_sample_product.SampleEvalsTest -v
```

Covers: the `sample/` product's enforced rule becomes a `rule:<id>` lever, its must-fire task's
fixture makes the check exit 1 with a line and its must-not-fire task's fixture makes it exit 0;
the adapter writes only inside a temp directory and removes it (asserted by comparing the repo's
`git status --porcelain` before and after, and by a task whose fixture would clobber a real path
if the root leaked); a check that exits 2, one that prints nothing on exit 1, and one that
exceeds `timeout_s` are each scored as a **fail** with `got: broken`, for both polarities; a card
whose `check:` script is missing everywhere scores as a fire, matching `run_check`'s own B-0021
behaviour; and the git-hook variables are absent from the check's environment.

### 3.5 Coverage, and the exemption that is counted

```bash
python -m unittest tests.test_evals.CoverageTests -v
asf evals check
```

Covers: every lever this repo's manifest declares has at least `min_tasks` tasks and at least one
of each polarity, or an `exemptions.json` entry with a reason and a card id — this is the test that
would have gone red the day the matcher shipped without an eval; a lever with one polarity only is
a coverage failure, not a pass; a synthetic roster with an undeclared, unexempted lever makes
`asf evals check` exit 1 naming it; and the same lever with an entry exits 0 and is reported as
`exempt`, counted in the totals.

### 3.6 The instrument is deterministic

```bash
python -m unittest tests.test_evals.DeterminismTests -v
```

Scores the whole shipped set twice in one process and asserts identical per-task outcomes and
identical hashes; asserts no adapter reads the clock or the network (the test replaces
`socket.socket` and `time.time` with raisers for the duration of the second run, save the wall
clock the reading itself records, which is taken outside the adapters).

### 3.7 The stream and the daily line

## 4. Records

**A new stream.** `metrics/evals/<YYYY-MM-DD>.jsonl` in the record clone, one line per lever per
run, keys sorted, UTC `ts`:

```
'evals': {
  'ts':             (('str',),          TS),    # when the reading was taken
  'set_hash':       (('str',),          REQ),   # the instrument
  'lever':          (('str',),          REQ),   # 'matcher' | 'brief-kind' | 'rule:R-0001'
  'lever_hash':     (('str', 'null'),   None),  # null for an exempt lever — it has no tasks
  'adapter':        (('str',),          REQ),
  'passed':         (('int',),          REQ),
  'total':          (('int',),          REQ),
  'exempt':         (('bool',),         False),
  'exempt_reason':  (('str', 'null'),   None),
  'exempt_card':    (('str', 'null'),   None),
  'unrecorded':     (('bool',),         False), # no pair and no exemption — the loud case
  'failures':       (('list',),         []),    # [{task, why, expected, got, detail}]
  'seconds':        (('num', 'null'),   None),
  'product':        (('str', 'null'),   None),
}
```

No key is `MATCH`: a reading names no card (§2.5).

**Files this change adds, and who owns them.**

| Path | Written by | Changed when |
|---|---|---|
| `evals/manifest.json` | a person, reviewed | a lever is added, renamed, or its globs move |
| `evals/exemptions.json` | a person, reviewed | a lever's gap is recorded, or closed |
| `evals/<lever>/*.json` | a person, reviewed; **never** in the same commit as the tool | a task is *added*. A task is not edited; a wrong task is deleted and a new one added, which the hash records as a new instrument |
| `evals/README.md` | a person | the rules above change |
| `metrics/evals/<day>.jsonl` | `asf evals run`, the tick's daily step | append-only, once a day per product |
| `metrics/daily/<day>.md`, `## Evals` | `asf metrics rollup` | rewritten for the day it renders |

**Not written.** The set hash is in no file (§1.4): it is computed on every read and appears only
inside a reading and on stdout. No card is created, no item's machine block changes, no existing
stream gains a key, and no rule card is added to this repo.

**Printed, before → after.**

| Where | Was | Is |
|---|---|---|
| `metrics/daily/<day>.md` | no eval section | `## Evals` — per-lever passed/total, the set hash, the exempt and unrecorded counts |
| `asf tick`, the daily step | `daily: stale ok …` | `daily: evals ok — 18/19 passed, 1 exempt` first |
| a commit staging a task and its tool | committed | `pre-commit: refused — an eval task and the tool it measures in one commit`, with the two commits to make |
| `asf evals run` | — | the `== EVALS` block of §2.4 |
| `asf evals check` | — | silence and 0, or the unrecorded levers and 1 |

## Stories

- S: `evals/` holds the set — a manifest of levers, JSON tasks one per file, and an exemptions file — and the loader refuses a malformed task by file and key — acceptance: `tests.test_evals.SetLoadTests` (§3.1)
- S: The set hash and each lever's hash are computed from the tasks' canonical bytes and stored nowhere, so a changed set is a new instrument and a reformat is not — acceptance: `tests.test_evals.SetHashTests` (§3.2)
- S: The matcher lever scores `match_event` over must-fire and must-not-fire tasks, and a bent task is reported with its `why`, `expected` and `got` — acceptance: `tests.test_evals.MatcherLeverTests` (§3.3)
- S: `build.detect_kind` is the brief generator's one kind-detection entry point, and its lever scores it over a pair including an unknown kind it must refuse — acceptance: `tests.test_evals.BriefKindLeverTests` (§3.3)
- S: Every enforced rule check is a lever, scored through `rules.run_check` in a temporary record root, where a check that says neither pass nor violation is a failure and never a pass — acceptance: `tests.test_evals.RuleLeverTests` and `tests.test_sample_product.SampleEvalsTest` (§3.4)
- S: A lever with no must-fire/must-not-fire pair lands only with a recorded exemption carrying a reason and a card, and an unrecorded one makes `asf evals check` exit 1 naming it — acceptance: `tests.test_evals.CoverageTests` and `asf evals check` (§3.5)
- S: The whole set scores identically twice, with no clock and no network inside any adapter — acceptance: `tests.test_evals.DeterminismTests` (§3.6)
- S: The reading is scored daily into a new `evals` metric stream, one event per lever, by the tick's daily step, without stopping the other daily parts — acceptance: `tests.test_metrics.EvalsStreamTests` and `tests.test_tick_steps.DailyEvalsTests` (§3.7)
- S: The daily scorecard carries a `## Evals` line per lever — passed over total, the set hash, the exempt and unrecorded counts — prints `no eval reading` when there is none, and prints an instrument change instead of a trend across two hashes — acceptance: `tests.test_metrics.EvalsDailyTests` (§3.7)
- S: A pre-commit refuses a commit staging a lever's eval task and that lever's own source together, naming both and the two commits to make, and `asf hooks install` upgrades a product's hook to run it — acceptance: `tests.test_evals.FreezeTests` and `tests.test_install.EvalsHookTests` (§3.8)
