# F-0051 — after the deploy, something signs in and looks

The factory can already tell you, to the commit, what is on production. `asf.harvest.deploy`
reads each environment's deployed sha off the newest successful run of its workflow, decides
whether the newest green trunk sha may go, dispatches it, and prints one line per environment
every tick (`asf/harvest/deploy.py:869`). `asf.views.prod` renders the gap: the customer-visible
pull requests merged to the trunk that the deployed sha does not carry yet. `asf.record.ingest`
closes a Feature when every child Task's merge is an ancestor of that sha and — for a product
whose prod deploy is dispatched by hand — the operator has ticked each child's pull request into
`checked.txt` (`asf/record/ingest.py:424`).

Every one of those readings is about **git**. Not one of them is about the product. The deploy
workflow concluded `success`, the merge commit is an ancestor of the deployed sha, therefore the
item is "in production" — and nothing anywhere has loaded a page, signed in, or clicked the thing
the pull request said to try. A deploy that ships a broken sign-in concludes `success`, the sha
contains every merge, `asf prod` shows a clean board, and the Features close. The only instrument
that would have caught it is a person who happened to open the site.

The pieces to fix that are almost all already here, unread. `asf.metrics.metrics.TRY_IT`
(`asf/metrics/metrics.py:856`) already parses the `Try it:` line out of a merged pull request's
body, and `release_items` already returns, per item, the pull requests a release carried and each
one's try-it line — it is used to render a line in a release note and for nothing else.
`asf.views.prod._is_customer` (`asf/views/prod.py:99`) already decides whether a landing is
customer-visible, from the product's own `customer_paths`. `app_host` has been a declared,
validated field of the product file since the config cutover — `docs/products.example.yaml:304`
says it is "used by the prod probe", and `asf/env.py:780` is the only code that has ever touched
it. `asf-prober` is a complete role with a complete launch row (`asf/roles/launch.py:51`:
`plan`, read tools, one output file, `restricted`), sitting in `roles.UNBOUND` under the reason
*"no phase yet — the production probe is a view, not a session"* (`asf/roles/roles.py:60`).

This Feature is the phase. After each successful prod deploy the tick dispatches one probe run of
the product's own headless journey workflow, on a light runner of the product's own pool, for the
sha that just went live. The run signs in as the probe identity through a code mailed to a
configured mailbox, walks the try-it path of every customer-facing pull request in that release
plus the product's standing journeys, and returns one verdict, one failing-step name and one
screenshot per journey. The tick reads that back, writes it into the record as a stream and onto
each item's own card as evidence, files a severity-one Bug for every failed journey naming the
step it failed at, and hands ingest one new input: a passing probe closes a non-customer-facing
Feature without the operator's tick; a customer-facing one still waits for a human.

What ASF does **not** do is drive a browser. The engine is the product's, in the product's repo,
on the product's runners, behind one workflow contract and one result schema. ASF chooses the
journeys, dispatches, reads back, judges, records and files. That line is where this spec spends
most of its decisions.

## 1. Decisions

### 1.1 In

- **One `probe:` block in the product file** (§2.1) — `workflow`, `role`, `identity`, `secrets`,
  `mailbox`, `journeys`, `artifact`, `timeout`, `origins`. Declared in `env.PRODUCT_FIELDS` and
  `env.NESTED_FIELDS` beside `ci` and `release`, with a `probe.config_problems` hook for the
  deeper shape, exactly as `ci.pool` and `ci.queue` already validate (`asf/env.py:642-647`).
  Documented in `docs/products.example.yaml`. **Unset, the whole Feature is off**: no dispatch, no
  stream, no doctor row, no change to any close — the same "unset means nothing is checked" rule
  `customer_content` follows.
- **`asf/probe/scope.py`** (§2.2) — `is_customer_visible(paths, changed_files, within=None)`,
  *moved* from `asf/views/prod.py:99` (the view imports it back), and `owed(product, sha,
  previous_sha, items)`: the release's items, each one's try-it line, and whether its landing is
  customer-visible. Built on `metrics.release_items` and `metrics.TRY_IT`, not a second parser.
- **`asf/probe/journey.py`** (§2.3, §2.4) — the journey list ASF sends and the result it reads
  back: `Journey`, `Result`, `journeys(product, owed)`, `parse_results(text)`. The sign-in journey
  is always first and always ASF's, never the product's to omit. A try-it line with no path in it
  is `unrunnable` — never silently a pass (the prober's own doctrine: an absence is reported as an
  absence, b103).
- **`asf/probe/host.py`** (§2.5) — `Host` with `dispatch`, `runs`, `artifact`; a `GitHubHost` over
  `gh workflow run`, `gh api .../runs` and `gh run download`. A test passes a fake, as `ci_pool`'s
  `Backend` already arranges.
- **`asf/probe/ledger.py`** (§2.6) — `state/<product>/probe.json`: one entry per `(target, sha)`,
  its state, its run id and its verdict. One deploy is probed once; a dispatch that never returns
  a result inside `timeout` is abandoned with a named reason, never retried forever.
- **The pass in the tick** (§2.7) — `step_harvest.probe_pass(ctx)`, immediately after
  `deploy_pass` (`asf/tick/step_harvest.py:141`), before the gate lock is looked at. Read back
  first, dispatch second; never waits for a run; one `probe:` line per tick. The dispatch goes
  through `ci_queue.admit`, as the deploy's own does (`asf/harvest/deploy.py:859`).
- **`metrics/probes/<day>.jsonl` in the record** (§2.8) — one line per journey, appended by the
  pass into the tick's record clone and committed with the tick's one commit. Added to
  `init.STREAM_FOLDERS` (`asf/init.py:28`).
- **The evidence on the item's own card** (§2.8) — ingest renders one `probe: …` line into the
  item's `evidence:` list and one `## History` line on the transition. Ingest stays the only
  writer of a card's machine block; the probe writes a stream, never a card.
- **The close rule** (§2.9) — `_in_prod` gains `probe` (`''`/`'pass'`/`'fail'`) and
  `customer_facing`, as an eight-clause table whose first six clauses are today's outcomes
  unchanged. `closing.Ev` gains `probe: str`, read by no rule directly — the rules keep reading
  `in_prod`, and the new field is what the evidence line and the `rule:` phrase name.
- **One more signature source for the Bug filer** (§2.10) — `probe_signatures(root, now, conv)`:
  one Bug per failed journey, severity `S1`, keyed `probe: <journey>: <step>`, titled with the step
  it failed at, linked to the run. It joins the five `asf/tick/file_bugs.py` already has
  (`ci_signatures` l. 61, `refusal_signatures` l. 109, `rule_violation_signatures` l. 156,
  `record_error_signatures` l. 211, `invariant_signatures` l. 380) and needs no new machinery.
- **The fence** (§2.11) — `asf probe lint` reads the probe workflow off the host and refuses a
  job that inherits secrets, names a secret beyond the two declared, asks for more than
  `contents: read`, or whose `runs-on` no pool runner satisfies. A result naming an origin outside
  the allowlist fails that journey whatever its own verdict said. The probe never dispatches
  before the operator has recorded the identity's consents.
- **`asf probe`** (§2.12) — one parser, five subcommands: `journeys`, `dispatch`, `read`, `lint`,
  `consent`. Two `asf doctor` rows. `docs/guide/production-probe.md`: the block, the workflow to
  paste, the result schema, and the three things the operator does once.

### 1.2 Out

- **ASF drives no browser, and ships no journey engine.** No dependency, no driver, no page
  object, no selector anywhere in `asf/`. The engine lives in the product's repo behind the
  workflow contract of §2.3. A factory that shipped a browser would own every product's markup.
- **No LLM interprets a try-it line.** v1 extracts the first path or URL out of the line and the
  journey is: sign in, navigate there on `app_host`, let it settle, screenshot, and fail on an
  error response or an error page. A line with no path is `unrunnable` and is named as such.
  Reading "toggle dark mode and check the header" as a click sequence is a real feature and a card
  of its own — it needs a session, a connection the `asf-prober` launch row does not carry
  (`connections=()`, `asf/roles/launch.py:51`), and widening `tools`, `writes` or `connections` is
  an operator action through the amendable set, never a product setting
  (`asf/roles/launch.py:72`). Naming it here is how its absence stays deliberate.
- **`asf-prober` is not bound to a brief kind.** `roles.BINDINGS` maps a *brief kind* to a role
  (`asf/roles/roles.py:45-56`); the probe is a workflow run, not a session, so there is no kind to
  bind. `UNBOUND['asf-prober']`'s *reason* is rewritten (§2.11) — the phase exists now, and it is
  not a session — and the three boundaries its launch row already states become the contract
  `asf probe lint` holds the probe job to. Binding the role would mean inventing a brief kind
  whose session cannot do the work.
- **No credential is stored, read or printed by ASF.** The identity's secret and the mailbox's
  secret are repository secrets, named in the product file and set by the operator. ASF passes
  their *names* to the workflow and never their values. `asf/credentials.py` — the "is this
  session still valid" surface, which still has no caller outside its own tests — is the natural
  home for an *earlier* warning that the probe sign-in has expired; this Feature does not build
  it, because a sign-in that stopped working already fails the first journey, loudly, as an S1.
- **No new tick step, no new clock, no new lane state, no new brief kind, no new correction
  kind.** The pass is four lines inside the harvest step that already runs the deploy pass.
- **No screenshot in the record.** The record is text. Screenshots are the run's artifact; the
  evidence line names the run, the artifact and the file inside it. The documentation work the
  card names consumes them from there, by a stable path (§2.3).
- **No change to `auto`-mode closing except a failed probe.** A product whose prod deploy ASF
  dispatches itself needs no operator tick today, and this Feature does not add one. What it adds
  there is the one direction that is never a widening: a journey that *failed* stops the close.
- **The probe is not a rule check.** It is not periodic, it has no `rules/R-nnnn.md` card, and its
  Bug is filed by the tick's own filer. A rule check asks "is the world still as it should be" on
  a clock; this asks "did this deploy work" once per deploy.

### 1.4 The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | The engine is the product's, behind a workflow + result-schema contract | ASF ships a headless driver and the journeys | A driver in `asf/` owns every product's markup, its auth, its waits and its flakiness — and the card says the runner is the product's pool, which is where its repo's tooling already runs |
| D2 | A try-it line is a path, extracted by regex | An agent reads the prose and acts | v1 must be deterministic and runnable by a workflow with no model. The prose reader needs a tool connection the `asf-prober` launch row does not carry (§1.2); shipping a probe that *guesses* at prose would report passes it did not earn |
| D3 | A try-it line with no path is `unrunnable`, a third verdict | Treat it as a pass, or as a fail | A pass it did not run is the exact defect the prober's doctrine names (b103); a fail would file S1 Bugs about pull-request prose. `unrunnable` blocks the close and prints a line |
| D4 | The result comes back as a workflow artifact, read with `gh run download` | The job pushes to the record; the job posts a check-run summary; the job calls an ASF endpoint | A CI job writing the record needs write credentials to the record — the one thing the probe must not have. An artifact is read-only from ASF's side and carries the screenshots in the same object |
| D5 | The mailbox is configuration the engine uses, never a protocol ASF speaks | ASF reads the mailbox and hands the code to the run | ASF would then hold a mailbox credential, on the tick host, for every product. The code has to be read on the runner anyway — that is where the sign-in is |
| D6 | The sign-in journey is ASF's and always first | The product lists it among its standing journeys | Every later journey depends on it, and a product that forgot it would report five green journeys taken while signed out. Its failure is also the one failure that explains all the others, so it is reported first and the rest are `unrunnable` |
| D7 | A failed probe stops a close in every mode; a passing probe replaces the ✓ only for a non-customer-facing item | Probe evidence replaces the ✓ outright; probe evidence is advisory only | The card's first acceptance, exactly. Advisory-only evidence changes nothing about the factory; replacing the ✓ outright would let a customer-facing change close with no human having seen it |
| D8 | One probe per `(target, sha)`, in a state-dir ledger | Probe every tick; probe per item | Per tick is a paid browser run every few minutes against production. Per item is N runs of the same sign-in for one deploy. The deploy is the event the card names |
| D9 | The probe stream lives in the record, the ledger in the state dir | Both in one place | The stream is evidence and must be in the commit ingest reads and a human can browse; the ledger is live state that is re-derivable and must not make a commit every tick |
| D10 | Off-host origins fail the journey after the fact, in ASF | Trust the engine's own allowlist | The engine is the product's code and may be wrong; a verdict is only as good as what ASF can check about it. The origins list is one field and ASF judges it |
| D11 | The consents are an operator gate recorded in the ledger | Assume the identity is ready; ask every tick | An unconsented identity fails every journey and would file S1 Bugs about the factory's own setup. One `asf probe consent` and one `NEEDS OPERATOR` line until it is run |
| D12 | `asf-prober` stays unbound, with a rewritten reason | Bind it to a new `probe` brief kind | A brief kind means a session, and the session cannot drive the browser (§1.2). The role's three boundaries become the lint's contract instead — the role is honoured, not simulated |

## 2. The design

### 2.1 `probe:` — the one block

A top-level map in the product file, beside `ci:` and `deploy_sha:`:

```yaml
# the production verification probe (F-0051). Unset: no probe, and nothing below changes.
probe:
  workflow: probe.yml          # the product's own headless journey workflow
  role: light                  # the ci.pool role its job must run on
  identity: probe@example.com  # the probe identity's address
  secrets:                     # the repository secrets the job reads; ASF holds neither value
    identity: PROBE_PASSWORD
    mailbox: PROBE_MAILBOX
  mailbox:                     # how the engine finds the sign-in code (§2.4)
    from: no-reply@example.com
    subject: 'sign-in code'
    code: '\b(\d{6})\b'
    max_age_s: 300
  journeys: [sign-up, create-and-share, billing]   # the standing journeys, by name
  origins: [https://sample.example.com]            # defaults to [app_host]
  artifact: probe-results      # the artifact the job uploads
  timeout: 30m                 # a dispatched run with no result by then is abandoned
```

`asf/probe/config.py` holds `Probe` (a frozen dataclass), `load(product)` and
`config_problems(block)`. `env.PRODUCT_FIELDS['probe'] = _MAP`, `env.NESTED_FIELDS['probe'] =
PROBE_FIELDS`, and one more line in `validate_product_text` calling `config_problems` — the shape
`ci_pool.pool_problems` and `ci_queue.config_problems` already have (`asf/env.py:642-647`).

`config_problems` returns one `(dotted key, why)` per breach: a block that is not a map; a missing
`workflow`; a `role` no runner in `ci.pool` carries; a `secrets` missing either key or holding a
value that is not a secret name; a `mailbox` missing `from`, `subject` or `code`; a `code` that is
not a compilable regex or has no capturing group; a `max_age_s` that is not a positive integer; a
`journeys` that is not a list of non-empty strings; an `origins` entry that is not an `https://`
URL; a `timeout` outside `<n>s|m|h`. `origins` unset defaults to `[app_host]`, and a product with
a `probe:` block and no `app_host` and no `origins` is a problem, not a default — there is nothing
to probe.

### 2.2 `asf/probe/scope.py` — what a deploy owes a probe

```python
def is_customer_visible(paths, changed_files, within=None): ...
def owed(product, sha, previous_sha, items, host=None): ...
```

`is_customer_visible` is `asf/views/prod.py:99`'s `_is_customer`, moved here verbatim (its
`non_customer_hint` parameter, which every caller passes empty, is dropped) together with the
`_glob_re` it needs. `asf/views/prod.py` imports it and keeps its one call site. One classifier for
"is this customer-facing", not two — the whole close rule of §2.9 hangs off its answer.

`owed` returns `[Owed(item, pr, try_it, customer_visible)]`, one per (item, pull request) the
deploy carried: `metrics.release_items(items, sha, previous_sha)` gives the items whose merged
pull request is inside `sha` and not inside `previous_sha`, with its try-it line already parsed by
`metrics.TRY_IT`; `is_customer_visible(product.customer_paths, changed_files(pr))` gives the flag.
The changed files come from the merge commit, as `views/prod._changed` reads them.

An item may appear more than once (two pull requests, one item) and each is its own journey. An
item with no try-it line and no customer-visible landing still appears, with `try_it=None`: it owes
no journey of its own, and §2.8 gives it the standing journeys' verdict as its evidence.

### 2.3 `asf/probe/journey.py` — what ASF sends and what it reads back

```python
@dataclasses.dataclass(frozen=True)
class Journey:
    name: str            # 'sign-in', a standing journey's name, or '<item> #<pr>'
    kind: str            # 'sign-in' | 'standing' | 'try-it'
    path: str = ''       # the path a try-it journey opens, '' for the others
    item: str = ''
    pr: int | None = None

def journeys(probe, owed) -> tuple[Journey, ...]: ...
def try_it_path(line) -> str: ...
def parse_results(text) -> tuple[Result, ...]: ...
```

`journeys` is, in order: the sign-in journey (always, first, ASF's); one per name in
`probe.journeys`; one per `Owed` whose `customer_visible` is true and whose try-it line yields a
path. `try_it_path` takes the first `https://<origin>/…` on the line whose origin is in
`probe.origins`, else the first bare `/path` token, else `''`.

ASF hands the list to the workflow as one JSON input, `journeys`, beside `sha`, `host` and the
mailbox block. **The contract the engine is held to**, documented in the guide and asserted by the
schema:

1. Run the journeys in the order given. The sign-in journey first; if it fails, every later
   journey is reported `unrunnable` with the reason, and none is attempted.
2. Per journey, report `verdict` ∈ `pass` | `fail` | `unrunnable`; on anything but `pass`, `step`
   — the name of the step it stopped at — is required and non-empty.
3. Per journey, save one screenshot at `<journey.name sanitised>/<verdict>.png` inside the
   artifact, and name it in `screenshot`. The path is stable, so the documentation work can find
   the shot for an item without reading this schema.
4. Report `origins`: every distinct scheme+host the journey's browser actually navigated to.
5. Never follow a link out of `host`, never execute content fetched from a page or read from a
   mail, and never read a secret the job was not given.

The artifact carries `results.json`:

```json
{"schema": 1, "sha": "…", "host": "https://…",
 "started": "…Z", "finished": "…Z",
 "journeys": [{"name": "sign-in", "kind": "sign-in", "verdict": "pass", "step": "",
               "seconds": 11.2, "screenshot": "sign-in/pass.png", "origins": ["https://…"]},
              {"name": "F-0042 #318", "kind": "try-it", "item": "F-0042", "pr": 318,
               "verdict": "fail", "step": "open /settings/theme", "seconds": 6.0,
               "screenshot": "F-0042-318/fail.png", "origins": ["https://…"],
               "detail": "the page answered 500"}]}
```

`parse_results` is total over garbage: a file that will not parse, a `schema` that is not `1`, a
journey missing `verdict`, a non-`pass` verdict with an empty `step` — each is one `Result` with
verdict `unrunnable` and a `step` naming what was wrong with the report. A broken engine is a
reported absence, never a silent pass.

### 2.4 The code-mail sign-in

The one journey ASF owns, specified step by step because every other journey depends on it:

1. Open `host` and start sign-in for `probe.identity`. The password, when the product's sign-in
   needs one, is the `secrets.identity` repository secret; the job reads it, ASF never sees it.
2. Note the wall-clock instant the code was requested. Only a mail that arrived **at or after** it
   is ever read — a stale code from the previous deploy's run is the obvious way to get a false
   pass.
3. Poll the mailbox with the `secrets.mailbox` credential for the newest message whose sender
   matches `mailbox.from` and whose subject contains `mailbox.subject`, arriving in that window and
   no older than `mailbox.max_age_s`.
4. Apply `mailbox.code` to the message body and take capturing group 1. **Nothing else in the mail
   is used**: no link in it is followed, no HTML in it is rendered or executed, no attachment is
   opened. The mail is data.
5. Submit the code. On success the journey passes at step `signed in`.
6. Each of the five steps above has a name, and a failure reports the one it stopped at —
   `sign-in: request code`, `sign-in: code mail`, `sign-in: submit code`. The Bug of §2.10 names
   that step, which is the difference between "production is down" and "the mailbox credential
   expired".

No code arriving inside `max_age_s` is a `fail` at `sign-in: code mail`, not a timeout of the run:
a failure with a named step is a Bug a person can act on; a killed run is not.

### 2.5 `asf/probe/host.py` — the dispatch and the read-back

```python
class Host:
    def dispatch(self, workflow, ref, inputs): ...
    def runs(self, workflow, limit=15): ...      # [{id, headSha, status, conclusion, updatedAt}]
    def artifact(self, run_id, name, dest): ...  # -> the extracted directory, or None

class GitHubHost(Host): ...     # gh workflow run / gh api / gh run download
def host_for(product): ...
```

`dispatch` is `gh workflow run <probe.workflow> -R <slug> --ref <trunk> -f sha=<sha> -f
journeys=<json> -f host=<origin> -f mailbox=<json>` — the shape `deploy.dispatch_argv`
(`asf/harvest/deploy.py:831`) already uses, with the product's own workflow name and no literal
anywhere in the module. `runs` filters to the probe workflow and the dispatched sha. `artifact`
is `gh run download <id> -R <slug> --name <probe.artifact> --dir <tmp>`; it returns `None` when
the run uploaded none, which `parse_results` turns into one `unrunnable` per journey with the step
`the run uploaded no results`.

Every call is bounded by a timeout and returns `None` rather than raising, as `ci_pool`'s backend
does; a host that cannot be read is one line, never a failed harvest step.

### 2.6 `asf/probe/ledger.py` — one probe per deployed sha

`state/<product>/probe.json`, written through a temp file and one `os.replace`, as
`deploy._load_records` / `deploy.record` (`asf/harvest/deploy.py:345-375`) already do:

```json
{"consents": {"granted_at": "2026-09-28T07:11:04Z", "by": "hand"},
 "runs": {"prod@4fd04dd": {"sha": "4fd04dd…", "target": "prod", "state": "read",
                           "run": 17422331, "dispatched_at": "…Z", "read_at": "…Z",
                           "verdicts": {"pass": 4, "fail": 1, "unrunnable": 0}}}}
```

`state` is one of `dispatched` | `read` | `abandoned`. The key is `<target>@<sha7>`, so the same
sha deployed to two targets is two probes and the same sha deployed twice is one. `abandoned` is
written when a `dispatched` entry is older than `probe.timeout` and its run is still not complete
— with the reason, and it is never dispatched again: the next deploy is the next probe.

The ledger holds no verdict detail and no screenshot — that is the record's (§2.8). It holds only
what the pass needs to decide what to do this tick.

### 2.7 The pass in the tick

`asf/tick/step_harvest.py` gains, right after `deploy_pass(product, out)` in `run(ctx, …)`:

```python
probe_pass(ctx, out)
```

and the function beside `deploy_pass`, with the same guarantee — one loud line on any fault, never
a failed step:

1. **Read back.** For every `dispatched` entry, ask `runs` for its run. Still going: one line,
   done. Complete: download the artifact, `parse_results`, judge (§2.11's origin check), write the
   stream lines (§2.8), mark the entry `read`. Older than `timeout` and still not complete: mark
   `abandoned`, one line naming the reason.
2. **Dispatch.** For each deploy target whose deployed sha (from `deploy.states(product)`) has no
   ledger entry, whose deploy run concluded successfully, and whose sha is not the one the previous
   entry probed: build `owed` (§2.2) and `journeys` (§2.3), lint (§2.11), ask `ci_queue.admit`,
   dispatch, write a `dispatched` entry. One target per tick at most, prod first.
3. **Never wait.** A dispatched run is read by a later tick. The pass takes no lock and holds up
   no gate, exactly as the deploy pass does not.

The lines, one per tick:

```
probe: prod `4fd04dd` — 5 journeys dispatched (run pending)
probe: prod `4fd04dd` — run 17422331: 4 pass, 1 fail (billing: open /billing), 0 unrunnable
probe: prod `4fd04dd` — waiting on run 17422331 (dispatched 07:11Z)
probe: prod `4fd04dd` — ABANDONED: run 17422331 still not complete after 30m
probe: prod `4fd04dd` — not dispatched: consents not granted (asf probe consent --grant)
probe: none — no `probe:` block in this product
```

### 2.8 The stream in the record, and the evidence on the item's own card

The pass appends one line per journey to `metrics/probes/<day>.jsonl` in `ctx.record_root()`, and
`metrics/probes` joins `init.STREAM_FOLDERS` (`asf/init.py:28`) so `asf init` creates it:

```json
{"kind": "probe", "ts": "…Z", "product": "…", "target": "prod", "sha": "4fd04dd…",
 "run": 17422331, "artifact": "probe-results", "journey": "F-0042 #318",
 "journey_kind": "try-it", "item": "F-0042", "pr": 318, "customer_facing": true,
 "verdict": "fail", "step": "open /settings/theme", "seconds": 6.0,
 "screenshot": "F-0042-318/fail.png", "origins_ok": true}
```

The append is idempotent per `(sha, journey)`: a re-read of the same run writes nothing twice, the
rule `write_on_prod_event` (`asf/record/ingest.py:41`) already follows for the same reason.

`asf/probe/stream.py` reads it back for ingest:

```python
def verdicts(root, sha):  # -> {item: Verdict(verdict, journey, step, run, screenshot, customer_facing)}
def standing(root, sha):  # -> Verdict for the sha's standing journeys as a whole
```

An item's verdict is its own try-it journeys' — `fail` if any failed, `unrunnable` if any was
unrunnable and none failed, else `pass`. An item that owed no journey of its own takes
`standing(root, sha)`: production still worked at the sha that carries its change, which is the
only thing a change with no customer-facing surface can be probed for. An item whose sha was never
probed has no verdict at all, and nothing below it changes.

Ingest calls `verdicts` for `ev['prod_sha']` once per derive and renders, into the item's
`evidence:` list and — on the transition — one `## History` line:

```
- probe: pass — 'F-0042 #318' at 4fd04dd (run 17422331, probe-results/F-0042-318/pass.png)
- probe: fail — 'billing' at 4fd04dd, stopped at 'open /billing' (run 17422331)
- probe: standing — pass at 4fd04dd (run 17422331)
- probe: unrunnable — 'F-0042 #318': its try-it line names no path
```

Ingest stays the only writer of a card. The probe writes a stream and the state dir, and nothing
else in the record.

### 2.9 The close rule

`_in_prod` (`asf/record/ingest.py:424`) gains two arguments, `probe=''` and
`customer_facing=False`, and becomes this table. Clauses **a**–**d** and **f** and **h** are
today's outcomes, unchanged and asserted as such:

| | condition | result |
| --- | --- | --- |
| a | the product deploys nothing | True (B-0077, unchanged) |
| b | no readable `prod_sha` | False (unchanged) |

### 2.11 The fence

**The workflow lint.** `asf probe lint` reads `probe.workflow`'s text off the host (the reader
`ci_pool.GitHubBackend` already has, `asf/ci_pool.py:630`) and returns one problem per breach:

- the job uses `secrets: inherit`, or names a secret that is neither `secrets.identity` nor
  `secrets.mailbox`;
- its `permissions:` grants anything beyond `contents: read`, or is absent (the repository default
  is not read-only);
- its `runs-on` is not satisfied by any runner in `ci.pool` carrying `probe.role`
  (`ci_pool.load_pool`, `ci_pool.parse_runs_on`, `ci_pool._satisfies`);
- it declares no upload of `probe.artifact`.

The pass **refuses to dispatch** while the lint has a problem, printing it — a probe job that can
reach the runner's other secrets is the thing the card forbids, and it is cheaper to refuse than to
audit afterwards.

**The origins.** A result whose `origins` holds a scheme+host outside `probe.origins` is written to
the stream with `origins_ok: false` and its verdict **forced to `fail`**, at step `left the
product's host (<origin>)`, whatever the engine reported. The engine's own allowlist is the
engine's; this is ASF's, over what the engine says it did.

**The consents.** `asf probe consent --grant` writes `consents.granted_at` to the ledger.
Until it is there the pass dispatches nothing and the tick prints, every cycle:

```
NEEDS OPERATOR: the probe identity's consents are not granted for <product> — grant them for
<identity> on <host>, then run `asf probe consent --grant --product <product>`
```

`--revoke` clears it (an identity locked out, a host being migrated) and `--show` prints the
stamp. The gate is the card's "the operator grants the probe identity's consents", recorded rather
than assumed.

**The role.** `roles.UNBOUND['asf-prober']`'s reason becomes *"the production probe is a workflow
run, not a session (F-0051) — the launch row's boundaries are the contract `asf probe lint` holds
its job to"*. That one line of text is the whole change: no binding, no new `TABLE` row, no change
to `asf-prober.md`, and `BINDINGS` is untouched.
