# F-0154 — five measured costs, and the same move four times

`29654dc1c` took the tick's Python CPU from 91 s to 22 s. The profile that followed it named what
is left, and this card carries those five items. They are measurements, not guesses, and four of
the five turn out to be the same defect wearing five coats: **a pass asks the same question of the
same unchanged thing several times over, because nothing in the pass remembers the answer.**

The exception is the first one, and it is not a performance item at all once you read it closely.
The flaky pass pages **a week of every workflow's runs on every tick** — 26–31 s of wall time — and
then filters that list in Python by comparing each run's *display name* to `conventions.ci_workflow`.
But `ci_workflow` is documented as, and everywhere else in this codebase consumed as, the workflow
**file name**: `deploy.py:346` and `evidence.py:551` both hand it to `gh run list --workflow`, which
takes a file name, an id or a name. The flaky pass is the one consumer that matches on the display
name instead — so for the documented config form it lists a week of runs, discards every one of
them, and files nothing. It is 26 s spent to reach zero.

So the shape of this spec is:

1. **The flaky pass asks the workflow for its own runs** — by id, resolved from the selector the
   product actually configured — over a window that starts where the last pass finished. The
   silent truncation at the API's 1,000-result cap goes with it, and the pass starts reading runs
   it has never been able to see.
2. **Four per-pass snapshots**, all the same shape as `lifecycle.RemoteHeads` (`:1750`) — the object
   this factory already built the last time it noticed a pass asking one question thirty times.
   Each is an optional keyword whose default is *exactly today's behaviour*, so a caller that does
   not pass one is not changed at all: the worktree's `git status`, the record's parsed cards, the
   lane's git facts about a branch, and the ingest's document lookups.

Nothing in here changes a verdict. Every one of the five is the same answer, reached with fewer
processes — and the acceptance tests are written as process counts, because for this card that *is*
the behaviour under test.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | Resolve `conventions.ci_workflow` to a numeric workflow id once per pass, through one `repos/{slug}/actions/workflows` listing, matching a workflow whose `id`, `name` or `path` basename equals the configured value; then list `repos/{slug}/actions/workflows/{id}/runs` | Passing the configured string straight into the URL path (the endpoint accepts a file name); `gh run list --workflow <wf>` as `deploy.py` does | The configured value may be either form (P2), and only the listing can tell which — putting a display name in the URL path 404s, and putting a file name through P1's filter reads nothing. One extra request per pass buys a selector that cannot be wrong either way. `gh run list` was the alternative to beat: it has no `--created` on every version this factory may run against, and `runs()` already speaks `api` + `--jq` |
| D2 | When resolution finds no workflow: print one line naming the configured value and the names it did see, then fall back to P1's listing and filter unchanged | Returning no runs; raising | A product whose selector this cannot place keeps exactly today's behaviour, and the line says why it is slow. A silent zero is the defect this card is fixing, not one to add |
| D3 | The workflow id is held on the `GitHubRuns` instance — one per pass — and never persisted | `state['workflow_id']` in `flaky.json` | A persisted id goes stale when the workflow file is renamed or replaced, and the failure is a silent zero again. One cheap request per pass against 25 s saved is not a trade worth thinking about (O6) |
| D4 | The listing window starts at `state['window_from']`: `now - SINCE_OVERLAP_HOURS` when the pass read everything it listed, or one second before the **`created_at`** of the oldest run it left unread; floored at `now - LOOKBACK_DAYS` | Narrowing the window to `state['last_pass']`, as the card's first sentence suggests | `MAX_RUNS_PER_PASS` and a failed `jobs()` listing both leave runs unread (P3), and today's fixed 7-day window is the only thing that brings them back. A window that moves to the last pass would step over them and **lose flakes** — a correctness regression in the name of speed. `window_from` moves forward only over runs that were actually read |
| D5 | The window is computed from `created_at`, and `runs()` returns it beside `ts` | Reusing `ts` (`updated_at or created_at`, `flaky.py:296`) | The API filters on `created`, and a long run is created well before it completes: a run created at 10:00 and finished at 10:30 would be excluded by a window of `created >= 10:29:59`. Mixing the two clocks loses exactly the runs the overlap exists to catch |
| D6 | `SINCE_OVERLAP_HOURS = 24` | An overlap of one tick interval | The overlap must exceed the longest run that can start before a pass and finish after it. A re-listed run is free — `seen` drops it before any log is read (P3) — so the only cost of being generous is listing rows, and 24 h of one workflow is a page |
| D7 | One `git status --porcelain` per worktree per pass, from a `WorktreeStatus` snapshot keyed on `(realpath(wt), HEAD sha, index mtime_ns, index size)`, threaded as `status=None` through `gather`, `unpublished` and their health callers | A pass-scoped memo keyed on the worktree path alone | P5 is decisive: the factory commits, resets, cherry-picks and pushes *inside* the pass, and re-gathers immediately after each. A path-keyed memo would answer those re-gathers with the pre-mutation status and call a just-published run unpushed. Every one of those mutations moves HEAD or the index, so this key misses exactly when it must |
| D8 | `--untracked-files` stays at its default everywhere in the health path | `--untracked-files=no`, the card's first suggestion | An untracked file is counted work today: it is a porcelain line, so `ev.uncommitted > 0`, so `Evidence.pushed` is False and B-0051 holds the run (P4). `-uno` would silently pass a session that wrote a new file and never added it — turning a held run into a finished one, which is the exact failure B-0051 exists to catch. A spec that traded that for 5 s would be trading the wrong thing |
| D9 | The card cache is validated by **content**, not by mtime — `load_items` reads the text as it does today and compares it to the cached text before reusing the parse | `(path, mtime_ns, size)` as the key | `_REGISTRY_CACHE` already made this choice for the same reason (P8): `load_items` must read the file anyway, because the record it returns carries `text`. With the read paid for, content equality has *no* staleness window at all, and there is nothing for a coarse filesystem clock or a same-nanosecond rewrite to defeat |
| D10 | Every hand-out is a copy: the dict, `entries`, `machine_keys`, `comments`, and every container value copied through | Handing out the cached `FrontmatterDict` | P7: callers mutate `rec['meta']` in place and reassign `meta.machine_keys`. | D11 | The lane cache is keyed on the resolved shas of the two refs, read with one `git rev-parse origin/<trunk> origin/<branch>`; a ref that does not resolve bypasses the cache and calls through | Keying on `(repo, trunk, branch)` with an `invalidate()` the lane calls after a fetch or a rewrite | The lane fetches, rebases, rewrites and archives branches mid-pass. | D13 | `plan_order.trunk_reader` returns a `TrunkReader` object: callable with one path exactly as today, plus `prefetch(paths)`; `backfill` and `overlay` call `prefetch` only when the reader they were handed has it | Changing the `read_plan(path)` contract to `read_plans(paths)` | Every test injects a bare callable as `read_plan`, and `overlay` is called from the wave with a reader built elsewhere. ## The design

### 1. The flaky pass asks one workflow for its own runs

`asf/tick/flaky.py`. Two new constants beside the existing ones:

```python
#: How far back the window may ever reach — the floor under ``window_from`` (D4).
LOOKBACK_DAYS = 7                   # unchanged
#: The steady-state window: longer than any single run, so a run created before the last pass and
#: completed after it is still listed (D5, D6).
SINCE_OVERLAP_HOURS = 24
#: A listing this long has hit the API's result cap: runs older than it are unreachable (D3).
TRUNCATED_ROWS = 1000
```

`GitHubRuns` gains one method and `runs()` changes shape:

```python
def workflow_id(self, selector):
    """The numeric id of the workflow ``selector`` names — its own id, its display ``name``, or
    its file name (``conventions.ci_workflow`` may hold any of the three, P2) — or None with the
    names that were seen, for the caller's one line (D2). Resolved once per instance (D3)."""

def runs(self, workflow, since):
    """``[{id, name, branch, ts, created, url}]``: the completed runs of ``workflow`` created on
    or after ``since`` (an ISO timestamp). One workflow's runs, asked of the workflow (D1) —
    ``repos/{slug}/actions/workflows/{id}/runs`` — so no display-name filter stands between the
    listing and the pass. When the selector resolves to nothing the listing falls back to every
    workflow's runs with the old filter, unchanged (D2)."""
```

`created` joins the row (D5); `ts` keeps its meaning (`updated_at or created_at`). The three-method
seam is untouched, so `tests/test_flaky.py`'s `FakeRuns` still answers for the whole pass.

`collect` changes in three places and nowhere else:

```python
since = window_since(state, now)                      # D4: state['window_from'], floored
listed = source.runs(workflow, since)
if len(listed) >= TRUNCATED_ROWS:
    out(f'file-bugs: flaky — {len(listed)} runs listed since {since}: the window is truncated, '
        f'runs older than it cannot be read')          # D3
unseen = sorted((r for r in listed if str(r['id']) not in state['seen']), key=lambda r: r['ts'])
batch, deferred = unseen[:MAX_RUNS_PER_PASS], unseen[MAX_RUNS_PER_PASS:]
...                                                    # the read loop, unchanged
unread = deferred + [r for r in batch if r['id'] in failed_jobs]
state['window_from'] = next_window(unread, now)        # D4: oldest unread created_at − 1s, or
                                                       # now − SINCE_OVERLAP_HOURS; floored at
                                                       # now − LOOKBACK_DAYS
```

`record_run`, `severity`, `file_or_update`, `file_flaky_bugs` and `run_pass`'s approval branch are
not touched (O2). `state['last_pass']` keeps being written and keeps meaning what it says; the
window reads `window_from`, which a state file written by an older version simply does not have —
and its absence is the full `LOOKBACK_DAYS` window, which is today's behaviour.

What it looks like when it is there: the pass makes two requests plus one per unread run instead of
paging a week of everything, and a product configured the documented way starts filing the flaky
Bugs it has never filed.

### 2. One `git status` per worktree per health pass

`asf/workers/lifecycle.py`, beside `RemoteHeads` and following it exactly:

```python
class WorktreeStatus:
    """``git status --porcelain`` for one pass over many worktrees: one process per worktree per
    *version* of that worktree, where the pass runs one per question — ten a run (P4).

    Keyed on what a change to the worktree moves: its HEAD sha, and the size and mtime of its own
    index (a linked worktree's index lives in its own git dir, not the common one). Every mutation
    the factory makes inside a pass — ``commit_leftovers``, ``publish``, the repair's ``reset``
    and ``cherry-pick`` — moves one of the two, so the re-gather that follows it is a miss by
    construction (P5, D7). A worktree whose git dir cannot be read is never cached: it is asked
    every time, exactly as today."""

    def lines(self, wt):
        """The porcelain lines, or None when the worktree is not one."""
```

`--untracked-files` is not passed (D8). The key's git dir is read off the files the way
`_common_git_dir` (`:1726`) already does, stopping at the worktree's own git dir rather than
following `commondir` — no subprocess for the key.

Threaded as an optional keyword, default `None` meaning *ask*, through `gather(product, run,
alive=None, worktree=None, heads=None, status=None)` and `unpublished(wt, branch, main='main',
status=None)`. `health.health` builds one beside the `RemoteHeads` it already builds at `:810` and
passes it to every `gather` in the pass; the double gather at `:816`/`:819` becomes one process, and
the per-run sites (`:385`, `:407`, `:415`, `:528`, `:689`, `:699`, `:715`) share the snapshot with
each other and with the reap loop. The `heads=` gap at those sites stays as it is (O4).

The five helpers in `health.py` that no caller anywhere in `asf/` or `tests/` reaches —
`pushed` (`:274`), `push_gap` (`:295`), `result_reason` (`:306`), `has_commits` (`:317`),
`worktree_empty` (`:352`) — are not given the keyword and not otherwise touched. They are dead
against `lifecycle.gather`/`derive`; naming them here is the record of that, not a licence to
delete them under a performance card.

### 3. A card is parsed once per version of its text

`asf/record/frontmatter.py` gains the copy P7 makes necessary:

```python
def clone(meta):
    """A fresh :class:`FrontmatterDict` with the same fields and the same formatting metadata —
    ``entries``, ``machine_keys``, ``comments`` — and every container value copied through, so a
    caller that mutates what it was handed (``rec['meta']['blockedBy'] = …``, a reassigned
    ``machine_keys``) touches nothing else (P7, D10). Scalars are shared; they are immutable."""
```

`asf/record/core.py`, the `_REGISTRY_CACHE` shape (P8, D9):

```python
#: One parse per card per version of its text. Keyed on the absolute path, validated on the text
#: itself: `load_items` reads the file either way, because the record it returns carries `text`.
_PARSE_CACHE = {}
_PARSE_CACHE_MAX = 4096    # above any record's card count: a smaller cap thrashes, it does not bound

def clear_parse_cache():
    """Forget every parse. For a test that writes a card behind the cache's back."""
```

`load_items`'s loop keeps its read and its `FrontmatterError` handling — a file that fails to parse
is not cached, so its error is reported on every call as it is now — and gains four lines: look up
by path, reuse when the cached text equals the text just read, otherwise parse and store, then hand
out `frontmatter.clone(meta)` with the shared `body` and `text` strings.

What it looks like when it is there: the record step's thirteen-plus `load_items` calls (P6) parse
the corpus once between them. The copy-out is not free, so the honest claim is *most* of the
card's 1–2 s, not all of it — and the test that proves it counts parses, which is the part this
change controls.

### 4. The lane's git facts, keyed on the shas they were read from

`asf/harvest/lane.py`, beside the three functions:

```python

    """``(trunk_sha, branch_sha)`` in one ``git rev-parse``, or None when either ref does not
    resolve — the caller then answers uncached, exactly as today."""

def clear_facts():
    """Forget every cached fact. For a test, and for a pass that wants to prove it re-reads."""
```

`touched_files`, `already_on_trunk` and `own_commits` keep their signatures and their return
shapes. Each resolves the pair first; on a hit it returns the stored answer, on a miss it does
what it does now and stores it. `already_on_trunk`'s key carries `item` and the deliverable path
too, because its answer depends on them (`deliverable_of`, `:834-839`); `own_commits` stores the
whole `(base, shas, why)` triple, refusals included — a branch with a merge on it is refused for
the same reason every time it is asked, until someone rewrites it and the key changes.

The hand-rolled version at `lane.py:1336` (`read once: nothing fetches before its 2nd use`) can
keep passing `files=`; it is correct and the cache makes it redundant rather than wrong.

What it looks like when it is there: the second and later questions about one branch cost one
`rev-parse` each instead of a `diff` (`touched_files`), a `diff` (`already_on_trunk`) or five
processes (`own_commits`).

### 5. The batched reads

**`doc_carriers`** (`asf/evidence/evidence.py`) gains a warmable companion:

```python
class DocCarriers:
    """Where each of many typed document paths lives, in one ``cat-file --batch-check`` (D12).

    ``warm(paths, branches)`` asks for the whole path × branch cross product at once;
    ``carriers(path, branches)`` answers ``(on_trunk, [branches])`` from that, and falls back to
    one :func:`doc_carriers` call for a path it was never warmed with."""
```

`doc_carriers` itself stays exactly as it is — it is the fallback and the single-path API.
`asf/record/ingest.py`: `derive` builds one `DocCarriers`, warms it from the `links.spec` and
`links.plan` of every card in `canonical` plus `ev['branches']`, and hands it to `_spec_home` and
`_plan_home` as an optional argument (default `None` → today's per-card `doc_carriers` call).

**The plan readers.** `plan_order.trunk_reader(product)` returns a `TrunkReader` (D13): callable
with one path as now, plus `prefetch(paths)` which reads the lot in one `read_refs` and serves from
it. `backfill` (`:259`) and `overlay` (`:298`) already compute their plan-path list before their
loop; each calls `prefetch` on the reader it was handed when the reader has one, and is otherwise
unchanged — a test's bare lambda has no `prefetch` and is not affected.

**`plan_tasks._mint`** splits into a collection pass and the minting loop (D14), with one
`evidence.read_refs` between them. The injected `read_ref` parameter stays for the tests that use
it; when it is given, the collection pass calls it per ref as now.

What it looks like when it is there: the ingest makes one `cat-file --batch-check` process where it
made one per card, and each plan reader two processes where it made two per plan.

## Acceptance tests

Every block is runnable from the repo root, as the suite runs them — one module per process,
hermetic (`tools/run_tests.py`).

Four of the five are process counts. That is deliberate: the behaviour this card changes *is* the
number of subprocesses a pass spawns, so a test that asserts only "the answer is still right" would
pass against the unfixed code. Each block below therefore does both — the count, and the answer.

### 3.1 The flaky pass

```bash
python3 -m unittest tests.test_flaky -v
```

New `WorkflowSelector`: with a `_run` double capturing argv, `workflow_id` resolves a selector that
matches a workflow's `name`, one that matches its file name, and one that is already the numeric id,
each to the same id, with **one** `actions/workflows` request for the instance however many times it
is asked (D3); `runs()` then requests `actions/workflows/<id>/runs` and applies no display-name
filter, returning a row whose `name` differs from the selector (P2's case — the row today's code
discards); an unresolvable selector prints one line naming the configured value and falls back to
`actions/runs` with the old filter, and the fallback's rows are exactly today's (D2).

New `PassWindow`: `window_since` on a state with no `window_from` is `now - LOOKBACK_DAYS` (an old
state file reads as today's behaviour); on one with a `window_from` inside the lookback it is that
value; on one older than the lookback it is the floor (D4). After a pass that reads everything,
`state['window_from']` is `now - SINCE_OVERLAP_HOURS` (D6); after a pass that leaves runs unread —
more than `MAX_RUNS_PER_PASS` unseen, and separately a run whose `jobs()` returns None — it is one
second before the oldest unread run's **`created_at`**, not its `ts` (D5), so the next pass's
window still lists it; and a run left unread by two passes running is read by the third rather than
stepped over. Truncation: a listing of `TRUNCATED_ROWS` rows prints the line and still reads its
batch (D3).

`PassTests`, `parse_flaky`'s tests and `test_only_the_ci_workflow_is_read` stay green unchanged —
the fake's three methods are the seam, and `collect`'s counting is untouched (O2).

### 3.2 One status per worktree

### 3.3 The card parse cache
