# F-0104 — the install that ticks, not the install that upgrades

`asf upgrade` reinstalls one thing: `pipx install --force git+<url>@<ref>`, which lands in the pipx
venv named by the distribution — `asf-factory` — and nothing else (`asf/upgrade.py:319-321`,
`:53`). It then verifies that one venv (`:472-480`), records the sha (`:266-267`) and prints
`upgrade: installed <sha>`.

A product's clock runs whatever its launchd plist names, and that is a different question. The
plist's `ProgramArguments[0]` is the `sys.executable` of the process that *wrote* it
(`asf/scheduler.py:201-213`, `:356-370`) — so a machine holding a pinned live install beside an
editable dev install, which F-0111 already found in the field and named
(`docs/specs/f-0111.md:9-11`, P3: "a pipx install made with `--suffix <s>` exposes it as `asf<s>`
… so one machine can hold several installs"), has clocks pointing at a venv `asf upgrade` never
touches. The upgrade succeeds, prints the new sha, records it — and the product keeps ticking the
old one. Nothing in the output or in `asf doctor` says so.

The other half is what the clock runs when the package is a checkout. `asf/snapshot.py` makes that
safe against a torn tree — the clock runs an immutable worktree of the checkout's `HEAD`, never the
live files — but safe is not *merged*: a checkout sitting on a branch ticks that branch's code into
the product. The doctor's one existing row here, `clock code`, reports the snapshot's sha against
the **checkout's own HEAD** and returns `ok` unconditionally, on a row registered `required=False`
so a failure would print `skip` rather than RED (`asf/doctor.py:350-362`, `:854-855`, `:1063-1077`).
There is no row that names which install a clock runs, and none that compares what ticks against
`origin/main`.

This card is: **the install each product clock runs is read from that clock's own plist — named,
sha'd and measured against `origin/main` in `asf doctor`, RED when it is editable or unmerged — and
`asf upgrade` reinstalls the venvs the clocks name, suffix and all, saying plainly when its install
is not the one that ticks.**

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | **The plist is the authority on which install ticks.** The new reader answers from `ProgramArguments` and `EnvironmentVariables`, and nothing else. | Asking the operator config which venv is live; asking `pipx list` which install is "the live one". | The plist is what launchd actually executes (P3, P4). A config key would be a second answer that drifts from the first, and `pipx list` cannot tell which of two installs a clock fires. This also makes the reader honest about a plist an older `asf` wrote, or one written by hand. |
| C2 | **A new module, `asf/clockinstall.py`.** | Growing `asf/drift.py`; growing `asf/scheduler.py`; putting it in `asf/upgrade.py`. | Both `asf/doctor.py` and `asf/upgrade.py` must read it, and `asf/upgrade.py` already imports `scheduler` lazily to avoid a cycle. `drift` answers for the *running* install (P7) and is imported by `upgrade`; `scheduler` is imported by nearly everything and must not start reading dist-info. A leaf module importing `env`, `scheduler`, `snapshot` and `drift` and imported by `doctor` and `upgrade` keeps the graph as it is. Named for the doctor row it feeds, and deliberately not `asf/install.py` (the `asf install` command) or `scheduler.clock_code` (the snapshot reader). |
| C3 | **Five kinds: `pinned`, `editable`, `snapshot`, `checkout`, `unknown`** — with the pipx venv name and its suffix carried beside the kind, so a suffixed install is `pinned` in venv `asf-factory<suffix>`, not a kind of its own. | A boolean `is_editable`; a kind per venv. | The kinds are what the RED rule and the upgrade's target set branch on; the venv name is what `pipx` needs on the command line. Keeping the suffix as data, not as a kind, is what makes one code path serve one install or three. |
| C4 | **The new row is added; the existing `clock code` row is left exactly as it is.** | Replacing `check_clock_code` with the per-clock rows. | They answer different questions from different sources: `clock code` reads `code/current`, written by the launcher at tick time — *what the last tick really ran* — while `clock install` reads the plist — *what the next tick will run, and whether it is a pinned merged install*. Replacing it would also rewrite two passing tests that never touch a plist (P13) for no gain, and drop the "the next tick takes it" line the snapshot arrangement needs. |
| C5 | **One row per clock, registered `required=True`.** | One folded row for the product; keeping `required=False`. | The card asks for RED, and `required=False` can only ever print `skip` (P5). One row per clock is what makes a product whose fast clock is pinned and whose daily clock is stale readable at a glance, and the labels are already the units the `SCHEDULER` section reports in. |
| C6 | **RED on the kind for `editable`, `checkout` and `unknown`; RED on a `snapshot` clock of a product whose repo is not the factory's source; RED for any kind whose sha is not an ancestor of `origin/main`.** | RED on `editable` alone, as the card's words say. | The card's own reason for the row is that "unmerged work never [reaches products]", and an editable install is only one of the three ways that happens. A `snapshot` clock is the factory's *own* documented dev arrangement (`asf/snapshot.py`), so it is not red for being a snapshot — but on a customer product it means the same thing an editable install means, and on any product it is red while the sha it ticks is off the trunk. |
| C7 | **A clock whose sha is off `origin/main` is RED even for the factory's own product** — including the ordinary case of an operator's checkout sitting on a branch. | Green (or `skip`) for the factory's own product, so a working checkout never reads red. | The row's whole claim is "what ticks is merged". A snapshot clock on a branch ticks that branch into the product, which is the incident this card exists for; a doctor that stays green through it is a doctor that never would have caught the original one. The row names the sha and `origin/main`'s sha, so the cost of the RED is one line the operator can read and dismiss, and clearing it is one `git checkout <trunk>` or one pause. |
| C8 | **Behind-ness and merged-ness are read from a local `origin/main` ref — no `git fetch`, no `git ls-remote`.** | `git ls-remote <url> main` per doctor run, so the answer is current to the second. | `drift` already answers the same question from the local ref (P7), and `asf doctor` is run on a red factory, in a terminal, sometimes with no network. A stale ref cannot make the row silently wrong either: the row prints the `origin/main` sha it compared against, so a stale ref is visible in the row itself. |
| C9 | **The trunk is read from the ASF source checkout on this host** — `drift.factory_root()`, else the first configured product whose `repo_dir` is the factory's source — and when there is none, no behind/merged judgement is made and the row says so. | Requiring the product's own repo to be the ASF repo (what `drift.check` does). | A customer product's clock runs the ASF live install while its `repo_dir` is its own application repo; `drift.check` returns `None` for exactly that product, which is why nothing measures it today. A host with a pinned install and no ASF checkout can still say which venv ticks and at what sha — it just cannot count the distance, and saying "cannot tell" is not the same as saying "ok". |
| C10 | **`asf upgrade` reinstalls every distinct pipx venv the product clocks name, plus the venv it is running from; clock venvs first, the running one last.** | Only the running venv (today); only the clock venvs. | The card's first bullet is exactly this. Clock venvs go first because reinstalling the running venv swaps files under this very process — the hazard the module docstring already names — and the install the products tick must land even if this process is torn afterwards. The running venv stays in the set so `asf` on PATH and the schema table it prints still mean what they say. |
| C11 | **An `editable` venv is never reinstalled — it is named, with the installer as the repair.** | Converting it to a pinned install, which is what the card's "move it to the merged head" would do most directly. | `pipx install --force git+…` over an editable venv silently destroys a working development install the operator is using from their own shell. `tools/install.sh` already owns replacing an editable install, under a tick lock and by explicit invocation. An upgrade that eats a dev install once is an upgrade nobody runs again. |
| C12 | **Where the upgrade's install is not the install that ticks, it says so per clock, and adds a `NEEDS OPERATOR` line for a product that is not the factory's own source.** | Refusing the whole upgrade; exiting non-zero. | The install still has to happen — `asf` on PATH, the schema check, the factory's own next tick all depend on it. What must stop is the *implication* of `upgrade: installed <sha>`: the line that follows it names the clock, the kind and the fact that this install is not the one ticking that product. Exiting non-zero would make the factory's own auto-upgrade (P10) report a failure for a state it cannot fix by itself. |
| C13 | **`upgrade_command` grows a third, defaulted argument `suffix=''` and writes `--suffix=<s>`.** | A new function; passing the venv name; `--suffix <s>` as two argv entries. | The default keeps every existing caller and `tests/test_install.py`'s pinned assertion (`['pipx','install','--force','git+…@abc']`) true, which matters while F-0207 is in flight over the same file (P12). The `=` form is not a style choice: the two-argv form exits 2 for any suffix starting with `-` (P11). |
| C14 | **`new_install_commit` takes the venv to verify and keeps its interpreter spawn; `clockinstall` reads a venv's commit off disk.** | One reader for both. | The verification must read what an *import* of the just-installed package resolves, immediately after `pipx install --force` in the same process (P2), and `FakeRun` pins that call; the doctor must read up to one venv per clock without spawning an interpreter for each, including venvs whose python it will never run. The disk reader is also `new_install_commit`'s fallback when the spawn answers nothing, so the two never disagree silently. |
| C15 | **The record gains `previous` and `venvs`; `sha` and `at` keep today's meaning.** | An append-only install log; a second state file. | `read_last`'s `at` feeds the batching window (P9), so its shape must not move. `previous` is the one datum the card's rollback needs ("reinstall the previous recorded sha"), and `venvs` is what makes "which install did this upgrade actually move" answerable after the fact. A log is a bigger record than one rollback step needs. |
| C16 | **The park/drain/debt half of the upgrade is untouched.** | Also making the upgrade refuse while worker sessions are in flight, as the card's third sentence asks. | That is F-0207, spec'd and planned and in flight over this exact module (P12): a durable due debt, the install tried at every process's exit, and a bounded drain window. Building a second answer here would collide with its Tasks and lose. Everything in this card sits outside the deferral: the target set, the verification, the record, and the doctor rows. |
| C17 | **The default upgrade target stays `main`'s head.** | Defaulting to the newest release tag, which the card's first bullet offers as an alternative ("or the newest tag once releases exist"). | `--to <tag>` already installs a tag and reports it (P8), and `install.newest_tag` already exists for the bootstrap. Moving the *default* changes what every product ticks and is a release-cadence decision that belongs with the release rollup, not with a card about which install ticks. |

### In, and out

**In.** `asf/clockinstall.py` (new): the plist reader, the five kinds, the venv/suffix, the sha, the
trunk, and the behind/merged answer. `asf/doctor.py`: one new check, one row per clock, the module
docstring's row list. `asf/upgrade.py`: the target venvs, `--suffix=`, per-venv `repo_url` and
verification, the "not the install that ticks" lines, `previous`/`venvs` in the record and the
rollback line. `docs/guide/upgrading.md`: what one `asf upgrade` moves, and what it does not.
`tests/test_clock_install.py` (new): every acceptance test below.

**Out.** (a) The deferral, the pending marker, the drain and F-0207's debt (C16). (b) Writing or
rewriting a plist: moving a clock onto a pinned install is `asf install`/`tools/install.sh`, and
this card only reads them. (c) Converting an editable venv (C11). (d) The default target and the
release cadence (C17). (e) `scheduler.clock_code`, `doctor.check_clock_code` and their two tests
(C4). (f) The schema table, `--skip-pipx`, the CI guard and `--to`'s tag resolution — all used
unchanged. (g) Any new operator-config key: the plists are the authority (C1). (h) `asf doctor`'s
`SCHEDULER` section, which F-0207 is editing.

## The design

### §1 `asf/clockinstall.py` — which install a clock runs

```python
"""asf.clockinstall — which install each product clock runs, read from that clock's own plist.

`asf upgrade` reinstalls a pipx venv; a clock runs whatever its plist's ProgramArguments name,
and on a machine that holds a pinned live install beside an editable dev one those are not the
same install (F-0111 P3). This module is the one answer to "what ticks this product, at what
commit, and is it merged" — the doctor's `clock install` row and the upgrade's target set both
read it, and neither guesses.
"""

#: The distribution's pipx venv name; a suffixed install is this plus its ``--suffix``.
DIST = cli.DIST_NAME          # 'asf-factory'

KINDS = ('pinned', 'editable', 'snapshot', 'checkout', 'unknown')


@dataclasses.dataclass
class ClockInstall:
    label: str          # the launchd label, '' when the product has no plist
    kind: str           # one of KINDS
    venv: str           # the pipx venv dir name ('asf-factory', 'asf-factory-live'), else ''
    suffix: str         # the pipx --suffix that venv carries, else ''
    interpreter: str    # ProgramArguments[0] as the plist holds it
    repo: str           # snapshot/checkout: the working tree whose HEAD it runs, else ''
    sha: str            # the commit that install runs, '' when it cannot be told
    why: str            # one phrase: how the kind was told
```

`read(path)` → `(argv, env_vars)` from `plistlib`; `([], {})` for a missing or unreadable file (the
`SCHEDULER` section already reports a plist launchd cannot hold, and an unreadable plist is a
missing one here too — `doctor._job_plist`'s own rule).

`classify(argv, env_vars, venvs_dir)` → `ClockInstall`, in this order, first match wins:

1. `argv[1]`'s basename is `snapshot.LAUNCHER` → `snapshot`; `repo` is the value after `--repo`,
   `sha` is `snapshot.current(<the --code-dir value>)[0]` — the sha the launcher last ran — and
   `why` is `snapshot launcher of <repo>`.
2. `argv[0]` is under `venvs_dir` → the venv is the first path component below it, `suffix` is the
   venv name past `DIST` (`''`, `-live`, `2`, …), and `sha`/editability come from
   `venv_commit(<venvs_dir>/<venv>)`. `editable` when that `direct_url.json` carries
   `dir_info.editable`, else `pinned`.
3. `env_vars['PYTHONPATH']` (else the interpreter's own package root) is a git working tree
   (`snapshot.is_checkout`) → `checkout`, `repo` that tree, `sha` its `HEAD`.
4. otherwise `unknown`, with `why` naming the interpreter that could not be placed.

`venv_commit(venv_dir)` → `(sha, editable)` from the one `*.dist-info/direct_url.json` under that
venv's `site-packages` for this distribution: `vcs_info.commit_id` and `dir_info.editable`.
`('', False)` when the file or the dist is not there — read off disk, no subprocess (C14).

`venvs_dir(run)` → `pipx environment --value PIPX_LOCAL_VENVS`, stripped; `''` when `pipx` is not
there (every clock then classifies by step 1, 3 or 4, and a pinned install reads `unknown` with
`why` saying `pipx is not on PATH`).

`for_product(product_name, cfg=None, run=subprocess.run)` → one `ClockInstall` per label in
`scheduler.product_labels(product_name, cfg)`, sorted by label; `[]` when there is no plist, and
`[]` for a scheduler kind that is not `launchd` (there is no plist to read — the caller says so).
`venvs_dir` is read once for the whole list.

### §2 the trunk, the distance, and whether it is merged

```python
def trunk(cfg=None):
    """``(repo, head)`` — the ASF source checkout on this host and its ``origin/main`` sha, or
    ``('', '')`` when this host has none. ``drift.factory_root()`` first (the running package's
    own tree), else the first configured product whose ``repo_dir`` is the factory's source
    (``drift.is_factory_source``). The ref is read locally: no fetch, no ls-remote (C8)."""


def against_trunk(sha, repo, head):
    """``(behind, merged)`` for one install's ``sha``:
    ``behind``  — ``int(git -C repo rev-list --count <sha>..<head>)``, or ``None`` when either
                  commit is not in that repo (a sha the host has never fetched);
    ``merged``  — ``git -C repo merge-base --is-ancestor <sha> <head>`` succeeded; ``None`` when
                  it could not be asked.
    Both ``None`` for an empty ``sha``, an empty ``repo`` or an empty ``head``."""
```

One `rev-parse` per doctor run and at most one `rev-list`/`merge-base` pair per distinct sha; the
results are memoised per `(sha, head)` for the run, so two clocks on one install cost one pair.

### §3 the doctor's `clock install` rows

`asf/doctor.py` gains:

```python
def check_clock_installs(cfg, product):
    """[(required, ok, detail)] — one row per product clock: which install it runs, its sha, how
    far behind origin/main, and RED when what ticks is not a pinned, merged install (F-0104)."""
```

and `run()` appends them right after the existing `clock code` row:

```python
    for required, ok, detail in check_clock_installs(cfg, product):
        rows.append(('clock install', required, ok, detail))
```

The RED rule, in one place, applied per clock:

| # | When | Row |
| --- | --- | --- |
| R1 | `kind` is `editable`, `checkout` or `unknown` | RED |
| R2 | `kind` is `snapshot` and `doctor.is_factory_repo(product)` is false | RED |
| R3 | `merged` is `False` — the sha is not an ancestor of `origin/main` | RED |
| R4 | otherwise | ok |

`required=True` on every one of them (C5), except the two rows that are statements about the host
rather than about an install, which are `required=False` and print `skip`: a product with no plist
in LaunchAgents, and a scheduler kind with no plists to read.

What the rows look like when this is there — a pinned live install, current, with a second clock a
few commits behind it:

```
clock install  ok    asf.<p>.fast · pinned asf-factory-live @ 9c1de44 · origin/main 9c1de44 · current
clock install  ok    asf.<p>.daily · pinned asf-factory-live @ 7a5881d · origin/main 9c1de44 · behind by 4
```

and the four reds:

```
clock install  RED   asf.<p>.fast · editable asf-factory @ 3f2a1c9 (<checkout>) · the clock ticks a working tree — reinstall it pinned: bash tools/install.sh <p> <ref>
clock install  RED   asf.<p>.fast · snapshot of <checkout> @ 3f2a1c9 · origin/main 9c1de44 · this product is not the factory's own source — reinstall it pinned: bash tools/install.sh <p> <ref>
clock install  RED   asf.<p>.fast · snapshot of <checkout> @ 3f2a1c9 · origin/main 9c1de44 · NOT on origin/main — unmerged work is ticking this product
clock install  RED   asf.<p>.fast · unknown · <interpreter> is not a pipx venv, a snapshot launcher or a checkout
```

and the two that are not judgements:

```
clock install  skip  (none) · no clock plist in ~/Library/LaunchAgents — the SCHEDULER section names the clocks
clock install  skip  kind:cron · no launchd plist to read
```

and, on a host with a pinned install and no ASF checkout (C9):

```
clock install  ok    asf.<p>.fast · pinned asf-factory-live @ 7a5881d · origin/main unknown (no ASF checkout on this host) — distance not measured
```

The module docstring's row list gains the row, beside the `clock code` sentence it does not
replace.

### §4 `asf upgrade` — the venvs the clocks name

```python
def targets(cfg=None, run=subprocess.run):
    """``([(venv, suffix)], [ClockInstall])`` — the venvs this upgrade must reinstall, and every
    clock whose install it will *not* move. Clock venvs first, in label order, then the venv this
    process runs from; deduplicated, order preserved. An ``editable`` clock venv is never a
    target (C11). Falls back to ``[(PACKAGE_NAME, '')]`` when there is no plist to read, no
    ``pipx``, or the config does not load — today's behaviour exactly."""
```

`_install(ref, run, out, pin=None)` loops over those targets:

```python
    for venv, suffix in venvs:
        url = repo_url(run, venv=venv)                       # that venv's own pipx spec
        cmd = upgrade_command(url, pin or ref, suffix)        # ['pipx','install','--force',
                                                              #  '--suffix=-live', 'git+…@<ref>']
        out('upgrade: ' + ' '.join(cmd))
        rc = run(cmd).returncode
        if rc != 0:
            return rc                                         # the line above names which venv
        got = new_install_commit(run, venv=venv)
        if not got or not (got.startswith(ref) or ref.startswith(got)):
            out(f'upgrade: FAILED — {venv} is at {(got or "unknown")[:7]}, not {ref[:7]}')
            return 1
        out(f'upgrade: installed {ref[:7]} in {venv}')
```

A single-install machine prints one `upgrade: installed <sha> in asf-factory` line, runs one
`pipx install --force git+…@<ref>` with no `--suffix`, and is byte-for-byte what it runs today but
for the ` in <venv>` tail. `upgrade_command(url, ref)` with two arguments is unchanged (C13).

Then, before the schema table, one line per clock the install did not move, and a `NEEDS OPERATOR`
line for each such clock on a product that is not the factory's own source (C12):

```
upgrade: asf.<p>.fast runs snapshot of <checkout> @ 3f2a1c9 — this install is not the one that ticks <p>
NEEDS OPERATOR: <p> ticks a working tree, not this install — bash tools/install.sh <p> <ref>
```

`repo_url(run, venv=PACKAGE_NAME)` and `new_install_commit(run, venv=PACKAGE_NAME)` keep their
current behaviour for the default venv, including the `<venvs>/<venv>/bin/python -c` spawn and its
`FakeRun` contract (P2), with `clockinstall.venv_commit` as the fallback when the spawn answers
nothing (C14).

### §5 the record, and the rollback the operator types

`record_last(sha, now=None, venvs=None)` reads the file first and writes:

```json
{"sha": "<the sha this call installed>",
 "at": 1759100000.0,
 "previous": "<the sha the file held before this call>",
 "venvs": {"asf-factory": "<sha>", "asf-factory-live": "<sha>"}}
```

`sha` and `at` keep exactly today's meaning, so `cooling`, `batch_hold` and
`tests/test_drift`'s three `record_last` calls read what they read now (C15); `previous` is absent
(not empty) the first time, and `read_last` still loads a file that has only `sha` and `at`.

After a successful install, `cmd_upgrade` prints the rollback as a command, once:

```
rollback: asf upgrade --to 7a5881d
```

— the `previous` sha, omitted when there is none. That is the card's rollback: `--to <sha>` already
installs an exact commit (P8), and now the sha to type is in the output and in the record.

### §6 the guide

`docs/guide/upgrading.md`'s "The package is shared across products — one `asf upgrade` upgrades it
for all of them" becomes true as stated and gains the two clauses it needs: that the upgrade
reinstalls the venvs the clocks name (a suffixed live install included), that it never touches an
editable one, and that `asf doctor`'s `clock install` row is where an operator sees which install
each product ticks. The rollback line is named beside `--to`.

## Records

- **`state/upgrade-last.json`** — unchanged keys `sha` and `at`; new `previous` (the sha the file
  held before this install, absent when there was none) and `venvs` (`{venv: sha}`, every venv this
  call moved). Nothing else reads the two new keys; `cooling`/`batch_hold` keep reading `at` (C15).
- **No new state file, and no new config key.** The plists are the authority on which install ticks
  (C1), and the trunk ref is read from a checkout that is already there (C9).
- **`asf upgrade` stdout** — one `upgrade: pipx install --force [--suffix=<s>] git+<url>@<ref>` and
  one `upgrade: installed <sha> in <venv>` per target venv, in target order; one
  `upgrade: <label> runs <kind> … — this install is not the one that ticks <p>` per clock the
  install did not move; one `NEEDS OPERATOR: <p> ticks … — bash tools/install.sh <p> <ref>` per such
  clock on a product that is not the factory's own source; one `rollback: asf upgrade --to <sha>`
  after a successful install. The `FAILED` line now names the venv that ended up at the wrong sha.
  Exit codes are unchanged, including `DEFERRED` (C12, C16).
- **`asf doctor` stdout** — one `clock install` row per product clock, in label order, in the main
  table right after `clock code`: the label, the kind, the venv or the checkout, the sha, the
  `origin/main` sha, and either `current` / `behind by N` / `NOT on origin/main` / a named repair.
  RED per §3's R1–R3, so `asf doctor` exits 1 while what ticks a product is editable, a bare
  checkout, unplaceable, an unmerged sha, or a snapshot on a product that is not the factory's own
  source. The `SCHEDULER` section is untouched.
- **Nothing is written to the ledger, the backlog or a plist.** This card reads plists; it never
  writes one.
