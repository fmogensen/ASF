# F-0190 — a test-runner config is not an undeployed change

A product's site row said `1 relevant commits behind main … waits on a hand deploy` for a commit
that changed exactly one file, `apps/site/playwright.config.ts`. The deployed site was
byte-identical to the trunk. The operator was asked, every tick, to hand-deploy nothing.

The count behind that line is one `git rev-list`:

```
git -C <repo> rev-list --count <deployed>..origin/main -- ':(glob)apps/site/**'
```

`asf/harvest/deploy.py:314-322`. Every file under the target's `paths` counts the same — a page,
a Playwright config, a `README.md`, an `e2e/` spec. The filter knows *where* a target's files
live; it has no way to say which of those files the deploy actually ships. So every test-only
edit under a scoped target reads as an undeployed change, `MANUAL:` shouts about it until someone
deploys, and a `mode: auto` target dispatches a real deploy workflow for it.

This card is not "make the count smarter". It is: **the filter gains a second half — an exclude
list, with a default set for the files no deploy ships — and the relevant count is commits
touching a path under `paths` *and* outside the excludes.** git's own pathspec algebra already
says exactly this, so the count stays one `rev-list`, not a per-commit walk.

### In, and out

**In.** `DEFAULT_EXCLUDES` in `asf/harvest/deploy.py`; an `excludes(product, env)` reader with the
add-to-defaults rule and the `exclude_defaults` switch; `pathspecs()` and `_behind()` taking
excludes; `_set_behind` / `_blank` / `_done` carrying an `exclude` fact and a `filtered()`
predicate; the five renderers moved onto `filtered()` (P5) including `asf prod`'s header; dev and
prod saying `relevant` when they carry a filter; the findings line naming the exclude count;
validation of `paths`, `exclude` and `exclude_defaults` on dev, prod and every named target; the
module docstring and `docs/products.example.yaml`.

**Out, deliberately.** The ON PROD table's `within` (C4); any change to what a *deploy* ships (this
is a counting rule, not a build rule); `customer_content` paths; the candidate/green/running rules;
per-product configuration of the default set (C3); any new command or view (C10); and — the one
that matters — any behaviour change for an environment that names neither `paths:` nor `exclude:`
(C2).

## The design

### 1. `asf/harvest/deploy.py` — the filter grows its second half

```python
#: Paths a deploy never ships: a commit touching only these is not a change to deploy. Added to
#: an environment's own ``exclude`` list unless ``exclude_defaults: false``, and engaged only
#: where the environment already has a filter — ``paths`` or ``exclude`` (never on its own).
DEFAULT_EXCLUDES = ('**/*.test.*', '**/*.spec.*', '**/e2e/**', '**/playwright.config.*',
                    '**/vitest.config.*', '**/__tests__/**', '**/*.md')


def _globs(v):
    """A ``paths``/``exclude`` value as a list of globs (a bare string is one glob)."""
    if isinstance(v, str):
        v = [v]
    return [g for g in v if isinstance(g, str) and g] if isinstance(v, list) else []


def paths(product, env):
    """The environment's ``paths`` globs ([] = every trunk commit counts)."""
    return _globs(env_cfg(product, env).get('paths'))


def excludes(product, env):
    """The environment's exclude globs: its own ``exclude`` list added to
    :data:`DEFAULT_EXCLUDES`, or that list alone under ``exclude_defaults: false``.

    [] when the environment names neither ``paths`` nor ``exclude`` — the defaults never make a
    filter where the operator asked for none, or a docs-only trunk commit would stop prod."""
    cfg = env_cfg(product, env)
    own = _globs(cfg.get('exclude'))
    if not own and not paths(product, env):
        return []
    if cfg.get('exclude_defaults') is False:
        return own
    return list(DEFAULT_EXCLUDES) + [g for g in own if g not in DEFAULT_EXCLUDES]


def filtered(f):
    """True when this environment's facts carry a relevance filter — ``paths``, ``exclude`` or
    both. The one predicate every line and every count asks."""
    return bool(f['paths'] or f['exclude'])
```

`pathspecs` and `_behind` take the second list:

```python
def pathspecs(globs, exclude=()):
    """``paths``/``exclude`` globs as git pathspecs (``**`` crosses ``/``; a trailing ``/`` is a
    directory). An exclude is the same glob under ``:(exclude,glob)``: git drops its files from
    the match, so a commit that touches only excluded files matches nothing and is not counted."""
    return ([':(glob)' + _dir(g) for g in globs]
            + [':(exclude,glob)' + _dir(g) for g in exclude])


def _behind(product, base, sh, globs=None, exclude=None):
    """Trunk commits ``base`` lacks — only those touching ``globs`` and outside ``exclude`` when
    either is given."""
    ...
    if globs or exclude:
        argv += ['--'] + pathspecs(globs or [], exclude or [])
```

(`_dir(g)` is today's `g + '**' if g.endswith('/') else g`, lifted out so both halves share it.)

The facts carry the list, and the relevance rule reads the predicate:

```python
def _blank(product, env):
    return {..., 'paths': paths(product, env), 'exclude': excludes(product, env),
            'relevant': None, ...}


def _done(f):
    f['prod'] = f['deployed']
    if f['relevant'] is None and not filtered(f):
        f['relevant'] = f['behind']
    return f


def _set_behind(product, f, sh):
    f['behind'] = _behind(product, f['deployed'], sh)
    if filtered(f):
        f['relevant'] = (0 if f['behind'] == 0
                         else _behind(product, f['deployed'], sh, f['paths'], f['exclude']))
```

So a scoped site target now runs

```
git -C <repo> rev-list --count <deployed>..origin/main -- \
  ':(glob)apps/site/**' ':(exclude,glob)**/*.test.*' ':(exclude,glob)**/*.spec.*' \
  ':(exclude,glob)**/e2e/**' ':(exclude,glob)**/playwright.config.*' \
  ':(exclude,glob)**/vitest.config.*' ':(exclude,glob)**/__tests__/**' ':(exclude,glob)**/*.md'
```

which is 0 for the card's commit, and the tick says so.

### 2. The words

Four line-writers move off `f['paths']` and onto `filtered(f)`, and two gain a clause:

* `_lag`, target branch — `rel = 'relevant ' if filtered(f) else ''`, and the `N in all` clause on
  the same predicate.
* `_lag`, dev/prod branch (C6) — with a filter,
  `main is 3 relevant commits ahead of prod \`abc123def\` (9 in all) (deployed 4h ago)`; with none,
  byte-for-byte today's `main is 9 commits ahead of prod \`abc123def\``.
* `_manual` — `rel` on `filtered(f)`.
* `decide`'s zero branch — `if filtered(f) and f['relevant'] == 0`, printing a scope built once:

```python
def _scope(f):
    """The filter in words: what a commit must touch, and that it must fall outside the
    excludes."""
    return ' '.join(x for x in (f"touching {', '.join(f['paths'])}" if f['paths'] else None,
                                'outside its excludes' if f['exclude'] else None) if x)
```

  → `deploy site: site \`ffffffff\` has every main commit touching apps/site/** outside its
  excludes (9 other commits since; mode manual)`.

* `findings` (C8) — `scope` becomes `', '.join(paths) or 'every commit'` plus
  `f' less {n} excludes'` when there are any:
  `site manual (site-deploy.yml, apps/site/** less 7 excludes)`.

* `asf/views/prod.py:226` — `rel = 'relevant ' if deploy.filtered(f) else ''`. `_check_rows` keeps
  taking `f['paths']` (C4).

### 3. `asf/env.py` — the config loads, or it refuses

`_target_problems` keeps its `mode` / `from` checks and delegates the three glob keys to a shared
helper, which `_deploy_problems` also calls for the `dev` and `prod` blocks (C9):

```python
def _relevance_problems(k, block):
    """[(dotted key, problem)] for the relevance filter of one environment block — ``paths``,
    ``exclude`` (both lists of non-empty globs) and ``exclude_defaults`` (a bool)."""
    out = []
    for key in ('paths', 'exclude'):
        v = block.get(key)
        if v is not None and not (isinstance(v, list)
                                  and all(isinstance(g, str) and g for g in v)):
            out.append((f'{k}.{key}', f'must be {_LIST} of path globs, not {v!r}'))
    d = block.get('exclude_defaults')
    if d is not None and not isinstance(d, bool):
        out.append((f'{k}.exclude_defaults', f'must be true or false, not {d!r}'))
    return out
```

### 4. The docs

The module docstring's **Named targets** paragraph gains the second half of the filter — that
`paths` and `exclude` together decide relevance, the seven defaults, `exclude_defaults: false`,
that the keys read for dev and prod too, and that with neither key an environment has no filter at
all. `docs/products.example.yaml` gains the commented keys under `targets.site` and a line under
`prod:` saying they are read there too; it must keep validating (P12).

## Acceptance tests

All in `tests/test_deploy.py`, beside the `NamedTargets` and `Validation` classes that own this
code today, plus one real-git class so the pathspec algebra is proved against git and not against
`FakeSh`.

**The filter reads.** `RelevanceFilter`: `excludes()` is the seven defaults for a target with
`paths` and no `exclude`; a target's own list is added after them, in order, with no duplicate when
it repeats a default; `exclude_defaults: false` leaves the list alone and an empty list with it
leaves `[]`; an environment with neither key gets `[]` even though the defaults exist (C2 — the
guard against changing prod); a bare string `exclude: 'docs/**'` coerces as `paths` does; `paths`
and `exclude` are read the same way under `deploy_sha.prod` as under `targets.site` (P1);
`filtered()` is true for paths-only, exclude-only and both, false for neither.

## Stories

- S: The exclude list resolves once, and the defaults never make a filter on their own — `DEFAULT_EXCLUDES` (the card's seven globs) with `excludes(product, env)` adding an environment's own `exclude:` after them, dropping them under `exclude_defaults: false`, coercing a bare string as `paths` does, returning `[]` for an environment that names neither key, reading the same under `deploy_sha.prod`/`dev` as under `targets.<name>`, and `filtered(f)` as the one predicate for "this environment has a filter" — acceptance: `python3 -m unittest -v tests.test_deploy.RelevanceFilter`
- S: Relevance counts only commits under `paths` and outside the excludes, proved against real git — `pathspecs()` emitting `:(exclude,glob)` for each exclude, `_behind()` passing both lists, `_set_behind` counting whenever there is a filter, and a real repo where the card's `playwright.config.ts`-only commit counts 0, an `e2e/`, `__tests__/`, `.spec.` or `.md` commit counts 0, a commit touching one source file among test files still counts, and an exclude-only filter counts everything-except — acceptance: `python3 -m unittest -v tests.test_deploy.RelevanceAgainstGit`
- S: Every line and every view reads the one predicate, and the excludes are visible in words — the zero-relevance line saying `has every main commit touching <paths> outside its excludes`, dev and prod saying `N relevant commits ahead (M in all)` when they carry a filter and nothing at all when they do not, `_manual` and `asf prod`'s header on `filtered(f)` rather than `paths`, the findings line naming `less N excludes`, and the git argv carrying the includes then the excludes in order — acceptance: `python3 -m unittest -v tests.test_deploy.RelevanceLines`
- S: A mistyped filter refuses the product load, on dev and prod as well as on a target — `paths`, `exclude` (lists of non-empty globs) and `exclude_defaults` (a bool) shape-checked by one shared helper for `deploy_sha.dev`, `deploy_sha.prod` and every `deploy_sha.targets.<name>`, with the documented example config carrying the new keys and still validating clean — acceptance: `python3 -m unittest -v tests.test_deploy.Validation tests.test_env`
