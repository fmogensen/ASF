# F-0131 — sixty runner-hours of timeouts, filed as "cancelled", blamed on nobody

Five runs on one branch of this very repo, read live from the CI API at `77224662a`:

```
36322982383 cancelled 2026-09-27T13:36:29Z → 19:36:48Z   worker/T-0196
36320865747 cancelled 2026-09-27T12:59:59Z → 19:00:19Z   worker/T-0196
36315778419 cancelled 2026-09-27T11:27:12Z → 17:27:31Z   worker/T-0196
36312697636 cancelled 2026-09-27T10:29:31Z → 16:30:25Z   worker/T-0196
36312688383 cancelled 2026-09-27T10:29:20Z → 16:29:39Z   worker/T-0196
```

Each ran **six hours to the second** and each carries two jobs that did the same:

```
tests (3.13)  cancelled  started 13:36:32  completed 19:36:47   (360 min)
tests (3.12)  cancelled  started 13:36:32  completed 19:36:47   (360 min)
```

and the host says, in its own words, what happened (`repos/…/check-runs/108630269013/annotations`):

```
The job has exceeded the maximum execution time of 6h0m0s
```

Ten jobs, 3 600 runner-minutes — sixty hours — of one hung suite, hitting the host's default job
limit five times over. The tree records every minute of it and blames nobody for it:

* the stream calls them `cancelled`, so `scorecard_rows`' `runner-minutes` row counts 3 600
  minutes of waste and attributes them to a **branch kind** — `cancelled: code 3600 (100 %)` — as
  if the branch had been superseded (and four of the five *were* superseded by a later push, which
  is true and beside the point);
* `diagnose.rank` counts a cancelled job as a run that is **not red**
  (`asf/scorecard/diagnose.py:212`), so `ci-job:tests (3.12)` shows 5 runs, 0 red, and no
  `ci_red_per_week` cause is ever raised. A job that has never once finished on that branch scores
  a clean sheet;
* `file_bugs.ci_signatures` keys on `failed_step`, which a cancelled job has none of, so no Bug is
  filed either.

Meanwhile the thing that would have prevented all five — *this job now runs close to its limit* —
is measured nowhere at all. `timeout-minutes` is never read out of the workflow, so nothing in the
tree knows a job's limit, which means nothing can say either *it hit it* or *it is about to*.

This card is therefore two halves of one fact. **Every cancelled job carries the cause of its
cancel** — `timeout`, `runner-loss`, or `failure` for a cancel that followed a verdict somewhere
else — computed at import from evidence that is free and durable, and **every job whose runs come
close to its limit is listed** in the scorecard, with the limit and the distance, before it starts
timing out.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | **Exactly the card's three classes**: `timeout`, `runner-loss`, `failure`. `failure` is the residue and says so — *the cancel followed a verdict or a decision somewhere else, and says nothing about this job*. | A fourth class for the outside cancels (`superseded`, `queue`, `operator`). | The card names three, and the run row already carries `superseded` for the one outside cancel worth splitting out (P9), so a fourth class would be a second copy of an existing field. The three that matter are the three that change what somebody does: raise a limit, look at a box, or look elsewhere. |
| C2 | **The cause is decided from the run and its jobs alone** — free, durable evidence the importer already fetches (P4), plus the job's limit. | Reading the job's annotations (`check-runs/<id>/annotations`), or its log. | The annotation is decisive for a timeout — it is quoted at the top of this spec — but the duration test gets the same answer for free, and a per-job request would be one more call for every cancelled job in the window. More importantly, the *runner-loss* wording (`lost communication with the server`) cannot be verified in this repo at all: it has no self-hosted runners, so a design that only ever claims `runner-loss` on that string would ship a class that might never fire and nobody would notice. Named as out, not overlooked — the endpoint exists and a later card can sharpen the residue with it. |
| C3 | **The timeout test leads the ladder**, before every other arm. | Deciding the outside cancels first, since they are commoner. | Four of the card's five runs were *also* superseded by a later push on the branch (P9's `superseded` would be true for them), and every one of them was a six-hour timeout. Whichever arm runs first wins the classification, and the job's own limit is the more specific fact: a job that ran to its limit hit its limit, whatever else was true of its run. |
| C4 | **`runner-loss` is claimed only when the limit is known** and the job died well short of it, with a sibling that reached a verdict. When no limit can be read, the residue is `failure`. | Making the residue `runner-loss` whenever nothing else explains it. | Without a limit, a timeout and a lost runner are the same observation, and the two blames are not interchangeable: `runner-loss` sends somebody to a box. The conservative direction is the honest one — a class that claims nothing is better than a class that accuses the wrong thing — and it keeps the classifier's output stable on a product whose workflow the backend could not read (C8). |
| C5 | **A run-wide cancel is `failure` for every one of its jobs**, and a *single* cancelled job in a run whose sibling reached a verdict is the job's own ending. | Trying to name *who* cancelled the run (the queue, a push, a person). | P15: the host has no per-job cancel, so "every started job of this run is cancelled" is exactly "something outside cancelled the run", and "one job cancelled, a sibling green" is exactly "this job ended by itself". P17 says the queue can no longer be asked, so naming the canceller is not available at import time and would need a second, persistent record for no new decision. The cost is a real blind spot, stated: a **one-job** run that loses its runner is run-wide by arithmetic and is filed `failure`. |
| C6 | **The limit comes from the workflow's `timeout-minutes`, else the host default 360**, read once per backfill and written onto each job row as `limit`. | Reading nothing and inferring a limit from observed durations; reading the workflow at each run's own head sha. | P2: the card's own incident is a *default*-limit timeout, so a design that only knows declared limits would miss the whole card. Per-sha reads would be one content fetch per distinct sha in the window. The price of the trunk's copy is stated: a limit changed inside the window is applied to the runs before the change too. |
| C7 | **The parser is one more function beside `parse_runs_on`, and the fetch is one more method on `Backend`** — `ci_pool.parse_timeouts(text)` and `Backend.timeouts()` / `GitHubBackend.timeouts()`, with the workflow-file walk factored out of `runs_on` and shared. | A YAML parse; a second workflow reader inside `metrics`. | P11: `ci_pool` is already the one reader of workflow files, with the product's own login, and its line reader already tracks `jobs:` and the job key's indent — which is exactly what separates a *job's* `timeout-minutes` from a *step's*. A second reader would be a second thing to keep in step with the host's file format. |
| C8 | **The limits read is a named, patchable seam that fails soft**: `metrics.job_limits(product)` returns `{}` on `BackendError` or with no product, and `ci_from_api(..., limits=None)` calls it once. | Constructing the backend inline inside `ci_from_api`. | P19: a host read that cannot be patched by module attribute puts a real `gh` call inside the suite's importer test. Failing soft to `{}` means a product whose workflows the backend cannot read keeps importing exactly what it imports today — no limit, no timeout class, no near-limit rows, and by C4 no `runner-loss` either. |
| C9 | **The classification is written onto the job row at import (`cause`), never recomputed by a reader.** A row with no `cause` is *unclassified*, and no reader guesses. | A reader that classifies on the fly from the stream. | P6: rows already on disk are never rewritten, so a recomputing reader would need the run's limit — which is not on those rows — and would answer differently for the same run in two different weeks. A stored class is a fact of the import that produced it. The cost is stated: the classes start at the first tick after the change, and the card's own five runs stay unclassified unless their day's stream is deleted and re-imported. |
| C10 | **Two new rows in the waste table, and the existing `runner-minutes` row untouched.** One row per non-zero cause (`cancelled: timeout`), one per job near its limit (`near limit: <job>`), both in the shape `red job:` already uses. | Rewriting the `runner-minutes` note to split by cause instead of by branch kind. | The branch-kind split answers a different question — *whose* minutes went — and it is goldened (P9). Adding rows leaves that answer alone and puts the cause where a reader can see both at once. Following `red job:`'s shape means the new rows are capped and sorted the way that row already is, with no new table and no new section. |
| C11 | **`diagnose` counts a `timeout` or `runner-loss` cancel as red, under the unchanged key `ci-job:<name>`.** A `failure`-class cancel and an unclassified one stay not-red, and the cause's detail line names the split. | Leaving `diagnose` alone; or a new cause key for the near-limit list. | P10: this is the one reader that *acts* — it raises the cause a card is filed from — and a classification nothing acts on is a number in a table. | C12 | **The near-limit half is a list and nothing else**: rows in the scorecard, no threshold config, no cause key, no Bug. | A `ci-limit:<job>` cause with its own threshold, filed as a card; a Bug from `file_bugs` for a repeated timeout. | The card says *list*. ## The design

### 1. `asf/ci_jobs.py` — what a job's ending says

```python
"""asf.ci_jobs — what a CI job's ending says: why a cancelled job was cancelled, and which jobs
run close to their limit.

The host has no separate conclusion for a job that ran out of time: it concludes ``cancelled``,
exactly as a job cancelled with its run does, and exactly as a matrix leg cancelled by its
sibling's failure does (F-0131 P1, P16). Three very different things, one word, and three
different people who should hear about them — so every cancelled job carries its cause:

``timeout``      it ran to its own limit. Raise the limit or make the job faster.
``runner-loss``  it started, ran well short of its limit, and the run reached a verdict without
                 it. Nobody outside a job can cancel one job (P15), so the runner went away.
``failure``      the residue: the cancel followed a verdict or a decision somewhere else — a
                 sibling's red, a newer push, the queue, a person. It says nothing about this job.

A job's ``cause`` is why *that job* stopped; a :class:`asf.scorecard.diagnose.Cause` is a
factory-wide diagnosis a card is filed from. The two are one import apart and are not the same
thing.

Pure functions over the job rows of the ``ci`` stream: no host call, no filesystem, no
configuration. The caller passes what it already has.
"""
from asf import ci_pool

#: a job conclusion that is a verdict of its own — :data:`asf.ci_pool.FAIL`, aliased rather than
#: copied so the tree keeps one definition of a red job (F-0131 C15)
RED = ci_pool.FAIL

#: it ran to its own limit
TIMEOUT = 'timeout'
#: it started, died well short of its limit, and the run reached a verdict without it
RUNNER_LOSS = 'runner-loss'
#: the cancel followed a verdict or a decision elsewhere; no claim about this job
FAILURE = 'failure'
CAUSES = (TIMEOUT, RUNNER_LOSS, FAILURE)

#: minutes of grace on the limit test: ``mins`` floors a duration to whole minutes and the host
#: overshoots by seconds (the live case: a 360-minute limit, 6 h 0 m 15 s of duration → 360).
TIMEOUT_SLACK_MIN = 1
#: a job whose p90 reaches this share of its limit is listed
NEAR_LIMIT_SHARE = 0.8
#: …once it has this many green runs to take a p90 of
NEAR_LIMIT_MIN_RUNS = 3
#: at most this many near-limit rows, worst first
NEAR_LIMIT_TOP = 4
CANCELLED = 'cancelled'
```

`cancel_cause` is the ladder, and the order is the design:

```python
def cancel_cause(job, jobs, conclusion, superseded=False):
    """The cause of ``job``'s cancel — one of :data:`CAUSES` — or None when ``job`` did not end
    ``cancelled``. ``jobs`` is every job row of the same run (``job`` included), ``conclusion``
    the run's own, ``superseded`` whether a newer run on its branch threw this one away.

    Each arm is tried in order; the first that holds is the answer.
    """
```

| order | the test | cause | why it is decidable |
| --- | --- | --- | --- |
| 1 | `job['limit']` is known and `job['minutes'] + TIMEOUT_SLACK_MIN >= job['limit']` | `timeout` | It ran to its limit; nothing else about the run changes that (C3). |
| 2 | any row of `jobs` concluded in `RED`, or `conclusion` is in `RED` | `failure` | `fail-fast` (P16), or a run that already has a verdict. |
| 3 | `superseded` | `failure` | A newer push threw the run away — even when one fast job had already gone green. |
