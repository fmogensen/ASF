# F-0345 — 0.4 is a number the gate can read

0.1 made the factory work, 0.2 made it improve itself, 0.3 made it deliver without a human in the
loop. 0.4 is the release where it gets **fast** and **cheap** — and that is the first release whose
subject is a number rather than a capability. A capability is done when it exists; a number is done
only when something reads it, every day, against a figure written down beforehand.

The factory already measures almost all of it. `asf scorecard` prints lead time, dollars per
Feature, tokens, CI minutes, repair sessions and dead sessions per week (`asf/views/scorecard.py`,
`asf/scorecard/score.py`); `asf.metrics.throughput` prints eight more with their own alarms —
seat use, first-pass CI, merge wait, time-to-detect, cloud outcomes; `asf/scorecard/program.py`
prints where the spend went that no landing needed — idle hours, waste by class, mechanical-only
corrections, heavy-model share. The reading is not the gap.

The gap is that **none of those numbers can be a target**. One command exists to judge the factory
against written figures — `asf scorecard --check <targets.yaml>` — and it reads exactly one of the
three rows, the program row (`asf/views/scorecard.py:271-283`: `program.load`, and nothing else).
So the only targets file in the repo (`docs/program/targets.yaml`, wave A) is twelve keys with
`op: measured` on every one of them: a baseline, because no threshold about speed or economy can be
written in the one place that is checked. A target naming `value.usd_per_feature` or
`throughput.seats.value` reads **not read** and misses, whatever the factory is actually doing (P1).
And the release gate — thirteen computed criteria, `asf/release.py` — never opens a targets file at
all (`grep -c targets asf/release.py` is **0**, P6).

That is why 0.4 opens here and not in an optimisation. On the week measured below the factory
landed 53 Features at $17.67 each — and spent 37 % of that week's dollars on runs that landed
nothing, sat idle 56 of 168 hours while rows waited, and let the median card→landed time grow from
1.5 days to 9.2 in three weeks (P3). Every one of those four is already a key in a row some command
prints. None of them is a commitment anything enforces.

This card makes 0.4's numbers readable in one place, writes them down, and makes the release gate
hold the product to them. It makes no Feature of 0.4 faster or cheaper: each of those is its own
card, and each is judged — for the first time — by a figure that was fixed before the work started.

## Decisions

### Preconditions — measured in this worktree at `edce03798`, 2026-10-10

P1, P2, P4–P8 come from the first script in `## Acceptance tests` (`the preconditions,
re-measured`), which reads the installed package only and runs anywhere. P3 and P9 come from the
second, which reads the first product's record and is the baseline every target below cites.

* **P1 — `--check` reads one row of three.** `cmd_check` (`asf/views/scorecard.py:271-283`) is two
  reads: `program.load(product, start, end, …)` and `targets.check(row, tg)`. `targets.lookup`
  (`targets.py:46-52`) walks that one mapping by dotted path and returns `_MISSING` the moment a
  segment is absent, and `check` (`:55-66`) makes a `_MISSING` a miss for every op but `measured`.
  Measured: `value.usd_per_feature` and `throughput.seats.value` against a program row read
  `(None, False)` — *not read*, hence missed, however fast or cheap the factory is.
* **P2 — the three rows carry 24, 26 and 8 keys, and no two overlap.** `program.row` has 24 keys
  (`idle_hours`, `offline_ticks`, `waste_by_class`, `mechanical_only_corrects`, `heavy_share`,
  `max_runs_job_head`, `infra_ended`, `rows_waiting_on_item`, … ); `score.window_row` has 26
  (`median_lead_days`, `median_task_days`, `usd_per_feature`, `own_usd_per_feature`,
  `repair_per_feature`, `dead_sessions`, `dead_usd`, `ci_min`, `tokens`, `s1`, and the nested
  `denials.{sessions,total,mean,share_pct,top}` and
  `first_push_green.{green,not_green,rate_pct,caught,branches,by_kind}`);
  `throughput.METRICS` is eight rows, each `{key,name,status,value,unit,detail,limit}`. Four names
  are in both the program row and the value row — `start`, `end`, `facts_disagree` (counted the
  same way by both) and **`usd`**, which is not: see P10. Namespacing the three rows is what makes
  that collision impossible to write by accident (D2).
* **P3 — the baseline, 7 days to 2026-10-10, the first product's record.**
  * speed: `median_lead_days` **9.2** (1.5 on the week of 2026-09-21, 4.8 on 09-28),
    `median_task_days` **6.7**, `idle_hours` **55.96** of 168, `throughput.seats` **19.5 %** busy
    and in **ALARM** with four idle stretches, the longest **759.8 min** at 0 of 12.5 seats,
    `throughput.merge` p90 **9.9 min**, `throughput.detect` p90 **19.9 min**,
    `throughput.first_pass` **0.928**, `offline_ticks` **41**.
  * economy: `usd` **936.64**, `usd_per_feature` **17.67**, `own_usd_per_feature` **13.47**,
    `dead_sessions` **278** of 1241 at `dead_usd` **302.61** (32 % of the week's dollars),
    `waste_by_class.failed.usd` **345.60** (37 %), `repair_per_feature` **7.6** (405 sessions),
    `mechanical_only_corrects.usd` **20.97**, `heavy_share` **0.622**, `ci_min` **40283.2**,
    `tokens` **2.81e9**, `throughput.cloud` dead rate **0.146** at $1.78/run.
  * first-push-green **16.6 %** (70 branches green, the rest naming a repair session, a second
    building session, a failing gate or a red head) — F-0301's metric, landed and reading.
  * the approvals hook refused **8342** tool calls across **2236** ended runs: **3.73** per run,
    **42.8 %** of runs carrying at least one. A refusal is a turn bought and thrown away.
* **P4 — `targets.parse` already has the vocabulary a threshold needs.** Six ops —
  `==`, `<=`, `<`, `>=`, `>`, `measured` (`targets.OPS`) — a numeric `value:` required for the
  five comparisons, and a free-text `why:` per target. Nothing about the file format has to change
  to express 0.4; only what the keys may name.
* **P5 — the only targets file in the repo is a baseline.** `docs/program/targets.yaml`: `wave: A`,
  12 targets, `op: measured` on all 12, its own comment saying "the baseline the later waves beat".
* **P6 — the release gate reads no targets file.** `asf/release.py` holds 13 criteria;
  `release.compute` (`:897-911`) appends the last three from their own modules
  (`tune_criterion`, `pr_ci_criterion`, `rehearsal_criterion`) — the shape a 14th takes.
  `grep -c targets asf/release.py` is **0**, and `release.DEFAULTS` has no such key.
* **P7 — every row can already be computed over any window.** `program.row(runs, start, end, …)`,
  `score.window_row(facts, start, end)` (`score.py:247-287`) and
  `throughput.evaluate(f, start, end, seat_cfg, cfg)` (`throughput.py:568-579`) all take the
  window. `throughput.compute` (`:594-604`) additionally computes a 7-day trend, which is one
  `evaluate` per day and which no target reads.
* **P8 — `score.window_row` needs facts; `facts.load` can skip the forge.**
  `facts.load(root, product, *, registry=True, forge=True, as_of=None)`; `throughput.load` already
  calls it with `forge=False` (`throughput.py:643`). The one thing the forge adds is `clutter`
  (stale PRs, branches), which `window_row` does not read and no target below names.
* **P9 — what each half of the row costs, on the first product's record.** `program.load`
  **27.3 s**, `facts.load(forge=False)` **45.5 s**, `score.window_row` **0.8 s**,
  `throughput.load` + `evaluate` **0.3 s**. Facts are the expensive half, and wave A's file does
  not need them.
* **P10 — two spends for one week.** Over the same 7 days `score.window_row` reads `usd`
  **936.64** (summed over `metrics/sessions`) and `program.row` reads `usd` **4351.41** (summed
  over the session registry's ended runs, priced by `asf.improve.measure`) — a factor of 4.6 on
  2257 runs against 1241 sessions. Which of the two is *the* dollar is not something this card can
  settle (see `NEEDS OPERATOR` and the Out list).
* **P11 — a new `release:` sub-key must not be registered as one.** `env.RELEASE_FIELDS`
  (`asf/env.py:609-611`) is validated one level deep, and the comment above it and at `:617-634`
  says why `release.gate`, `release.floor`, `release.seats` and `release.channels` are listed in
  `DOCUMENTED_UNCHECKED_FIELDS` instead: a *registered* sub-key is what the oldest pinned reader
  refuses (`tests.test_env.PinnedReader`), while an unregistered one only draws a doctor warning.
* **P12 — the record holds no Story for F-0345**, and this session's block is `S:134605-134654`.

### In

* **`asf/scorecard/targets.py` — three namespaces, one window.** `NAMESPACES = ('program',
  'value', 'throughput')`; `needs(targets)` → the namespaces a parsed file asks for; `row(root,
  product, start, end, need=None)` — the module's one reader — builds exactly those halves over
  exactly that window; `lookup` falls back to the program half for a key whose first segment is no
  namespace, so `docs/program/targets.yaml` reads unchanged (D2).
* **`asf/scorecard/targets.py` — two derived numbers, and no more.** Per throughput metric,
  `alarm` is 1 when its status is `ALARM` else 0; `throughput.alarms` is their sum. A status is a
  word, and `op: '=='` cannot read a word (D4).
* **`asf/scorecard/targets.py` — `render` names the window and the row each key came from**, and
  says `not read` against the namespace that was not loaded, never against a number.
* **`asf/views/scorecard.py` — `cmd_check` is the same three lines over the new row**:
  `targets.parse` → `targets.row(…, need=targets.needs(tg))` → `targets.check` → `render`. Exit
  codes unchanged: 0 every target met, 1 one missed, 2 a file that will not parse.
* **`docs/program/targets-0.4.yaml` — 0.4's numbers**, `wave: 0.4`, 23 targets, every one carrying
  its P3 baseline in `why:` (D5, and the table in §3).
* **`asf/release.py` — criterion 14, *release targets met***: `targets.criterion(product, root,
  cfg, now)` read whole from `asf.scorecard.targets` and appended by `compute` beside the other
  three (P6); `n/a` — met — when the product's `release:` block names no targets file.
* **`asf/env.py` — `release.targets` in `DOCUMENTED_UNCHECKED_FIELDS`**, never in
  `RELEASE_FIELDS` (P11), and `asf/release.py`'s `settings` reading it as a string path.
* **`docs/products.example.yaml` — the `release.targets` line**, in the commented `release:` block
  beside `gate:`.
* **Tests**: `tests/test_scorecard_targets.py` (three classes, Stories 1–3) and
  `tests/test_release_targets_criterion.py` (one class, Story 4); the first script of
  `## Acceptance tests` as the first module's `MeasuredTodayTests`.

### Out

* **Every optimisation 0.4 is made of.** Nothing here makes one session cheaper or one Feature
  faster. The charter below names the work by the number it must move; each is its own Feature,
  minted by the groom when the Epic is decided, and none is a Story of this card.
* **Reconciling the two spends (P10).** This card points the money targets at `value.*` — the
  dollar the weekly SCORECARD prints, the one an Epic's `spend_usd` rolls up and a budget stops on
  (`asf/budget.py`) — and keeps `program.usd` in the file as `measured`, so both numbers are
  printed side by side on every check. Making them agree is a card of its own: it is a defect in
  one of two ledgers, not a target.
* **`asf.metrics.reds`' run-window targets** (first pass over the last N PRs, runner-class reds,
  trunk green). They are not time-window readings, they already have thresholds of their own in
  `improve.scorecard.throughput.*`, and release criterion 12 already gates on them. The day-window
  `throughput.first_pass` row is the one a 0.4 target names.
* **Writing a baseline.** `--check` stays a read: no snapshot file, no `--baseline` flag, nothing
  appended to `metrics/`. The baseline lives in each target's `why:` and in P3 of this spec.
* **The trend.** A target reads a reading, never a 7-day curve, and the curve costs one `evaluate`
  per day (P7). The check calls `evaluate`, not `compute`.
* **The forge.** The composite row loads facts with `forge=False` (P8). A number that needs a
  network call is not a number a gate should wait on.
* **New thresholds anywhere but the file.** No alarm default moves,
  `improve.scorecard.throughput.*` is untouched, `release.DEFAULTS` gains no number. 0.4's figures
  live in one tracked file, which is the point.
* **Turning the gate on for any product.** The repo ships the file and the criterion; pointing a
  product's `release.targets` at it is operator config, which this repo never writes (see
  `NEEDS OPERATOR`).
* **The Epic's budget and its close.** Both are the operator's (E-0003's first line).

### Preconditions the work depends on

1. `targets.parse` needs no change to express a threshold (P4), so wave A's file and 0.4's file
   are the same format and one reader reads both.
2. All three rows take `(start, end)` (P7), so one window spans the composite and no key has to be
   printed with a window of its own.
3. `facts.load` is one call both halves share, and `throughput.load` accepts the facts it is
   handed (`throughput.py:674-677`), so a file naming both `value.*` and `throughput.*` pays
   P9's 45.5 s once.
4. `release.compute` appends criteria from their own modules and `_na(key, name, why)` is the met
   verdict for a criterion that does not apply (`release.py:188-189`) — criterion 14 needs no new
   machinery in the gate.
5. `env.load_file` reads the YAML `--check` already parses, and resolves nothing: a relative
   `release.targets` is resolved by the criterion against `product.repo_dir`.
6. `DOCUMENTED_UNCHECKED_FIELDS` is the registration a `release:` sub-key gets (P11), so a product
   that sets `release.targets` loads on this release and is not refused by a pinned reader.
7. `tests/test_scorecard.py::TargetsTests` and `::ProgramTests` already cover the file format and
   the program row, so the new module owns only what is new.

## The design

### 1. `asf/scorecard/targets.py` — one row, three namespaces, one window

The module keeps its shape — `parse`, `lookup`, `check`, `render` pure over their inputs — and
gains the reader the module docstring promises:

```python
#: the rows a target may name, each a namespace at the top of the row :func:`row` builds. A key
#: whose first segment is none of these is a program-row key, as every target written before
#: F-0345 is (D2).
NAMESPACES = ('program', 'value', 'throughput')


def needs(targets):
    """The namespaces ``targets`` asks for — the halves :func:`row` must build, and no more
    (D3: facts cost 45.5 s on a real record, the program row 27.3 s)."""


def row(root, product, start, end, need=NAMESPACES):
    """The composite row over ``[start, end)``: ``program`` (:func:`asf.scorecard.program.row`),
    ``value`` (:func:`asf.scorecard.score.window_row`) and ``throughput`` (one entry per
    :data:`asf.metrics.throughput.METRICS` key, from :func:`~asf.metrics.throughput.evaluate` —
    never ``compute``: a target reads a reading, not a trend).

    The module's only reader. One window for all three, so two keys of one file are never two
    windows. Facts are loaded once for both halves that need them, with ``forge=False``: a gate
    waits on no network. A namespace outside ``need`` is absent, and every key under it reads
    *not read*.
    """
```

`lookup` gains the fallback, three lines, and keeps returning `_MISSING` for anything else:

```python
    parts = key.split('.')
    cur = row if parts[0] in NAMESPACES else row.get('program', _MISSING)
```

and the throughput half is flattened by key, with the two derived numbers of D4:

```python
    rows = throughput.evaluate(f, start, end, seat_cfg, cfg)
    out['throughput'] = {r['key']: dict(r, alarm=1 if r['status'] == throughput.ALARM else 0)
                         for r in rows}
    out['throughput']['alarms'] = sum(1 for r in rows if r['status'] == throughput.ALARM)
```

`render` gains one header line naming the window, and the per-line `why` stays as it is:

```
scorecard --check <p> 2026-10-03T18:57:19Z → 2026-10-10T18:57:19Z (program, value, throughput)
```

A key under a namespace that was not loaded prints `not read` exactly as a missing key does today —
which is correct and is the reason `needs` is computed from the file rather than passed in: the
only way a namespace is missing is that no target named it.

### 2. `asf/views/scorecard.py` — `cmd_check`, unchanged in shape

```python
def cmd_check(args, product):
    """``asf scorecard --check <targets.yaml> [--window …]``: exit 1 listing each missed target."""
    from asf.scorecard import program, targets
    try:
        tg = targets.parse(env.load_file(args.check))
        start, end = program.window(_window(args))
    except (OSError, ValueError) as e:
        print(f'scorecard --check: {e}')
        return 2
    row = targets.row(root, product, start, end, need=targets.needs(tg))
    results = targets.check(row, tg)
    print(targets.render(results, product.name, start, end, need=targets.needs(tg)), end='')
    return 0 if all(ok for _t, _v, ok in results) else 1
```

`program.window` stays the window parser (`7d`, `36h`, `since=<iso>`), `--all`'s other products
still reach `idle_hours` through `row`'s program half, and the three exit codes are what they were.
`--json` is not added: the one caller that wants the numbers as data is the release gate, and it
calls `targets.row` directly.

### 3. `docs/program/targets-0.4.yaml` — the release's figures

```yaml

  - {key: program.mechanical_only_corrects.usd, op: '<=', value: 5, why: code could resolve these (baseline 20.97)}
  - {key: value.repair_per_feature, op: '<=', value: 4, why: repair sessions per Feature (baseline 7.6)}
  - {key: program.heavy_share, op: '<=', value: 0.45, why: share of spend on the heavy model (baseline 0.622)}
  - {key: value.ci_min, op: '<=', value: 20000, why: CI minutes in the window (baseline 40283)}
  - {key: value.denials.mean, op: '<=', value: 1, why: refused tool calls per run (baseline 3.73)}
  - {key: value.denials.share_pct, op: '<=', value: 15, why: runs carrying one (baseline 42.8 %)}

  - {key: value.usd, op: measured, why: the scorecard's dollar, the one every target above reads}
  # ---- speed

  - {key: value.median_task_days, op: '<=', value: 1.5, why: a Task's own lead (baseline 6.7)}
```

- [ ] the alarm number of a metric reading not applicable is zero
