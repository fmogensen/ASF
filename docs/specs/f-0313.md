# F-0313 — the review was written, read and thrown away

A review session's whole deliverable is one file it leaves in its worktree. The harvest is what
binds that file to the code it reviewed and files it off the branch, and it does so through one
call, `asf/workers/health.py:466-471`:

```python
    try:
        filed = review_store.take(review_store.root(product), product.conventions, wt, branch,
                                  item, ev.remote_sha)
    except (OSError, ValueError, subprocess.SubprocessError) as e:
        found.append((job, 'filed', f'review not filed: {(str(e) or type(e).__name__)[:200]}'))
        return ev
```

`take` refuses out loud when the worktree it is handed is no git checkout — deliberately, because
nothing it holds can be bound to a head (`review_store.py:181-189`, a product's T-0091). The
refusal is caught here, logged, and that is the end of it. The review is still sitting in the
directory. Nobody reads it again, nothing retries, and the `except` branch returns the evidence
untouched, so no entry is filed and the run carries no `review_filed`.

What follows is mechanical. The lane finds no review for the head and says `no ASF review yet`
(`lane.py:1454`). The row's next wave asks the relaunch cap, which reads the session's own report
— `status: done` — as a terminal claim and parks the row at one launch
(`relaunch.py:276-304`). The PR is green, mergeable and unparked, and it will sit there until a
new commit or `asf unpark`. The card names #1191, #1184, #1142 and "many earlier ones", and 2–4
such rounds each for `review-t-0817`, `t-0807`, `t-0709`, `t-0812`, `t-0799`, `t-0720`, `t-0663`
and `t-0591`.

The card's requirement is the sentence the `except` branch is missing: **a finished review is
recovered, not dropped.** Everything needed is already on disk — the review file is a plain file
in a plain directory, and the only thing git was being asked for is a sha the product repo knows
perfectly well. P1 and P2 below measure that: every `git` command in such a worktree fails, and
the review file reads fine, with the exact head it reviewed written inside it.

## Decisions

### Preconditions — measured in this worktree at `5b2a8f06a`, 2026-10-08

Each block below is the output of a script run against this tree. The fixture is the card's own
failure: a linked worktree `worktrees/review-t-1` on `worker/T-1`, a review written at
`conventions.review_path('t-1', 1)`, then `.git/worktrees/review-t-1` removed — the sandbox
refusal the card names, as git sees it afterwards.

* **P1 — git is wholly gone in that worktree; the filing refuses and files nothing.**

  ```
  git rev-parse --show-toplevel: rc=128 out='' err='fatal: not a git repository: <repo>/.git/worktrees/review-t-1'
  git status --porcelain:        rc=128 out='' err='fatal: not a git repository: <repo>/.git/worktrees/review-t-1'
  git rev-parse HEAD:            rc=128 out='' err='fatal: not a git repository: <repo>/.git/worktrees/review-t-1'
  is_checkout: False
  NotACheckout: <tmp>/worktrees/review-t-1 is not a git checkout: the review of T-1 on worker/T-1 cannot be filed from it
  entries filed: []
  ```

  Not one git question can be asked there — not `HEAD`, not `status`, not the toplevel. This is
  why `take` cannot file: it has no head to bind to, and `is_checkout` is right to say so.
* **P2 — the review itself is perfectly readable, and it names the PR head.** The same directory,
  read with no git at all (`review.worktree_review`, which is `os.walk` plus `open`,
  `review.py:205-227`):

  ```
  worktree_review round/path: 1 docs/reviews/1-t-1.md chars 217
  verdict block: approved fc5c6ecd4 ()
  block head == origin head of the branch: True fc5c6ecd4
  ```

  The file is there, its round is there, its verdict is there, and the sha in its `verdict` block
  is byte-identical to `origin/worker/T-1`. The one fact `take` could not get from the broken
  worktree is written inside the file it was trying to file.
* **P3 — the evidence the harvest hands `take` is empty for such a worktree, and the product repo
  has the head anyway.** `lifecycle.gather` returns early when `git status` fails
  (`lifecycle.py:2525-2527`):

  ```
  ev.worktree: False  ev.head: ''  ev.remote_sha: ''
  remote_head(repo, branch): fc5c6ecd4
  ```

  So `ev.remote_sha` — the argument `file_review` passes as the PR head — is `''` in exactly the
  case that needs it, while `lifecycle.remote_head` asked in the **product repo** answers at once.
  The recovery's head must come from the repo, never from the worktree.
* **P4 — the drop, as the card reports it.** `health.file_review` on that worktree:

  ```
  found: [('review-t-1', 'filed', 'review not filed: <tmp>/worktrees/review-t-1 is not a git
           checkout: the review of T-1 on worker/T-1 cannot be filed from it')]
  ev returned unchanged: True | review_filed on run: None
  entries: []
  ```

  One log line, nothing filed, nothing marked, the evidence returned as it came.
* **P5 — a review run that filed nothing is judged a failure, and its report still reads
  terminal.**

  ```
  judge, nothing filed : failed: empty branch: nothing to land
  judge, review_filed  : finished
  terminal(REPORT)     : 'status done'
  counted(run)         : True
  ```

  `review_filed` is the only thing that makes a review run read as finished
  (`lifecycle.py` / `tests/test_review_store.py:213-221`), and `relaunch.counted` counts the run
  regardless: its two exclusions are `heartbeat_refused` and `stopped_by` (`relaunch.py:89-93`).
* **P6 — the park, verbatim.** One ended run, `CAP = 2`, a `status: done` report:

  ```
  streak len: 1
  verdict: review-t-1 launched 1 time(s) on fffffffff with the card and cause unchanged, its last
           report: status done. Not relaunched: the row is parked until a new commit, review, card
           edit or decision changes its state, or `asf unpark T-1`
  ```

  The terminal shortcut parks at one launch (`relaunch.py:276-281`) — the card's
  `launched 1 time(s) … last report: status done. Not relaunched`, to the word. The session said
  `done` because it *was* done; the work it finished is what nobody collected.
* **P7 — the lane's line.** `lane.review_reason({})` → `(1, 'no ASF review yet')`, printed as
  `waiting worker/T-78560: PR #1191 not approved — no ASF review yet: review round 1 asked for`
  (`lane.py:2477-2481`). The line is honest about the absence and says nothing about the cause, so
  nothing in the tick output connects it to the `review not filed` line health printed above it.
* **P8 — a relaunch destroys the evidence, so the recovery can never be left to it.**
  `spawn.make_worktree` sets a non-checkout directory aside in the trash and cuts a fresh checkout
  below (`spawn.py:769-781`, the T-0091 fix). Running `tests.test_non_checkout_worktree`:

  ```
  set aside <tmp>/state/sample/worktrees/again: a leftover directory with no git checkout, not
  reused (<tmp>/state/sample/trash/again-20261008T215345)
  Ran 66 tests in 2.968s — OK
  ```

  The review file goes into the trash with the directory. **The recovery must run before any
  relaunch of that job**, and it does, by the tick's own order (P9).
* **P9 — the ordering holds by construction.** The tick runs
  `record → wave → health → groom → prs → harvest → daily` (`asf/tick/tick.py:2`). Only health
  writes `ended` (`health.py:962-968`), `relaunch.streak` counts only runs that carry `ended`
  (`relaunch.py:115-116`), and `spawn` refuses a job whose run is still live. So the first wave
  that could relaunch a review job is the one *after* the health pass that ended it — the same
  pass that would run the recovery. And the lane runs in `harvest`, after `health`, in the same
  tick (`tick.py:644`: `ctx.lane_passed = False` so "the branches health just settled advance in
  its lane pass"), which is what makes the card's "within one wave" reachable at all.
* **P10 — the session's REPORT is a second copy of the verdict, and it does not live in the
  worktree.** The review brief's last line is `Final message: the verdict block, the failing rows,
  the gate lines` (`briefs/templates/review.md:44`), and the run's log is
  `<ASF_HOME>/logs/jobs/<product>/<job>.jsonl` (`runtime.job_log_path`), outside every worktree.
  `runtime.read_result` returns the result line of the log's **last** run, so a relaunch of the
  same job overwrites the answer: the REPORT must be read at the run's end, which is where
  `file_review` already runs.
* **P11 — a recovered review text reads correctly under either `verdict_block` setting.** The flag
  defaults to `off` (`review.block_mode`), where the **table** answers first and a bare block
  would not be read. Measured, for a text carrying a `verdict:` line, a `head:` line and the block:

  ```
  required rows for code: ('the diff stays inside writes', 'every step of the task is implemented',
    "the acceptance tests are byte-identical to the plan's", 'those tests were run and are green',
    'the gate commands are green', 'no secret value printed, no background process, no skipped check')
  reviews.verdict(no table, required): ''
  verdict_of(block=False): approved     verdict_of(block=True): approved
  head_of(block=False)   : aaaaaaaaa    asks_nothing: True
  ```

  `reviews.verdict` returns nothing for a text with no table, so `verdict_of` falls through to the
  `verdict:` line (`review.py:264-271`) and both settings agree. A `changes` block reads `changes`
  under both, with `asks_nothing` false. A bare fenced block alone also reads `approved` at
  `block=False` — but it carries no `head:` line for `head_of`, which is why the recovered text is
  written with all three and not as a raw dump.
* **P12 — nothing in the record retries, counts or names an unfiled review today.**
  `grep -rn "review_unfiled\|unfiled" --include=*.py asf/` finds nothing. The only trace a dropped
  review leaves anywhere is the one `review not filed:` line in the tick log (P4), and no reader
  reads it.

### Preconditions the work depends on

* The worktree **directory** still exists and its `docs/reviews/` is readable. When it does not,
  the REPORT path (§1–§2) answers with no worktree at all, and when neither answers, the mark and
  the relaunch do (§3).
* The product repo is a checkout that knows `origin/<branch>` — true for every caller of
  `health.file_review`, which already uses `product.repo_dir` throughout.
* `health` runs in the tick after the wave and before the lane (P9). Nothing in this change
  reorders the tick.
* `conventions.review_path` / `review_pattern` is the one path contract, and the slug is the
  item's id lower-cased. Both readers (`review.pick`, `review.pattern_rx`) already answer for a
  bare directory.
* A review run's `launch_head` is on its launch line (`relaunch.py` reads it throughout), so the
  head the session was handed is a recorded fact even when its worktree is gone.

### The choices

| # | Chosen | Against | Why |
|---|---|---|---|
| D1 | `take` keeps raising `NotACheckout`; the recovery is a second function the caller reaches through the `except` | Make `take` fall back internally | `take`'s contract is "file what this checkout holds, bound to its HEAD" and its refusal is a measured fix of its own (T-0091, P1). A fallback inside it would hide, in one function, two different answers to "which head is this review about". The `except` branch is also exactly where the drop happens today, so the diff lands on the defect |
| D2 | The worktree file first, the REPORT second | The REPORT first; only the REPORT | The file is the review — the table, the C list, the I list, every finding a correction would answer. The REPORT carries the verdict and nothing else (P10), so a REPORT-recovered `changes` would send a correction a C list it cannot read. The file is also the common case: the sandbox refused `.git/worktrees/…`, not the worktree's own `docs/` (P2) |
| D3 | The head the entry binds to, in order: the review's own `verdict` block `head:`, then its `head:` line, then the run's `launch_head`, then `origin/<branch>` — and each must be a commit the product repo can `rev-parse --verify`; when none is, nothing is filed | Always the PR head, as the card words it | The card's words are satisfied in the measured case, because the block's head *is* `origin/<branch>` (P2). Preferring the review's own head costs nothing there and refuses to do the one unsafe thing available: binding an approval to code the session never read. A head the repo cannot resolve is not a head — it files nothing and relaunches instead |
| D4 | The PR head comes from `lifecycle.remote_head(product.repo_dir, branch)` | `ev.remote_sha`, as `take` is called today | P3: `ev.remote_sha` is `''` for precisely these worktrees, because `gather` gave up at the first failed `git status`. The product repo answers |
| D5 | A recovered REPORT becomes a review text with a `verdict:` line, a `head:` line and the block verbatim, under a heading that says it was recovered and from where | File the raw REPORT text; file a synthesised table | P11: those three keys make it read identically under `verdict_block: off`, `warn` and `on`, and `head_of` answers for the readers that ask the file rather than the entry name. The provenance heading is for the human who opens the review in a correction brief and wonders why it has no table |
| D6 | The entry is filed through `review_store.put`, under the same layout, and the recovery is skipped when the run already carries `review_filed` | A separate store or file name for recovered reviews | A recovered review is a review: every reader must find it without knowing it was recovered. `put` writes one stamped file per call, so the `review_filed` guard is what keeps a second health pass from filing a duplicate — the normal path is idempotent only because `take` deletes the file it filed, which a recovery over a possibly read-only worktree cannot rely on |
| D7 | `review_unfiled` carries `n` — how many unfiled runs of this job stand on this head — and `counted` exempts only `n <= 1`; the park that follows the second reads `review round <n> was never filed: <why>` instead of the report's `status done` | Exempt every unfiled review run; exempt none; a separate relaunch queue | "Relaunched once" is the card's word and the loop bound in one number. Exempting every such run is unbounded (a worktree that cannot be built would relaunch for ever); exempting none is today's park. The claim swap is what makes the second outcome a park that *names the cause* — "never a silent park" has to hold on the park too, not only instead of it |
| D8 | The mark carries the action as health decided it (`a fresh review round is launched` / `parked: …`), and the lane prints it | The lane re-derives the action from `n` | One owner for the decision. The lane prints what the record says, so the waits line and the park reason cannot disagree about what the factory did |
| D9 | The waits-line clause is appended inside `lane.review_reason`, after the existing `why` | A new line of its own; a new lane state | `review_reason`'s `why` is already both the printed line and the recorded lane reason (`lane.py:2477-2481`, `tests/test_lane.py:82`), so one change reaches both, and the card's "one waits line" stays one line. | D10 | `lifecycle.unfiled_review(path, item, head)` is the reader, beside `review_answered` and `corrected_on` | Read the sessions file in `lane.py` | Those two are the precedent for exactly this question — "what did another run of this item do" — and they live in `lifecycle` because the lane is not a reader of the registry's shape (`lifecycle.py:3206-3246`) |

## The design

Six files. One text builder in the review reader, one filing function in the store, the `except`
branch in health, one mark and one reader in `lifecycle`, the cap's two rules in `relaunch`, and
the clause in the lane's line.

### 1. `asf/evidence/review.py` — a REPORT's verdict, as a review

```python
#: The heading a recovered review carries, so a reader of one knows it was not written as a file.
RECOVERED = 'Recovered verdict'


def recovered_review(report, head, item='', n=0, source='the session REPORT'):
    """A review text built from the verdict block in a finished session's ``report``, bound to
    ``head`` — or '' when the report carries no valid block (:func:`verdict_block`).

    The text carries its ``verdict:`` line, its ``head:`` line and the block verbatim, so it
    reads the same under every ``flags.verdict_block`` setting (F-0313 P11): at ``off`` the
    table answers first and there is none, so the ``verdict:`` line does; past ``off`` the block
    does. It carries no check table: a row with no evidence counts as ``fail`` (the review
    template), and a recovery has no evidence to put in one.
    """
```

It builds, for an approved block on `fc5c6ec…`:

````markdown
# Recovered verdict — T-1 review round 1

The review session finished and its review could not be filed from its worktree. This verdict is
the one its REPORT printed, recovered by the harvest (F-0313). It carries no check table.

verdict: approved
head: fc5c6ecd4...
asks: none

```verdict
verdict: approved
head: fc5c6ecd4...
asks: []
```
````

### 2. `asf/evidence/review_store.py` — the filing, with a head of its own

```python
#: Where a recovered review came from (:func:`recover`'s third return value).
FROM_WORKTREE, FROM_REPORT = 'the review file in its worktree', 'the session REPORT'


def recover(store, conv, repo, wt, branch, item, pr_head='', report='', launch_head=''):
    """File the review of a finished session whose worktree is no git checkout — what
    :func:`take` refuses (:class:`NotACheckout`) because nothing there can be bound to a head.

    Returns ``(round, entry path, source)``, or None when there is nothing to file.

    The review is read without git: the newest review file of ``item`` in ``wt``
    (:func:`asf.evidence.review.worktree_review` — ``os.walk`` and ``open``), else the verdict
    block of ``report`` as a review text (:func:`asf.evidence.review.recovered_review`).

    The head it is bound to is the first of these the repo can ``rev-parse --verify``: the head
    the review itself names (its ``verdict`` block, then its ``head:`` line), the run's
    ``launch_head``, ``pr_head``. None of them resolvable is None: an entry bound to a sha no
    reader can resolve is worse than no entry (F-0313 D3).

    Nothing is written to ``wt`` and nothing is removed from it: the sandbox that broke the
    gitdir may refuse writes there too. The caller's ``review_filed`` is what keeps a later pass
    from filing the same review twice (F-0313 D6).
    """
```

### 3. `asf/workers/health.py` — recover, then mark, then one line

`file_review`'s `except` branch becomes the recovery. The rest of the function is untouched.

```python
#: health's mark on a review run whose review could not be filed: ``{round, head, why, at, n,
#: action}`` — ``n`` counts the unfiled runs of this job standing on this ``head``, this one
#: included, and ``action`` is what the factory did about it, in words the lane prints (F-0313).
REVIEW_UNFILED = 'review_unfiled'


def recover_review(product, job, run, ev, found, why):
    """A review `take` could not file, recovered (:func:`asf.evidence.review_store.recover`) and
    filed, or — when there is nothing to recover — marked ``review_unfiled`` so the relaunch cap
    does not count the run as a launch (:func:`asf.workers.relaunch.counted`) and the lane's
    waits line can name it. One ``recovered`` line either way, never a silent drop."""
```

* The head: `lifecycle.remote_head(product.repo_dir, branch)` (D4, P3).
* Filed → `pool_mod.update_session(product, job, review_filed=path, review_unfiled=None)`,
  `run['review_filed'] = path`, one line, and the evidence is re-gathered exactly as the normal
  path does, so the run is judged `finished` and not `failed: empty branch` (P5):

  ```
  recovered review-t-78560          round 1 of T-78560 filed off worker/T-78560 against
                                    fc5c6ecd4 (the review file in its worktree; its worktree is
                                    not a git checkout) — 20261008T214548123456Z-r1-fc5c6ec….md
  ```
* Nothing to recover → the mark, with `n` counted off `lifecycle.item_runs`, and:

  ```
  recovered review-t-78560          round ? of T-78560 was not filed (its worktree is not a git
                                    checkout, and its REPORT carries no verdict block) — a fresh
                                    review round is launched
  ```

### 4. `asf/workers/relaunch.py` + `asf/workers/lifecycle.py` — an unfiled review is no launch

```python
#: Unfiled review runs of one job on one head that the cap does not count: the first. A second
#: says the worktree cannot be built by trying again, and the row parks (F-0313 D7).
UNFILED_FREE = 1


def counted(run):
    """False for a run the relaunch cap never counts, as it never counts a spent window's: one
    health marked ``heartbeat_refused`` (F-0279), one the operator stopped (``asf stop``), and
    the first whose finished review could not be filed (``review_unfiled``, F-0313) — none of
    them says anything about the work."""
    unfiled = run.get('review_unfiled') or {}
    if unfiled and int(unfiled.get('n') or 1) <= UNFILED_FREE:
        return False
    return not run.get('heartbeat_refused') and not run.get('stopped_by')
```

and in `_assess`, where the terminal claim is read, the mark speaks for the run instead of its
report — so the park that does come names the cause (D7):

```python
    claim = '' if heartbeat_refused(text) else terminal(text)  # F-0279: not the work's claim
    unfiled = runs[0].get('review_unfiled') or {}
    if claim and unfiled:   # F-0313: the report said done; what failed was the filing
        claim = f'review round {unfiled.get("round") or "?"} was never filed: {unfiled["why"]}'
```

`RUN_FIELDS` gains `'review_unfiled'` (D11), and `lifecycle` gains the lane's reader:

```python
def unfiled_review(path, item, head):
    """The ``review_unfiled`` mark of the newest ended ``review`` run of ``item`` launched on
    ``head`` that never filed its review, or None — with the job that wrote it. A run that
    carries ``review_filed`` is not one, whichever way it filed."""
```

### 5. `asf/harvest/lane.py` — the waits line

`branch_facts` asks it where it already asks `review_answered`, and only for a head with no

### S-84455: a finished session's REPORT verdict, as a review text every reader reads alike

Design §1 — `review.recovered_review` and `review.RECOVERED` (D5; P10, P11). Acceptance is the
first fenced block of `## Acceptance tests`. The text carries three statements of the same verdict
because the readers disagree about which one they read: at `verdict_block: off` the table answers
first and a recovered review has none, so the `verdict:` line must carry it; past `off` the block
does; and `head_of` reads a `head:` line, not an entry name.

- [ ] a report carrying an approved verdict block becomes a text whose verdict reads approved with the block flag off
- [ ] the same text reads approved with the block flag on, and its head is the sha the block named
- [ ] a changes block becomes a text that reads changes under both settings, and asks_nothing is false for it
- [ ] the asks the block listed are carried into the text, so a correction brief can name them
- [ ] a report with no verdict block returns the empty string, and a block whose head is not a sha counts as none
- [ ] a report with two blocks is read like every other reader reads one: the first valid block wins
- [ ] the text carries no check table, and it carries the recovered heading and the head it is bound to
- [ ] the head the text is bound to is the one the caller passed, not one the report mentions elsewhere

### S-84456: the review in a worktree that is no git checkout, filed against a head the repo knows

Design §2 — `review_store.recover`, beside the `take` whose refusal it answers (D1, D2, D3, D6;
P1, P2, P3). Acceptance is the second fenced block. The head order is the whole safety argument:
the review's own head first means a recovery can never bind an approval to code the session did
not read, and an unresolvable head files nothing at all rather than an entry no reader can use.

- [ ] a worktree that is no git checkout but holds a review file files that file whole, with its round and its table
- [ ] the entry is bound to the head the review's own verdict block names, when the repo can resolve it
- [ ] a review naming no head in a block but carrying a head line is bound to that head instead
- [ ] a review naming no head at all is bound to the run's launch head, and with none to the PR head
- [ ] a head none of those four sources resolves in the repo files nothing and returns nothing
- [ ] the newest round in the directory is the one filed when the worktree holds several
- [ ] a worktree directory that holds no review file falls back to the report's verdict block and files that
- [ ] a worktree that is gone entirely still files from the report, since the report is read off the run and not the tree
- [ ] neither a review file nor a report block returns nothing, and files nothing
- [ ] nothing is written into the worktree and nothing is deleted from it, so a read-only worktree recovers the same way
- [ ] the entry lands in the same store layout as a review that take filed, and the store's own readers find it
- [ ] take still raises its loud refusal for the same worktree, unchanged

### S-84457: the harvest recovers a finished review instead of dropping it, and marks the run when it cannot

Design §3 — `health.recover_review` and the `except` branch that calls it (D4, D6, D12; P4, P5,
P8, P9). Acceptance is the third fenced block, and it is the card's fourth requirement: a worktree
whose gitdir is missing, the harvest run over it, and the entry, the unparked row and the queued
relaunch asserted.

- [ ] a review worktree whose gitdir is missing has its review filed by the harvest, and an entry exists for the branch afterwards
- [ ] the PR head the entry is bound to is read from the product repo, not from the broken worktree whose evidence is empty
- [ ] the run carries review filed after the recovery, so the pass judges it finished and not an empty branch
- [ ] the pass prints exactly one line for the run, and it names the round, the branch, the head and where the review came from
- [ ] a second health pass over the same run files no second entry, because the run already carries review filed
- [ ] a worktree with no review file and a report with a verdict block is recovered from the report, and the line says so
- [ ] a worktree with no review file and no report block files nothing and marks the run unfiled instead
- [ ] the mark carries the round, the head, why the filing failed, the count of unfiled runs on that head, and the action taken
- [ ] the mark is cleared when a later pass does file the review
- [ ] a review run whose worktree is a sound checkout is filed exactly as before, by take, with no recovery and no mark
- [ ] a coder run and a live review run are still left alone

### S-84458: an unfiled review is not a launch the park rule counts, once per head, and the park that follows names it

Design §4 — `relaunch.UNFILED_FREE`, `counted`, the claim in `_assess`, `RUN_FIELDS` and
`lifecycle.unfiled_review` (D7, D10, D11; P5, P6). Acceptance is the fourth fenced block. One
number bounds the loop: the first unfiled run on a head buys a relaunch, the second parks, and the
park says why instead of repeating the report's status done.

- [ ] a review run marked unfiled with a count of one is not counted by the cap, so a row with one such run is not parked
- [ ] the same run with a count of two is counted, and the row parks
- [ ] the park reason for a counted unfiled run names the round that was never filed and why, not the report's status done
- [ ] a run marked unfiled that later filed its review is counted again, as any finished run is
- [ ] the heartbeat and operator-stop exclusions keep working beside the new one
- [ ] review unfiled is a run field, so a null line clears it and it never folds into the next run
- [ ] the lane's reader returns the newest unfiled mark of the item's review runs on the head given, with the job that wrote it
- [ ] the reader returns nothing for a run that filed its review, and nothing for a head no review run was launched on

### S-84459: one waits line names the unfiled review and the action taken, never a silent park

Design §5 — `lane.review_reason`'s clause and the fact `branch_facts` reads for it (D8, D9; P7).
Acceptance is the fifth fenced block. The clause is appended, never substituted, so the lane's
recorded reason and every landed assertion of the printed line stay what they were when no review
was dropped.

- [ ] a head with no review and an unfiled review run gets a waits line naming the round, why it was not filed, and the action taken
- [ ] the action in the line is the one the record says the factory took, not one the lane derives for itself
- [ ] a head with no review and no unfiled run gets exactly the line it gets today, byte for byte
- [ ] a head whose review was filed gets its normal verdict line, with no clause about filing
- [ ] the round the line asks for is unchanged by the clause
- [ ] the lane records the same string it prints, so the row's reason names the unfiled review too
- [ ] the whole wave over a branch whose review was dropped prints that one waits line and no park line
