# F-0133 — three ways a fresh install quietly does less than it looks like it is doing

Three gaps the first customer install found. None of them raises anything: each one is silent, and
each one is silent in the same way — the machinery runs, prints its usual line, and the result does
not survive or never happens at all.

1. **The groom writes and does not commit.** `cmd_groom` rewrites cards, writes
   `groom/<date>.md`, the digest and `index.json`, and touches git nowhere (P1). On the console
   that is already fixed — `asf/cli.py` wraps it in `_published` (P2, the `354e2f66c` hotfix). On
   the tick, which is where the groom actually runs, `step_groom` calls `cmd_groom` **directly**
   (P3) and the output waits for the tick's one end-of-tick commit (P4). When that commit does not
   happen — or happens and its push is refused — the next tick's `ensure_clone` does
   `git reset --hard origin/<main>` and `git clean -fdq`, and the groom's work is **gone**, not
   merely dirty (P5).

2. **A stamp ASF did not write skips the native daily.** `daily_due` reads
   `<state>/<product>/daily.stamp` and compares its stripped contents against today's date. A
   pre-ASF daily job left a file there holding exactly `YYYY-MM-DD`, which is byte-for-byte what
   ASF writes — so ASF read another job's stamp as its own and skipped (P6, reproduced).

3. **A new product does not groom.** `approvals.groom` is unset unless someone types it;
   `asf init` writes no `approvals:` block at all (P7). Unset, `feeder.rows.groom_rows` returns
   `[]` before it reads anything else (P8): no `GROOM → ADJUDICATE` session, no `GROOM → CLERK`
   session, no policy pass, no digest. Intake still mints cards, so the inbox *looks* attended —
   the questions simply accumulate with nobody minted to answer them. Nothing says so (P9).

This card is: **the groom commits what it wrote, the daily trusts only a stamp in ASF's own
format, and `asf init` turns the groom on.**

| C1 | **The publish moves *inside* `cmd_groom`; `asf/cli.py` stops wrapping it.** | Adding a second `_published` call in `step_groom` and in `answers.apply_pending_answers`. | The card names the shape — *"like `asf inbox` does"* — and `cmd_inbox` publishes from inside itself (`asf/groom/inbox.py:150`). One seam covers all three callers (P2, P3) instead of three that must each be remembered. | C2 | **Today's body becomes `_groom(args, root)`; the new `cmd_groom` is the four-line wrapper.** | Threading a `publish_changes` call through every `return` in the body. | The body has four exits (parse errors, `_write_incremental`, the two prints). A groom that swept up `health`'s half-written state would be a new failure mode in place of the old one. |
| C4 | **A refused push is left as it is.** | Retrying, or holding the output somewhere outside the clone. | `publish_changes` already prints one stderr warning on a refusal and `shadow.push` already rebases onto a moved origin (P11). What this card removes is the *other* exposure — a tick that never reaches `finish`, a `finish` whose record lock is held, a `finish` that raises. | C5 | **The stamp gains a format of its own: `asf-daily <YYYY-MM-DD>`.** | Leaving the format and only adding the doctor row, as the card's "or" allows. | The card's own failure is a file whose contents are *indistinguishable* from ASF's (P6). ## The design

### §1 The groom commits its own output

`asf/groom/groom.py` — today's `cmd_groom` is renamed `_groom` with **no other change**, and the
name it gave up becomes the wrapper:

```python
def _commit_message(args):
    """The subject the groom's own commit carries: the date it groomed, and which of the three
    ways it was called."""
    date = args.date or datetime.datetime.now(datetime.timezone.utc).strftime('%Y-%m-%d')
    if getattr(args, 'answers_file', None):
        return f'groom: {date} (answers)'
    if getattr(args, 'incremental', False):
        return f'groom: {date} (tick)'
    return f'groom: {date}' + (' --apply' if getattr(args, 'apply', False) else '')


def cmd_groom(args, root):
    """``asf groom``: intake, the policy pass and the questions — and then a commit of what it
    wrote, pushed (F-0133).

    The groom rewrites cards, ``groom/<date>.md``, the digest and ``index.json`` and, until this,
    committed none of it: on the console that was papered over by ``asf.cli._published``, but the
    tick calls this function directly (:mod:`asf.tick.step_groom`) and the output waited for the
    tick's one end-of-tick commit. Anything that stopped the tick reaching it — a later step
    raising, the record lock held, a refused push — left the work in the clone, and the next
    tick's ``ensure_clone`` resets hard and cleans: the groom's cards and its file were *lost*,
    not merely uncommitted.

    Only what this call changed is committed (:func:`asf.record.publish.publish_changes` diffs
    against the snapshot taken here), so an earlier step's writes to the same clone stay for
    ``finish``. A ``root`` that is not a checkout with an ``origin`` is left entirely alone."""
    from asf.record import publish
    before = publish.snapshot(root)
    rc = _groom(args, root)
    publish.publish_changes(root, before, _commit_message(args))
    return rc
```

`asf/cli.py:491-494` loses its wrapper — the command publishes itself now:

```python
    if args.command == 'groom':
        from asf.groom.groom import cmd_groom
        return cmd_groom(args, resolve_record(args))
```

Three things are load-bearing. The snapshot is taken **before** `_groom` runs, so the paths
committed are exactly the paths this call changed (P11, C3). The publish runs on every exit of
`_groom`, including its `return 1` on parse errors — where it finds nothing changed and does
nothing. And `snapshot` returning `None` on a non-checkout (P10) is what leaves every existing
groom test, which builds its record with `make_repo`, untouched.

### §2 A stamp ASF did not write is not ASF's stamp

`asf/tick/steps.py`, replacing the three functions at `:174-190`:

```python
#: The first token of the daily stamp ASF writes. A file at :func:`stamp_path` that does not
#: begin with it was written by something else (F-0133: a pre-ASF daily job left one holding a
#: bare ``YYYY-MM-DD``, which is byte-for-byte what ASF used to write, and ASF skipped its own
#: daily for the rest of that day). One line, so the file stays readable by eye.
STAMP_MARKER = 'asf-daily'
_STAMP_RE = re.compile(r'^' + STAMP_MARKER + r'\s+(\d{4}-\d{2}-\d{2})$')


def read_daily_stamp(product):
    """``(date, foreign_text)`` for the file at :func:`stamp_path`.

    ``(date, None)`` — ASF's own stamp, and the day it stamped.
    ``(None, text)`` — a file is there and ASF did not write it; ``text`` is its first line
    (``'(empty)'`` for a file with nothing in it), for the doctor row to quote.
    ``(None, None)`` — no file at all: the daily has simply never run.

    The two absent cases are told apart on purpose: a product whose daily has not run yet is not
    a product with somebody else's job writing into its state dir."""
    try:
        with open(stamp_path(product), encoding='utf-8') as f:
            text = f.read()
    except OSError:
        return None, None
    first = next((ln.strip() for ln in text.splitlines() if ln.strip()), '')
    m = _STAMP_RE.match(first)
    if m:
        return m.group(1), None
    return None, (first or '(empty)')


def daily_due(product, force=False, today=None):
    """True when ``--daily`` was passed, when ASF's own stamp is not today's, or when the file
    at :func:`stamp_path` is not ASF's stamp at all — a stamp ASF cannot read as its own is no
    evidence that ASF ran, whatever date it carries (F-0133)."""
    if force:
        return True
    date, _foreign = read_daily_stamp(product)
    return date != (today or _today())


def write_daily_stamp(product, today=None):
    with open(stamp_path(product), 'w', encoding='utf-8') as f:
        f.write(f'{STAMP_MARKER} {today or _today()}\n')
    clear_daily_failure(product)
```

`daily_catch_up_due` is unchanged and gains the fix for free: it calls `daily_due`, so a tick after
the daily clock's hour on a day whose stamp is foreign runs the catch-up daily rather than
believing the day is done.

`asf/doctor.py`, a new check and one row appended right after `scheduler` (the daily is a clock's
business):

```python
def check_daily_stamp(product):
    """The doctor's ``daily`` row: ``(ok, detail)``. Not ok when the file at
    ``steps.stamp_path`` was written by something other than ASF — the case F-0133's card
    found, where a pre-ASF daily job's stamp made the native daily skip. It is a warning, not a
    red: ASF now runs its daily regardless, and a foreign stamp is replaced by ASF's own the
    moment that daily succeeds, so a required row would exit 1 on a product that is working."""
    from asf.tick import steps as steps_mod
    date, foreign = steps_mod.read_daily_stamp(product)
    if foreign is not None:
        return False, (f'{steps_mod.stamp_path(product)} is not ASF\'s stamp ({foreign!r}) — '
                       f'ASF writes "{steps_mod.STAMP_MARKER} <date>" and runs the daily '
                       'regardless; point the other job at a file of its own')
    if date is None:
        return True, 'no stamp yet — the daily has not run'
    return True, f'last run {date}'
```

```python
    ok, detail = check_daily_stamp(product)
    rows.append(('daily', False, ok, detail))
```

### §3 A new product grooms

`asf/init.py`, `render_product_yaml` — one block, after `ci:`:

```python
    out += ['approvals:',
            '  # the groom: its policy pass, its adjudicate and clerk sessions, its daily digest.',
            '  # Off (or absent) means the inbox is typed but nothing decides it and nobody is',

`asf/approvals.py`, `check_doctor` — one clause, first, so it leads the detail:

### What it looks like when it is there

The tick's groom step, with something to say:

```
== groom
groom 2026-09-30 (tick): inbox 2 card(s), asked 1, added 3 line(s), by rule 1, open 4
```

and, in the record clone, before the next step runs:

```
$ git -C <state>/<product>/record log --oneline -1
a1b2c3d groom: 2026-09-30 (tick)
$ git -C <state>/<product>/record status --porcelain -- groom features bugs index.json
$
```

A tick that dies in `wave` two steps later now loses nothing the groom wrote.

The daily, on a day another job got to the stamp first:

```
$ cat <state>/<product>/daily.stamp
2026-09-30
$ asf tick --steps daily --product <p>
daily: stale ok — 0 items past their limit
daily: rollup ok — rollup 2026-09-29: 4 items, 2 releases
daily: scorecard ok — scorecard 2026-09-30: 6 causes, 0 over threshold
[step:daily] 4.2s
$ cat <state>/<product>/daily.stamp
asf-daily 2026-09-30
```

and the doctor, in the window before that run:

```
== DOCTOR <p>
scheduler   ok    3 jobs loaded
daily       skip  <state>/<p>/daily.stamp is not ASF's stamp ('2026-09-30') — ASF writes
                  "asf-daily <date>" and runs the daily regardless; point the other job at a
                  file of its own
```

A new product, the moment `asf init` finishes:

```

## Records

- **The record repo** — one new commit per groom that changed something, ahead of the tick's own:
  `groom: <date>`, `groom: <date> --apply`, `groom: <date> (tick)` or `groom: <date> (answers)`,
  signed off, carrying only the paths that call changed — the groom file, the digest, the cards it
  edited, the cards intake minted, and the `index.json` those imply. The tick's `tick: state <ts>`
  commit is unchanged and still carries everything else.
- **`<state>/<product>/daily.stamp`** — one line, `asf-daily <YYYY-MM-DD>`, rewritten by
  `write_daily_stamp` after every daily that passed. The path does not move (C7). A file there in
  any other shape is read as nobody's stamp: the daily runs, and the next success replaces it.
- **`<state>/<product>/daily.failure`** — unchanged: written when the daily step exits non-zero,
  removed by `write_daily_stamp`.
- **`products/<name>.yaml`** — a file `asf init` writes new gains an `approvals:` block with three
  comment lines and `groom: auto`. An existing file is still never rewritten (`asf init` prints the
  discovery diff and leaves it), so the block is an addition to new products only.
- **`asf doctor`'s table** — one new row, `daily`, between `scheduler` and `cli:*`: `ok` with
  `last run <date>` or `no stamp yet — the daily has not run`, `skip` with the foreign stamp's
  first line quoted. Never red (C9). The `approvals` row's detail gains a leading
  `groom off: …` note when the gate is not `auto`; the row stays `ok` either way (C12).
- **No card, no Bug, no event.** Every one of the three is a commit, a file's contents or a line of
  a table. Nothing here writes to the record's items.

## Stories

- S: The groom commits and pushes its own output, on the tick as well as on the console — `cmd_groom` becomes `_groom` with a `publish.snapshot` → `_groom` → `publish.publish_changes` wrapper and a `_commit_message` naming the date and the call shape, so the tick's `step_groom` and `answers.apply_pending_answers` publish too and `asf/cli.py` stops wrapping it; only the paths that call changed are committed (an earlier step's writes stay for `finish`), a record that is not a checkout with an origin is left entirely alone, and the groom's cards and `groom/<date>.md` no longer wait for a tick-end commit the next `ensure_clone` would reset away — acceptance: `python3 -m unittest -v tests.test_groom_publish tests.test_groom_every_tick`
- S: A stamp ASF did not write never skips the native daily, and the doctor says whose it is — `steps.STAMP_MARKER`/`_STAMP_RE` and `read_daily_stamp` returning `(date, None)`, `(None, text)` or `(None, None)`, `daily_due` due for anything that is not ASF's own stamp of today (a bare `YYYY-MM-DD` included, with no grandfathering), `write_daily_stamp` writing `asf-daily <date>`, the catch-up inheriting the fix, and `doctor.check_daily_stamp` as a warning row quoting the foreign first line without reddening the install — acceptance: `python3 -m unittest -v tests.test_tick_steps tests.test_doctor tests.test_tick`
- S: A new product grooms by default, and one that does not is told so — `init.render_product_yaml` writing an `approvals:` block with `groom: auto` and the three comment lines that say what it turns on, the written file still loading with `groom_auto` True and the gate still filtered out of the approvals matrix, and `approvals.check_doctor` leading its detail with `groom off: inbox is not groomed — no adjudicate or clerk session is ever launched and no policy answers a card (intake still types them); set approvals.groom: auto` while the row stays `ok` — acceptance: `python3 -m unittest -v tests.test_install tests.test_approvals`
