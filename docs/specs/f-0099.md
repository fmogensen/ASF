# F-0099 — the groom runs on the tick clock

At 20:45 on 2026-09-23 seven cards sat in the intake directory waiting for the 06:00 daily —
four of them decided by the operator earlier the same day. Nothing was broken: the groom is a
part of the `daily` step (`asf/tick/step_daily.py:127`), the `daily` step is stamped once a day
(`asf/tick/steps.py:174`), and every card filed after it ran waits for tomorrow. The factory
ticks every ten minutes and grooms every twenty-four hours.

B-0089 closed on eb8cb90 with only half of its direction built: auto-filed S1/S2 Bugs are
decided by rule from their first groom, but since T-0035 *every* new item — Bug or Feature —
arrives through `asf inbox`, and an inbox card is neither auto-filed nor carries a `signature:`,
so `decide_recurring_bug` never sees it. Everything else waits three days
(`groom_undecided_section`, `asf/groom/groom.py:362`) before it is so much as asked about.

This spec moves the groom onto the tick clock: its own step, between `health` and `wave`, so a
card filed at 10:03 is typed at 10:10, asked at 10:10, and — when a rule or the adjudicator
answers it — decided and launched before 10:20. The per-date groom file stays the ledger it is,
but becomes additive within the day and idempotent across ticks, because a file rewritten every
ten minutes is a file nobody can read and a commit nobody wants.

This changes code under `asf/`, `tests/` and `sample/product.yaml` in this repository. It
changes no card in any record; it changes how often, and how early, the things that write to
cards run.

## 1. Decisions

### 1.1 In

- A **`groom` tick step** — `asf/tick/step_groom.py`, seventh name in `steps.STEPS`, placed
  `record → health → **groom** → wave → prs → harvest → batch → daily`. Owner `asf`, no product
  yaml change needed to get it (§2.1).
- The groom's three inputs, **all applied on every tick**: the pending `<job>.answers` files, the
  previous day's groom file, and **today's own groom file** (§2.3). `apply_pending_answers` and
  its siblings move out of `step_daily` into `asf/groom/answers.py`, where they belong.
- The **`daily` step reduced to `stale` and `rollup`** (§2.2). Its `groom` part becomes the new
  step; its `file-bugs` part is deleted outright — `run_step0` has run `cmd_file_bugs` on every
  tick since B-0060 (`asf/tick/tick.py:88`), so the daily copy was a second run of the same
  thing, hours later.
- An **additive, idempotent day file** (§2.4): a question's line is written once, the day it is
  first asked; an answered line is never rewritten; a question that no longer stands is dropped;
  the answer slot alone is re-derived each tick. Two `asf groom` runs over an unchanged record
  produce a byte-identical `groom/<date>.md`, digest, index and event stream.
- **Every undecided open item is a question from its first groom** (§2.5): the `Undecided > 3
  days` section becomes `Undecided`, threshold zero, and no card is asked twice in one file.
  `Undecided > 14 days` stays exactly as it is — it is `close_on_starvation`'s section, not a
  second question.
- **Intake with no per-run limit, and a filing stamp** (§2.6): `process_inbox` keeps typing every
  `*.md` in the intake directory in one run, now with a test that says so; `asf inbox` writes a
  `filed:` header, and intake emits one `intake` event per minted card carrying it.
- **An adjudicate round per question set** (§2.7): the adjudicate job becomes
  `groom-<date>-<sig>`, where `<sig>` is eight hex of the open-question id set.
  `groom.adjudicate_attempts` (default 2) becomes the cap *per set* rather than per day, bounded
  by a new `groom.adjudicate_rounds_per_day` (default 12). Without this the whole loop stalls
  after two sessions a day and the tick cadence buys nothing.
- **The measure** (§2.8): two scorecard rows — `intake → decided` and `decided → first session`,
  median and p90 minutes over the rollup's 7-day window — computed from the `intake`,
  `groom_answer` and `launch` events.
- **`asf doctor`: a step no clock ticks** (§2.9), plus `groom` added to `sample/product.yaml`'s
  dispatch clock. A step that exists but is on no clock is the exact failure this card is about,
  and it is invisible today.
- `asf groom --rebuild`: re-render today's file from the record, keeping answered lines (§2.4) —
  the escape hatch for a question whose text or bar went stale mid-day.

### 1.2 Out

- **B-0089's closing defect.** The card's last paragraph names a second defect: B-0089 closed
  because a commit named it, although its acceptance (the operator's direction in its body) was
  unmet. That is F-0080's definition of done, in `asf/harvest/`, and fixing it means deciding
  what evidence closes an item — a different subsystem, a different acceptance, and a change that
  would close or reopen cards in the live record. It needs its own Bug card and its own session.
  Nothing in this spec depends on it, and nothing here needs revisiting when it lands. The report
  this session ends with carries the `NEEDS OPERATOR:` line that files it.
- **Shortening the tick interval.** Ten minutes stays ten minutes. `asf inbox → decided` is
  bounded by one tick after this lands, which is the card's ask.
- **Deciding a card by rule that no rule understands.** The second tick *types* a card, *asks*
  it, and decides it when a policy answers it or the adjudicator's answers file is waiting.
  A plain Feature card is answered by no policy today (`policy.POLICIES` — four rules, none of
  which says `yes` to an arbitrary card), and inventing a fifth "decide anything new" policy is
  a way to decide things wrongly at speed. The acceptance test of §3/T9 therefore runs the
  adjudicate answer as a staged file, which is the production path minus the model.
- **A new policy, a new answer verb, a new section.** The section list changes by one rename and
  one threshold; the four policies, the answer grammar and the digest's four parts are untouched.
- **Incremental re-derivation.** The groom re-reads the whole record each tick, as it does now.
  "What is new since the last tick" is a property of the *output* — only new questions appear —
  not a scan window (choice row).
- **`index.json`'s per-tick churn.** `do_index` stamps a `generated` field and already runs on
  every tick from the `record` step; the groom step adds no new writer of it.
- **Touching the live `~/.ASF/products/asf.yaml`.** The `groom` step must be added to a clock
  there for any of this to run on the operator's factory. That file is not in this repository;
  `asf doctor` learns to say so (§2.9) and the report carries the line.

### 1.4 The choices

| Choice | Chosen | Against | Why |
|---|---|---|---|
| Where the groom runs | its own tick step, `groom` | a part of `daily` that tests its own stamp; a part of `record` | A step is the unit the operator schedules, the manifest lists, the tick times and the step log records. Hiding a per-tick job inside a once-a-day step is how the current defect came to be. |
| Its place in the order | after `health`, before `wave` | first; last | `health` writes the `ended` lines, so the groom's suppression and the adjudicate row see a true in-flight set; running before `wave` is what lets a card decided at 10:10 get its session at 10:10 rather than 10:20. |
| The day file across ticks | additive: one line per question, written once, answered lines kept forever, dead questions dropped, only the answer slot re-derived | rewrite it wholesale each tick; a new file per tick (`groom/<date>T<hhmm>.md`) | The card asks for additive and idempotent. A wholesale rewrite churns every age string into the diff 144 times a day; a file per tick breaks `groom_state`'s "newest file" and the one-digest-per-day contract. |
| An open question's `— <why>` | frozen at the text it had when first asked that day | recomputed each tick, so the age is current | An age recomputed every ten minutes makes the file differ on every tick, which is exactly the idempotency the card forbids. The live age is one `asf stale` away, and tomorrow's file asks again with a fresh one. `--rebuild` re-renders on demand. |
| The `(spoken for: …)` / `(barred: …)` marks | re-derived every tick, never kept | kept with the line | A session ends and its question becomes askable again; an approval flips and a bar lifts. These are statements about *now*, not answers. Only a real answer is a ledger entry. |
| Which file `--apply` reads | the previous day's **and** today's, every run | today's only; the previous day's only (today) | An answer typed into today's file at 10:03 must land at 10:10, and one typed into yesterday's at noon must still land. Both applications are idempotent, so applying both every tick is free. |
| The digest's write | written only when its body (the text minus the `— generated by asf groom@<sha> <HH:MM>` stamp) changed | written every run, as today | `cli.stamp` carries `HH:MM`: written every run, the digest alone would put a diff in every one of the day's 144 tick commits. |
| `file-bugs` in the daily | deleted | kept | `run_step0` runs it on every tick already. The daily copy re-ran the same command against the same clone hours later; nothing reads it that the tick's own run has not already produced. |
| Where the answers-file helpers live | `asf/groom/answers.py` | left in `asf/tick/step_daily.py` | After this change `step_daily` holds no groom code at all, and `step_groom` would otherwise import the daily step to do the groom's work. |
| "Every undecided item" | every open item with `decided != true`, types `decision` and `rule` excluded as today, asked at most once per file | every open item, duplicates and all; keep a 1-day threshold | The card says *from its first groom*, so the threshold is zero. Asking one card twice in one file doubles the adjudicate brief for nothing — the sections it is already in (`inbox`, `auto_bugs`) ask it better, with the reason that matters. |
| `Undecided > 14 days` | unchanged, still its own section | folded into the new `Undecided` section | `_POLICY_BY_SECTION` binds `close_on_starvation` to `undecided14`. Folding the sections would either fire starvation on day-zero cards or silently disable it. |
| The adjudicate cap | per **question set** (`groom-<date>-<sig>`, `adjudicate_attempts` tries each), bounded by `adjudicate_rounds_per_day` | per day, as today; per question; uncapped | Per day, the factory answers at most two batches a day and the tick cadence changes nothing downstream. Per set, a question that has had its two hearings goes to the operator and a *new* question gets a fresh one — which is the behaviour the card is asking for. The day ceiling is the stop on a pathological day where every tick brings a new card. |
| How the set is identified | eight hex of sha1 over the sorted open-question ids, carried in the job name | a new `questions:` field on the ledger row; a `<date>.asked` side file | The ledger already records `job`; counting attempts at a set is then a count over lines the factory already writes, with no new state and no new file to keep in sync. |
| The answers file's name | `groom/<job>.answers` (`<date>-<sig>.answers`), the legacy `<date>.answers` still read | one `<date>.answers` for the day | Two rounds in one day would otherwise write the same path, and a staged answers file carried in late from an ended session's worktree would land on a later round's questions. The date prefix keeps the supersede rule (§2.7) working. |
| What "superseded" compares | the **date** prefix only, strictly later | the whole file stem | With a signature in the name, a whole-stem compare would let round B's answers declare round A's superseded inside one day. Only a *later day's* adjudicator overrules an earlier day's. |
| Where the measure is read from | the `events` stream, joined `intake → groom_answer(decided) → launch` | the cards' `## History` (dates, no clock); the sessions ledger alone | History lines carry a date and no time, so the minutes the card asks for are not in them. Every leg of the join already has, or gains, a timestamped event. |
| Cards decided outside the groom | not counted, and the row says `n=` | guess a decision time from `stage_since` | `asf set decided true` writes no event. A number that quietly includes guessed times is worse than a number that says how many pairs it measured. |
| Getting the step onto a clock | `asf doctor` reports any `asf`-owned step no clock ticks; `sample/product.yaml` updated | edit the live product yaml from code; add a default clock | The operator's yaml is theirs. A doctor line is how every other "installed but cannot run" defect in this tree is surfaced (`check_scheduler`, `check_drift`). |

## 2. The design

### 2.1 `asf/tick/step_groom.py` — the step

```python
"""asf.tick.step_groom — the tick's ``groom`` step: intake, the policy pass, the questions.

Runs on every tick, between ``health`` (whose ``ended`` lines make the in-flight set true) and
``wave`` (which launches what this step just decided). Three parts, in order: the pending
answers files, then ``asf groom --apply`` against the record clone. One line:
``groom: <what cmd_groom printed>``.
"""

def run(ctx, out=print):
    from asf.groom import answers, policy
    from asf.groom.groom import cmd_groom
    product, root = ctx.product, ctx.record_root()
    n = answers.apply_pending_answers(product, root, event=ctx.event, out=out)
    epic = (product.conventions or {}).get('default_bug_epic')
    rc = cmd_groom(_ns(date=None, apply=True, rebuild=False, product=product.name,
                       default_bug_epic=epic, answers_file=None, event=ctx.event), root)
    if rc:
        raise StepFailed(f'groom exited {rc}')
    return 0
```

`steps.STEPS` becomes `['record', 'health', 'groom', 'wave', 'prs', 'harvest', 'batch',
'daily']` and `ASF_CALLABLES['groom'] = 'asf.tick.step_groom:run'`. Nothing else in
`asf/tick/steps.py` changes: an undeclared step with an `asf` implementation resolves to `asf`
(P1), so no product yaml is refused for not knowing the name.

`run_record_step` drops its `apply_pending_answers` call and the `do_index` that followed it
(`asf/tick/tick.py:118-120`): the same work now happens one step later, in the step that owns it,
and `cmd_groom` re-indexes at the end of its own run.

`sample/product.yaml`'s dispatch clock becomes `steps: [health, groom, wave, prs, harvest,
batch]`.

### 2.2 `asf/tick/step_daily.py` — what is left

`parts()` returns two:

```python
return [
    ('stale',  lambda: cmd_stale(_ns(json=False), root)),
    ('rollup', lambda: cmd_rollup(_ns(day=yesterday(), no_releases=False,
                                      product=product.name), root)),
]
```

`groom` moved to §2.1; `file-bugs` is deleted (the `record` step runs it every tick).
`_ANSWERS_FILE_RE`, `_newest_answers_file`, `pending_answers_files`, `_newest_applied`,
`carry_staged_answers` and `apply_pending_answers` move verbatim to **`asf/groom/answers.py`**,
with `_ANSWERS_FILE_RE` and `_newest_applied` changed as §2.7 requires. `step_daily` keeps
`yesterday`, `run_part`, `parts` and `run`; it imports nothing from `asf.groom` afterwards.

### 2.3 `cmd_groom` — one pass, three answer sources

```
1  load the record                               (unchanged)
2  apply, in order, all idempotent:
     a  groom/<previous date>.md   — an answer typed into yesterday's file
     b  groom/<date>.md            — today's file, as this day's earlier ticks left it   [new]
     c  args.answers_file          — when one is passed (the CLI path)
3  process_inbox — every card in the intake dir, no limit; one `intake` event each        [§2.6]
4  build the sections fresh from the record: question text only, every slot `____`
5  merge with today's file on disk                                                        [§2.4]
6  suppress → policy pass (the slots only)                                                (unchanged)
7  write groom/<date>.md
8  apply the file just written  — the controller's answers                                (unchanged)
9  write groom/<date>-digest.md, if its body changed; do_index; print; emit groom_open
```

Step 2b is the change that makes the day file a working ledger: an answer that appears in it at
any point in the day is applied by the next tick, whoever wrote it. `--apply` still gates 2a and
2b together; the tick always passes it.

### 2.4 The additive day file

A line in `groom/<date>.md` is in exactly one of four states, read off its answer slot:

| State | Shape | Kept across ticks? |
|---|---|---|
| answered | `- [ ] F-0099 … → answer: yes` / `controller: <policy> no` / `adjudicator: …` | **verbatim, forever within the day** — this is the ledger |
| open | `… → answer: ____` | its *question text* is kept; the slot is re-derived |
| barred | `… → answer: ____ (barred: approvals.new_epic)` | as open |
| spoken for | `- [x] … → answer: (spoken for: CARD → SPEC)` | as open |

```python
def merge_day_file(existing_text, sections):
    """`{section key: [lines]}` for today's file: every answered line of `existing_text` first,
    in its own order, then the question text `existing_text` already carries for a question
    `sections` still asks (slot reset to `____`), then `sections`' new questions, appended.
    A question `sections` no longer asks and nobody answered is dropped: nobody should be asked
    a question that no longer stands."""
```

The token a line is matched by is its item id (`F-0099`), its intake token (`inbox:foo.md`), or,
for a shape proposal, `shape.proposal_key(verb, ids, areas)` — the key `apply_proposal` already
uses to record a decline, so a re-proposed merge is recognised as the same question.

Ordering is therefore stable: a question keeps the position it was first written at for the
whole day, and new questions land at the end of their section. Two runs over an unchanged record
produce the same bytes, because every input to the merge is either the file itself or the record.

`asf groom --rebuild` skips the "keep the question text" half: answered lines are still kept
verbatim, every other line is re-rendered from the record. It is the one way a stale `why`, a
lifted bar or a renamed card is refreshed inside a day.

The digest is written through `metrics.write_if_changed`-style comparison on its body — the text
with the trailing `— generated by asf groom@<sha> <HH:MM>` line dropped. An unchanged day leaves
the file, stamp and all, exactly as it was.

### 2.5 Every undecided item, from its first groom

`GROOM_SECTIONS`' second entry becomes `('Undecided', 'undecided')`; `build_groom_sections`
calls `groom_undecided_section(canonical, now, 0, exclude=asked_elsewhere)` where

```python
asked_elsewhere = origin_ids | {id of every line already in sections['auto_bugs']}
```

`groom_undecided_section` keeps its `days` parameter (14 still uses it) and its `decision`/`rule`
type exclusion; with `days=0` the `age > threshold` test passes for every open item whose
`decided` is not `true`, from the first groom after it is created. `Undecided > 14 days`
(`undecided14`) and its `close_on_starvation` binding are untouched, and it keeps excluding
`origin_ids` exactly as today.

The reason text stays `undecided <age>`, so a card asked on its first groom reads `undecided 4m`
and the same line still reads `undecided 4m` at midnight (§1.4, the frozen `why`).

### 2.6 Intake: no limit, and a filing stamp

`process_inbox` is unchanged in its loop (P4) and gains one parameter, `event=None`, emitting per
minted card:

```python
event('intake', item=new_id, type=type_, rule=rule, filed=filed_at, waited_min=…)
```

`filed_at` is the card's `filed:` header when it has one, else the intake file's mtime as an
ISO-8601 UTC stamp. `cmd_inbox` writes the header:

```
# Groom every tick
filed: 2026-09-23T20:45:11Z
parent: E-0002
```

`INBOX_KV_RE` gains `filed` so the line is read as a header rather than the first line of the
description, and `derive` ignores it (it is not one of the shape's inputs). A card filed before
this lands has no header and falls back to its mtime.

The test the card asks for is the one nobody wrote: seven cards in the intake directory, one
`asf groom`, seven outcomes — every card either minted or carrying a `## Question`, none left
untouched.

### 2.7 An adjudicate round per question set

`asf/groom/policy.py` (stdlib only, so `hashlib` is fine):

```python
def question_signature(ids):
    """Eight hex over the sorted open-question ids — the identity of one round's question set."""
    return hashlib.sha1('\n'.join(sorted(ids)).encode()).hexdigest()[:8]

def adjudicate_rounds_per_day(product):
    """``groom.adjudicate_rounds_per_day`` (default 12): the day's ceiling on adjudicate rounds."""
```

`step_wave.groom_state` gains three keys and changes one:

```python
sig      = policy.question_signature(open_ids)
job      = f'groom-{date}-{sig}'
attempts = <ledger rows whose job == job>              # was: whose job == f'groom-{date}'
rounds   = <distinct groom-<date>-* jobs in the ledger>
answers  = <state dir>/groom/{date}-{sig}.answers
```

`feeder.rows.groom_row` then holds back when **any** of: a session whose job starts with
`groom-<date>` is in flight (one adjudicate session at a time, as today); `attempts >=
adjudicate_attempts(product)`; `rounds >= adjudicate_rounds_per_day(product)`. Its `groom_date`
attribute — the `KIND_JOB_KEY` that names the job (`asf/tick/step_wave.py:31`) — carries
`f'{date}-{sig}'`, so the job and the branch (`branch_for(product, 'groom', f'{date}-{sig}')`)
are the round's, not the day's.

`answers.py`:

```python
_ANSWERS_FILE_RE = re.compile(r'^(\d{4}-\d{2}-\d{2})(?:-[0-9a-f]{8})?\.answers$')
```

`_newest_applied` returns the newest *date* (group 1) of the `.answers.done` files, and
`apply_pending_answers` supersedes a pending file only when a **strictly later date** has been
applied. `carry_staged_answers` needs no change: it already derives the file stem from the job
name (`job.rsplit('groom-', 1)[-1]`), which is now `<date>-<sig>`.

`cmd_groom`'s answers-file branch reads the date from group 1 for the groom file it attributes
sections to, and the whole stem for `adjudicator_job=f'groom-{stem}'`.

`digest.render_digest`/`write_digest` take `queued: bool` in place of `(attempts, cap)`: true
when `groom_row` would still launch a round for this set, and the day's remaining open questions
are listed under **Spoken for**; false and they are `NEEDS OPERATOR` lines under **For you**.
`cmd_groom` computes it from the same three tests `groom_row` applies.

### 2.8 The measure

`metrics.intake_latency_rows(events, conv=None)` joins the `events` stream:

| Leg | From | To |
|---|---|---|
| `intake → decided` | the `intake` event's `filed` | the first `groom_answer` with `field == 'decided'`, `value == 'true'` for that item |
| `decided → first session` | that `groom_answer`'s `ts` | the first `launch` event for that item at or after it |

Two rows, appended to `scorecard_rows`' output:

```
| intake → decided        | median 11 min, p90 23 min | 14 of 17 cards measured (3 decided outside the groom) |
| decided → first session | median 9 min, p90 12 min  | 12 of 14 decided cards launched                       |
```

`render_daily` reads `read_stream(root, 'events', week)` (P9) and passes it through;
`scorecard_rows(ci, sessions, ticks, conv=None, events=())` keeps its positional signature, so
every existing caller and test is unaffected. With no events the two rows read `no pairs
measured` and divide by nothing.

### 2.9 `asf doctor` — a step on no clock

```python
def check_clock_steps(product):
    """Every ``asf``-owned step that no clock ticks: installed, implemented and never run.
    One NEEDS OPERATOR line naming the step and a clock to add it to."""
```

Run for each product beside `check_scheduler`, over `scheduler.clocks(product)` and
`steps.resolve(product)`; a step whose owner is `off` is deliberate and not reported. On the
operator's factory today it reports exactly one thing — `groom` — which is this card.

### 2.10 The footprint

| File | What changes |

## 4. Records

**Files, in the record clone.**

| Path | Before | After |
|---|---|---|
| `groom/<date>.md` | written once a day, wholesale | written every tick, additively; answered lines immutable within the day |
| `groom/<date>-digest.md` | rewritten every gated run, stamp and all | rewritten only when its body changed |
| `metrics/events/<day>.jsonl` | `groom_answer`, `groom_open`, `launch`, … | plus `intake`, one per minted card |
| `metrics/ticks/<day>.jsonl` | `steps: [record, health, wave, …]` | `steps:` carries `groom` with its own `ok` and `seconds` |
| `metrics/daily/<day>.md` | the waste table | plus the two latency rows |

**Files, in the state dir** (`~/.ASF/state/<product>/`).

```
groom/<date>-<sig>.answers        the round's answers, written by its adjudicate session
groom/<date>-<sig>.answers.done   applied
groom/<date>.answers[.done]       still read; written by no new code
daily.stamp                       unchanged — it now gates stale and rollup only
```

**The new event.** One line per card minted by intake:

```json
{"kind": "intake", "item": "F-0101", "type": "feature", "rule": "parent-feature",
 "filed": "2026-09-23T20:45:11Z", "waited_min": 7, "product": "asf",
 "ts": "2026-09-23T20:52:03Z"}
```

`ts` is the mint; `filed` is the `filed:` header `asf inbox` wrote, or the intake file's mtime for
a card filed before this lands. `waited_min` is the difference, so the row is readable without a
join.

**The intake card gains one header line**, `filed: <ISO-8601 UTC>`, written by `asf inbox` and
read by nothing but the event above. It never reaches a card's frontmatter.

**Not written.** No new field on any card. No new state file. No new stream: `events` stays out
of `metrics.STREAMS` (it is not appended through the validated path). `daily.stamp` keeps its
meaning; the groom no longer consults it.

**Config, new.** `groom.adjudicate_rounds_per_day` (default 12). `groom.adjudicate_attempts`
keeps its name and default and changes meaning from per day to per question set — recorded here
because a product that tuned it is tuning something different afterwards.
