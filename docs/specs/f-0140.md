# F-0140 — the torn tree is fixed; the two things the fix left behind are not

The card asks that the self-hosting product tick from an immutable snapshot: resolve the
checkout's HEAD at tick start, run from a cached worktree at `state/<product>/code/<sha>`, reuse
it while HEAD is unchanged, prune the older ones, render that command from the scheduler, and
have `doctor` show which sha the clock runs.

**All of that is on the trunk.** It landed in `cfa8a1932` — `fix(workers,scheduler): isolated
worker env and HOME; the clock ticks from a snapshot`, W6 of the 0.1.3 fix package — as
`asf/snapshot.py`, the `snap_repo` branch of `scheduler.render` and the doctor's `clock code`
row. The card is still `New` because that commit named it by **title-slug** in a `Fixes:`
trailer and never by id, so nothing matched the landing back to F-0140. The card's own two named
tests — *a tick started while the checkout moves still imports one consistent tree*, *the
snapshot is reused while HEAD is unchanged* — exist as
`tests/test_snapshot.py:68` and `:103`, and they **pass as written today**; §3.1 is the probe
that ran them against this checkout, and its outcome is why this spec re-mints none of it.

So this spec is the specification of record for the snapshot clock — §2.0 states the shipped
design, unchanged, so the contract is written down where the reviewer and the next reader can
find it — and its Stories are only the three things the fix left behind:

**The launcher is a copy that nothing refreshes.** The clock does not execute `asf/snapshot.py`;
it executes `launch.py`, a byte copy written into `<state>/<product>/code/` by
`scheduler.write_launcher`, whose *only* caller is `scheduler.install` (`asf/scheduler.py:455`).
No tick, no upgrade and no harvest ever rewrites it. A fix to the launcher therefore reaches the
package, ships, and is still not what the clock runs — for ever, until an operator happens to
re-run `asf clock install`. The one file whose whole purpose is to survive a moving checkout is
the one file that never moves with it.

**The pool only age-prunes.** `snapshot.prune` removes a snapshot when nothing has launched from
it for `KEEP_UNUSED_S` — 24 hours — and that is the only bound. There is no cap on how many
exist. On this product the trunk takes **~150 commits a day** (89–197 over the last ten days,
§P7), and a linked worktree of this repo is **~26 MB** of files. Every distinct HEAD a tick
observes mints one, and each is kept a full day past its last use, so the steady state is about
a day's worth of landings: on the order of **100–150 worktrees and 3–4 GB**, every one of them
also registered in the operator's own development checkout, where `git worktree list` has to
carry them.

**The doctor row names the sha and nothing else.** `check_clock_code` reports the sha the clock
last ticked from and the HEAD to come. Neither of the two failures above is visible in it: a
clock running a stale launcher and a code dir holding 140 worktrees both read as a healthy green
row.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | Keep the snapshot road; do not build the pinned-install road | `asf upgrade --to <sha>`, re-pinned by harvest after every landing (the card's *"Or"*) | It is the one that landed and is green. It also costs less per landing: a snapshot is one `git worktree add` against a shared object store, where the pinned road is a `pipx` build **per landing** — ~150 a day (P7) — and leaves a window between the landing and the re-pin in which the clock runs code the trunk no longer has. The pinned road stays the right answer for a product that is *not* the factory's own source, and `clockinstall` already describes both |
| C2 | The launcher refreshes **itself**, from the snapshot it just made | Having the tick call `scheduler.write_launcher`, or having `asf upgrade` do it | The launcher is the only participant that runs on every tick, already knows the snapshot's path, and is the thing being refreshed. A tick-step writer would have to import `asf.scheduler` — the moving tree — to repair the file whose entire job is to not depend on it. `upgrade` does not run on this product's clock at all |
| C3 | Refresh for the next tick; never re-exec in this one | `os.execve`ing the refreshed launcher immediately | O5. One clock period of lag against a self-restarting process that can loop on a launcher which refreshes to something that refreshes back |
| C4 | Bound the pool by **count** (`KEEP_MAX = 4`), with an hour of `IN_USE_S` grace | Raising `KEEP_MAX` to cover a day; or lowering `KEEP_UNUSED_S` from 24h to, say, 1h | Age alone cannot bound a pool whose input rate is 150/day (P7); a count can, and 4 is already more than the one snapshot a tick needs plus the ones its neighbours are mid-tick on. The grace is what keeps a *running* tick's tree under it — the marker is stamped at launch and never again, so without it a long tick is exactly the case a count cap would delete. An hour is far past any clock's period. Lowering the age bound alone would still leave the count unbounded inside the window |
| C5 | A doctor row that says it, even though the refresh self-heals | Leaving the row as it is, since I2 repairs the drift at the next tick | The case where the drift matters most is the case where the self-heal never fires — a clock that is not ticking. The row is also the only place the pool's size is ever stated to a human |

## The design

### 0. What already holds — no change, stated so the contract is written down

The scheduled job is not `python -m asf.cli tick` in the checkout. `render` (P3) emits:

```
<python> <state>/<product>/code/launch.py --repo <checkout> --code-dir <state>/<product>/code -- \
    -m asf.cli tick --product <product> [--shadow]
```

with the job's working directory set to the code dir and **no** `PYTHONPATH` in its environment.
`launch.py` is a byte copy of `asf/snapshot.py` (P4), importing nothing from `asf` (P2). At every
firing it resolves the checkout's `HEAD` to a commit sha — one atomic ref read, so it either sees
the tree before the rewrite or after it, never during — makes sure `<code>/<sha>` is a detached
worktree at that sha, records the sha in `<code>/current`, prunes, and `execve`s the interpreter
with `PYTHONPATH` set to the snapshot alone (P1). A snapshot that cannot be made refuses the tick
with exit 2 rather than falling back to the live checkout, which is the failure being prevented
(P5). The tick's *subject* is still the live checkout: `repo_dir` comes from config (P9).

This spec changes three things inside that pipeline and nothing else.

### 1. The launcher refreshes itself — `asf/snapshot.py`

```python
#: Snapshots kept beyond the current one, by last use (C4).
KEEP_MAX = 4

#: A snapshot launched from this recently is never removed — a tick may still be running from it.
IN_USE_S = 3600


def refresh_launcher(snapshot_dir, launcher):
    """Bring the installed launcher up to date with the snapshot's own ``asf/snapshot.py``.

    The clock runs a copy (``<code>/launch.py``) written once by ``asf clock install``; without
    this, a fix to this file would ship and never be what the clock executes. The copy is
    replaced for the *next* launch — this process goes on running the code it was started with.

    Never called when this file is running as the package module: the source is another sha's
    copy and the target is ``__file__``, which would be a developer's working file.
    """
    source = os.path.join(snapshot_dir, 'asf', 'snapshot.py')
    try:
        with open(source, encoding='utf-8') as f:
            new = f.read()
        with open(launcher, encoding='utf-8') as f:
            if f.read() == new:
                return False
        _write(launcher, new)
    except OSError:
        return False
    return True
```

and in `main`, between the `ensure` and the `execve`:

```python
    print(f'snapshot: {os.path.basename(snap)[:12]} ({snap})', flush=True)
    me = os.path.abspath(__file__)
    if os.path.basename(me) == LAUNCHER and refresh_launcher(snap, me):
        print(f'snapshot: launcher refreshed from {os.path.basename(snap)[:12]}', flush=True)
    os.chdir(snap)
    os.execve(...)
```

Three properties this shape has to keep, each with a test in §3.2:

- **The guard is on the basename, not on a flag.** `os.path.basename(__file__) == LAUNCHER`
  is true only of the installed copy. Under `python -m asf.snapshot`, `__file__` is the package's
  own `asf/snapshot.py` and the refresh is skipped — otherwise a test, or an operator debugging
  the launcher by hand, would have the working file rewritten with the snapshot's bytes (I6).
- **It never refuses the tick.** Every failure path returns `False`. A code dir that has gone
  read-only, a snapshot missing `asf/snapshot.py` (an older sha, before this file existed) and a
  racing writer all leave the old launcher in place and the tick running.
- **Two clocks refreshing at once is safe.** Both write identical bytes through `_write`'s
  per-pid temp and `os.replace`; the rename is atomic, so no launch ever reads a half file. The
  refresh deliberately sits outside `ensure`'s lock — it needs nothing the lock protects.

`scheduler.write_launcher` (P4) is unchanged and stays the install-time writer: the first copy
still has to come from somewhere, and a code dir with no `launch.py` has no tick to self-heal
from.

### 2. The pool is bounded by count — `asf/snapshot.py`

`prune` grows two keyword arguments and one clause:

```python
def prune(repo, code_dir, keep=(), now=None, keep_unused_s=KEEP_UNUSED_S,
          keep_max=KEEP_MAX, in_use_s=IN_USE_S):
    """Remove the snapshots that are neither current, in use, nor among the most recent.

    A snapshot survives when it is in ``keep`` (the sha this tick runs), when something launched
    from it within ``in_use_s`` (a tick may still be inside it — the marker is stamped at launch
    and not again), or when it is one of the ``keep_max`` most recently used. Everything else
    goes, however young: the trunk of a self-hosting product takes ~150 commits a day and each
    snapshot is a whole working tree, so age alone is not a bound (C4). ``keep_unused_s`` stays
    the second rule, so a pool under the cap still empties when the clock stops.
    """
```

The surviving set is computed once, from `(sha, last_use)` pairs — the marker's mtime, or the
directory's for an incomplete one — as

```
keep ∪ {sha : now - used < in_use_s} ∪ {the keep_max shas with the largest used}
```

and every snapshot outside it is removed, plus every snapshot inside it that is older than
`keep_unused_s`. Removal is the existing `_remove` (`git worktree remove --force`, then
`shutil.rmtree`) followed by one `git worktree prune` in the source repo, so the registrations in
the operator's checkout go with the directories.

The resulting bound, against P7's rates: at most `keep_max` plus whatever distinct HEADs the
clocks observed in the last hour — four clocks and the queue can start at most ~20 ticks in an
hour, so ~24 worktrees, ~600 MB worst case, against the ~150 and ~3.9 GB that age alone permits.
The common case is far smaller: the pool holds the current sha and the four before it.

### 3. The doctor says both — `asf/scheduler.py`, `asf/doctor.py`

```python
def launcher_stale(product_name):
    """``(stale, reason)`` — whether the installed ``launch.py`` differs from this package's
    ``asf/snapshot.py``. ``(False, '')`` when there is no launcher: the clock is not a snapshot
    clock, and there is nothing to be stale."""
```

`clock_code` (P8) adds two keys — `launcher_stale` and `snapshots`, the length of
`snapshot.snapshots(code_dir(product_name))` — and `check_clock_code` grows one clause and one
suffix:

```
clock code   OK      snapshot 4f2a91c0d3b8 (6m ago); checkout HEAD 9e27c70e5a11 (the next tick
                     takes it) · 5 snapshots
clock code   YELLOW  snapshot 4f2a91c0d3b8 (6m ago) · 5 snapshots — launcher is stale: the
                     installed launch.py differs from this package's asf/snapshot.py; the next
                     tick refreshes it, or `asf clock install --product sample`
```

The row stays informational (`required=False`, P8) and `ok` stays `True` in every branch: a stale
launcher is a lag, not a breakage, and the tick that reports it is the tick that fixes it (C5).
The count carries no unit — O2 keeps the filesystem walk out of `doctor`.

## Records

- **`~/.ASF/state/<product>/code/launch.py`** — already written by `asf clock install`; this
  card adds a second writer, the launcher itself, at the end of every tick's snapshot step. Same
  bytes, same atomic temp-and-replace. Host state, untracked, never in the record.
- **`~/.ASF/state/<product>/code/<sha>/` and `<sha>.ok`** — unchanged in shape. What changes is
  how many there are: bounded by `KEEP_MAX` plus the last hour's ticks instead of by 24 hours of
  landings. Their removal also removes the matching registration in the development checkout's
  `.git/worktrees`, through the `git worktree prune` that `_remove` already follows.
- **`~/.ASF/state/<product>/code/current`** — unchanged: the sha the clock last ran, which is
  what the doctor row reads.
- **Two new keys on `scheduler.clock_code`'s dict**, `launcher_stale` and `snapshots`, and a
  longer detail on the existing `clock code` doctor row. No new row.
- **Nothing in the record.** No `metrics/` event, no `index.json` field, no product-config key,
  no schema version. `KEEP_MAX` and `IN_USE_S` are module constants, not product settings: a
  product cannot tune how many worktrees of the factory's own source its clock keeps, and none
  has asked to.
- **One line in `CHANGELOG.md`** under the next version, naming the launcher refresh and the
  bounded pool.
