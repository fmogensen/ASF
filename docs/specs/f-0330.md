# F-0330 — the outcome was declared, parsed, and written nowhere

The factory has a grammar for a session's machine-readable outcome, a parser for it, and no
applier. `asf/workers/report.py:120-130` reads three typed fields off any REPORT:

```python
def ruling_fields(text):
    rep = parse(text)
    writes = _claim(rep.get('writes'))
    return {'blocked_on': _claim(_first_line(rep.get('blocked_on'))),
            'writes': writes.split() if writes else None,
            'superseded_by': _claim(_first_line(rep.get('superseded_by')))}
```

It has exactly two production callers, and both use it as a *negative gate*:
`asf/workers/health.py:89` (`… and ruling_fields(text)['blocked_on'] is None`) and
`asf/workers/lifecycle.py:1217-1220` (`… or fields['blocked_on'] or fields['superseded_by']:
return None`). Neither writes anything. No module anywhere writes `superseded_by:`, an `after:`
edge or a corrected `writes:` onto a card from a declared outcome — P1 below is the grep.

What *does* happen is `asf/tick/step_health.py:180-225`, `file_rulings`: the `ruling:` paragraph is
appended to the card's `## History` as prose and the run is marked `adjudicated`. The item keeps
its state, keeps its footprint, keeps its row — and the next tick launches the same session at the
same finding.

The card names four instances. They are four distinct holes, each one measured below against the
reporting product's own record:

* **T-0353** was ruled `superseded_by: T-0091` three times (2026-10-08 12:04, 14:08, 15:48). All
  three rulings sit on the card as History prose; its frontmatter carries **no** `superseded_by:`
  to this day. An operator ran `asf retire` at 19:53 — four hours and two wasted adjudicate
  sessions after the first ruling said the same thing (P2, P3).
* **T-0537** got a groom `reshape:` on 2026-10-07 which is still on the card. It was already
  `Active`, and the feeder's RESHAPE → PLAN row is built only for a Task at `state: New`
  (`asf/feeder/rows.py:1828`, `:1864-1873`), so the reshape is invisible to the feeder and the
  coder relaunched on the unchanged card until an operator amended it by hand on 2026-10-08
  19:08 (P4, P5).
* **T-0436** named the same two paths under `needs writes:` in three reports — its own operator
  ruling says so ("three reports named these files under needs writes:"). Its History carries no
  `footprint widened:` line at all over 14 sessions: `report_facts` reads a claim only off a run
  that ended `finished` **and** carries no pending correction, and all three of those runs ended
  in a failure class (P6, P7).
* **B-1557** had three correct sessions each report the same duplicate in prose. The brief's
  `superseded_by:` line is marked *adjudicate only*, so a fix or correct session has no typed field
  to declare it in — the one instance of the four that is a grammar hole rather than an applier
  hole (P8). This is the one instance no longer live: between the measurement and this writing an
  operator retired B-1557 by hand (`state: Closed`,
  `removed: "retired: Superseded by B-1553: …"`). That closes the instance and *confirms* the hole
  twice over — the hand retire is the labour the applier removes, and it left `superseded_by:`
  unset on B-1557 and `supersedes:` unset on B-1553, which is exactly the half-written pair D2
  exists to avoid. The grammar hole itself is unchanged and still measured at this head (P8).

One shape underneath all four: **a declared, machine-readable outcome is never written to the
card, so the row that produced it survives and is launched again.** This spec closes it with one
applier and three seams that make a declared outcome reachable.

## Decisions

### Preconditions — measured in this worktree at `3cf265460`, 2026-10-10

  ```

  So the applier loads a `canonicalize(load_items(root))[0]` record of its own for the cycle clause
  and the successor's `supersedes:`, and keeps using `items` for `closed_state` (§1, C2).
* **P15 — `pending_correction` does not filter a parked correction, and `footprint_hold` erases
  one.** The two halves of why §3 narrows its gate instead of dropping it:

  ```

  ```

  So a caller that drops the gate gets the parked run handed to it, and the hold it then writes
  replaces the park with a six-key dict carrying neither `parked` nor `reason` — the redaction
  security hold, the relaunch cap and the operator question all lift silently (§3, C1).
* **P16 — `write_card` hard-codes the writer label.** Measured at this head:

  ```

    write_card hard-codes writer='widen'? True

  So reusing it unchanged (D8) would file every applied ruling's I3 refusal under `widen`. The
  label is a free-form string that `stage.guarded` only prints
  (`asf/record/stage.py:216-228`; the tree already passes six different ones), so the fix is one
  keyword with `'widen'` as its default, not a registration (§1, C4).
* **P17 — a *parked* correction still speaks for its item.** `correction_rows` adds the id to the
  `ids` it returns as `spoken` at `asf/feeder/rows.py:1030`, **before** the `if c.get('parked'):`
  branch at `:1037`. Measured through the real function at this head:

  ```
  parked correction -> spoken ids: ['T-0001']
    rows: [('FIX → CORRECT', 'PARKED redaction', 'operator', False)]
  live correction   -> spoken ids: ['T-0001']
    rows: [('FIX → CORRECT', 'would launch', '', True)]
  ```

  So `held`, which is `spoken | …` (`:2613-2615`), holds the item in both cases, and §2's `held`
  guard suppresses the reshape pair for a parked correction as well as a live one. The parked row
  itself survives — that is the row the person it waits on reads (§2, S-92308).
* **P18 — one item's rulings arrive as several runs, in one pass.** `lifecycle.latest(path)` is
  `{job: rs[-1] for job, rs in runs(path).items()}` (`asf/workers/lifecycle.py:469-471`, stable at
  the trunk) — its own
  docstring reads "`{job: its latest run}`". One entry **per job**, so the three adjudicate sessions
  that each ruled T-0353 superseded are three entries one `apply()` sees together, and the three
  unread rulings in the record today are applied on one tick. That is why D1 carries all of
  `groom.py:358-371` and not the cycle clause alone: `:358-360` makes the second and third ruling of
  one decision write nothing, and `:362-365` refuses a second ruling that names a different
  successor — a pair the cycle clause cannot see, because two distinct successors close no ring.

### In

1. One new pass, `asf/tick/apply_rulings.py`, in the health step: a run's declared
   `superseded_by:`, `blocked_on:` and `writes:` are written onto the card through the record's own
   writer, each behind its own gate, each with one History line and one commit per card written —
   two for a supersession, which writes the successor's `supersedes:` half as well.
2. `branch_rows` gives an Active Task whose `reshape:` is pending the RESHAPE → PLAN row and holds
   its PLAN → CODE row — the pair `task_rows` already builds for a New one.
3. `report_facts` reads a run's `needs writes:` claim whatever class the run ended in and whether
   or not an unparked correction is already pending on it — carrying that correction's own text
   into the footprint hold that replaces it, so the round the run was owed is not lost. A *parked*
   correction is still skipped: a park waits for a person.
4. The brief's TAIL offers `superseded_by:` to a `fix-bug` or `correct` session, not only to
   `adjudicate`.

### Out

* **An ungated supersession.** A `superseded_by:` naming a card that is open, absent from the
  record, or the item itself is **not** applied: the pass says so in one line and the item keeps
  its row exactly as today. Retiring an item against a successor that has not landed would drop
  live work on one session's word (D1).
* **`blocked_on:` and `writes:` from a non-adjudicate run.** Those two are plan decisions. Only an
  `adjudicate` run may declare them; a coder's or correct run's copies are parsed and ignored, as
  today (D5).
* **Re-deciding anything the prose ruling says beyond its typed fields.** The `ruling:` paragraph
  keeps going to `## History` verbatim, by `file_rulings`, unchanged. No model reads it here and no
  text of it is parsed beyond the first sentence used as the `removed:` reason.
* **The reshape session's own behaviour.** This spec gives an Active Task's pending reshape a row;
  what the reshape session then does with it is the existing machinery (`asf/briefs`, the reshape
  brief, `rejudge.take_no_split`), untouched.
* **`trunkclose.KINDS`.** Adding `'fix-bug'`/`'correct'` to it was considered and rejected: its
  verifier requires the trunk sha be attributable to *this* item
  (`asf/workers/trunkclose.py:126-129`), and B-1557's evidence is a sha that names B-1553. The
  supersession applier is the mechanism that case needs (D6).
* **Any change to `report.py`'s parsers.** `ruling_fields`, `footprint_claim`, `no_split` and
  `needs_input` are read by nine production call sites between them; this spec adds callers and
  changes none of them.
* **A new card field, a new index key, a new event stream.** Every field written here already
  exists and is already read (P4, P9).

### Preconditions the work depends on

* `set_typed` writes any typed field under any writer name, through the parser and the record
  stage's guard (P9). The name is a free-form label, not a key into an allowlist: `stage.guarded`
  takes it as a string and only prints it (`asf/record/stage.py:216-228`). `set_typed`'s own
  callers already pass six different labels (`set` — its default, `retire`, `replan`, `widen`,
  `undeliver`, `trunk-check`), and `guarded` is handed a good many more besides by callers that do
  not go through `set_typed` at all (`ingest`, `plan-tasks`, `untick`, `audit-proofs`, `slice`,
  `plan-order`, `file-bugs`, `migrate-landing`, and `correct`'s own step name). So
  `'ruling'` needs no registration — but it does need `write_card` to stop hard-coding `'widen'`
  (P16, D8). If a writer allowlist is ever added to that path, `'ruling'` must be in it.
* `tools/check_record_writers.sh` constrains *who opens a card file*, not the writer label: its
  rule is that no module under `asf/record/` writes a card in place outside `asf/record/writer.py`.
  The applier writes through `set_typed` and `card_writer`, so the gate is green by construction.
* `lifecycle.closed_state(items, id)` is truthy for a `Resolved`, `Closed` or `removed:` card and
  falsy for an open one and for an id the index does not hold (P10).
* `conflicts.supersession_edges(canonical)` and `conflicts.cycles(edges)` are pure over the records
  they are handed (`asf/groom/conflicts.py:107-165`), so the applier's gate reads the graph the
  same way `asf check` and the groom do (P13). `supersession_edges` reads `rec['meta']`
  (`:114-115`), so what it is handed must be a `canonicalize(load_items(root))[0]` record and never
  the health step's flat `items` — the applier loads that record once per pass (P14, §1).
* `lifecycle.pending_correction` tests `corr.get('text')` only (`asf/workers/lifecycle.py:1115-1129`):
  it does **not** filter a `parked` correction, and `footprint_hold`'s fresh dict does not carry one
  — so the caller that narrows the gate must keep the `parked` clause itself (P15, §3; the shape is
  at `asf/workers/correct.py:67`).
* `conflicts.supersession_findings` reports a supersession written on one card only, with no
  exemption for a removed loser, so a complete write means both halves (P13).
* `removed:` on a card removes every row the feeder would build for it (P4).
* `replan.task_pending` answers an Active Task and goes quiet once the reshape is applied (P11).
* The health step runs `file_rulings` before `rejudge` and `widen_footprints`
  (`asf/tick/step_health.py:270-272`, the three calls in that order), so a pass inserted between
  the first and the second sees the prose already filed. It does **not** hand the two later passes
  a changed view for free: `run` loads `items` once (`:266`) and hands that same object to both, and
  nothing in the step re-reads `index.json` after `_reindex`. The inserted pass must therefore
  update `items` in place for every field it writes, as `asf/tick/rejudge.py:144-145` already does
  (§1).
* `widen_footprint.write_card` and `_reindex` already do card-write-plus-commit-plus-reindex
  against the record clone; this pass reuses them rather than opening a second way to write a card.
* `lifecycle.latest(path)` is `{job: its latest run}` — one entry **per job**
  (`asf/workers/lifecycle.py:469-471`, P18), so several rulings on one item reach one pass together,
  and the gate must be idempotent over the pair and refuse a rival successor, not only a ring (D1).
* `correction_rows` puts an item in the `spoken` set it returns whether or not the correction is
  parked (`asf/feeder/rows.py:1030` ahead of `:1037`, P17), so §2's `held` guard holds the reshape
  pair in both cases and the parked `waits_on='operator'` row is what remains.

## The design

### 1. `asf/tick/apply_rulings.py` — the applier

One module, one entry point, no subprocess of its own beyond the card commit
`widen_footprint.write_card` already makes.

```python
"""asf.tick.apply_rulings — a session's declared outcome, written onto the card.

``file_rulings`` files the ``ruling:`` paragraph as prose (B-0064). This pass applies the three
typed fields beside it (:func:`asf.workers.report.ruling_fields`), each behind its own gate:

* ``superseded_by: <id>`` — the item is retired against it: ``removed:`` (the words
  :func:`asf.record.retire.removal` builds, so an applied ruling and a hand ``asf retire`` read
  the same) and ``superseded_by: <id>``, in one write — and ``supersedes:`` on the successor's own
  card in a second, because a pair written on one card only is an ``asf check`` finding
  (:func:`asf.groom.conflicts.supersession_findings`) and clearing those by hand is the work this
  pass exists to remove. Gated: the id is a card the record holds, is not the item,
  :func:`asf.workers.lifecycle.closed_state` says it is done or removed — retiring against a
  successor that has not landed would drop live work on one session's word — the pair is not
  already applied, the item carries no rival ``superseded_by:``, and
  :func:`asf.groom.conflicts.cycles` says the new edge closes no ring: the same six clauses
  ``asf.groom.groom`` applies to this same write, and the last three matter here most on an item
  ruled superseded more than once, which is the shape this item was reported for.
* ``blocked_on: <id>`` — ``after:`` gains the id, so the row waits visibly instead of relaunching.
  Gated: the id is a card, is not the item, and does not already reach it through ``after:``.
* ``writes: <globs>`` — the Task's footprint is replaced. The record stage's I3 refuses a
  footprint that would intersect another Active Task's; the refusal is reported, the card is
  unchanged (:func:`asf.tick.widen_footprint.refused_by`).

``blocked_on:`` and ``writes:`` are an ``adjudicate`` run's alone. ``superseded_by:`` is also read
off a ``fix-bug`` or ``correct`` run: a duplicate is a finding, and the fix lane is what finds it
(a product's B-1557, three correct sessions reporting the same duplicate in prose).

A run is read once (``outcome_read``). Every write goes through
:func:`asf.tick.widen_footprint.write_card` — the parser, the stage's guard, one commit of that
card alone — and the index is re-derived once at the end, so this tick's wave plans off the
applied outcome. A supersession is therefore two commits, one per card, as a groom ``keep`` is.
"""
```

* `KINDS = {'superseded_by': ('adjudicate', 'fix-bug', 'correct'), 'blocked_on': ('adjudicate',),
  'writes': ('adjudicate',)}` — D5 in one table.
* `reason(text)` — the `removed:` why: the ruling's own first sentence, whitespace folded, cut to a
  length that keeps the card's frontmatter readable; when the run declared no `ruling:` (a correct
  session's duplicate), the report's `tests:`/`left out:` words are not used — the reason is
  `f'superseded by {sid}, reported by {job}'` plus the first sentence of the report body if there
  is one. A reason is never empty: `retire.removal` is given one either way.
* `supersede(ctx, items, canonical, run, sid, out)` — the gate (D1), which is six clauses in two
  groups. First the four that decide whether this edge may be written at all: the record holds both
  cards (`items is not None` and `sid in items`, **and** `item` and `sid` are both in `canonical` —
  the gate's own reads are of `canonical`, and the two shapes can disagree), `sid != item`,
  `lifecycle.closed_state(items, sid)` is truthy, and
  `conflicts.cycles(conflicts.supersession_edges(canonical) | {(item, sid)})` is empty. Then the two
  that `asf/groom/groom.py:358-365` carries beside its own cycle clause — *already applied* and *a
  rival successor* — which this applier needs for the same reason and hits more often. The whole
  gate, in the order it is read:

  ```python
  if items is None or sid not in items or item not in canonical or sid not in canonical:
      return out(f'ruling {job}: {item} → {sid} not applied — the record holds no such pair')
  if sid == item:
      return out(f'ruling {job}: {item} cannot supersede itself')
  if not lifecycle.closed_state(items, sid):
      return out(f'ruling {job}: {sid} is not done — {item} stands')
  succ_meta = canonical[sid]['meta']
  if (canonical[item]['meta'].get('superseded_by') == sid                  # groom.py:358-360
          and item in as_list(succ_meta.get('supersedes'))):
      return out(f'ruling {job}: {item} is already superseded by {sid} — nothing to apply')
  existing = canonical[item]['meta'].get('superseded_by')                  # groom.py:362-365
  if existing and existing != sid:
      return out(f'ruling {job}: {item} is already superseded by {existing}, not {sid} '
                 f'— a person decides which')
  ring = conflicts.cycles(conflicts.supersession_edges(canonical) | {(item, sid)})
  if ring:                                                                 # groom.py:368-371
      return out(f'ruling {job}: {item} → {sid} would close a supersession ring {ring[0]}')
  ```

  Then two `write_card` calls, the item's first:

  ```python
  removal = retire.removal(reason, [])
  err = write_card(root, item, {'removed': removal, 'superseded_by': sid},
                   stamp, f'ruling applied: superseded_by → {sid} ({job})', product,
                   writer='ruling')
  if err:
      return out(f'ruling {job}: {item} not retired — {err}')
  canonical[item]['meta'].update({'removed': removal, 'superseded_by': sid})   # mirrored the moment
  supersedes = sorted(set(as_list(succ_meta.get('supersedes'))) | {item})      # each half lands,
  err = write_card(root, sid, {'supersedes': supersedes},                      # not after both
                   stamp, f'ruling applied: supersedes → {item} ({job})', product,
                   writer='ruling')
  if err:
      return out(f'ruling {job}: {sid} does not list {item} — {err}')
  succ_meta['supersedes'] = supersedes                      # the pass's own record, both halves
  ```

  **Both of the carried-over clauses are reachable here, and neither is theoretical.** `apply()`
  reads `lifecycle.latest(path)` (below), which is `{job: its latest run}`
  (`asf/workers/lifecycle.py:469-471`) — one entry **per job**, and three adjudicate sessions on one
  item are three jobs. T-0353, this spec's flagship instance, was ruled superseded *three times*
  and all three went unread, so the first tick after this lands hands all three to one pass. Without
  the already-applied clause the second and third write the pair again: six commits and six History
  lines for one decision, where the `## Records` table promises one line per applied field and two
  commits per supersession — and the `removed:` reason the card keeps ends up being the last
  session's words rather than the ruling that decided it. Without the rival-successor clause, two
  rulings naming *different* closed successors leave the item `superseded_by:` the second while both
  successors list it in `supersedes:`, which is exactly the half-written pair D2 exists to prevent
  (`conflicts.supersession_findings` then names the first successor's dangling half) — produced by
  the applier itself, on a card it has already retired. The cycle clause does not catch that case:
  two different successors close no ring. Both clauses read `canonical`, which the mirror below
  keeps current inside the pass, so the second ruling of one pass sees the first's write.

  **`items` and `canonical` are two different record shapes, and the gate needs both.** `items` is
  the flat `{id: card}` the health step already holds — `health.record_items`
  (`asf/workers/health.py:99-111`) reads `index.json`, so a card there has no `meta` key — and it is
  what `lifecycle.closed_state` wants. `conflicts.supersession_edges`, though, reads `rec['meta']`
  (`asf/groom/conflicts.py:114-115`), so handing it `items` is a `KeyError: 'meta'`. `canonical` is
  therefore a `canonicalize(load_items(root))[0]` record, loaded **once per pass** by `apply()` and
  handed down: `widen_footprint._card` (`:353-356`) already has exactly that loader, and loading it
  per card would mean a third read on top of the two `write_card` already makes for a supersession.
  The successor's `supersedes:` is read off `canonical[sid]['meta']` for the same reason — it is a
  typed list field, which the flat index card does not necessarily carry in parsed form.

  **And because it is loaded once, each applied supersession is mirrored back into it before the
  next ruling is read** (D12) — the two mirror lines in the block above. Each is placed **directly
  after the write it mirrors**, not after both have succeeded: the item's half goes into `canonical`
  the moment its own `write_card` returns clean, ahead of the successor's write. Were both mirrors
  left to the end, the successor's error would `return` past them, and the item's half — already on
  its card — would stay invisible to the rest of the pass; a reciprocal ruling later in the same
  pass would then escape the cycle clause, which is the exact staleness D12 exists to close. The
  partially-applied state the spec already accepts below (the item retired, the successor's half
  owed to `asf check`) is unchanged by the ordering; what changes is that the pass's own record
  tells the truth about it. `canonical` is the pass's
  own picture of the record, and three of its readers are inside the pass: the successor's
  `supersedes:` list, D1's cycle clause, and D1's two carried-over clauses. Without the mirror, a pass that applies two rulings
  against one successor computes the second list off a `succ` that predates the first write, and
  `set_typed` **replaces** the field — so the first loser's id is dropped from `supersedes:` and
  `conflicts.supersession_findings` reports precisely the half-written pair this applier exists to
  stop producing (`T-0001 is superseded_by T-0002, which does not list T-0001 in supersedes:`). A
  cluster of duplicates retired against one survivor is the ordinary shape of this work — a
  product's T-0091/T-0353 and B-1553/B-1557 both are — and D5 now lets `fix-bug` and `correct`
  runs declare it, so several in one pass is the expected case, most of all on the first tick after
  this lands, when every unread ruling in the record is applied at once. The same staleness reaches
  D1's gate: `supersession_edges(canonical)` cannot see an edge an earlier ruling in the same pass
  already applied, so two reciprocal declarations would both pass the clause that exists to refuse
  the ring they close — which is why the item's half is mirrored too, not only the successor's.

  The mirror is the only existing writer's own shape: `groom._write_card`'s contract is "Write
  typed `fields` on a card, append one History line, **and mirror both into `rec`**"
  (`asf/groom/groom.py:171-180`), and its last line is `rec['meta'].update(fields)`. That mirror is
  what lets successive `keep`s in one groom pass accumulate, and this pass needs it for the same
  reason. `canonical` and `items` are kept current for two different readers and are never
  conflated: `canonical` for this pass's own gate and successor read, `items` for the step's later
  passes (below).

  The successor's half is what keeps `conflicts.supersession_findings` quiet (P13); it is the shape
  `asf/groom/groom.py:383-385` already writes, down to the `sorted(set(...) | {loser})`. The item's
  write comes first, so a failure on the successor's card leaves the item retired and `asf check`
  naming the half — the same state a hand `asf retire` leaves, never a live item with a dangling
  `supersedes:`. On a failed gate: one line naming which clause failed, the run marked, nothing
  written on either card.
* `block(ctx, items, run, bid, out)` — the gate, then `{'after': [*existing, bid]}` and
  `- <stamp> ruling applied: after: +<bid> (<job>)`.
* `refootprint(ctx, items, run, globs, out)` — `{'writes': globs}` and
  `- <stamp> ruling applied: writes: → <globs> (<job>)`; an I3 refusal is printed with the owner
  `refused_by` names and the card is left alone.
* `apply(ctx, items, out=print)` — loads `canonical` once (above); then over
  `lifecycle.latest(path)`: skip a run that is not ended, is of a kind no field admits, or carries
  `outcome_read`; read `report.ruling_fields` off its log; call the three appliers in the order
  `superseded_by` → `blocked_on` → `writes` and stop after a supersession (a retired item has no
  footprint left to correct); mark `outcome_read=1`; emit one `ctx.event('ruling applied', …)` per
  write. `_reindex` once if anything was written. Returns `{job: [fields applied]}`.

  **Every applied field is also written back into `items` in place**, the way
  `rejudge.take_no_split` does it (`asf/tick/rejudge.py:144-145`:
  `items[item_id] = dict(task, reshape=None, …)` immediately after the card write) — behind the
  same `items is not None and item in items` guard that line carries, for the same reason:

  ```python
  if items is not None and item in items:
      items[item] = dict(items[item], removed=removal, superseded_by=sid)   # supersede
      items[item] = dict(items[item], after=[*existing, bid])               # block
      items[item] = dict(items[item], writes=globs)                         # refootprint
  ```

  **`items` can be `None`, and every read of it in this module is guarded.** `health.record_items`
  returns None when there is no index to read (`asf/workers/health.py:102,109`) — which is exactly
  why `rejudge.py:144` reads `if items is not None and item_id in items:` and not the assignment
  alone. Unguarded, the gate's own `sid in items` raises `TypeError: argument of type 'NoneType'
  is not iterable` before any clause is reached; the `step_health` wrapper catches it, so the
  health step still stands, but the pass then prints that one line every tick and never applies a
  ruling at all — a silent version of the defect this item is about. So `apply()` treats a `None`
  `items` as "the record cannot be read this tick": one line, nothing applied, no run marked
  `outcome_read` (an unread ruling must still be there next tick).

  This is not bookkeeping — it is what keeps the two passes *after* this one in the same step from
  acting on a card that no longer says what they think. `step_health.run` loads `items` once
  (`asf/tick/step_health.py:266`) and hands that same object to `rejudge` (`:271`) and
  `widen_footprints` (`:272`), both of which run after the insertion. `_reindex` rewrites
  `index.json`, but nothing inside the step re-reads it. So without the write-back,
  `widen_footprint.report_facts` calls `_task(items, run['item'])` whose
  `lifecycle.closed_state(items, item_id)` (`widen_footprint.py:95-97`) still sees no `removed:`,
  reads the just-retired Task as open, and lands a `writes:` update plus a relaunch correction on a
  removed card — the exact thing the stop-after-a-supersession rule above stops the applier itself
  from doing. `revert_overlaps`, `serialize_overlaps` and `rejudge.take_no_split` read the same
  stale dict. The write-back is also why `canonical` is not reused for this: `canonical` is the
  applier's own read of the record, while `items` is the object the rest of the step shares.

The two `Row`s are `task_rows`' pair at `:1864-1873`, identical in kind, action, `waits_on` and
`brief_kind`, so the two states produce the same two rows and the reshape brief sees no new case.
The predicate is `task_pending` and not a bare `v.get('reshape')`, so a reshape already carried out
by hand (`asf set <tid> reshape_applied=current`) raises no row (P11) — which a bare truth test
would. The `continue` puts it ahead of the CONFLICT → REBASE row on purpose: rebasing a branch
whose Task is about to be re-cut is the work T-0537 spent sessions on.

The *guards*, though, are not the same, because the two functions keep them in different places.
`task_rows` carries its guards in the loop filter above the branch (`:1827-1830`:
`state == 'New'`, `not in busy`, `not blocked`, `not delivered`), while `branch_rows`' own filter
(`:1198-1200`) carries only `type`, `state == 'Active'` and `busy`. So the new branch states the
three that matter explicitly:

* `v['id'] not in held` is checked **in the branch** (D13), and it is what keeps the parity claim
  above true. `held` is not only about a dead branch: `_candidates` builds it as
  `held = (spoken | review | landing | lanes | landed…)` (`:2613-2615`), and `spoken` is the set of
  items a FIX → CORRECT row already speaks for. It is how `branch_rows` honours the invariant
  `_candidates` states a few lines further down — "a Task a correction row speaks for gets no
  PLAN → CODE row too: one session per branch" (`:2619`) — and the New-state counterpart gets
  that same protection by a different route, because `_candidates` passes
  `feature_rows(items, product, (busy - docs_waiting) | tasks_spoken, …)` (`:2629`) and `task_rows`
  filters `t['id'] not in busy` (`:1828`), so a New Task a correction speaks for never reaches its
  `if t.get('reshape'):` branch at all. Without the guard here the two states diverge exactly where
  §2 claims they agree: a New Task with a pending correction yields one launching row (FIX →
  CORRECT), while an Active one would yield two — a `correct` session on `worker/<tid>` and a
  `reshape` session on `plan/<tid>` in the same tick — and the `correct` session would spend its
  round on the very cut the reshape is replacing. That is T-0537's waste re-created in a new shape
  by the section that exists to end it.

  **A *parked* correction holds the item too, and that is the right answer rather than a gap.**
  `correction_rows` adds the item to the `ids` it returns as `spoken` at `asf/feeder/rows.py:1030`
  — **before** the `if c.get('parked'):` branch at `:1037` — so a parked correction puts the item in
  `spoken`, hence in `held`, hence past this guard, and the item's one row that tick is the parked
  `FIX → CORRECT … waits_on='operator'` row a person reads. The reshape pair returns on the tick
  after the park is lifted or cleared. Holding it is correct on its own terms: a park is a redaction
  hold, a relaunch cap or an open operator question on *that* branch, and re-cutting the plan under
  a person's open question is the kind of automatic move §3's own narrowed gate refuses one section
  down. It is also the only answer `branch_rows` can give: it is handed one flat `held` set and
  cannot tell a parked correction from a live one, so honouring the opposite would need a new
  parameter — subtracting the parked ids from `held` instead would also un-guard the `idle_branch`
  arm at `:1212-1213` and relaunch a coder onto a parked branch. S-92308 asserts the parked case
  this way round, and asserts the parked row is still there.
* `v['id'] not in landed` is the second parity clause, and it is `task_rows`' own: that function
  skips a Task the trunk already names *before* reaching its reshape branch
  (`if t['id'] in on_trunk: continue`, `:1835`), so the New state raises no reshape row for work
  that is already there. `branch_rows` has the same set in hand one line above its loop
  (`landed = landed_ids(items, landed_shas)`, `:1197`), and for an Active card it reduces to much
  the same thing — the record's Resolved/Closed are filtered out by the loop's own
  `state != 'Active'`, so what remains is the trunk's own names and a retired-done card. Without
  the clause an Active Task whose work reached the trunk under a sibling's commit, and whose
  ingest has not caught up, would draw a reshape session to re-cut a plan for surface that already
  exists — the gap B-0076 names, in the one arm that had no guard against it.
* `delivered(items, v, landed_shas)` is checked **in the branch**, because the `continue` would
  otherwise put it ahead of the `idle_branch` arm — the only place `branch_rows` checks `delivered`
  (`:1212-1213`, inside that arm's own `elif` condition), and the one its own docstring points at
  ("A Task a delivery speaks for (:func:`delivered`) is built there instead", `:1194-1195`).
  Without it, a Task a delivery speaks for would get a launching RESHAPE → PLAN row re-cutting a
  member of a delivery `delivery_rows` is building on the lead's branch, plus a PLAN → CODE
  `WAITS ON reshape` row for an item the delivery owns. No filter downstream is a *reliable*
  removal of either: `candidates` filters `branch_rows`' output by `stalled` and by `in_progress_by`
  (see the note on citations below), neither of which a delivery member carries, and `blocked_row`
  is applied per call site, never to `branch_rows`. The post-filters further down
  (`hold_parks`, `drop_gone`, `hold_unlanded`, `hold_replanning`, `hold_unreadable`, `hold_classes`,
  `hold_shelved`, `asf/feeder/rows.py:2639-2645`) do each catch a stray pair in the state they
  speak for — `hold_unlanded` is in fact why the parity claim above holds in a case §2 never
  claims, a reshape-marked Task with an unlanded `after:` yielding `WAITS ON <id>` and no reshape
  row in *both* states — but none of them keys on a delivery. `delivery_rows` is what speaks for a
  member, so the guard belongs in the branch.
* **The ordering against `_pr_closed` is deliberate too, and it is the second thing the `continue`
  pre-empts.** `branch_rows`' chain is `_pr_closed` → `_pr_conflicting` → `idle_branch`, and the
  new branch sits ahead of all three. For CONFLICT → REBASE the reason is above: rebasing a branch
  whose Task is about to be re-cut is wasted work. For `_pr_closed`'s STALE → CLOSE
  (`:1204-1207`) the same answer holds and for the same reason — **the reshape row wins, and the
  dead branch is reaped on a later tick.** A Task whose PR was closed unmerged *and* whose reshape
  is pending is a Task whose branch is going to be re-cut from the reshaped plan anyway; sending a
  `close` session at the old branch first spends a session tidying a branch the reshape is about to
  replace, and the CLOSE row returns the moment the reshape is applied and `task_pending` goes
  quiet (P11), because `_pr_closed` is a property of the card's `evidence:`, not a one-shot. The
  cost is bounded and named: one tick's delay in reaping one dead branch. S-92308 asserts this case
  the same way it asserts the CONFLICT one.
* `blocked` is **deliberately not** checked, matching `branch_rows`' every other arm: that function
  ignores `blocked:` throughout, and an arm that read it would be the only one. An Active Task
  marked `blocked:` and carrying a pending reshape is precisely the case the reshape session
  answers, so holding its row back would reinstate the loop this spec closes.

`held` and `landed` are also `idle_branch`'s own two guards (`:1212-1213`), and the new branch
re-reads them for a different question. There they answer "should a coder be relaunched on this
dead branch"; here they answer "does anything already speak for this item, and is its work already
on the trunk" — which is why they cannot be left to that arm: the `continue` never reaches it. They
are the Active-state spelling of the two filters that protect the New state one function away
(`_candidates`' `tasks_spoken` argument, `task_rows`' `on_trunk` skip), and that is what makes the
parity claim above a fact rather than an intention.

### 3. `asf/tick/widen_footprint.py` — a failed run's claim is still read

`report_facts` (`:134-171`) loses one gate, narrows a second and gains one carry. The gates first:

```python
-        if run.get('end_reason') != lifecycle.FINISHED or lifecycle.landed(run):
-            continue
-        if lifecycle.pending_correction(run, path):
-            continue
+        if not run.get('ended') or lifecycle.landed(run):
+            continue
+        corr = lifecycle.pending_correction(run, path)
+        if corr and corr.get('parked'):
+            continue   # a park waits for a person: never answered by a widening
```

The `pending_correction` gate is **narrowed, not dropped**: the lookup stays and one clause of it
stays with it. A *parked* correction is a hold whose whole point is that no session may answer it,
and `lifecycle.pending_correction` (`asf/workers/lifecycle.py:1115-1129`) does not filter `parked`
— it tests `corr.get('text')` and nothing else. The clause above is the shape
`asf/harvest/transplant.py:138`, `asf/workers/correct.py:67` and `asf/harvest/mechanical.py:472`
already use, and it costs this spec nothing: T-0436's three runs all ended in plain, unparked
failure classes, so §3's own case still lands.

Without it, a widening lifts the park. `footprint_hold` builds a *fresh* correction dict
(`lifecycle.py:3310-3317`) and `update_session` writes it whole (`asf/workers/pool.py:246-253`), so
`parked: True` and `reason:` are simply gone — and every reader of the park goes quiet with them:
`asf/feeder/rows.py:1037-1040` stops building the `waits_on='operator'` row, `asf/workers/correct.py:67`
and `asf/workers/unpark.py:43` stop skipping the run, `asf/views/status.py:569` stops listing it.
The sharpest instance is the redaction hold (`lifecycle.py:3337-3344`), parked on the first refusal
because *"a person decides, not another session"*: a coder run ended `failed: hook refused` on a
redaction finding, not landed, whose REPORT also claims `needs writes:` outside its footprint would
have that security hold replaced by a FOOTPRINT correction and be relaunched automatically. The
`RELAUNCH_CAP` park (`asf/workers/relaunch.py:338-340`) and the `BLOCKED` park of an open operator
question (`lifecycle.py:3019-3020`) are the same dict and would lift the same way.

`footprint_claim` itself already refuses to widen a `done`-and-pushed report (`report.py:209-212`,
T-0349), so dropping the `FINISHED` gate does not turn advisory output into a widening — the
status check that matters is inside the parser, not in this loop.

Narrowing the `pending_correction` gate means a run that already carries an *unparked* correction
can gain a `footprint` one. Two rules keep that single:

* `report_facts` runs before `refusal_facts` in `run()` (`:670-675`) and sets `footprint_read=1`
  on the session; `refusal_facts` then finds the correction `footprint_hold` wrote — kind
  `FOOTPRINT`, not `HOOK_REFUSED` — and skips it at `:278`. The report's claim wins over the
  refusal's parsed paths, which is the right order: the claim is what the session *said*, the
  refusal text is what a parser guessed from a hook's output.
* The previous failure's text is carried into the footprint correction **by `report_facts`
  itself** — a second change this section makes, not something `footprint_hold` does. Narrowing the
  `pending_correction` gate alone would lose it: `footprint_hold`
  (`asf/workers/lifecycle.py:3310-3319`) takes no `before` argument and builds a *fresh*
  `{'correction': {…}}` dict from its `text` alone, and `update_session` writes that dict whole
  (`asf/workers/pool.py:246-253`), so the pending correction's own text is overwritten. The
  `before` that `apply()` passes to `correction_text` at `:504` is `corr.get('text')` — by then
  `corr` *is* the footprint correction, so `before` is the footprint hold's own line, not the
  failure before it. `refusal_facts` is the landed precedent for carrying
  (`asf/tick/widen_footprint.py:290-293`): it prefixes the pending correction's text and reuses
  its `at`. `report_facts` takes the same shape — the lookup stays, only the `continue` goes:

  ```python
         # corr is the lookup the narrowed gate above already made — the park clause and this
         # carry are the two readers of it
         fields, line = lifecycle.footprint_hold(
             run, needs, f'report: {source}',
             (f'{corr["text"]}\n' if corr else '')
             + f'the session reports it needs {" ".join(needs)} outside writes: ({source})',
             (corr or {}).get('at') or pool_mod.now_iso())
  ```

  So a run that owed a red-gate round comes back relaunched on the wider footprint *carrying the
  gate it still owes*, instead of silently losing it. The previous correction's `tests` are **not**
  carried: `footprint_hold`'s `tests=()` is passed by one caller in the whole tree
  (`asf/harvest/lane.py:1424-1427`, the red-gate hold), and a report claim has no test list to put
  there.

  That has one named consequence, and it is accepted rather than fixed. The case §3 newly
  admits — a `finished` run already carrying a `red gate` correction — is precisely the one whose
  pending correction *does* carry `tests`, and `correction_text` renders them as a
  `failing tests: …` line (`asf/tick/widen_footprint.py:346-347`). So that line **goes** from the
  relaunch brief. Nothing is lost outright: the carried prose above still names the red gate in
  the words `lane.py` wrote, and the relaunched session re-runs the gate anyway. Carrying `tests`
  instead would mean the footprint correction claims a test list the *report's* claim never made,
  which `correction_text` would then print as this hold's own red. S-92309 asserts the line's
  absence and the prose's presence together, so a later reader sees the trade rather than
  inferring it.
