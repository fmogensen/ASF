# F-0173 — the last hole in the adjudicate loop is a sha that moved under a ruling nobody disputed

Three fixes closed B-1377's adjudicate loop on 2026-09-26 — `5103a343` (a ruling stands on the head
it was launched on, not only the sha it names), `bdd0fb76` (a check the CI queue cancelled to re-run
is pending, not red) and `46676430` (a note after `superseded_by:` is not a claim). What they left
is one narrow, reproducible hole, and it is the one the card names:

> It does not stand when the lane itself rebases the branch onto trunk **after** the ruling (same
> patches, new shas), so one extra adjudicate launches before the loop guard parks.

Every clause `lifecycle.overruling` offers today is an identity over a **sha**:

```
asf/workers/lifecycle.py:773-782   (HEAD d6a2206d5)

    m = PUSHED_SHA_RE.search(rep.get('pushed') or '')
    sha = m.group(0).lower() if m else ''
    if sha and head.lower().startswith(sha):
        return run.get('job')
    if not report_mod._claim(rep.get('commits')) and run.get('launch_head') \
            and run['launch_head'].lower() == head.lower():
        return run.get('job')  # launched on this head, committed nothing: the head it ruled on
    if sha and unchanged_since and unchanged_since(sha):
        return run.get('job')  # the head is that sha plus the review commit on top of it
    return None
```

A rebase changes every sha on the branch and changes no code. The ruled sha is no longer the head
(clause 1), the recorded `launch_head` is no longer the head (clause 2), and the ruled sha is no
longer an *ancestor* of the head, which is the first thing `only_reviews_since` checks (clause 3).
So `overruling` returns None, the lane takes T5 instead of T5a — `REVIEW → BACK, kind=review` — off
a review file whose findings a ruling already answered, and the feeder spends another adjudicate
session on it. The loop guard parks the item one session later, which means the defect is bounded
but not free: one session, every time the lane restacks a branch that is waiting on a ruling.

The shape of the answer is already in this repo, one line above the call site. The **review** that
raised the C list has exactly the same problem — its `Head:` sha also stops being the head when the
lane rewrites the branch — and B-0147 answered it with `asf.evidence.review.same_code`: *no file
outside the reviews directory differs, or the two carry the same own patch over the trunk*, that
second half being `git patch-id --stable` over the branch's own diff (`_own_patch`,
`asf/evidence/review.py:303-314`). `tests/test_review_reader.py:242` pins a restack onto a newer
trunk keeping a review current.

So F-0173 is a one-measure change, not a new mechanism: **the ruling is measured with the same ruler
its review is measured with.** A review that survives the lane's rewrites, and a ruling that answered
it, survive or fall together.

## Decisions

### In

- `lifecycle.overruling` stops asking *is this sha the head* only, and asks *does the head carry the
  code this ruling ruled on* — through a caller-supplied predicate, so `lifecycle` stays free of git.
- Both shas a ruling offers go through that predicate: the `pushed:` sha it claims, **and** the
  `launch_head` spawn recorded, the latter still only for a run that committed nothing.
- `asf/harvest/lane.py` supplies `asf.evidence.review.same_code` over `origin/<branch>` against
  `origin/<trunk>` — byte for byte the measure the line above already uses for `is_current`.
- The T5a doc line in `lane.py`'s transition table is corrected: *on this very head* → *on the code
  this head carries*.

### Out

- **`review_answered` (B-0149, `lifecycle.py:2306-2329`) is not touched**, though its
  `(r.get('launch_head') or '').lower() == head.lower()` has the identical flaw. It routes to a
  *fresh review round*, not to a new adjudicate session, so it costs no session when it misses; and
  widening a rule that suppresses a review round is a different risk from widening one that
  suppresses a duplicate ruling. It is a card of its own if it is ever measured.
- **A ruling never learns to answer a review written after it.** `overruling` compares no
  timestamps today, so a round-2 review of unchanged code can already be overruled by a round-1
  ruling through the `unchanged_since` clause. This spec neither closes nor widens that: see D6.
- **No new field, no new stream, no new module.** Nothing is written to the ledger, nothing to
  `metrics`, no file is added to `asf/`. See *Records*.
- **`_own_patch` / `same_code` are not modified.** They ship, they are tested, and this card's only
  claim on them is a second caller.
- **The reachability of `overruling` at all** — F-0157's subject, an adjudicate run that correctly
  commits nothing being judged `failed: empty branch` and so never `finished` — is out of scope and
  untouched here. See P6 and D7.

## The design

### 1. `asf/workers/lifecycle.py` — `overruling` asks about code, not shas

The signature loses `unchanged_since` and gains `same_code`, and the three sha identities become one
loop over the candidates a ruling offers.

```python
def overruling(path, item, head, same_code=None):
```

The docstring's last paragraph is rewritten to say what is now true (keeping its first two
paragraphs — the B-1377 story and the `pushed:`-sha-is-a-claim story — as they stand):

> The `pushed:` sha is the session's own claim, and it names the commit *it* thinks of as the tip —
> B-1377's rulings named the code commit under the review commit that is the head, and misspelled
> it past its ninth digit (`99bcb623ee0a…` for `99bcb623e36e…`), four more sessions. So a ruling
> offers two shas: the one it claims, and — for a run that committed nothing — spawn's recorded
> `launch_head`, the fact behind the claim. Either stands on `head` when it *is* `head`, or when
> `same_code(sha)` (the lane's :func:`asf.evidence.review.same_code`) says `head` carries the code
> that sha carried: the same tree outside the reviews directory, or the same own patch over the
> trunk. The lane rewrites a branch without changing what was ruled on — a review commit on top, a
> reword, a sign-off, a restack onto a moved trunk — and the ruling is measured with the same ruler
> B-0147 measures its review with, so the two stand or fall together.

The body's tail (`:773-782`) becomes:

```python
    m = PUSHED_SHA_RE.search(rep.get('pushed') or '')
    ruled = [m.group(0).lower()] if m else []
    if not report_mod._claim(rep.get('commits')) and run.get('launch_head'):
        ruled.append(run['launch_head'].lower())  # the fact behind the claim, for a run that
        # committed nothing: one that committed has moved the head past what it ruled on
    for sha in ruled:
        if head.lower().startswith(sha) or (same_code and same_code(sha)):
            return run.get('job')
    return None
```

Everything above `:773` — the newest-finished-adjudicate selection, `status: done`, a `ruling:`
paragraph, no `blocked_on` / `superseded_by`, and the `finished(r)` (or, post-F-0157,
`delivered(r)`) guard at `:760` — is unchanged.

Two notes for the reader of the diff:

- Every arm returns the same `run.get('job')`, so the order of the candidates and of the two tests
  inside the loop is a cost question only, never an outcome question. The cheap string test is
  first, so an unchanged head still answers without shelling out to git.
- The `head.lower().startswith(sha)` prefix test is kept as-is for the `pushed:` sha, which may be
  abbreviated to 7 characters (`PUSHED_SHA_RE`). For a 40-character `launch_head` it is equality.

### 2. `asf/harvest/lane.py` — the lane hands over the measure it already uses

At `:1376-1378`:

```python
                # the review's C list an adjudicate ruling already answered on this code
                f['overruled'] = lifecycle.overruling(
                    self.path, item, head,
                    lambda sha: review_mod.same_code(repo, conv, sha, f'origin/{b}',
                                                     trunk=f'origin/{trunk}'))
```

That is the call on the line above it (`is_current`, `:1368-1369`) with the same `repo`, `conv`,
`ref` and `trunk`. `review_mod.only_reviews_since` loses its only caller; it stays in
`asf/evidence/review.py` — it is a correct, tested function, and removing it is a separate tidy this
card does not take.

The T5a row of the transition table at `:37-40` is corrected in place:

```
- T5a REVIEW → GATE            ... unless an adjudicate ruling already answered it on the code
                               this head carries (:func:`asf.workers.lifecycle.overruling`): it
                               overruled the C list and pushed nothing — no second hold, no
                               second ruling
```

### 3. What it looks like when it is there

The lane rebases a branch that is waiting on a ruling, force-pushes it as the factory, and on the
next pass the review is still current (B-0147) and the ruling still stands (this card). The branch
goes `REVIEW → GATE` with `reviews/1-t-0001.md overruled by adjudicate-t-0001's ruling`, the hold
stays settled, and the feeder is never asked for a second adjudicate. When the head carries a real
new commit instead, the review is not current, the lane asks for round 2, and nothing about this
change is consulted.

## Acceptance tests

Three blocks, all runnable from the repo root at this head. No fixture outside `tests/` and no
network.

### A. The lane's own rebase keeps the ruling — the card's named test

New method on `LaneRepo` (`tests/test_lane.py`), standing on `_adjudicated` (P7). The pass before
the rebase is a plain `git fetch` into the product checkout — what `lane_pass` itself does at the
start of every pass (P9) — and the test **asserts** the ruled head is still readable there
afterwards, so D5's precondition is proved rather than assumed.

```
python3 -m unittest -v tests.test_lane.LaneRepo.test_a_ruling_stands_when_the_lane_rebases_the_branch_under_it
```

It must:

1. `path, head = self._adjudicated(None)` — a done ruling naming the head, `commits: none`.
2. `sh(['git', 'fetch', '-q', 'origin'], cwd=self.repo)` — the lane saw this head while it was the
   tip.
3. `self.push_main({'t.txt': 't\n'}, 'chore: the trunk moves')`, then in `self.worker`: fetch,
   `checkout -B worker/T-0001 origin/worker/T-0001`, `rebase -q origin/main`, `push -f`.
4. Assert the new `origin/worker/T-0001` sha differs from `head`, and that
   `git cat-file -e <head>^{commit}` still succeeds in `self.repo`.
5. `lane.lane_pass(self.product(lane={'review': {'code': 'required'}}), self.state_dir, ...)`.
6. Assert the lane record is `lane.GATE`, its `reason` contains `overruled` and
   `adjudicate-t-0001`; `lifecycle.pending_correction(lifecycle.latest(path)['adjudicate-t-0001'],
   path)` is None; and `lifecycle.corrections(path)['T-0001']['settled']` is True — no second
   adjudicate is asked for.

### B. A rebase that also carries new work never keeps the ruling

Same class, the bound on A. The head is rebased **and** a commit that changes `a.txt` is pushed on
top: the review is no longer current, the T5a arm is never reached, and the lane asks for round 2 —
`(lane.REVIEW, 2)`, with no correction for `T-0001` on the ledger, exactly as
`test_a_correct_session_that_pushes_new_commits_asks_for_a_new_review_round` requires without a
rebase.

```
python3 -m unittest -v tests.test_lane.LaneRepo.test_a_rebase_that_carries_new_code_never_keeps_the_ruling tests.test_lane.LaneRepo.test_a_correct_session_that_pushes_new_commits_asks_for_a_new_review_round
```

### C. Both of a ruling's shas go through the predicate — the unit

A new `unittest.TestCase` class in `tests/test_lifecycle.py` (its own ledger writer; it subclasses
no existing test class, so no host suite is re-run under it). With a stub predicate and no git it
pins, in one place, the whole contract of the new parameter:

- a ruling whose `pushed:` sha is one the predicate accepts → the job;
- a ruling whose `pushed:` sha is unreadable garbage but whose `launch_head` the predicate accepts,
  `commits: none` → the job (the case B-1377's last rulings were in, after a rebase);
- the same ruling with `commits: abc1234 fix: C1` → None (D4);
- a predicate that accepts nothing → None, and it is **not** called at all when the head already
  equals the claimed sha (the cheap test first);
- `same_code=None` → the pre-card behaviour: sha identity only.

```
python3 -m unittest -v tests.test_lifecycle.RulingAcrossARebaseTests
```

### D. Nothing that stood before falls

```
python3 -m unittest -v tests.test_lane.LaneRepo tests.test_lifecycle tests.test_review_reader
```

`tests.test_lane.LaneRepo` is 15 tests and ~34s at `d6a2206d5` (measured in this worktree), four of
them the ruling tests `5103a343` added; all four must stay green with no edit.

## Records

Nothing new is written down. That is the point of the card, and it is worth stating explicitly
because a reviewer will look for the row:

- **No ledger field.** `sessions.jsonl` gains nothing. The change reads `launch_head`, which
  `spawn` already writes on every launch line, and the ruling's REPORT text, which is already
  stored as the run's result.
- **No metrics stream and no scorecard cause key.** No `diagnose.metric` key is renamed or added,
  so the card that filed this defect verifies itself on the key it was filed under.
- **No record page, no new card, no approval class.**
- **The one thing that changes what is written** is the lane record on the run line: on a rebased
  branch whose ruling stands, `lane.state` is `GATE` with
  `reason: <review path> overruled by <job>'s ruling` where today it is `BACK` with
  `reason: kind=review` followed by a new `correction` entry and an adjudicate launch. Same two
  strings the T5a arm already writes (`asf/harvest/lane.py:1150-1151`) — this card only changes how
  often the lane reaches them.
- **The docstrings are the record of the rule**: `overruling`'s last paragraph and the T5a row of
  the transition table, both rewritten above, are where the next reader learns that a ruling is
  measured by code and not by sha.

## Stories

- S: A ruling is measured by the code it ruled on, not by the sha that carried it — `overruling` takes one `same_code` predicate in place of `unchanged_since` and runs it over both shas a ruling offers (the `pushed:` claim, and the `launch_head` fact for a run that committed nothing), and the lane hands it `asf.evidence.review.same_code` over `origin/<branch>` against `origin/<trunk>` — the same measure the line above already uses for the review — so the lane's own rebase onto a moved trunk keeps the ruling, a head carrying new code does not, and no second adjudicate is launched either way — acceptance: `python3 -m unittest -v tests.test_lane.LaneRepo tests.test_lifecycle.RulingAcrossARebaseTests tests.test_review_reader`
