# F-0083 — Scheduler clocks are configuration: each job group on its own interval, per product

Epic: E-0001 — ASF 0.1 — a working factory. Branch: `spec/F-0083`.

Today the clock of a factory job comes from the command line: `asf scheduler install --steps
record --interval 600` (`asf/scheduler.py:444-448`), with `scheduler.interval_s` in
`config.yaml` as the one fallback for every job and every product (`asf/scheduler.py:79-85`), a
hard-coded `DAILY_CALENDAR = {'Hour': 6, 'Minute': 50}` for the daily (`asf/scheduler.py:42`),
and the grouping itself (`record` / `health,wave,prs,batch` / `daily`) typed out in
`tools/cutover.sh:166,450-456`. After this change a product's yaml says which jobs exist, what
each one ticks and how often. `asf scheduler install` takes no clock from its arguments.

## Decisions

### In

- A `clocks:` block in `products/<name>.yaml`: one entry per job, each with a name, the steps
  it ticks (or `shadow: true`) and exactly one of `every: <duration>` or `at: "HH:MM"`.
- `asf scheduler render|install|status` read the clocks from the product file. Each clock
  becomes one job, labelled `<label_prefix>.<product>.<clock>`, logging to
  `<ASF_HOME>/logs/tick-<product>-<clock>.log`.
- Whole-file `install` (no `--clock`) makes the loaded jobs match the file: it installs every
  declared clock and retires (boots out, removes the plist of) every loaded job whose label
  starts with `<label_prefix>.<product>.` but is not a declared clock.
- A shadow clock: `asf tick --product <p> --shadow` on its own interval.
- Validation at render/install time: unknown step, step with no owner, both or neither of
  `every`/`at`, a malformed duration or time, `shadow` together with `steps`. Each is a
  one-line refusal with exit 2. No job is written.
- The callers that read the old clock move with it: `asf doctor`'s never-ran check and
  `tools/cutover.sh`'s job install.
- `docs/products.example.yaml` and `sample/product.yaml` carry a `clocks:` block. The
  config example does not mention `scheduler.interval_s`.

### Out

- Weekly, monthly or weekday-only schedules. A clock is an interval or one wall-clock time a
  day. Anything else is a later card.
- Time zones. `at:` is the machine's local time, which is what launchd's
  `StartCalendarInterval` and cron already use.
- The adapters for `systemd` / `gh-actions` / `claude-routines`. They still render the
  `NEEDS OPERATOR` marker, now naming the clock's `every`/`at`.
- Changing what a tick does. `asf tick --steps` / `--daily` / `--shadow` are unchanged, and
  so is the rule that a `[daily]`-only job renders `--daily` (`asf/scheduler.py:125`).
- Writing any event into the product's record. Installing a job is an operator action on
  this machine, not a factory state change (see Records).
- Installing anything automatically. The clocks only take effect when an operator (or
  `tools/cutover.sh`) runs `asf scheduler install`.

### Preconditions

- The product-file loader (`asf.env.loads`) already parses the block below: nested maps,
  inline `[a, b]` lists, `true`, and `"06:50"` / `06:50`, both as the string `06:50`. Checked
  against `origin/main` at `cb0cbb7`.
- `asf.tick.stale.limit_seconds` already parses `<n><s|m|h|d>` (the `stage_limits`
  format). Clocks reuse it, so one duration syntax covers the whole product file.
- `asf.tick.steps.STEPS`, `resolve` and `check_owned` already say which steps exist and
  who owns each one. Clocks validate against them rather than keeping a second list.
- `env.PRODUCT_FIELDS` rejects unknown top-level keys (`asf/env.py:222-227`), so `clocks`
  must be added there, or every product that uses it fails to load.

### Choices

| # | Choice | Chosen | Against | Why |
|---|---|---|---|---|
| D1 | Where clocks live | top-level `clocks:` in `products/<name>.yaml` | `scheduler.clocks` in `config.yaml` keyed by product; extending the existing `steps:` map | The card says per product, in the product's yaml. `steps:` answers *who owns a step*, not *when it runs*, and one step can sit in two clocks. `config.yaml` keeps the machine facts (`kind`, `label_prefix`, `legacy_labels`). |
| D2 | Shape of an entry | `name: {steps: [..], every: 5m}` / `{steps: [daily], at: "06:50"}` / `{shadow: true, every: 30m}` | a list of entries; cron strings | Named entries give each job a stable label and log name. A duration uses the file's existing syntax. A cron string can't be rendered for launchd without a parser, and it hides the interval from `doctor`. |
| D3 | Job label | `<prefix>.<product>.<clock-name>` | `<prefix>.<product>.<steps-slug>` (today) | Two clocks can tick the same steps (for example a fast and a slow `prs`). Adding a step to a clock shouldn't rename its job and its log. The name is what the operator wrote. |
| D4 | A job that is no longer declared | whole-file `install` retires loaded `<prefix>.<product>.*` jobs that are not declared clocks | leave them loaded; warn only | "A clock is a line in a file" only holds if deleting the line stops the job. Otherwise D3's rename (`…health-wave-prs-batch` → `…dispatch`) leaves two jobs running the same steps. `--clock <name>` never retires anything, and `legacy_labels` jobs (a different prefix) are never touched. |
| D5 | Product with no `clocks:` | refuse: `NEEDS OPERATOR: products/<p>.yaml declares no clocks — add a clocks: block (see docs/products.example.yaml)`, exit 2 | a built-in default set (today's 600 s / 06:50) | A built-in default is the hidden clock this card removes. Jobs already loaded keep running, because refusing to *install* doesn't touch them. This matches the step manifest's "declared nowhere is a refusal, not a silent skip" (`asf/tick/steps.py:12`). |
| D6 | `--steps` / `--interval` on `asf scheduler` | removed; `--clock <name>` picks one clock | keep them as overrides | An override on the command line is the thing the card retires. `status --label` stays for reading a job that isn't a clock (a legacy one). |
| D7 | Validation depth at install | unknown step and ownerless step both refused at install | leave ownership to the tick (exit 2 at run time) | A job whose every run exits 2 is the "installed but cannot run" failure `asf/scheduler.py:3-8` exists to prevent. `check_owned` is cheap and already written. |
| D8 | Whole-file install when one clock is bad | atomic: validate every clock first, write none if any is refused | install the good ones | A half-applied file leaves the loaded jobs matching neither the old file nor the new one. The refusal names every bad clock at once. |
| D9 | Minimum and granularity of `every` | at least 60 s. launchd takes any whole second. cron takes whole minutes under 60, or whole hours that divide 24; any other value renders the `NEEDS OPERATOR` marker for that clock. | clamp to cron's grid silently | Today `max(1, interval // 60)` quietly turns 90 s into 1 m and 2 h into `*/120`, which is not a valid cron field. A clock the scheduler can't express is refused, not approximated. |
| D10 | `scheduler.interval_s` in `config.yaml` | no longer read; `asf doctor` prints one YELLOW line when it is present | still read it as a default | One number for everything is what the card replaces. The yellow line tells an operator who still has the key why editing it changes nothing. |
| D11 | Doctor's never-ran threshold | the plist's `StartInterval`; for a calendar job, 86400 s | `scheduler.interval_s` (today) | Today a daily job falls back to the global 600 s. It has to come from the job itself. |
| D12 | Cutover | iterate the declared clocks (`render --json`), install each with `--clock`, and skip a clock whose steps the manifest doesn't own (the legacy job stays loaded, as today). Gate 3 reads the first clock whose steps include `record`. | keep the hard-coded three groups | Otherwise cutover installs the old labels, and the next whole-file install retires them (D4). |

## The design

### The product file

```yaml
# products/<name>.yaml
clocks:
  record:
    steps: [record]
    every: 5m
  dispatch:
    steps: [health, wave, prs, harvest, batch]
    every: 10m
  daily:
    steps: [daily]
    at: "06:50"
  shadow:
    shadow: true
    every: 30m
```

Rules, checked by `scheduler.clocks(product)`:

- Clock name: `[a-z0-9][a-z0-9-]*` (it goes into a label and a file name).
- `steps`: a non-empty list of names from `asf.tick.steps.STEPS`, each with an owner
  (`steps.resolve` + `steps.check_owned`). Order doesn't matter: the tick runs them in
  manifest order (`parse_steps`).
- `shadow: true`: runs `asf tick --shadow` (record against the shadow clone, never pushed).
  It excludes `steps`.
- Exactly one of `every` (duration `<n><s|m|h|d>`, at least 60 s) or `at` (`HH:MM`, 24 h,
  local time).
- Anything else in an entry is refused by name, so a typo (`evrey:`) doesn't fall through to a
  default.

### `asf/env.py`

- `PRODUCT_FIELDS['clocks'] = _MAP`. The deep checks stay in the scheduler, which knows the
  steps.

### `asf/scheduler.py`

- Removed: `DEFAULT_INTERVAL_S`, `DAILY_CALENDAR`, `interval_s()`, and the `--steps` /
  `--interval` arguments.
- New `Clock` (a small namedtuple): `name, steps, shadow, interval_s, calendar`.
- New `clocks(product) -> [Clock]`, in file order. It raises `SchedulerError` whose message
  lists every refused clock, one `clock <name>: <why>` clause each.
  - No `clocks:` → `SchedulerError(NEEDS OPERATOR line from D5)`.
- `tick_argv(product_name, clock)`: `--shadow` for a shadow clock, `--daily` for a
  `[daily]`-only clock, otherwise `--steps a,b,c`.
- `label_for(product_name, clock_name, cfg)` → `<prefix>.<product>.<clock_name>`.
  `log_path(product_name, clock_name)` → `logs/tick-<product>-<clock_name>.log`.
- `render(product, clock, cfg=None)`: the job dict as today (`kind, label, path, plist|line,
  log, argv, product`), plus `clock` (the name), `steps` and `every_s` or `at`.
  - launchd: `StartInterval = clock.interval_s` or
    `StartCalendarInterval = {'Hour': h, 'Minute': m}`.
  - cron: `*/m * * * *` (m < 60), `0 */h * * *` (h divides 24), `m h * * *` (at). Anything
    else sets `needs_operator` (D9).
- `retire_candidates(product_name, declared_labels, cfg)`: the labels from `loaded_jobs(cfg=cfg)`
  that start with `<prefix>.<product>.` and aren't in `declared_labels`.
- CLI:
  ```
  asf scheduler render  [--product P] [--clock NAME] [--json]
  asf scheduler install [--product P] [--clock NAME]
  asf scheduler status  [--product P] [--clock NAME | --label L] [--json]
  asf scheduler list    [--json]
  ```
  - `render` with no `--clock` covers every clock. `--json` gives a list of job dicts. Plain
    output gives one `# <label>` header line per clock, then its plist, cron line or marker.
  - `install` with no `--clock` validates everything (D8), installs each clock (the existing
    `install(job)`), then `uninstall(label)` for each `retire_candidates` label and prints
    `scheduler: retired <label> (not a clock in products/<p>.yaml)`. With `--clock`, it
    installs that clock only and retires nothing.
  - `status` with no `--clock` / `--label` prints one line per declared clock. It exits 1 if
    any clock isn't loaded.
  - An unknown `--clock` → `scheduler: no clock <name> in products/<p>.yaml (clocks: a, b)`,
    exit 2.
  - Any `SchedulerError` → its line(s) on stdout, exit 2, nothing written.
  - Exit codes otherwise as today: 0, or 3 for the non-launchd kinds' install.

### `asf/doctor.py`

- `scheduler_rows`: `interval = data.get('StartInterval') or (86400 if
  data.get('StartCalendarInterval') else None)`. With no interval, no never-ran check (D11).
- New YELLOW row `config  scheduler.interval_s is set but no longer read — clocks live in
  products/<p>.yaml` when the key is present (D10).
- Every declared clock whose label isn't loaded → RED row `<label>  declared in
  products/<p>.yaml but not loaded — asf scheduler install --product <p>`. A product without
  `clocks:` → one RED row with the D5 line. "Nothing ticks this product" is red today; a
  product without clocks is the same situation.

### `tools/cutover.sh`

- Drop `DISPATCH_STEPS` and `INTERVAL`. List the clocks with `run_scheduler render --product
  "$PRODUCT" --json` (name, label and steps per clock).
- For each clock: if `manifest_owns "<its steps>"`, call `install_job <clock>`, which runs
  `run_scheduler install --product "$PRODUCT" --clock <clock>` and writes a
  `record_manifest scheduler_install` row with the rendered label, as today. Otherwise print
  `<clock> (<steps>): the manifest does not own these steps — leaving the legacy job loaded`.
- Gate 3 (`RECORD_LABEL`) uses the first clock whose steps contain `record`. With no such
  clock, gate 3 fails with the D5-style NEEDS OPERATOR line.
- A product without `clocks:` fails at the listing step, before gate 2 changes anything.

### Examples and sample

- `docs/products.example.yaml`: the block above with a comment saying each entry is one job,
  plus the rules in two lines.
- `sample/product.yaml`: the same block, so `test_sample_product` exercises it.
- `docs/config.example.yaml`: the `scheduler:` comment says clocks live in the product file.

## Records

- **Files on this machine.** Each `install` writes
  `~/Library/LaunchAgents/<prefix>.<product>.<clock>.plist` (launchd) and creates
  `<ASF_HOME>/logs/tick-<product>-<clock>.log` when the job first runs. A retired job's plist is
  deleted, and its log stays where it is. cron and the unadapted kinds write nothing; they
  print the line or marker.
- **Printed lines**, the operator's audit trail for an install: `scheduler: wrote <path>`,
  `scheduler: bootstrapped <label>`, `scheduler: retired <label> (not a clock in
  products/<p>.yaml)`, and the refusals (`clock <name>: <why>`, the D5 `NEEDS OPERATOR` line).
- **Cutover manifest.** `tools/cutover.sh` keeps writing one `scheduler_install` row per
  installed job, now one per clock. `tools/rollback.sh` reads those rows unchanged.
- **The product's record**: nothing new. The ticks the clocks start keep writing their existing
  `metrics/ticks/<day>.jsonl` line (`product`, `steps`), and the steps list is how a reader
  tells which clock produced a line.
- **Config.** `products/<name>.yaml` gains `clocks:`. `config.yaml`'s `scheduler.interval_s` is
  dead (D10). `scheduler.kind`, `label_prefix` and `legacy_labels` keep their meaning.

## Stories

- S-7200: Clocks are declared in the product yaml and validated, and a missing block is a NEEDS OPERATOR refusal — acceptance: `python3 -m unittest tests.test_clocks.ClocksParseTest -v`
- S-7201: Each clock renders one job labelled and logged by its name, on its own interval or wall-clock time, per product — acceptance: `python3 -m unittest tests.test_clocks.ClocksRenderTest -v`
- S-7202: The cron adapter renders every/at exactly and refuses a clock it can't express — acceptance: `python3 -m unittest tests.test_clocks.ClocksCronTest -v`
- S-7203: A whole-file install makes the loaded jobs match the file: it installs every clock, retires this product's undeclared jobs, and is atomic — acceptance: `python3 -m unittest tests.test_clocks.ClocksInstallTest -v`
- S-7204: The CLI takes `--clock`, not `--steps`/`--interval` — acceptance: `python3 -m unittest tests.test_clocks.ClocksCliTest tests.test_scheduler -v`
- S-7205: Doctor reads each job's own interval, flags a declared clock that isn't loaded, and marks `scheduler.interval_s` as not read — acceptance: `python3 -m unittest tests.test_doctor -v`
- S-7206: Cutover installs the declared clocks, not a hard-coded three — acceptance: `python3 -m unittest tests.test_cutover -v`
- S-7207: The example and sample product files declare the card's four clocks — acceptance: `python3 -m unittest tests.test_sample_product -v`
