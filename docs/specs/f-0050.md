# F-0050 — The product improvement loop

The factory already has a loop pointed at itself. `asf/scorecard/loop.py` measures the line —
sessions, runs, CI, lead time, cost per Feature — diagnoses a cause over its threshold, files a
card, and two weeks after that card lands reads the same number again to see whether it moved.
Every number it reads is a number the *factory* produced while building.

This spec builds the counterpart pointed at the **product**: one loop per product, reading the
measurements the product itself declares, taken by a probe identity the product configures,
against guardrails the product sets, filing its proposals into that product's own record. The
factory learns nothing about the product from building it; it learns by measuring it.

The card's standing guardrails are the design, not a preamble to it:

| The guardrail | Where it becomes mechanical |
| --- | --- |
| the loop ships without per-change approval | `propose_product_change` defaults to `auto` (§2.5); a card is not a merge, and the ordinary lane still stands between the card and the trunk |
| a new feature is a proposal for a human | a guardrail the product has **never met** is not a regression — the card is filed undecided into intake (§2.4) |
| the probe identity is development-only and touches no customer data | a probe aimed at the product's own `app_host` is refused before it runs, and it runs under a worker account's environment, never the operator's (§2.3) |
| a worse measurement reverts | the verify pass files a revert card naming the landing sha (§2.6) |
| writer, reviewer and fixer are never the same session | holds already — three roles, three launches, three worktrees (P5) |
| production, money, security, customer data and legal always need a human | holds already — all five default `human-now` in `approvals.CLASSES` (P4) |

**Verified in this worktree at `3624ba524`.** Every `file:line` below was read there.

## 1. Decisions

### 1.1 What already holds

- **The scorecard loop is the factory's half of this, and its skeleton is reusable.**
  `asf/scorecard/loop.py:410` — `daily(product, root)` is drain → measure → snapshot → diagnose
  and file → verify → drain. `enqueue` (`:160`) appends one entry to a per-target queue,
  `drain` (`:178`) writes queued inbox cards and History lines into the record clone, deduping on
  a marker string; `verify` (`:332`) compares a number `verify_weeks` either side of a card's
  landing and reopens the card when it did not move; `moved` (`:323`) is the comparison. This
  spec reuses the queue, the drain and the shape of the state file, and replaces the facts.
- **The scorecard already distinguishes a `factory` cause from a `product` one, and the
  distinction does not reach far enough.** `asf/scorecard/diagnose.py:36` —
  `FACTORY, PRODUCT = 'factory', 'product'` — but the only `PRODUCT` causes it raises are
  `ci-job:<name>` and `gate:<signature>` (`diagnose.py:106`, `:115`). A red CI job is still a
  measurement of the *line*: it is what happened while building the product, not what the product
  does. Nothing in the tree today reads a number the product itself produces.
- **A card records the commits that landed it.** `asf/scorecard/facts.py:183` —
  `landing_shas(meta)` reads a typed `landed: <sha>` and the ingest's evidence lines
  (`merge <sha> of <branch> lands <id>`, `PR #<n> merged (<sha>)`), and `card()` (`:207`) carries
  it on every loaded card. A revert has a sha to name without any new machinery.
- **There is an operator-configured probe contract already, twice.** `asf/rules/rules.py:147-165`
  runs a check script with a timeout: rc 0 is clean, rc 1 with lines is a violation, **anything
  else — a bad rc, an `OSError`, a timeout — is *broken*, never a violation**. `asf/credentials.py`
  mirrors it for a signed-in tool (`run_probe`, `:269`; `STATES = ('valid', 'invalid', 'broken')`,
  `:66`) and keeps only the last non-empty line of what the probe said, scrubbed and truncated
  (`DETAIL_MAX = 160`, `:32`). §2.3 is that contract a third time, with a number in the line.
- **A probe already runs under an identity that is not the operator's.**
  `asf/credentials.py:202` — `probe_env(provider, cfg, product)` builds a worker account's own
  environment through `runtime.build_env(runtime.Job(...))`, exactly as `asf/doctor.py:326` does
  for the push probe, or `hermetic.worker_base()` when no account is named. `asf/hermetic.py:144`
  `build(..., mode='worker')` starts from nothing and keeps only `WORKER_ALLOW` (`:63` — `PATH`,
  `LANG`, `TERM`, `TMPDIR`, `USER`, `SHELL`), every `LC_*`, and the names
  `worker_pool.env_passthrough` lists. An operator's token in the tick's environment does not
  reach a probe unless the operator names it.
- **The product's live host is already written down.** `docs/products.example.yaml:305` —
  `app_host: https://sample.example.com`, *"the product's own live URL, used by the prod probe /
  release notes"*; `asf/env.py:780` is the accessor. §2.3 has something concrete to refuse
  against.
- **`improve:` is the block every loop's settings already live in.** `asf/env.py:505-509` —
  `IMPROVE_FIELDS = {'thresholds', 'epic', 'window_days', 'premium_models', 'scorecard'}`, where
  `scorecard` is *"the value loop's settings (asf.scorecard.loop)"*, and `asf/env.py:487` lists
  `improve` in `PRODUCT_FIELDS`. A third loop is a third key in that table.
- **The daily step is where a per-product loop hangs, and one part failing does not stop the
  others.** `asf/tick/step_daily.py:31-37` — `parts()` returns `[('stale', …), ('rollup', …),
  ('scorecard', …)]`; `run_part` (`:40`) catches every exception and turns it into rc 1 with one
  line, and `run` (`:52`) runs all of them before raising.
- **Minting an id in the record clone is allowed.** `asf/record/ids.py:25-37` — `mint_id` refuses
  without `BACKLOG_ID_RANGE` only when the root has a `.git` **file**, i.e. a linked worktree.
  `asf/tick/shadow.py:44` — `record_dir(product)` is `state/<product>/record`, a clone with a
  `.git` directory. `write_new_item` (`ids.py:59`) takes arbitrary typed fields, so a card can be
  written carrying `decided`, `parent`, `rank` and `source`.
- **The five classes the card calls untouchable are untouchable.** `asf/approvals.py:61-125` —
  `spend_money`, `touch_production`, `touch_security`, `touch_customer_data` and `touch_legal`
  each carry `'human-now'` as their default level. Nothing in this spec widens any of them.

### 1.2 In

1. `improve: {product: {...}}` — one product's measurements, its probe identity, its guardrails
   and the loop's own settings, read off that product's file (§2.1).
2. `asf/product_loop/probe.py` — running one measurement, its reading contract, and the refusals
   that keep the probe identity development-only (§2.2, §2.3).
3. `asf/product_loop/loop.py` — the loop: measure, record the readings, propose, verify, revert
   (§2.4–§2.6), filing only into its own product's record.
4. A new approval class `propose_product_change`, default `auto` (§2.5).
5. `asf product-loop` as the operator's read of it, a fourth part of the daily step as the
   factory's, and one `asf doctor` row (§2.7).
6. `tests/test_product_loop.py`, and the two documented example files gaining the block.

### 1.3 Out

- **Deciding what a product should measure.** ASF cannot know whether a product's number is a
  conversion rate, a p95 or an error budget. The product declares its measurements and their
  guardrails; the loop reads them, ranks their breaches, and never invents one.
- **Merging, deploying, or touching the product's repo at all.** The loop writes into
  `~/.ASF/state/<product>/` and, through the queue, into that product's record clone. It opens no
  branch, no PR and no deploy. A revert is a *card* naming a sha, and the ordinary lane reverts it
  the way it lands everything else. `touch_production` stays `human-now`.
- **Measuring the product in production.** §2.3 refuses a probe aimed at `app_host`. A product
  whose only measurable environment is production gets no loop until it has a development one —
  that is the card's own guardrail, and it is not negotiable here.
- **A/B testing, experiment assignment, or a traffic split.** The loop compares the same
  measurement before and after a landing in time, not two cohorts at once. `ab_pair` already
  exists on a card (`asf/scorecard/facts.py:213`) and is a different Feature.
- **Reverting by force.** The loop never rewrites the trunk, never force-pushes, and never
  reverts a commit itself. It files a card that says which sha to revert and why.
- **Backfilling readings for days already past.** The first run is the baseline; a verdict needs
  readings on both sides of a landing, so the first revert is possible only once the loop has run
  either side of one.
- **Widening any of the five human-now classes**, or a per-measurement approval level. One class,
  three levels, the same shape as `propose_improvement` (F-0091 §2.4).

### 1.5 The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | A **new package** `asf/product_loop/`, beside `asf/scorecard/` and `asf/improve/` | Adding the measurements to `asf/scorecard/diagnose.py` as more `PRODUCT` causes; adding them to `asf/improve/classes.py` | `diagnose.causes` takes `Facts` — sessions, runs, CI, items — and every one of its causes is arithmetic over what the *line* did. A product measurement has no session behind it, arrives from a subprocess, can be *broken* rather than high or low, and is filed under a different approval class with a different revert rule. Folding it in would make `Facts` a union type and `causes()` a function with two unrelated halves. `asf/improve/` is the waste catalogue and is further away still. A name not called `product` avoids reading as `asf.env.Product` at every import site. |
| D2 | The settings are `improve: {product: {...}}` | A new top-level `product_loop:` block in `PRODUCT_FIELDS`; a file of its own | `improve:` is already the one block a product's loops are configured in — `improve.thresholds` is the waste pass, `improve.scorecard` is the value loop (`env.py:505-509`). A third loop is a third key, one line in `IMPROVE_FIELDS`, and an operator looking for "how does the factory improve things" finds all three in one place. |
| D3 | A measurement is an **operator-declared command that prints one number**, under the rules/credentials contract: rc 0 and a parseable last line is a reading, anything else is `broken` | A metrics endpoint ASF scrapes; a JSON file the product writes; a fixed catalogue of measurements ASF knows how to take | ASF is generic — `tools/check_generic.sh` forbids even a vendor's name in a tracked file — so it cannot ship a scraper for one product's telemetry. A command is the one interface every product can satisfy, and the tree already runs operator scripts under this exact contract twice (`rules.py:147`, `credentials.run_probe`). A file the product writes would need a schema, a writer and a staleness rule; a command's freshness is the moment it ran. |
| D4 | **Broken is not bad.** A probe that times out, crashes or prints an unparseable line yields *no reading* — never a low one | Treating a failed probe as a breach; treating it as the last known value | The constitution's own sentence: *"An absence is reported as an absence — 'I found nothing' is a result, and 'nothing was checked' is a different result that must never be printed as the first one"* (`docs/CONSTITUTION.md:145`). This is the single most dangerous edge in the spec: a loop that reverts on a broken probe reverts good changes every time the probe's own dependency wobbles. A broken probe files nothing, reverts nothing, and appears in the readings as `state: broken` with its last line. |
| D5 | The regression / new-feature split is decided by **whether the product has ever met this guardrail** in the loop's own reading history | Asking the model to judge; a `kind:` the operator types per measurement; treating every proposal as a new feature | The card says a new feature is a proposal for a human, and the loop needs a rule it can apply without judgement. A guardrail the product met last week and breaches today is a *regression*: the product could do this, and now cannot — restoring it is not a new product decision, and it is exactly what "ships without per-change approval" is for. A guardrail never met is an *aspiration*: no amount of measurement makes it a thing the factory may decide alone, so it goes to a human undecided. The rule reads off the loop's own `product-loop.jsonl` and is one function with a unit test. |
| D6 | "Worse" is measured as **movement in the breach distance, scaled by the guardrail**: `breach(after) - breach(before) >= revert_margin × abs(guardrail)` | A ratio `after/before` (the scorecard's `moved`, `loop.py:323`); an absolute delta per measurement | A ratio breaks on the numbers a product actually measures: a rate that was 0 cannot worsen by a ratio, a "higher is better" measurement inverts the comparison, and a negative reading makes the ratio meaningless. Normalising to the *breach distance* — how far past the guardrail the reading sits, always "bigger is worse" whichever direction the measurement runs — makes one comparison correct for both directions and every sign, and the guardrail is the natural scale to express the margin in. |
| D7 | `revert_margin` defaults to **0.05**, `min_readings` to **3** each side, `verify_days` to **7** | The scorecard's `min_move: 0.2`; a single reading each side | The scorecard's 0.2 is the bar for calling a fix *successful* — deliberately high, because a card that half-worked should be reopened. This is the opposite test: the bar for calling a change *harmful*, which should be low, because the cost of an unnecessary revert is one lane, and the cost of a missed one is a product that silently got worse. Three readings a side is the smallest number a median is meaningful over, and it is what stops one bad probe run from reverting. |
| D8 | A revert arrives as a **card naming the sha**, decided, at the top of the board | The loop reverting the commit itself; a PR the loop opens; a deploy rollback | The card's own acceptance: *"a proposed product change arrives as a card, never as a merge"*, and a revert is a proposed product change. `touch_production` is `human-now` (P4) and the harvest owns the trunk — a loop that force-reverted would be the one thing in the tree that writes to the trunk without the lane. Filing it decided and ranked first is what makes it *automatic* without making it a merge: the next tick's feeder picks it up like any other decided card, and it lands through review, CI and `merge_routine_pr` exactly as everything else does. |
| D9 | One approval class `propose_product_change`, default **`auto`** | Reusing `propose_improvement` (F-0091); a bare `improve.product.autofile: true`; a `human-now` default | The card asks for a loop that ships without per-change approval, and the approval matrix is the one file an operator narrows. `propose_improvement` is about the *factory's* waste and lives in another record; riding this in on it would mean an operator cannot hold one without holding the other. The default is `auto` because that is what the card asks for, and because the counterweight is real: the card is not a merge, the lane's review and CI are unchanged, and §2.6 undoes what the loop got wrong. |
| D10 | The loop's target is **always `product.name`** — no scope split, and `improve.scorecard.file_to` does not redirect it | Reusing `loop.target_of` (`loop.py:88`) | Acceptance #1 is *"writes only to that product's record"*. `target_of` exists to send a *factory* cause to the factory's own record, which is right for the scorecard and wrong here: every measurement this loop reads belongs to one product, so every proposal does too. Hard-coding the target is how that acceptance is a property of the code and not of a config nobody set. |
| D11 | Its **own queue file**, `product-loop-queue.jsonl`, and `enqueue`/`drain` gain a `queue=` argument | Sharing `scorecard-queue.jsonl`; a second copy of `drain` | One keyword argument on two functions buys two loops that cannot corrupt each other's pending writes and two files an operator can read separately. Copying `drain` would give the dedupe-by-marker rule two homes. |
| D12 | A fourth part of the **daily step**, after `scorecard` | A weekly step with its own stamp (F-0091's `improve`); its own tick step | A product measurement is a daily reading by nature — a verdict needs `min_readings` on each side of a landing, and a weekly cadence would make the first verdict a month out. `step_daily.run_part` (`:40`) already isolates a failing part, which matters more here than anywhere: this part shells out to a command the operator wrote. |
| D13 | A product that configures no `improve.product` runs nothing and returns 0 | Defaulting to some measurement; a doctor failure for every product | The loop's input is entirely operator-declared (D3), so an unconfigured product has nothing to read. One line — `product-loop: not configured` — and rc 0 keeps every existing product's daily step exactly as it is today. |

## 2. The design

### 2.1 The configuration — `improve: {product: {...}}`

In `docs/products.example.yaml`, inside the existing `improve:` block:

```yaml
improve:
  # the product improvement loop (F-0050): what this product measures about itself, who takes
  # the reading, and the guardrail each reading is held to. Unset — the loop does nothing.
  product:
    epic: E-0002                # proposals hang here; else conventions.default_bug_epic
    probe:
      account: probe            # a worker_pool account name — the probe identity. Unset: an
                                #   environment with nothing of the operator's in it
                                #   (asf.hermetic.build mode=worker).
      base_url: https://dev.sample.example.com   # the development environment. NEVER app_host:
                                #   a probe aimed at the live host is refused before it runs.
      timeout: 120              # seconds, per measurement
    verify_days: 7              # the window each side of a landing a verdict is read over
    min_readings: 3             # readings needed on each side before there is a verdict at all
    revert_margin: 0.05         # how far past the guardrail a reading must move to count as worse
    max_per_run: 2              # proposals filed per run; the rest are still breached tomorrow
    measurements:
      - name: signup_completion
        command: tools/probe/signup.sh
        unit: '%'
        direction: higher-is-better    # higher-is-better | lower-is-better
        guardrail: 80
      - name: search_p95_ms
        command: tools/probe/search-latency.sh
        unit: ms
        direction: lower-is-better
        guardrail: 400
```

`asf/env.py:505` gains one key — `IMPROVE_FIELDS['product'] = _MAP` — and `asf/env.py:813`'s
`Product.improve` already returns the whole block, so no new accessor.

`asf/product_loop/measures.py` is pure — no file, no clock, no subprocess:

```python
DEFAULTS = {'verify_days': 7, 'min_readings': 3, 'revert_margin': 0.05, 'max_per_run': 2,
            'timeout': 120}
HIGHER_BETTER, LOWER_BETTER = 'higher-is-better', 'lower-is-better'


@dataclasses.dataclass(frozen=True)
class Measurement:
    name: str
    command: str
    unit: str
    direction: str       # HIGHER_BETTER | LOWER_BETTER
    guardrail: float


def settings(product):
    """``improve.product`` with the defaults filled in, its measurements parsed and its probe
    resolved. A measurement missing a name, a command or a numeric guardrail is dropped (and
    named in ``problems``) rather than guessed at: a guardrail nobody wrote is not a guardrail."""
```

`settings` returns `Settings(measurements, probe, epic, verify_days, min_readings,
revert_margin, max_per_run, problems)`. A malformed measurement never becomes a silent default —
it lands in `problems`, which the command prints and `asf doctor` reads (§2.7).

The one piece of arithmetic every other part is built on, and the answer to D6:

```python
def breach(m, value):
    """How far past its guardrail a reading sits — **always bigger is worse**, whichever
    direction the measurement runs. Negative is slack: the reading is inside its guardrail."""
    return (value - m.guardrail) if m.direction == LOWER_BETTER else (m.guardrail - value)


def breached(m, value):
    return breach(m, value) > 0


def worse(m, before, after, margin):
    """True when ``after`` sits at least ``margin`` of the guardrail further past it than
    ``before`` did. ``None`` when either side has no reading — never ``True`` (D4)."""
    if before is None or after is None:
        return None
    return breach(m, after) - breach(m, before) >= margin * abs(m.guardrail or 1.0)
```

### 2.2 `asf/product_loop/probe.py` — one measurement, one reading

The contract, third time in this tree (D3), stated on the function:

```python
STATES = ('ok', 'broken')

@dataclasses.dataclass(frozen=True)
class Reading:
    name: str
    state: str            # 'ok' | 'broken'
    value: float = None   # never set when broken (D4)
    detail: str = ''      # the probe's own last line, scrubbed and truncated — never a token
    taken_at: str = ''


def take(measurement, env_map, cwd, timeout, now, run=subprocess.run):
    """One measurement. ``rc 0`` and a last non-empty stdout line matching ``<name>=<number>``
    (or a bare number) → ``ok`` with that value. Any other rc, an unparseable line, an
    ``OSError``, a ``TimeoutExpired`` or an ``AuthEnvError`` → ``broken`` with no value: a probe
    that could not answer has not answered, and an absence is never a bad reading."""
```

- The command is `shlex.split` and run with `cwd=product.repo_dir` — the probe script lives in
  the product's own repo, like a rule's check script (`rules.resolve_script`).
- `detail` is the last non-empty line of stdout, else of stderr, run through
  `redact.scrub(..., redact.default_patterns(root))` and truncated at 160 characters — the same
  treatment `credentials._detail` gives it. A probe against a development environment still
  prints into a record.
- The value is parsed from `<name>=<number>` or a bare number, tolerating a `%`, `ms` or `s`
  suffix. Two readings in one run of one measurement is an unparseable answer, i.e. broken.

### 2.3 The probe identity is development-only

Built exactly as `credentials.probe_env` does (P3), with the refusals that make the card's
guardrail mechanical:

```python
def probe_env(settings, cfg, product):
    """The environment every measurement runs under: the worker account
    ``improve.product.probe.account`` names, built through
    :func:`asf.workers.runtime.build_env` — or :func:`asf.hermetic.worker_base` when it names
    none. Then, set last and never inherited:

        ASF_PRODUCT_PROBE=1          so the product's own script can assert where it is
        ASF_PROBE_BASE_URL=<base>    the development environment it must talk to
        GIT_TERMINAL_PROMPT=0        a credential it cannot reach fails, it does not hang
    """


def refusals(settings, product):
    """Every reason this product's probe may not run, or ``[]``. Checked **before** any
    subprocess starts; a non-empty list means the run takes no reading at all."""
```

The refusals, each its own line and its own test:

| Refusal | The line |
| --- | --- |
| no `probe.base_url` | `improve.product.probe.base_url is unset — the loop has no development environment to measure` |
| `base_url`'s host equals `app_host`'s host | `improve.product.probe.base_url is the product's live host (<host>) — the probe identity is development-only and touches no customer data` |
| `probe.account` names no `worker_pool` account | `improve.product.probe.account: <name> is not a worker_pool account` |
| a measurement's `command` resolves to nothing under `repo_dir` | `<name>: command not found in the product repo — <command>` |

The host comparison is on the parsed host alone (`urllib.parse.urlsplit(...).hostname`, lowered),
so `https://sample.example.com/health` and `http://Sample.Example.com` are both the live host. A
product with no `app_host` fails only the first refusal — there is no live host to be confused
with, and the operator still has to name a development one.

This is a refusal, not advice: when `refusals()` is non-empty the loop prints each line prefixed
`NEEDS OPERATOR:`, takes no reading, files nothing, and returns 0. A misconfigured probe is an
operator's to fix; it is not a reason to stop the tick.

### 2.4 The loop — measure, record, propose

`asf/product_loop/loop.py`, mirroring `scorecard/loop.py:410`:

```python
def daily(product, root, out=print, now=None):
    """The loop, once: drain, measure, record the readings, propose, verify, drain. Returns 0."""
```

1. **drain** whatever the last run queued (§2.5).
2. `cfg = measures.settings(product)`. No measurements → `out('product-loop: not configured')`,
   return 0 (D13). `refusals` non-empty → print them, return 0 (§2.3).
3. **measure**: `probe.take(...)` per measurement, serially, under one `probe_env`.
4. **record** one line in `~/.ASF/state/<product>/product-loop.jsonl` — every reading of this run,
   `ok` and `broken` alike (§4). This file is the *only* history the loop reads: the before/after
   of a verdict, and the "has this guardrail ever been met" of D5, both come off it.
5. **propose**, per breached measurement, worst breach first, at most `max_per_run`:
   - already in the state file under this measurement with no verdict → nothing (one open
     proposal per measurement, ever);
   - `met_before(history, m)` — any `ok` reading of this measurement, on any earlier line, with
     `breach <= 0`:
     - **true → a regression.** The product could hold this guardrail and now cannot. Filed per
       §2.5 at the `propose_product_change` level; at `auto` it is written into the record
       **decided**, so the next tick's feeder picks it up with no human in the way.
     - **false → a new feature.** This guardrail has never been met. Filed as an **undecided
       intake card**, at every level, whose text says so in as many words: *"this product has
       never met this guardrail in the loop's readings — this is a new feature, and a human
       decides it."* The groom types it and a human decides it.
6. **verify** every filed proposal whose card has landed (§2.6).
7. **drain** again, then one line:
   `product-loop: 4 reading(s), 1 broken · 2 breached · 1 filed (1 regression, 0 new feature) · 1 verdict (1 reverted)`.

`met_before` is the whole of D5 and is a pure function over the history — the test for it is a
list of dicts, no probe and no clock.

### 2.5 What a proposal is, and where it goes

The target is `product.name`, always, with no scope argument and no `file_to` (D10). `enqueue` and
`drain` gain `queue=QUEUE` and the loop passes `PRODUCT_QUEUE = 'product-loop-queue.jsonl'` (D11).

`drain` gains a third entry kind beside `inbox` and `history` (P1):

```python
elif e.get('kind') == 'card':
    # a decided card: mint an id in this record and write the item (ids.mint_id /
    # ids.write_new_item). Deduped on the same marker as an inbox card, so a queue drained
    # twice writes one card.
```

and calls `index.do_index(root)` once when it wrote any. Everything else about `drain` — reading
the queue, the marker dedupe, leaving a History line whose card is not minted yet queued — is
unchanged.

The three shapes, and what differs:

| | regression | new feature | revert |
| --- | --- | --- | --- |
| entry kind | `card` at `auto`, else `inbox` | `inbox`, at every level | `card` at `auto`, else `inbox` |
| typed | `decided: true`, `parent: <epic>`, `rank: 20`, `source: product-loop:<name>` | none — the groom types it | `decided: true`, `parent: <epic>`, `rank: 0`, `source: product-loop:revert:<sha7>` |
| marker | `product-loop: <name> #<n>` | `product-loop: <name> #<n>` | `product-loop: revert <sha7> #<n>` |
| title | `<name> is <value> <unit>, past its guardrail of <guardrail>` | `<name> has never met its guardrail of <guardrail> <unit>` | `Revert <sha7>: <name> got worse after <id> landed` |

The level is `approvals.level_of(product, 'propose_product_change')`:

- **`auto`** (the default) — a regression and a revert are written into the record as decided
  cards; a new-feature proposal still goes to intake undecided.
- **`groom`** — everything goes to intake, including a revert. An operator who narrows to this is
  saying no card of this loop's reaches the board without the groom seeing it.
- **`human-now`** — nothing is written into the record. The readings are still taken and still
  recorded (they are the history every later verdict needs), and one line per proposal:
  `NEEDS OPERATOR: product-loop proposes <name> (<the sentence>) — widen approvals: propose_product_change in products/<p>.yaml`.

The class joins `approvals.CLASSES`:

```python
ActionClass(
    'propose_product_change',
    "filing a card the product improvement loop proposes from the product's own measurements",
    'auto', ('product_loop',),
    why='proposing a product change is the product loop\'s, off a measurement — not a session\'s',
    instead='name the change you would propose under `left out:` in your report'),
```

Every card carries, in its `## Description`: the reading and its guardrail, the probe's own last
line, the window it was read over, how it will be verified, and the marker. Its `## Acceptance` is
the number that closes it — `signup_completion reads at or above 80 % over the 7 days after
landing`. The whole text goes through `loop._scrub` (`loop.py:244`) before it is queued.

### 2.6 A worse measurement reverts the change

`verify(product, history, cfg, state, cards_of, now)` — the same shape as `scorecard/loop.py:332`,
with D6's comparison and one new outcome.

For each filed proposal with no verdict, whose card `cards_of(product.name)` shows as landed at
`landed`, once `now >= landed + verify_days`:

```
before = median of this measurement's `ok` readings in [landed - verify_days, landed)
after  = median of this measurement's `ok` readings in [landed, landed + verify_days)
```

- **fewer than `min_readings` on either side → no verdict.** The loop waits. It does not revert,
  does not close, does not reopen.
- `worse(m, before, after, revert_margin)` is `None` (a side with no reading) → **no verdict**.
  This is D4 arriving where it matters most.
- **False** → the verdict is `held`. One History line on the card, and the state entry closes:
  `- <date> product-loop: signup_completion held — 74 before, 81 after (median over 7 days each side of landing 2026-10-04)`.
- **True → the revert.** One History line on the card in the same shape but reading `got worse`,
  and one revert card (§2.5) naming every sha in `cards_of(...)[iid]['landing_shas']`, with the
  two numbers and the original card's id in its Description, `rank: 0`, decided.

The rails, each its own test, because an automatic revert is the one thing in this spec that can
do damage on its own:

1. **A revert card is never itself verified.** Its state entry is written with
   `verdict: 'revert'` at the moment it is filed, so the loop cannot revert a revert.
2. **One revert per proposal.** The verdict closes the entry; a measurement still breached
   afterwards is a *new* proposal at `#n+1`, going through `met_before` again like any other.
3. **No sha, no revert card.** A card whose `landing_shas` is empty gets the History line
   (`got worse … landed without a traceable commit to revert`) and the verdict, and nothing else:
   the loop says what it found and leaves the decision where it belongs. `facts.UNTRACEABLE`
   already names this state.
4. **A broken probe never reverts** — rails 1 and 2 of §2.6 above, and D4.
5. **The loop never reverts a change it did not propose.** Only cards in its own state file, keyed
   by its own marker, are verified at all.

### 2.7 The command, the step and the doctor row

**`asf product-loop [--product P] [--dry-run] [--json]`** — `dry-run` takes the readings and
prints everything it would file, writing neither the history line, the state file, nor the queue;
`--json` prints the run's readings and proposals as JSON. `asf/cli.py` gains the parser beside
`scorecard`'s (`cli.py:320`).

**The step**: `asf/tick/step_daily.py:31` gains a fourth part, after `scorecard`:

```python
    # the product loop: measure the product itself, propose a card per breached guardrail,
    # revert a change the measurement got worse after (F-0050)
    ('product-loop', lambda: product_daily(product, root)),
```

`run_part` already turns an exception into rc 1 and one line without stopping the others
(`step_daily.py:40`), which is what a part that shells out to an operator's script needs.

**The doctor row**: one more row appended beside the others at `asf/doctor.py:832-844`, in the
same `(name, required, ok, detail)` shape:

- skip — the product declares no `improve.product`;
- **red** — `refusals()` is non-empty; the detail is its first line, so a probe aimed at the live
  host is the loudest thing on the page;
- amber/advice — `settings().problems` is non-empty (a measurement dropped for a missing
  guardrail);
- green — every measurement parsed and the probe configured, with the count:
  `2 measurement(s), probe <account> → <host>`.

The row never runs a probe. `asf doctor` is a read of the configuration, and taking a
measurement is the daily step's job.

## 4. Records

**Files.**

| Path | Written by | Shape |
| --- | --- | --- |
| `~/.ASF/state/<product>/product-loop.jsonl` | `loop.daily` | one line per run: every reading, `ok` and `broken` alike — the only history the loop reads |
| `~/.ASF/state/<product>/product-loop-state.json` | `loop.daily` | one entry per measurement: the open proposal, its marker, its card, its baseline, its verdict, its log |
| `~/.ASF/state/<product>/product-loop-queue.jsonl` | `loop.enqueue` | pending writes into this product's record; emptied by `drain`, and only ever this product's |
| `<record>/<intake_dir>/product-loop-<name>-<n>.md` | `drain` (`inbox`) | a new-feature proposal, and everything at `groom` |
| `<record>/features/F-xxxx.md` | `drain` (`card`, at `auto`) | a decided regression or revert card |
| `<record>/…/<id>.md` `## History` | `drain` (`history`) | one line per verdict |

**A reading line**, `product-loop.jsonl`:

```json
{"date": "2026-09-28", "as_of": "2026-09-28T06:12:04Z", "product": "sample",
 "readings": [
   {"name": "signup_completion", "state": "ok", "value": 71.0, "unit": "%",
    "guardrail": 80, "direction": "higher-is-better", "breach": 9.0, "breached": true},
   {"name": "search_p95_ms", "state": "broken", "value": null,
    "detail": "probe timed out after 120s"}]}
```

`value` is absent from every `broken` reading — there is no field for a number nobody took.

**A proposed card's typed fields**, and what each is for:

```yaml
source: product-loop:signup_completion    # the dedupe key — one open proposal per measurement
parent: E-0002                            # improve.product.epic, else conventions.default_bug_epic
decided: true                             # a regression or a revert at `auto`; never a new feature
rank: 20                                  # a revert is 0 — the top of the board
```

**A History line**, one per verdict, on the card the loop filed:

```
- 2026-10-11 product-loop: signup_completion got worse — 82 before, 69 after (median over 7 days
  each side of landing 2026-10-04); revert filed for a1b2c3d
- 2026-10-11 product-loop: search_p95_ms held — 410 before, 360 after (median over 7 days each
  side of landing 2026-10-04)
```

**Printed.** The §2.4 summary line in the tick log every day, each `NEEDS OPERATOR:` line from
§2.3 and from `human-now`, and — in `asf doctor` — one row.

**Not written.** No new `metrics.SCHEMAS` key, no event stream of its own, no file in the product's
repo, no branch, no PR, and nothing at all in any record but this product's.
