# F-0325 — a declared `wave` clock is the wave job, not a tick on the product's tick lock

A product that declares its own clock named `wave` with `steps: [wave]` gets
`asf tick --steps wave`. That is a tick, so it takes the product's one tick lock
(`asf/tick/tick.py:339`, `acquire_lock` with `wait_s=0`) and prints
`tick: another tick of <p> is running — skipped` whenever a long tick holds it. On one product on
2026-10-08 that line repeated 1,270 times in a day: during a 10-minute tick the product had 6 rows
ready and its cloud lane at 2/32, so launches only ever happened in the gaps between ticks.

Being *named* `wave` it also keeps the dedicated wave job out: `asf/scheduler.py:551` installs that
job only `if WAVE_CLOCK not in declared`. The clock written to make the wave prompt is the one
thing that stops the wave from being prompt.

The fix is to read such a clock as what the operator meant: a declaration of the wave job
(`asf/tick/wave_clock.py`, `asf wave`), rendered as that job at the cadence the clock declares,
under `tick-wave.lock` and never the product's tick lock.

## Decisions

### In

1. `asf/scheduler.py` — a declared clock named `wave` carrying exactly the `wave` step and
   nothing else is built with `command = WAVE_COMMAND`: it renders `asf wave --product <p>`,
   at its own `every:` or `at:`, keeping its name, its label and its `steps: [wave]`.
2. `asf/scheduler.py` — because that clock now *is* the wave job, the dedicated job is no longer
   missing when it is declared, and is never appended a second time beside it.
3. `asf/doctor.py` — a new `check_wave_clock(product)`, printed beside `check_clock_steps`, names
   the two shapes ASF will not convert: a clock named `wave` that is not the wave job, and a
   declared wave clock held back by `clocks.wave: off`.
4. `docs/products.example.yaml` — comment lines under the `clocks:` block saying what a clock
   named `wave` means. Comments only: no new key, so the file's parse is untouched.

### Out

* The native job's own behaviour. `asf/tick/wave_clock.py` is not edited: the locking, the
  marker, the private record clone and `ran_recently` already work and are already tested
  (`tests/test_wave_clock.py`). This card moves one clock onto that job; it does not change it.
* `asf.scheduler.clock_of_plist`. It has an arm for the CI queue's job and none for the wave's, so
  an installed `asf.<p>.wave` job reads back as `None` (P9) and `status` would call it "not a job
  this adapter renders". That path is only reached for an **undeclared** installed job, and this
  change makes a declared wave clock *more* often declared, never less — so no new case reaches it.
  Noted, not fixed.
* The upgrade drain. `asf.upgrade.TICK_PATTERN` does not match `asf wave`, so a converted clock's
  runs stop being counted by the drain and `upgrade.waiting()` no longer pauses them (D8). That is
  the dedicated job's existing behaviour, which this card makes one more clock share; changing it
  would be a change to the job, which is out.
* Any clock that carries the `wave` step under a different name (`launch: {steps: [wave]}`). It is
  the same tick-lock shape, but the dedicated job is still installed beside it (P1c), so rows are
  still launched and the only cost is a noisy log. Lower severity, different card.

## The design

### §1 `asf/scheduler.py` — the predicate

Beside `WAVE_CLOCK` / `WAVE_COMMAND` (`asf/scheduler.py:92-98`), the step name the clock carries
and the predicate that recognises the declaration:

```python
#: the tick step the wave job runs — the step a declared ``wave`` clock carries (F-0325)
WAVE_STEP = 'wave'


def declares_wave_job(clock):
    """Whether ``clock`` is the operator's own declaration of the wave job (F-0325): named
    :data:`WAVE_CLOCK`, carrying :data:`WAVE_STEP` and nothing else.

    Such a clock used to be built as a plain tick, so it ran ``asf tick --steps wave`` and took
    the product's one tick lock (:func:`asf.tick.tick.lock_path`) — on a busy product it skipped
    every firing a long tick ran through, and being named ``wave`` it also kept the dedicated job
    from ever being installed beside it. It is rendered as that job instead, at the ``every:`` or
    ``at:`` it declares. ``steps`` is left as declared on purpose: :func:`tick_argv` dispatches on
    ``command`` before it reads ``steps``, and :func:`asf.doctor.check_clock_steps` reads the
    ticked set out of ``steps`` — emptied, it would report the wave step as being on no clock.
    """
    return (clock.name == WAVE_CLOCK and not clock.shadow
            and list(clock.steps or []) == [WAVE_STEP])
```

### §2 `asf/scheduler.py` — the wave block of `clocks()`

`asf/scheduler.py:551-554` reads, today:

```python
    if WAVE_CLOCK not in declared and any('wave' in (c.steps or []) for c in built):
        from asf.tick import wave_clock
        if not wave_clock.off():
            built.append(Clock(WAVE_CLOCK, [], False, wave_clock.every_s(), None, WAVE_COMMAND))
    return built
```

and becomes:

```python
    if WAVE_CLOCK in declared:
        # the operator's own declaration of the wave job (F-0325): rendered as that job, at the
        # cadence it declares, under tick-wave.lock — never as a tick on the product's tick lock
        if any(declares_wave_job(c) for c in built):
            from asf.tick import wave_clock
            if not wave_clock.off():
                built = [c._replace(command=WAVE_COMMAND) if declares_wave_job(c) else c
                         for c in built]
    elif any(WAVE_STEP in (c.steps or []) for c in built):
        from asf.tick import wave_clock
        if not wave_clock.off():
            built.append(Clock(WAVE_CLOCK, [], False, wave_clock.every_s(), None, WAVE_COMMAND))
    return built
```

The `elif` is what retires the card's second clause: the declared name no longer merely *blocks*
the job, it *is* the job, so there is exactly one clock named `wave` on either path and exactly one
label `asf.<p>.wave`. The `any(declares_wave_job(c) …)` guard keeps D7's laziness — a clock named
`wave` that is not the job never reads `config.yaml`.

When it is there, `asf scheduler render --clock wave` on a product declaring
`wave: {steps: [wave], every: 1m}` prints a plist whose `ProgramArguments` end
`-m asf.cli wave --product <p>` and whose `StartInterval` is `60`, and `asf scheduler install`
replaces the tick plist at the same label `asf.<p>.wave` — no label churn, nothing retired, one
bootstrap.

### §3 `asf/doctor.py` — the shapes the conversion cannot reach

Beside `check_clock_steps` (`asf/doctor.py:1572`), and printed beside it at
`asf/doctor.py:2187-2188`:

```python
def check_wave_clock(product):
    """One ``NEEDS OPERATOR`` line per wave-clock shape ASF will not convert to the wave job
    (F-0325, :func:`asf.scheduler.declares_wave_job`).

    Two of them. A clock *named* ``wave`` that is not the job holds the label
    ``<prefix>.<product>.wave`` the job would be installed under, so the job is never added
    beside it (:func:`asf.scheduler.clocks`) — a shadow clock, or one carrying steps besides
    ``wave``. And ``clocks.wave: off`` in ``config.yaml`` forbids the job outright, which leaves a
    declared ``wave: {steps: [wave]}`` clock running as a tick on the product's tick lock, the
    very thing it was written to avoid. A product whose clocks do not load has nothing to read:
    the scheduler section reports that.
    """
    from asf.tick import wave_clock
    try:
        built = scheduler.clocks(product)
    except scheduler.SchedulerError:
        return []
    wave = next((c for c in built if c.name == scheduler.WAVE_CLOCK), None)
    if wave is None:
        return []
    path = f'products/{product.name}.yaml'
    if not scheduler.declares_wave_job(wave):
        shape = 'shadow: true' if wave.shadow else f"steps: [{', '.join(wave.steps or [])}]"
        return [f'NEEDS OPERATOR: clock wave in {path} is not the wave job ({shape}) — it holds '
                f'the label the wave job installs under, so the wave job is never installed '
                f'beside it; rename the clock']
    if wave_clock.off():
        return [f'NEEDS OPERATOR: clock wave in {path} runs the wave step as a tick on the '
                f"product's tick lock, because clocks.wave: off in config.yaml keeps it from "
                f'running as the wave job — remove clocks.wave: off to give it its own lock']
    return []
```

A converted clock produces no line: `declares_wave_job` is true and `off()` is false, which is the
whole point.

### §4 `docs/products.example.yaml` — what the name means

Four comment lines appended to the prose above the `clocks:` block
(`docs/products.example.yaml:596-604`), after the `every_n:` paragraph:

```yaml
# A clock named `wave` carrying only `steps: [wave]` is the wave job (`asf wave`), not a tick: it
# runs the launch path alone under its own lock, so it never skips while a long tick holds the
# product's tick lock. Any other clock named `wave` (a shadow clock, or one with further steps)
# keeps the job from being installed at all — `asf doctor` names it.
```

No key is added, so `env.loads` on the file parses to exactly the keys it parses to today.

## Records

Nothing is written to the record (the backlog): the wave job has no commit of its own —
`wave_clock._Context.event` returns `None` and the job never pushes — so no row, card or event
moves because of this change. What it does write down, all of it host-local state under
`state/<product>/`:

| What | Where | When |
| --- | --- | --- |
| the job definition | the plist `~/Library/LaunchAgents/asf.<p>.wave.plist` (or the crontab line) — `ProgramArguments` ending `-m asf.cli wave --product <p>` in place of `… tick --product <p> --steps wave`, same label, same `StartInterval` | `asf scheduler install`, which prints its own `installed`/`replaced` line for that label |
| the job's log | `scheduler.log_path(<p>, 'wave')` stops carrying `tick: another tick of <p> is running — skipped` and starts carrying the job's own lines (`wave: …`, or the launch path's) | every firing |
| the run marker | `state/<p>/wave-job.json` (`{"at": "<UTC stamp>"}`), written by `wave_clock.note_ran` whether or not anything launched | every firing. This is new for such a product, and it is what makes the product's own tick skip its wave step (`tick.wave_job_recent` → `wave_clock.ran_recently`) instead of repeating the same plan-and-screen pass |
| the lock | `state/<p>/tick-wave.lock` instead of contention on `state/<p>/tick.lock` | every firing |
| the doctor's lines | stdout of `asf doctor`, below the `== SCHEDULER <p>` table | every run, for the two shapes of §3 only |

No existing file changes format and no state file is migrated: a product that has been running the
tick form simply starts writing `wave-job.json` and stops writing skip lines.
