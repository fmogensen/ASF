# F-0303 — ask git for the peel, or the tag object is what you get

`asf upgrade --product <p> --to v0.1.254` resolved the tag to `78242c1`, the **tag object**, and
read GitHub's check runs on it. There are no check runs on a tag object — the API answers
`422 No commit found for SHA` — so the guard was Unknown, the move deferred, and the line the
operator got was `CI unknown (gh could not read the check runs)`: a message that names neither
the sha it asked about nor the fact that the sha was not a commit. Passing `5c94c907`, the commit
the tag points at, worked.

The cause is one word of `git ls-remote`'s behaviour that the code assumed and never checked.
`resolve_ref` asks `git ls-remote <url> <ref>` and then looks through the answer for a `^{}`
line — the peel, which names the commit an annotated tag points at. That line is printed by an
**unfiltered** listing. Given a ref pattern, `ls-remote` prints only refs the pattern matches,
and `v0.1.254` does not match `refs/tags/v0.1.254^{}`. So the peel-seeking branch has never once
fired in production, and `resolve_ref` has always returned the tag object for an annotated tag.

The test that was supposed to cover this is `tests/test_install.py:723`,
`test_an_annotated_tag_prefers_its_dereferenced_commit`. It hands the function a fake
`ls-remote` answer containing the peel line — output real git does not produce for the command
the code actually runs. The fake asserted the assumption instead of testing it, so the branch
shipped green and dead.

The fix is to ask for the peel by name: `git ls-remote <url> <ref> <ref>^{}`. Measured below for
every ref kind, against real git and against this repo's own remote.

### In

* **The peel, asked for by name.** `asf/upgrade.py` — `resolve_ref` runs
  `git ls-remote <url> <ref> <ref>^{}`. One new module constant, `PEEL`, for the suffix the
  reader looks for and the pattern the writer asks for, so the two can never drift (they are the
  same string, and the defect was exactly that they described different commands).
* **The Unknown that names itself.** `ci_verdict`'s unreadable-check-runs detail carries `gh`'s
  own reason, which the `Result` already holds (P10). The card's symptom line is a message that
  diagnosed nothing; the next defect of this class should be readable off the deferral.
* **A test real git answers.** A new `tests/test_tag_resolution.py`: a real temp repo, a real
  annotated tag, real `subprocess.run`, and the four callers' behaviour at a tag. No network.
* **The lying test, named honestly.** `tests/test_install.py:723` keeps its fake answer and gains
  an assertion on the argv `resolve_ref` actually runs, so it can no longer pass on an answer the
  real command does not give.

### Out

* **Peeling a bare 40-hex `--to`.** An operator who pastes an annotated tag object's own sha
  still gets the 422 — now with the sha and `HTTP 422` in the line (S-79357), which is the
  remedy. Peeling it would cost a network round trip on the one form P2 exists to keep free, for
  a spelling nobody has used.
* **`resolve_target`'s order.** The checkout is still asked before the remote. A branch name
  resolved against a checkout that is behind origin, or shadowed by a local ref of the same
  name, is a real hazard and is not this card's: it is a judgement about which answer wins, not
  a wrong answer to a right question. `--to <tag>` is immune — a tag that exists locally points
  where the remote's does.
* **`ci_verdict`'s early return on an unreadable read** (P11). No retry and no `/status`
  fallback is added: with the sha correct there is nothing to recover from, and a second read on
  a genuine `gh` failure is the rate-limit latch's business, not this card's.
* **`ci_state`/`refuses` reading `gh run list` for a sha with no runs as `clear`** (P12). It is
  why the install path failed late instead of early; with the sha right it never arises. Making
  "no runs at all" Unknown would defer every install at a head CI has not started on — a
  different card.
* **`asf/cli.py:166` and `asf/install.py:newest_tag`** (P17). They read tag names only.
* **The two pre-existing reds of P18.** Not caused here, not fixed here.

## The design

Two functions in one file, plus the tests. The two are independent — either lands without the
other — but S-79357 is what makes a future sha-is-not-a-commit readable, so they land together.

### 1. `asf/upgrade.py` — the peel, asked for

Next to `HEX40` (`:429`), which is the other thing this module knows about the shape of a
resolved commit:

```python
#: The suffix ``git ls-remote`` puts on the extra line that names the commit an annotated tag
#: points at. An unfiltered listing prints that line unasked; a listing given ref patterns
#: prints it only for a pattern that matches it, so it is asked for by name (F-0303).
PEEL = '^{}'
```

`resolve_ref` then asks for both patterns and scans the answer with the same constant:

```python
def resolve_ref(url, ref, run=subprocess.run):
    """``ref`` as a commit, for the CI guard, ``write_pending`` and the marker (PD12): unchanged
    when it already is a 40-hex sha, else the commit ``git ls-remote <url> <ref> <ref>^{}`` names
    — the dereferenced commit on the ``^{}`` line for an annotated tag, else the line's own sha.
    ``None`` when ``ref`` matches nothing on ``url``. The peel is asked for by name: a filtered
    ``ls-remote`` prints it only for a pattern that matches it (F-0303)."""
    if not ref or HEX40.match(ref):
        return ref
    patterns = [ref] if ref.endswith(PEEL) else [ref, f'{ref}{PEEL}']
    text = _out(run, ['git', 'ls-remote', url, *patterns])
    lines = [ln for ln in (text or '').splitlines() if ln.strip()]
    deref = next((ln for ln in lines if ln.endswith(PEEL)), None)
    line = deref or (lines[0] if lines else '')
    return line.split('\t')[0].strip() or None
```

Three lines change: the docstring's command, the `patterns` line, and the literal at `deref`.
Everything after it — the `deref or lines[0]` preference, the `None` on no match — is as it was,
and now reachable.

What it looks like when it is there, for the card's own tag:

```
$ git ls-remote <url> v0.1.254 'v0.1.254^{}'
78242c1db843f77aae41d342b3c6264f68893d1a        refs/tags/v0.1.254
5c94c907ae84aca4fcce99f9804850cc87a5fb54        refs/tags/v0.1.254^{}
```

`resolve_ref` returns `5c94c907…`; `resolve_target` returns it unchanged (P7, last step); the
guard reads `repos/<slug>/commits/5c94c907…/check-runs`, which P6 measured at 9 check runs; the
move proceeds. `pipx` still receives the tag as the operator gave it (`_install`'s `pin`,
`:724-731`) — unchanged, and now the post-install comparison at `:733` is commit against commit,
so P12's false FAILED is gone.
