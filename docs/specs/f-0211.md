# F-0211 — the mechanism landed; the setting is invisible

The card asks for five things. All five are on `main`, in one commit, and that commit names this
very card:

```
f5816335c  2026-09-24  fix(briefs): the session model by kind and item class, in code —
                       S2/S3 and Task reviews run light
           Fixes: inbox/session-model-per-class-within-a-kind-e-g-s2-fix-bug-reviews-on-the-light-model.md
```

Clause by clause, against this checkout at `ee3ae8de6`:

| 2 | The class is the item's severity for Bugs, feature/task/story otherwise | `item_class` (`asf/briefs/build.py:204`), `MODEL_CLASSES` (`:55`) — `epic` too | landed |

| 4 | A plain string keeps working | `if isinstance(override, str): return override.strip()` (`:229-230`) | landed |
| 5 | doctor shows the resolved table | `model_table` (`:235`) → `doctor.model_table_lines` (`asf/doctor.py:609`) → `run()` (`:868`) | landed |
| 6 | Tests: a map resolves by severity and by type; a string is unchanged; an unknown class falls back to default | `tests/test_briefs.py:1022`, `:1016`, `:1022` and `:1035`, `:1047` | landed |

And the saving is real, not a field in a document: the label `model_for` resolves travels
`brief.model` → `worker_row(... model=brief.model ...)` (`asf/tick/step_wave.py:477`) →
`pool.Row.model` → `spawn.model_arg(row.model, cfg)` (`asf/workers/spawn.py:892`) →
`runtime` `--model <id>` (`asf/workers/runtime.py:105-106`). An S2 review is launched on the light
model today.

**So this spec does not re-specify the mechanism.** What is left is the half the landing did not
do, and it is the half the customer actually reported against — a spend setting they cannot find:

1. `docs/guide/product-config.md:81` still documents `models:` as `<kind>: heavy|light` — "which of
   the **two** model labels a job kind runs on". One label per kind, two labels, no classes. The
   map form is not in the guide at all.
2. `docs/products.example.yaml:116-125` is worse than silent, it is **wrong**: it puts `review` and
   `adjudicate` wholly under `heavy` and `correct` wholly under `light`, which is the routing as it
   was *before* `f5816335c`. Its only worked example is `review: light`.
3. `docs/guide/troubleshooting.md:79` calls the label set "`heavy` or `light`".
4. Nothing drives a `models:` map through the **product file**. Every test builds
   `product(conventions={'models': …})` in Python (`tests/test_briefs.py:1022`), so the yaml subset
   reader and `env.validate_product_text` are never asked whether the shape the documentation shows
   is a shape a product file may hold. Both forms do work — verified by hand in this checkout, P11 —
   and nothing keeps them working.

The shape of this spec is therefore: **the routing is documented in the one form that cannot rot —
the tool's own output, compared against the tool — and the yaml path the customer will copy is
pinned by a test.** No file under `asf/` changes.

## The design

### 1. The conventions-table row

`docs/guide/product-config.md:81` — the escaped pipes are the table's, and stay:

```markdown
| `models:` → `<kind>: heavy\|light\|cheap`, or a map of those by item class | per kind × class | which model label a job kind runs on, and which label each item class within that kind runs on — below |
```

`per kind × class` is the default cell, because that is what the built-in table now is (P3): unset
does not mean "one label per kind" any more.

### 2. The subsection

Inserted at `docs/guide/product-config.md:223`, before `### What approves a spec or a plan`
(D7). Its shape — the prose is the author's, the clauses are fixed:

`````markdown
### `models` — the model a session runs on, per kind and per item class

Three labels, mapped to real model ids in `~/.ASF/config.yaml` under `worker_pool.models`:
`heavy` for judgement, `light` for code, `cheap` for clerical work with a right answer. A label the
pool has no entry for refuses the launch (see troubleshooting) — except `cheap`, which falls back to
`light`, so a pool configured before the cheap tier keeps running at the price it already paid.

The built-in default is per brief kind **and** per item class. A class is the item's severity when
it is a Bug — `S1`, `S2`, `S3` — and otherwise its type: `task`, `story`, `feature`, `epic`. A brief
with no item at all — a groom day, a rebase of a branch whose card has gone — takes the kind's own
default, which is the label its whole row shows below when the row is one label.

`asf doctor` prints the resolved table for *your* product, one `model table` row per kind. With no
override it reads:

```
spec: heavy
…                        ← the 19 lines of `doctor.model_table_lines`, verbatim
delivery-code: light
```

To override, give a kind one label — which covers every class — or a map by class:

```yaml
conventions:
  models:
    coder: heavy                                              # every class of coder brief
    review: {S1: heavy, S2: light, S3: light, feature: heavy, default: light}
    fix-bug:
      S1: heavy
      default: light
```

**`default:` is a floor for every class you do not name, including the ones the built-in table
routes to `heavy`.** `review: {S2: light, default: light}` makes S2 Bug reviews light *and*
Feature-level reviews light. Name the classes you mean to keep heavy, or leave `default:` out — a
map without one keeps the built-in label for every class it does not name. Check the result with
`asf doctor` before you believe it.

A value of any other shape — a list, a number, a map with a non-string in it — is not a silent
default: the readers keep the built-in table and `asf doctor`'s `conventions` row goes red with the
key and its line in your product file.
`````

The `…` line above is this spec's own elision. The guide's block carries **all 19 lines**, verbatim
and in order, regenerated by the one-liner in §3.1 — the test asserts equality against
`doctor.model_table_lines`, so an elision inside it is red (D1).
