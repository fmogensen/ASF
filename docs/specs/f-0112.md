# F-0112 — the release channel: a product's tick installs the next ASF tag, and puts it back when the doctor goes red

On 2026-09-24 the operator asked that "when a new version of asf is available, let the session
know, so that it can update automatically". A product's operating Claude Code session cannot do
it: the approvals hook refuses `pipx install` in an auto session, and a session that reinstalled
the package it is running would tear itself. The product's launchd tick runs outside Claude Code,
so the update belongs there.

The factory already upgrades itself — but only for the one product whose repo *is* ASF's source.
`asf/drift.py` compares the installed commit against that checkout's trunk head and, under
`approvals.upgrade: auto`, runs `asf upgrade --ref <head>`; `asf/upgrade.py` carries the whole
safety apparatus around that install (the pending marker, the drain, the CI refusal, the
verification, the clock reload). A customer product has no ASF checkout, so `drift.check` returns
`None` for it and nothing happens — its `asf` stays at whatever tag `tools/install.sh` pinned
until somebody runs the installer again by hand.

This change gives every other product the second channel: not the trunk's head but ASF's newest
**release tag**, read from the remote at most once an hour, installed under a policy the product
file declares, and put back when the doctor that follows the install goes RED. The two channels
are exclusive — a product is on exactly one of them, decided by whether its repo is the factory's
own source — so nothing about ASF's own dogfooding changes.

## Decisions

### In

- **One new behaviour flag, `conventions.flags.upgrade`** — the scalar `auto | notify | off`,
  default `notify` (D1). Landed as a flag, not the top-level `PRODUCT_FIELDS` key this section
  first named (T-0431): `tests/test_env.py`'s pinned-reader test refuses a new top-level key on an
  older build, so a new switch is a flag instead (PR #675). `Product.upgrade` reads it through
  `self.flag('upgrade')`, lower-cased and whitespace-stripped, and `docs/products.example.yaml`
  documents it under `conventions.flags:`, beside the product's other flags, with one line saying
  which channel it governs. A word that is none of the three **reads as `notify`** and is a
  doctor RED (D2): a typo must never be the reason a factory installs unattended.
- **Two exclusive channels, chosen by structure and not by name.** The tick's version check
  becomes an `if` over `drift.is_factory_source(product.repo_dir)`: true — today's trunk channel,
  `drift.report(...)` under `approvals.upgrade`, byte-for-byte unchanged; false — the new
  **release channel**, `upgrade.release_report(ctx)` under `upgrade:`. No product is on both, and
  no product is named anywhere (D3).
- **The newest release, read at most once an hour, from one cache shared by every product**
  (D4): `upgrade.latest_release(url, now=…, run=…)` returns `(tag, sha)` for the greatest
  `v<major>.<minor>.<patch>` tag on `url`, out of `$ASF_HOME/state/releases.json` when that entry
  is younger than `RELEASE_POLL_S` (3600), else `git ls-remote --tags <url> 'v*'` — without
  `--refs`, so the peeled `^{}` line gives the commit the tag points at. Every read, successful or
  not, stamps `at`; a failed read keeps the previous `tag`/`sha` rather than forgetting them, so a
  dead network neither hammers the remote nor un-knows the release. `cli.latest_release()` is
  routed through the same cache, so `asf status` stops shelling out to `git ls-remote` on every
  run (P6).
- **Version comparison as a tuple, with `+N` counting as ahead** (D5).
  `upgrade.version_tuple('v0.1.62')` → `(0, 1, 62, 0)`; `'v0.1.62+7'` → `(0, 1, 62, 7)` — a
  checkout or a sha install seven commits past the tag. `upgrade.newer(latest, installed)` is a
  plain tuple `>`: `v0.1.63` is newer than `v0.1.62` and than `v0.1.62+7`; `v0.1.62` is not newer
  than `v0.1.62+7`. An installed release that cannot be read at all (`None` — an install of a bare
  sha with no build stamp) is **never** upgraded automatically: the channel prints what it could
  not read and holds (D6).
- **`notify` — the line, once per tag, in the log and in the digest.** When `newer`, the channel
  prints `UPGRADE AVAILABLE <old> → <new>` (the trunk channel's own wording,
  `asf/drift.py:151`), records the tag in the product's channel state, and sets it on the tick
  `Context` so `summary.digest` carries it as a third optional line beside `stale_line` (P11). A
  later tick that sees the same tag prints nothing. The standing statement lives in two views that
  are never once-only: `asf status`'s Version row (P6) and the doctor's new `upgrade` row.
- **`auto` — install, re-render the clocks, run the doctor.** When `newer` and nothing is
  mid-landing (P8, D7), the channel:
  1. captures the pin it is leaving — `(tag, sha)` from `cli.version_string()`'s two halves (P5);
  2. `upgrade.install(ref=<new tag>, owner=product.name, wait_s=upgrade.drain_wait_s())` — the
     whole existing protocol (P3), unchanged and unduplicated: the marker parks the other
     products' ticks, the floor drains, a red remote CI at the tag refuses, the new venv's own
     `direct_url.json` verifies the install. `DEFERRED` is not a failure and files nothing;
  3. runs `asf scheduler install --product <p>` and then `asf doctor --product <p>` **through the
     new install's own binary** (`upgrade.venv_bin()`, the `asf` beside the `python` that
     `new_install_commit` already reads), because this process still holds the old package (D8);
  4. logs `upgrade: <old> → <new>` — the card's line — **and** the sha-shaped
     `tick: ran asf upgrade (<old sha> → <new sha>), exit 0` that `asf release-readiness` mines
     (P7, D9);
  5. ends the tick, exactly as the trunk channel does after an install (P2).
- **A RED doctor rolls the install back and files a Bug.** `asf doctor` exiting non-zero means
  RED (P10). The channel then prints
  `rollback: doctor RED after <new> — reinstalling <old>`, calls `upgrade._install(<old sha>,…)`
  (the bare install: the floor already drained and the marker is already cleared — D10),
  re-runs `scheduler install` on the restored binary, and files one Bug in the record clone
  through `file_bugs` under the signature `upgrade <new tag>: doctor RED`, so a release that is
  red on two products, or on two ticks, bumps one card rather than minting three (D11). The Bug is
  committed and pushed by the channel itself (`shadow.commit_local` + `shadow.push`, P12), because
  the tick ends before its record step. Severity `S1`: the product cannot take the next release
  until somebody reads it.
- **A doctor row, `upgrade`**, on every product: the policy, the installed release, the newest
  known release and the age of the cache entry — `auto · v0.1.62 → v0.1.63 available (read 12m
  ago)`. RED only for a policy word that is not one of the three (D2), or when the last release
  install was rolled back and the newer tag is still the newest (the product is stuck on a
  release it cannot take).
- **Documentation**: the new key in `docs/products.example.yaml`, and a `## The release channel`
  section in `docs/guide/upgrading.md` — the three policies, the hour, what a rollback writes, and
  the sentence that a product whose repo is ASF's own source is on the trunk channel instead.

### Out

- **Changing the trunk channel.** `asf/drift.py`'s comparison, `approvals.upgrade`, the batching
  interval (`upgrade.min_interval_min`), the `Urgent: yes` override and the pending-marker
  protocol are untouched. This card adds a second question ("is there a newer *release*?") in
  front of the same install.
- **Putting ASF's own product on the release channel.** It is the factory's source; it upgrades to
  trunk heads on purpose, several a day, and that is how a release gets tested before it is cut.
  An operator who wants otherwise edits nothing today — there is no switch, and inventing one
  would make the dogfooding path optional.
- **Widening the drain to worker sessions.** The floor `upgrade.other_ticks()` holds is ticks and
  background harvests (P3). A live worker session running `asf brief` under a package swap is a
  real hazard, and an old one — it is the trunk channel's hazard too, every day, and fixing it
  here would change the existing path for one product's benefit. The card's own condition
  (mid-landing) is implemented; the rest is its own card.
- **Rolling the *record* back.** A rollback restores the package, never the record, the clocks'
  content or anything the new release already wrote. A release whose schema migration cannot be
  undone is `asf upgrade`'s schema table's problem (`asf/upgrade.py:row`), and the filed Bug is
  what says so.
- **A second release source.** The tags read are ASF's own, off the url the running install came
  from (P4). A product does not get to point the channel at a fork; that is operator config
  (`$ASF_REPO_URL`) and already exists.
- **Notifying the running Claude Code session directly.** The card's mechanism is the log and the
  digest, which is what the operating session already reads. No message is pushed into a session.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | A top-level scalar `upgrade: auto\|notify\|off`, default `notify` | a map (`upgrade: {policy: auto}`), or a fourth `approvals` class | the card writes the scalar; a map buys nothing with one value, and an approvals class would make the decision the hook's, which is exactly what F-0108 established the tick cannot ask a session to do |
| D2 | An unrecognised word reads as `notify` **and** is a doctor RED | refuse the product load, or read as `off` | refusing the load takes the whole product down over a typo in a new key; reading as `off` silently stops the notifications the default promises. Loud and least-privileged is the pair |
| D3 | The channel is chosen by `drift.is_factory_source(repo_dir)` | a fourth policy word (`trunk`), or a product-file switch | the two channels answer different questions and only one of them can work per product; making it structural means no product file can get it wrong, and `check_generic.sh` stays satisfied — nothing names a product |
| D4 | One cache for every product, `$ASF_HOME/state/releases.json`, keyed by url | one cache per product's state dir | every product asks the same remote the same question; per-product caches multiply the hourly budget by the number of products, and ten products on 5-minute clocks is 120 `ls-remote` an hour |
| D5 | `(major, minor, patch, past)` tuples, `+N` as the fourth element | string compare, or `packaging.version` | `v0.1.9` vs `v0.1.62` is the string compare's classic wrong answer; `packaging` is a dependency this package does not have, and `+N` is not a PEP 440 local version but ASF's own "commits past the tag" |
| D6 | An unreadable installed release holds, and says so | assume the static `__version__` and compare | `__version__` is never bumped per release (P5, `docs/guide/upgrading.md`) — comparing against it would read as `BEHIND` forever and reinstall on every tick |
| D7 | Mid-landing = `occupancy(...)['landing']` non-empty | count live sessions, or the harvest lock | it is the card's own word and P8 is the one place the record answers it; a live session that has pushed nothing loses nothing to a package swap between ticks |
| D8 | The post-install `scheduler install` and `doctor` run through the new venv's `asf` | call `scheduler.install()` / `doctor.run()` in-process | this process has the *old* package's modules loaded and its metadata cached; calling in-process would render the old clocks and run the old doctor, and would be the exact B-0135 tear the install protocol exists to prevent |
| D9 | Both lines are logged — the card's `upgrade: <old> → <new>` and the sha-shaped `tick: ran asf upgrade (…), exit 0` | only the card's line | P7: `release-readiness`'s upgrade criterion matches hex shas in that exact sentence. A tag-only line would silently zero the `min_upgrades` count that gates cutting the next release |
| D10 | The rollback calls `upgrade._install` directly | `upgrade.install(owner=…)` again | the marker/drain protocol has already run and cleared; re-entering it would write a second pending marker for a *downgrade* and park every product's ticks for it |
| D11 | One Bug per `(release tag, doctor RED)` signature, bumped | one Bug per rollback | the same bad release hits every product on the channel and every tick until somebody acts; `file_bugs` already bumps a count once a day against a signature (P12) |
| D12 | `cli.latest_release()` is routed through the new cache | leave it, and cache only the channel's reads | it is the same question against the same remote; leaving two readers means `asf status` can print a newer tag than the tick acts on, which is the confusing half of a race for no gain |

## The design

### `asf/env.py` — the key, as landed (T-0431, PR #675)

Not a top-level `PRODUCT_FIELDS` key: `tests/test_env.py`'s pinned-reader test refuses a new one
on an older build, so the switch is a flag instead, read the way every other
`conventions.flags.*` switch is.

```python
#: what ``conventions.flags.upgrade`` may say; anything else reads as UPGRADE_DEFAULT and is a
#: doctor RED. Not a top-level PRODUCT_FIELDS key (T-0431): the pinned-reader test
#: (tests/test_env.py:PinnedReader) refuses a new one, so a new switch is a flag (PR #675).
UPGRADE_POLICIES = ('auto', 'notify', 'off')
UPGRADE_DEFAULT = 'notify'
```

```python
    @property
    def upgrade(self):
        """``conventions.flags.upgrade`` — how this product's tick takes a new ASF *release*
        (F-0112): ``auto`` installs it, ``notify`` (the default) says so once per tag, ``off``
        says nothing. A word that is none of the three reads as ``notify`` and is a doctor RED.
        Read only for a product whose repo is not the factory's own source — that one is on the
        trunk channel, under ``approvals.upgrade``."""
        word = str(self.flag('upgrade') or UPGRADE_DEFAULT).strip().lower()
        return word if word in UPGRADE_POLICIES else UPGRADE_DEFAULT

    @property
    def upgrade_declared(self):
        """The raw ``conventions.flags.upgrade`` value — ``None`` when absent, the literal
        string when present, unnormalised. For the doctor row that must quote a typo back;
        :attr:`upgrade` cannot, since it has already folded the typo into the default."""
        return self.flag('upgrade')
```

### `asf/upgrade.py` — the release channel

The module already owns "reinstall the package at a named ref, safely" (P3). It gains the section
that answers *which* ref, for a product that is not the factory's source.

```python
#: the newest release tag is read from the remote at most this often, for every product at once
RELEASE_POLL_S = 3600
#: ``v<major>.<minor>.<patch>``, optionally ``+<commits past it>`` (asf.cli's release string)
RELEASE_RE = re.compile(r'^v(\d+)\.(\d+)\.(\d+)(?:\+(\d+))?$')


def releases_path():
    """``<ASF_HOME>/state/releases.json`` — ``{<url>: {'tag', 'sha', 'at'}}``, one entry per
    remote, shared by every product (D4)."""


def latest_release(url, now=None, run=subprocess.run):
    """``(tag, sha)`` of the greatest ``v<major>.<minor>.<patch>`` tag on ``url``, from the cache
    while its entry is younger than :data:`RELEASE_POLL_S`, else ``git ls-remote --tags <url>
    'v*'`` — the peeled ``^{}`` line is the commit an annotated tag points at. Every attempt
    stamps ``at``; a read that fails keeps the entry's previous ``tag``/``sha``. ``(None, None)``
    when nothing was ever read."""


def installed_release():
    """``(tag, sha)`` of the running install: the tag ``tools/install.sh`` pinned (``cli._release``
    — a git install's ``requested_revision``, else a checkout's ``git describe``, else the build
    stamp) and the commit it was built from (``drift.installed_commit``). ``tag`` is ``None`` when
    the install records no release at all."""


def version_tuple(text):
    """``(major, minor, patch, past)`` of a release string, or ``None``. ``v0.1.62`` →
    ``(0,1,62,0)``; ``v0.1.62+7`` → ``(0,1,62,7)`` — seven commits past the tag, and so *ahead*
    of it (D5)."""


def newer(latest, installed):
    """True when release ``latest`` is past release ``installed``. False when either is unreadable
    — an unknown install is never upgraded on a guess (D6)."""


def mid_landing(product):
    """``[(item, branch)]`` of this product's items pushed and waiting on the lane
    (:func:`asf.workers.lifecycle.occupancy`'s ``landing``) — the sessions an install must not
    land under (P8). ``[]`` when the ledger cannot be read: an unreadable ledger holds, it never
    clears."""
```

The channel state, one file per product, `<state_dir>/upgrade-release.json`:

```json
{"notified": "v0.1.63",
 "last": {"from": "v0.1.62", "from_sha": "3ae93bb…", "to": "v0.1.63",
          "at": 1790000000.0, "result": "installed"}}
```

`result` is `installed` or `rolled-back`. `notified` is the notify-once stamp (the tag, not a
timestamp: a tag notified stays notified until a newer one is cut).

```python
def release_report(ctx, out=print, now=None, run=subprocess.run):
    """The version check for a product that is not the factory's source: the newest ASF release
    against the installed one, under the product's ``upgrade:`` policy. Returns
    ``'none' | 'notified' | 'held' | 'installed' | 'rolled-back' | 'failed'`` — the tick ends
    after the last three, whose install replaced the package under it.

    Never raises: a version check has never been allowed to stop a tick (asf/drift.py:139)."""
```

Its shape, in order:

| Step | What it does |
| --- | --- |
| 0 | `policy = product.upgrade`; `off` → print the `factory:` line and return `'none'` |
| 1 | `url = repo_url(run)`; `(tag, sha) = latest_release(url, now, run)`; `(old, old_sha) = installed_release()` |
| 2 | print `factory: asf <old> @ <old_sha7> · release <tag> · <current\|BEHIND\|release unreadable>` — one line every tick, on every policy, so a log always says which release is running |
| 3 | `newer(tag, old)` false → return `'none'` |
| 4 | `policy == 'notify'` → if the channel state's `notified` is already `tag`, return `'none'`; else print `UPGRADE AVAILABLE <old> → <tag>`, set `ctx.upgrade_line` to the same string, write `notified`, return `'notified'` |
| 5 | `policy == 'auto'`, `mid_landing(product)` non-empty → print `upgrade: held — <n> item(s) mid-landing (<item> on <branch>, …)`, return `'held'` |
| 6 | `rc = install(ref=tag, owner=product.name, wait_s=drain_wait_s(), run=run)`; `DEFERRED` → return `'held'` (the install said why itself); non-zero → print `upgrade: FAILED <old> → <tag> (exit <rc>)`, record it, return `'failed'` |
| 7 | print `upgrade: <old> → <tag>` and `tick: ran asf upgrade (<old_sha> → <sha>), exit 0` (D9); `_new_asf(['scheduler', 'install', '--product', product.name], run)` |
| 8 | `_new_asf(['doctor', '--product', product.name], run)`; exit 0 → record `installed`, return `'installed'` |
| 9 | RED: print `rollback: doctor RED after <tag> — reinstalling <old>`; `_install(old_sha or old, run, out)`; `_new_asf(['scheduler','install',…])`; `file_red_bug(ctx, old, tag, doctor_output)`; record `rolled-back`; return `'rolled-back'` |

```python
def venv_bin(name='asf', run=subprocess.run):
    """``<PIPX_LOCAL_VENVS>/asf-factory/bin/<name>`` — the *new* install's own binary. This
    process holds the old package's modules and metadata, so everything that must see the new one
    is a subprocess of it (D8), exactly as :func:`new_install_commit` already does for python."""


def _new_asf(argv, run=subprocess.run, out=print, timeout=600):
    """Run the new install's ``asf <argv>``; returns ``(rc, output)``. A binary that is missing or
    will not start is ``(2, <why>)`` — treated as RED, so a broken install rolls back."""
```

### `asf/tick/tick.py` — the fork

```python
    with locks.record('version check', wait_s=0) as ok:
```

### `asf/tick/summary.py` — the digest

## Records

- **`$ASF_HOME/state/releases.json`** — `{<url>: {'tag', 'sha', 'at'}}`. The hourly tag cache,
  shared by every product and by `asf status`. Deleting it costs one `ls-remote`.
- **`$ASF_HOME/state/<product>/upgrade-release.json`** — `{'notified': <tag>, 'last': {'from',
  'from_sha', 'to', 'at', 'result'}}`. `result` is `installed` or `rolled-back`. The notify-once
  stamp and the last outcome the doctor row reads. Per product: two products take the same release
  independently, and each says so once.
- **The tick log** (`$ASF_HOME/logs/tick-*.log`), one `factory:` line every tick and, on a change:
  - `UPGRADE AVAILABLE <old> → <new>` — once per tag, under `notify`;
  - `upgrade: <old> → <new>` — the card's line, under `auto`;
  - `tick: ran asf upgrade (<old sha> → <new sha>), exit 0` — the sha-shaped line
    `asf release-readiness` counts (P7, D9);
  - `upgrade: held — <n> item(s) mid-landing (…)`;
  - `rollback: doctor RED after <new> — reinstalling <old>` — matched by
    `release._ROLLBACK_RE`, so a rollback lands in the upgrade-safety criterion as a rollback and
    holds the next release gate.
- **The tick digest** (B-0087) — the `UPGRADE AVAILABLE` line as a third optional row beside the
  record-stale line, so the operating session reads it without opening the log.
- **One Bug in the product's record**, signature `upgrade <tag>: doctor RED`, severity S1, parent
  `conventions.default_bug_epic`. Bumped, not duplicated, on every later RED of the same release.
  Committed and pushed by the channel itself (the tick ends before its record step).
- **No migration, no new install-time file.** The pin the comparison reads is the one pipx already
  recorded (P5). A product that declares no `upgrade:` key gets `notify`, which writes nothing
  until a new release is cut.
