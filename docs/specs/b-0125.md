# B-0125 — spec: what the approvals hook costs under load

Item: B-0125 — approvals hook errors look like refusals (S1). Epic: E-0001.
Plan: `docs/plans/b-0125.md`. The fix itself — the wording, the log, the tick line — is specified
there. This file answers the card's other clause:

> Investigate the likely causes under load (the hook re-reads config and product files on every
> call; concurrent writes to `approvals.jsonl`; a slow start of the installed binary).

It is written so the next intermittent refusal is diagnosed against numbers rather than
re-investigated from scratch. Every figure below was measured in this worktree on 2026-09-25,
Python 3, darwin 27.0.0, against a temp `ASF_HOME`.

## §1 What the hook does on every call

`run_hook` (`asf/approvals.py:777`) returns 0 immediately when there is no `ASF_JOB` (D4). Inside
a factory session, `_enforce` (`:796`) does this on **every** `Bash`, `Write`, `Edit`,
`MultiEdit` and `NotebookEdit` call:

| step | where | what it reads |
| --- | --- | --- |
| `env.load_product` | `:808` | the product YAML, parsed **and re-validated** every call |
| `item_of_job` | `:809` | the whole of `sessions.jsonl`, folded to `{job: latest run}` |
| `amendable.write_target` | `:811` | the amendable-set match, in memory |
| `classify` | `:832` | the recognisers, in memory |
| `is_granted` → `_fold` → `read` | `:848` | the whole of `approvals.jsonl` — **only** when a grantable class matched |
| `append` | `refuse`, `:493` | one `O_APPEND` line |

The last row is the one that matters for the common case: when `classify` returns nothing,
`_enforce` returns 0 at `:833` and **the ledger is never read**. An ordinary `ls` does no ledger
I/O at all. This is why a growing `approvals.jsonl` is not the first suspect.

## §2 The three candidate causes, measured

### 2.1 Re-reading config and product files — real, and it grows with the session registry

Per-call cost of the whole allow path (200 calls, warm interpreter), varying `sessions.jsonl`:

| lines in `sessions.jsonl` | ms/call |
| --- | --- |
| 1 | 3.07 |
| 100 | 8.68 |
| 1 000 | 52.48 |
| 5 000 | 208.07 |

It is linear in the registry, not in anything the call itself carries. `item_of_job` (`:596`)
goes through `lifecycle.latest` → `runs` → `fold(read_lines(path))`
(`asf/workers/lifecycle.py:202-208`), which parses every line of the file to keep the last run
per job. `sessions.jsonl` is append-only and never compacted, so this cost only rises over an
install's life. At 5 000 lines every tool call in every session pays 208 ms before it is allowed.

`env.load_product` (`asf/env.py:656-666`) additionally opens the YAML twice — once to load, once
to re-read the text for `validate_product_text` — on every call. It is a small file; it is the
registry fold that dominates.

Nothing here refuses anything. It makes the hook slow, which matters for 2.3.

### 2.2 Concurrent writes to `approvals.jsonl` — not the cause

`append` (`:493-495`) is `open(path, 'a')` — `O_APPEND` — and one `f.write` of one line.
Measured: 8 spawned processes × 60 lines each, at three payload sizes spanning the 8 KB cap
`_intended_change` (`:669-672`) puts on a captured `patch`:

| `patch` size | lines on disk | parse | torn |
| --- | --- | --- | --- |
| 100 B | 480 | 480 | 0 |
| 4 000 B | 480 | 480 | 0 |
| 8 192 B | 480 | 480 | 0 |

No interleaving at any size the hook can actually produce. And even if a line were torn, `read`
(`:498-514`) catches `json.JSONDecodeError` and skips it, so a tear can only ever *lose* a
record — a hold that never opens, or a `resolved` that never closes. It cannot manufacture a
refusal. Concurrent ledger writes are ruled out as the cause of B-1372's refused `ls`.

The reverse direction is worth one line of warning: because a bad line is skipped silently, a
ledger corrupted some other way degrades quietly rather than loudly.

### 2.3 A slow start of the installed binary — the first-order cost

The hook is a fresh process per tool call. Measured end to end, `python3 -c "import
asf.approvals"` — the import alone, before `run_hook` does any work:

| run | wall |
| --- | --- |
| 1 | 978 ms |
| 2 | 1 344 ms |
| 3 | 1 105 ms |

Of that, `-X importtime` attributes ~700–810 ms to `asf.approvals`' own import tree, dominated by
`asf.amendable` (434 ms cumulative) → `asf.hooks` (229 ms) and `asf.briefs.build` (200 ms) →
`asf.workers.stall` → `asf.metrics.metrics` (80 ms), plus `_hashlib` (87 ms) and `dataclasses`/
`inspect` (84 ms).

So a single ordinary tool call costs the session on the order of **1 second of hook before any
policy is evaluated**, and 2.1 adds to it. Under load — many sessions, each with a per-call
hook — this is where a timeout becomes reachable, and a hook the runtime kills on a timeout is
exactly the failure this card is about: indistinguishable, before the fix, from a refusal.

## §3 The conclusion, and what is deliberately not fixed here

- The refused `ls` is not explained by the ledger (§2.2) and not by policy: it is an internal
  failure — a crash, a transient read, or a kill on a slow start (§2.3) — that the old wording
  dressed as a refusal. That is what `docs/plans/b-0125.md` fixes, and it is the whole of this
  card's S1.
- The performance findings are **not** fixed here. They are genuine and they are separable:
  - the ~1 s import is a change to how the hook is dispatched (a lazier import graph, or a
    resident hook), which is a design change with its own blast radius;
  - the linear `item_of_job` fold needs either a compacted or an indexed `sessions.jsonl`, which
    changes a file other components read.

  Either inside an S1 about wording would widen it past recognition. They are recorded here so
  the next session has the numbers and can raise them as their own cards.
- What this card *does* change about diagnosis: every such failure now writes its traceback to
  `~/.ASF/logs/approvals-hook.log` (rotated at 4 MiB), and a run of them says so once in the
  tick. The next occurrence is readable instead of inferred.
