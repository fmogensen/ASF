# F-0342 — a move must move the floor the product actually runs

`asf upgrade --product <p> --to <sha>` is the one way a pinned product changes the code it runs
(`asf/upgrade.py:900-924`). It installs the target venv beside the running one, reads positive CI
evidence on the exact sha, drains the merge queue, holds the floor quiet, boots the clocks out,
writes the pin (`state/<p>/install.json`), **re-renders the clocks from it**, installs the hooks,
smokes what it wrote and resumes. Every step but one is about the product's floor as ASF 0.1
defined it: a `clocks:` block in the product file, rendered by `asf scheduler install --product
<p>` (`asf/scheduler.py:1630-1643`).

ASF 0.2 replaced that floor. A product on the kernel runs **two launchd jobs** — `asf.<p>.kernel`
(`asf kernel tick`) and `asf.<p>.kernel-watch` (`asf kernel watch`) — written and loaded only by
`asf.kernel.host` from the interpreter its caller hands it (`asf/kernel/host.py:76-93`,
`:361-397`). The move has never been told. `grep -c kernel asf/upgrade.py` is **0** (P2).

So the move's one job — move the pin — is the one thing it does not do on such a product, and it
fails in whichever of two ways the product file happens to choose:

* the 0.1 `clocks:` block is still in the file, its clocks paused since the cutover: the move
  rewrites **those** plists at the new pin, loads none of them, reports `moved <p> to <v>` — and
  both kernel jobs still run the venv they ran before. The pin on record is a label only (P14b).
* the `clocks:` block is gone: `asf scheduler install --product <p>` refuses with `NEEDS
  OPERATOR: products/<p>.yaml declares no clocks` and exits **2**, so the move puts the pin back
  and resumes. The move cannot succeed at all, and its refusal asks for a block the product does
  not need (P14a).

Underneath both, three more gaps of the same kind. The move's quiesce cannot see a kernel tick at
all — `MOVE_PATTERN` matches `-m asf.cli tick`, never `-m asf.cli kernel tick` (P1) — so a move
boots the floor out from under a tick mid-apply, which is the exact accident
`asf.kernel.host.tick_lock` exists to prevent (`host.py:404-412`). The smoke replays every plist
that happens to sit under the product's label prefix (P7, P15), so a retired 0.1 plist naming a
pruned venv fails a move that has nothing to do with it. And `asf scheduler install --product
<p>`, run on a kernel product while its jobs are loaded, counts both of them as undeclared and
**retires them** — bootout plus `rm` of the plist (P16). Inside the move that one does not bite,
and only because the move boots them out first.

This card is one rule, applied everywhere the move touches the floor: **the move's floor is the
set of jobs the product is actually running, each re-rendered at the pin by the installer that
owns it.** The kernel's two jobs are the kernel's to render; a 0.1 clock is the scheduler's; a job
the move did not quiesce is nobody's to write.

## Decisions

### Preconditions — measured in this worktree at `21ddb0489`, 2026-10-10

Each was measured from the repo root; both scripts are in `## Acceptance tests` (`the
preconditions, re-measured`) so a reviewer can replay every number below.

* **P1 — the move's quiesce cannot see the kernel's own processes.** `MOVE_PATTERN`
  (`upgrade.py:933`) matched against a plist's real argv: `-m asf.cli tick --product alpha
  --steps x` **True**; `-m asf.cli kernel tick --product alpha` **False**; `-m asf.cli kernel
  watch --product alpha` **False**. `product_processes` (`:1109-1126`) is the only reader, and
  `floor_busy` (`:1129-1142`) is built on it, so on a kernel product the floor reads quiet while
  the tick runs.
* **P2 — `asf/upgrade.py` does not know the kernel exists.** `grep -c kernel asf/upgrade.py` is
  **0**: no job name, no module, no import, in 1801 lines.
* **P3 — the kernel's own quiet signal is a lock the move does not read.** `floor_busy` reads one
  state file, `harvest.lock` (`:1135-1138`). The kernel tick holds
  `state/<p>/kernel.lock` for its whole apply (`asf.kernel.loop.LOCK_FILE`, `loop.py:40`,
  `lock()` at `:52-65`), and `asf.kernel.loop` has no reader for "is it held" — only `lock()`,
  which raises `Locked`. `asf.harvest.harvest.try_lock_held` (`harvest.py:1069-1075`) is the
  shape such a reader has here.
* **P4 — the move's install step is the whole-file 0.1 install.** `MoveOps.install_clocks`
  (`upgrade.py:1310-1317`) calls `cmd_scheduler` with `scheduler_command='install'`,
  `clock=None` — every declared clock rendered and written, the paused ones among them
  (`_launchd_install` writes the plist and declines to load it, `scheduler.py:913-931`), and the
  retire pass over every loaded label the file does not declare (`:1634-1640`).
* **P5 — a kernel job is not a 0.1 clock and cannot be adopted as one.**
  `clock_of_plist('asf.alpha.kernel', {'ProgramArguments': [… 'kernel', 'tick', '--product',
  'alpha'], 'StartInterval': 120}, 'alpha')` is **None** (`scheduler.py:1323-1351`: no `--steps`,
  no `--daily`), so `adopt` (`:1398-1411`) declares nothing for it and the "declares no clocks"
  refusal of P14a stands after adoption has run.
* **P6 — the smoke has no no-op form for either kernel command.** `noop_command`
  (`scheduler.py:780-794`) returns **None** for `-m asf.cli kernel tick --product alpha` and for
  `-m asf.cli kernel watch --product alpha`; for a 0.1 tick it returns the same argv with
  `--manifest`. A clock with no no-op form is still smoked for its interpreter, env, cwd and
  tools (`:830-840`) — a `--shadow` clock is in that case today.
* **P7 — the smoke replays every plist under the product's prefix.** `smoke(product, cfg, run,
  timeout)` takes no job argument; `paths` comes from `product_labels(name, cfg)`
  (`scheduler.py:813-815`), which is a glob of `~/Library/LaunchAgents/asf.<p>.*.plist`
  (`:1041-1051`). An unreadable plist, a missing interpreter, or a tool off that plist's `PATH`
  is a `failure` (`:842-856`), and a failure rolls the move's pin back (`upgrade.py:1507-1527`).
* **P8 — `SMOKE_TIMEOUT_S` is 60s; `host.SHADOW_TIMEOUT_S` is 900s.** The kernel tick's own
  read-only form is `asf kernel tick --product <p> --dry-run` (`host.run_dry`, `:196-211`) and
  the shadow preflight gives it fifteen minutes. `asf kernel tick --product <p> --help` exits
  **0** and prints its usage.
* **P9 — the kernel's jobs can already be rendered for any interpreter.** `host.jobs(product,
  cfg=None, python=None)` takes the interpreter and defaults to `sys.executable`
  (`host.py:76-93`); `host.install(product, dry_run, cfg, python, out, accept_diff, run)` is its
  one caller, and it adds the shadow preflight, the kernel lock and `prune_venvs`
  (`:361-397`). `host.TICK` is `'kernel'` and `host.WATCH` is `'kernel-watch'` (`:60-61`).
  `installs.interpreter(venv)` is `<venv>/bin/python` (`installs.py:176-177`), and
  `scheduler.pinned_venv(<p>)` is the pin's venv (`scheduler.py:318-329`).
* **P10 — nothing anywhere answers "is this product on the kernel".** No public name in
  `asf.kernel.settings` or `asf.kernel.host` contains `kernel` as a predicate; the `kernel:`
  block cannot answer it either, because every key of it has a default
  (`settings.read(None)` fills all nineteen sections, `settings.py:208-377`) — a 0.1 product may
  carry the block and never have cut over, and a cut-over product may carry no block at all
  (`tests/kernel/test_host.py:91` builds exactly that product).
* **P11 — what a move does today on a kernel product, end to end** (the second script; a temp
  `ASF_HOME`, a fake `launchctl`, two fake venvs, no network):
  * **P14a**, no `clocks:` block — `asf scheduler install --product alpha` prints `NEEDS
    OPERATOR: products/alpha.yaml declares no clocks — add a clocks: block (see
    docs/products.example.yaml)` and returns **2**. In the move that is
    `upgrade.py:1491-1497`: the pin is written back to what it was, one `NEEDS OPERATOR` line,
    exit 1. **The pin cannot move, ever, on this product.**
  * **P14b**, the 0.1 `clocks:` block still in the file with `tick` paused — rc **0**;
    `asf.alpha.tick.plist` is **rewritten**, its interpreter the *new* pin's, not loaded (the
    pause record holds it); and `asf.alpha.kernel` and `asf.alpha.kernel-watch` **still name the
    old venv's interpreter**. The move goes on to print `moved alpha to <v>`.
  * **P15** — `product_labels('alpha')` is `['kernel', 'kernel-watch', 'tick']`: the smoke
    replays the resurrected 0.1 plist too.
  * **P16** — `retire_candidates('alpha', ['asf.alpha.tick'])` with all three labels loaded is
    `['asf.alpha.kernel', 'asf.alpha.kernel-watch']`. `asf scheduler install --product alpha`
    would boot both out and delete their plists (`uninstall`, `scheduler.py:936-955`).
* **P12 — a bare resume brings a retired floor up.** `asf scheduler resume --product <p>` with no
  `--clock` resumes every pause record *and* every label with a plist on disk
  (`scheduler.py:1467-1470`), and `resume` loads the plist as it finds it — it never re-renders
  (`:1104-1124`). So every paused 0.1 plist the move keeps fresh at the current pin is one
  command away from running a second factory beside the kernel.
* **P13 — the record holds no Story for F-0342**, and this session's block is `S:124905-124954`.

### In

* **`asf/upgrade.py` — the floor, read and split.** `KERNEL_CLOCKS = (host.TICK, host.WATCH)`;
  the quiesce list the move already computes (`:1428`) split into the kernel's jobs and the 0.1
  clocks; one refusal when both halves are non-empty (D4); two lines naming the floor it found
  and the retired clocks it is leaving alone; the dry run's step list written from the split.
* **`asf/upgrade.py` — `MoveOps.install_floor(product_name, clocks)`** in place of
  `install_clocks`: the kernel's jobs through `host.jobs(product, cfg, python=installs.
  interpreter(scheduler.pinned_venv(<p>)))` + `scheduler.install(job)`; each 0.1 clock through
  `asf scheduler install --product <p> --clock <c>`, one clock per call. Called from the forward
  path and from both rollback paths (`:1490-1527`), which therefore put the kernel's jobs back at
  the restored pin for free.
* **`asf/upgrade.py` — the quiesce covers the kernel.** `MOVE_PATTERN` gains `kernel tick` and
  `kernel watch`; `floor_busy` gains one line for a held `state/<p>/kernel.lock`.
* **`asf/upgrade.py` — `MoveOps.smoke(product_name, clocks)`** passes the floor through to the
  scheduler's smoke.
* **`asf/kernel/loop.py` — `locked(state_dir)`**: True while another process holds the product's
  kernel lock. A read, never a hold.
* **`asf/scheduler.py` — `smoke(product, cfg, run, timeout, clocks=None)`**: `clocks`, given,
  narrows the replay to those clock names' plists.
* **`asf/scheduler.py` — `noop_command`** maps `kernel tick` and `kernel watch` to the same argv
  with `--help` appended (D6).
* **`asf/scheduler.py` — `retire_candidates`** never names the kernel's two jobs (D7).
* **Tests**: one new module `tests/test_upgrade_kernel_floor.py`, five classes, one per Story; the
  `clocks` argument on `tests/test_upgrade.py`'s `FakeOps.install_clocks`/`smoke`; the two
  measurement scripts of `## Acceptance tests` as the module's own fixtures.

### Out

* **Retiring a kernel product's 0.1 clocks.** The move leaves every paused clock's plist, pause
  record and product-file entry exactly as it found them, and says so in one line. Deleting a
  plist an operator can still read is not a side effect a `--to <sha>` should have, and there is
  no per-clock retire command to call (`asf scheduler uninstall` takes `--host` only,
  `scheduler.py:1526-1528`). What the operator should do with them is a doctor row, and that is
  its own card.
* **The cutover itself.** Nothing here moves a product onto the kernel, pauses its 0.1 clocks,
  rewrites its product file or removes its `clocks:` block. The move reads the floor it finds.
* **`asf kernel install`'s own behaviour.** Its shadow preflight, its `tick_lock` and its
  `prune_venvs` are unchanged and the move calls none of them (D3). `host.jobs` keeps its
  signature and stays the one renderer of those two jobs.
* **Running the kernel tick's own command in the smoke.** `--dry-run` is the real no-op form and
  it is allowed fifteen minutes (P8); the smoke allows sixty seconds and a failure rolls the pin
  back. A dry run in the smoke would time out and turn every move into a rollback — the defect
  this card is fixing, by another route. `--help` is what the smoke gets (D6), and the plan diff
  stays `asf kernel install`'s.
* **A 0.1 `asf watch` process.** `MOVE_PATTERN` has never matched the 0.1 keep-alive
  (`asf.tick.watch`, `cli.py:905-907`) and still does not. It is not a clock, it holds no lock
  the move reads, and nothing about this card changes what it is.
* **The shared, unpinned upgrade** (`asf upgrade` with no `--product`), its pending marker, its
  deferral and `reload_clocks` (`upgrade.py:1-95`, `:717-895`). A pinned product is never parked
  by it (`marked_products`, `:163-168`) and a kernel product on the kernel's own venv family is
  not a product it installs.
* **`asf scheduler install --product <p>` on a kernel product as an operator command.** After
  D7 it no longer retires the kernel's jobs, which is the part that can destroy a floor; that it
  still writes and loads a 0.1 floor beside the kernel, and still refuses a product with no
  `clocks:` block, is the cutover's business and the doctor's, not the move's.
* **Any new config key.** The floor is read off disk; nothing about it is a knob.

### Preconditions the work depends on

1. `asf.kernel.host` imports only the standard library at module level (`host.py:46-58`), so
   `asf.upgrade` and `asf.scheduler` can import it inside a function with no cycle — the idiom
   both modules already use for every cross-module read.
2. A booted-out job keeps its plist: `bootout_clocks` calls `launchctl bootout` only
   (`scheduler.py:1097-1102`), and only `uninstall` removes a plist (`:936-955`). So the kernel
   jobs' definitions are on disk throughout the move, and "this product is on the kernel" can be
   read at any point in it.
3. `scheduler.install(job)` writes and loads any job definition, whoever rendered it
   (`:891-911`), and `_launchd_install` declines to load a label with a pause record
   (`:913-931`). The kernel's jobs carry no pause record of their own except the one this move
   writes, which its `finally` clears (`upgrade.py:1530-1536`).
4. `cmd_scheduler` with `args.clock` set renders and installs exactly that clock and skips the
   retire pass (`scheduler.py:1577-1586`, `:1634`), and refuses with a named line and exit 2 when
   the file declares no such clock (`:1578-1582`).
5. `MoveOps` is the only seam the move's tests replace (`tests/test_upgrade.py:77-120`): every
   launchd, plist, venv and settings effect goes through it, so each Story below is testable with
   no host state.
6. `_quiesced_switch` already restores the pin and re-installs on a non-zero install rc and on a
   failed smoke (`upgrade.py:1490-1527`), and resumes exactly the clocks the attempt paused in
   its `finally` (`:1530-1536`). One installer swapped in covers the forward path and both
   rollbacks.
7. `installs.write(<p>, sha, venv, previous=…)` records the previous venv in `install.json`
   (`installs.py`), and `host._pins()` reads every product's `install.json` when it prunes
   (`host.py:116-132`) — so a venv a `--rollback` needs is never pruned. The move calls no prune
   of its own (D3).
8. `pinned_venv` reads `install.json`, so the kernel jobs rendered after `installs.write` take
   the new pin and the ones rendered after a restore take the old one, with no sha threaded
   through the call (`scheduler.py:318-329`).
9. An `flock` taken non-blocking and released at once is a read of whether another process holds
   it; a tick that starts inside that window finds the lock taken and skips its turn, which is
   already the documented behaviour of a reinstall holding it (`host.py:404-412`).

## The design

### 1. `asf/upgrade.py` — the floor a move moves

The module comment over the per-product move (`:900-924`) gains the kernel's floor, and two names
go beside `MOVE_PATTERN`:

```python
#: the clock names of the kernel's own two launchd jobs (:mod:`asf.kernel.host`): a floor the
#: kernel renders and owns, never a clock of the product file's ``clocks:`` block. A move splits
#: the floor it quiesces on this set and hands each half to its own installer (F-0342)
KERNEL_CLOCKS = ('kernel', 'kernel-watch')      # asf.kernel.host.TICK, .WATCH


def on_kernel(product_name, cfg=None):
    """True when ``product_name``'s floor is the kernel's: a job definition for its tick
    (``asf.<p>.kernel``) is on disk. Read off disk, not out of the product file: every key of the
    ``kernel:`` block has a default, so the block is no evidence either way (P10). A booted-out
    job keeps its definition, so this answer holds throughout a move."""
```

`KERNEL_CLOCKS` is asserted equal to `(host.TICK, host.WATCH)` by a test rather than imported at
module level, so the constant stays readable where it is used and cannot drift (P1 of the test
module).

`move` computes the quiesce list as it does today and splits it:

```python
    quiesce = [c for c in ops.clock_names(product_name) if c not in ops.paused(product_name)]
    kernel = [c for c in quiesce if c in KERNEL_CLOCKS]
    legacy = [c for c in quiesce if c not in KERNEL_CLOCKS]
    if kernel and legacy:
        out(f'NEEDS OPERATOR: {product_name} runs the kernel floor '
            f'({", ".join(kernel)}) and its 0.1 clock(s) {", ".join(legacy)} are still loaded — '
            f'two floors on one product, and a move cannot leave both right. Pause them: '
            f'`asf scheduler pause --product {product_name} --clock {",".join(legacy)} '
            f'--reason "the kernel floor replaced it"` — then run the move again')
        return 2
    clocks = quiesce
```

The refusal sits where the split is, before the `steps` list and before `pipx install`: nothing is
paused, nothing is written, nothing is downloaded, and `--dry-run` refuses the same way.

With the floor read, the move says what it found — one line, and one more only when there is
something it is deliberately not touching:

```python
    if kernel:
        out(f'upgrade: {product_name} runs the kernel floor ({", ".join(kernel)})')
        retired = sorted(set(ops.clock_names(product_name)) - set(quiesce) - set(KERNEL_CLOCKS))
        if retired:
            out(f'upgrade: its 0.1 clocks ({", ".join(retired)}) are paused — this move writes '
                f'no plist of theirs and smokes none of them')
```

and the step list of `--dry-run` names the installer each half gets, in place of today's single
`asf scheduler install --product <p>` line:

```
  6. record ~/.ASF/state/<p>/install.json: 1111111 <venv>; previous 0000000 <venv>
  7. render kernel, kernel-watch from <venv>/bin/python (asf.kernel.host) and load them
  8. asf scheduler install --product <p> --clock <c>   (one per 0.1 clock quiesced; none here)
  9. asf hooks install --product <p>
 10. smoke: kernel, kernel-watch — each plist's interpreter imports asf.cli and loads the
     product, gh auth status, git/claude/toolchain --version under the plist env, and each
     clock's own command in its no-op form (any failure: roll back)
```

### 2. `asf/upgrade.py` — `MoveOps.install_floor`, by owner

`install_clocks` is replaced by one method that takes the floor:

```python
    def install_floor(self, product_name, clocks):
        """Re-render exactly the floor the move quiesced, from the pin on record (rc; 0 is fine).

        The kernel's two jobs (:data:`KERNEL_CLOCKS`) are rendered by their own writer
        (:func:`asf.kernel.host.jobs`) from the pinned venv's interpreter and written through
        :func:`asf.scheduler.install` — the move never grows a second renderer of them (D1, D3).
        Every other name goes through its own command, one clock per call (``asf scheduler
        install --product <p> --clock <c>``): the whole-file install would write the plists of
        clocks this move never quiesced and retire every loaded label the file does not declare
        (D2)."""
```

* **The kernel half.** `host.jobs(env.load_product(<p>), cfg, python=installs.interpreter(
  scheduler.pinned_venv(<p>)))` renders both jobs, and the method installs the ones the move
  quiesced — normally both, and exactly the subset when only one was loaded. `pinned_venv` reads
  `install.json` (P8/8), so the forward path renders from the sha just written and a rollback
  renders from the sha just restored, with nothing threaded through the call. A `scheduler.
  install` line containing `failed` is rc 1; a `SchedulerError` or `ConfigError` out of the
  render is rc 2 with a `NEEDS OPERATOR` line, which the caller already turns into a restored pin.
* **The 0.1 half.** One `cmd_scheduler(Namespace(scheduler_command='install', product=<p>,
  clock=<c>, …))` per name; a non-zero rc from any of them is the method's rc.
* **Order.** The kernel's jobs last, so that on a product with both halves (which D4 refuses, and
  which a future mixed state could still produce) the factory's own tick is the last thing loaded.

The three call sites in `_quiesced_switch` (`:1490`, `:1520`, and the forward path's
`rc = ops.install_clocks(...)`) become `ops.install_floor(product_name, clocks)`, and the smoke
becomes `ops.smoke(product_name, clocks)`. No other line of `_quiesced_switch` moves: the pin
restore, the hooks, the host clocks, the `finally` that resumes exactly what it paused, and the
rollback's own `NEEDS OPERATOR` line are what they are, and the rollback now puts the kernel's
jobs back at the pin that was running because it goes through the same installer.

`MoveOps.smoke` grows the argument and passes it on:

```python
    def smoke(self, product_name, clocks=None):
        """``(ok_lines, failures)`` of :func:`asf.scheduler.smoke` over ``clocks`` — the floor
        this move moved, never a plist a retired floor left on disk (D8)."""
```

### 3. `asf/upgrade.py` — the quiesce covers the kernel's processes

```python

                r'|-m asf\.tick\.step_harvest( |$)')
```

Measured against the five argv shapes a plist or a dispatcher produces: the 0.1 tick, `ci queue

```python

```

with the reader in `asf/kernel/loop.py` beside `lock`:

```python
def locked(state_dir):
    """True while another process holds ``state_dir/kernel.lock`` — a tick is inside its apply.

    A read, never a hold: the ``flock`` is taken non-blocking and released at once, so a tick
    that starts inside that window finds the lock taken and skips its turn, exactly as it does
    for a reinstall holding it (:func:`asf.kernel.host.tick_lock`)."""
```

A missing lock file is False. An `OSError` opening one that exists is True — a lock the move
cannot read is a lock it must not step over.

## Records

No card is minted, no item's state moves, no note is appended, nothing is written to the record
and nothing is pushed. The change alters **which files a move writes**, and adds one line to what
it prints.

* **`state/<p>/install.json`** — the pin, unchanged in shape and in when it is written
  (`installs.write`, before the floor is rendered; restored to the previous record on a failed
  install or a failed smoke). This card changes nothing about it; it is the fact the floor is
  now rendered *from* (D1, P8/8).
* **`~/Library/LaunchAgents/asf.<p>.kernel.plist` and `…kernel-watch.plist`** — rewritten by the
  move, from the pinned venv's interpreter, with the `kernel:` block's intervals and the floor's
  `ASF_HOME`/`HOME`/`PATH`, and loaded. **This is the write the move did not make**, and the whole
  of "the pin cannot move".
* **`~/Library/LaunchAgents/asf.<p>.<clock>.plist` for a 0.1 clock the move quiesced** — written
  one clock at a time, as the whole-file install wrote it. For a 0.1 clock the move did **not**
  quiesce — a paused one, the retired floor of a kernel product — **nothing is written at all**,
  where today the plist is rewritten at the new pin (P14b). No plist is ever deleted.
* **`state/<p>/paused-clocks.json`** — the move's own pause records, one per job it quiesced
  (`reason: upgrade`, with its pid), cleared by the `finally` that resumes them. A pause record
  the move did not write is never touched, and its clock's plist is not touched either.
* **`state/<p>/upgrade-draining.json`, `state/<p>/upgrade-pending.json`** — the drain and hold
  markers, unchanged.
* **`state/<p>/kernel.lock`** — **read** only, and only to answer whether a tick is applying. The
  flock is taken non-blocking and released at once; the file is created by the kernel, never here.
* **The move's own output** — the floor line (`<p> runs the kernel floor (kernel,
  kernel-watch)`), the retired-clocks line when there are any, the two-floor `NEEDS OPERATOR`
  refusal, the `kernel.lock is held` line among the floor's busy lines, and `scheduler.install`'s
  own `wrote`/`bootstrapped` lines for the two jobs. `logs/tick-<p>-kernel.log` and
  `logs/kernel-<p>.log` are the jobs' own, written by the jobs, not by the move.

A refused move (D4, a red CI, a drain that times out) writes nothing but its own lines, and a
rolled-back one leaves `install.json` and all four plists exactly as it found them.
