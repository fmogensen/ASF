# F-0283 — the hook ran whatever asf was installed last

A product's `pre-commit` (the index render) and `pre-push` (redact) `exec`
`$HOME/.local/bin/asf`. On the factory host that path was pipx's link to the shared `asf-factory`
venv — v0.1.106+4 — while the product ran 0.1.217. So every commit and every push of that
product was gated by months-old code, whatever version the product had been moved to, and a fix
that landed in the product's own build never reached its hooks. Seen 2026-10-07 on a product: the
record and code repos' `.githooks` both `exec`ed that link, and record pushes were still refused
for 78 findings after the redact fix (F-0273) had landed in the pinned build.

Half of this is already closed, and it closed hours ago. F-0121's spec-amend landed
`asf/dispatch.py` at `f2dd68af5` (2026-10-08 01:56): `~/.local/bin/asf` is now meant to be a
dispatcher — a POSIX `sh` script that resolves the product and `exec`s *that product's* pinned
`bin/asf` from `state/<p>/install.json`. `asf hooks install` writes it, moves a pipx link aside to
`<path>.pipx-link`, points every hook it writes at it, relinks every agent home, and refuses with
a `NEEDS OPERATOR` line when a pinned product's hooks would name anything else; `asf upgrade
--product` runs the same install; `asf doctor` has two rows that go red on a path that is not the
dispatcher. None of that is re-specified here. It is the precondition.

What is left is the part that does not depend on an operator having just run a command. The
hook's own `exec` is blind: it names a *path*, and the file behind that path can stop being the
dispatcher at any moment — `pipx install --force git+<url>@<sha>` (`asf/upgrade.py:391`, and the
install script) recreates pipx's own link there and nothing notices. `dispatch.install` has
exactly **one** caller in the tree (`asf/hooks.py:669`), reached only from `asf hooks install` and
from a product move, so between operator commands the path can sit wrong for months — which is
the window the card measured. Worse, the pre-launch refresh moves hooks the *other* way on every
single launch: `ensure_account_hooks` resolves `asf` from `PATH` and `merge` overwrites the
dispatcher command it finds with it, so a launch quietly undoes what `asf hooks install` wrote.
And the session shim's trunk check falls back to `command -v asf` by design — the unpinned build,
named outright.

And one hook names no asf at all. The record's own `pre-commit` and `pre-push` are `asf init`'s,
and both run **bare `asf`** — `asf check --staged` (the card's `pre-commit`, "the index.json
render") and `exec asf redact --<name>` — resolved from `PATH` at hook time, which is the shared
install by definition and never a pin. `asf hooks install` does not move them: `init_hook_upgrade`
answers first and returns init's own body, `stale_own_hook` finds no `GIT_HOOK_MARKER` and
declines, and the file is left byte-identical (P17) — while `hooks.verify` and `asf doctor` are
*already* red for it and already name `asf hooks install --product <p>` as the remedy (P18). A red
row whose remedy is a no-op, for as long as the product lives.

So this spec makes the invariant hold without an operator in the loop: **the asf a hook runs is
checked at hook time, the dispatcher is re-asserted every tick, every hook asf writes names it,
and a hook that is not the pin's is loud instead of silent.**

### In

1. **The hook checks what it is about to run.** `_git_hook_body` gains one `sh` guard: while the
   product is pinned, a candidate `asf` that does not carry the dispatcher's marker line is
   skipped with one line on stderr, and the chain goes on to the next candidate — the
   repository's own `tools/checks/redact.sh` — refusing only when nothing is left to scan with.
2. **A hook that is not this build's body is visible.** `hooks.verify` and `asf doctor`'s
   `redaction hooks` row go red for a hook that is asf's but is not the body this build writes,
   so the one case a body change cannot reach on its own — a tracked `.githooks` the approval gate
   withheld (P8) — says so instead of sitting silently stale.
3. **The dispatcher is re-asserted every tick.** `dispatch.reassert()`, called from `cmd_tick`'s
   existing preflight: a pipx link that took the path back is undone within one pass instead of at
   whatever operator command comes next.
4. **Every hook asf writes names the dispatcher.** One `hooks.which_asf()` used by `install`, the
   `--dry-run` plan and the pre-launch refresh, so a launch stops moving the account's `approvals`
   and `unpushed` hooks onto the shared install (P6).
5. **The session shim's trunk check runs the pin or nothing.** The `command -v asf` fallback goes,
   and an asf at `$HOME/.local/bin/asf` that is not the dispatcher refuses the push rather than
   answering the trunk question from another build.
6. **The record's own hooks name the dispatcher too.** `asf hooks install` rewrites the bare `asf`
   of an `asf init`-written hook to the dispatcher's path — the card's `pre-commit`, the record's
   `asf check`, included — so the remedy `hooks.verify` and the doctor row have been naming all
   along actually clears them (P17, P18, P20).

### Out

- **The dispatcher itself is not re-specified.** Its resolution order, `install.json`, `pin_cli`,
  the `.pipx-link` backup, `link_factory_cli`, the `NEEDS OPERATOR` on a foreign file — all
  F-0121's, all on the trunk, all unchanged (P2).
- **pipx keeps owning the `asf` console script.** Installing the shared factory under a
  `--suffix` so it can never take `~/.local/bin/asf` again is the larger fix and a change to how
  the factory is installed, not to how its hooks run. The re-assertion makes the window one tick
  wide, which is what the card's months-long window asks for.
- **No new `asf doctor` row.** `cli dispatcher` (P10) already carries the standing state of the
  path and already names the remedy; this spec only widens `redaction hooks` to the hook's body.
- **No new command, no new config key, no new state file, no new convention.**
- **The approval gate is not relaxed.** A tracked `.githooks` hook stays withheld until
  `touch_security` is answered (P8). This spec makes that withholding *visible*; it does not write
  through it, and `--approve` keeps being the one way past it.
- **The redaction gate's own logic is untouched.** `asf redact`, its findings, the
  `Redaction: unchecked` trailer and the landing re-scan are not in this change.
- **No pin check inside the running CLI.** See C1: the build that runs is the stale one.
- **The `prepare-commit-msg` / `commit-msg` halves of the session shim are untouched** — they run
  `git interpret-trailers` and `awk`, never asf, so no build can be the wrong one.
- **`asf init`'s template keeps naming bare `asf`.** A record is initialised before any pin
  exists, on a host that may have no factory at all; bare `asf` is the only thing `asf init` can
  write, and `asf hooks install` is what moves it onto the dispatcher afterwards (C14).
- **The tick does not install hooks.** Re-asserting the dispatcher (In 3) rewrites a file the
  operator owns; rewriting a product's *tracked* `.githooks` is a change to its source and the
  approval gate's question (P8). A record whose hooks are still init's stays red in `asf doctor`
  until `asf hooks install` is run — with, now, a remedy that clears the row.

## The design

### 1. The hook body's guard — `asf/hooks.py`

`_git_hook_body` takes one more argument and bakes two lines plus a function. For a pinned
product (`pin_required=True`) it renders:

```sh
#!/bin/sh
# written by asf hooks install — the redaction gate (F-0075)
# the asf a hook runs must be the dispatcher while <p> is pinned (F-0283)
pin_marker='# asf dispatcher — written by `asf hooks install`'
warned=
asf_pinned() {
    [ -x "$1" ] || return 1
    [ -z "$pin_marker" ] && return 0
    head -n 3 "$1" 2>/dev/null | grep -qF "$pin_marker" && return 0
    [ -n "$warned" ] || echo "asf: $1 is not asf's dispatcher, so it is not <p>'s pinned build (F-0283) — skipped; run: asf hooks install --product <p>" >&2
    warned=1
    return 1
}
if asf_pinned "<asf_path>"; then exec "<asf_path>" redact --<name> --product <p>; fi
if asf_pinned "$HOME/.local/bin/asf"; then exec "$HOME/.local/bin/asf" redact --<name> --product <p>; fi
# no asf here (a cloud container): the repository's own check, else refused
top=$(git rev-parse --show-toplevel 2>/dev/null)
if [ -n "$top" ] && [ -x "$top/tools/checks/redact.sh" ]; then exec "$top/tools/checks/redact.sh" --<name>; fi
echo "asf: REDACTION REFUSED (<name>) — no asf that is <p>'s build and no tools/checks/redact.sh here: nothing can scan this <commit|push> for names or secrets, so it is refused (a pushed branch is public before any landing re-scan). Install asf, or add tools/checks/redact.sh." >&2
exit 1
```

`pin_marker` is `shlex.quote(dispatch.MARKER)` — single-quoted, so the marker's own backticks are
literal (C2). For an unpinned product the one difference is `pin_marker=''`, which makes
`asf_pinned` equivalent to today's `[ -x … ]` (C5): one body shape, one baked value.

`ensure_git_hooks` computes `pin_required` once per call, from `os.path.isfile(dispatch.record_path(product.name))` — the same reading `_pinned` already does — and passes it to
`_git_hook_body`, to `stale_own_hook` and through `_own_upgrade`, so a hook written before a pin
is rewritten with the guard at the first install after the move and a hook written for a pin that
has since been removed is rewritten without it. Nothing else about the write changes: a foreign
hook is still left alone and refused, a withheld path is still skipped, `_pin_refusal` still
stands (C6).

The recogniser functions are not changed: `is_git_hook_ours`, `hook_entry`,
`init_hook_upgrade`, `staged_check_upgrade` and `add_staged_flag` all read the new body correctly
as it stands (P11).

    ``(False, None)`` — nothing to do — when the path does not exist (a host with no factory CLI

### 6. The record's own hooks name the dispatcher — `asf/hooks.py`

```python
def init_cli_upgrade(text, name, asf_path):
    """``text`` with the bare ``asf`` of each command line replaced by ``asf_path``, for a hook
    :mod:`asf.init` wrote (its :data:`asf.init.INIT_MARKER`) that still resolves ``asf`` from
    ``PATH`` — whatever was installed last, never the product's pin (F-0283: the record's
    ``pre-commit`` ran its ``asf check`` and its ``asf redact`` through a months-old shared
    install). None when ``text`` is not one of asf init's, when no line names a bare ``asf``, or
    when ``asf_path`` is not the dispatcher (:func:`asf.dispatch.is_ours`): a hook is moved onto
    the pin, never off it."""


def hook_upgrade(text, name, asf_path, product_name):
    """The text hook ``name`` should now hold, or None — the one chain :func:`ensure_git_hooks`
    writes and :func:`plan` reports, so the two cannot disagree (P21, C16)."""
    up = (init_hook_upgrade(text, name) or staged_check_upgrade(text, name)
          or _own_upgrade(text, name, asf_path, product_name))
    return init_cli_upgrade(up if up is not None else text, name, asf_path) or up
```

The command word is matched at the start of a line, `exec` allowed before it, and only the bare
name — `^[ \t]*(?:exec[ \t]+)?asf(?=[ \t])` — so init's `asf check --staged || exit 1` and its
`exec asf redact --pre-commit` are rewritten and every other line is left exactly as it stands:
`top="$(git rev-parse --show-toplevel)"`, the `ASF_HOOK_RUNNING` guard, the `cd`, and every `#`
comment, init's own included. The path is written `shlex.quote(asf_path)` — the quoting
`dispatch.render` writes and `hook_entry` already reads, single quotes included (P20, C2).

Composing rather than adding a fourth `or` is what makes one pass enough: an older init hook that
`init_hook_upgrade` brings up to the current body has that body rewritten in the same write, so a
second `asf hooks install` changes nothing — the promise `ensure_git_hooks` already makes (P20).

`plan` reports the row as `upgrade` through the same `hook_upgrade`, so a tracked `.githooks`
asks the `touch_security` question once and `--approve` is the one way past it, exactly as for
every other hook row (P8). Nothing else moves: `init.PRE_COMMIT` and `init.PRE_PUSH` are not
edited (C14); `hook_entry`'s rule for a bare name is not edited either (P19) — after the rewrite
there is no bare name left in the line to read; and a hook an operator wrote is still left
untouched and still refused (C15).
