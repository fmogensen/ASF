# F-0094 — the row that breaks an Epic into Features

The feeder's ladder begins one rung too high. Every row in `asf/feeder/rows.py` starts from a
card that already exists: `CARD → SPEC` wants a decided Feature, `PLAN → CODE` wants a Task of an
approved plan, `BUG → FIX` wants a filed Bug. `UNDECIDED → DECIDE` is the only row that speaks for
a card nothing has started, and it too needs the card to be there first.

Nothing proposes the Features of an Epic. An Epic can be decided, carry a full description and a
prototype link, and have zero Features beneath it — and the feeder emits **no row at all** for it,
not a launching one and not a waiting one. It is not held, not starved, not over budget: it is
invisible. The tick will never start work on it, and no view says why (P1, measured).

This card is: **a decided Epic with no open Features gets one session whose whole job is to draft
its Feature cards, filed through the intake the groom already types — so ranking, the decision
gate and the approval matrix all still apply, unchanged.**

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | **The session files intake cards with `asf inbox`, one call per Feature.** | Writing an answers file the next tick applies, the way `groom-clerk` does; calling `asf new feature` directly. | `asf inbox` is already the one command the approval matrix points a session at for "I have an idea that is not my work" (P8), it publishes to the record by itself, and it mints nothing — so the card's "they go through the inbox" needs no new applier, no new file format and no new record writer. `asf new feature` would put a decided-looking card straight into the record and skip the intake's own typing, which is the gate the card says must still apply. |
| C2 | **Each drafted card carries a `parent: <epic id>` line and an `## Acceptance` checklist.** | Leaving intake to infer the Epic from shared title words. | `infer_parent_epic` picks the open Epic sharing the most title words and asks a question when none does — for a Feature drafted *from* an Epic the parent is known exactly, and guessing it is a question the clerk then has to answer. The acceptance list is what makes the card usable by the `CARD → SPEC` session that follows, and it is what stops a card whose wording carries a defect word from being typed as a question (P9). |
| C3 | **The gate is "no *open* Feature beneath the Epic", not "no Feature at all".** | Zero Features ever. | The card's own words. An Epic whose Features are all delivered but which is still open is exactly the case that needs the next slice proposed; an Epic that is done should be Resolved, and a Resolved Epic never matches (the row requires the Epic itself open). |
| C4 | **The brief is given the titles of the Epic's already-finished Features, and told not to draft them again.** | Letting the session read the Epic's card and work it out. | C3's cost is the duplicate: an Epic on its second slice has delivered Features whose titles the session would otherwise re-propose. The titles are in the index the brief builder already holds, so this is one context key, not a new fact. |
| C5 | **`EPIC → FEATURES` is a `CAPPED_KIND`.** | Firing until the Epic has a Feature; a bespoke "once per Epic" counter. | Two loops are possible and the cap closes both: a session that files nothing (a delivered Epic, C3) and a session whose cards intake left as questions. At the attempt limit the row becomes `STALEMATE → ADJUDICATE`, where the answer is "close this Epic" or "here are its Features" — an operator-visible row instead of a silent relaunch. A bespoke counter is a second thing that can disagree with `attempts`. |
| C6 | **The row is gated on `approvals.groom: auto`, like every other groom-derived row.** | Always on. | The card asks for exactly this ("gated like other groom-derived work"), and it is also what makes the lane coherent: with the groom off, `process_inbox` never runs, so the drafted cards would pile up in the intake directory as files nobody types. One gate, already read by `groom_rows` (P13), no new setting. |
| C7 | **An Epic already named by a pending intake card gets no row** — `intake_parents`, a new caller-supplied input built by `step_wave.plan_inputs` from the record's intake directory. | Deriving it from the index; leaving the one-tick window to the attempt cap. | The window is real: the session ends, the cards sit in the intake directory, and the Epic still has no open Feature until the groom's next intake pass — so without this the row fires again and a second session drafts the same Features. The feeder may not read a directory (P11), and `groom_state` is the settled precedent for a fact the caller supplies. It is a *separate* input, not a `groom_state` key, because `groom_state` is `None` until a groom file exists and this fact does not depend on one. |
| C8 | **`intake_parents` defaults to `()` and the gate degrades to the index alone.** | Requiring it. | Every existing `plan_rows` caller keeps working unchanged, and a test or a bare `asf next` over an index with no record beside it still plans. The cost of not having it is a duplicate the attempt cap bounds (C5), never a wrong row. |
| C9 | **Ordered by the Epic's own rank, tier 2, one row per Epic.** | A tier of its own; ahead of the groom rows. | "The Epic's rank orders it" is the card's own sentence. Tier 2 is where all discretionary new work sits, and `feature_order` already puts the Epic's rank first — a row with no Feature sorts on the Epic's rank directly. |
| C10 | **The kind joins `HELD_KINDS['features']`.** | Its own hold class; exempt from the budget. | It is new work under an Epic (P4), so `feeder.hold: features` should stop it with the rest and an Epic past its `budget_usd` must not start its own expansion — an Epic that is over budget proposing more Features is the exact opposite of what F-0052 is for. One list, two gates, no way for them to disagree. |
| C11 | **The brief is a new kind, `epic-features`, on the HEAVY model.** | Reusing `groom` or `adjudicate`. | Drafting the Features of an Epic from its description is the most judgement-heavy thing in the lane and its template says something no existing template says. Reusing a kind would make one template serve two jobs and one golden brief unprovable. |
| C12 | **The brief lands in its own Story, before the feeder's.** | One Task for the whole card. | The template is in the amendable set, so a Task writing it is `CONSOLE → AMEND` — the operator's session (P15) — and the `KINDS` entry must land *with* the template or `tests/test_briefs.py` is red for a kind with no template (P14). Ordering the amend Story first means the trunk never carries a row kind whose brief cannot be built. |
| C13 | **How many Features a session may draft is stated in the brief, not in a convention.** | A `conventions.feeder.features_per_epic` key. | A number no code reads is not a setting; the brief is where the session's instructions live, and the template is amendable, so the operator can change it without a release. |
| C14 | **Nothing about the intake, the groom, `derive`, `process_inbox` or the decision gate changes.** | Teaching intake a "drafted by a session" shape. | The whole point of routing through the inbox is that the cards arrive by the path the record already trusts. A drafted card is indistinguishable from one an operator filed, and that is the property that keeps ranking and approval applying. |

## The design

### §1 `asf/feeder/rows.py` — the row

The module docstring's row table gains one entry, between `UNDECIDED → DECIDE` and
`GROOM → ADJUDICATE`:

```
    EPIC → FEATURES        a decided, open Epic with no open Feature beneath it: one session
                           drafts its Feature cards from the Epic's description and files them
                           with ``asf inbox``, so the groom's intake types them and every gate
                           (the decision, the approval matrix, the Epic's rank) still applies.
                           Gated on ``approvals.groom: auto``; an Epic a pending intake card
                           already names gets none (``intake_parents``)
```

The constant, beside `UNDECIDED`:

```python
EPIC_FEATURES = 'EPIC → FEATURES'
```

and it joins both gate lists:

```python
CAPPED_KINDS = frozenset({CARD_SPEC, STARVED_SPEC, STARVED_PLAN, PLAN_CODE, CONFLICT, STALE,
                          EPIC_FEATURES})

HELD_KINDS = {'features': (CARD_SPEC, STARVED_SPEC, STARVED_PLAN, PLAN_CODE, SPEC_PLAN,
                          DIRECT_BUILD, REPLAN, EPIC_FEATURES),
              'bugs': (BUG_FIX,)}
```

`BUDGET_HELD_KINDS` is derived from `HELD_KINDS` (P4), so the budget hold follows for free.

The row function, beside `undecided_rows`:

```python
def epic_rows(items, product, busy, intake_parents=()):
    """EPIC → FEATURES (F-0094): one session per decided, open Epic that has no open Feature
    beneath it — the rung the feeder never had. Every other row starts from a card that already
    exists; this one proposes the cards.

    The session writes no code and no document: it drafts Feature cards from the Epic's
    description and files them with ``asf inbox``, so the groom's intake types them
    (:func:`asf.groom.inbox.process_inbox`) and they arrive undecided, under the Epic, with
    their acceptance list — ranked by ``feature_order`` and decided by the decision gate like
    any other card. Nothing about that path changes here.

    Gated on ``approvals.groom: auto``, like every other groom-derived row (:func:`groom_rows`):
    with the groom off, intake never runs and a drafted card is a file nobody reads.

    ``intake_parents``: the Epic ids a card **already in the intake directory** names as its
    parent — the caller's fact, since the feeder reads no filesystem
    (:func:`asf.tick.step_wave.plan_inputs`). Between the session ending and the groom's next
    intake pass the Epic still has no open Feature, and without this the row would fire again
    and draft the same Features twice. A caller that passes none gets the index's gate alone,
    and :data:`CAPPED_KINDS` bounds the repeat.
    """
    if not groom_policy.groom_auto(product):
        return []
    pending = set(intake_parents or ())
    out = []
    for e in sorted(ix.of_type(items, 'epic'), key=lambda e: (ix.rank(e), e['id'])):
        if e.get('decided') is not True or not is_open(e) or e['id'] in busy or e.get('blocked'):
            continue
        if e['id'] in pending:
            continue
        features = [it for it in ix.subtree(items, e) if it['type'] == 'feature']
        if any(is_open(f) for f in features):
            continue
        done = len(features)
        out.append(Row(
            tier=2, kind=EPIC_FEATURES, item_id=e['id'], feature_id='', action=LAUNCH,
            brief_kind='epic-features', branch=branch_for(product, 'epic', e['id']),
            reason=(f"decided {ix.age(e.get('stage_since'))}, no open Feature"
                    + (f" ({done} delivered)" if done else ' ever')
                    + ' — nothing proposes its Features')))
    return out
```

Three things are load-bearing. `decided is not True` is the same identity test
`undecided_rows` uses, so a card carrying the string `"true"` is not decided here either. The
subtree scan (not `children`) is what makes the gate true for an Epic whose Features hang under it
through anything; `PARENT_TYPES` puts a Feature directly under an Epic today, and the scan costs
nothing and cannot go stale if that changes. And `feature_id=''` is deliberate — this row is about
an Epic, and `GROOM → ADJUDICATE` already ships a launching row with an empty `feature_id` (P6).

In `candidates()`, the signature gains the input and the rows are appended beside the undecided
ones — after the Feature rows, so an Epic's expansion never sorts ahead of work already in flight:

```python
def candidates(index, product, inflight, attempts=None, occupancy=None, groom_state=None,
               landed_shas=None, decision_limit=None, intake_parents=()):
    ...
    rows += undecided_rows(items, product, busy, decision_limit)
    rows += epic_rows(items, product, busy, intake_parents)
```

`plan_rows` takes the same keyword and passes it straight through. `key()` needs no change: a row
with an empty `feature_id` already falls to `order = (ix.BIG, ix.BIG, '~')`. That would sort every
Epic row last within tier 2 — which is wrong for C9, so `key()` gains one clause beside the groom
clause:

```python
        if r.kind == EPIC_FEATURES:
            # an Epic's own row has no Feature: order it on the Epic's rank directly, so a
            # product that ranks an Epic first gets its expansion first (F-0094 C9)
            epic = items.get(r.item_id) or {}
            return (r.tier, 1, (0, 0), ix.rank(epic), ix.BIG, r.item_id, 5, seq)
```

The tuple is the same width and the same types as the Feature branch's, element for element: the
phase is pinned at 1 (start, not finish), so every Task row of every Feature goes ahead of any
Epic expansion; `(0, 0)` is what every phase-1 row already carries, so an Epic's row interleaves
with Feature rows on rank rather than sinking below all of them; the Epic's rank stands where
`feature_order` puts an Epic's rank, and `ix.BIG` in the Feature-rank slot puts an Epic's own row
behind any Feature row of the same Epic. `finish_phase` is not consulted for it.

### §2 The caller's fact — which Epics already have cards waiting

`asf/groom/inbox.py`, beside `question_lines`:

```python
def intake_parents(root, intake_dir=None):
    """The Epic (or other item) ids the cards **currently** in the intake directory name as
    their ``parent:`` — the fact `asf.feeder.rows.epic_rows` cannot derive from ``index.json``.
    A card that has been typed is gone from this directory (``process_inbox`` moves it to
    ``done/``), so an id stops being named the moment its Feature exists.

    File-name order, deduplicated, uppercased. A directory that is not there is no ids.
    """
    d = os.path.join(root, intake_dir or DEFAULT_INTAKE_DIR)
    if not os.path.isdir(d):
        return frozenset()
    out = set()
    for name in sorted(os.listdir(d)):
        path = os.path.join(d, name)
        if not name.endswith('.md') or not os.path.isfile(path):
            continue
        with open(path, encoding='utf-8') as f:
            text = f.read()
        body, _question = _split_question(text)
        parent = (parse_inbox_file(body).headers.get('parent') or '').strip().upper()
        if parent:
            out.add(parent)
    return frozenset(out)
```

`asf/tick/step_wave.py`, in `plan_inputs` — the one place every planner reads (P12):

```python
    return {'attempts': attempts(product), 'occupancy': occupancy(product),

            'intake_parents': _intake_parents(product, root),

def _intake_parents(product, root):
    """F-0094: the parents of the cards waiting in the record's intake directory, for the
    EPIC → FEATURES row. Never raises — a record that cannot be read plans without the fact,
    and the attempt cap bounds the duplicate it costs."""
    from asf.groom import inbox as inbox_mod
    try:
        return inbox_mod.intake_parents(root, product.conventions.intake_dir)
    except OSError:
        return frozenset()
```

It is read whether or not `groom_auto` is on: the fact is about files, the gate is
`epic_rows`' own (C6).

### §3 The brief — `epic-features`

## Records

Nothing new is written to the record by this change itself. What the lane it opens writes is
already-shipped machinery:

- **`<intake_dir>/<slug>.md`, one per drafted Feature** — written by `asf inbox` and committed to
  the record with the message `record: inbox <file>` (P8). `# <title>`, a `parent: <epic id>`
  line, the description, an `## Acceptance` checklist. Nothing marks it as session-drafted: that
  is C14, and it is what keeps every downstream gate applying to it unchanged.
- **The Feature card** — written by the groom's next `process_inbox` pass, not by this change:
  `parent: <epic id>`, `decided: false`, the acceptance list, and a History line
  `created (inbox) — shape: default → feature`. The intake file moves to `<intake_dir>/done/<slug>.md`
  with a `→ F-xxxx` first line (P10).
- **`<state>/sessions.jsonl`** — the ordinary launch and end lines for job `epic-features-e-0004`,
  item `E-0004`. This is what `attempts` counts, and so what C5's cap and the stalemate read.
- **The feeder's rows** — one more row kind in `asf next`, the wave table and the status cell, with
  no schema change: `Row` gains no field, and `feature_id` is `''` for it.
- **What is not written**: no new typed field on an Epic, no new file format, no new approval
  class, no new convention key (C13), and no id minted by the session (P16, `asf inbox` mints
  nothing).
