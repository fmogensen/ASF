# F-0114 — an upgrade migrates itself, an older install still reads the files, and every release is tested into HEAD

Sixty-five releases were cut in five days. Nothing in the suite installs any of them and upgrades
it, so "does v0.1.7 → HEAD still work" is answered by the first customer who tries it. The card
names five gaps. Reading the code at `f2523fce8` narrows three of them, widens one, and turns one
into something worse than it was written:

- **The halt the card is afraid of does not exist.** `schema.require` — the exit-3, NEEDS OPERATOR
  refusal every writing command is supposed to make first — has **no caller in `asf/`** (P1). A
  release that bumped `SCHEMA_VERSION` today would not stop the factory; it would run every
  writing command against an unmigrated record, silently. The guide promises the refusal
  (`docs/guide/upgrading.md`, "Schema migrations"). The code does not make it. That is the worse
  failure, and it is in scope: the card's acceptance asks for a tick that migrates itself rather
  than halting, and a tick that migrates itself needs the halt to exist for the migrations it
  *cannot* run.
- **The config half of the check never fires either.** `config_version()` reads
  `config.yaml['schema_version']`, absent means "no opinion", and `_set_config_version` writes the
  key with a `re.sub` that only rewrites a line already there (P3). No shipped `config.yaml`,
  example or sample carries it (P4), so no install has ever been stamped and none ever will be.
- **The strict reader is the product file, not the operator config.** `config.yaml` has no
  declared field table at all — only `worker_pool` and `cloud` are checked (P5) — so it is already
  tolerant. `products/<p>.yaml` is checked against `PRODUCT_FIELDS` and an unknown **top-level**
  key refuses the load, which kills every command and collapses the doctor to one red row (P6,
  P7). The guide already documents this as the rollback hazard and names a workaround per key
  (`conventions.auth_env`, `docs/guide/upgrading.md`, "Rolling back").

After this change: a release that raises the schema migrates every product on the way in, and a
tick that finds a record below the package's version runs the migration itself and logs
`migrate: schema a → b`; `config.yaml` and `products/<p>.yaml` carry a version of their own and
field renames are migrations with a backup; a file written by a newer `asf` is read with a warning
instead of refused; a migration that cannot be additive says so, snapshots first, and
`asf upgrade --to <ref>` puts the snapshot back; and a CI job installs released tags into a temp
HOME, ticks them, upgrades to HEAD and proves doctor, tick and record all green — including two
products at different versions sharing one `config.yaml`.

### In

- **`schema.require` gets its callers, and a migration it can run itself is run, not refused.**
  Every migration declares whether it is *additive* — a record at `n-1` that a package at `n` can
  still read and write. The refusal now fires only for a non-additive gap; an additive one is
  migrated in place by whoever noticed it.
- **The tick migrates itself.** At the start of `_run_steps`, under the record lock and before any
  step, a record below the package's `SCHEMA_VERSION` is migrated (drained, bounded) and one line
  goes to the tick log: `migrate: schema a → b`. In flight past the bound, the tick says so and
  goes on with its steps (an additive gap) or stops with the operator line (a non-additive one).
- **Every upgrade path migrates on the way in.** `upgrade.cmd_upgrade` — the single funnel of P11 —
  runs `schema-migrate --drain` for every installed product after a successful install, before it
  prints the table. `tools/install.sh` gets it for free; F-0112's auto path, when it lands, calls
  the same function.
- **`config.yaml` and `products/<p>.yaml` carry `schema_version`,** with a version number of their
  own (`CONFIG_VERSION`) and their own `CONFIG_MIGRATIONS`. A rename or removal of a config field
  is a migration entry, applied on upgrade, after a backup of every file it rewrites.
- **A renamed field keeps being read.** A `CONFIG_MIGRATIONS` entry declares `renames` and
  `removes`; the renames stay readable — old name honoured, new name winning — for at least one
  minor version, and every read of an old name produces one deprecation line in the doctor. The
  two hand-written pairs of P19 move into that table, and `doctor._capacity_deprecations` is
  deleted in favour of `capacity.deprecations`.
- **The reader is tolerant across versions, strict inside one.** An unknown key in a
  `products/<p>.yaml` whose `schema_version` is **greater** than the package's `CONFIG_VERSION` is
  a warning — a doctor row saying `written by a newer asf?` and naming the key — not a load
  failure. Every other problem stays fatal, and an unknown key in a file at or below the package's
  version stays fatal: a typo is still a typo.
- **Rollback is a stated property with a test.** `MIGRATIONS` and `CONFIG_MIGRATIONS` entries carry
  `additive: True | False`. A non-additive entry must raise the **minor** version, must snapshot
  the record and every config file before it runs, and `asf upgrade --to <ref>` restores that
  snapshot and installs `<ref>`. A non-additive entry landing without a minor bump is a red test,
  not a discovery in the field.
- **`upgrade-matrix`, a job in `tests.yml`.** Per selected released tag: install it into a temp
  HOME from a venv, `init` the tag's own `sample/`, tick once, upgrade to HEAD, then doctor green,
  one tick green, the record at `SCHEMA_VERSION`. Plus a mixed-version leg: two products, one
  `config.yaml`, one on an older install and one on HEAD, both green.
- **The release gate reads it.** `release.DEFAULTS['ci_steps']['upgrade_matrix']` and a ninth
  `Criterion`; and `CHANGELOG.md`'s entry for a release lists every migration in it, checked by the
  same test that checks the entry exists.

### Out

- **Migrating a record *down*.** Forward-only stays forward-only (`migrate_dir` already refuses a
  record newer than the package). Rollback is "restore what was there before", never "un-apply".
- **F-0112's `upgrade: auto | notify | off` release channel.** Not landed (P12). This Feature puts
  the migration inside `cmd_upgrade` so that when the channel lands it inherits it; it does not
  build the channel.
- **Rewriting `config.yaml`'s validation into a declared field table.** P5's tolerance is the
  behaviour this card wants for the operator config; making it strict first and tolerant second
  would be work in a circle.
- **Cross-**major** compatibility.** Every rule below is scoped to a `0.x` line; `1.0` is not
  promised anything here.
- **Replacing `tests/test_sample_product.py`'s fixture with a shared library.** The matrix script
  builds its own fixture from the tag's tree (it must run the *old* package, which cannot import
  HEAD's test helpers). The duplication is named in the design and bounded to the fixture.

## The design

### 1. `asf/schema.py` — two numbers, declared migrations, and the refusal that fires once

```python
SCHEMA_VERSION = 1        # the record: index.json + every card's machine block
CONFIG_VERSION = 1        # ~/.ASF/config.yaml + ~/.ASF/products/*.yaml

class Migration(NamedTuple):
    apply: callable       # fn(record_dir) or fn(paths) — as today
    additive: bool        # a package at `n` still reads and writes a record at `n-1`
    note: str             # one line, for the CHANGELOG and the tick log

MIGRATIONS = {1: Migration(_migrate_to_1, additive=True, note='the first stamped schema')}
CONFIG_MIGRATIONS = {1: Migration(_config_to_1, additive=True, note='the first stamped config')}
```

- `pending(product)` → `[(a, b, Migration)]` for the record and `[(a, b, Migration)]` for the
  config: what stands between each file's stamp and the package's number.
- `blocking(product)` → the subset of `pending` whose `additive` is False. `require(product)`
  refuses — the existing `EXIT_MISMATCH` and `NEEDS OPERATOR: run asf schema-migrate — <detail>` —
  **only** when `blocking` is non-empty, or when a file's stamp is *newer* than the package's
  (forward-only, unchanged: `migrate_dir` already raises that one).
- `auto_migrate(product, drain_s, out)` → `(ok, lines)`: drain up to `drain_s`, apply everything
  pending, one commit per step as today, and return the `migrate: schema a → b` lines. Called by
  the tick and by `cmd_upgrade`; `cmd_schema_migrate` keeps its own longer drain.
- `_set_config_version` is fixed to **insert** the key when the file has no `schema_version:` line
  (P3), writing it as the file's first key, and to stamp every `products/*.yaml` the same way.
- A pre-migration snapshot for any non-additive step (D10): `snapshot(product, version)` tags the
  record clone `asf-schema-<a>` (pushed) and copies the config files under
  `~/.ASF/state/backups/config-<a>-<stamp>/`; `restore(version)` is its inverse.
- `changelog_notes()` → the `note` of every migration introduced since a given version, for the
  release entry.

`require` is wired once, in `asf/cli.py`'s dispatch: a command whose `surface.COMMANDS` effect is
`RECORD` calls it before `run` (D3). `tick` is on that list and calls it after its own
`auto_migrate`, so the only mismatch that can reach it is one the tick could not resolve.

### 2. `asf/tick/tick.py` — the migration before the steps

In `_run_steps`, immediately after the upgrade block (P10, `asf/tick/tick.py:394-412`) and before
the daily catch-up:

```
tick: schema 1 → 2 pending (additive) — migrating
migrate: schema 1 → 2            # one line per step, the record clone's own commit subject
tick: config schema 1 → 2 — renamed feeder.capacity → capacity.per_product.sessions (backup: …)
```

- Runs under `locks.record('schema migrate')`, the same lock the version check already takes.
- Drain bound `schema.TICK_DRAIN_S` (D4), overridable as `upgrade.migrate_drain_s`.
- Still in flight past the bound: `tick: schema 1 → 2 still pending — 2 session(s) in flight; the
  next tick retries` and the steps run (additive) or `NEEDS OPERATOR: run asf schema-migrate
  --drain — …` and the tick returns 3 (non-additive).
- A push refused leaves the commit local, exactly as `migrate_product` does today (P9); the next
  tick pushes it.

### 3. `asf/upgrade.py` — the upgrade migrates what it installed

`cmd_upgrade` (P11) gains one step between the install and the table:

```
upgrade: installed a1b2c3d
migrate: schema 1 → 2            # per product, via schema.auto_migrate(drain_s=…)
upgrade: package v0.1.64, schema 2 (config schema 2)
| product | record schema | config schema | package | action |
```

- Skipped when `--skip-pipx` was given and nothing was installed — the table stays a read-only view.
- `row(name)` grows a `config schema` column, and its `action` for a pending additive migration
  becomes `none (the next tick migrates)`.
- `--to <ref>` (D11): restore the newest snapshot at or below `<ref>`'s `CONFIG_VERSION`, then
  `_install(ref)`, then the doctor. No snapshot and no `--force`: exit 2 naming each file and key
  the older release will refuse.

### 4. `asf/env.py` — a version on the file, a warning instead of a refusal

- `PRODUCT_FIELDS` gains `'schema_version': None` — a known key, so a stamped file loads on this
  release and every later one (D12).
- `_problems(text) -> (errors, warnings)` replaces the body of `validate_product_text`.
  `validate_product_text(text)` returns `errors` — the same 3-tuples, the same order (D9).
  `product_warnings(text)` returns `warnings`.
- The one rule that moves a problem from `errors` to `warnings`: it is an unknown-key problem
  (top level or a nested table) **and** the file's `schema_version` is greater than
  `schema.CONFIG_VERSION`. Shape problems, enum problems and every `_deploy_problems` /
  `cloud.config_problems` / `ci_pool` / `ci_queue` / `credentials` finding stay fatal at any
  version, and an unknown key in a file at or below the package's version stays fatal.
- `load_config` gains the same treatment for its two validated sections, so a `worker_pool` key a
  newer release added is a warning under a newer stamp rather than a `ConfigError` (P5 leaves the
  rest already tolerant).
- `deprecated_reads(data)` → `[(old, new)]` for every old name still present, read from
  `schema.CONFIG_MIGRATIONS`'s `renames`. The old name keeps being honoured; the new one wins when
  both are set.

### 5. `asf/doctor.py` — one row, and the existing rows stay visible

- A new non-required row, `schema`, after `config`:
  - `ok` — `record 2, config 2, package 2`;
  - warning — `products/sample.yaml: 'lane_timeout' is not a field of the product file — written
    by a newer asf? (file schema 3, this package 2)`, one line per key;
  - warning — `schema 1 → 2 pending (additive) — the next tick migrates`;
  - red — `schema 1 → 2 pending (not additive) — run asf schema-migrate --drain`.
- `check_config` no longer collapses the table when the only problems are tolerated ones (P7): it
  loads the product from the warnings path and the rest of `doctor.run` proceeds.
- `_capacity_deprecations` is deleted; `check_capacity` calls `capacity.deprecations(cfg)`, which
  now reads `CONFIG_MIGRATIONS`'s renames (P19, and the comment at `asf/doctor.py:499` asked for
  exactly this).

### 6. `tools/upgrade_matrix.py` and the `upgrade-matrix` job

A standalone script — standard library, no import of `asf` (it must run beside two different
installs), invoked from the workflow, never named inside `asf/**/*.py` (P20).

```
python3 tools/upgrade_matrix.py --plan                 # the selected tags, as JSON, for fromJSON()
python3 tools/upgrade_matrix.py --tag v0.1.7           # one leg
python3 tools/upgrade_matrix.py --mixed v0.1.7         # the two-product, one-config leg
```

`--plan` (D6) reads `git tag`, keeps the oldest and newest of every `major.minor` line, both sides
of every tag where `<tag>:asf/schema.py`'s `SCHEMA_VERSION` or `CONFIG_VERSION` changed, the newest
`KEEP_RECENT = 3`, and everything in `PINNED`; sorted oldest first, de-duplicated.

One leg, all under one temp `HOME` and one temp `ASF_HOME`:

1. `git archive <tag> sample | tar -x` — the tag's own fixture (D7). No `sample/config.yaml`:
   print `skipped: <tag> carries no sample/` and exit 0, counted in the summary.
2. bare origins for `sample/repo` and `sample/backlog`, `@REPO@`/`@BACKLOG@`/`@SAMPLE@` filled in,
   a PATH whose `gh` is an offline stub — the shape of P17, built by the script.
3. `python -m venv old && old/bin/pip install git+file://$PWD@<tag>` (D8).
4. `old/bin/asf init --product sample` and `old/bin/asf tick --product sample`; both must exit 0.
   A tag that cannot do either is a **failure**, not a skip — that is a release nobody could run.
5. `new/bin/asf upgrade --skip-pipx` (HEAD's venv, built once and cached across legs) — records the
   table before the upgrade.
6. `new/bin/asf tick --product sample` — the assertion of acceptance 1: it migrates itself.
7. Assert: the tick exited 0; `new/bin/asf doctor --product sample` exits 0; `index.json`'s
   `schema_version` equals HEAD's `SCHEMA_VERSION`; when a migration was due, the tick's output
   carried `migrate: schema a → b` and the record clone carries that commit.

`--mixed <tag>`: one `config.yaml` with `default_product: sample`, two products `sample` and
`sample2` (a copy with its own origins), the old venv ticking `sample2` and HEAD ticking `sample`,
each after the other. Assert both doctors exit 0 and neither `config.yaml` load raises — the
version-skew case of gap 3.

In `.github/workflows/tests.yml`, after the existing jobs:

```yaml
  upgrade-matrix:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        tag: ${{ fromJSON(needs.plan.outputs.tags) }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }          # the tags are the input
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - name: upgrade-matrix
        run: python3 tools/upgrade_matrix.py --tag ${{ matrix.tag }}
      - name: upgrade-matrix mixed versions
        run: python3 tools/upgrade_matrix.py --mixed ${{ matrix.tag }}
```

The step is named `upgrade-matrix` because `release.step_state` matches on the step name (P14).

### 7. `asf/release.py` — the gate, and the notes

- `DEFAULTS['ci_steps']['upgrade_matrix'] = 'upgrade-matrix'` (P15).
- A ninth `Criterion('upgrade_matrix', 'Upgrade from every selected release (in CI)', …)` in
  `evaluate`, red when the step is absent or any leg is not `success`, with the same

- `CHANGELOG.md`'s entry for a release lists `schema.changelog_notes()` for the migrations it

## Stories

Nine Stories, each one a behaviour the suite can name. A line that a landed test already asserts
carries `— proven by <path>`; every other line is what the Task minted for it must prove.

### S-69204: The refusal fires only on a non-additive gap, and every record writer makes it

- [ ] Each `MIGRATIONS` and `CONFIG_MIGRATIONS` entry carries `apply`, `additive` and a one-line `note`, and `schema.pending(product)` returns one `(a, b, Migration)` per step standing between a file's stamp and the package's number.
- [ ] `schema.blocking(product)` is the subset of `pending` whose `additive` is false, and `schema.require` returns without exiting when `pending` is non-empty while `blocking` is empty.
- [ ] A blocking gap makes `schema.require` print `NEEDS OPERATOR: run asf schema-migrate — <detail>` on stderr and exit 3 without writing — proven by tests/test_install.py
- [ ] `migrate_dir` raises on a record stamped newer than the package: forward-only is unchanged — proven by tests/test_install.py
- [ ] Every command whose `surface.COMMANDS` effect is `RECORD` calls `require` before its `run`, wired once at `asf/cli.py`'s dispatch rather than per command.
- [ ] `surface.COMMANDS` gains no row — the count literal in `tests/test_surface.py` stays 59 — because this Feature adds no command.

### S-69205: The tick migrates an additive gap itself instead of stopping

- [ ] The tick migrates a record below the package's `SCHEMA_VERSION` before its first step, under the record lock, and then runs its steps instead of returning the mismatch.
- [ ] Each applied step is its own `migrate: schema a → b` commit in the record clone, and running the same migration again commits nothing — proven by tests/test_install.py
- [ ] The tick log carries `tick: schema a → b pending (additive) — migrating` and then one `migrate: schema a → b` line per applied step.
- [ ] The tick's drain is bounded by `schema.TICK_DRAIN_S`, overridable as `upgrade.migrate_drain_s`, and never by the module's `DRAIN_TIMEOUT_S`.
- [ ] Past the bound with an additive gap, the tick logs `tick: schema a → b still pending — N session(s) in flight; the next tick retries` and runs its steps anyway.
- [ ] Past the bound with a non-additive gap, the tick prints the `NEEDS OPERATOR: run asf schema-migrate --drain` line and returns 3.
- [ ] A drain that gives up at its bound names the sessions still in flight and returns non-zero — proven by tests/test_install.py
- [ ] A refused push leaves the migration commit local and says so, and the next tick pushes it.

### S-69206: Every upgrade path migrates every installed product on the way in

- [ ] `tools/install.sh` and F-0112's auto path inherit the migration by going through `cmd_upgrade`, with no migrate call of their own.

- [ ] `asf upgrade` prints `upgrade: package <v>, schema <n> (config schema <n>)` after its migration lines and before the table.

### S-69207: `config.yaml` and `products/<p>.yaml` carry a version of their own, and a rename is a migration with a backup
