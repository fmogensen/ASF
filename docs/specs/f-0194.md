# F-0194 — the CI the factory owns

Operator, 2026-09-25: *"we're not using \<the code host\>, we're using ci with \<a vm provider\>,
which should be an asf option for external ci .. could be any vm connected really"* — the two
vendor names the card quotes are redacted here, as this repo requires.

Today every path from *a sha exists* to *that sha is green* runs through GitHub Actions. The lane
asks `gh pr checks`; the trunk-red walk asks `repos/<slug>/commits/<sha>/check-runs`; the CI start
queue exists to pack GitHub's runner pool and to cancel GitHub's runs; the CI ceiling is the sum of
`ci.pool` runner slots; the red log a correction carries is fetched from
`repos/<slug>/actions/jobs/<id>/logs`. A self-hosted runner does not change any of that — it only
moves where the job *executes*. The queueing, the registration, the artifact quota and the run
concurrency all still belong to the host.

That has a cost the factory has already paid twice. F-0178 exists because an artifact quota of
0.5 GB turned a **required** job red and the only instrument was an operator with `gh api`;
F-0179 exists because the runner pool's own labels are expressed in a language (`runs-on`
expressions) the factory has to reverse-engineer. Both are the same shape: the thing that decides
whether work lands is owned by someone else.

This card is the other option. A product names machines (`ci.hosts`) and commands (`ci.jobs`); ASF
pushes a sha to a machine, runs the command in a disposable directory, and records the exit code
and a log tail. The results arrive in the *same vocabulary* the lane already judges — a list of
`{name, bucket, …}` check dicts and a `(state, detail, checks)` triple — so required-check judging,
the `WAITING_CI` pending clock, trunk-red, send-back and the gate are not touched at all. The PR
host stays, for exactly two jobs: code review and merging.

The design rule this whole spec follows: **nothing downstream of the triple learns a new shape.**
Every new line of behaviour is on one side of one seam.

## Decisions

### In scope

- `ci.provider: vm` as a third provider value, and the three config blocks behind it: `ci.hosts`
  (ssh target, labels, slots, root), `ci.jobs` (a named command, whether it is required, its
  timeout, its labels, its artifact globs), and the reuse of F-0178's `ci.artifacts.retention_days`
  for the artifacts the VM keeps.
- A transport that is one `ssh` and one `git push` — the sha goes **to** the machine, so a CI host
  never holds a credential for the code host.
- `dispatch` / `collect` / `cancel` over a disposable per-run directory: checkout at the sha, run
  the job's command detached, exit code and a bounded log tail collected, directory removed.
- The pass (`asf ci vm`, its own one-minute clock, and one call at the end of the lane pass):
  dispatch to free slots, collect what finished, cancel what a newer head superseded, fail what
  ran past its timeout, prune artifacts past their retention.
- The results store (`ci-vm.json`) and the one function that renders it as check dicts, wired into
  the three `pr_checks` call sites, into `trunk_red`, into `red_evidence` and into
  `ci_green_runs`.
- `required_checks` for a vm product: `conventions.landing_checks` when named, else the `ci.jobs`
  entries marked `required`.
- `asf capacity` and the status Capacity row counting `ci.hosts` slots as the CI ceiling and
  dispatched-not-finished jobs as the runs in flight.
- `asf doctor`: host reachability, free disk, the bare repo, a required name that names no job, and
  orphaned run directories.
- An optional, write-only commit status posted to the PR host so a human looking at the PR sees
  the same verdict.
- `docs/products.example.yaml` and a `docs/guide/ci-vm.md`.

### Out of scope, and why

- **Replacing `ci.provider: github-actions`.** Nothing about the existing provider changes. Every
  branch this spec adds is reached only when the provider is `vm`; a product that does not set it
  cannot tell this landed. That is also what makes the card's own acceptance (the first adopting
  product "can switch from github-actions to vm by changing config alone") a config change and not
  a migration.
- **The CI start queue (`asf.ci_queue`) under `vm`.** `ci_queue.mode` already returns `off` for a
  product with no `ci.pool` (P8), and a vm product has none. The queue's whole subject — measured
  per-class runner demand, the head guard, backfill, cancelling GitHub runs — is about a pool ASF
  does not control. Under `vm` ASF *is* the scheduler: a job waits for a free slot and takes it,
  in one deterministic order (C9). No part of the queue is ported, and no part of it is deleted.
- **`ci_pool` / `ci.reserve` / `asf ci reconcile` under `vm`.** They reconcile *registered runner
  labels* on a code host. A vm host registers nothing. `ci_pool.backend_for` already answers None
  for a non-github provider and every caller already prints "no runner backend for ci.provider"
  (P9); that stays the answer.
- **The dev deploy sha from a vm run.** `WorkflowDeploy._dev_deployment` reads `ci.workflow`'s
  newest trunk run whose `ci.dev_job` succeeded — both are workflow-job concepts. A vm product that
  wants a dev sha names `deploy_sha.dev` explicitly. `ci_green_runs` **is** in scope (C11), because
  it is what `deploy_sha.prod.from: ci` reads and leaving it `[]` would silently stop prod deploys
  for a vm product.
- **`path_filtered`'s skipped/missing reasoning.** It reads `repos/<slug>/actions/runs?head_sha=`
  to decide whether the *workflow* chose not to create a job. Under `vm` there is no workflow to
  make that choice, and P6 shows the branch is unreachable anyway: every required name always has
  a row (C4), so `missing` and `skipped` are both empty and `not_green` never calls it.
- **A second artifact store.** `ci.artifacts` already exists as F-0178's key with
  `retention_days`; a `ci.hosts[].artifact_days` would be a second answer to one question (C12).
  Uploading artifacts off the VM to an object store is a separate card: this spec keeps them on the
  machine that made them, under a retention, and says where they are.
- **Concurrency inside one job.** A `ci.jobs` entry is one command. A product that wants a matrix
  names several jobs; `required_name`'s matrix-leg rule (`e2e (shard 1)` answering for `e2e`) still
  works if it names them that way, because nothing about that function changes.
- **Any new authentication mechanism.** The ssh target is whatever the operator's own ssh config
  and agent already resolve. ASF adds `BatchMode=yes` so a host that would prompt fails fast
  instead of hanging (C3), and nothing else.
- **A vendor, product, machine or account name anywhere.** The card's own last line; the repo
  enforces it (`tools/check_generic.sh`, P12).

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| C1 | **One seam: `GitHubHost.checks(number, required, head)`, a method, returning today's `(state, detail, checks)` triple.** Its default body is today's `pr_checks(self.slug, number, required, self.rerun_ids())`; under `ci.provider: vm` it is `ci_vm.checks_at(product, head, required)`. The three call sites (P1) each become `self.checks(...)`. | A `VmHost(Host)` subclass; a `ci.provider`-keyed source object threaded through the lane; branching inside `pr_checks` itself. | The lane's `Host` adapter is about **where a branch lands** — `landing: pull-request` vs `fast-forward` — and under this card landing does not change: the PR host still opens, reviews and merges. A `VmHost` would have to reimplement `open`, `merge`, `recheck`, `conflicting`, `cancel_ci`, `unmark_heavy`, `has_queue` and the whole `heavy_after_review` path to change one read, and every one of those reimplementations is a place the two providers can drift. A method with one override point is the smallest change that makes the claim *"the rules apply unchanged"* structurally true rather than merely intended. Branching inside `pr_checks` is rejected because it takes a `slug` and no product — it would have to grow a product argument at four call sites to reach the config, which is the same edit with worse naming. |
| C2 | **The results store is a single JSON file per product, `<state_dir>/ci-vm.json`, keyed sha → job → row.** | A sqlite database; one file per run; rows in the record. | sha → job → row is exactly the shape every reader wants: `checks_at(sha)` is one dict lookup, `trunk_red(names)` is a lookup per sha in the walk it already does, `ci_green_runs` is a scan for shas all of whose required jobs passed. `ci-queue.json` is the same choice in the same directory for the same reason (`ci_queue.QUEUE_FILE`). It is factory state, not a record fact: it is derivable again by re-running CI, and a record item that carried CI results would make every green a commit in the backlog repo. |
| C3 | **The transport is `ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new -o ConnectTimeout=<n> <target> sh -s`, with the script on stdin.** No `-i`, no user, no port, no `ProxyJump` flags: the target string is whatever the operator's own `~/.ssh/config` resolves, and any option beyond these three is theirs to put there. | An ssh library (paramiko); flags for key, port and jump host; `StrictHostKeyChecking=no`. | The card's requirement is *any ssh-reachable machine*, and the thing that already knows what "reachable" means on this operator's network is their ssh config. Re-expressing a subset of it as `ci.hosts` fields would be a second, worse configuration language, and the first host it could not express would be a card. `BatchMode=yes` is not a convenience: without it a host whose key is missing prompts, and a prompt inside a tick pass is a hang, not a failure. `accept-new` rather than `no` so a *changed* key still refuses — a changed host key on a machine that runs the product's test suite is exactly the event that should stop the pass. Script on stdin, not argv, so quoting is the shell's problem once and not per call. |
| C4 | **`checks_at` emits a row for *every* required name: `pass`/`fail`/`cancel` for a concluded job, and `pending` for a required job with no row at the sha at all** — including one that has not been dispatched yet, and one whose name matches no `ci.jobs` entry (its detail says so). | Emitting only the jobs that have rows; emitting `fail` for a required name with no job. | P7 is the whole reason: with `required` names, `pr_checks` judges only the checks present, and an empty `judged` list is **green**. A store that has not dispatched anything yet would therefore read green and merge an ungated branch — the single worst failure this card could have. Rendering the absence as `pending` makes the safe answer the automatic one, and it makes the lane's own instruments work on it: the `ci_since` clock ages it, `landing_checks_missing` governs it, and the pending line names the job. `fail` is wrong because nothing failed; blaming a branch for a config error is how a correction session gets launched at nothing. A required name with no `ci.jobs` entry also gets a red doctor row (C15), because pending forever is a hang and the operator must be told which name it is. |
| C5 | **The sha travels *to* the VM: one `git push` from the factory's own checkout to a bare repo at `<root>/repo.git` on the host, as `refs/asf/<run_id>`.** The host is then `git worktree add` at that ref into the run directory. | The VM clones or fetches from the code host. | A VM that fetches from the code host needs a credential for the code host — one per machine, rotated per machine, and invisible to `asf doctor`. The whole point of this card is that the factory stops depending on the code host for CI; a design whose first act is to hand every CI box a repo token keeps the dependency and adds a secret-distribution problem. Pushing means the only credential in play is the ssh access ASF already needs to run anything at all, the machine needs nothing but `git` and `sh`, and an air-gapped-from-GitHub host works. It also makes the sha's availability ASF's own problem, which is where the `git` failure should be reported. |
| C6 | **The run directory is `<root>/runs/<run_id>` with `run_id = <sha12>-<job>-<attempt>`, and the whole tree under `<root>` is ASF's**: `repo.git`, `runs/`, `artifacts/`. Cleanup removes the run directory; artifacts are moved to `<root>/artifacts/<sha12>/<job>/` first. | A per-run temp dir from `mktemp`; reusing one checkout per host. | A named, derivable path is what makes `collect` a poll and not a bookkeeping exercise: the pass can list `runs/` and compare it to the file, which is how an orphan directory becomes a doctor row instead of silent disk. One shared checkout per host is rejected outright — two jobs at two shas on one host is the normal case with `slots: 2`, and a shared working tree makes them corrupt each other. `git worktree` off one bare repo gives the isolation without re-transferring the repo per run. |
| C7 | **The job's timeout is enforced by the pass's own clock, not by the remote.** A run whose `started` is older than its `timeout_min` is cancelled and recorded `timeout` (bucket `fail`), with the log tail collected first. The start script uses no `timeout(1)`. | `timeout <n> sh -c …` on the remote; both. | `timeout(1)` is coreutils, and "any ssh-reachable machine" includes ones where it is absent or is BSD's — a start script that silently does nothing on such a host would give a job no timeout at all, which is the failure mode that looks like a hung pool. The pass's clock works on every host identically, is the clock the operator can actually see (it is in the file), and is the one ASF can test without a remote. Doing both would mean two answers to "why did this job stop", and the remote's would win invisibly. |
| C8 | **Supersession is per branch, decided from `git ls-remote`: when a branch's head moves, every `running` run at the old sha for that branch is cancelled (`bucket` `cancel`, `superseded_by` the new sha) and the new head is dispatched.** A trunk sha is never superseded. | Cancelling nothing (let it finish); cancelling on any newer sha anywhere. | This is `ci_queue.cancel_duplicate_pushes`'s rule, which exists because a run on a sha nobody will merge is a slot spent on a dead answer — and under `vm` slots are the scarce thing by construction. Per *branch* rather than per sha because that is what "a newer push supersedes the run" means: two branches at two shas are two answers both still wanted. The trunk is exempt because a trunk result is evidence about that commit forever — `trunk_red` walks history and `ci_green_runs` reads it, and cancelling the older one would erase the answer to "which commit broke it". |
| C9 | **Dispatch order is: every trunk sha first, then branches by name, then jobs in `ci.jobs` declaration order.** Deterministic, with no record read. | `ci_queue.record_rank` (the record's own `asf next` order); newest-sha-first; a `ci.jobs[].priority`. | A trunk job gates every deploy and every `trunk-red` judgement, so it goes first for the same reason the queue puts trunk runs at rank 1. Beyond that, the queue's priority machinery exists to pack a pool ASF cannot see into; here the pass sees every slot and every run, and the honest scheduler is the simple one. Branch-name order is arbitrary but *stable*, which is what makes the acceptance tests assertions rather than approximations — and an operator who needs priority has `ci.jobs` order and `capacity` already. Re-deriving the record's order would mean loading the record in a one-minute clock for a tie-break. |
| C10 | **`trunk_red` under `vm` reads the same store, keeping its exact `{name: sha}` contract and its `TRUNK_RED_DEPTH` first-parent walk.** A name with no row at a sha is "no completed run" — the walk continues to the commit before, exactly as today. | A separate vm-only trunk judgement; treating a missing row as not-red at the newest sha only. | The walk *is* the rule the card says applies unchanged ("a check still running on the newest commit is judged by the one before"), and it is expressed entirely in terms of "does this name have a completed run at this sha". Under `vm` that question is a dict lookup instead of an API call; nothing else about it needs to be different. Keeping the B-0129 rule (a sha with a red attempt is red even if a retry went green) matters more here, not less: re-dispatching a vm job is cheap and would otherwise launder flakes. |
| C11 | **`red_evidence` uses a log tail the check dict already carries, and `ci_green_runs` reads the store — both by one `if`, with the Actions path untouched.** A vm check row carries `log` (its tail, already trimmed by `red_log_lines`' rules at collection time); `red_evidence` yields it with no call of any kind. `ci_green_runs` under `vm` returns the trunk shas, newest first, all of whose required jobs passed. | Leaving `red_evidence` empty for vm (`''` is its documented no-evidence answer); leaving `ci_green_runs` at `[]`. | `red_evidence` exists because a product spent five correction rounds on "checks red: gate" with nobody told which lint failed where. | C13 | **The pass runs in three places and is idempotent under a lock: `asf ci vm --apply`, its own one-minute clock (`CI_VM_CLOCK = 'ci-vm'`, installed for every product whose provider is `vm`, retired when it is not), and one call at the end of `lane_pass`.** A pass that cannot take the lock prints one line and returns None. | A new tick step; the `harvest` step only; the existing `ci-queue` clock. | P11: this is `queue_pass`'s own arrangement, chosen for the same reason — a CI pass that only runs on the tick's 7–24 minute clock leaves slots idle and results unread for a quarter of an hour, and runs not at all while an upgrade is pending. Two views would be two numbers to reconcile. |
| C15 | **`asf doctor` grows one `ci vm` label with five row kinds, and no row at all for a non-vm product.** Required: a host that does not answer (`ssh … true` inside `ConnectTimeout`), free disk at `<root>` under a floor (`df -Pk`, red under 10%/2 GiB, advisory under 25%), a missing or broken `<root>/repo.git`, and a required check name matching no `ci.jobs` entry (C4). Advisory: a run directory on a host with no `running` row in the file. | Folding the rows into `ci pool`; a required row for the orphan; checking every host on every doctor run in parallel. | P18 is the shape; a separate label because `ci pool` is documented as "the declared runner pool against the CI host" and an operator reading a red `ci pool` row on a product with no pool would be reading a lie. The required-name row is required because C4's `pending` is otherwise a silent permanent hold. The orphan is advisory because it costs disk, not correctness, and the pass cleans it. Serially, one host at a time, inside `ConnectTimeout`: the doctor is a table, not a monitor, and a thread pool to save two seconds is a thread pool to debug. |
| C16 | **The commit status posted to the PR host is one-way and never read back**: off by default (`ci.post_status`), one `gh api -X POST repos/<slug>/statuses/<sha>` per concluded job with `context: asf/<job>`, and no reader anywhere asks the host for it. | Posting a check run (the Checks API); reading the posted status back as the source of truth; on by default. | The store is the judge (C1/C2); a status that could also be *read* would be a second source of truth with a network in front of it, and the first time they disagreed the factory would believe the slower one. A commit status is the smallest write that makes a PR page show the verdict to a human, needs no app installation (the Checks API needs one), and is already covered by the dry-run backstop because `harvest._gh` refuses a mutating `api -X POST` (P14). Off by default because it is a write to someone else's system in service of a human's convenience, and a product that has switched to `vm` precisely to stop depending on that system should have to ask. |
| C17 | **Every ssh that changes the remote asks `mutation_guard.is_active()` itself and prints `would_line('ssh', …)`; a poll never does.** The predicate lives in `ci_vm` (`_MUTATING = start, cancel, cleanup, prune`), not in `mutation_guard`. | Extending `is_mutating_gh` to cover ssh; threading `dry_run` only. | P14's whole argument is that threading a flag fails open: `step_wave.lane_pass` hardcoded `dry_run=False` and a dry run deleted two branches and cancelled four runs, with every local check individually correct. An ssh that starts a test suite on a machine, kills a process group or `rm -rf`s a directory is in exactly that class and must be behind the same backstop. The predicate stays in `ci_vm` because `is_mutating_gh` answers a question about a `gh` argv and there is no ssh argv to inspect — the caller knows whether it is starting a job or reading a file, and a predicate that tried to guess from a shell script would be a parser. |
| C18 | **A collected log tail is bounded at collection: `RED_LOG_TAIL_BYTES` (256 KiB) read off the remote, then `red_log_lines`' own rules applied, then at most `RED_LOG_LINES` (40) lines stored.** | Storing the whole log; storing it on the VM only and fetching on demand. | F-0178's own subject is a factory that let a store grow until a required job went red; a results file that accreted whole CI logs per sha per job would be that bug in `~/.ASF`. 40 lines is already the number `red_evidence` hands a correction session (P5), so storing more would be storing what nothing reads. ### 2. The transport and the three remote scripts (`asf/ci_vm.py`)

```python
def ssh_argv(host, timeout_s=CONNECT_TIMEOUT_S):
    """``['ssh', '-o', 'BatchMode=yes', '-o', 'StrictHostKeyChecking=accept-new',
    '-o', f'ConnectTimeout={timeout_s}', host.ssh, 'sh', '-s']`` — the whole flag set (C3)."""


def run_ssh(host, script, kind='read', timeout_s=None, run=subprocess.run):
    """``(rc, stdout, stderr)`` for ``script`` on ``host``'s stdin. ``kind`` other than ``read``
    is a write: a dry run in progress refuses it, prints :func:`asf.mutation_guard.would_line`
    and returns ``(1, '', line)`` without starting ssh (C17). Never raises: an ``OSError`` or a
    timeout is ``(124, '', <why>)``."""
```

Three script constants, each a `sh` program with `{}` slots filled by `shlex.quote`:

- **`REMOTE_START`** — `mkdir -p <root>/runs <root>/artifacts`; `git init --bare -q <root>/repo.git`
  if absent; `git -C <root>/repo.git worktree add -q --detach <rundir>/src <ref>`; write
  `<rundir>/cmd`; start it detached in its own process group, stdout and stderr to `<rundir>/log`,
  and on exit write the code to `<rundir>/exit`; print the pid to stdout.
- **`REMOTE_POLL`** — for each directory under `<root>/runs`: print `<run_id> <exit-or-dash>
  <pid> <bytes-of-log>`. One call per host per pass, whatever the number of runs.
- **`REMOTE_CANCEL`** — `kill -TERM -<pgid>` then, after a grace, `kill -KILL -<pgid>`; print
  what it killed.

Cleanup and the prune are two more, small enough to inline: move `<rundir>/src/<glob>` into
`<root>/artifacts/<sha12>/<job>/`, `git -C <root>/repo.git worktree remove --force`, `rm -rf`
the run directory and the pushed ref; and `find <root>/artifacts -mindepth 2 -maxdepth 2 -type d
-mtime +<days> -exec rm -rf {} +`.

The sha's own transport is not ssh:

```python
def push_sha(product, host, sha, run_id, run=subprocess.run):
    """``git push --force <ssh://…/repo.git> <sha>:refs/asf/<run_id>`` from the product's own
    checkout (C5): ``(True, '')`` or ``(False, why)``. A write — refused under a dry run."""
```

### 5. The pass (`asf/ci_vm.py`, `asf/harvest/lane.py`, `asf/scheduler.py`, `asf/ci_pool.py`)

```python
def vm_pass(product, out=print, dry_run=False, now=None, run=subprocess.run, wait_s=0):
    """One pass under ``<state_dir>/ci-vm.lock``: collect, supersede, time out, dispatch, prune.
    ``(dispatched, concluded)``; None when another pass holds the lock. Not a vm product:
    ``(0, 0)``, no ssh and no git call."""
```

In order, because each step frees what the next one needs:

1. **collect** — one `REMOTE_POLL` per host with a `running` row. A run with an `exit` file
   concludes: `passed` on 0, else `failed`; its log tail is read and trimmed (C18); artifacts are
   moved and the run directory removed. One line per conclusion:
   `ci vm: <branch> <sha9> gate passed on ci-1 (4m12s)`.
2. **supersede** — one `git ls-remote --heads origin` (P16). A `running` run whose branch's head
   has moved is cancelled (C8): `REMOTE_CANCEL`, cleanup, `state: cancelled`,
   `superseded_by: <new sha>`. One line naming both shas.
3. **time out** — a `running` run past `timeout_min`: log tail collected, cancelled, cleaned,
   `state: timeout` (C7). One line with the limit.
4. **dispatch** — for every sha that matters (the trunk head, then each lane branch's head, C9)
   and every job with no row at it: pick a host whose labels satisfy the job's and that has a free
   slot, `push_sha`, `REMOTE_START`, write the `running` row. One line:
   `ci vm: dispatch worker/T-0700 abc123def gate → ci-1 (slot 2/2)`. No host free, or none whose
   labels fit: one line saying which, and the next pass tries again.
5. **prune** — at most once an hour per product, one `find … -mtime +<days>` per host (C12).

Its three entry points (C13/P11):

- `lane_pass` ends with, beside the queue's own call:
  ```python
      from asf import ci_vm
      if ci_vm.vm_pass(product, out=lane.out, dry_run=lane.dry_run) is None:
          lane.out('ci vm: its own pass is running — the lane leaves the CI pass to it')
  ```
- `scheduler.py`: `CI_VM_CLOCK = 'ci-vm'`, `CI_VM_COMMAND = 'ci-vm'`, `CI_VM_EVERY_S = 60`,
  installed for every product with `ci_vm.enabled(product)` and retired when it is not — the same
  never-declared, install-and-retire treatment `QUEUE_CLOCK` gets, and the same module docstring
  paragraph.
- `ci_pool.register`: `ci_vm.register(sub)` after `ci_queue.register(sub)`, giving
  `asf ci vm [--apply] [--dry-run]` — the view without `--apply` (the hosts, their slots, what is
  running and at which sha), the pass with it.

## Acceptance tests

Two new files, and amendments to four existing ones. **No network and no real ssh anywhere**: the
fake host is a local `sh` script that the test puts on `PATH` as `ssh`, strips the flags and the
target off its own argv, and runs the remaining script on stdin against a temp directory — so
`REMOTE_START`, `REMOTE_POLL` and `REMOTE_CANCEL` are *actually executed* and the assertions are
about what they did, not about what was sent. `git push` targets a bare repo in another temp
directory over a `file://` URL.

**The config.** `tests/test_ci_vm.py::Config` — `hosts`/`jobs` parsed with every default applied
(`slots` 1, `timeout_min` 45, `root` relative); `config_problems` on an unknown host field, a
missing `ssh`, a missing `command`, a duplicate name, `slots: 0`, `timeout_min: -1`, a job label no

## Records

- **`~/.ASF/state/<product>/ci-vm.json`** (new) — the results store of §3: `version`, `at`, and
  `runs[sha][job]` carrying `state`, `host`, `run_id`, `pid`, `branch`, `attempt`, `started`,
  `ended`, `exit`, a log tail of at most 40 lines and `superseded_by`. Written atomically, by the
  pass only. This is the judge of red and green for a vm product; nothing else is.
- **`~/.ASF/state/<product>/ci-vm.lock`** (new) — the pass's own lock, so the lane's call and the
  clock's are the same pass (C13).
- **On each CI host, under `<root>`** — `repo.git` (a bare repo ASF pushes shas to, created on
  first dispatch), `runs/<run_id>/` (`src` worktree, `cmd`, `log`, `exit`, removed at conclusion)
  and `artifacts/<sha12>/<job>/` (kept for `ci.artifacts.retention_days`, default 7). Nothing is
  written outside `<root>`, and a refs namespace `refs/asf/*` in `repo.git` that cleanup deletes.
- **The tick and `asf ci vm` stdout** — one line per dispatch, conclusion, supersession, timeout
  and prune, each naming the branch, the sha's first nine characters, the job and the host; one
  line when no slot or no matching host was free; one line when another pass holds the lock.
- **`asf doctor`'s new `ci vm` rows** — five kinds (C15), and none at all for a non-vm product.
- **`asf capacity` / the status Capacity row** — the ceiling now reads `ci.hosts: ci-1 2, ci-2 1`
  for a vm product, and the in-flight count comes from the store rather than from `gh`.
- **The scheduler** — one more installed job per vm product, `asf.<product>.ci-vm`, every 60s,
  never declared in a manifest and retired when the provider changes (C13). The tick's eight steps
  are unchanged (P20).
- **The PR host** — read exactly as before (PRs, review, merge). One *new* write, only with
  `ci.post_status`: a commit status per concluded job. No workflow is dispatched, no run is
  cancelled, no artifact is uploaded, and `gh run list` is not called at all for a vm product.
- **Nothing in the record.** No card, no Story, no field: a CI result is derivable by running CI
  again, and a backlog commit per green would be a commit per push.
