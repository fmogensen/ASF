# F-0328 — the run's own conclusion is the first thing to read, and nothing reads it

The batch judge asks every required check what it concluded and never asks the **run** the check
belongs to whether it reached a verdict at all. `verdict` (`asf/merge_queue.py:562-591`) reads a
required check that concluded `skipped` as red, by a rule written down on purpose — a path filter
that skipped the suites landed a code PR once (2026-09-26) — and a host-cancelled run skips every
required job downstream of the one it cut. So the two readings collide: the run says *I judged
nothing*, the checks say *gate skipped, gate-tests skipped, m6-e2e skipped*, and only the second is
read.

The card's incident is that collision, logged twice in one pass. `asf.ci_queue._contention`
(`asf/ci_queue.py:2987-3022`) read the host's cancel correctly — `rules` hit its 10-minute timeout
while its measured p50 is under half that, so *"runner contention, not a verdict — re-run
requested"* — and `asf.merge_queue`'s judge, running in the same job a few lines later
(`asf/ci_queue.py:4443-4446`: `queue_pass` then `merge_queue_pass`), dropped the batch with
*"red on gate (skipped), gate-tests (skipped), m6-e2e (skipped)"* and split it. Two halves of one
queue, one run, opposite answers.

The requirement is the card's sentence: **a host-cancelled run whose downstream jobs are skipped is
not a verdict on the batch.** It is the rule the module already states for a check
(`NONVERDICT`, `asf/merge_queue.py:182-185`) applied one level up, to the run.

* **P1 — the incident reproduces, line for line.** Checks `gate (skipped)`,
  `gate-tests (a) (skipped)`, and a run `{id: 600001, conclusion: cancelled}` on the batch sha.
  One pass:

  ```
  merge queue: batch dropped — red on gate (skipped), gate-tests (skipped)
  merge queue: batch splits — 1 and 1 PR(s), each cut on main alone
  ```

  The batch is dropped as red and split into two single-PR batches — two more full CI runs — on a
  run that judged nothing. This is the card's line with the card's cause.

* **P2 — the escape hatch that exists needs an upstream check that concluded badly, and a cut
  short run often has none.** `skipped_behind` (`asf/merge_queue.py:1438-1473`) reads the
  workflow's `needs:` graph at the batch sha and, for each skipped required job, looks for an
  upstream check run of the **same run** that completed neither green nor skipped. `bad` empty
  for even one skipped job returns None for the whole batch — *"a skipped job has no such
  upstream (skipped on its own `if:`): judged as before"* — and the judge falls straight through
  to red. In P1 that is exactly what happened. It is the common shape, not a corner: a required
  job whose nearest upstream is itself `skipped`, a required job declared in another workflow
  file, a cancel that landed before the upstream job produced a check run at all.

* **P3 — when the upstream *is* there, the graph answers three of the four flavours, and the one
  it gets wrong is the card's.** Same shape plus an unrequired `rules`; the column that decides is
  the **run's** conclusion, which nothing reads today:

  | `rules` concluded | its annotations | the run concluded | what the judge does today |
  |---|---|---|---|
  | `failure` | `The operation was canceled.` | `failure` | `_runner_lost` fires → re-run `--job 600002`, batch pending. Right |
  | `cancelled` | — | `cancelled` | `skipped_behind` → all causes in `NONVERDICT` → re-run `--job 600002`, batch pending. Right |
  | `failure` | `… has exceeded the maximum execution time of 10 minutes.` | `failure` | `skipped_behind`'s else branch: *"skipped behind rules (failure) — the real cause"* → triaged as the code's failure. Right: a run that concluded `failure` reached a verdict |
  | `failure` | `… has exceeded the maximum execution time of 10 minutes.` | `cancelled` / `timed_out` | the same else branch, the same triage — **wrong**: this is the host's timeout, and the run says so |

  The fourth row is the contention timeout the card names, and it is the only shape
  `_contention` can act on at all: `_explain` skips every run whose conclusion is not `cancelled`
  or `timed_out` (`asf/ci_queue.py:3078`). `flake.is_infra` (`asf/flake.py:240-246`) excludes a
  `timeout-minutes` message from its runner-loss signatures deliberately — for `explain_cancels`,
  *"a timeout is a verdict"* — so the one annotation that proves the host cut the run short is the
  one that makes it read as the code's. The run's conclusion is the fact that separates row 3 from
  row 4, and rows 1 and 2 show the graph already gets its own cases right.

* **P4 — the judge holds the answer in its hand and drops it.** `_workflow_runs(lane.slug, sha)`
  returns each run's own `conclusion`; the judge calls it inside `_runner_lost`'s branch
  (`asf/merge_queue.py:1035`), inside `skipped_behind` and inside `_nonverdict`, and no caller
  ever looks at `conclusion` for the run the skipped checks belong to. `_run_id(r)`
  (`asf/merge_queue.py:1122-1128`) already maps a check run to its run id.

* **P5 — the two halves can agree, because the first writes down what it did.** `_contention`
  claims every contention cancel in `ci-cancels.json` through `ci_queue.claim_cancel` with
  `cause` `contention-rerun` (the host was asked for the re-run), `contention-refused` (it
  refused and will not be asked again) or `contention-alarm` (twice on one head), carrying
  `sha`, `branch`, `job`, `p50`, `timeout` and `attempt`. `queue_pass` writes those claims
  before `merge_queue_pass` runs in the same job (`asf/ci_queue.py:4443`, `:4446`), so in the
  incident's pass the claim was already on disk. It is not *guaranteed* to be: the merge queue
  also runs from the harvest, where `explain_cancels` has not run.

* **P6 — the claim key is the run id, and the two halves would overwrite each other.**
  `claim_cancel(state_dir, rid, cause, …)` is keyed by run id, and `explain_cancels` skips a run
  already in `claims` unless it is a later attempt of a `contention-rerun`
  (`asf/ci_queue.py:3077-3081`, `_new_attempt`). An `MQ_RERUN` claim the merge queue wrote on a
  run would silence `_contention` on it for ever; a `contention-rerun` claim does not stop
  `_nonverdict` asking for a second re-run of the same run.

* **P7 — `_nonverdict` cannot re-run a skipped job usefully.** With the skipped checks marked
  `cancelled` its `jobs_of` reads a job id off each one and asks
  `gh run rerun --job <skipped job id>` (`asf/merge_queue.py:1306-1319`). Re-running a job that
  was skipped runs nothing: the job the run must repeat is the upstream the host cut. Where the
  `needs:` graph *can* name that upstream, `--job <upstream id>` is the better ask — the host
  re-runs that job and the jobs that need it, without the run's unrequired jobs — and that is the
  ask `skipped_behind`'s branch already makes (P3 row 2). Where it cannot, the ask has to be the
  whole run.

* **P8 — a `recut` is already the safe answer and costs nobody.** `('recut', why, None)` drops
  the batch and puts every member back in the pool with no blame and no ledger row
  (`asf/merge_queue.py:791-796`), and the fresh cut's push starts a fresh run on a new sha.

* **P9 — two of the three contention causes are bare literals, and the three strings are read in
  two other modules.** `CONTENTION_RERUN, CONTENTION_ALARM` are named at
  `asf/ci_queue.py:2963-2964`; the refused cause has no constant at all and is a literal at its
  one `claim_cancel` call site (`asf/ci_queue.py:3020`), and `CONTENTION_ALARM` is spelled out as
  a literal beside its own constant at `asf/ci_queue.py:3009`. All three strings also appear
  read-side, as keys and members of mapping tables rather than as causes written: `HONOURED`
  (`asf/ci_cancels.py:46-47`, each mapped to `'timeout'`) and `RUNNER_CLAIMS`
  (`asf/metrics/reds.py:65`). Those are lookups against what is already on disk, so the strings
  are the interface and they do not change (D7, and the Out row below).

* **P10 — the PR-side half of the card needs no second change.** PR #1247's red at 14:39 is this
  red reaching a member: a red batch sends its culprit back with a `landing-gate` correction
  naming the failing jobs. A batch that is never red writes no such hold. `_hold_regate_why`
  (`asf/merge_queue.py:607-646`) is the existing cleanup for holds already written, and it
  already clears one naming jobs flake triage never re-ran.

* **P11 — `red - skipped` cannot see a judged leg beside a skipped one.** `skipped_behind`'s
  prefix (`:1444-1446`) and `_runner_lost`'s (`:1179-1180`) both build `red` and `skipped` as sets
  of **job keys**, while `why` carries one entry per check run — `verdict` loops over every run of
  a required name (`:575-586`). So a required job with one matrix leg a runner concluded `failure`
  and a sibling leg `skipped` — the shape a cancel makes whenever a leg had not started — gives
  `red = skipped = {gate-tests}` and `red - skipped` empty: the skip-only prefix opens on a red
  that holds a real verdict. Measured:

  ```
  state red | why 'gate (skipped), gate-tests (failure), gate-tests (skipped)'
    skipped ['gate', 'gate-tests']  red-skipped []
    key-wise skip-only prefix opens: True | entry-wise (_skip_only) opens: False
  ```

  The card's own shape, for contrast, opens both ways, and the two skipped required checks name
  one run:

  ```
  state red | why 'gate (skipped), gate-tests (skipped)'
    key-wise opens: True | entry-wise opens: True
    run ids of the skipped required checks: ['600001']
  ```

* **P12 — a hand-carried hotfix for this card is already on origin, closed, and does not cover
  the card's shape.** `fix/F-0328-pending-not-red` (two commits, 2026-10-09, cut from
  `e5444102c`) carries the `verdict()` change in **`c6cb1a21f`** alone — *"the merge queue reads
  not-yet-run required jobs as pending, never red"*, `asf/merge_queue.py` and
  `tests/test_merge_queue.py`; its other commit `6a81462dc` is *"the cloud create body drops
  `run_once_at`"* over `asf/workers/remote.py`, which carries a `fix(F-0328)` subject but is no
  part of this defect. So one commit is what is measured below. It sits behind PR #1261 — titled
  *"hotfix, do not merge"* and closed, as #1260 before it — so the trunk does not and will not
  carry it: every line
  measured above is measured against the trunk. What it does is hold a required check that reads
  `skipped`/`cancelled` **while another job of its own run is still queued or in progress**
  pending instead of red (a `live_ids` set of the runs with an unfinished job). Loading that
  file's `verdict` beside the trunk's and calling both with `NONVERDICT` on four shapes:

  ```
  the card: three required skipped on one completed cancelled run
    trunk  red     | gate (skipped), gate-tests (skipped), m6-e2e (skipped)
    hotfix red     | gate (skipped), gate-tests (skipped), m6-e2e (skipped)
  its own shape: a sibling job of the same run still in progress
    trunk  red     | gate (skipped), gate-tests (skipped), m6-e2e (skipped)
    hotfix pending | gate (skipped, its run still in progress), gate-tests (skipped, its run
                     still in progress), m6-e2e (skipped, its run still in progress)
  one leg judged beside a skipped leg, run completed cancelled
    trunk  red     | gate (skipped), gate-tests (failure), gate-tests (skipped), m6-e2e (skipped)
    hotfix red     | gate (skipped), gate-tests (failure), gate-tests (skipped), m6-e2e (skipped)
  a path-filtered skip on a healthy completed run
    trunk  red     | gate (skipped)
    hotfix red     | gate (skipped)
  ```

  It is a **different defect printing the same line**: the card's run has *completed* `cancelled`,
  so `live_ids` is empty, the condition never opens and the red falls through unchanged. Its
  reading is not adopted here (the `verdict()` row of Out stands, and the hotfix is the live
  demonstration of why — it rewrites the reader all five callers share to answer one of them).
  The one place the two could touch is the new wording, and they do not: `skipped, its run still
  in progress` is appended to `verdict`'s **pending** list, never its red one, so `_skip_only`'s
  exact `(skipped)` suffix test over the red entries reads the same whether or not that shape is
  ever landed.

### Preconditions the work depends on

* `NONVERDICT` (`asf/merge_queue.py:185`) is the shared vocabulary for "judged no code" and holds
  `cancelled`, `timed_out`, `stale` and `startup_failure`; the first two are the conclusions
  `explain_cancels` reads as the host's cancel (`asf/ci_queue.py:3078`), so every run the
  contention reader can act on is one `run_cut_short` can act on.
* `_workflow_runs` returns `conclusion` and `status` per run on the sha, and `_run_id` resolves a
  check run to its run (P4).
* `_nonverdict`'s once-per-(sha, job) claim, its `RERUN_GRACE_S` grace and its ALARM re-cut are
  the machinery this routes into, unchanged in shape (P8). Its own `ids` for a `gone` batch are
  the run ids of the marked checks it is handed (`:1282-1287`), so the re-run is derived from the
  checks and not re-derived here — a superset of what `run_cut_short` returns rather than a second
  derivation of it (§2c).
* `queue_pass` runs before `merge_queue_pass` in the queue's own job (P5).

## The design

Three files. `asf/merge_queue.py` carries the rule and says it in its own module header — §1, §2,
§3 and §5 are all edits to that one file, §5 to its module docstring; `asf/ci_queue.py` gains one
constant and uses two; `tests/test_mq_batch_survival.py` carries the cases. That is the whole
footprint a plan's `writes:` needs: three paths, five sections.

### 1. `asf/merge_queue.py` — the entry-wise prefix and the pure reader

Beside `_skipped` (`asf/merge_queue.py:1476-1478`), which stays as it is for its four callers:

```python
def _skip_only(why):
    """The required job keys a red verdict ``why`` reads as ``skipped`` when **every** red entry
    in it is one — else None. One entry per check run, not per job (:func:`verdict` loops over
    every run of a required name), because a required job with one matrix leg a runner concluded
    ``failure`` and a sibling leg ``skipped`` — the shape a cancel makes when a leg had not
    started — has ``red - skipped`` empty and is still a verdict (F-0328)."""
    red = [e for e in (why or '').split(', ') if e]
    if not red or any(not e.endswith('(skipped)') for e in red):
        return None
    return {e.split(' ', 1)[0] for e in red}
```

Then, beside `skipped_behind`, which it is deliberately not part of (D2):

```python
def run_cut_short(runs, why, wf):
    """``(runs, run ids)`` when the red verdict ``why`` is no verdict at all because the host cut
    its run short: every red entry in ``why`` is a required check that concluded ``skipped``
    (:func:`_skip_only`), and every workflow run those skipped checks belong to (``wf``, by
    :func:`_run_id`) concluded in :data:`NONVERDICT` — a cancel, a timeout, a supersede, a run
    whose jobs never started. ``runs`` comes back with those checks re-marked ``cancelled``, the
    non-verdict they are, so :func:`_nonverdict` reads them; the run ids are the runs to re-run
    whole (a skipped job has nothing of its own to re-run — F-0328 P7). None when any red entry is
    a check a runner judged (a verdict, whatever happened to its run afterwards), when a skipped
    check names no readable run, or when its run reached a verdict of its own — a path-filtered
    skip on a healthy run is red, as it has been since 2026-09-26. ``why`` must be the one
    :func:`verdict` returned for these ``runs``, which is what makes every name in it a required
    one; no ``required`` is taken, because a second filter on names that are required by
    construction would guard nothing (F-0328 D2). Not
    :meth:`asf.harvest.lane.Lane.cut_short`, which cuts a PR's gate short. Pure: the caller reads
    the checks and the runs once (F-0328)."""
```

The body, in order: `from asf.harvest import deploy` — in the body, because `asf/merge_queue.py`
has no module-level `deploy` import and every one of its users does it inside its own function
(`:571`, `:1049`, `:1174`, `:1233`, `:1418`, `:1448`), which `run_cut_short` is now one of;
`skipped = _skip_only(why)`; `if not skipped: return None`;
`by_id = {str(r.get('id')): r for r in wf or ()}`. Then, for each name in `sorted(skipped)`, every
check run of that job key (`deploy.job_key`) whose conclusion is `skipped`: its `_run_id`, and
that run's conclusion. A missing id, a run not in `by_id`, or a conclusion outside `NONVERDICT`
returns None — **every** skipped check is read, not the first one that names a run, so two legs of
one job on two runs with one of them healthy is nothing at all. Finally `marked` — the skipped
required checks as `dict(r, conclusion='cancelled')`, the same re-marking `_runner_lost` and the
`behind` branch already do (`asf/merge_queue.py:1192-1196`, `:1054-1057`) — and the sorted run
ids. Nothing in `runs` is mutated: the marking is a new list of new dicts.

### 2. `asf/merge_queue.py` — the judge reads the run after the graph and before the blame

In `_judge` (`asf/merge_queue.py:1029-1065`). Four edits, spelled out because two of them are
one-line conditions that decide whether the common red crashes or pays for nothing:

**a. the gated read, and the guard `_runner_lost` used to get for free.** Today
`wf = _workflow_runs(lane.slug, sha) if lost is not None else None` at `:1035` *is* the guard for
`:1036`'s `if wf is not None:` — the `lost` unpacking under it is only safe because `wf` is None
whenever `lost` is. Reading `wf` earlier breaks that: `:1035` is deleted and `:1036`'s condition
has to carry both facts itself, or `marked, jobs, names = lost` raises
`TypeError: cannot unpack non-sequence NoneType` on every ordinary red.


`skipped_behind`'s `wf=wf` is a plain keyword it already takes and needs nothing else: handed a
list it uses it, handed None it reads for itself as today (an unreadable listing, where both
readers decline anyway).

**b. the cut-short block, after `skipped_behind`'s non-verdict branch.** That branch
(`:1053-1061`) is unchanged and always returns, so reaching the block below with `behind` truthy
means the graph named a cause a runner judged:


The `lane.out` of the second block is `:1062-1063` moved down below the cut-short test, unchanged
in text: a run the host cut short must never be announced as having a real cause. `said` stays
bound in the first `if behind:` block and is not shadowed — the cut-short line is `cut_said`, and
the cut-short block returns on every path it takes. `causes` keeps its place and its use by the

**c. `_nonverdict` gains one keyword.**

```python
def _nonverdict(lane, batch, runs, required, st, rerun_jobs=None, wf=None, rerun_run=False):
```

`rerun_run` makes the ask the whole run: `jobs_of = {rid: [] for rid in ids}` (so the job ids the
marked skipped checks carry are not asked for — P7), and `--failed` is suppressed in the `else`
arm, which becomes `+ (['--failed'] if gone and not rerun_run else [])`. The call is then
`['run', 'rerun', rid, '-R', lane.slug]`.

That `jobs_of` assignment lands **after** the loop that builds it (`asf/merge_queue.py:1305-1308`)
**and after** the `if rerun_jobs:` override below it (`:1309-1310`) — last of the three, or a
caller that passed both keywords would get the by-job ask instead. No call site this design
creates passes both (the cut-short block passes `rerun_run=True` alone, the two existing branches
pass `rerun_jobs=` alone), so nothing breaks either way today; the order is pinned here so it is
not a thing to rediscover when a third caller appears. Everything else about it is untouched: the `MQ_RERUN`
claim written before the host is asked, `RERUN_GRACE_S`, the `MQ_ALARM` re-cut on a second
non-verdict and the `MQ_REFUSED` path when the host says no all stand.

`ids` is derived from the marked checks it is handed (`:1282-1287`) and so **covers** the run ids
`run_cut_short` returned, but it is not always exactly that set: `gone` is built from *every*
required check whose conclusion is in `NONVERDICT` (`:1236-1245`), and a required check that
genuinely concluded `cancelled` is `pending` in `verdict`'s reading, so it never appears among
`why`'s red entries that `run_cut_short` reads. When such a check names a different run, `ids`
holds that run too and the re-run covers it, while the queue's line names only the runs
`run_cut_short` found. That is the right way round — the re-run is at least as wide as the
non-verdict — and the two sets coincide whenever the cancelled and the skipped checks belong to
one run, which is the incident's shape and the common one.

**d. the `behind` branch's own `_nonverdict` takes the snapshot too** — the edit D4 needs to be
true, and the only one of the four that changes a line this card otherwise leaves alone.
`asf/merge_queue.py:1058` is today:

```python
            got = _nonverdict(lane, batch, marked, required, st, rerun_jobs=jobs or None)
```

and becomes:

```python
            got = _nonverdict(lane, batch, marked, required, st, rerun_jobs=jobs or None, wf=wf)
```

Without it the skip-only red that reaches this branch — a required job skipped behind an
unrequired upstream the host cancelled, P3 row 2 — reads `_workflow_runs` twice: the gated read at
the top, then `:1252`'s `wf = _workflow_runs(...) if wf is None else wf` again. `_nonverdict`
already accepts the keyword and already guards on `if wf is None`, so this is the whole change,
and it is what makes S-91806's *"a skip-only red reads the workflow runs listing once"* true on
every path rather than on three of four.

### 3. `asf/merge_queue.py` — who asks, when the CI start queue already did

Beside `_ci_queue_holds`, which answers the same shape of question for the queue's `relief`
cancels:

```python
def _contention_held(lane, batch, sha, wf, said, jobs):
    """What to do about a batch whose cut-short run the CI start queue already read as runner
    contention (:func:`asf.ci_queue._contention`, the claim in ``ci-cancels.json``): ``None``
    when there is no such claim — this judge asks for the re-run itself. Its
    ``contention-rerun`` is left to land, the batch pending, while a run on the sha is live or
    the claim is younger than :data:`RERUN_GRACE_S`; past that, and for a ``contention-refused``
    or a ``contention-alarm`` — the queue has had its answer on that run — the batch is cut
    again, nobody blamed, with the :data:`MQ_ALARM` claim at the ``mq:<sha>`` key so
    :func:`doctor_rows` sees it. Never red: the claim is the host's cancel, not a reading of the
    code (F-0328 D6)."""
```

It reads the claims once (`ci_queue.load_claims(lane.state_dir)`), takes those whose `cause` is
in `(ci_queue.CONTENTION_RERUN, ci_queue.CONTENTION_REFUSED, ci_queue.CONTENTION_ALARM)` and
whose `sha` is the batch sha, and prefers the newest by `at`. "Live on the sha" is
`any(r.get('status') != 'completed' for r in wf or ())` — the same read `_nonverdict` makes at
`:1255`, off the `wf` already in hand. The pending answer is
`('pending', f'{said} — the CI start queue re-ran it as runner contention', None)`.

The re-cut answer is `('recut', f'{said} — contention {cause} on {sha[:9]}, no re-run coming',
None)`, and it writes the same ALARM claim `_nonverdict` writes before its own re-cut — an ALARM
line in the queue's own voice and the claim that makes the line visible outside the pass log:

```python
        members = ', '.join(f"#{m.get('pr')}" for m in batch['members'])
        lane.out(f"merge queue: ALARM {batch['ref']} {said} — contention {cause}, no re-run "
                 f'coming; cut again ({members}), no member blamed')
        ci_queue.claim_cancel(lane.state_dir, f'mq:{sha}', MQ_ALARM, ci_queue._now(), sha=sha,
                              ref=batch['ref'], jobs=jobs,
                              prs=[m.get('pr') for m in batch['members']], why=said)
```

`jobs` is the sixth parameter — `sorted(skip)`, the skipped required job keys §2a bound to gate
the read and which `run_cut_short` re-derives from the same `why`; it is the same `jobs=` value
`_nonverdict` would have claimed on the path not taken. `skip` is non-None on every path that
reaches this call, because `run_cut_short` returns None whenever `_skip_only` does. `members` and the claim's keywords are
built exactly as `_nonverdict` builds them at `:1279-1281`, so the two ALARM claims read back
identically and `doctor_rows` needs no new case.

Without that claim the drop is a line in one pass's output and nothing else: `doctor_rows`
(`asf/merge_queue.py:1329-1347`) builds its `queue cancels` row **only** from `ci-cancels.json`
entries whose `cause` is `MQ_ALARM` (`:1341-1342`), and `_contention_held` is the one ALARM path
in this design that does not reach `_nonverdict`'s own claim (`:1279-1280`, `:1292-1293`) — so
`asf doctor` would stay green on the one shape D6 hands off, which is the louder half of D5's
bound missing. This is also what keeps `## Records` and D10 true as written: they justify minting
no new cause *because* the existing ALARM raises the existing row.

It does not cross P6. `_nonverdict` keys this claim `f'mq:{sha}'`, by batch sha and not by run id
(`:1279`, `:1292`), so it cannot overwrite the start queue's contention claim at the run-id key
and cannot silence `_explain`, whose skip is by `str(rid)` (`asf/ci_queue.py:3079-3080`). What D6
forbids is a merge-queue claim **on that run**; this is a claim on the batch's sha.

### 4. `asf/ci_queue.py` — the third cause, named; the other two, used

sentence:

> A **run** the host cut short is the same non-verdict one level up: when every red entry of a
> verdict is a required check `skipped` and the runs those skips belong to concluded `cancelled`
> or `timed_out` (:func:`run_cut_short`), nothing judged the batch — whatever cut the run, a
> skipped job is no reading of the members' code. Where the `needs:` graph can name the job the
> host cut (:func:`skipped_behind`) that job is re-run and this never fires; where it cannot, the
> run is re-run whole once per batch sha, then the batch is cut again. A cancel the CI start queue
> already read as runner contention (:func:`asf.ci_queue._contention`) is its re-run to own: the
> queue waits for it, and cuts again when it was refused or alarmed.

### What it looks like when it is there

The card's pass, line for line:

```
ci queue: run 601 on batch/20261008-163914-e6eb3a8 at e6eb3a8 cancelled by the host — job rules
  hit its 10 min timeout but its p50 is 3 min: runner contention, not a verdict — re-run of its
  failed jobs requested (once per head)
merge queue: batch/20261008-163914-e6eb3a8 gate (skipped), gate-tests (skipped), m6-e2e (skipped)
  — the host cut short run(s) 601: the required jobs judged no code
merge queue: batch/20261008-163914-e6eb3a8 @ e6eb3a8 pending — gate (skipped), gate-tests
  (skipped), m6-e2e (skipped) — the host cut short run(s) 601: the required jobs judged no code —
  the CI start queue re-ran it as runner contention
```

PRs #1294, #1295 and #1254 stay in the batch. No ledger row, no `landing-gate` hold, no split, no
member blamed. With no contention claim on the run, the middle line is followed by
`merge queue: … rerun once (…; run(s) 601)` and the batch is pending on the queue's own re-run;
a second cut-short run on the same sha cuts the batch again with an ALARM and a `queue cancels`
doctor row.

Had the start queue's re-run been refused instead, the third line is the drop rather than the
wait, and it raises the same row:

```
merge queue: ALARM batch/20261008-163914-e6eb3a8 gate (skipped), gate-tests (skipped), m6-e2e
  (skipped) — the host cut short run(s) 601: the required jobs judged no code — contention
  contention-refused, no re-run coming; cut again (#1294, #1295, #1254), no member blamed
```

and `asf doctor` carries `merge queue ALARM batch/20261008-163914-e6eb3a8 @ e6eb3a8: … — no
verdict after one re-run, cut again (#1294, #1295, #1254)` until `ALARM_WINDOW_S` passes. The
three PRs are back in the pool, blameless, and the next cut starts a fresh run on a fresh sha.

### S-91805: a workflow run the host cut short is no verdict, and one reader says so

Design §1 — `_skip_only` and `run_cut_short`, pure, beside `skipped_behind` and not folded into it
(D1, D2; P2, P4, P11). Unit cases only: the condition is the whole Story, and it is the one piece
of this change that can be asserted without a batch, a git repo or a fake host.

- [ ] a red whose every red entry is a required check that concluded skipped, on a run whose conclusion is cancelled, comes back with those checks re-marked cancelled and that run's id
- [ ] the same shape on a run whose conclusion is timed out comes back the same way, because both conclusions are in the non-verdict set
- [ ] a red that names one required check a runner judged beside the skipped ones comes back as nothing at all
- [ ] a required job with one matrix leg a runner judged failure and a sibling leg of the same job skipped comes back as nothing at all, because the test is over the red entries and not their job keys
- [ ] a skipped required check on a run that concluded failure comes back as nothing at all
- [ ] a skipped required check on a run that concluded success comes back as nothing at all
- [ ] a skipped required check whose details link names no run id comes back as nothing at all
- [ ] a skipped required check whose run is absent from the runs listing comes back as nothing at all
- [ ] skipped required checks spread across two cut-short runs come back with both run ids, sorted
- [ ] two skipped legs of one job on two runs, one of them cut short and one of them healthy, come back as nothing at all, because every skipped check is read and not only the first
- [ ] a check the product does not require is neither read nor re-marked, whatever it concluded, because the names read come from the red entries and those are required by construction
- [ ] a matrix leg answers for its job, so a skipped leg named with a suffix is read as its job key
- [ ] the runs passed in are not mutated: the marking is a copy, and the caller's list is unchanged
- [ ] a verdict that is green or pending, or a red with no skipped check in it at all, comes back as nothing at all

### S-91806: the batch judge reads the run after the graph and before the blame, re-runs it whole once, then cuts again

Design §2 — the ordering, `_nonverdict`'s `rerun_run`, and the one gated `_workflow_runs` read
handed down (D3, D4, D5; P1, P3, P7, P8). This is the card's incident as an assertion: the shape
P1 dropped and split now survives.

- [ ] a batch whose required jobs are only skipped on a host-cancelled run stays in flight, pending, and is not dropped
- [ ] its whole run is re-run once, by run id, with neither the failed nor the job flag
- [ ] no member is sent back, no landing-gate hold is written and no correction names a skipped job
- [ ] the batch is not split, and no second cut of halves is pushed
- [ ] no red ledger row is written for the batch
- [ ] the one re-run is claimed in the cancels file under the existing re-run cause, keyed by the run id, before the host is asked
- [ ] a second cut-short run on the same batch sha cuts the batch again, raises an alarm line naming the batch and blames no member
- [ ] the re-cut batch carries a new sha, and the trunk has not moved
- [ ] a required job skipped behind an unrequired upstream the graph can name keeps its by-job re-run, and the whole-run re-run is not asked
- [ ] a required job skipped behind an unrequired upstream that a runner judged, on a run the host cut short, is re-run as a whole run and is never announced as the real cause
- [ ] an ordinary red whose required job a runner failed reads the workflow runs listing not at all, and is judged exactly as it is today
- [ ] a skip-only red reads the workflow runs listing once, however many of the four readers below the gate need it
- [ ] a required job skipped behind an unrequired upstream the host cancelled reads the listing once too, not twice, so the branch that re-runs by job shares the one snapshot
- [ ] a run listing the host cannot read leaves the batch judged exactly as it was before this change
- [ ] the line the queue prints names the run ids and says the required jobs judged no code
- [ ] the skipped checks reach no flake settle, so no quarantine entry is written and no attempt is spent

### S-91807: a contention cancel is the CI start queue's re-run to own, and its refusal cuts the batch again

Design §3 and §4 — `_contention_held`, and the three contention causes named where they are used
(D6, D7; P5, P6, P9). The two halves of the queue stop asking the host the same question twice,
and stop waiting for each other for ever.

- [ ] with a contention re-run claim on the batch's sha the judge asks the host for nothing and the batch stays pending
- [ ] it writes no claim of its own on that run, so the start queue's once-per-head guarantee is still readable in the cancels file
- [ ] the pending line names runner contention and the start queue as the half that re-ran it
- [ ] a contention re-run claim older than the re-run grace with nothing live on the sha cuts the batch again, with an alarm line and no member blamed
- [ ] a contention re-run claim older than the grace with a run still in progress on the sha leaves the batch pending
- [ ] a contention refused claim cuts the batch again at once, never red
- [ ] a contention alarm claim cuts the batch again at once, never red
- [ ] a contention claim that cuts the batch again writes the queue's existing alarm claim under its batch-sha key, raises the queue cancels doctor row, and leaves the start queue's own claim on the run untouched
- [ ] a contention claim for another sha is not this batch's and is ignored
- [ ] the newest claim decides when more than one names the sha
- [ ] the refused cause is a named constant in the start queue module and the claim its one call site writes is read back by that name
- [ ] the alarm cause the start queue writes is the constant that already existed, and the string on disk is unchanged
- [ ] all three contention constants are keys of the honoured-cause table that map to timeout, and members of the runner-claims tuple the red metrics read, so the read side still classifies every claim the start queue writes

### S-91808: a job a runner judged, a leg a runner judged, and a path-filtered skip on a healthy run, are still red

Design §1's refusals, pinned as batch-level cases (D9; P11; the 2026-09-26 incident). The rule
must not become a way for a real red to be forgiven by cancelling its run.

**Two of these shapes do not reach red in one pass, and the cases must not pretend they do.** A
required check that concluded `failure` carries a job id, and a check that carries a job id is one
`flake.triage` re-runs once before any blame: both shapes below end their first pass at
`pending — re-running <job> (flake triage)`, with nothing sent back. That is the correct behaviour
and it is *also* the proof the rule declined — a cut-short batch never reaches the triage at all
(§2b returns first, and D1's branch returns before `flake.settle`). So each of the two is pinned
twice: once on the first pass, where the right assertion is that the triage has it, and once with
the triage's one re-run already spent, where the red and the culprit land. Spending it is a
fixture step, not a wait: seed `flake.load(state_dir)['reruns'][f'{sha}|{name}'] = {'name': name,
'sha': sha, 'attempts': 1, 'at': flake._iso(flake._now())}` and `flake.save` before the pass,
where `name` is the check run's own name — the matrix leg's suffix included, so `gate-tests (b)`,
not `gate-tests`, because the triage keys on the check and not on its job
(`asf/flake.py:518-519`). The precedent is
`tests/test_merge_queue.py:980-987`, `test_a_hold_the_triage_re_ran_stands`.

- [ ] a required job that failed on a runner inside a cancelled run is not read as a non-verdict: its first pass is held by the flake triage, pending, with no whole-run re-run asked and no member sent back
- [ ] the same job, with the triage's one re-run already spent, drops the batch as red and sends its culprit back, exactly as it does today
- [ ] a required job with one leg a runner judged and a sibling leg skipped on a cancelled run is not read as a non-verdict either: its first pass is held by the flake triage on the judged leg, and no whole-run re-run is asked
- [ ] the same leg, with the triage's one re-run already spent, drops the batch as red and sends its culprit back
- [ ] a required job skipped by its own path filter on a run that completed successfully drops the batch as red, which is the rule a skipped required check is not green
- [ ] a required job skipped behind an unrequired upstream that failed on a healthy run is still named as the real cause and still read by the triage and the blame
- [ ] a required job lost with its runner is still re-run by job, not by run, so the existing runner-loss path is unchanged
- [ ] the merge queue module's existing suites pass whole, with no assertion relaxed
