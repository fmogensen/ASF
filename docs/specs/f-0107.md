# F-0107 — `asf install`: one command from zero to a ticking factory (from a release tag, doctor green)

Epic: E-0001 — ASF 0.1 — a working factory. Branch: `spec/F-0107`.

The card was written on 2026-09-24, when nothing took a machine from zero to a ticking factory.
Since then `tools/install.sh`, `asf upgrade`, the version stamp and the pinned clocks landed, so
four of its nine acceptance bullets are already true in this checkout (see Preconditions, with the
anchor for each). What is still missing is the *zero* half: the installer refuses to start until
the operator has hand-written `~/.ASF/config.yaml` and `~/.ASF/products/<p>.yaml`
(`tools/install.sh:135-136`), it never runs `asf init`, it touches no worker account, the
`/asf:*` plugin exists only inside a checkout (B-0047), there is no tick dry run, there is no
`asf uninstall`, and the ref it pins by default is `main`'s head rather than a release
(`tools/install.sh:48`).

After this change one line installs the factory from the newest release tag and hands over to a
new command, `asf install`, which writes the operator config, adopts the product, finds or files
the worker account, installs the hooks, the clocks and the plugin, and ends on a green
`asf doctor` and one `asf tick --dry-run`. Running it again repairs. `asf uninstall` takes the
jobs, the hooks and the plugin away and leaves the record, the repos and the config exactly where
they were.

## Decisions

### In

- **The seam.** `tools/install.sh` keeps only what must run before the package exists: the
  prerequisite check, resolving the ref, and the `pipx install --force git+<url>@<ref>` it already
  performs while holding the product's tick lock. Everything after that becomes
  `asf install --product <p> [flags]`, which the bootstrap `exec`s with its own flags passed
  through. Steps 2-6 of today's script move into Python unchanged in behaviour.
- **`asf install --product <p>`** — a new module `asf/install.py`, registered through
  `asf.init.register_commands` (`asf/cli.py:282`). Flags: `--repo DIR`, `--repo-url URL`,
  `--record DIR`, `--record-url URL`, `--scheduler {launchd,cron,none}`,
  `--account NAME[:CONFIG_DIR]` (repeatable), `--fake-workers`, `--console-permissions
  user|repo`, `--allow-checkout`, `--yes`. On a tty a missing `--repo`, `--record` or
  `--scheduler` is asked for, once each, with the default in the prompt; with `--yes`, or off a
  tty, a missing one that has no default is a `NEEDS OPERATOR` line and a non-zero exit before
  anything is written.
- **The package is never installed by `asf install`.** It reports what it is
  (`asf.cli.version_string`) and, when that is a checkout or editable install, refuses with one
  `NEEDS OPERATOR` line unless `--allow-checkout` is given. "From a release tag, not a checkout"
  is enforced here, where the running package can be identified, rather than trusted to the
  shell.
- **`~/.ASF/config.yaml`** is written by `asf install` when it is absent, from a template that
  lives in the package (`asf.install.CONFIG_TEMPLATE`): `default_product`, `scheduler.kind`,
  `capacity.total.sessions`, `worker_pool.backend`, `worker_pool.models` (three `# TODO` model
  ids) and `worker_pool.accounts`. An existing file is never rewritten: the keys it lacks are
  printed as the diff that was not made, the way `asf init` prints a product-file diff
  (`asf/init.py:1-12`).
- **`~/.ASF/products/<p>.yaml` and the record stay `asf init`'s** (`asf/init.py:328-334`).
  `asf install` runs `asf init --product <p> [--repo DIR] [--backlog DIR]`, which discovers the
  product file, lays down or adopts the record, writes the record's git hooks and prints the
  first roadmap.
- **The repos.** `--repo` and `--record` are directories on this machine. `--repo-url` /
  `--record-url` clone into them, and only when the directory does not exist; an existing
  directory is read, never written to. No default path is invented: without `--repo` the cwd is
  the product repo (`asf init`'s own default).
- **The worker account.** `--account NAME[:CONFIG_DIR]`, repeatable, writes one stanza per
  account (`role: local`, `cap: 2`, `config_dir`, `home`). With no flag, `<ASF_HOME>/accounts/*`
  is read: each directory that holds the runtime's credential file becomes one stanza. With
  neither, one stanza is written with its `auth_env` commented out and a `NEEDS OPERATOR` line
  names the one human act (`claude setup-token`) — the install carries on, and the doctor's
  `worker secrets` row (`asf/doctor.py:268`) stays red until it is done. `--fake-workers` writes
  `backend: fake` and no account at all: that is what `sample/config.yaml` uses.
- **`asf plugin install [--dir DIR]`** — a third action beside `build|check`
  (`asf/plugin_build.py:188-192`) — writes the whole marketplace tree from the CLI's own parser
  (`plugin_build.expected_files`, `asf/plugin_build.py:133-146`) into `<ASF_HOME>/plugin` by
  default. Nothing is read from a checkout, so a `pipx` install has the `/asf:*` skills (B-0047).
- **The console half of the plugin install** is one `NEEDS OPERATOR` line carrying the two
  commands with the written path (`/plugin marketplace add <ASF_HOME>/plugin`, then
  `/plugin install asf@asf`). When the worker runtime's own CLI offers a non-interactive plugin
  install, probed once at run time, `asf install` runs it instead and says which it used.
- **Idempotence, and the failure discipline.** The prerequisite, config and adopt steps abort
  (nothing after them can work); hooks, clocks, plugin, console permissions, doctor and the dry
  run each record a failure and let the rest run, exactly as `tools/install.sh` does today. Every
  step reports `wrote` / `already in place` / `repaired`, and a second run of the same command
  writes nothing new: the clocks are made to match the file (F-0083), `hooks install` merges
  (`asf/hooks.py:252`), the plugin tree is regenerated byte-identical, and `asf init` refuses to
  overwrite.
- **The verification tail.** `asf doctor --product <p>` — with the pre-existing-RED baseline the
  script already takes, so only a RED this install caused fails it — then
  `asf tick --product <p> --dry-run` (`asf/tick/tick.py:344-346`), which works on a throwaway copy
  of the state directory and launches nothing. Both count as steps.
- **`asf uninstall --product <p> [--dry-run]`.** Boots out and removes every loaded job labelled
  `<label_prefix>.<p>.*`, the never-declared `ci-queue` clock included (`asf.scheduler.uninstall`,
  `asf/scheduler.py:477`; `loaded_jobs`, `:614`); removes the hook entries ASF wrote from every
  account settings file (`asf/hooks.py:246,276`) and the `pre-commit` / `pre-push` files ASF wrote
  in the product repo and in the record (`hooks.is_git_hook_ours`, `asf/hooks.py:92`); removes the
  generated plugin tree under `<ASF_HOME>/plugin`. It prints one row per target — `removed`,
  `absent`, or `left (not ours)` — and ends with the one command it will not run itself
  (`pipx uninstall asf-factory`).
- **The default ref is a release.** With no `ref` argument the bootstrap resolves the newest
  `v<major>.<minor>.<patch>` tag on the remote, ordered numerically, and pins that. `main` or a
  sha as the second argument still pins exactly that. The ordering rule has one owner,
  `asf.install.newest_tag(refs)`; the bootstrap's inline `python3` applies the same rule, and one
  test pins the two answers equal on one fixture remote.
- **`asf upgrade --to <sha|tag>`** is the documented name for the existing `--ref`
  (`asf/upgrade.py:625`), which is kept as an accepted alias. A tag value is resolved to its
  commit before the CI-red guard reads CI (`upgrade.refuses`, `asf/upgrade.py:437-445`) and passed
  to `pipx` as given. The clock reload (`upgrade.reload_clocks`, `asf/upgrade.py:463-489`) and the
  doctor's installed-sha-against-trunk row (`doctor.check_drift`, `asf/doctor.py:481-490`) already
  exist; this card proves them, it does not rebuild them.
- **Five lines of README**, and a guide that no longer opens with two files to copy by hand
  (`docs/guide/getting-started.md:15-45`).

### Out

- Installing `pipx`, `git`, `gh`, `python3` or the worker runtime. Each is checked and named in
  one `NEEDS OPERATOR` line; none is installed.
- Minting, reading or copying a credential. `auth_env` files stay the operator's own
  (`docs/config.example.yaml`); the installer writes their paths, never their contents.
- Writing anything under the worker runtime's own configuration directory. The plugin tree goes
  under `<ASF_HOME>`; the two `/plugin` console commands stay the operator's.
- A doctor row for the plugin, and any plugin version check. The install prints what it wrote.
- `pipx uninstall`. `asf uninstall` would be removing the interpreter running it; the line is
  printed for the operator.
- Purging `~/.ASF` (config, `products/`, `state/`, `logs/`) or any record card. An uninstall is
  not a wipe, and a reinstall must find the config it left.
- A second product's configuration beyond its own `products/<p>.yaml` and the account stanza it
  needs. One `asf install` run is one product.
- The `systemd` / `gh-actions` / `claude-routines` scheduler adapters. `--scheduler` takes what
  `asf scheduler` implements (`launchd`, `cron`, `none`); any other kind keeps rendering the
  `NEEDS OPERATOR` marker it renders today (`asf/scheduler.py:414`).
- Changing what a tick does, how a job is rendered, the drift row, or the version stamp. All four
  already carry the card's bullets 7, 9 and 10 — see Preconditions.
- Windows.

## The design

### 2.1 `tools/install.sh` — the bootstrap, and nothing more

```
bash tools/install.sh <product> [ref] [-- <asf install flags>]
curl -fsSL <raw url>/tools/install.sh | bash -s -- <product> [ref] [-- <flags>]
```

What stays: the `pipx` / `git` prerequisite check; resolving `ref`; the `pipx install --force
git+<url>@<ref>` call made while holding `<ASF_HOME>/state/<product>/tick.lock`, bounded by
`ASF_INSTALL_LOCK_WAIT_S`; the `<ASF_HOME>/logs/install.log` line; the `pipx ensurepath` check;
and the whole-script `{ … }` wrapper that makes the file safe to rewrite mid-run.

What changes: with no `ref`, the newest release tag is resolved from
`git ls-remote --tags --refs <url> 'v*'` and ordered by D6's rule, and the script says which tag
it chose (`install: product <p>, release v0.1.1 from <url>`); `ASF_REF=main` or a second argument
still pins a branch head or a sha.

What goes: steps 2-6. After the package is on `PATH` the script `exec`s

```
asf install --product <product> [the flags after --]
```

so there is one implementation of every step and one exit status. The baseline-doctor reader, the
clock read-back retry and the console-permissions offer move into `asf/install.py` with their
behaviour intact — including the rule that a RED the doctor showed *before* this install is a
warning naming it as pre-existing, and only a new RED fails the step.

### 2.2 `asf install` — the steps

One line per step, in order, each `ok` / `wrote …` / `already in place` / `repaired …` /
`FAILED … (exit N)`, then a summary table and a single exit status (0 when every step passed).

| # | step | abort? | idempotent because |
| --- | --- | --- | --- |
| 1 | the host: `git`, and `gh` unless the product has no PR host | yes | reads only |
| 2 | this `asf`: the release and commit it is; a checkout install refuses without `--allow-checkout` | yes | reads only |
| 3 | `~/.ASF/config.yaml`: written from the template when absent, else the diff not made | yes | never overwrites |
| 4 | the repos: `--repo-url` / `--record-url` cloned into a directory that does not exist | yes | an existing directory is left alone |
| 5 | `asf init --product <p> [--repo] [--backlog]` — the product file, the record, the record's git hooks, the first roadmap | yes | `asf init` adopts an ASF-shaped record as is and never rewrites the product file |
| 6 | the account: `--account`, else detection, else one stanza and the operator line | no | an account already in `worker_pool.accounts` is left as it stands |
| 7 | `asf hooks install --product <p>` | no | `hooks.merge` merges and keeps unrelated keys |
| 8 | `asf scheduler install --product <p>`, then every declared clock read back; one retried bootstrap before it fails, naming the label | no | a whole-file install makes the loaded jobs match the file (F-0083) |
| 9 | `asf plugin install` | no | the tree is regenerated byte-identical |
| 10 | `asf console-permissions offer` (printed), or `install --scope <s>` with `--console-permissions` | no | the writer is idempotent and keeps unrelated keys |
| 11 | `asf doctor --product <p>`, against the baseline read before step 3 | no | reads only |
| 12 | `asf tick --product <p> --dry-run` | no | a throwaway copy of the state directory; pushes nothing, launches nothing |

The last lines are the plugin's two console commands (or what the probe ran instead), and
`asf install: done` — or one `NEEDS OPERATOR` line per failed step.

### 2.3 The config template

`asf.install.CONFIG_TEMPLATE` is one `str` with `{}` slots for `default_product`,
`scheduler.kind`, the sessions total and the account block. Written only when
`<ASF_HOME>/config.yaml` is absent; the directory and `<ASF_HOME>/products/` are created. Its
comment header points at `docs/config.example.yaml` for every key it does not write. Nothing it
writes is a `# TODO` except the three `worker_pool.models` ids, which no discovery can fill.

### 2.4 The account

`asf.install.detect_accounts(home)` returns `[(name, config_dir)]` for each directory under
`<ASF_HOME>/accounts/` holding the runtime's credential file; `--account` overrides it. Each
account is written as `name`, `role: local`, `cap: 2`, `config_dir`, `home`, with `auth_env`
commented. Nothing reads a credential's contents, and no account name reaches the product repo or
the record.

### 2.5 `asf plugin install`

`plugin_build.install(dest)` writes `expected_files` relative to `dest` (default
`<ASF_HOME>/plugin`): `.claude-plugin/marketplace.json` at the top, then
`plugin/.claude-plugin/plugin.json`, `plugin/skills/<name>/SKILL.md` for every view and dialogue,
and `plugin/hooks/hooks.json`. Strays under `plugin/skills` in the destination are removed — a
skill dropped from the CLI must not linger in an installed tree. `build` and `check` keep reading
`default_plugin_dir` (the checkout); `install` never does.

### 2.6 `asf uninstall`

```
asf uninstall --product <p> [--dry-run]
```

| target | what happens | left alone |
| --- | --- | --- |
| clocks | every loaded job labelled `<prefix>.<p>.*` is booted out, its plist removed | another product's jobs; a legacy label the operator still declares |
| runtime hook entries | the entries `hooks._is_ours` recognises are dropped from every account settings file | every other key in that file |
| git hooks | the `pre-commit` / `pre-push` files ASF wrote in `repo_dir` and `backlog_dir` are removed | a foreign hook — reported as `left (not ours)` |
| plugin tree | `<ASF_HOME>/plugin` is removed | the checkout's `plugin/` |
| the record, the repos, `~/.ASF/config.yaml`, `products/`, `state/`, `logs/` | untouched | — |

`--dry-run` prints the same table and removes nothing. The final line is
`asf uninstall: the package itself: pipx uninstall asf-factory`.

### 2.7 `asf upgrade --to`

`--to` is added with `--ref` as its alias (`dest='ref'`), and the help names a sha or a tag. When
the value is not a 40-hex sha it is resolved with `git ls-remote <url> <ref>` before
`upgrade.refuses` reads CI, so a tag is guarded the same way a sha is; `pipx` receives the value
as the operator gave it, so `direct_url.json` records the tag and `version_string` reports the
release (`asf/cli.py:91-104`). The clock reload and the doctor's drift row are unchanged.

### 2.8 The README and the guide

`README.md`'s Install section becomes five lines or fewer — the prerequisites sentence, one fenced
`curl … | bash -s -- <product> -- --repo <dir> --record <dir> --scheduler launchd` line, and one
sentence naming `asf doctor` and the two `/plugin` commands. `docs/guide/getting-started.md`
loses "copy these two files" as step 1 and gains the flag table; `docs/guide/upgrading.md` names
`--to`; `docs/guide/troubleshooting.md` gains the three `NEEDS OPERATOR` lines the installer can
print.

## Records

- **`<ASF_HOME>/config.yaml`** — written once, when absent: `default_product`, `scheduler.kind`,
  `capacity.total.sessions`, `worker_pool.backend|models|accounts`. Never rewritten.
- **`<ASF_HOME>/products/<p>.yaml`** — written by `asf init`, unchanged by this card.
- **`<ASF_HOME>/plugin/`** — the generated marketplace tree: `.claude-plugin/marketplace.json`,
  `plugin/.claude-plugin/plugin.json`, `plugin/skills/<name>/SKILL.md`, `plugin/hooks/hooks.json`.
  Removed by `asf uninstall`.
- **`<ASF_HOME>/logs/install.log`** — one tab-separated line per bootstrap run
  (`<utc>\t<product>\t<ref>`), as today; `asf release-readiness` counts them. `asf uninstall`
  appends one line of the same shape with the ref `uninstall`, so the log reads as the machine's
  install history rather than half of it.
- **The clocks** — `~/Library/LaunchAgents/<prefix>.<p>.<clock>.plist` per declared clock, and
  `<ASF_HOME>/logs/tick-<p>-<clock>.log` once each first runs (F-0083). `asf uninstall` removes
  the plists and leaves the logs.
- **The hooks** — the runtime hook entries in each account's settings file, and `pre-commit` /
  `pre-push` in `repo_dir` and `backlog_dir`. Both are written by the existing writers.
- **The record**: nothing. An install is an operator action on one machine, not a factory state
  change — the same rule F-0083 states for installing a job. No card, no event, no
  `metrics/*.jsonl` line is written by `asf install` or `asf uninstall`. The dry run's tick works
  on a throwaway copy and writes nothing anywhere.
- **Printed output** — the step lines, the summary table, the doctor table and its stamp, the dry
  run's plan, and one `NEEDS OPERATOR: <what> — <the command>` line per human act: a missing
  prerequisite, a missing account token, the two `/plugin` commands, a clock still not loaded
  after the retry, and `pipx uninstall asf-factory`.
