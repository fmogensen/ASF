# F-0284 — a land request may wait on a check, never on a check that cannot start

GitHub runs no `pull_request` workflow on a pull request its own merge reads
`mergeable: CONFLICTING`. The required checks are therefore never created, `verdict` reports each
one as `(not started)`, and `requested_ready` prints

```
merge queue: asf land PR #N pending at <head> — gate (not started), gate-tests (not started)
```

once a pass, for as long as the head stands. Nothing bounds it: no run is coming, so no run ever
arrives to end the wait. The card's sighting is that line under a `land --priority` request — a PR
at a head the host read `CONFLICTING` with zero runs and its last run on an older head — which is
the most expensive shape it has, because a priority request is first in line and everything behind
it is waiting for a verdict that cannot be reached.

The CI queue's silence in the sighting is a consequence, not a second defect. A `pull_request` run
is GitHub's to start; it is never a start the factory asks the CI queue for, and the CI queue holds
no conflict read at all (P3). There is nothing for it to list.

**Half of this card is landed, and neither half covers the shape the card was cut from.** A PR with
no factory branch prefix has been marked red at once since #613 (P4), and a factory branch the lane
holds a run for has gone BACK to its conflict rebuild since the F-0287 fix (P5) — which landed
2026-10-07 23:17, hours *after* the 14:2x sighting. What neither covers is the branch in between:
a factory-prefixed branch the lane holds **no** run for satisfies neither guard and falls through to
the endless pending line, measured here (P6). And both guards rest on a single read of GitHub's own
`mergeable`, which is `UNKNOWN` until GitHub computes it — so a head that git itself will not merge
onto the trunk waits silently too, also measured (P9).

This spec closes both: a land request may wait on a check, never on a check that cannot start.

### In

1. **One question, asked once per request per pass: can this head's required checks ever start?**
   `merge_read(lane, n, branch)` returns the host's `mergeable` *and* git's own merge of the branch
   onto the trunk, as one answer. GitHub's `CONFLICTING` is decisive, because it is GitHub's own
   merge that gates the workflow (P2). Where GitHub has not answered — `UNKNOWN`, unreadable — git
   answers instead (P9, P10), the idiom the direct path already uses.
2. **Three outcomes, and waiting is only one of them.** A factory branch the lane holds a run for
   goes BACK to its conflict rebuild, exactly as it does today (P5). Every other conflicting
   request is red. A request waits only when the merge is clean.
3. **The red's `why` names who moves the head.** A PR with no factory prefix is its author's, and
   its text does not change by a byte (P15). A factory branch no run holds is nobody's — an
   `asf land` request is never factory work (P7) — so its `why` says that the lane will not rebase
   it and what the operator can do instead.
4. **A wait on checks that have not started says what it is waiting for.** When no required check
   has started and GitHub has not answered its own mergeability, the pending line names that
   (`GitHub reads mergeable: UNKNOWN; git merges … clean`). The wait is then a fact an operator can
   read, not a line that looks identical to a wait that will never end.
5. **The conflicting files, read once.** `merge_read` returns the paths `git merge-tree` names, and
   `_conflict_back` is handed them rather than reading them again.

### Out

- **No watchdog, no deadline, no escalation on a pending request.** Nothing counts passes or opens
  an operator card, because after this change a wait that cannot end is not a wait: it is a red or a
  BACK on the pass that sees it. A bound on a *legitimate* wait is a different card.
- **No change to the CI queue** (P3). It never listed the PR because nothing asked it to, and a
  `pull_request` run is not a start it admits. Named here so the next reader does not read the
  card's second clause as asking for one.
- **No change to `verdict`, to `(not started)`, or to the required set.** `(not started)` is the
  truth about the check; the defect was acting on it, not reporting it.
- **No new state file, no new command, no new convention key, no operator question.**
  `land-requests.json` keeps its shape — a `red` of `kind='conflict'` is what #613 already writes.
- **The factory never rebases a PR it does not own.** A PR with no factory prefix stays its
  author's; the queue tells it and moves on.
- **`asf land --priority` keeps exactly its current meaning** (P14): it orders the line. It gains no
  conflict path of its own.
- **The host's `CONFLICTING` is never overridden by a clean `merge-tree`** (P11). Git's answer is
  only consulted where GitHub has given none.
- **The landed halves are not re-implemented.** P4's red text and P5's BACK path stand; only their
  guards and the read beneath them change.

## The design

All of it is in `asf/merge_queue.py`. No other file changes.

### 1. The one read — replacing `conflicts_with_trunk`

```python
#: what the two merges say about PR's head: whether its required checks can ever start
#: (:func:`merge_read`), the paths git names, and GitHub's own ``mergeable`` word
Merge = collections.namedtuple('Merge', 'conflicting files host')


def merge_read(lane, n, branch):
    """:data:`Merge` for PR ``n`` on ``branch``: can this head's required checks ever start?

    ``conflicting`` is True when they cannot. GitHub runs no ``pull_request`` workflow on a PR its
    own merge reads ``mergeable: CONFLICTING``, so that word is decisive — it is GitHub's merge
    that gates the workflow, and a clean ``git merge-tree`` never overrides it (a merge driver
    GitHub cannot apply: :func:`asf.harvest.lane.host_reads_dirty`). ``MERGEABLE`` is decisive the
    other way: the checks are coming, the head is simply waiting for them.

    Where GitHub has not answered — ``UNKNOWN``, which is what it reads until it computes the
    merge, or an unreadable answer — git answers instead, on the refs this pass has already
    fetched: a head git will not merge onto the trunk is a head whose checks will not start either,
    and waiting for GitHub to agree is the silent forever this card is about (F-0284).

    One host read per request per pass; ``files`` are the paths ``git merge-tree`` names, so the
    caller never reads them twice."""
    host = H.gh_json(['pr', 'view', str(n), '-R', lane.slug, '--json', 'mergeable'], None)
    host = host.get('mergeable') if isinstance(host, dict) else None
    files = lane_mod.conflict_files(lane.repo, lane.trunk, branch, fetch=False) if branch else []
    if host == 'CONFLICTING':
        return Merge(True, files, host)
    if host == 'MERGEABLE':
        return Merge(False, [], host)
    return Merge(bool(files), files, host)
```

### 2. The three outcomes — in `requested_ready`

The two guards at `:2661-2676` become one read and one decision. `_none_started(why)` is the
predicate already spelled inline at `:2656`, lifted so this block and that one read the same thing.

```python
def _none_started(why):
    """True when ``why`` (a pending :func:`verdict`) says every required check has no run at all —
    the only pending shape in which no run may ever arrive."""
    return bool(why) and all(w.endswith('(not started)') for w in why.split(', '))
```

### 3. The red's `why` — who moves the head

```python
def _conflict_why(lane, b, n, run, files):
    """The red's ``why`` for an `asf land` PR whose required checks can never start. What differs
    is who moves the head: a PR with no factory prefix is its author's — this text is a landed
    surface the status view renders and the suite pins, and it does not change. A factory branch
    the lane holds no run for is nobody's: an `asf land` request is never factory work
    (:meth:`asf.harvest.lane.Lane.branch_facts`), so the lane does not rebase it and the line says
    so rather than leaving an operator to infer it from silence."""
    if lane.conv.branch_kind(b) and run is None:
        where = f' in {", ".join(files)}' if files else ''
        return (f'conflicts with {lane.trunk}{where} and no session run holds {b} — an asf land '
                f'request is never factory work, so the lane does not rebase it: rebase the '
                f'branch onto origin/{lane.trunk} and push, or hand its card back to a session')
    return f'conflicts with {lane.trunk} — merge or rebase it'
```

### 4. `_conflict_back` is handed the files it used to read

```python
def _conflict_back(lane, b, n, head, run, files):
    """… ``files``: the conflicting paths :func:`merge_read` already read (empty — ``host_dirty`` —
    when only GitHub's own merge says so: a merge driver it cannot apply)."""
    rec = lifecycle.lane_of(run)
    f = {'branch': b, 'item': rec.get('item') or (run or {}).get('item'),
         ...
         'conflict': list(files), 'host_dirty': not files, 'correction': None}
```

### What it looks like when it is there

A conflicting land request is gone from the pending lines within one pass of the head being seen,
and it is gone in one of exactly two ways:

```
merge queue: asf land PR #1143 conflicts with main at 0c14763cc3a1 — back to the lane for a rebase
merge queue: asf land PR #1143 red at 0c14763cc3a1 — conflicts with main in a.txt and no session
  run holds worker/F-0284 — an asf land request is never factory work, so the lane does not rebase
  it: rebase the branch onto origin/main and push, or hand its card back to a session
```

and a request that really is waiting says what for:

```
merge queue: asf land PR #1143 pending at 0c14763cc3a1 — gate (not started), gate-tests (not
  started); GitHub reads mergeable: UNKNOWN and git merges worker/F-0284 onto main clean — the
  checks have not started yet
```

## Stories

Two Stories, declared here from this session's `BACKLOG_ID_RANGE` (`S:73904-73953`) for the record
to mint (`asf.record.idcheck.declared_stories`). The Feature holds none yet. Neither has landed: at
`950173683` a factory-prefixed branch the lane holds no run for falls through both guards to the
endless pending line (P6), and the read both guards rest on takes `UNKNOWN` for mergeable (P9).

They are ordered, and the order is a dependency: S-73904 fixes what is done with the host's answer,
S-73905 widens what that answer is. S-73904 alone leaves the `UNKNOWN` wait silent; S-73905 alone
would feed git's answer into the same hole.

The headings and checkbox lines below carry **no backticks** on purpose:
`asf.record.idcheck.declared_stories` reads them through `_prose`, which replaces every code span
with a space, so a backticked identifier would be gone from the title and the acceptance line the
record mints.

### S-73904: An asf land request whose required checks can never start leaves the wait on the pass that sees it, by the one route its owner can take

- [ ] a factory branch the lane holds a run for and GitHub reads conflicting goes BACK with the lane's conflict correction, no red written — the landed behaviour, kept
- [ ] a factory-prefixed branch the lane holds no run for is marked red instead of waiting, because an asf land request is never factory work and the lane will not rebase it
- [ ] that red's why names the branch no run holds and says the lane does not rebase it, and what to do instead
- [ ] a PR with no factory branch prefix is marked red with the text it is marked red with today, byte for byte, so the status view and the suite that pins it do not move
