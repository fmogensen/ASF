## Evidence on the card

> 2026-10-08T18:31:58Z watchdog: BREACH check_cancelled #1233@4a831f9c8 — 14 min, limit 10 min
> (owner ci) — worker/T-80572: tests (3.13) cancelled, nothing running → re-ran failed jobs of
> run(s) 37823005647 (once on this head)

The watchdog kept firing `check_cancelled` for a check the lane had already reran.

## Cause

`check_cancelled` (`asf/dwell.py:413`) reads every entry of a PR's `statusCheckRollup` and flags
any required one whose `conclusion` is `CANCELLED` or `TIMED_OUT`. GitHub's rollup never drops a
check-run once a rerun has added a new entry of the same `name` — the pre-rerun `CANCELLED` entry
stays in the list forever, alongside the rerun's own, later entry. `check_cancelled` scanned the
whole rollup rather than the latest state per check, so a required check already fixed by its one
rerun kept judging the stale `CANCELLED` twin as a live breach, indefinitely.

This is not a new shape of bug in this codebase: `asf/harvest/lane.py:5401`'s `latest_checks()`
already dedups a rollup to one entry per `name` — the newest by `completedAt` — to solve the
identical "stale cancelled twin" problem for `pr_checks()` (`asf/harvest/lane.py:5331`). The fix
for this card is the same dedup, applied where `check_cancelled` builds its own `checks` list.

## Resolution

`asf/dwell.py` gains `_latest_by_name(checks)`, mirroring `lane.py`'s `latest_checks()`: one
entry per `name`, the newest by `completedAt` (a still-running check, with no `completedAt`,
counts as the newest), the list's original order kept. `check_cancelled` calls it right after
building `checks` and before judging `_RUNNING` or `CANCELLED`/`TIMED_OUT`, so the stale pre-rerun
entry is never judged beside its own rerun's later result. See `docs/plans/b-82658.md` for the
Task, its Steps, and the named acceptance test.
