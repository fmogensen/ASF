# F-0335 — the claims that were recorded somewhere else

A `Proves:` claim is how a Task says which Story acceptance line its test proves, and the tick of
that line is the one thing that makes a Story done ("no test, no done", `asf/proves.py:306-341`).
The floor reads those claims itself: `asf.evidence.evidence.landed_proves` (`:1536`) scans the
merged pull requests and the trunk's own commits, and `asf.record.ingest.tick_proven` (`:1469`)
flips each claimed bullet to `- [x]` — once, never in reverse.

That scan is **windowed**, and the window is not a detail:

* the pull-request side reads `gh pr list --state all --limit 300` (`evidence.py:398-400`). On
  this repo the newest pull request is **#1379** and the 300th newest is **#1080**: every merged
  pull request at or below **#1079** — 1079 of 1379, 78 % of them — is outside the window and its
  body can never be read again (P1).
* the commit side reads `git log --grep=^Proves: origin/main --since=<the record's first commit>`
  (`:1592-1594`, `record_since` `:1094`). A claim on a commit older than the record predates the
  window too.
* both sides go through `sh()`, which returns `""` for **every** failure — a timeout, a missing
  `gh`, a rate limit (`:84-97`) — so a host that cannot reach the forge scans zero pull requests,
  ticks nothing, and says nothing. `pr_list` turns that empty string into `[]` (`:402-403`), and
  the result is cached for 180 s either way (`PR_TTL`, `EVIDENCE_TTL`, `:49-50`).

A claim is made once, at the moment a branch lands, and read by a scan that will stop being able
to see it. The claim itself is small and perfectly serialisable — `{story, line, test, pr, sha}`
is everything `landed_proves` produces (`:1566-1567`) — so the answer is to **record it outside
the record when it is made, and reconcile it in afterwards**. This spec is the reconcile: one
command that reads a ledger-shaped file of those rows, cross-checks every row against the floor's
own reading of the trunk, and ticks each line once.

It is a reconcile and not an import, which is the whole of its design: the file is never
authority. Where the floor's own scan holds a claim, the floor's values are what get written;
where only the file holds one, the floor re-reads the sha the row names and admits the claim only
if the trunk's own commit carries it. **Not one byte of the file reaches the record** (D4).

### In

* **One command**, `asf reconcile-proofs --claims <file>`: read-only by default, writes with
  `--apply` — the shape `asf audit-proofs` already has (`reopen.py:264`, `cli.py:813-818`).
* **One new module**, `asf/record/reconcile_proofs.py`: the file reader, the cross-check against
  the floor, the verdict table, the printed report and the one writer.
* **Seven verdicts**, a closed vocabulary, one per claim row: `confirmed`, `floor-only`,
  `admitted`, `already`, `refused`, `unconfirmed`, `malformed` (§1.3).
* **The targeted re-read**: for a row the floor's windowed scan does not hold, one
  `git log -1 --format=%B <sha>` plus the ancestry check `evidence.ancestry` (`:1710`) over
  `origin/<trunk>` — the floor verifying the one sha the row points at, instead of re-scanning a
  window that cannot reach it.
* **The idempotent tick**: `proves.tick` per admitted line, one `## History` line per line newly
  proved, one `frontmatter.render` write per Story that changed, through
  `stage.guarded(root, 'reconcile', …)`.
* **One regex widening** in `asf/proves.py`: `PROVED_ENTRY_RE` credits a `reconcile: proved line
  <n>` entry beside an `ingest:` one (§2), so the entry this pass writes is the entry
  `proved_lines` reads.
* **The declared row** in `asf/surface.py`, and the count in `tests/test_surface.py` that it
  moves (§4) — in scope because it is part of this change, not a surprise for the coder.

### Out

* **Changing `landed_proves`, its window, or its two sources.** The scan is read exactly as it is
  read today and is preferred over the file wherever it speaks (D1). Widening `--limit 300`, or
  paging the forge, is a different card with a different cost.
* **Fixing the pull-request-side parse (P2).** `- proves: Proves: S-… line 1 — …` is a claim
  `CLAIM_RE` refuses for its line anchor. Whether the fix belongs in the lane's rendering of the
  report or in the anchor is a real question with its own blast radius — every `Proves:` reader
  in the factory — and its own measurement. Nothing here depends on it: this spec treats a null
  `pr` as the normal case, and a file row's `pr` as a cross-check that is reported and never
  written (D4).
* **Writing the ledger file.** This card reconciles a file *in*; producing one is the parent's
  (F-0334, ASF 0.3) and the lane's. The spec specifies the format it reads and refuses anything
  else, which is the contract a producer is written against.
* **Closing anything.** The reconcile writes `## Acceptance` and `## History` and never the
  machine block, so no state, stage, `landed:` or `closed` field moves. A Story whose last
  unproved line this ticks becomes done at the next `asf ingest`, through `closing.RULES` reading
  `proves.unproved` exactly as it does today (D7).
* **Unticking, reversing, or reconciling in the other direction.** A line ticked in the record
  and absent from the file is left alone; `asf untick` stays the one reverse (P4).
* **A tick step, a clock, or a config key.** The command is run by a person or by a job that
  already knows the file's path; `--claims` is required and there is no `proves.claims_file` to
  register with `config_keys` and `doctor` (D8).
* **Inline `proven by` proofs, deferrals, and the review-claim path.** `proves.unproved`'s other
  three ways to prove a line (`:484-520`) and `ingest.review_proven` (`:1393`) are untouched.
* **Executing, resolving or trusting the file's `test` text.** It is compared, never run and
  never written (D4).

### Preconditions the work depends on

1. `proves.tick(body, line_no, note, suffix=None)` is idempotent and one-directional, and
   `proves.proved_lines(body)` is the record's statement that a line is proved (P4). The reconcile
   adds no new tick mechanism; it decides *which* lines to hand that function.
2. `landed_proves(product, prs, refused=…)` yields `{story: [{line, test, task, pr, sha, source}]}`
   and fills `refused` with the same shape plus `why` (`:1536-1607`). `evidence.load` already
   returns both under `ev['proves']` and `ev['proves_refused']` (`:950`, `:968-969`), so the
   floor's side costs this command no new round-trip.
3. `evidence.ancestry(product, bases)` answers "is this sha on the trunk" from one `rev-list`, and
   falls back to `merge-base --is-ancestor` for anything that is not a full 40-hex oid
   (`FULL_SHA_RE`, `:1707`). The admit path needs no new git reader.
4. `stage.guarded(root, writer, fn, …)` runs one writer, validates its change against the record
   invariants and puts back what they refuse (`stage.py:216-228`). A writer not in `stage.WRITERS`
   still runs, staged under its own name (`:29-31`) — so `reconcile` needs no entry in that tuple,
   which is the order the *tick* runs its writers in.
5. The only invariant in play is **I1** (the card still parses): this writer touches no machine
   block, so I2's `schema_version`, I3's `writes:`, I10's open-Task rule and I14's landing fact
   cannot fire on it, and I11 reads only the derived `Children`/`Backlinks` sections.
6. `asf audit-proofs` is the precedent for a record command that is read-only unless `--apply`,
   with `_published` wrapping only the writing half (`cli.py:813-818`); `reopen._product` and
   `reopen._canonical` (`:40-56`) are the two helpers such a command needs.
7. The record holds no Story for F-0335 and this session's range is `S:121155-121204` (P8).

### The choices

| | chosen | against | why |
|---|---|---|---|
| D1 | **The floor's scan is preferred wherever it speaks**: a row the scan also holds is written from the scan's entry — its `task`, `pr`, `sha`, `test` — and the file's values are only compared | Merge the two, newest wins; or let the file's richer row (it has a `pr`, P2) override | The card says so, and the reason is that the scan's entry is derived from the trunk this minute while the file's was written by something that is no longer running. Where they agree, nothing is lost. Where they disagree, the disagreement is the interesting output (`mismatch`, printed) and the trunk still decides |
| D2 | **A file-only row ticks only against a targeted re-read of the trunk**: the row's `sha` must be a full oid, reachable from `origin/<trunk>`, and its own commit message must carry a claim `parse_all` *counts* and that matches the row's `(story, line, test)` | Trust a file-only row on its face (it is the operator's own file); or drop it with a warning | Trusting it makes the file a second record with no evidence behind it, and this product's whole rule is that *a claim is not evidence until it is on the trunk* (`landed_proves`' own docstring). Dropping it makes the file useless, which is the state P1 describes. The third way is the one that works: the file is a **pointer**, and the floor still proves what it points at. It also costs one `git log -1` per unmatched row and no forge call |
| D3 | The History entry reads **`reconcile: proved line <n>`**, and `PROVED_ENTRY_RE` is widened to credit it beside `ingest:` | Write `ingest: proved line <n>` from a command that is not ingest, and change no regex | A one-line regex change against a lie in the record that nobody could later untangle: the entry is the only audit trail a tick has, and "which pass proved this, from which sha" is exactly the question a reconcile exists to answer. The widening is `(?:ingest|reconcile)` and touches nothing else — `UNTICK_ENTRY_RE` discards by line number regardless of who proved it (P4), so `asf untick` keeps working unchanged |
| D4 | **Nothing from the file is ever written into the record.** On a `confirmed` row the written values are the scan's; on an `admitted` row they are the ones parsed out of the trunk commit; the file's own `test` text is compared and discarded | Write the file's row through on an admitted claim — it is the same claim, after all | The file is operator-supplied data of unknown provenance, and a record card is read by every reader in the factory including the redaction gate and the review. Keeping the write path fed only by the trunk means a malicious or merely stale file can at most cause the floor to *look* at a sha it would otherwise not have looked at. "Admitted" never means "copied" |
| D5 | **Seven verdicts, one per row, in a closed vocabulary**, printed as a table with a count line | A boolean (ticked / not ticked) plus a log | Six of the seven are reasons a line did *not* tick, and they are not the same reason: `refused` is a bad claim, `unconfirmed` is a claim with no trunk behind it, `malformed` is a bad file, `already` is success on a second run. A reconcile whose output cannot distinguish "your ledger is ahead of the trunk" from "your ledger is malformed" sends a person to the wrong place |
| D6 | **A refusal is a verdict on the row, never a veto on the line.** A refused row ticks nothing; if a different row (or the floor's own scan) proves the same line, that line still ticks | Hold the whole line when any claim against it is refused | This is already the record's rule: `proves.unproved(…, refused=…)` reports `partial claim` for a line that is *otherwise* unproved, and says nothing about a line something else proved (`:507-520`, D9 of F-0257). A qualified claim is a session saying "I have part of this"; it is not evidence against a colleague who has the whole of it |
| D7 | **The reconcile ticks proof and closes nothing.** No machine field is written | Re-derive the affected Stories and their Features in the same pass, the way `audit-proofs --apply` reopens | Deriving state is `asf ingest`'s one job, over the whole record, from the whole evidence (`ingest.derive`). A second deriver that sees only the Stories one file mentions would decide a Feature's state on a fraction of its children. Ticking is monotone and local; closing is global. The next ingest closes what this made closable, and that is one tick of latency for a correctness property worth far more |
| D8 | `--claims <path>` is **required**, with no config key and no default location | A `proves.claims_file` config key, registered in `config_keys` and surfaced by `doctor` | A key means a registration in `KNOWN_CONFIG_KEYS`, a `TYPED` row, a doctor row and a test that walks the source for unread keys — four registrations for a path the one caller already has in hand. Nothing schedules this command (Out), so there is no unattended caller that would need the key. It is a flag away if that changes |
| D9 | The file is **JSONL**: one JSON object per line, keys `story`, `line`, `test`, `pr`, `sha`; unknown keys ignored, `pr` nullable | CSV; a Markdown table; the `Proves:` trailer grammar itself | A `test` is a path with `::` nodes, and a claim's text may carry commas, quotes and em dashes — CSV and a Markdown table both need escaping rules this spec would have to invent. JSONL is what every other sidecar in this factory already is (`sessions.jsonl`, `metrics/events/<day>.jsonl`, `invariants-report.jsonl`), it is line-addressable so a malformed row names its own line number, and it is append-only by construction, which is the shape of a ledger |
| D10 | A malformed line is **one finding, and the pass continues** | Refuse the whole file on the first bad line | A ledger is appended to by whatever recorded the claim, and one bad append must not strand every good row behind it. The exit status still says it (D11) |
| D11 | Exit **0** when every row either ticked, was already ticked, or was confirmed; **1** when any row is `refused`, `unconfirmed` or `malformed`; **2** when the file cannot be read at all | Always 0 — the write succeeded, after all | A `--apply` that ticks nine lines and silently drops a tenth is how a ledger drifts out of step for a month. The write stands either way (the exit code is read after the writing, and `_published` publishes regardless); the status is the one thing a caller checks |
| D12 | Stories S-121155–S-121159 from this session's range `S:121155-121204` | — | The record holds no Story for F-0335 (P8) |

## The design

One new module, one widened regex, one command, across **six paths** — the footprint the plan's
`writes:` must carry, because a Task that writes a path absent from `writes:` is held:

```
asf/record/reconcile_proofs.py       §1   the reconcile: reader, cross-check, verdicts, writer (new file)
asf/proves.py                        §2   PROVED_ENTRY_RE credits a reconcile entry
asf/cli.py                           §3   the parser and the dispatch
asf/surface.py                       §3   the declared row
tests/test_reconcile_proofs.py       §4   the acceptance (new file)
tests/test_surface.py                §4   the declared-command count, 59 → 60
```

Nothing is deleted. `landed_proves`, `tick_proven`, `ingest`, `audit-proofs`, `untick` and every
other `Proves:` reader keep their behaviour byte for byte; the only shipped assertion that moves
is the one `tests/test_surface.py` makes about the size of the declared table (P6, §4).

### 1. `asf/record/reconcile_proofs.py` — the reconcile

#### 1.1 The row

```python
#: The keys a ledger row carries — the shape `landed_proves` produces (evidence.py:1565-1567).
CLAIM_KEYS = ('story', 'line', 'test', 'pr', 'sha')


@dataclasses.dataclass(frozen=True)
class Row:
    """One line of the ledger, parsed. ``n`` is its 1-based line number in the file and ``raw``
    its text — the two things a finding must name. Nothing here is ever written to a card (D4)."""
    n: int
    raw: str
    story: str = ''      # upper-cased
    line: int = 0        # 1-based, the nth ## Acceptance bullet
    test: str = ''
    pr: object = None    # an int, or None
    sha: str = ''        # lower-cased
    why: str = ''        # '' for a well-formed row; else why it is malformed
```

#### 1.2 Reading the file

```python
def read_rows(path):
    """``[Row, …]`` — one per non-blank line of the JSONL ledger at ``path``, in file order.

    A line that is not a JSON object, or whose ``story`` is not an id token, ``line`` not a
    positive integer, ``test`` not a non-empty string or ``sha`` not hex, comes back with ``why``
    set and never reaches the cross-check (D10): the pass goes on and the row is reported
    ``malformed`` against its own line number. Unknown keys are ignored (D9). Raises ``OSError``
    for a file that cannot be read — the caller's exit 2 (D11)."""
```

A blank line and a `#` comment line are skipped and are not rows. The reader never resolves,
opens or executes `test`.

#### 1.3 The cross-check and the verdicts

```python
#: Every verdict a claim row can get. One row, one verdict (D5).
CONFIRMED   = 'confirmed'    # the floor's scan holds it too — written from the scan's entry
FLOOR_ONLY  = 'floor-only'   # the scan holds it and the ledger does not — written, and said
ADMITTED    = 'admitted'     # ledger-only, and the trunk's own commit carries it (D2)
ALREADY     = 'already'      # the Story's ## History already records the line as proved
REFUSED     = 'refused'      # a claim the floor refuses — never ticks (D6)
UNCONFIRMED = 'unconfirmed'  # ledger-only, with no trunk behind it — never ticks
MALFORMED   = 'malformed'    # not a well-formed ledger row (D10)

TICKING = (CONFIRMED, FLOOR_ONLY, ADMITTED)
```

```python
@dataclasses.dataclass(frozen=True)
class Verdict:
    story: str
    line: int
    verdict: str
    test: str      # the text that would be written: the floor's, or the trunk's (never the file's)
    task: str
    pr: object
    sha: str
    where: str     # 'scan', 'trunk <sha[:9]>', 'ledger line <n>', or ''
    note: str      # a refusal's why, a mismatch's two values, a malformation's reason; else ''
```

```python
def reconcile(canonical, ev, rows, on_trunk, body_of):
    """``[Verdict, …]`` — one per claim key, sorted by ``(story, line, test)``. Pure but for the
    two injected readers (D2, and the same injection rule `proves.claims_on_branch` follows):

    * ``on_trunk(sha) -> bool`` — ``evidence.ancestry(product, ['origin/<trunk>'])``;
    * ``body_of(sha) -> str`` — the commit message of one sha, ``''`` when there is none.

    The key set is the union of ``ev['proves']``'s claims and the ledger's rows. For each key:

    1. the Story must be a Story in ``canonical`` and ``line`` within its ``## Acceptance``
       bullets (`proves.card_bullets`), else :data:`REFUSED` carrying `proves.validate`'s own two
       words for it — ``unknown story`` and ``no such line`` (`proves.py:202-231`). Its third,
       ``not this Task's``, is not checked here: a ledger row carries no Task of its own to check
       a Story against, and the Task a confirmed or admitted row writes is the trunk's;
    2. a key in ``ev['proves_refused']`` is :data:`REFUSED`, carrying that entry's ``why``;
    3. a line already in `proves.proved_lines` of the Story's body is :data:`ALREADY`, whatever
       either side says — this is what makes the second run a no-op (§1.5);
    4. a key the scan holds is :data:`CONFIRMED` when the ledger holds it too and
       :data:`FLOOR_ONLY` when it does not, written from the scan's entry (D1). A ledger ``pr`` or
       ``sha`` that disagrees with the scan's goes in ``note`` as ``mismatch: pr 412 vs none`` and
       changes nothing;
    5. a ledger-only key is :data:`ADMITTED` when its ``sha`` is a full oid, ``on_trunk(sha)``, and
       ``parse_all(body_of(sha))`` *counts* a claim with the same ``(story, line, test)`` — written
       from that parsed claim, with ``task`` taken from the commit subject's id token as
       `landed_proves` takes it (`evidence.py:1596`). Otherwise :data:`UNCONFIRMED`, with ``note``
       saying which step failed: ``no sha``, ``not a full oid``, ``not on the trunk``, ``the commit
       carries no such claim``, or ``the commit's claim is refused: <why>``;
    6. a malformed row is :data:`MALFORMED` with its ``why``, and is never a key of anything.
    """
```

Two properties worth naming because the tests pin them: step 3 is checked **before** step 4 and
step 5, so an already-proved line never re-enters the ticking set; and a `REFUSED` verdict on
`(S, n, testB)` is independent of a `CONFIRMED` one on `(S, n, testA)` — the refusal is the row's,
not the line's (D6).

#### 1.4 The write

```python
def apply(root, canonical, verdicts, stamp):
    """Tick every line a :data:`TICKING` verdict proves, once. ``[(story, line), …]`` newly
    ticked, sorted.

    Over the Story cards named by those verdicts only. Each card is re-read off ``rec['path']``
    and parsed afresh (the same reason `ingest.tick_proven` does: a card may have been rewritten
    since ``canonical`` was loaded), then per verdict:

        body, changed = proves.tick(body, v.line, None)

    A line that was already ``- [x]`` with no proved-line entry still gets its entry — the
    re-credit `tick_proven` makes (`ingest.py:1495-1497`), without which a hand-ticked line could
    never count as proved. One ``## History`` line per line newly credited:

        - <stamp> reconcile: proved line <n> — <task>[, PR #<pr>] (<test>) from <sha[:9]>

    the ``PR #`` clause omitted where ``pr`` is null (as `tick_proven` omits it, `:1500`), and the
    ``from <sha>`` clause carrying the one thing ingest's line lacks: which commit proved it. One
    ``frontmatter.render`` write per Story whose history grew, through
    :mod:`asf.record.writer`; a Story with no new line is not opened for writing at all.

    No machine field is written: no ``state``, no ``stage``, no ``landed:``, no ``updated:``
    (D7)."""
```

The suffix argument of `proves.tick` is left `None`: the suffix is the review path's
(`tick_proven:1505`), and a reconcile has no review file to name.

## Records

No card is minted, no state is derived, no event is emitted, no metrics row is appended, no
branch is touched and no file is created outside the fixture and the new module. The record gains
exactly two kinds of character on a Story card, and both are the ones a tick has always written.

| What | Where | What changes |
|---|---|---|
| the acceptance bullet | the Story card's `## Acceptance`, through `proves.tick` | `- [ ]` → `- [x]`, the bullet's own text byte-identical, no suffix (`tick(body, line, None)`). **No new shape** |
| the proof entry | the Story card's `## History`, one line per line newly credited | **New words, old grammar**: `- <stamp> reconcile: proved line <n> — <task>[, PR #<pr>] (<test>) from <sha[:9]>`. `PROVED_ENTRY_RE` credits it (§2); `asf untick` reverses it unchanged |
| the card write | `asf.record.writer.write_card`, one `os.replace` per Story whose history grew | As every record writer writes. A Story with no new line is never opened for writing |
| the staged change | `stage.guarded(root, 'reconcile', …)` | **New writer name**, staged under its own name. Not added to `stage.WRITERS` — that tuple is the order the *tick* runs its writers in, and nothing in the tick runs this (D8, precondition 4) |
| the machine block | — | **Untouched.** No `state`, `stage`, `stage_since`, `landed`, `closed` or `updated`. A Story made closable here is closed by the next `asf ingest` (D7) |
| the report | stdout, one table row per claim key plus a verdict count line | **New output.** Read-only unless `--apply`; the shape `audit-proofs` prints (`reopen.py:273-283`) |
| the exit status | the process | **New meaning**: 0 clean, 1 any `refused`/`unconfirmed`/`malformed` row, 2 the ledger unreadable (D11) |
| the ledger file | the path `--claims` names | **Never written.** The reconcile only reads it, and reads it whole each run |
| the published commit | the record clone, via `_published` on `--apply` only | `record: reconcile-proofs --apply`, in the shape every other console writer publishes (`cli.py:692-701`) |
| `index.json`, the tables, the feeder rows | — | Unchanged: no derived section and no state moved, so nothing re-indexes |

NEEDS OPERATOR: none — the format is this spec's to specify (D9) and the producer is the parent's
(F-0334, Out). The one figure a checkout cannot replay is P1, whose command is read-only and
printed with it, and nothing in the design turns on its exact value: the window is finite, which
is the only thing the reconcile needs to be true. Re-read it with
`gh api -X GET "repos/<owner>/<repo>/pulls?state=all&per_page=100&page=3&sort=created&direction=desc" --jq '[.[].number] | {first: .[0], last: .[-1], n: length}'`

## Stories

Five Stories, one per section of `## The design` plus the two the behaviour the card names splits
into (`a refused claim never ticks`, `running twice ticks each line once`). Each is **declared**
below as a `### S-…: <title>` heading with its acceptance lines under it, with ids from this
session's range `S:121155-121204` — that heading is what `asf.record.idcheck.declared_stories`
reads and what `asf.record.plan_tasks` mints the card from, so a cited id with no declaration is a
phantom and the plan citing it is refused whole.

Each acceptance line is one physical line of plain text with no backticks, on purpose: the reader
is line-anchored (`asf.record.idcheck.CHECKBOX` matches a single line) and `_prose` replaces every
inline code span with one space before parsing, so a wrapped line reaches the minted card
truncated and an identifier inside backticks reaches it missing.

that say an existing behaviour is unchanged, which are the facts this change relies on rather than
adds.

### S-121155: the verdict table over the two sides, with the floor's own scan preferred wherever it speaks

Design §1.1 and §1.3 (D1, D4, D5; P2, P3). Acceptance is the first fenced block of
`## Acceptance tests`. One row, one verdict, from a closed vocabulary; the scan's entry is what
gets written wherever the scan holds the claim, and a ledger value that disagrees is reported and
discarded.

- [ ] a claim key the floor's scan holds and the ledger holds too is confirmed
- [ ] a claim key the floor's scan holds and the ledger does not is floor-only, and still ticks
- [ ] a confirmed row is written from the scan's task, pull request and sha, not the ledger's
- [ ] a ledger row whose pull request number disagrees with the scan's is confirmed on the scan's value, and the disagreement is reported as a mismatch
- [ ] a ledger row whose sha disagrees with the scan's is confirmed on the scan's value, and the disagreement is reported as a mismatch
- [ ] the verdict vocabulary is closed, and every verdict a reconcile returns is one of its seven names
- [ ] the verdicts come back sorted by story, then line, then test
- [ ] a claim key naming an id the record holds no Story card for is refused and never ticks
- [ ] a claim key naming a line outside the Story's acceptance bullets is refused and never ticks
- [ ] a claim key naming an id the record holds as a Task, not a Story, is refused and never ticks
- [ ] the reconcile reads the trunk only through the two injected readers, so it runs with no git and no forge
- [ ] a Story the ledger never mentions and the scan never claims produces no verdict at all

### S-121156: a ledger-only row ticks only against the trunk's own re-read of the sha it names

Design §1.2 and §1.3 step 5 (D2, D9, D10; P1). Acceptance is the second fenced block. The ledger
is a pointer and never an authority: the floor re-reads the one commit the row names, and admits
the claim only if that commit carries it.

- [ ] a ledger-only row whose sha is on the trunk and whose commit carries the same claim is admitted and ticks
- [ ] an admitted row is written from the claim parsed out of the commit, never from the ledger's own text
- [ ] an admitted row takes its task from the commit subject's id token, as the floor's own scan takes it
- [ ] a ledger-only row with no sha is unconfirmed and ticks nothing
- [ ] a ledger-only row whose sha is not a full forty-character oid is unconfirmed and ticks nothing
- [ ] a ledger-only row whose sha the trunk does not reach is unconfirmed and ticks nothing
- [ ] a ledger-only row whose commit carries no claim at all is unconfirmed and ticks nothing
- [ ] a ledger-only row whose commit carries a claim for another line is unconfirmed and ticks nothing
- [ ] a ledger-only row whose commit carries the claim qualified is unconfirmed, and the note names the refusal
- [ ] every unconfirmed verdict carries a note naming which step of the admit failed
- [ ] a line of the ledger that is not a JSON object is malformed, named by its own line number, and the rows after it still reconcile
- [ ] a row missing any of story, line, test or sha is malformed and is never a claim key
- [ ] a row whose line is not a positive integer is malformed
- [ ] a row carrying keys the format does not name is read on its named keys and is not malformed
- [ ] a blank line and a comment line are not rows
- [ ] a row whose pull request number is null is well-formed
- [ ] a ledger that cannot be read at all is one message and exit status two

### S-121157: a refused claim never ticks, and never unticks what stands

Design §1.3 steps 1, 2 and 6, and §1.4 (D6; P5). Acceptance is the third fenced block. A refusal
is a verdict on the row, not a veto on the line, and nothing in this command reverses a tick.

- [ ] a claim the floor's scan refused as qualified is refused here too, carrying the same reason
- [ ] a refused row ticks nothing, and the line it names is left unticked
- [ ] a refused row against a line another row proves leaves that line ticking
- [ ] a refused row against a line already ticked in the record leaves the tick and the proof entry exactly as they are
- [ ] an unconfirmed row against a line already ticked in the record leaves the tick and the proof entry exactly as they are
- [ ] a malformed row against a line already ticked in the record leaves the tick and the proof entry exactly as they are
- [ ] the command has no path that unticks a line, and the one reverse is still the operator's own untick
- [ ] a run whose every row is refused writes nothing and leaves every card byte-identical

### S-121158: running twice ticks each line once, and the entry it writes is the entry the record credits

Design §1.4 and §2 (D3, D7; P4). Acceptance is the fourth fenced block. The second run is a
no-op because the record itself says the line is proved, and the entry that says so is the entry
the record's own reader credits.

- [ ] one pass over a ledger with a confirmed row flips the bullet and appends one proof entry
- [ ] a second pass over the same ledger leaves the card byte-identical
- [ ] a third pass leaves it byte-identical again
- [ ] the second pass reports the row as already, not as confirmed
- [ ] the rest of the card's body outside the ticked bullet and the new history line is byte-identical after the first pass
- [ ] the card's machine block is byte-identical after the pass, so no state and no stamp moved
- [ ] the proof entry names the pass, the line, the task, the test and the short sha of the commit that proved it
- [ ] the proof entry omits the pull request clause when the claim carries no pull request number
- [ ] the proof entry includes the pull request clause when the claim carries one
- [ ] the record's own reader credits a reconcile proof entry as proving that line
- [ ] the record's own reader still credits an ingest proof entry as proving that line
- [ ] a line already ticked by hand with no proof entry gets its proof entry, so it can count as proved
- [ ] an acceptance bullet the pass ticks still satisfies the record's own story shape check
- [ ] a Story with no new line is never opened for writing
- [ ] a Story with no acceptance section at all is left untouched

### S-121159: the command — read-only by default, declared in the surface, its exit status its own

Design §1.5, §3 and §4 (D8, D11; P6). Acceptance is the fifth fenced block. The command's default
is to say what it would do, and its exit status is what an unattended caller reads.

- [ ] the command is a registered subcommand taking a required claims path, an apply flag and a product
- [ ] the command name is declared in the surface table, with the record as its effect and apply as the flag that makes it write
- [ ] the declared description opens with a verb the surface's own closed list holds
- [ ] the declared table holds one more command than it did
- [ ] a run without apply prints the table and leaves every card byte-identical
- [ ] a run with apply writes the ticks the same run without apply printed
- [ ] the printed table carries one row per claim key, with its verdict, the test, where it came from and its note
- [ ] the printed count line names each verdict that occurred and how many
- [ ] the printed last line names how many lines would tick and across how many stories
- [ ] a run whose every row ticked or was already ticked exits zero
- [ ] a run with any refused row exits one
- [ ] a run with any unconfirmed row exits one
- [ ] a run with any malformed row exits one
- [ ] a run against an unreadable ledger exits two and writes nothing
- [ ] the writing half runs through the record stage under its own writer name
