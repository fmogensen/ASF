# F-0033 — the factory's own loop is a test, not a hope

CI already runs `sample/` — a second product with conventions of its own — through `asf init`, one
`asf tick`, `asf next` and `asf doctor`, on the `fake` worker runtime with no model, no account
and no network (`.github/workflows/tests.yml`, the step *the sample product, end to end*). F-0087
went further and walked two *failure* paths through whole ticks: a red gate held and corrected,
and a session that said done without pushing.

What no test walks is the **success** path. `sample/`'s first tick launches the S1 Bug and stops
there — an open S1 holds every tier-2 row back (`asf/feeder/tiers.py:30`), so `F-0001` never
leaves `card`. Nothing in CI has ever seen a spec become a plan, a plan mint a Task, a Task land,
or a release note get cut. Every hinge between those stages is live code with no end-to-end
witness:

| The hinge | Who owns it | What proves it today |
| --- | --- | --- |
| a spec branch lands → the Feature is `spec-approved` | `asf/record/ingest.py:408` (B-0059: a document the lane landed **is** approved) | unit tests on `feature_stage`, never a real landing |
| `spec-approved` → a `STARVED → PLAN` row | `asf/feeder/rows.py:340` | `tests/test_feeder.py`, off a hand-written index |
| a plan lands → its `### Task N:` headings become Task cards | `asf/record/plan_tasks.py:mint_plan_tasks` | `tests/test_plan_tasks.py`, off a fixture plan |
| a minted Task → a `PLAN → CODE` row on the code lane | `asf/feeder/rows.py:task_rows` | `tests/test_feeder.py` |
| a code branch lands → the Feature reaches `landed` | `asf/harvest/harvest.py`, `evidence.feature_stage` | `tests/test_harvest.py`, per-function |
| a landing → `releases/<day>-<sha7>.md` | `asf/metrics/metrics.py:write_trunk_release` | `tests/test_metrics.py`, with a stubbed repo |

Each one is tested alone. The *seam* between them is not, and a seam is where a night is lost:
the tick runs, every module is green, and the loop stalls at a stage nobody watched. This spec
makes the whole chain one test, running the real command line against `sample/`, and pins the
tables it produces to goldens so a change that quietly reshapes the record's output is a red
build rather than a surprise the next morning.

## 1. Decisions

### 1.1 In

1. One new scenario class in `tests/test_sample_product.py` that drives `sample/` from its first
   tick to a landed Task and a cut release note, on the `fake` runtime, through `asf.cli` as a
   subprocess — the same shape `FailurePathsBase` already uses.
2. The test **plays each session's writes** between ticks: the spec file, the plan file, the
   Task's code. The `fake` runtime returns a scripted result and touches no git
   (`asf/workers/runtime.py:228`), so the commits a real session would make are the test's to
   make — exactly as `HeldThenCorrectedThenLanded` already does for the Bug's fix.
3. Goldens for the tables the loop stamps: the `BOARD` and `ROADMAP` views, the daily scorecard
   `metrics/daily/<day>.md`, and the release note `releases/<day>-<sha7>.md`. A normaliser
   replaces every volatile value before comparison, and `ASF_UPDATE_GOLDEN=1` regenerates them —
   the mechanism `tests/test_briefs.py:39` already established.
4. The Feature's **stage ladder** asserted as an ordered list: `card → spec-draft →
   spec-approved → plan-approved → building 0/1 → landed`, one entry per tick, so a stage the
   loop skips or repeats is named in the failure.
5. A named CI step so the scenario's red is legible on its own rather than buried in the module.
6. Dropping inherited `GIT_CONFIG_*` in the fixture's environment (§2.6) — without it the
   scenario cannot run on an operator's machine at all.

### 1.2 Out

- **No new fixture product.** The loop runs against `sample/` as it stands. A fixture cut to make
  the loop short would prove a shape nobody ships.
- **No change to any production code path** beyond §2.6's one-line environment fix. If the loop
  is broken, this test is what says so; a spec that both writes the test and fixes what it finds
  cannot fail honestly.
- **The review-verdict path.** The loop reaches `spec-approved` by landing the spec on the trunk
  (B-0059), which is how `sample/` — a `landing: fast-forward`, no-PR product — actually works.
  The other route to `approved`, a `reviews/…` file carrying `APPROVED`, is not exercised here.
  Note for whoever picks that up: `evidence.discover` builds its review-file patterns from
  `rx_review` (`asf/evidence/evidence.py:243`), which hardcodes `<slug>-review-r<n>.md` and never
  reads `conventions.review_pattern` — so `sample/`'s own `reviews/{slug}-r{n}.md` would not be
  found. That is a separate defect and not this card's.
- **`asf doctor`'s cleanliness under the loop.** The existing `test_doctor_is_clean` covers it.
- **The `daily` step.** `sample/` declares `steps: {daily: off}`; the rollup that matters runs in
  every tick's `record` step.

### 1.4 The choices

| Chosen | Against | Why |
| --- | --- | --- |
| Run the loop from `sample/`'s real first tick, S1 Bug and all | a doctored copy with `B-0001` pre-`Resolved`, to save three ticks | The S1 lane *is* part of the loop: that an incident holds the Features back and then releases them is behaviour worth a witness. The saving is a few seconds of fake-runtime ticks. |
| The test plays each session's writes | teach `FakeRuntime` to write files from the script | A runtime that writes is no longer a replay of a result; it becomes a second implementation of a session, with its own bugs. The scripted-result / test-writes split is the one F-0087 already proved. |
| Goldens with a normaliser, `ASF_UPDATE_GOLDEN=1` to regenerate | assert a handful of substrings per table | The card asks for tables asserted against goldens. A substring assertion passes while the rest of the table rots; a golden makes every column a tripwire, and the update flag keeps it cheap to accept a deliberate change. |
| Normalise by *replacing* volatile values with stable tokens (`<SHA>`, `<DAY>`, `<TMP>`, `<HH:MM>`) | strip the volatile lines out | A stripped line cannot regress. Replacing keeps the line's shape — a table that loses its stamp line, or grows a second sha column, still fails. |
| Assert the stage ladder as an ordered list gathered per tick | assert only the final stage | The final stage is reachable by accident. The ladder names *which* hinge broke, which is the difference between a five-minute fix and a bisect. |
| A second, explicit rollup for the following day to cut the Task's release note | accept the one release the loop cuts | `write_trunk_release` caps releases at one per day (`metrics.py:836`). Within one test run the first release names `B-0001`. The Task's release note is a real artefact of the loop and is cut by running the rollup the way the next day's tick would. Both are asserted. |
| One named CI step for the scenario | fold it into the existing end-to-end step | The existing step's name is its diagnosis. A separate step means the build log says *the loop* broke, not *the sample* broke. |
| `GIT_CONFIG_*` dropped in the fixture env (§2.6) | leave it, since CI is green | A dogfood test an operator cannot run is a test that only ever runs where nobody is looking. This is the one production-adjacent change in scope, and it is confined to the test's environment builder. |

## 2. The design

### 2.1 Where it lives

`tests/test_sample_product.py` — the module that already owns `sample/`. The new class reuses
`FailurePathsBase`: its per-class temp copy of `sample/`, its bare origins, its `_fill`ed
`ASF_HOME`, its `script()` / `tick()` / `background_harvest()` helpers and its
`session_commits` / `session_pushes` pair. Nothing about the fixture is rebuilt.

Goldens live in `tests/fixtures/sample_loop/`:

```
tests/fixtures/sample_loop/
  board.md            # `asf backlog --product sample`
  roadmap.md          # `asf roadmap --product sample`
  scorecard.md        # metrics/daily/<day>.md
  release-bug.md      # the release the loop cut, naming B-0001
  release-task.md     # the release the following day's rollup cuts, naming the Task
```

### 2.2 The scenario, tick by tick

`WholeLoopFromCardToRelease(FailurePathsBase)`. Each tick runs `asf tick --product sample
--fresh` and waits for its background harvest; between ticks the test plays whatever session that
tick launched. `stage()` reads `F-0001`'s `stage` out of the record's `index.json` after each
tick and appends it to `cls.ladder`.

| tick | what the factory does | what the test plays next |
| --- | --- | --- |
| 1 | `wave` launches `fix-bug-b-0001` on `bugfix/B-0001` | commits `GREEN_COUNT` to `src/count.py` and a passing `tests/test_empty.py`, pushes |
| 2 | `health` ends it; `harvest` lands `bugfix/B-0001` | — |
| 3 | `ingest` marks `B-0001` `Resolved`; the S1 lane clears; `wave` launches `spec-f-0001` on `spec/F-0001` | writes `specs/f-0001.md` (the sample's `specs_dir`), commits, pushes |
| 4 | `harvest` lands `spec/F-0001` — docs only, never held (P2) | — |
| 5 | `ingest`: `spec_on_main` → stage `spec-approved`; `wave` launches `plan-f-0001` on `plan/F-0001` | writes `plans/f-0001.md` with one `### Task 1:` heading carrying a `writes:` line, commits, pushes |
| 6 | `harvest` lands `plan/F-0001` | — |
| 7 | `record`: `plan-tasks` mints the Task card; `wave` launches its coder on `feature/T-xxxx` | commits the Task's change, pushes |
| 8 | `harvest` lands `feature/T-xxxx`; `ingest` closes the Task | — |
| 9 | `ingest`: the Feature reaches `landed`; the tables are read | — |

The Task's id is minted by `asf`, never by the test: the scenario reads it back out of
`index.json` (`type: task`, `parent: F-0001`) and asserts the branch the wave chose is
`feature/<that id>` — `sample/`'s own `code` prefix, not the default `worker/`.

### 2.3 The ladder

```python
EXPECTED_LADDER = ['card', 'card', 'card', 'spec-draft', 'spec-approved',
                   'spec-approved', 'plan-approved', 'building 0/1', 'landed']
```

One entry per tick, asserted as a whole list. A stage that appears twice where it should appear
once, or a stage that never appears, names its own hinge.

### 2.4 The normaliser

One module-level function, used by every golden comparison:

```python
def normalise(text, tmp, day, ids):
    """Volatile values → stable tokens, so a golden compares only what the loop decides."""
```

| Replaced | Token | Why it is volatile |
| --- | --- | --- |
| any 7–40 hex run that is a git sha | `<SHA>` | new every run |
| the scenario's temp root | `<TMP>` | `mkdtemp` |
| today's date, and the following day | `<DAY>`, `<DAY+1>` | the clock |
| any ISO timestamp | `<TS>` | the clock |
| the stamp line's `HH:MM` | `<HH:MM>` | the clock; the rest of `— generated by asf <cmd>@<SHA> …` is kept, so losing the stamp fails |
| the minted Task id | `<TASK>` | `mint_id` depends on what the record already holds |

Everything else — every column, every row, every heading — is compared literally.

### 2.5 The release notes

The loop cuts `releases/<day>-<sha7>.md` at the tick where `B-0001`'s fix lands, because a
commit naming an item reached the trunk and no release exists for that day. `write_trunk_release`
then refuses a second one the same day (`metrics.py:836`), so after the Task lands the scenario
runs the rollup the next day's tick would run:

```
python3 -m asf.metrics.metrics --root <record> --product sample rollup <day+1>
```

That cuts `releases/<day+1>-<sha7>.md`, naming the Task. Both files are asserted against their
goldens, and both tags are asserted present in the repo's bare origin — a release note whose tag
was never pushed is a release that did not happen.

### 2.6 The one environment fix

`asf/hermetic.py:38-49` *appends* to `GIT_CONFIG_COUNT` and keeps whatever `GIT_CONFIG_KEY_n` /
`GIT_CONFIG_VALUE_n` pairs the caller already had. An operator running the suite from inside an
`asf` session inherits that session's `core.hooksPath`, pointing at *their* product's hook dir;
the child `git` reads it, the wave's hook preflight finds a `pre-commit` that is not the sample
product's, and refuses to launch — `waits fix-bug-b-0001 … NEEDS OPERATOR: …/githooks/pre-commit
is not asf's`. No session launches, and every scenario in the module fails at `setUpClass`.

The fix is confined to the fixture: `FailurePathsBase.setUpClass` drops every inherited
`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*` and `GIT_CONFIG_VALUE_*` from the base environment before
`hermetic.build` adds its own. This is the test's environment, not `hermetic.build`'s contract —
changing the contract would be a production change, and §1.2 refuses that.

### 2.7 CI

`.github/workflows/tests.yml` gains one step after the existing end-to-end one:

```yaml
      # F-0033: the whole loop — card → spec → plan → task → harvest → release notes — against
      # the sample product on the replay runtime, with the stamped tables pinned to goldens.
      - name: the whole loop, card to release notes (goldens)
        run: python3 -m unittest -v tests.test_sample_product.WholeLoopFromCardToRelease
```

The existing `tests` step already runs the module as part of `tools/run_tests.py`; the named step
is there so the build log names the loop when the loop is what broke. Budget: the module runs in
90s today with two 5-tick scenarios; a third 9-tick scenario on the same fake runtime keeps it
inside the runner's ordinary time.

## 3. Acceptance tests

Every block below is runnable from the repo root as it stands.

### 3.1 The whole loop, on its own

```bash
python3 -m unittest -v tests.test_sample_product.WholeLoopFromCardToRelease
```

Green: the ladder matches, the Task was minted and landed, both release notes exist, every golden
matches.

### 3.2 The goldens regenerate, and regenerating changes nothing

```bash
ASF_UPDATE_GOLDEN=1 python3 -m unittest tests.test_sample_product.WholeLoopFromCardToRelease
git diff --exit-code tests/fixtures/sample_loop/
```

`git diff --exit-code` exits 0: the goldens on disk are what the loop produces. This is the check
that the normaliser is complete — an un-normalised sha would make the second command fail.

### 3.3 The module, whole — the existing scenarios still pass

```bash
python3 -m unittest -v tests.test_sample_product
```

### 3.4 An operator can run it

```bash
env -u GIT_CONFIG_COUNT -u GIT_CONFIG_KEY_1 -u GIT_CONFIG_VALUE_1 \
  python3 -m unittest tests.test_sample_product.WholeLoopFromCardToRelease
python3 -m unittest tests.test_sample_product.WholeLoopFromCardToRelease
```

Both green, and both identical. Before §2.6 the second fails at `setUpClass` with
`KeyError: 'fix-bug-b-0001'` on any machine whose shell is inside an `asf` session.

### 3.5 A broken loop is a red build

```bash
python3 - <<'EOF'
import re, pathlib
p = pathlib.Path('asf/record/ingest.py')
t = p.read_text()
p.write_text(t.replace("or bool(fev.get('spec_on_main'))", "or False", 1))
EOF
python3 -m unittest tests.test_sample_product.WholeLoopFromCardToRelease ; echo "exit=$?"
git checkout -- asf/record/ingest.py
```

`exit=1`, and the failure names the ladder: `spec-draft` where `spec-approved` was expected. This
is the card's third line — a change that breaks the loop fails CI rather than failing a night.

### 3.6 The suite, hermetic, the way CI runs it

```bash
python3 tools/run_tests.py
```

**Rows.** None. This spec adds no field to any card and writes nothing to the record's items.

**Files changed.**

| Path | Change |
| --- | --- |

| `.github/workflows/tests.yml` | one named step (§2.7) |
| `sample/README.md` | one line: the sample is now walked from card to release note, not only through one tick |

**Events.** None new. The loop writes the events it already writes — `launch` per session, the
tick's `metrics/ticks/` line, `metrics/events/` — and the scenario reads them rather than adding
to them. The release tags the loop cuts (`release-<day>-<sha7>`, or `v<version>` where the
sample declared one) land in the scenario's own bare origin and nowhere else.

**What is deliberately not written down.** No golden holds a sha, a timestamp, a temp path or a
minted id (§2.4). A golden that did would be rewritten on every run, and a fixture that changes
every run asserts nothing.
