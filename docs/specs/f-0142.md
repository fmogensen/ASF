# F-0142 — the tick says which step it is inside, and the doctor reads that line

B-0119 fixed half of one bug. A command step's own stdout now streams into the tick log as it is
produced, so a `factory-batch.sh` that runs for ten minutes is visibly working. But an `asf`-owned
step — `record`, `groom`, `wave`, `harvest` — prints nothing at all until it ends, and then one
line: `[step:harvest] 812.4s`. While a step runs there is no line saying which step it is, who owns
it, which process is in it, or when it began. B-0119's own plan filed the rest as this card:

> The card's Description also asks for a line when *each* step … starts and ends, naming the step,
> owner, pid and time and flushed at once, so that the doctor's SCHEDULER row can show the tick's
> current step. That is a second, independent piece of work: it touches the step-loop in
> `asf/tick/tick.py` … and `asf/doctor.py` … neither of which this Task changes.
> — `docs/plans/b-0119.md`, "Accepted costs"

This card closes it. Two changes, and they are the pair the card names: the tick prints a start line
and an upgraded end line around every step it actually runs, and the doctor's SCHEDULER row reads
that line back to name the step the tick is inside right now.

The second half is what the pid is for. An operator running `asf doctor` mid-tick today reads
`state=running  runs=7  last-exit=0  last-run=3s`: the job ran and the last one was green. It does
not say whether this tick is eight seconds into `record` or thirteen minutes into `harvest` — the two
readings an operator wondering *is it stuck* actually needs to tell apart. And a tick killed mid-step
reads the same as a healthy one, because `parse_print` reads `last exit code` and has no notion of a
signal (P10).

### In

- **A start line per step the tick actually runs**, flushed at once:
  `[step:<name>] start owner=<asf|command> pid=<pid> at=<ISO8601Z>`.
- **The existing end line grows the same three fields**, keeping its current prefix byte for byte:
  `[step:<name>] <seconds>s ok=<yes|no> owner=<asf|command> pid=<pid> at=<ISO8601Z>`.
- **The pairing contract**: every start line is followed by an end line for the same step unless the
  tick's process died between them. The one path that could start a step and not end it — the command
  step's own lock (P3) — is where the start line goes *after* the guard, not before it.
- **`asf doctor`'s SCHEDULER job row reads the last step line of that job's own log** and says which
  step the tick is inside, how long it has been in it, and which process is in it:
  `step: harvest running 13m (asf, pid 48213)`.
- **A tick that died mid-step is YELLOW and says so**, with the step it did not finish:
  `step: harvest unfinished — its tick (pid 48213) is gone, started 3h ago`. That is the reading P10
  makes invisible today.
- **One tail reader**, `_log_lines`, bounded to the last 1 MiB. `_log_tail` is rewritten over it and
  stops reading a whole multi-megabyte log to get one line (P7).
- **The prose both shapes are already documented in** (P16), and a test that reads it from the
  checkout.

### Out

- **A start/end line for a step the tick skipped.** `off`, `daily already ran today`, `at ci
  capacity`, the queue hold, `already running` — none of them starts a step, and a start line for one
  would be a lie the doctor then reports as a running step.
- **`[step:<name>] FAILED <why>`.** It stays exactly what it is: the line `run_asf_step` prints when
  a step raises, before the end line's `ok=no`. The two are not redundant — `FAILED` carries the
  reason, `ok=no` carries the fact in the machine-readable pair.
- **`[record:<part>]` and `[command:<step>]`.** `timed()`'s parts and B-0119's streamed command
  output are both untouched (P15, P4). The card is about the step loop.
- **The `metrics/ticks` line.** `ran`'s entries stay `{step, ok, seconds}` (plus `finish`'s `reason`)
  and the `steps:` array keeps its schema. The log line is for a person watching; the ticks stream is
  the record, and it already carries every field the new lines do except the pid.
- **A state file naming the current step** (`state/<product>/tick.step` or similar). See D8.
- **Rotating or truncating the tick log.** It grows without bound today; D7 bounds what the *doctor*
  reads, which is the cost this card creates. Rotation is its own card.
- **Making the doctor read the tick's *own* liveness any other way** — `ps`, the product's
  `tick.lock`, launchd's `state`. See D5.
- **`--shadow` and `--dry-run`** (P17), and `asf watch`, which reads the ticks stream and not the log.
- **A pid on `[command:<step>]` lines** (the child process's own pid). The line the doctor reads is
  the step's, not the command's; see D4.

### The choices

| # | Chosen | Against | Why |
| --- | --- | --- | --- |
| D1 | The end line keeps its exact current prefix — `[step:<name>] <seconds>s` — and appends the new fields | a second, separate end line beside the existing one; or a wholly new shape with the seconds moved | the card says the existing line "carries no owner, pid or timestamp", which asks for that line to carry them, not for a second one. Keeping the prefix is also what makes the blast radius three lines instead of twelve: `TIMING_RE` loses its `$` and every `steps_only` equality (P13) stays green |
| D2 | The start line's marker is the literal word `start` where the end line has its seconds | `[step:x] 0.0s start`, or a different bracket prefix like `[start:x]` | the doctor must tell the two apart by shape alone, and `start` versus `\d+\.\ds` is a one-token discriminator that also reads correctly to a person. A `0.0s` on a line printed before the work is a false measurement |
| D3 | `owner` is the loop's own token, `asf` or `command` | a fuller string like `asf.tick.step_harvest:run`, or the command line itself | the two tokens are the whole vocabulary already in hand (P2), they are what `--manifest` prints, and the command line is on the `[command:<step>]` lines anyway. A log field a person greps should be one of a known, short set |
| D4 | `pid` is the **tick process's** pid (`os.getpid()`), for both owners | the child process's pid for a command step | the field exists so a reader can ask *is this still going*, and the tick is the process that owns the step. It is also the only pid available where the line is printed — `run_command` spawns the child afterwards, inside another module — and one meaning for the field across both owners is what lets the doctor probe it without a branch |
| D5 | Liveness is `lifecycle.pid_alive(pid)` off the line | launchd's `state=running`, already in the row; the product's `tick.lock`; a `ps` scan | `state` is launchd's view of the *job*, which under the snapshot launcher is the launcher process and not the tick (`scheduler.render`); it is also still `running` while an orphaned command step outlives the tick. | D9 | The end line carries `ok=yes|no` | step, owner, pid and time only, as the card lists | one token, and it makes the pair self-describing: today a command step's failure is a separate `tick: step <s> exited N` line and an `asf` step's is `[step:<s>] FAILED …`, so nothing says *this step ended badly* in the step's own line. Named here rather than smuggled: it is the one field beyond the card's four, the doctor does not read it, and it costs no test |
| D10 | Both lines are printed with `flush=True` | rely on `cli.main`'s `line_buffered` (P5) | the card says "flushed at once", and P5 holds only for the `asf` entry point: a tick driven any other way — a wrapper, an embedded call, a future launcher that pipes — block-buffers again and the start line, whose whole purpose is to be readable *before* the step ends, is the one line that must not wait. `timed()` already does exactly this (P5) |
| D11 | The start line goes *after* the command step's lock guard, so it has two call sites — one per owner branch — sharing one formatter | one call site beside `t0 = time.monotonic()`, before the guard | one call site emits a start line for a step that is then skipped (P3), and the doctor would report a step no process is in. Two calls to one formatter is the honest shape: an `asf` step and a command step begin at different moments, and the `owner` the line carries is precisely that difference |
| D12 | `step_timing_line` is renamed `step_end_line`, with `step_start_line` as its pair | keep the old name and add `step_start_line` beside it | `step_timing_line` has one caller in the package and one in the tests (P14), and a pair of functions that print a pair of lines should be named as one. "Timing" also stops being what the line is once it carries the owner and the pid |
| D13 | The doctor's field is inserted between `last-run=` and `log:` | append it after `log: <tail>` | the tail is arbitrary free text of unknown length — a command's own output line (P4) — and nothing should be read after it. The step field belongs beside `last-run`, which is the other freshness fact on the row |
| D14 | `current_step` returns `None` the moment it meets an end line, scanning backwards | scan forward and pair up starts with ends; count them | one backwards scan to the first step line of either kind answers the whole question, because the loop is strictly sequential: the last step line in the file is either the step that is running or the last one that ended. Pairing would have to decide what an unmatched end means, which D11's contract already makes unnecessary |
| D15 | `_log_tail` is rewritten over the new `_log_lines` | leave `_log_tail` reading the whole file and give the new reader its own | two readers of one file in one function, with two different notions of how much of it to read, is one of them wrong. **The one behaviour change:** a log whose last 1 MiB contains no newline at all now yields that partial line rather than the file's true last line — a case no tick log can produce, since every line it writes ends in one |

## The design

### `asf/tick/tick.py` — the pair of lines

`step_timing_line` becomes `step_end_line` and gains a sibling. Both take their pid and their
timestamp as arguments defaulting to the live values, so a test can pin the whole line:

```python
def step_start_line(step, owner, pid=None, at=None):
    """``[step:<name>] start owner=<asf|command> pid=<pid> at=<ts>`` — printed as the step begins,
    so the tick log names the step it is inside while the step is still running, and the doctor's
    SCHEDULER row can read it back (F-0142). ``pid`` is the tick's own process: the step's owner is
    what the line is about, and a command step's child is named on its own
    ``[command:<step>]`` lines (D4)."""
    return (f'[step:{step}] start owner={owner} pid={pid or os.getpid()} '
            f'at={at or _stamp()}')


def step_end_line(step, seconds, ok=True, owner='asf', pid=None, at=None):
    """``[step:<name>] <seconds>s ok=<yes|no> owner=<owner> pid=<pid> at=<ts>`` — printed as each
    step ends, so a slow step is named in the log while the tick is still running, and the start
    line it closes is no longer read as a running step.

    The ``[step:<name>] <seconds>s`` prefix is the shape this line has always had and is what
    `asf doctor` matches an *ended* step on (D1); the fields after it are F-0142's."""
    return (f'[step:{step}] {seconds:.1f}s ok={"yes" if ok else "no"} owner={owner} '
            f'pid={pid or os.getpid()} at={at or _stamp()}')
```

### `asf/doctor.py` — the row reads it

One bounded tail reader, which `_log_tail` is rewritten over (D7, D15):

```python
#: how much of a tick log's end the doctor reads. The log is never rotated, so reading all of it
#: to find one line is an unbounded cost on every `asf doctor` (F-0142, D7). A step that prints
#: more than this after its start line shows no `step:` field — the row says what it says today.
LOG_TAIL_BYTES = 1024 * 1024

#: the tick's per-step lines (`asf.tick.tick.step_start_line` / `step_end_line`). `[step:<name>]
#: FAILED …` matches neither, and the end pattern also matches the pre-F-0142 shape, so a log
#: written by an older install reads as "no step running" rather than as a running one.
_STEP_START_RE = re.compile(r'^\[step:([a-z-]+)\] start owner=(\S+) pid=(\d+) at=(\S+)')
_STEP_END_RE = re.compile(r'^\[step:([a-z-]+)\] \d+\.\ds')


def _log_lines(path, limit=LOG_TAIL_BYTES):
    """The log's last ``limit`` bytes as non-empty rstripped lines, oldest first; ``[]`` when there
    is no log or it cannot be read."""


def _log_tail(path):
    """The log's last non-empty line, or None when there is no log yet."""
    lines = _log_lines(path)
    return (lines[-1] if lines else '') if os.path.exists(path or '') else None
```

The reader the card asks for, and the one thing on the row that is not a fact about the *last* tick:

```python
def current_step(path, alive=None, now=None):
    """The step a tick is inside, read off the tick log's own start line (F-0142):
    ``{step, owner, pid, alive, seconds}``, or ``None``.

    ``None`` when there is no log, when the last per-step line in the tail is an *end* line (the
    tick is between steps, or over), and when no per-step line is in the tail at all. A start line
    whose pid no longer answers is returned with ``alive`` false: that tick died inside that step,
    which is the one failure launchd's own `last exit code` cannot show (D6). ``seconds`` is how
    long ago the line's ``at`` was, or None when it cannot be parsed."""
    for line in reversed(_log_lines(path)):
        if _STEP_END_RE.match(line):
            return None
        m = _STEP_START_RE.match(line)
        if m:
            step, owner, pid, at = m.groups()
            return {'step': step, 'owner': owner, 'pid': int(pid),
                    'alive': (alive or lifecycle.pid_alive)(int(pid)),
                    'seconds': _since(at, now)}
    return None


def step_detail(running):
    """The row's ``step:`` field for a :func:`current_step` result."""
    age = '' if running['seconds'] is None else f" {format_age(running['seconds'])}"
    if not running['alive']:
        started = '' if running['seconds'] is None else \
            f", started {format_age(running['seconds'])} ago"
        return (f"{running['step']} unfinished — its tick (pid {running['pid']}) is gone"
                f"{started}")
```

## Records

- **The start line**, on the tick's stdout — which under a scheduler *is*
  `<ASF_HOME>/logs/tick-<product>-<clock>.log` (P6) — one per step the tick runs, flushed at once:
  `[step:<name>] start owner=<asf|command> pid=<pid> at=<ISO8601Z>`. Written by
  `tick.step_start_line` from `_run_steps`, and by nothing else.
- **The end line**, same file, one per step that started plus one per step that fell through a
  capacity or queue hold (P3): `[step:<name>] <seconds>s ok=<yes|no> owner=… pid=… at=…`. Its
  `<seconds>s` prefix is the record `asf doctor` matches an ended step on, and the pre-F-0142 shape
  is a prefix of it — an older log reads as "no step running", never as a running one.
- **The pairing contract**: a start line is followed by an end line for the same step unless the
  tick's process died between them. That is the whole of what `doctor.current_step` relies on.
- **`asf doctor`'s SCHEDULER job row** gains one field, between `last-run=` and `log:`:
  `step: <name> running <age> (<owner>, pid <n>)`, or
  `step: <name> unfinished — its tick (pid <n>) is gone, started <age> ago`. Absent when the job's
  log has no per-step line in its last 1 MiB.
- **One new doctor level transition**: `OK → YELLOW` when a job's last tick died inside a step.
  `YELLOW` is never folded into the doctor's exit code (P9), so no install that passes today fails
  after this change. `RED` is never reached by this path and never downgraded by it.
- **Nothing else is written.** No record card, no metrics event, no state file, no new config key, no
  new file anywhere. The `metrics/ticks` line and its `steps: [{step, ok, seconds}]` array are
  untouched, and `asf watch` reads that stream, not the log.
- **`docs/guide/operating.md`** — the start/end pair, that a skipped step prints neither, and that
  the doctor reads the start line. **`docs/guide/getting-started.md`** — the `step:` field on the
  SCHEDULER row and the YELLOW it can raise.
- **A product with no clock installed, and any `scheduler.kind` but `launchd`, is unaffected** (P11):
  the row this field lands on is not built for them.
