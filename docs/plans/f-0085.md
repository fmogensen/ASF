## Decisions (where the spec is silent, wrong, or needs a contract)

| # | Point | Decision | Why |
| --- | --- | --- | --- |
| PD1 | Story ids | The record holds no Story card for F-0085. This plan reserves **S-8400 … S-8409** from this session's `BACKLOG_ID_RANGE` for the spec's ten `- S:` lines, **in the spec's order** (S-8400 = the gate and config … S-8409 = the digest). `asf.record.plan_tasks.stories_of` keeps only ids the record holds, so until those cards exist the Task cards carry no `stories:`. The operator mints them (see the report) | A `stories:` line with no id cannot be checked for coverage. An id made up outside the range would be a guess |
| PD2 | How a policy name reaches the History line | §2.2 step 3 says `→ answer: controller: <word>`, and §2.2's last paragraph says the `who` is a known policy name *following* `controller:`. Both hold if the rendered answer is **`controller: <policy> <word>`**, e.g. `→ answer: controller: decide_recurring_bug yes`. A bare `controller: <word>` (hand-written) keeps `(controller, starvation policy)` | Needed to reconcile the two. The existing test `test_controller_prefix_changes_history_attribution` stays green |
| PD3 | The list of known policy names | `POLICY_NAMES` is a tuple in `asf/groom/groom.py`, the applier's side. `policy.POLICIES` must name exactly those (a test asserts it) | `policy.py` imports `groom.py` to apply its answers. Putting the names in `groom.py` avoids an import cycle |
| PD4 | How a barred question is marked in the groom file (§2.8, T7) | It stays an answerable line for the operator, but its answer slot reads `→ answer: ____ (barred: approvals.new_epic)`. **An open question** is a `- [ ]` line whose text ends exactly in `→ answer: ____`. A barred line does not end that way, so it is never counted open, never put to the session, and `_parse_answer` does not recognise it | T7 needs barred questions out of the row's open list. The groom file is the only thing the row counts (§2.5) |
| PD5 | Where the digest's reasons come from | History says *what* was applied and by whom. The *why* comes from the `<why>` of that card's line in `groom/<date>.md` (rule answers) and in `<date>.answers.done` (adjudicator rulings) | History lines carry no reason (§4's shape), yet §2.7's example does. Both files are in the record or the state dir, so the digest stays derived (D9) |
| PD6 | Open questions under the attempt cap, in the digest | Listed under **Spoken for** as `GROOM → ADJUDICATE`. Once `groom-<date>` has used `groom.adjudicate_attempts` runs with no answers file, those questions go to **For you** as `NEEDS OPERATOR` lines instead (D8). Also in **For you**: every `NEEDS OPERATOR:` line from an applied answers file, and every barred question | The spec's four sections have no other place for "asked, not yet answered". The session does speak for them |
| PD7 | The session's reach (D12) | The `groom` brief's `add_dirs` also carries the directory of `groom_file` (the record clone's `groom/`) and of `answers_file` (`<state>/groom/`, created if absent) | `add_dirs_for` today gives only `job_grants`. Without this, the session could neither read the groom file nor write the one file it exists to write |
| PD8 | "The open questions listed in the preamble" (§2.6) | The row carries them. `Row` gains `groom_date`, `groom_file`, `answers_file` and `open_questions` (a tuple of question lines), and `briefs.build.context` gains `open_questions` besides the spec's `groom_file` and `answers_file` | §2.6 asks for the list *in* the brief, yet names only two new context keys. This adds the third it implies |
| PD9 | The job name (D7) | `step_wave.job_name(brief_kind, item_id, key=None)`, with `KIND_JOB_KEY = {'groom': 'groom_date'}` naming the Row attribute. `worker_row` passes `getattr(row, KIND_JOB_KEY[kind])` | The date must travel on the row: `worker_row` sees only the row and the brief |
| PD10 | The printed line when the gate is off | Unchanged: `groom <date>: applied N, inbox N card(s) — …`. The `by rule / spoken for / open` counts appear only under `auto` | T1: the gate-off product "behaves exactly as today" |

### Shared contracts (the Tasks below code against these)

- `asf.groom.policy.groom_auto(product) -> bool` — the single gate (§2.1). Module-level imports:
  stdlib and `asf.env` only, so `asf.feeder.rows` may import it.
- `asf.groom.policy.open_questions(text) -> [(item_id, line)]` — the `- [ ]` lines ending exactly in
  `→ answer: ____` (PD4), in file order.
- `Row` (feeder) new optional fields: `groom_date=''`, `groom_file=''`, `answers_file=''`,
  `open_questions=()`.
- `groom_state = {'date', 'file', 'answers', 'open': [ids], 'lines': [lines], 'oldest', 'attempts'}`.
- The answers file is `os.path.join(env.state_dir(product), 'groom', f'{date}.answers')`.
- `cmd_groom(args, root)`: new optional `args.event` (a `ctx.event`-shaped callable or None) and
  `args.answers_file` (a path or None).
