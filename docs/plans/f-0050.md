# Plan F-0050 — six Tasks: the configuration, the probe, the proposal, the revert, the step, the command

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0050.md` (approved). Branch:
`plan/F-0050`.

Six Tasks, cut on the spec's own §2 section boundaries. Task 1 is everything an operator writes —
`improve: {product: {...}}`, the breach arithmetic it is read through, and the
`propose_product_change` class with its two yaml rows (§2.1, §2.5's class). Task 2 is the probe:
one reading and the development-only identity (§2.2, §2.3). Task 3 is the loop's first half —
measure, record, `met_before`, propose — with the queue's third entry kind it needs (§2.4, §2.5).
Task 4 is the second half: the verdict, the revert card and the five rails (§2.6). Task 5 is the
fourth part of the daily step and Task 6 the operator's two views (§2.7).

**The wave order is six waves of one Task: 1 → 2 → 3 → 4 → 5 → 6.** This plan is a chain, and PD4
says why rather than pretending otherwise: `tests/test_product_loop.py` is a single module named by
all nine of §3's fences, and `asf/product_loop/loop.py` is a single module carrying §2.4, §2.5 and
§2.6. Two Tasks whose `writes:` intersect never run together, so every pair here is ordered, and
declaring it on an `after:` line costs nothing and makes the order the plan's rather than the
scheduler's.

§3's preamble binds every Task — *"All from the repository root, stdlib only, no `~/.ASF` and no
network: every probe in the suite is a `run=` double or a script in
`tests/fixtures/product_loop/`"* — and so does its whole-suite fence, which has no Story of its
own. Both are copied into every Task's **Acceptance** beside the Task's own, and every **Gate**
runs them plus `tools/check_conventions.sh`, which PD20 shows this Feature can trip.

Each Task's own **Acceptance** is the §3 fence its Story names, copied byte for byte.

### Task 1: `improve: {product: {...}}` — the settings, the breach arithmetic, and the approval class
stories: S-33050
writes: asf/product_loop/__init__.py, asf/product_loop/measures.py, asf/env.py, asf/approvals.py, docs/products.example.yaml, sample/product.yaml, docs/guide/product-config.md, tests/test_product_loop.py, tests/test_approvals.py
after: none

§2.1, plus §2.5's `ActionClass` and the two yaml rows it cannot land without (PD8). Everything an
operator writes and everything that reads it, and one module that is pure — no file, no clock, no
subprocess, so its whole test is a dict in and a dataclass out.

`measures.py` is also where the one piece of arithmetic every later Task is built on lives:
`breach` is always *bigger is worse*, whichever direction the measurement runs, which is D6's
whole answer and the reason `worse` is one comparison rather than two.

**Files**

- `asf/product_loop/__init__.py` — new package, the docstring naming the three modules and the
  three files under `~/.ASF/state/<product>/` (§4)
- `asf/product_loop/measures.py` — `DEFAULTS`, `HIGHER_BETTER`, `LOWER_BETTER`, `Measurement`,
  `Probe`, `Settings`, `settings`, `epic_of`, `breach`, `breached`, `worse`
- `asf/env.py` — `IMPROVE_FIELDS` gains `'product': _MAP`
- `asf/approvals.py` — `propose_product_change` in `CLASSES`
- `docs/products.example.yaml` — a new `improve:` block carrying §2.1's `product:` map, and
  `propose_product_change: auto` in the `approvals:` block
- `sample/product.yaml` — `propose_product_change: auto` in its `approvals:` block
- `docs/guide/product-config.md` — the `improve.product` keys and what each is for
- `tests/test_product_loop.py` — new module; `SettingsTests`, `BreachTests`
- `tests/test_approvals.py` — `known_readers` gains `'product_loop'`

**Steps**

1. `asf/product_loop/__init__.py`: the package docstring. It names the interface, never a backend
   and never an Epic id (PD20a): the loop reads the measurements a product declares, takes them
   through a probe identity the product configures, and files into that product's own record. Name
   the three state files by their constants' homes, not by copying their string literals.
2. `asf/product_loop/measures.py`, opening with §2.1's `settings` docstring copied as it stands.
   `DEFAULTS = {'verify_days': 7, 'min_readings': 3, 'revert_margin': 0.05, 'max_per_run': 2,
   'timeout': 120}` and `HIGHER_BETTER, LOWER_BETTER = 'higher-is-better', 'lower-is-better'`
   exactly as §2.1 writes them. No import of `asf.env`, `os`, `time` or `subprocess` — the module
   is pure, and `SettingsTests` asserts that with `ast.parse` over its own source.
3. `Measurement` frozen, the five fields §2.1 names in that order (`name`, `command`, `unit`,
   `direction`, `guardrail`); `guardrail: float`. `Probe(account, base_url, timeout)` frozen, all
   three optional. `Settings(measurements, probe, epic, verify_days, min_readings, revert_margin,
   max_per_run, problems)` frozen, `measurements` and `problems` tuples.
4. `settings(product)`: `product.improve.get('product')` when `improve` is a dict and that key is a
   dict, else an empty map — so a product with no `improve:` at all, or an `improve:` without
   `product:`, yields `Settings` with no measurements and no problems, and D13's "not configured"
   is `not cfg.measurements`. Fill each numeric from `DEFAULTS` the way `scorecard.loop.settings`
   does (`asf/scorecard/loop.py:54-57`): take the yaml value only when
   `isinstance(v, (int, float)) and not isinstance(v, bool)`, never on truthiness (PD16).
5. Parse each entry of `measurements:`, in file order. A `name`, a `command` and a numeric
   `guardrail` are required; `unit` defaults to `''` and `direction` to `LOWER_BETTER` when unset.
   A missing or non-string `name`, a missing `command`, a non-numeric or boolean `guardrail`, or a
   `direction` that is neither constant, appends one line to `problems` naming the index and what
   is wrong (`measurement 2: guardrail is not a number — 'eighty'`) and drops the entry. A
   `guardrail: 0` parses (PD16). A duplicate `name` drops the later one with a problem line: the
   name is the dedupe key of every proposal and of every reading line (§4), so two of them would
   make one measurement's history the other's.
6. `Probe` from `probe:`: `account`, `base_url` and `timeout` (the last from `DEFAULTS['timeout']`
   under the same numeric test). No refusal is raised here — §2.3 owns every refusal, and
   `settings` must stay pure and total so `asf doctor` can read it without deciding anything.
7. `epic_of(settings, product)` → `settings.epic` else
   `product.conventions.default_bug_epic` else `None` (PD10). Read the convention through
   `asf.conventions`, never as a literal, and write no Epic id in the module (PD20a).

10. Rail 4 — **a broken probe never reverts** — is steps 4 and 7 together, and gets its own test

11. Rail 5 — **the loop never reverts a change it did not propose.** Only entries in its own state
