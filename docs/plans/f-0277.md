# Plan F-0277 — three Tasks: the trunk's own answer reaches the two readers that never asked it

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0277.md` (approved).
Branch: `plan/F-0277`.

**Three Tasks, two waves.** The spec's *In* is already three surfaces with one fact under them,
and the split follows the import graph rather than the prose: the fact is a pure function in
`asf/trunk_watch.py` that both readers import (C1), and the two readers are in packages that do
not see each other — `asf/evidence/` and `asf/workers/`+`asf/tick/`. So the fact lands first,
alone, and the two readers land beside each other after it.

```
wave 1   Task 1  asf/trunk_watch.py + evidence.queue_landed      after: none
wave 2   Task 2  evidence.chosen_pr wired into discover()        after: Task 1
         Task 3  lifecycle.ended_prs(landed=) + step_wave        after: Task 1
```

Task 2 and Task 3 run together: their `writes:` are disjoint (`asf/evidence/evidence.py` and
`tests/test_pr_cache_trunk.py` against `asf/workers/lifecycle.py`, `asf/tick/step_wave.py` and
`tests/test_occupancy_trunk_landed.py`), and neither reads a line the other writes — both read
only `trunk_watch.landed_prs`, which Task 1 has landed by then. Task 1 and Task 2 do intersect
on both of Task 1's evidence-side files, and that costs nothing: Task 2 is `after: Task 1`
regardless, because `chosen_pr`'s whole third argument is the map `landed_prs` returns.

Splitting Task 1 off rather than folding it into Task 2 is C1 and C12 taken literally. C12 says
both readers are fixed in one card; C1 says the rule may not live in the evidence pass, because
`asf/workers/lifecycle.py` is the second reader and must not import it. A single Task over all
five files would be one session holding the evidence pass, the lane lifecycle and the tick's wave
step at once — the three places the spec is most careful to keep apart.

**Every anchor the spec cites was re-read in this worktree at `3a9406786`, and the chain the card
turns on was run, not reasoned about.** Baselines, the three subject forms, the three derived
states and the rule order are in PD7. Eight findings are recorded below; one is a signature the
spec names by a function that does not exist (PD1), the rest are preconditions for a coder who
would otherwise hit them mid-edit. None changes the design, and none widens the footprint.

### Task 1: the trunk's landed PR numbers become one fact both readers can import
stories: S-74154
writes: asf/trunk_watch.py, asf/evidence/evidence.py, tests/test_pr_cache_trunk.py
after: none

The spec's *The design* §1, and nothing else. One new pure function beside `pr_of`, and
`queue_landed` becomes its two-line reading — same name, same one caller, same two landed
assertions (C3/P18). Nothing in this Task changes a derived state or a lane record: it puts the
fact where C1 says it must live, so Task 2 and Task 3 can both import it without importing each
other.

`landed_prs` is `{pr number: sha}`, not a set (C4): the sha is the Task's `merged_sha` and it is
in the same subject row, so a second lookup is a second chance to disagree. It reads all three
landing subjects through `pr_of` (C2) — `merge-queue: #<n> …`, `… (#n)`, `Merge pull request
#<n> …` — which is already the trio `asf/facts/landing.py:170-178` treats as one question, and
which is what closes P12's hole: a queue landing recorded by the queue's *trailer* rather than its
subject carries the `… (#n)` form and today's `queue_landed` misses it entirely.

It takes both row shapes, because its two callers produce different ones: `first_parent` yields
`{'sha', 'author', 'at', 'subject', 'body'}` dicts (`asf/trunk_watch.py:125-143`) and
`main_commits` yields `(sha, subject, [path, …])` tuples (`:1093-1102`). Both are newest first,
and the newest wins when two rows name one number.

stories: S-74155

The spec's *The design* §3 — the other half, and the one the trunk-keyed PR cache cannot help
with, because nothing in this path asks the trunk at all. `ended_prs(state_dir)` opens
`cache-prs.json` and counts only rows already saying MERGED or CLOSED, with no age check and no
trunk read (P7, re-read here at `asf/workers/lifecycle.py:1374-1392`). An hour-old OPEN row for a
PR the trunk carries returns `{}`, `pr_ended` is None (P8), `occupancy` keeps the lane record live,
and the Feature's next Task waits — until the next evidence pass rewrites the file ~45 min later.

`ended_prs` takes `landed=()` as a keyword (C7) rather than learning to read a repo: it is given a
state directory and no product, and the pass that *does* hold the product does the IO (P10). Every

written **last** and wins (C8), carrying the cached row's `headRefOid` when the cache has one, else
None (C9) — `pr_ended` ignores the head for MERGED, so nothing reads it, and the trunk sha would be
the *batch's* sha rather than the PR head's.

`occupancy` itself is untouched (P9): `pr_ended` reads MERGED, the branch goes on `dead_branches`,
`landed[item]` is set from the lane record's own sha, and the item leaves both `busy` and
`waiting_landing`. The feeder reads `occupancy` and nothing else, so the next-Task row follows with
no new code. `TRUNK_LANDED_DAYS = 2` (C10) is slack for a weekend without reading a month of trunk
every wave; the bypass watcher's `window_days` answers a different question and stays uncoupled.
