# Plan F-0094 — two Tasks, a strict chain: the brief and its five fences first, then the row that fires it

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0094.md` (approved). Branch:
`plan/F-0094`.

**Two Tasks, chained.** The spec's C12 rules the split and its order: the brief template is in the
amendable set, so the Task that writes it is `CONSOLE → AMEND` — the operator's session, never a
coder's (P15) — and the `KINDS` entry must land *with* the template or the whole-set fences are red
for a kind with no template (P14). Ordering the amend Story first means the trunk never carries a
row kind whose brief cannot be built. Measured at this branch point: Task 1's footprint gives
`CONSOLE → AMEND T-xxxx WAITS ON console: amendable asf/briefs/templates/epic-features.md`, and
Task 2's gives `PLAN → CODE T-xxxx WAITS ON T-xxxx` while Task 1 is unlanded (PD1).

1. **Task 1 — the `epic-features` brief, and the five fences a new session kind is inside.** The
   template, `KINDS`, `MODEL_TABLE`, the `done_features` context key and the fact behind it, the
   `ROWS` entry and the golden — **and two the spec's `## In` does not name**: the `BINDINGS` entry
   in `asf/roles/roles.py` (PD3) and the record grant in `add_dirs_for` (PD5). `after: none`.
2. **Task 2 — the `EPIC → FEATURES` row.** `epic_rows()`, the two gate lists, the `key()` clause,
   `intake_parents` through `candidates`/`plan_rows`/`plan_inputs`, the reader in
   `asf/groom/inbox.py` — **and one more the spec does not name**: `NO_LANDING_KINDS`, without
   which a *successful* session is judged `failed` (PD2, the one finding that decides whether this
   card works at all). `after: Task 1`.

Wave order: **1**, then **2**. Their `writes:` are disjoint (PD1).

Read **PD2 before writing a line of Task 2** — it is the difference between a lane that works and
one that adjudicates every Epic after three ticks. **PD3 and PD4 before touching `KINDS`** — the
moment the kind joins it, two tests in `tests/test_roles.py` decide both the role and the model
label, and only one pair of answers is green. **PD5 before assuming the session can write the
record.** **PD7 before wording the template's `{done_features}` heading**, and **PD8 before

after: none

The spec's `## The design` §3 in full, plus the two fences it does not name (PD3, PD5). After this
lands, `asf brief --kind epic-features` builds a brief that tells a session to draft an Epic's
Feature cards and file them with `asf inbox`, on the HEAVY model, under the interrogator's role,
with the record's intake directory on its `--add-dir` list — and the trunk carries no row kind yet,
so nothing launches it until Task 2 lands.

This is a `CONSOLE → AMEND` Task: `asf/briefs/templates/epic-features.md` is in the `role_agents`
amendable kind, so the operator's session writes it, never a coder's (P15, PD1).

Three things are load-bearing. **`KINDS` and everything else land in one commit** — the moment
`epic-features` is in `KINDS`, five whole-set fences iterate it, and a half-landed kind is a red
suite for a kind with no template (P14). **HEAVY is not a preference** (PD4): with the
`asf-interrogator` binding, LIGHT, CHEAP and a missing `MODEL_TABLE` row are each one red test.
And **the record grant is what makes `asf inbox` reachable at all** (PD5) — without it the
session's only write is outside every directory it can see.

Read **PD3 and PD4 before touching `KINDS`**, **PD5 before writing the `add_dirs_for` clause**,
**PD7 before wording the `{done_features}` heading**, **PD13 before writing the defect-word
sentence**, and **PD8 before the `ROWS` entry and the golden**.

### Task 2: the EPIC → FEATURES row, the pending-intake fact, and the landing judgement that makes a filing session succeed
stories: S-36901
writes: asf/feeder/rows.py, asf/groom/inbox.py, asf/tick/step_wave.py, asf/workers/lifecycle.py, tests/test_feeder.py, tests/test_inbox_shape.py
after: Task 1

The spec's `## The design` §1 and §2 in full, plus `NO_LANDING_KINDS` (PD2). After this lands, a
decided, open Epic with no open Feature beneath it gets one tier-2 `EPIC → FEATURES` row on
`epic/<id>`, ordered by the Epic's own rank behind every Task row, held by `feeder.hold: features`
and by an Epic past its budget, capped into `STALEMATE → ADJUDICATE` after three sessions — and the
session that files its cards and pushes nothing is recorded `finished`, not `failed`.

Three things are load-bearing. **`NO_LANDING_KINDS`** (PD2): measured, without it a successful
session judges `failed: unpushed work`, charges an attempt, and adjudicates the Epic on the third
tick. **`over_budget_epics` reaches this row through `ix.epic_of`, not `rows.epic_of`** (PD11) —
the index reader's version tests the item itself first, which is the only reason an Epic's own row
is under its own budget; the module-local `epic_of` at `:514` starts from the parent and would
return None. And **`intake_parents` defaults to `()` everywhere** (C8, PD9), so every existing
caller keeps working and a bare `asf next` over an index with no record beside it still plans.

Read **PD2 before anything else**, **PD9 before touching `plan_rows`' signature**, **PD12 before
the `key()` clause**, and **PD11 for the fourteen acceptance rows that were already measured green
against §1 as written** — the row code needs no invention, only transcription.
