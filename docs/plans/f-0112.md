# Plan F-0112 — the release channel: a product's tick installs the next ASF tag, and puts it back when the doctor goes red

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0112.md` (approved). Branch:
`plan/F-0112`.

Six Tasks. The spec's design section is sectioned by the module that gains the surface, and the cut
follows it, with one rule laid over the top: **nothing that can install a package lands before the
thing that decides *which* package, and nothing that decides lands before the install it calls can
survive being handed a tag.** That last clause is not decoration — read in this checkout,
`upgrade._install` verifies its install by comparing the new venv's `direct_url.json` commit
against the ref it was given, so `install(ref='v0.1.63')` fails verification on a perfectly good
install and returns 1 (PD3). The spec's `auto` path calls exactly that. So Task 2 teaches the
existing install the difference between "the ref pipx installs" and "the commit that proves it"
before any Task calls it with a tag.

Task 1 is `asf/env.py` — the `upgrade:` key, its three words, its default and the raw word the
doctor row needs. Task 2 is `asf/upgrade.py`'s release primitives — the hourly shared cache, the
version tuple, the mid-landing read — plus the tag-safe install and `cli.latest_release()`'s
routing through the cache. Task 3 is `release_report` itself, the `notify` policy, and the fork in
`asf/tick/tick.py` that makes the two channels exclusive, with the digest line. Task 4 is the
`auto` path — the install at the tag, the clocks and the doctor through the new binary, and both
log lines. Task 5 is the rollback and the one S1 Bug. Task 6 is the standing views: the doctor's
`upgrade` row and the guide's `## The release channel` section.

Two Tasks need nothing landed and start at once — Task 1 (one key on one class) and Task 2 (the
primitives, which read the install and never write it). They both create content in
`tests/test_release_channel.py`, so the feeder will run them one after the other; the wave below is
the dependency order, not a promise of concurrency. Tasks 3, 4 and 5 are a genuine chain — each
extends `release_report`'s own body — and Task 6 reads the channel state Task 5 writes.

Wave order: **1 ‖ 2 → 3 → 4 → 5 → 6**.

Every Task after the first two writes `asf/upgrade.py`, which is why they queue whatever their
`after:` says; here the queue costs nothing, because `after:` already serialises them. Task 6 is
the only Task whose `writes:` is disjoint from every other (`asf/doctor.py`,
`docs/guide/upgrading.md`, `tests/test_doctor.py`), and it still waits, for the `rolled-back` state
its RED case reads.

The spec's last two fences — the example product file with the new key, and the whole suite as CI
runs it — bind every Task, so every Gate below runs `bash tools/check_generic.sh` and
`python3 tools/run_tests.py` beside its own.

### Task 2: the release primitives — the hourly shared cache, the version tuple, and an install that can be handed a tag
stories: S-32801
writes: asf/upgrade.py, asf/cli.py, tests/test_release_channel.py, tests/test_install.py
after: none

The spec's §`asf/upgrade.py` down to `mid_landing`, D4, D5, D6, D7 and D12 — plus the correction
PD3, PD4 and PD5 all turn on. Everything here is a reader except the cache file and the `sha=`
parameter; no policy is consulted and no channel exists yet, so this Task changes no behaviour of
any product.

**Files**

- `asf/upgrade.py` — `RELEASE_POLL_S`, `RELEASE_RE`, `releases_path`, `latest_release`,
  `installed_release`, `version_tuple`, `newer`, `mid_landing`; `sha=` on `install`, `_install` and
  `refuses`, and `_ref_label`
- `asf/cli.py` — `latest_release()`'s remote branch routed through the cache (D12)
- `tests/test_release_channel.py` — `VersionComparisonTests`,
  `LatestReleaseIsReadOnceAnHourTests`, `MidLandingTests`, `TagInstallVerifiesByShaTests`
- `tests/test_install.py` — `LatestReleaseTests` (PD8)

**Steps**

1. `RELEASE_POLL_S = 3600` and `RELEASE_RE = re.compile(r'^v(\d+)\.(\d+)\.(\d+)(?:\+(\d+))?$')` at
   module level, with the spec's comments. `releases_path()` returns
   `os.path.join(env.ASF_HOME, 'state', 'releases.json')` — the exact shape `pending_path()` uses
   (`asf/upgrade.py:70-71`), one file for every product and for `asf status` (D4), written through
   the existing `_write_json` so the write is atomic and makes its directory.
2. `latest_release(url, now=None, run=subprocess.run)` → `(tag, sha)`. Read the cache; when its
   entry for `url` has an `at` younger than `RELEASE_POLL_S`, return its `tag`/`sha` and shell out
   to nothing. Otherwise `git ls-remote --tags <url> 'v*'` — **without** `--refs`, because the
   peeled `^{}` line is the commit an annotated tag points at and that sha is what PD3 and PD5 both
   need. Pick the greatest tag by `version_tuple`, prefer its peeled line's sha over the tag
   object's. Every attempt stamps `at`, successful or not; a failed read keeps the entry's previous
   `tag` and `sha` rather than forgetting them, so a dead network neither hammers the remote nor
   un-knows the release. `(None, None)` when nothing was ever read. The function never raises.
3. `version_tuple(text)` → `(major, minor, patch, past)` or `None` (D5): `v0.1.62` → `(0,1,62,0)`,
   `v0.1.62+7` → `(0,1,62,7)`. A plain tuple, not a string compare and not `packaging` — `v0.1.9`
   against `v0.1.62` is the string compare's classic wrong answer and `packaging` is not a
   dependency of this package. `+N` is ASF's own "commits past the tag", written by
   `cli._described_release` (`asf/cli.py:71-77`), and not a PEP 440 local version.
4. `newer(latest, installed)` is `version_tuple(latest) > version_tuple(installed)` with either
   side unreadable returning **False** (D6). An install whose release cannot be read at all is
   never upgraded on a guess: `__version__` is never bumped per release, so comparing against it
   would read as BEHIND forever and reinstall on every tick.
5. `installed_release()` → `(tag, sha)` of the running install: the tag from
   `cli._release(cli._checkout_root(), cli._direct_url())` — a git install's `requested_revision`,
   else a checkout's `git describe`, else the build stamp — and the commit from
   `drift.installed_commit()`. `(None, <sha>)` when the install records no release. Both are
   existing readers (P5) and nothing new is recorded at install time.
6. `mid_landing(product)` → `[(item, branch)]` from
   `lifecycle.occupancy(pool.sessions_path(product))['landing']` (PD14), sorted by item. The whole
   call is wrapped: any exception returns `[]`— and `[]` **holds** the install, it never clears it,
   so an unreadable ledger is the conservative answer. The docstring says which way round that is,
   because the return being empty means "nothing is landing" at the call site and the two readings
   of an error are opposite.
7. **The tag-safe install** (PD3, PD5). `refuses(url, ref, run=subprocess.run, sha=None)` and
   `_install(ref, run, out, sha=None)` and `install(…, sha=None)` each gain the parameter;
   `install` passes its own down to both. Inside `_install`: `target = sha or ref` is what
   `ci_red(url, target, run)` is asked about and what the new venv's `direct_url.json` commit is
   verified against, while `upgrade_command(url, ref)` still installs the **ref** the caller named
   — the tag, so pipx records it as `requested_revision` and `installed_release()` can read it
   next tick (PD4 is why that matters). `record_last(sha or ref)` keeps that file holding shas, as
   `batch_hold` expects. With `sha=None`, `target is ref` and every existing caller is unchanged:
   the trunk channel does not move a byte.
8. `_ref_label(ref)` — a ref matching `RELEASE_RE` prints whole, anything else `[:7]`. The three
   messages that today print `{ref[:7]}` (`refuses`'s red-CI phrase, `_install`'s skip line and its
   FAILED line) read it, so a tag never prints as `v0.1.6`.
9. `asf/cli.py`: `latest_release()` keeps its signature, its docstring and its checkout-first
   branch. Its remote branch becomes `tag, _sha = upgrade.latest_release(url)` and
   `return (tag, None) if tag else None` (PD6, D12) — the `(tag, None)` shape `views/status.py:421`
   unpacks is unchanged, `asf status` stops shelling out to `git ls-remote` on every run, and the
