# Plan F-0184 — nine Tasks, four waves: the measure and the stream first, then the census that tiers off them, then the four readers that pace off the census, then the documentation

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0184.md` (approved). Branch:
`plan/F-0184`.

**Nine Tasks, four waves.** The card is five stages over eight modules, and the dependency is one
shape: nothing can be tiered before there is something to measure, and nothing can be paced before
there is a census to pace off. So the two leaves go first (the measure, the stream), the census sits
alone in the middle, and the four readers that consume it run together.

1. **Task 1 — the measure.** `asf/ci_measure.py`, `tests/test_ci_measure.py`. `after: none`.
2. **Task 2 — the `ci` stream's selector and its four figures.** `asf/metrics/metrics.py`,
   `tests/test_metrics.py`. `after: none`.
3. **Task 3 — `ci.pool: discover`, the census, the tier, the tick.** `asf/ci_census.py`,
   `asf/ci_pool.py`, `tests/test_ci_census.py`. `after: Task 1`.
4. **Task 4 — `asf-` is ASF's namespace, and the `runs-on` nobody can route.** `asf/ci_pool.py`,
   `tests/test_ci_pool.py`, `tests/test_ci_reserve.py`. `after: Task 3`.
5. **Task 5 — the four doctor rows.** `asf/doctor.py`, `tests/test_doctor.py`.
   `after: Task 1, Task 3`.
6. **Task 6 — `capacity.batch`'s measured pair.** `asf/capacity.py`, `tests/test_capacity.py`.
   `after: Task 3`.
7. **Task 7 — the queue's two wait limits.** `asf/ci_queue.py`, `tests/test_ci_queue.py`.
   `after: Task 3`.
8. **Task 8 — queue wait per Feature, beside CI minutes.** `asf/scorecard/score.py`,
   `asf/views/scorecard.py`, `tests/test_scorecard.py`. `after: none`.
9. **Task 9 — the documentation.** `docs/products.example.yaml`, `docs/guide/ci-runner-pool.md`.
   `after: Task 3, Task 4, Task 6`.

Wave order: **(1, 2, 8) → (3) → (4, 5, 6, 7) → (9)**. Every `writes:` set is pairwise disjoint
except Tasks 3 and 4, which share `asf/ci_pool.py` and are a strict chain anyway (PD22).

**Five findings change what a Task must build, and every one of them is read off this checkout, not
argued.** Two of them are defects in the spec that would stop a coder's work from running at all:

**Read PD2 before writing a line of Task 2.** The spec's P9 says the `ci` event's `jobs` value *"is
schema-checked as `'list'` only, so its elements' fields are not validated and may be added to."*
That is false. `metrics.py:223` applies `JOB_SCHEMA` to every job dict and `_apply` **raises** on an
unknown key (`:167-169`). §2.2's job fence, written as it stands, makes every backfill raise
`SchemaError: ci.jobs[0]: unknown key(s) queued_s, seconds` — the card's whole measure reads an
empty stream for a new reason.

**Read PD1 before writing Task 3's acceptance.** §3.1 asks that `capacity.product_ci` return
`(5, 'ci.pool: asf-fast 1, asf-bulk 4')`. `slots_by_role` ends `return dict(sorted(out.items()))`
(`ci_pool.py:209`), so the reachable string is `'ci.pool: asf-bulk 4, asf-fast 1'`. O9 forbids
touching that function. The spec's expected string is wrong; the assertion is not.

**Read PD3 before putting the census row anywhere.** `ci_pool.doctor_rows` returns `[]` at `:885-886`
*before* any host call when the pool is empty, so §3.1's two halves — "exactly what a no-pool product
returns" and "one required doctor row naming the missing census" — cannot both live in that function.

**Read PD4 before writing `apply_tiers`.** `start_trial` takes a plan `Step`, and D9 forbids calling
`plan`. The `current` the Step carries becomes `labels_before`, and `check_trials`' rollback brings
the runner to **exactly** that list — so a Step built with the tier alone strips the reserve label off
a demoted box on a failed trial.

**Read PD6 before writing Task 6.** §2.4's *"class **online** slots"* is not computable from the
census: the record has no `online` key. §3.6's own arithmetic is over the census's slots, and a
`backend.runners()` inside `batch_shape` would put a `gh` round trip on `capacity.py:594` — the exact
thing D1 exists to refuse, one module over.

| PD1 | **`slots_by_role` sorts its roles alphabetically, so §3.1's `'ci.pool: asf-fast 1, asf-bulk 4'` is unreachable — and §Records' identically-shaped `ci census` row *is* reachable, because that one is new code** | `slots_by_role` (`ci_pool.py:205-209`) ends `return dict(sorted(out.items()))`, and `pool_ci` (`:212-219`) joins that dict in its order. **Measured** in this worktree: a census of one `asf-fast` and four `asf-bulk` gives `pool_ci` → `(5, 'ci.pool: asf-bulk 4, asf-fast 1')`. `'asf-bulk' < 'asf-fast'`, so fast can never come first through this path. **The spec's §3.1 string is wrong.** Two repairs were available and both are refused: ordering `slots_by_role` by `ci_census.TIERS` would change the detail line of every **declared** pool, which O9 forbids in as many words (*"every test of the declared path keeps passing unchanged"*); and naming the tiers so they sort the wanted way (`asf-a-fast`) is a label rename for a cosmetic reason. **Decided:** Task 3 asserts `(5, 'ci.pool: asf-bulk 4, asf-fast 1')` and says in a comment that the order is `slots_by_role`'s, not a tier ranking. The *rest* of §3.1's sentence — that `product_ci` returns 5 with no `capacity.ci` declared, and 6 after a sixth runner — is exactly right and is the load-bearing half (P4: `capacity.py` needed no change). **And the distinction that keeps §Records honest:** the `ci census: 6 runners — asf-fast 2, asf-bulk 4` row is built by `ci_census.census_rows`, a function this card writes, so it orders by `TIERS` deliberately and fast **does** come first there. Two rows that look alike, one constrained by ten-year-old sorting and one not; do not "fix" either to match the other. |
| PD2 | **`_apply` raises on an unknown job key, so §2.2's two new job figures must also be declared in `JOB_SCHEMA` — the spec's P9 says otherwise and is wrong, and following it makes every backfill raise** | `JOB_SCHEMA = {'name', 'conclusion', 'runner', 'minutes', 'failed_step'}` at `metrics.py:160-161`, and `_apply(JOB_SCHEMA, j, f"ci.jobs[{n}]")` runs over **every** job of **every** `ci` event at `:223`. `_apply` opens `unknown = sorted(set(obj) - set(schema))` and `raise SchemaError(f"{where}: unknown key(s) …")` (`:167-169`) — it does not drop, it refuses. **Measured:** `_apply(JOB_SCHEMA, {'name': 'gate', 'conclusion': 'success', 'minutes': 3, 'seconds': 182.4}, 'ci.jobs[0]')` → `SchemaError: ci.jobs[0]: unknown key(s) seconds`. So P9's *"its elements' fields are not validated and may be added to"* is false on both halves: they are validated, and they may not be added to. §2.2's fence adds `wall_minutes` and `queue_s` to the **run** schema and says nothing about the job one. **Decided:** `JOB_SCHEMA` gains `'seconds': (('num', 'null'), None)` and `'queued_s': (('num', 'null'), None)` — `'null'` because §2.2's own docstring says *"None when either is absent"* and `_CHECK['num']` (`:108`) rejects None, and defaulted because a job dict recorded before this change must still validate, which is the property D5 and `## Records` both claim for all four figures. The run's two keep the spec's `(('num',), 0)` exactly: they are computed from the run's own stamps and never None. This is a **completion** of I3, not a widening: the same four figures, declared in the two schemas that actually check them. |
| PD3 | **`doctor_rows` returns `[]` before it reads the host when the pool is empty, so the `ci census` row cannot live in it — it is `ci_census.census_rows`, wired in `doctor.py`** | `doctor_rows` (`ci_pool.py:880-898`) opens `pool = load_pool(product)` / `if not pool: return []` — *"`[]` without a pool — no CI host call at all then"*. §3.1 asks for two things of one function: that `doctor_rows` over a discovered product with no census return *"exactly what they return for a product with no pool at all"* — which is `[]` — **and** *"one required doctor row naming the missing census"*. A row returned from `doctor_rows` breaks the first clause; the first clause is the one D2 rests on (the degradation is to today's no-pool behaviour, not to a new failure). **Decided:** `ci_census.census_rows(product)` returns `[(required, ok, detail)]` — the count-and-tiers row, the `no census yet` row, the amber-past-`CENSUS_STALE_S` row — and `doctor.py` calls it beside `check_ci_pool`, as its own `ci census` row group (Task 5), exactly as `check_ci_runners` and `check_cloud` sit beside it at `doctor.py:959-963`. `ci_pool.doctor_rows` is **not touched by this card at all** except for Task 4's `drift` row. **Two consequences, both correct and both named so nobody patches them:** a discovered product whose census is empty gets **no** drift rows, so §2.6's required `runs-on` row does not fire until the first census is taken — right, because there is no tier to route to yet, and the `ci census: no census yet — the next tick takes one` row is the one that should speak. And `census_rows` is the only new required row that fires with no host call whatever, which is what makes `asf doctor` on a fresh discovered product still a local command. |
| PD4 | **`start_trial` takes a plan `Step` and D9 forbids calling `plan`, so `apply_tiers` builds the Step itself — and its `current` must be the runner's whole label set, or a failed trial strips the reserve label off the box** | `start_trial(product_name, step, now=None)` (`ci_pool.py:1072-1076`) reads `step.runner`, `step.entry.role`, `step.current` and `step.add`, and writes `labels_before=list(step.current)`. `Step` (`:919-929`) is a dataclass whose last four fields have defaults, so it is constructible by hand. **The trap is what `labels_before` is for.** On a failed trial `check_trials` runs `_set_labels(backend, host, [_norm(l) for l in t.get('labels_before', [])])` (`:1146`), and `_set_labels` (`:1079-1088`) brings the runner to **exactly** `want`: it adds what is missing and removes every non-default label that is not in the list. A Step built as `current=[old_tier]` therefore makes a failed promotion remove the runner's `asf-pr-fast` reservation and any `class-` label it carries — a rollback wider than the write it is rolling back, and it contradicts §3.1's own requirement that unrelated labels survive. **Decided:** `apply_tiers` builds, per moved runner, `Step(runner=r.name, current=sorted(r.norm_labels()), target=sorted(r.norm_labels() - {old} | {new}), add=[new], remove=[old] if old else [], blocked=[], trial=(new == FAST), entry=PoolEntry(runner=r.name, role=new, …), host=r)`, writes only `add` then `remove` through `backend.add_labels` / `backend.remove_label` (D9 — never `_set_labels`, which is the full sweep), and calls `start_trial` only when `new == FAST` (D10). `current` is the runner's **whole** normalised label set as the host reported it, so a rollback restores the box to what it was and nothing more. Do not reach for `_set_labels` to do the write: it is the sweep D9 refuses, and `apply` (`:1012`) is the command that owns it. |
| PD5 | **D8's floor and D10's trial collide: the trial withdraws the tier label while its job runs, and on a floored fleet that empties the fast tier D8 exists to keep full. The floor is re-applied by the next census, and that is the whole answer** | `check_trials` on a job still running does `backend.remove_label(host, t['role'])` and marks the trial `running` — *"'{role}' withdrawn until it ends"* (`ci_pool.py:1120-1127`). `t['role']` on a tier promotion **is** `asf-fast`. So a fleet where D8's floor promoted exactly one runner, whose promotion is a trial (D10), loses its only `asf-fast` label the moment that runner picks up a job — and every `runs-on: [self-hosted, asf-fast]` is unsatisfiable until the verdict lands, which is the failure D8's own reasoning calls *"the worst version"* of the card's fourth acceptance. **Decided: nothing in `check_trials` changes, and the floor is not made conditional.** The floor is evaluated on **every** `refresh`, off the census file, and the withdrawal is invisible to it: `refresh` reads the tier a runner *carries* from the **census** (D6's `carried`), not from the host's labels, so the next tick sees the runner as `asf-fast`, finds the tier non-empty, and moves nothing. The exposure is therefore one tick long, bounded by the trial job's own duration, and it is the price D10 names — *"a box promoted on a stale median is caught by its first real fast job"*. Two things follow and both are binding: **`refresh` must read `carried` from the census, never from `runner.labels`** (a host read would make the withdrawal look like a demotion and start a flap on every trial), and `apply_tiers` must **not** re-add a label a trial has withdrawn — the runner is not in `moves`, so it does not, and it must stay that way. The alternative — exempting a floored promotion from the trial — was rejected: a floored runner is the *least* proven box in the fleet (its ratio is above `DEMOTE_AT`), so it is the one promotion that most needs a judged job. |
| PD6 | **`batch_shape` reads slots off the census, not off the host: §2.4's word "online" is not in the census record, and a host call there would be D1's sin one module over** | §2.4 says `parallel` is *"`min(class online slots // needs[class])` over the classes the run needs"*. The census record is `{runner, tier, ratio, n, green_rate, flaky, since, why}` (`## Records`) — **no `online`** — and `cached()` returns `PoolEntry` rows, which have no such field either. The only way to know online is `backend.runners()`, and `batch_shape(product, cfg)` is called from `capacity.py:594` (the `ASF_CAPACITY_*` environment every batch step is handed) and `harvest/lane.py:3117`. A `gh` round trip at either is precisely what D1 refused for `load_pool`, for precisely the same reason. **And §3.6's own arithmetic settles it:** *"a census of 2 `asf-fast` and 4 `asf-bulk` and a cached measure of `{asf-fast: 2, asf-bulk: 4}` returns `runners` 6 and `parallel` 1"* — `min(2//2, 4//4) = 1`; *"with 4 `asf-fast` and 8 `asf-bulk` it returns `parallel` 2"* — `min(4//2, 8//4) = 2`. Both are over the census's slots with no online filter anywhere. **Decided:** `runners` is `sum(expected_run_needs(product).values())` and `parallel` is `min(slots_of_tier[c] // n for c, n in needs.items() if c in slots_of_tier)` floored at 1, where `slots_of_tier` is `ci_pool.slots_by_role(ci_census.cached(product))` — two file reads and no network. ### Task 1: the measure — per runner per job kind, a median, a ratio, a green rate, a baseline and a regression
stories: S-37353, S-37360, S-37361

after: none

how long each box takes on each job kind, how that compares to the fleet's best, how often it comes
back green, what a timing guard should expect of it, and which green job has quietly grown half again
past its own baseline.

This Task is the whole card's foundation and it is also its most self-contained piece: a new module
over hand-built dicts, with no host, no product config, and no other Task's code. It is written
against events that carry `seconds` and `queued_s` — which Task 2 is adding — and D5 is exactly why
that is not a dependency: *"the measure tolerates a job with no `seconds`, falling back to
`minutes × 60`"*. Write the fallback first and the fine reading second; both paths are tested here
and both are exercised in production during the fortnight after Task 2 lands.

**Read PD14 before writing the skipped-job case.** The jobs jq already drops `skipped`
(`metrics.py:1688`), so that case is a property of `MEASURED`/`RATED` over hand-built events, not a

Four things are load-bearing. **A ratio needs two boxes** (D12): a job kind only one runner has ever
run has no fleet best, its ratio is 1.0 by construction, and including it drags every specialised
box's figure toward 1.0 — so a kind fewer than two runners have `MIN_READINGS` of appears in
`medians` and in **no** `ratios`. **A runner's one number is the median of its ratios** (D13), not
the worst (which condemns a box for one badly-matched job) and not the mean (which lets many fine
kinds hide one terrible one). **The green rate's denominator is `RATED` only** (D14): a cancelled or
skipped job says nothing about the box, and counting cancellations makes every box look flaky on a
day the relief pass cancelled a lot. **A baseline is never invented** (§2.5): a job kind with
readings on neither the runner nor its tier exits 1 printing nothing, because a guard that cannot
get a baseline should skip its check.
