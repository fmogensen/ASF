# Plan F-0114 — the upgrade migrates itself, the files carry a version, and every release is tested into HEAD

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0114.md` (approved). Branch: `plan/F-0114`.

Seven Tasks, cut the way the spec's `## The design` is cut — by the module that gains the surface.
Task 1 is `asf/schema.py` and the one line of `asf/cli.py` that finally calls it: two version numbers,
migrations that declare whether they are additive, `pending`/`blocking`/`auto_migrate`, the snapshot
and its restore, and the refusal wired once at the dispatch. Task 2 is `asf/env.py`: the version on
the file, a tolerant reader across versions and a strict one inside a version, and the rename table
read as deprecations. Task 3 is `asf/doctor.py` and `asf/capacity.py` — the new `schema` row, the
`config` row that stops swallowing the rest of the table, and the two hand-written deprecation lines
deleted in favour of the table. Task 4 is `asf/tick/tick.py`: the migration that runs before the
steps, drained to a bound, one line per step. Task 5 is the install side — `asf/upgrade.py`,
`asf/init.py`, `asf/install.py` — the upgrade that migrates what it installed, the `config schema`
column, `--to <ref>`, and the stamp on a file the moment it is first written. Task 6 is
`tools/upgrade_matrix.py` and the `upgrade-matrix` job. Task 7 is `asf/release.py` and
`asf/metrics/metrics.py`: the ninth criterion, the `### Migrations` heading in a release's notes, and
the guide brought into step with all of it.

Only Task 1 starts at once; it invents every fact the other six read. Tasks 2, 4 and 5 each need only
Task 1 — the reader needs `CONFIG_VERSION` and `CONFIG_MIGRATIONS`, the tick needs `auto_migrate` and
the dispatch guard's exemption, the upgrade needs `auto_migrate`, `snapshot` and `restore`. Task 3
needs Task 2's `product_warnings` and `deprecated_reads`. Task 6 needs Tasks 4 and 5 both landed,
because a leg's assertion *is* "the tick migrated itself after the upgrade installed HEAD". Task 7
needs Task 6, because a gate criterion that reads a job's step is only honest once the job exists.

Wave order: **1 → 2 ‖ 4 ‖ 5 → 3 ‖ 6 → 7**.

Every Task's `writes:` is disjoint from every other's except `tests/test_schema_version.py`, which
Tasks 1, 3 and 4 all touch — the spec fixes the module name in its fences, so it is not a choice
(PD16). The queue costs nothing here: Task 1 is alone in wave 1, Task 4 is in wave 2 and Task 3 in
wave 3, so no two of the three are ever eligible at the same time.

§Acceptance tests' last fence — `check_conventions.sh`, `check_generic.sh` and `asf plugin check` —
binds every Task, so every Gate below runs it beside its own, and every Gate ends with
`python3 tools/run_tests.py`.

### Task 1: `asf/schema.py` — two numbers, migrations that say whether they are additive, and the refusal that finally has callers
stories: S-69204, S-69207, S-69210
writes: asf/schema.py, asf/cli.py, tests/test_schema_version.py, tests/test_surface.py
after: none

The spec's §1 whole: `CONFIG_VERSION` beside `SCHEMA_VERSION`, a `Migration` record carrying
`additive`, `pending`/`blocking`/`auto_migrate`, the `_set_config_version` that can insert, the
snapshot and its restore, `changelog_notes` — and the one guard at `asf/cli.py`'s dispatch that turns
`require` from a function with no caller (P1) into the refusal the guide has been promising. Nothing
in this Task changes what any command *prints* on a matching install: every version in the field is
`1`/absent, so `pending` is the config stamp alone and every step of it is additive.

**Files**

- `asf/schema.py` — `CONFIG_VERSION`, `TICK_DRAIN_S`, `tick_drain_s`, `Migration`, `MIGRATIONS`,
  `CONFIG_MIGRATIONS`, `product_version`, `config_files`, `pending`, `blocking`, `require`,
  `auto_migrate`, `migrate_config`, `_set_config_version` (insert), `snapshot`, `restore`,
  `snapshots`, `changelog_notes`; `check`, `migrate_dir` and `migrate_product` keep their signatures
- `asf/cli.py` — one guard in `_main` after `parse_args` (PD5, PD6)
- `tests/test_schema_version.py` — `RequireRefusesOnlyANonAdditiveGapTests`, `ConfigMigrationTests`,
  `EveryMigrationIsAdditiveOrBumpsTheMinorTests`; `RecordCarriesSchemaVersionTests` and
  `IngestKeepsTheStamp` untouched
- `tests/test_surface.py` — `EveryRecordWriterChecksTheSchemaTests`; the `COMMANDS` count literal is
  **not** touched (P21: this Feature adds no command)

**Steps**

1. `CONFIG_VERSION = 1` beside `SCHEMA_VERSION = 1`, with D1's comment: one key name
   (`schema_version`), two numbers, each compared against its own file — a config-field rename must
   not cost the 500-card commit a record bump costs (P8). `TICK_DRAIN_S = 120` (D4) and
   `tick_drain_s(cfg=None)` reading `config.yaml`'s `upgrade.migrate_drain_s`, non-negative number or
   the default (PD14), the shape `upgrade._config_number` already uses.
2. `class Migration(NamedTuple)`: `apply` (the callable, as today), `additive: bool` — "a package at
   `n` still reads and writes a file at `n-1`" — `note: str` (one line, for the CHANGELOG and the
   tick log), and, for the config table, `renames: dict` and `removes: tuple`, both defaulting empty,
   from the spec's **In** bullet "a `CONFIG_MIGRATIONS` entry declares `renames` and `removes`". One
   record type, two tables.
3. `MIGRATIONS = {1: Migration(_migrate_to_1, additive=True, note='the first stamped schema')}` —
   the existing `_migrate_to_1` and its docstring unchanged — and
   `CONFIG_MIGRATIONS = {1: Migration(_config_to_1, additive=True, note='the first stamped config',
   renames={'feeder.capacity': 'capacity.per_product.sessions', 'worker_pool.reserve_for_s1':
   'capacity.reserve_for_s1'}, removes=())}`. `_config_to_1(paths)` stamps and changes nothing else
   (PD8), with a docstring saying why the renames are declared and not applied.
4. Reading the numbers. `config_version()` keeps its meaning exactly — `None` when the key is absent,
   "no opinion" (PD7) — and `product_version(name)` reads `products/<name>.yaml`'s `schema_version`
   the same way. `config_files()` → `[config_path()] + sorted(products/*.yaml)`, the set a config
   migration stamps and a snapshot copies.
5. `pending(product)` → `{'record': [(a, b, Migration)], 'config': [(a, b, Migration)]}`: the steps
   standing between each file's stamp and the package's number, the record's taken as the lowest
   stamp over `record_dirs(product)` (absent counts as 0) and the config's as the lowest over
   `config_files()` (absent counts as 0). A stamp *greater* than the package's is never in `pending`
   — that is forward-only, and it is `migrate_dir`'s existing refusal, unchanged.
6. `blocking(product)` → the entries of `pending` whose `additive` is False, plus the newer-than-the-
   package case of step 5. `require(product)` keeps its signature, its `EXIT_MISMATCH` (3) and its
   exact line — `NEEDS OPERATOR: run asf schema-migrate — <detail>` — and changes only its condition:
   it refuses when `blocking(product)` is non-empty and returns True otherwise (D2). `check(product)`
   is left as it is: `upgrade.row` is its only caller (P2) and the table it renders still wants to
   show a pending additive step.
7. `auto_migrate(product, drain_s=None, out=print)` → `(ok, lines)`. `drain_s` defaults to
   `tick_drain_s()`. It drains through the existing `sessions_in_flight`/`DRAIN_POLL_S` loop bounded
   by `drain_s`; applies the record steps through `migrate_dir` against the tick's clone with
   `shadow.commit_local`, one commit per step as today, then pushes as `migrate_product` does (a
   refused push leaves the commit local for the next tick, P9); applies the config steps through
   `migrate_config`. It returns one `migrate: schema a → b` line per record step and one
   `upgrade: config.yaml schema a → b — <note>` line per config step. Still in flight past the
   bound: `(False, [f'schema {a} → {b} still pending — {n} session(s) in flight'])`, applying
   nothing — the caller decides what that means (Task 4).
8. `migrate_config(target=None)`: for each pending config step, `snapshot` first when the step is not
   additive (D10), run its `apply` over `config_files()`, then stamp every one of them.
   `_set_config_version(version, path=None)` is fixed to **insert** `schema_version: <n>` as the
   file's first key when no `schema_version:` line is there (P3) and to leave every other byte alone
   — no reserialise: these files carry the operator's comments, and `docs/config.example.yaml` is
   mostly comment. It stamps `config.yaml` and every `products/*.yaml` the same way.
9. `snapshot(product, version)` (D10): tag the record clone `asf-schema-<a>` at the commit before the
   first step and push the tag, and copy `config.yaml` and every `products/*.yaml` under
   `~/.ASF/state/backups/config-<a>-<stamp>/`. `snapshots()` lists what is on disk, newest first, as
   `(version, stamp, dir)`. `restore(version)` is its inverse: the config files copied back, and the
   record clone brought to the tag as a **fresh commit** (`git checkout <tag> -- .` then a commit) —
   never a history rewrite, never a force-push, so a record with an origin other people pull stays
   safe to restore from any checkout.
10. `changelog_notes(since_record, since_config)` → the `note` of every `MIGRATIONS` entry above
    `since_record` and every `CONFIG_MIGRATIONS` entry above `since_config`, in version order; `[]`
    when nothing lies between. Task 7's release notes are its only caller.
11. `cmd_schema_migrate` keeps its own longer drain (`--drain-timeout`, 3600 s) and its exit codes,
    and now migrates the config too: it prints one `schema-migrate: config.yaml schema a → b` line
    per config step and keeps the existing `schema-migrate: config.yaml schema_version → N` line for
    the stamp. The module docstring's "Rollback is reverting that commit and reinstalling the older
    package" is replaced by D10's sentence.
12. `asf/cli.py`: after `args = parser.parse_args(argv)` and before `root = os.getcwd()`, one block
    (PD5): look the command up in `surface.COMMANDS`; when its effect is `surface.RECORD`, and its
    `flag` column is `None` or that flag/subcommand is present on `args`, and the command is not
    `tick` (PD6), call `schema.require(product)` for the product the command resolves. A
    `ConfigError` out of that resolution is **not** swallowed and **not** turned into a schema
    refusal: it propagates to `main`, which already renders it as the `NEEDS OPERATOR` line and
    exit 2. Reads never check — the table is the whole rule, and no command body is edited.
13. `RequireRefusesOnlyANonAdditiveGapTests`: a record and a config both at the package's numbers
    pass; an additive gap passes and writes nothing; a non-additive gap exits 3 with the line, for
    the record and for the config independently; a file stamped *newer* than the package exits 3 with
    `migrate_dir`'s forward-only wording; an **absent** stamp never refuses (PD7).
14. `ConfigMigrationTests`: `pending` over an unstamped `config.yaml` and two unstamped
    `products/*.yaml` is one additive step each; `migrate_config` stamps all three and leaves every
    other line byte-identical, comments included; the stamp lands as the file's **first** key;
    running it twice changes nothing the second time (idempotent); a non-additive entry snapshots
    first and the snapshot holds the pre-migration bytes; `restore` puts them back.
15. `EveryMigrationIsAdditiveOrBumpsTheMinorTests` — the rule of D10 as a test over the tables, not
    over a run: for every entry of `MIGRATIONS` and `CONFIG_MIGRATIONS` with `additive=False`, the
