# Plan F-0140 — the three things the snapshot fix left behind

Epic: E-0004 — Control plane — the factory's dashboard, served from the record. Spec:
`docs/specs/f-0140.md` (approved). Branch: `plan/F-0140`.

The card's own subject — *tick from an immutable snapshot* — is already on the trunk and green; the
spec's §3.1 is the probe and `O1` is its consequence. Verified again here at this branch point:
`python3 -m unittest -q tests.test_snapshot` → `Ran 9 tests in 2.808s … OK`. So this plan mints no
Task for the snapshot clock itself, and three for the three Stories the fix left behind.

Three Tasks, cut one per Story, and they run **1 → 2 → 3**, one at a time:

1. **the launcher refreshes itself** — `snapshot.refresh_launcher` and the call in `main()`. The one
   file whose whole purpose is to survive a moving checkout starts moving with it.
2. **the pool is bounded by count** — `KEEP_MAX`, `IN_USE_S` and `prune`'s new clause. ~150 landings
   a day stop becoming ~150 worktrees.
3. **the doctor says both** — `scheduler.launcher_stale`, two keys on `clock_code`, one suffix and
   one clause on the row.

The order is not a convenience, and PD16 is why: `prune` runs inside the **installed copy** of the
launcher, never inside the package. A landed change to `prune` therefore reaches the clock only
after something rewrites `<code>/launch.py` — which is exactly what Task 1 builds. Land 2 before 1
and the bound sits on the trunk, green, and bounds nothing that is running. Task 3 waits on 2
because its row reports the count whose meaning Task 2 fixes, and because all three Tasks write
`tests/test_snapshot.py`, so the queue serialises them whatever the `after:` lines say.

**Read PD2, PD3, PD7, PD8 and PD17 before writing a line.** Those are the five places where the
spec, followed literally, names a command that does not exist, a doctor status that cannot be
printed, a test that cannot pass, a count that will not come out at the stated number, and a gate
line that exits `126`. Every one of them is expected, measured here, and has its correction named.

PD16 also carries the one thing a human must do, and it is stated once more at the end of this
plan: after Task 1 lands, the launcher already on disk still has no `refresh_launcher` in it, so the
self-heal cannot start itself.

### Task 1: the launcher refreshes itself from the snapshot it just made
stories: S-39350
writes: asf/snapshot.py, tests/test_snapshot.py
after: none

The spec's `I1`, `I2`, `I6` and `## The design` §1 in full — `refresh_launcher(snapshot_dir,
launcher)`, the call in `main()` between `ensure` and `execve`, and the basename guard. This is the
half of the card that unblocks the other two: until the installed `launch.py` moves with the
package, a fix to the launcher ships and is still not what the clock runs, for ever (PD16).

`scheduler.write_launcher` (P4) is not touched and stays the install-time writer: the first copy has
to come from somewhere, and a code dir with no `launch.py` has no tick to self-heal from.

Read **PD4** (the fixture's checkout has no `asf/` package — which is why the nine existing tests
need no edit, and why this Task's own tests must build one), **PD5** (where the marker line goes),
**PD6** (the guard test runs against a temp copy of the package, never the worktree's file) and
**PD7** (the read-only clause of §3.2 cannot hold as written; the two reachable OSError paths that
replace it) before starting.

**Files**

- `asf/snapshot.py` — `refresh_launcher(snapshot_dir, launcher)` below `_write` (`:112-116`) and
  above `prune` (`:127`); the three lines in `main` between the `snapshot:` print (`:209`) and
  `os.chdir(snap)` (`:210`); the module docstring's step list (`:11-18`) gains the refresh as its
  own step
- `tests/test_snapshot.py` — `SnapshotCase.launch` (`:59-64`) gains an optional `launcher=`;
  `LauncherRefreshTests`, a new class built on `SnapshotCase`

**Steps**

1. `refresh_launcher(snapshot_dir, launcher)` in `asf/snapshot.py`, with the spec's body and
   docstring byte for byte (§1): read `<snapshot_dir>/asf/snapshot.py`, read `launcher`, return
   `False` when they are equal, else `_write(launcher, new)` and return `True`; **one** `except
   OSError: return False` around all of it. `_write` (`:112-116`) is reused unchanged — its per-pid
   temp and `os.replace` are what make two clocks refreshing at once safe, and what makes a half
   file unreadable by a launch. Place it after `_write` and before `prune`: it is a writer, it
   depends on `_write`, and it must be above `main`.
2. In `main`, immediately after the `snapshot:` print (`:209`) and **before** `os.chdir(snap)`:
   `me = os.path.abspath(__file__)`, then
   `if os.path.basename(me) == LAUNCHER and refresh_launcher(snap, me):` printing
   `f'snapshot: launcher refreshed from {os.path.basename(snap)[:12]}'` with `flush=True`, byte for
   byte as §1 writes it. The guard is on the basename and not on a flag (I6): under
   `python -m asf.snapshot`, `__file__`'s basename is `snapshot.py`, never `LAUNCHER`
   (`= 'launch.py'`, `:42`), so the refresh is skipped and a developer's working file is never
   overwritten with another sha's bytes. Take the name from `LAUNCHER`, never a literal.
3. No `execve` of the refreshed copy, in this tick or any other (C3, O5). The refresh is for the
   **next** launch; this process goes on running the code it was started with. One clock period of
   lag is the whole cost, and a launcher that re-execs a launcher that refreshes back is a loop.
4. The refresh sits **outside** `ensure`'s `fcntl.flock` (`:162-163`) and is called after `ensure`

### Task 2: the snapshot pool is bounded by count, not only by age
stories: S-39351
writes: asf/snapshot.py, tests/test_snapshot.py
