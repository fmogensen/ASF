# Plan F-0061 — eight Tasks: the contract, the wiring, the seven rules, the measure, and the session that fires them

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0061.md` (approved). Branch:
`plan/F-0061`.

Eight Tasks, in one chain. The spec puts all thirteen of its acceptance classes in a single new
module, `tests/test_rule_hooks.py`, so every Task's footprint intersects every other Task's on that
one file and no two of them can ever run together. The chain is therefore declared on `after:`
lines rather than left for the queue to discover (PD1), and the Tasks are cut as large as their
subject allows so the chain is eight deep and not twelve.

**The wave order is one strict chain: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8.** Task 1 is the contract
every rule is written against (§2.4) and the core directory's README (§2.1); Task 2 is the two
wiring changes that make an installed hook actually run in a worker session plus the doctor row
that makes an unenforced one visible (§2.2, §2.3, §2.12's first half); Tasks 3–6 are the seven
rules themselves, each Task shipping a card, a shim and a `decide` together so no state of `main`
ever carries a live hook whose module is missing (PD2); Task 7 is `asf rules hooks` (§2.12's
second half); Task 8 is the whole-directory assertion and the end-to-end fixture session (§3's T1
and T11), which can only be written once every card exists.

§3's preamble binds every Task — stdlib only, hermetic, no network, no `gh`, no real account
settings file touched, every test pointing `ASF_HOME`, `ASF_CORE_RULES_DIR` and the accounts'
`config_dir` at a tmpdir — and so does §3's T13, the tree-wide guard that has no Story of its own.
Both are copied into every Task's **Acceptance** beside the Task's own fence, and every **Gate**
runs T13. The suite fence `python3 tools/run_tests.py` is copied into every Acceptance as §3
writes it and is run by this product's external CI on the pull request, never on the session's
host (the standing rule; `approvals.full_suite_command`, `asf/approvals.py:374`).

Each Task's own **Acceptance** is the §3 fence its Story names, copied byte for byte.

## Decisions

| # | Question | Decided |
|---|---|---|
| PD1 | How the work is cut | Eight Tasks in one chain, cut by what each piece is rather than by Story, because the footprints leave no choice. Every one of §3's thirteen fences names a class in `tests/test_rule_hooks.py`; the fences are binding byte for byte, so the test module cannot be split per rule to open the footprints up. With one file shared by all eight, the scheduler would serialise them whatever this plan said, and twelve Tasks (one per Story) would be twelve serial handoffs for the same work. So: the contract, the wiring, four rule Tasks, the measure, the proof. Four Tasks carry two Stories each. |
| PD2 | Why a rule's card, shim and module land in one Task | A card in `rules/` with a `hook:` line is what makes the hook *live*: `declared_hooks` returns it, `hooks install` writes `asf hook rNNNN` into every account's settings, and the runtime runs it on the next tool call. A commit that lands `R-0003.md` and `r0003.sh` without `asf/rules/hooks/r0003.py` leaves a shim whose `python3 -m` exits 1 on every `Bash` call of every session — a `PreToolUse` non-blocking error, printed to every transcript, for as long as the next Task takes. So no Task lands a card without the module its shim execs, and Task 1 lands `rules/README.md` alone (prose, no `hook:` line, nothing declared). |

| PD5 | **Seven rules are hooked, not six, and every count in the shipped output says seven** | The spec says six in five places (§1.1's "six of them hooked", §2.1's tree, §2.2's sample summary line, T1's "seven `R-000N.md` and six `r000N.sh`", T11's and §2.12's "6 declared, 6 installed"). All seven rows of §1.1's table carry an event, all seven rows of §2.12's table carry an event and `3/3` installed, §2.1's own parenthetical corrects itself mid-sentence ("six: R-0007's Stop hook has one too"), and T1 requires that *every hooked card* have a script. `declared_hooks` emits one `(event, name)` pair per `hook:` event of every card (`asf/hooks.py:219-237`), so seven carded events is seven pairs, seven shims and seven modules. | PD6 | **The `PreToolUse` matcher is `*`, so each rule module filters on `tool_name` itself** | The "tool" column of §1.1's table is not something the settings file can express. `declared_hooks` returns `(event, name)` and nothing else, and `merge` writes `{'matcher': '*', 'hooks': [...]}` for every non-`Stop` event (`asf/hooks.py:266-269`) — there is no per-tool matcher anywhere in the installer, and adding one would change the shape `approvals` is already installed in. So the tool restriction is the first two lines of each `decide`: R-0001, R-0002, R-0003 and R-0005 return None unless `tool_name == 'Bash'`; R-0004 and R-0006 unless it is one of `Write`, `Edit`, `MultiEdit`. `hookcall.run` does not do it for them — three of the six want a different set, and a `tools=` argument every caller passes differently is not a shared contract. Task 8's fixture session is what proves it: it drives each installed command with a call JSON for the *wrong* tool and requires rc 0 and empty stderr. |
| PD7 | **Five `PreToolUse` hooks fire on every tool call, beside `approvals` — the cost, stated, not fixed here** | Matcher `*` (PD6) means a session's every `Bash`, `Write`, `Edit` and `MultiEdit` call spawns six `asf hook` processes, each a `bash` shim over a python start. The spec does not mention it and this plan does not widen scope to fix it: consolidating the rule hooks behind one dispatcher entry is a different card, and doing it here would mean `declared_hooks`, `merge` and `_is_ours` all change shape in the Feature that first gives them something to install. What this plan does do is make the wasted work cheap — each module's tool-name guard (PD6) is its first statement, so four of the five exit after one `json.loads`, and no module imports `env`, `approvals` or anything that reads a config file before that guard has passed. Recorded so the latency is read as a known consequence of §2.2's design and not as a defect one of these Tasks introduced. |
| PD8 | **The shim's `python3` cannot be assumed to import `asf`, and Task 2 closes that inside §2.3's own function** | D4 makes each hook a four-line `bash` shim over `python3 -m asf.rules.hooks.rNNNN`. That resolves today only by accident: `asf` on PATH is `tools/asf`, which sets `PYTHONPATH` to the checkout root before `exec python3 -m asf.cli`, and `cmd_hook`'s `subprocess.run(['bash', script])` inherits it (`asf/hooks.py:394`). Under the other install mode — `pipx install asf-factory`, the one `runnable_asf`'s own refusal text names (`asf/hooks.py:165`) — `python3` on PATH is the system interpreter, `import asf` fails, the shim exits 1, and a `PreToolUse` rc of 1 is a non-blocking error: **the rule is silently unenforced**. That is precisely the failure §2.3 exists to close, one layer down, so it is closed in the same place: `cmd_hook` runs the resolved script with `ASF_PYTHON=sys.executable` and `hermetic.package_parent()` prepended to `PYTHONPATH`, and every shim is `exec "${ASF_PYTHON:-python3}" -m asf.rules.hooks.rNNNN`. Two lines in `asf/hooks.py`, no new file, no new footprint. |

No Task edits `pyproject.toml`. |

Stated so a coder does not go looking for the reader. |

### Task 1: the hook contract — allow, refuse, fail closed, one ledger row, and the core directory's README
stories: S-30553
writes: asf/rules/hookcall.py, asf/rules/hooks/__init__.py, rules/README.md, tests/test_rule_hooks.py
after: none

§2.4, and §2.1's README. One new module that every rule below is written against, one empty
package for them to live in, and the prose that states the reserved band. Nothing in this Task
declares a hook: `rules/README.md` carries no frontmatter and no `hook:` line, so `declared_hooks`
still returns `[]` after it lands and `hooks install` writes exactly what it writes today (PD2).

**Files**

- `asf/rules/hookcall.py` — **new**. The contract:
  - `CALL` and `HOOK_ERROR_LINE` as §2.4 gives them, `HOOK_ERROR_LINE` in the shape
    `asf.approvals.HOOK_ERROR_LINE` already uses (`asf/approvals.py:813`) but naming the rule:
    `'rule hook {rule} broke ({why}) — the call is refused; this is the hook, not you'`.
  - `run(rule, decide, stdin_text=None, environ=None, out=sys.stderr)` → the rc the runtime
    reads. Four rules, in this order: `ASF_JOB` unset → `0` before anything else, before any
    import that reads a config file (D12, the discriminator `approvals.run_hook` already uses at
    `asf/approvals.py:854`); `decide` → `None` → `0`, silent, nothing appended; `decide` → lines
    → `2`, the lines on `out`, one `refused-rule` row appended; any exception → `2` with
    `HOOK_ERROR_LINE` and one `rule-hook-error` row.
  - A `Ctx` (a small dataclass or a namedtuple, not a dict) carrying what every rule needs and
    none re-derives: `product` (`env.load_product(environ['ASF_PRODUCT'])`), `job` (`ASF_JOB`),
    `item` (`ASF_ITEM`), `cwd` (the call's `cwd`, else `os.getcwd()`), `in_worktree` (the
    `.git`-is-a-file test — call `asf.record.ids._in_worktree`, do not copy it), `in_backlog` and
    `in_repo` (the cwd inside `product.backlog_dir` / `product.repo_dir`, by
    `os.path.commonpath` on real paths).
  - The refusal row: `{'event': 'refused-rule', 'rule': rule, 'item': …, 'job': …, 'tool': …,
    'detail': <the command or path, first 120 chars, scrubbed>, 'ts': …}`, appended with
    `approvals.append` to `approvals.ledger_path(product)`. **No `hold` key** — a refusal never
    parks an item, the shape `refused-full-suite` already established (`asf/approvals.py:894`).
  - The error row: `{'event': 'rule-hook-error', 'rule': rule, 'job': …, 'why': …, 'ts': …}`,
    plus the traceback through `approvals._log_traceback` — **not** `record_hook_error`, which
    writes `hook-error` and would make the tick announce the approvals guard as broken (PD12).
    Both writes are wrapped so a failing ledger never turns one error into two, the way
    `record_hook_error`'s docstring states.
  - A `refusal(subject, title, rule, *lines)` helper that renders §2.4's four-part shape — what
    was refused, why, `instead:`, and the literal line
    `This is not a question for a person: do not print NEEDS OPERATOR for it.` — so seven modules
    do not each format it.
- `asf/rules/hooks/__init__.py` — **new**, empty but for a one-line docstring naming the package
  as the hook half of the core rules.
- `rules/README.md` — **new**, and the `rules/` directory with it. States: the reserved core band
  `R-0001`–`R-0099` and why (D11 — a product's record mints `R-` ids from its own counter, and
  without a band the first product to mint `R-0001` shadows the core card of that id in every
  table that joins them); the card shape, with `id`, `type`, `title`, `check` and `hook`; that the
  `hook:` half binds from this directory on `asf hooks install` while the `check:` half binds only
  through a product's own record card of the same basename (§1.2, PD11); and that a product
  adopting a core rule's check half writes its own one-line `R-` card pointing at the same
  basename. Generic: no path, no account, no product name.
- `tests/test_rule_hooks.py` — **new**. `ContractTests` only; the other twelve classes are the
  Tasks below. A tmpdir `ASF_HOME`, a fixture product, and a `decide` stub per case.

**Steps**

1. `rules/README.md` and the directory, and `asf/rules/hooks/__init__.py`.
2. `asf/rules/hookcall.py`: `Ctx` and its builder first, then `run`, then `refusal`. `run`'s
   `ASF_JOB` check is the first statement of the function body and no module-level import in the
   file reads a config or a product (PD7).
3. `ContractTests`: the four cases of T4 — `ASF_JOB` unset returns 0 and writes nothing whatever
   `decide` would have said; `None` returns 0 and writes nothing; lines return 2, print them to
   `out`, and append exactly one `refused-rule` row with no `hold` key; a raising `decide` returns
