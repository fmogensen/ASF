# Plan F-0127 — the worktree records its own setup, and the spawner asks it instead of the clock

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0127.md` (approved). Branch: `plan/F-0127`.

Two Tasks, cut the way the spec's `## The design` is cut — by the file that gains the surface. Task 1
is all of `asf/workers/spawn.py`: the marker (`SETUP_MARKER`, `setup_marker_path`, `setup_done`,
`_record_setup`), the two lines `run_worktree_setup` gains around its unchanged middle, the two lines
of guessing `spawn` loses, and the three test classes the spec's fences name. Task 2 is
`docs/guide/product-config.md` — the `worktree_setup` row in the `## Conventions` table, the
subsection under it, and the first test in this suite that reads that file.

Task 1 is one function's check, one function's write and one call site, all inside one module; the
spec's three new test classes cannot be split off it, because two of them fail until `spawn` stops
guessing and the third tests the functions the same diff introduces. Splitting it would buy no
parallelism — both halves write `asf/workers/spawn.py` and `tests/test_worker_isolation.py` — and
cost a review round (PD1).

Wave order: **1 → 2**.

The two footprints are disjoint, so the queue never holds Task 2 on account of `writes:`. It waits on
Task 1 anyway, by `after:`, because its prose asserts behaviour Task 1 lands: the trunk would
otherwise carry an operator guide saying a worktree records its setup while the code still reads
`os.path.exists` (PD5).

§Acceptance tests' last fence — the whole suite and both tree fences, as the pull request's CI runs
them — binds every Task, so every Gate below runs `python3 tools/run_tests.py` beside its own.

### Task 1: the worktree's own record of its setup, and the spawner that reads it instead of a path
stories: S-33900, S-33901
writes: asf/workers/spawn.py, tests/test_worker_isolation.py
after: none

The spec's first four **In** bullets and both of its `asf/workers/spawn.py` design blocks: one import,
one constant, three functions, two lines added to `run_worktree_setup`, two lines deleted from `spawn`,
and the module docstring's step 1. `run_worktree_setup`'s environment, masking, log, timeout, failure
text and `clear` keep every byte they have; `make_worktree`, `_place_worktree`, `_reclaim`, the reaper
and the `spare` rule are not opened.

**Files**

- `asf/workers/spawn.py` — `import json`; `SETUP_MARKER`; `setup_marker_path`; `setup_done`;
  `_record_setup`; `run_worktree_setup` (the marker check at the top, the marker write at the end,
  its docstring); `spawn` (`own_path` and `fresh` deleted, the `elif` become an `else`); the module
  docstring's step 1
- `tests/test_worker_isolation.py` — `WorktreeSetupMarker` (new, `unittest.TestCase`, its own git
  fixture), `WorktreeSetupAfterReclaim` and `WorktreeSetupRunsOnce` (new, `IsolatedSession`)

**Steps**

1. `import json` into the module's list (`asf/workers/spawn.py:29-34`), in alphabetical place. No
   `datetime`: `pool_mod.now_iso()` is already this module's way to stamp a UTC time, and `spawn`
   stamps `started` with it (`:765`).
2. `SETUP_MARKER = 'asf-setup'` beside `WORKTREE_SETUP_TIMEOUT_S` (`:668`), with the spec's comment
   block byte for byte — that the marker is in the **git admin dir** and never in the tree, that an
   untracked file in the tree would read as uncommitted work for ever
   (`asf.workers.worktrees.safety`), and that `git worktree remove` / `prune` delete the admin dir
   with the tree, which is what makes a recreated path count as fresh (D1/D2). The literal is the
   factory's own state name inside git's own directory, not a product convention (PD8).
3. `setup_marker_path(worktree)` → `os.path.join(_admin_dir(worktree), SETUP_MARKER)`, or `''` when
   `_admin_dir` is `''`. Through `_admin_dir` (`:181-192`) and never by joining the tree's basename
   onto `<repo>/.git/worktrees/`: git suffixes an admin dir whose name is taken, and `_admin_dir`
   reads the tree's own `.git` file, so a suffixed one resolves to its own (P9). This is the reader
   `_reclaim` already uses for `rebase-merge` and `MERGE_HEAD` (`:311-317`).
4. `setup_done(worktree, command)` — the spec's function, byte for byte, with its docstring: the
   marker parses as JSON and its `command` equals `command` exactly (D3 — the text the operator
   wrote, not a hash and not a flag). `except (OSError, ValueError, AttributeError): return False`
   covers an absent file, a truncated or non-JSON one, and a JSON scalar that has no `.get`. No
   admin dir is **not** set up (D8): the case is unreachable, because `make_worktree` returns only
   linked worktrees git made, and on an unreachable path running an idempotent command again beats
   handing a session a tree that may hold no dependencies.
5. `_record_setup(worktree, command, took_s)` — the spec's function, byte for byte: one JSON object,
   `{'command': command, 'at': pool_mod.now_iso(), 'took_s': took_s}`, `sort_keys=True`, returning
   the path or `''`. `except OSError: return ''` and nothing raised: a marker that cannot be written
   is not a failed launch (D7) — the setup ran, the tree is good, and the only cost of a lost marker
   is one repeat of an idempotent command on the next launch in that tree.
6. `run_worktree_setup` gains exactly two lines. After `if not command: return None`:
   `if setup_done(worktree, command): return None` with the spec's comment — this tree already ran
   exactly this command (D6). The decision lives inside the function, not at the call site, because
   the function already owns "declares no command → None, nothing ran", and keeping the two together
   keeps `setup_s is None` meaning exactly *no setup ran on this launch* on the ledger (P11). At the
   success tail, `return round(time.monotonic() - started, 1)` becomes `took = …`,
   `_record_setup(worktree, command, took)`, `return took` — so the marker is written **after** the
   command succeeded and never on a failure or a timeout. The middle is untouched: `seed_home`, the
   `build_env` `Job`, `auth_env_values`, the `subprocess.run` with `shell=True` / `cwd=worktree` /
   `stdin=DEVNULL`, the masked log, the `why` branches, the `repo_lock` + `_discard`, and the
   `SpawnError` with its `clear` (P3, P4).
7. Its docstring gains the spec's clause and keeps the rest: "Returns the seconds it took, or None
   when the product declares no command **or this worktree already carries the marker for it**
   (:func:`setup_done`) — a reused tree keeps the install it already has." The existing first
   sentence reads "in the fresh ``worktree``"; drop the word *fresh* there, since the function is
   now what decides what fresh means.
8. In `spawn`, delete `own_path = os.path.join(worktrees_dir(product), row.job)` and
   `fresh = not os.path.exists(own_path)` (`:743-744`). `grep -n own_path asf/workers/spawn.py` must
   come back empty afterwards — they have no other reader (P6). The gate
   `elif fresh and worktree == own_path:` becomes `else:` with the spec's comment: whether this
   worktree is fresh is the worktree's own record, not whether its path existed a moment ago. The
   `if cloud:` arm above is untouched — nothing is set up or built on this host for a session that
   runs off it (P12, D9) — and so are the lines below it: `reserve_id_range`, `write_brief` and the
   session line still come after the setup, so a refused launch reserves no ids, writes no brief and
   appends nothing (P5). `setup_s` is still written onto the record only when it is not None (`:793-794`).
9. The module docstring's step 1 (`:12-14`) loses the emphasis on *fresh* and says what now decides,
   in the spec's words: "… only a live run's worktree refuses (:func:`make_worktree`); the product's
   ``conventions.worktree_setup`` then runs in it unless the worktree already records that exact
   command (:func:`run_worktree_setup`, :func:`setup_done`) — a failure refuses the launch and
   removes the worktree;".
10. `WorktreeSetupMarker(unittest.TestCase)` — its own fixture and no inheritance (PD6): a tmpdir,
    `git init` a repo with one commit, then `git worktree add` a linked tree. Cases: `setup_marker_path`
    resolves under the admin dir the tree's own `.git` file names, and for a **second** worktree whose
    name git had to suffix it resolves to that tree's own dir and not the first's; `setup_done` is
    False with no marker; `_record_setup` then `setup_done` is True for that command, and the file on
    disk parses as one object with `command`, `at` and `took_s` and nothing else; `setup_done` is
    False for a different command; False for a truncated file, for `not json`, and for a bare JSON
    string or list; False for a path that is not a worktree at all (`_admin_dir` → `''`), and
    `_record_setup` there returns `''` and raises nothing; `_record_setup` returns `''` when the
    admin dir is unwritable and still raises nothing (D7). One case is the reason for D2: after
    `_record_setup`, `git status --porcelain` in the tree is `''` — so `worktrees.safety` still
    calls it safe and the reaper can still reap it (P8) — and the marker's path is not under the
    worktree.
11. `WorktreeSetupRunsOnce(IsolatedSession)` — three launches on one worktree, each a real process
    through `IsolatedSession.spawn`, with a command that appends a line to a file **outside** the
    tree (`self.tmp`, not the worktree — PD7), so "how many times did it run" is countable and the
    tree stays clean. First launch: the file has one line, `rec['setup_s']` is a float, and
    `setup_marker_path(rec['worktree'])` holds a marker naming the command. Between launches the run
    is ended the way a correction's relaunch finds it, so `make_worktree` reuses the same tree and
    `rec['worktree']` is the same path. Second launch: the counter file still has one line, `setup_s`
    is **not** in the record (P11), and `<job>.setup.log`'s mtime has not moved — nothing ran,
    nothing was logged (PD3: the marker is what skipped it, asserted by its bytes, not by `fresh`).
    Third launch, with a product whose `worktree_setup` is a different command: the counter file
    gains a line, `setup_s` is a float again, and the marker now names the new command (the spec's
    fourth **In** bullet — a changed command re-runs).
12. `WorktreeSetupAfterReclaim(IsolatedSession)` — the card's own test, and the one that fails today.
    Launch once with a setup command that writes a file into the worktree. Then make that tree a
    stale orphan by the shape PD4 sets out: truncate `pool_mod.sessions_path(product)` so no run is
    recorded for it, and `mock.patch.object(spawn_mod, 'ORPHAN_GRACE_S', 0)` around the second
    launch. Assert the second launch is the same path, that the file the first setup wrote is **gone**
    (the tree really was discarded and recreated, not reused), that the setup ran again — the file is
    back — that the marker under the new admin dir names the command, and that the record carries
    `setup_s`. Without the change the second launch hands over a checkout with neither the file nor a
    marker and records no `setup_s`, and the assertions fail. One case asserts the same through the
    other creating path: a worktree whose branch is on origin (`_place_worktree:472-480`) gets its
    setup too, because its admin dir carries no marker.
13. The three existing `WorktreeSetup` cases and `IsolatedSession`'s five are edited nowhere: a fresh
    worktree has no marker, so the command still runs under the worker environment with the account's
    HOME and no operator secret; a failing setup still refuses the launch, removes the worktree and
    leaves `load_sessions(product) == {}`; a product with no command still runs nothing and records
    no `setup_s`. `tests/test_cloud.py:360` is untouched — the cloud arm is not entered by this diff.

**Files**

**Steps**

1. The table row, the spec's, byte for byte, placed after the `amendable_paths` row and before
   `landing` so the two derived-or-declared rows stay together:
   `| \`worktree_setup\` | none | a shell command run in every fresh worker worktree before its
   session starts — the dependency install or codegen the product's gate needs. Must be idempotent —
   see below |`. The default column reads `none`, which is what `DEFAULT_WORKTREE_SETUP = None`
   means to a reader of a yaml file (`asf/conventions.py:195-197`).
2. The subsection, the spec's six bullets and its two opening paragraphs byte for byte, headed
   `### \`worktree_setup\` — the command a fresh worktree needs` — a `###`, not the spec's `####`,
   for the reason PD11 gives. Nothing in the prose changes: git gives a worker session a checkout
   and nothing else; the command runs in the **worktree** under the environment the session itself
   will have (the worker allow-list, the account's own HOME, the product's `auth_env`, never the
   operator's environment and never a value the tick happens to carry, with the cross-reference to
   operating.md's Safety); its output goes to `~/.ASF/state/<product>/briefs/<job>.setup.log` with
   every `auth_env` value masked; it gets **900 seconds**, and a failure or a timeout **refuses the
   launch and removes the worktree** and names the log, with the same failure twice in a row a
   `NEEDS OPERATOR` telling the operator which key to fix; it runs **once per worktree**, a reused
   worktree keeps the install it already has, and a recreated one or one whose recorded command is
