# B-0123 — plan: a regular tick catches up a missed daily once, not tomorrow

Item: B-0123 — a failed daily run is never retried until the next day (S2). Epic: E-0001 — ASF
0.1 — a working factory. Branch: `fix/B-0123`. No spec exists; the Acceptance below is the
record.

## Cause

The daily clock (`clocks: {daily: {steps: [daily], at: "06:00"}}`) fires once a day. When that
run misses its own window — the host offline, a step failing before it stamps
(`asf/tick/steps.py:stamp_path`) — nothing else even looks at `daily`: every other clock's own
tick (`record`, `dispatch`) never carries `daily` in its own `--steps`, so the stamp sits stale
until tomorrow's 06:00 fires again. `groom --apply`, the stale sweep, `file-bugs` and the rollup
all ride inside that one step (`asf/tick/step_daily.py`), so a missed window loses a whole day of
all four, not just one.

## Task 1 — a regular tick runs `daily` itself once its own time has passed

writes: `asf/tick/steps.py` `asf/tick/tick.py` `tests/test_tick.py`

- Step 1: `asf/tick/steps.py` — `_daily_clock_time(product)` reads `clocks:` for the entry whose
  `steps:` carries `daily` and returns its `at: "HH:MM"` as `(hour, minute)`, or `None` when no
  clock is shaped that way.
- Step 2: `daily_catch_up_due(product, now=None)` — true when that time has passed today
  (`now >= at`) and `daily_due(product, today=...)` (the existing staleness check) still says the
  stamp is stale.
- Step 3: `daily_catch_up_message(product)` — the tick log's one line naming the catch-up.
- Step 4: `asf/tick/tick.py:_run_steps` — after the version-check and upgrade-pending gates, when
  this tick's own `rows` does not already carry `daily` (it isn't the daily clock's own tick),
  resolve `daily`'s owner/command and, when the owner isn't `off` and `daily_catch_up_due` is
  true, print the catch-up message and append `(daily_step, daily_owner, daily_command)` to
  `rows` — the existing per-step loop runs it exactly like any other step, including stamping on
  success.
- Step 5: tests, in `tests/test_tick.py` (`DailyCatchUpTests`):
  - `test_a_failed_daily_catches_up_once_on_the_next_regular_tick` — the 06:00 (here: `00:00`, a
    time always already past) clock's own tick fails; the next dispatch tick names the catch-up,
    runs `daily`, and stamps today.
  - `test_a_successful_daily_is_not_run_again_by_a_later_regular_tick` — a successful 06:00 tick;
    the next dispatch tick never mentions `daily` again, and the mocked runner is called exactly
    once.

## Task 2 — the catch-up line names the failed run's own reason (round 1/2 C)

writes: `asf/tick/steps.py` `asf/tick/tick.py` `tests/test_tick.py`

- Step 1: `asf/tick/steps.py` — `daily.failure`, a state file beside `daily.stamp`
  (`failure_path`/`write_daily_failure`/`read_daily_failure`/`clear_daily_failure`); a successful
  `write_daily_stamp` clears it, since a fresh success makes the last reason stale.
- Step 2: `asf/tick/tick.py` — the two places a `daily` step's failure is already detected write
  the reason there: `run_asf_step`'s exception handler (the same `detail` it already logs, and
  already threads into `ctx.stale_reason` for `record`) and the declared-command branch's
  `step_rc` (as `"exited <rc>"`).
- Step 3: `daily_catch_up_message` reads the file back and names the reason
  (`"daily: catching up — 06:00 run failed: <reason>"`), falling back to the original wording
  when there is none — the daily clock never ran at all today, so there is nothing to report as
  failed, only that it hasn't succeeded.
- Step 4: `test_a_failed_daily_catches_up_once_on_the_next_regular_tick` asserts the reason
  (`"…run failed: daily parts failed: rollup"`, the exact message `step_daily.run` raises) instead
  of the generic wording.

## Acceptance

- [x] A failed 06:00 run, with a later successful tick, runs `daily` once
      (`test_a_failed_daily_catches_up_once_on_the_next_regular_tick`).
- [x] A successful 06:00 run is not run again by a later tick
      (`test_a_successful_daily_is_not_run_again_by_a_later_regular_tick`).
- [x] The tick log names the catch-up with the failed run's own reason, not a generic line.
- [x] `python3 -m unittest tests.test_tick` is green (59 tests).

## Accepted costs

- `_daily_clock_time` falls through to `None` (no catch-up, ever) for a product whose daily clock
  uses a different config shape than `steps: [daily]` + `at: "HH:MM"` — not a bug against today's
  config shapes, but worth knowing if a product's clocks are ever reshaped.
- A declared-command `daily` step's failure reason is only ever `"exited <rc>"` (the exit code) —
  it cannot carry more detail than the subprocess's own exit status already does, unlike the
  `asf`-owned path which threads the exception's own message.
