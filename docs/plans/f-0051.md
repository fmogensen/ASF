# Plan F-0051 — after the deploy, something signs in and looks

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0051.md` (approved). Branch:
`plan/F-0051`.

Nine Tasks, cut by the module that owns the new surface, which is how the spec's own §2 is
sectioned. Task 1 is the `probe:` block and the package (§2.1), Task 2 the one customer-visible
classifier and what a deploy owes (§2.2), Task 3 the journey list, the sign-in contract and the
result schema (§2.3, §2.4), Task 4 the stream in the record (§2.8, first half), Task 5 the fence —
the lint, the origin judgement, the consent stamp in the ledger, and the prober's rewritten reason
(§2.6, §2.11), Task 6 the host, the dispatch, the read-back and the pass in the tick (§2.5, §2.7),
Task 7 the evidence on the item's own card and the eight-clause close rule (§2.8 second half,
§2.9), Task 8 the severity-one Bug (§2.10), Task 9 `asf probe`, the two doctor rows, the guide and
the two whole-tree fences (§2.12).

The Feature is a chain at its head and a fan at its waist. Tasks 1 → 2 → 3 → 4 are strictly
serial: `scope.owed` needs `Probe`, `journey.journeys` needs both `Probe` and `scope.Owed`, and a
stream line carries a `Result`'s fields. Once the stream's line shape exists, three Tasks read it
from three different directions and write three disjoint sets — Task 5 (the fence and the ledger),
Task 7 (ingest and closing) and Task 8 (the Bug filer) — and each builds its own `metrics/probes`
fixture by hand, so none waits on the pass that will write those lines in production. Task 6 needs
Task 5's `fence.lint`, `fence.judge` and `ledger`, and Task 9 needs everything.

Wave order: **1 → 2 → 3 → 4 → 5 ‖ 7 ‖ 8 → 6 → 9**.

§3's rule that the whole suite stays green binds every Task, so every Gate below runs
`python3 tools/run_tests.py` beside its own fence, and every Gate runs both whole-tree fences —
this Feature adds a package under `asf/`, which is what P10 puts inside them.

**Steps**

### Task 3: the journeys ASF sends, the sign-in it always runs first, and the schema it refuses to read loosely
stories: S-33102
writes: asf/probe/journey.py, tests/test_probe_journey.py
after: Task 1, Task 2

§2.3 and §2.4: the list ASF hands the workflow, the five-step sign-in journey that is always first
and always ASF's, and the reader that turns a broken report into a reported absence rather than a
silent pass. This Task ships no io and no host — it is pure over a `Probe`, a list of `Owed` and a
string.

**Files**

- `asf/probe/journey.py` — `Journey`, `Result`, `SIGN_IN`, `journeys`, `try_it_path`,
  `parse_results`
- `tests/test_probe_journey.py` — T3

**Steps**

1. `Journey`: frozen, `name`, `kind` (`sign-in` | `standing` | `try-it`), `path`, `item`, `pr`.
   `Result`: frozen, `name`, `kind`, `verdict`, `step`, `seconds`, `screenshot`, `origins`,
   `item`, `pr`, `detail`.
2. `journeys(probe, owed)`, in order: the sign-in journey, always and first (D6); one per name in
   `probe.journeys`, in configuration order; one per `Owed` whose `customer_visible` is true and
   whose try-it line yields a path, named `<item> #<pr>`.
3. `try_it_path(line)`: the first `https://<origin>/…` on the line whose origin is in
   `probe.origins`, else the first bare `/path` token, else `''`. An off-origin URL yields `''`

4. `parse_results(text)`, total over garbage: invalid JSON, a `schema` that is not `1`, a missing

6. The five sign-in step names of §2.4 are module constants — `sign-in: request code`,
   `sign-in: code mail`, `sign-in: submit code`, `signed in` — so the Bug of §2.10 and the guide

### Task 4: the probe stream in the record — one line per journey, written once
stories: S-33105
writes: asf/probe/stream.py, asf/init.py, tests/test_probe_stream.py
after: Task 1, Task 3

§2.8's first half: `metrics/probes/<day>.jsonl` — the writer that is idempotent per `(sha, journey)`
and the two readers ingest will call. This is the line shape Tasks 5, 7 and 8 all read, which is
why it lands before the fan.

**Files**

- `asf/probe/stream.py` — `PROBE_KIND`, `Verdict`, `append(root, product, target, sha, run,
  artifact, results, owed, now)`, `verdicts(root, sha)`, `standing(root, sha)`
- `asf/init.py` — `'metrics/probes'` in `STREAM_FOLDERS` (l. 28)
- `tests/test_probe_stream.py` — T5's stream half

**Steps**

1. `append` writes §2.8's line, one per `Result`, with `customer_facing` taken from the matching
   `Owed` at probe time — written down when it was computed, never recomputed from a tree that
   has moved on (§2.9) — and `origins_ok` from the judged result.
2. The append is idempotent per `(sha, journey)`: the day file is read first and an existing line
   for the pair writes nothing, the rule `ingest.write_on_prod_event` (`asf/record/ingest.py:41`)
   already follows, including its tolerance of an unparseable line in an unvalidated stream.
3. The writer makes its own directory (PD14): `os.makedirs(os.path.dirname(path), exist_ok=True)`
   before the append, because `STREAM_FOLDERS` reaches only records that `asf init` creates from
   here on.
4. `verdicts(root, sha)` returns `{item: Verdict(...)}`: an item's verdict is its own try-it
   journeys' — `fail` if any failed, `unrunnable` if any was unrunnable and none failed, else
   `pass`. `standing(root, sha)` returns the sha's standing journeys folded the same way.
5. An item that owed no journey of its own has no entry of its own; the caller (Task 7) falls
   back to `standing`. An item at an unprobed sha is absent from both, and nothing changes for it.
6. `tests/test_probe_stream.py`: writing the same run's results twice appends each `(sha, journey)`
   line exactly once; the three folds over two try-it journeys of one item; `standing` over a sha;
   an unprobed sha yielding nothing; and the directory created on a record that has none.

**Gate**
