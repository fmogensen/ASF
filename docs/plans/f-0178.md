# Plan F-0178 — the factory holds a product's Actions artifact storage under its quota: one bounded list read, a daily prune that never touches what anyone is reading, an early oldest-first prune above the threshold, and two rows that say the reading out loud

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0178.md` (approved). Branch:
`plan/F-0178`.

Three Tasks, one per Story, cut exactly where the spec's C17 cuts them:

1. **the reader, the age rule and the configuration** — `asf/ci_artifacts.py` (the bounded list
   read, the used total, the protection set, the age rule, the capped delete, the state file, the
   daily entry point, `doctor_line`), the `ci.artifacts` block with its shape check and its
   `CI_FIELDS` entry, the `artifacts` part in `step_daily.parts`, `asf ci artifacts [--prune]`, and
   the three documents that describe them.
2. **the threshold rule** — `monitor`, the hysteresis target, the `artifact_quota` sub-pass in
   `step_health.run`, and the `artifacts X GB / Y GB` clause on the status Runners row, all over
   Task 1's reader.
3. **the doctor** — the `ci artifacts` reading row off Task 1's state file, and one advisory row per
   `upload-artifact` step with no `retention-days` in the product's own checked-out workflows.

They run **in three waves, not two**. Task 2 and Task 3 are both `after: Task 1` — Task 2 is a rule
over Task 1's reader, and Task 3's reading row reads Task 1's state file and its scan lands in Task
1's module — and their `writes:` intersect at `asf/ci_artifacts.py`, so the feeder queues them.
**PD3** is where the spec's C17 claim that the third *"shares nothing with the first two and could
land in any order"* is corrected: it shares the module and the state file, and saying so is cheaper
than discovering it in a conflict.

**Read PD2, PD4, PD5 and PD9 before writing a line.** Each is a place where a literal reading of the
spec's design does not do what the spec's own text says it does: §1's `read` bounds nothing, because
`gh api --paginate` makes every request before the row cap can drop a row, so C8's cap protects the
one case it was written for not at all (PD4); §1's `read` takes the slug off `product.repo_slug`,
which is None for every product that configures only a `repo_dir`, so the whole card is silently off
for them (PD2); §5's clause is appended at one of `runners_cell`'s four returns, so a product with
no self-hosted pool — the ordinary GitHub-hosted product this card is written for — never sees the
reading the card asks for (PD5); and §8's dry-run output cannot happen, because the three-refusals
stop fires first (PD9).

## What this plan leaves where the spec left it

The `billing/shared-storage` endpoint is not read, and neither is the billing endpoint that replaced
it (P1, P2, C1) — the reading is the sum of `size_in_bytes` over the repository's non-expired
artifacts, and nothing here will ever produce an account-wide figure.

`quota_gb` gets no default and is never inferred (C3). A product that configures the block and not
the quota gets the daily prune, the reading, and a row that names the key it is missing — and no
early prune. This plan mints no card to go looking for an API that reports the allowance; P3 says
there is none.

Caches and run logs are untouched, no run is ever deleted, and neither
`artifact-and-log-retention` endpoint is read or written (the spec's **Out**, P6). A prune makes the
retention setting moot for what already exists, and the setting is an operator's to make.

No product's workflow file is edited (C15). The doctor's advisory row reports a step by file and
line and offers no `--fix`, because the product's CI is the product's — and on the product that
filed this card it will report nothing at all (P7), which is the correct answer.

`asf/merge_queue.py`, `asf/ci_pool.py`'s runner rules, the CI start queue and the capacity ceilings
are not touched. `ci_pool.register` gains one sub-parser and nothing else; the Runners row gains one
clause and nothing else.
