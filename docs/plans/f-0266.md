# Plan F-0266 — the refusal ASF made is written down once, read off the record, and carried into the one sentence the operator sees

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0266.md` (approved). Branch:
`plan/F-0266`.

Five Tasks, cut on **who owns the wording** — one module writes and recognises every refusal, and
each of the three places a refusal is produced or read is wired to it on its own files:

1. **the one owner, and the record's own refusals** — `asf/workers/refusals.py` whole (§1), with
   `from_record` over `publish_refused` and a refusal-kind `correction` (§1, C5). S-64354 and
   S-64356 are **one** Task because both are the same new module and the same new test file:
   `from_record` is four lines of that module's surface, and a Task that delivered the module
   without it would publish a `Refusal` shape its own next Task rewrites. Nothing else in the
   tree changes — S-64356's whole claim is that `lifecycle.publish` and `asf/harvest/lane.py`
   keep writing no ledger line, which is a test, not an edit.
2. **the session's own refusal, written down** — the hook shim's three refusal points (§2) and
   `refusals.env_for`/`clear` beside `pushlog`'s at `spawn` and at a heartbeat continuation.
3. **the dead reason carries it, and the cloud leg that earns a log read** — `cloud.classify`'s
   `refusal=` keyword and `cloud.sync`'s two reads (§3), `_run_log_tail` and `actions.Gh.log_tail`
   (§4), plus the one trailing argument on `remote.evidence` that **PD1** shows the card needs.
   S-64357 and S-64358 are one Task because `_run_log_tail` is called from the very block
   S-64357 adds, and because their `writes:` are the same two files either way: split, the queue
   serialises them and the first landing ships a `REPORT_MISSING` arm with nothing behind it.
4. **the dead reason survives the pass and reaches the operator** — `dead_why` in `RUN_FIELDS`,
   `cloudpid.why`, health's one write, `dead_census`'s second axis and the Dead group's `Why`
   column (§5).
5. **the regression replay, test-only** — `tests/test_dead_reason.py`, the 2026-10-07 replay and
   its before-picture. No code change (the spec's own last two acceptance lines of S-64359).

They run **1 → (2 | 3 | 4) → 5**. Task 1 is the wave of its own that every other Task needs: all
four read `refusals`. Tasks 2, 3 and 4 need nothing of each other — the shim's ledger, the dead
reason's clause and the end record's field are three independent readers of the same module — and
only Tasks 2 and 4 meet, on `tests/test_workers.py`, where the queue serialises them in whichever
order it likes (**PD10**). Task 5 is `after: Task 1, Task 2, Task 3, Task 4`: the replay asserts
the sync's line, `cloud-sessions.json`'s `why`, the run's `dead_why`, the doctor's line and the
Dead row in one fixture, so it needs all four landed.

**Read PD1, PD2, PD3 and PD4 before writing a line.** Each is a place where following the spec's
design literally ships something that does not fix the bug the card exists for, or that costs the
factory something worse: §3's one-line `refusal=` leaves a `claude-remote` run's recorded refusal
unreachable because `remote.evidence` calls `classify` itself (PD1); §5's `Why` column reads a
field the Dead group can never carry, because `dead_why` and that group are disjoint by
construction (PD2); §1's `last` attributes one job's current ledger to every historical dead run
that `dead_census` folds, which is the cross-run attribution C7 forbids (PD3); and §2's "captured
instead of passed straight through" buffers a pre-push check that runs for minutes, which reads as
a stalled session and gets this very session relaunched on top of itself (PD4).

The fences of *The fences, and the suite* bind every Task, so every Gate and Acceptance block
below carries them beside its own.

The product's own pre-push check is `bash tools/check_generic.sh && bash tools/check_conventions.sh && python3 tools/run_tests.py --touched origin/main --shards 2` — minutes of it. A `out=$(… 2>&1)` capture prints nothing until it returns, and a session whose output has gone quiet is ended and continued by a new session from its branch (this repo's own standing rule, and `heartbeat.observe`'s judgement). Shipping that would make this card's fix the cause of the failure mode it is about. **Decided: stream and capture, never buffer.** At each of the two capture sites, in POSIX `sh`: `rcf=$(mktemp 2>/dev/null)` and `outf=$(mktemp 2>/dev/null)`; when either is empty, fall through to today's straight-through line unchanged and write no ledger entry (C4 — the record is not worth failing or silencing a hook for). Two named behaviour changes, both sanctioned by S-64355's own wording ("that output still reaches stderr"): the hook's **stdout is merged into stderr**, and a failed `mktemp` leaves the hook exactly as it is today. The push-allow site needs no capture at all (**PD8**), so this applies to two of the three points, not three. |

### Where the spec is wrong

Six findings above are defects in the approved spec, not choices this plan is making, and they are
listed here so the next reader does not have to infer which is which. **This plan adds no scope
for any of them**: each is the minimum change that makes the spec's own acceptance line true.

- **PD1** — §3 edits one `classify` call site, but `remote.evidence` calls `classify` too, so a
  `claude-remote` run's recorded refusal is unreachable and leg 5's `refusal is None` guard locks
  it out. The plan adds one trailing defaulted argument to `evidence`.
- **PD2** — §5's `Why` column reads `dead_why`, which the Dead group can never carry: health
  writes that field in the same call that takes the run out of the group. The plan adds one
  fallback read of `cloudpid.why`, the field `dead_why` is a copy of.
- **PD3** — §1's `last` cannot honour C7 from the ledger alone: the file is per job, not per run.
  The plan filters it to the run's own `started`/`ended` window.
- **PD4** — §2's capture of the hook's output, taken literally, silences a pre-push check that
  runs for minutes. The plan streams it through `tee` and carries the hook's status out in a file.
- **PD5** — §1's `refguard` pattern carries a `(?: \(warn\))?` alternative that can never match
  and must never be made to: a warn line is a push that proceeded. The plan drops it.
- **PD6** — §1's `CORRECTION_KINDS` is not a subset of `KINDS`, contradicting `Refusal.kind`'s own
  docstring, and omits `gate`, which is the pre-push door the card names. The plan adds `gate` and
  widens the docstring by one clause.

Everything else below is the spec as approved.
