# B-0119 — plan: tick logs stay empty while steps run; a live tick looks the same as a hung one

Item: B-0119 — tick logs stay empty while steps run; a live tick looks the same as a hung one.
Epic: E-0001 — ASF 0.1 — a working factory. Branch: `fix/B-0119`. No spec exists; the Acceptance
below is the record.

## Cause

A command step's whole stdout/stderr was collected by a single `proc.communicate(timeout=timeout)`
call and emitted only once the process exited. `~/.ASF/logs/tick-<product>-{tick,batch,daily}.log`
therefore stayed empty for the entire length of a running step — `factory-cron.sh` and
`factory-batch.sh` are themselves command steps that can run for minutes — so the operator reading
the log could not tell a step that was still running from one that had hung.

## Task 1 — a command step's own output streams as it is produced

writes: `asf/tick/steps.py` `tests/test_tick.py`

- Step 1: in `asf/tick/steps.py:run_command`, replace the single `proc.communicate(timeout=...)`
  call with a `select`/`readline` loop against `proc.stdout` that calls `emit(prefix +
  line.rstrip('\n'))` as each line is produced, instead of only once the process ends.
- Step 2: keep the existing timeout behaviour: past `deadline`, kill the whole process group
  (`os.killpg`), drain and emit whatever is left buffered, then emit the `timeout after {timeout}s
  — killed` line and return 124.
- Step 3: test, in `tests/test_tick.py`:
  - `test_b0119_output_is_emitted_as_the_command_runs_not_buffered_to_the_end` — a two-line shell
    command with a 1s sleep between the lines; asserts both lines were emitted and that the second
    arrived more than 0.5s after the first, proving the emit happened mid-run and not after exit.

## Acceptance

- [x] A command step's output lines reach the tick log as they are written, not only after the
      step's process exits (`tests/test_tick.py:558`,
      `test_b0119_output_is_emitted_as_the_command_runs_not_buffered_to_the_end`).
- [x] The existing timeout, kill-the-process-group and exit-code behaviour of `run_command` is
      unchanged (`test_timeout_kills_a_sleep`, `test_timeout_kills_the_whole_process_group`,
      `test_failing_command_step_exits_1_and_later_steps_still_run`).

## Accepted costs

The card's Description also asks for a line when *each* step — `asf`-owned steps included, not
just a command step's own stdout — starts and ends, naming the step, owner, pid and time and
flushed at once, so that the doctor's SCHEDULER row can show the tick's current step. That is a
second, independent piece of work: it touches the step-loop in `asf/tick/tick.py` (a start/end
line around every step, `asf`-owned or not) and `asf/doctor.py` (reading the log to show the
current step), neither of which this Task changes. Task 1 above closes the half of the bug that
was actually reported as reproducing — a command step's own output going silent mid-run — and
leaves the start/end-line-plus-SCHEDULER-row half to a follow-up card, filed via `asf inbox`
against this item as `inbox/tick-a-start-end-line-per-step-owner-pid-time-and-doctor-s-scheduler-shows-the-current-step.md`
(awaiting the groom to give it an id).
