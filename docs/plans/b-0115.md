# B-0115 — plan: a timed (calendar) clock does not run at load

Item: B-0115 — scheduler install runs the daily clock at load, hours outside its declared time.
Epic: E-0001 — ASF 0.1 — a working factory. Branch: `fix/B-0115`. No spec exists; the Acceptance
below is the record.

## Cause

`asf-live scheduler install` builds a `launchd` plist in `asf/scheduler.render()`. The plist was
assembled as one shared dict, and `RunAtLoad: True` was set on it unconditionally before the
calendar/interval branch chose between `StartCalendarInterval` and `StartInterval`. A calendar
clock (`clock.calendar` set — e.g. the daily clock at `{'Hour': 6, 'Minute': 50}`) therefore
carried `RunAtLoad` too, and `launchd` ran it once immediately on load, hours outside 06:50, in
parallel with the interval-driven tick and batch jobs.

## Task 1 — a calendar clock does not carry `RunAtLoad`

writes: `asf/scheduler.py` `tests/test_scheduler.py`

- Step 1: in `asf/scheduler.py:render()`, move `RunAtLoad` out of the shared `plist` dict.
- Step 2: on the calendar branch (`clock.calendar` set), set only `StartCalendarInterval`; do
  not set `RunAtLoad`.
- Step 3: on the interval branch, keep `RunAtLoad: True` alongside `StartInterval` — an interval
  clock has no fixed time to be "outside", so running once at load is correct for it.
- Step 4: tests, in `tests/test_scheduler.py`:
  - `test_daily_calendar_job_does_not_run_at_load` — the `DAILY` clock (`{'Hour': 6, 'Minute':
    50}`, matching the card's example) renders a plist with no `RunAtLoad` key.
  - `test_interval_job_still_runs_at_load` — the `RECORD` interval clock still renders
    `RunAtLoad: True`.

## Acceptance

- [x] A calendar clock's rendered plist has no `RunAtLoad` key
      (`tests/test_scheduler.py:283-286`, `test_daily_calendar_job_does_not_run_at_load`).
- [x] An interval clock's rendered plist still carries `RunAtLoad: True`
      (`tests/test_scheduler.py:288-290`, `test_interval_job_still_runs_at_load`).
- [x] The existing golden-plist coverage for an interval job is unchanged
      (`tests/test_scheduler.py:242`, still expects `RunAtLoad: True`).

## Accepted costs

`cron` (`asf/scheduler.py:374+`) is untouched: a crontab line never fires at install, so it has
no `RunAtLoad`-equivalent problem, and no companion fix is needed there.
