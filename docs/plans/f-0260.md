# Plan F-0260 — the answer is carried to where a tick can read it, the refusal is said in words, and no mint steps on an id origin already holds

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0260.md` (approved). Branch:
`plan/F-0260`.

Five Tasks, cut along the four seams the spec names, in the order a tick meets them — and cut so
that **every seam that can be measured alone is measured alone before anything reads it**:

1. **the carry, in `asf/groom/answers.py`** — one answers-file shape for the scanner and the
   applier, and `carry_checkout_answers`, which reads the operator's checkout and writes one file
   into the state dir. Nothing outside that module and its new test module changes; the tick's
   groom step already calls `apply_pending_answers`, so the carry lands wired.
2. **the sync that says why, in `asf/tick/shadow.py` and `asf/tick/tick.py`** — `Sync` instead of
   a bool, the three refusal lines with their drift and their record-relative paths, the
   `NEEDS OPERATOR` line, the event, and the `record-health.json` write that Task 3 reads.
3. **the two read views, in `asf/tick/record_health.py` and `asf/views/status.py`** — `line`'s
   checkout sentence and the one branch in `stale_cell`'s first reader, over the block Task 2
   writes. It needs Task 2's landed `Sync`, its landed `update` and its landed write.
4. **the allocator, in `asf/record/ids.py`** — the `claim or worktree` gate goes and the floor is
   read from `origin/<trunk>`. Independent of every other Task: no file it writes is written by
   any of them, and nothing it changes is read by them.
5. **the add/add discard, named** — `_resolve_by_ownership` returns what it threw away and `push`
   says so. It is last because its contract is four landed exact-output assertions
   (`tests/test_tick.py`), and it shares `tests/test_tick.py` with Task 3 and
   `asf/tick/shadow.py` + `asf/tick/tick.py` with Task 2.

They run **(1 | 2 | 4) → 3 → 5**. Tasks 1, 2 and 4 have disjoint `writes:` and no dependency on
one another, so they are one wave. Task 3 waits on Task 2 and shares `asf/tick/record_health.py`
with it: Task 2 owns the whole write side of the refusal — the `Sync` record, the three lines, the
`NEEDS OPERATOR`, the event, and `record`/`update` — and Task 3 adds only the two read views over
the block that write produces. Task 5 waits on Task 2 and Task 3 because its
`writes:` intersects both — `asf/tick/shadow.py`/`asf/tick/tick.py` with Task 2 and
`tests/test_tick.py` with Task 3 — and a queue is the right answer there: all three edit
`_resolve_by_ownership`'s own file or its own test module.

**Read PD1 through PD6 before writing a line.** Each is a place where following the spec's design
literally ships something red, something silently lost, or something that lies: a clean add/add
resolution aborts the push (PD1), the `record_checkout_stale` event never reaches origin (PD2),
`record-health.json`'s new field is wiped by the next tick (PD3), A2's own driver prints no
`[step:record]` row at all (PD4), an adjudicator's answers file for the same day is marked
superseded and never applied (PD5), and the carry's stated predicate cannot read an answer (PD6).

The fences of §*The fences, and the suite* bind every Task, so every Gate and Acceptance block
below carries them beside its own.

| PD1 | **`_resolve_by_ownership` returning a list makes `push` abort the rebase on every clean resolution, because `[]` is falsy** | The spec's §2 says the signature *"changes from `-> bool` to `-> list | None` (`None` for the conflicts it still refuses)"*. But its one caller is `while rebase.returncode != 0: if not _resolve_by_ownership(path): … rebase --abort; return False` (`asf/tick/shadow.py:146-151`), and a modify/modify resolution — the common case, the one four landed tests assert (P19) — returns an **empty** list of discards. `not []` is `True`, so the rebase would be aborted and the push refused for every conflict the function just resolved: `test_f0087_typed_field_and_machine_block_on_one_card_resolve_by_ownership_under_the_race` (`tests/test_tick.py:303-325`) and `test_conflict_on_machine_owned_card_content_is_re_derived_and_pushed` (`:346-362`) both go red, and so does the production path B-0044 exists for. **Decided:** the caller tests identity, never truth — `got = _resolve_by_ownership(path)` then `if got is None:` — and the discards **accumulate across the loop**: `discarded += got`, declared before the `while`, because the rebase replays commit by commit and the function is called once per conflicted step. The accumulated list, not the last call's, is what `push` prints. |
| PD2 | **`ctx.event('record_checkout_stale', …)` written from `commit_and_push` never reaches origin: the clone has already been committed and pushed, and the next run's `ensure_clone` destroys it** | The spec's §3 puts the event in `commit_and_push`, after `sync_operator_checkout`. Measured: `commit_and_push` (`asf/tick/tick.py:294-311`) runs `commit_local` → `push` → `sync_operator_checkout`, in that order, and `ctx.event` appends to `metrics/events/<day>.jsonl` **in the clone** (`:249-257`). An append after the push is either an untracked file or an unstaged modification, and `ensure_clone` opens every run with `fetch` + `reset -q --hard origin/<branch>` + `clean -fdq` (`asf/tick/shadow.py:76-79`) — the first discards the modification, the second the untracked file. So the event would be written on every tick and land on none. `record_health.py`'s own docstring already names this exact case: *"a failing record step is exactly the case where the clone's own push can't reach origin, so nothing written to it survives to the next tick"* (`:4-6`). **Decided:** the refusal's event is emitted by the **next** tick's record step, read out of `record-health.json` — the artifact built to survive a dead push — immediately before `record_health.record(...)` in the step loop (`asf/tick/tick.py:645-647`), which is inside the step loop and therefore **before** `finish`'s commit, so the line lands in that tick's own push. The tick log's `record:` line, its `NEEDS OPERATOR` line, `record-health.json` and the Stale row are all same-tick and exactly as prompt as today's line; only the record's own archival copy lags by one tick, and since the refusal is said again every tick while it holds (D5) that lag is invisible from the second tick on. The two alternatives were rejected: moving the whole sync before the commit makes a clean checkout lag one tick behind origin and turns `test_a_pushed_tick_fast_forwards_the_operator_checkout` red, and committing-and-pushing a second time just to carry the event adds one record commit per tick while the operator's tree is dirty — 28 of them in the measured hour, which makes the checkout *further* behind. |
| PD3 | **`record_health.record(product, ok=True)` writes `{'ok': True, 'ts': now}` and drops every other key, so the `checkout` field is destroyed by the next tick's record step** | `asf/tick/record_health.py:38-39`, read verbatim: the success branch builds a fresh two-key dict. The sync runs in `finish`, after the record step, so the write order within one tick is `record(ok=True)` → … → `update(checkout=…)`; on the next tick `record(ok=True)` wipes it again, and between the two writes any early exit (B-0083's `break` at `asf/tick/tick.py:648-652`, a crash, a `--steps` run that never reaches `finish`) leaves the file with no `checkout` block while the drift is still there — and the Stale row then goes back to blaming the factory, which is the defect. It also wipes the streak the row's `(<n> ticks)` needs. **Decided:** two functions, one block each. `record(product, ok, reason=None, now=None)` keeps its signature and its two branches and gains one line: it carries any existing `checkout` block through verbatim (`prev = read(product) or {}` is already read on the failure branch; the success branch reads it too and copies `checkout` if present). A new `update(product, checkout=None, now=None)` owns that block alone: it reads, replaces `checkout` and writes, and computes the block's **own** `since`/`ticks` streak — extended when the previous block carried a refusal, started at this tick when it did not, and the key removed entirely when `checkout` is `None` (the sync moved, or had nothing to say). `ok`, `ts`, `since`, `reason` and `ticks` at the top level stay the record step's and are never touched by `update`. This is the spec's own "the plan decides whether that is a second `record(...)` call or an `update(product, checkout=…)`", decided for `update`: a second `record(...)` call would have to be passed the step's `ok` from `finish`, which does not know it. **Both functions are Task 2's**, beside the one call site in `commit_and_push` that needs them — a write and its caller in one Task. Task 3 adds only `line`'s new sentence over the block they produce, which is why Task 3 is `after: Task 2` and the two share this file. |
