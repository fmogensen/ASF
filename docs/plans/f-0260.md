# Plan F-0260 — the file the operator is told to write in is read, the refusal that followed is readable, and no mint steps on an id origin already holds

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0260.md` (approved). Branch:
`plan/F-0260`.

Four Tasks, cut along the spec's own four seams — **the carry, the refusal, the allocator, the
discard** — and ordered so that the one pair that shares a file is a queue and the rest is one
wave:

1. **the operator's answer, carried — `asf/groom/answers.py`** — `carry_checkout_answers`, one
   call inside `apply_pending_answers`, and `_ANSWERS_FILE_RE` widened to the shape the applier
   already accepts with the date taken from its group (§1, D1-D3, D9, P15-P17). One existing
   module, one new test module. Nothing else in the factory reads either function.
2. **the refusal, said in four places — `asf/tick/shadow.py`, `asf/tick/tick.py`,
   `asf/tick/record_health.py`, `asf/views/status.py`** — `sync_operator_checkout` split into a
   read-only probe and the merge it guards, returning a `Sync` record whose lines carry the drift
   and the record-relative paths and no machine path; one `NEEDS OPERATOR` line, one event, one
   `record-health.json` field and the Stale row's own words, with `[step:record]`'s `ok=` untouched
   (§2 first half, §3, D4, D5, D10, D11, P5-P8, P18).
3. **one allocator, and a floor origin agrees with — `asf/record/ids.py`** — the `claim or
   worktree` gate goes, `origin_top` is new, and both the claim path and the local fallback clear
   origin's own top (§4, D6, D7, P9-P11). One existing module, one new test module.
4. **a card the push discards is named by its id — `asf/tick/shadow.py`, `asf/tick/tick.py`** —
   `_resolve_by_ownership` tells add/add from modify/modify and returns what it dropped, `push`
   says which, and the tick raises one `NEEDS OPERATOR` naming the ids to re-file (§2 second half,
   D8, P12, P13, P19).

They run **(1 | 2 | 3) → 4**. Tasks 1, 2 and 3 need nothing of one another: their `writes:` are
disjoint (`asf/groom/answers.py` against the four `asf/tick` + `asf/views` files against
`asf/record/ids.py`), so they are one wave. Task 4 is `after: Task 2` and the reason is **the
file, not the logic**: `_resolve_by_ownership` and `push` are in `asf/tick/shadow.py` and the
`NEEDS OPERATOR` it raises is in `commit_and_push` in `asf/tick/tick.py` — both files Task 2
rewrites, and `tests/test_tick.py` is where both Tasks' cases live (the spec's A3 block is half
Task 2's and half Task 4's). Nothing in Task 4 calls anything Task 2 adds, so shipped alone it
would build and pass; shipped *beside* Task 2 it would be two sessions editing one function's
neighbourhood, which is the one thing a disjoint `writes:` buys. The queue is the cheaper trade.

**Read PD1, PD2, PD4, PD5 and PD7 before writing a line.** Each is a place where following the
spec's design literally ships something that does not survive the next tick, breaks four landed
tests, or fails a gate before a single test runs: the event the spec writes from `commit_and_push`
is destroyed by the clone's own reset before it is ever committed (PD1), `_resolve_by_ownership`'s
new return value is falsy on success and the landed call site reads it as a refusal (PD2),
`asf/tick/shadow.py` sits **exactly** on its raw-git-call ceiling so one more `['git'` line fails
`check_clients.sh` (PD4), `asf/record/ids.py`'s ceiling is zero so `origin_top` may not call git at
all (PD5), and `record_health.record(ok=True)` throws away every key but two, which silently
deletes the field §3 adds (PD7).

The fences of §*The fences, and the suite* bind every Task, so every Gate and Acceptance block
below carries them beside its own.

| PD1 | **The event the spec writes from `commit_and_push` can never reach the record: the clone is `reset --hard` and `clean -fdq` at the head of every record step, and `commit_and_push` writes after its own commit** | §3 puts `ctx.event('record_checkout_stale', …)` in `commit_and_push`, which is where the sync runs — and the sync runs *last*, after `commit_local` and `push` (`asf/tick/tick.py:300-310`). So an event written after that tick's `commit_local` is in the clone's working tree, uncommitted, and is deleted by the next tick's reset before anything commits it. It reaches no `metrics/events/` file on origin, ever. The spec's Records table requires it to. **Decided:** the read-only half of the sync becomes `shadow.probe_operator_checkout(product, out=print)` and it runs at the **top** of `commit_and_push`, before `commit_local` — so the event is part of the commit `commit_local` makes and the push carries it.
