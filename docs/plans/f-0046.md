# Plan F-0046 — the record stops holding two live answers to the same question

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0046.md` (approved). Branch: `plan/F-0046`.

Six Tasks, cut by the module that owns the new surface — which is how the spec's own §1.2 lists the
work. Task 1 is the whole pure half in one new module (`asf/groom/conflicts.py`: the graph §2.2, the
reader §2.5, the pass §2.6, the line grammar and `conflict_lines` §2.7); Task 2 is the check and the
two fields a hand may write (§2.3, §2.1); Task 3 is the one clause that drops a superseded rule from
the rule run (§2.4); Task 4 is the History appender losing its literal (§2.9); Task 5 is the groom
section, its dedupe token and the answer grammar the adjudicator is handed (§2.7); Task 6 is the
applier's fourth arm and its two refusals (§2.8).

Tasks 1, 3 and 4 write three disjoint sets and start at once. Tasks 2 and 5 both read Task 1's module
and write nothing the other writes, so they run together as soon as it has landed. Task 6 writes
`asf/groom/groom.py` and `tests/test_groom.py`, which is Task 5's set exactly, so it queues behind
it — and it needs Task 4's `append_section_lines` to merge a `## Source` at all.

Wave order: **1 ‖ 3 ‖ 4 → 2 ‖ 5 → 6**.

§3.7's last fence — the whole suite green — binds every Task, so every Gate below runs
`python3 tools/run_tests.py` beside its own.

The order is not asserted, it is parsed: `asf.record.plan_order.task_order` over this file returns
`{1: [], 2: [1], 3: [], 4: [], 5: [1], 6: [1, 4, 5]}` — acyclic, and the waves above — and
`asf.tick.migrate.plan_task_records` reads six Tasks whose `writes:` lines come back exactly as
written, disjoint within each wave.

**Steps**

1. The module docstring says what the module is and what it may not do — pure, no io, no git, no

   messages on *the other* card's `id:` line, each naming the `asf set` that fixes it. A dangling
   id is reported and then dropped from the edge set before `cycles` runs, so one missing card

5. The pass, §2.6: `CONFLICT_OVERLAP = 0.5` with its comment (strictly above, as
   `groom_near_duplicates` is strictly above its own, `asf/groom/groom.py:585`); `live`,

   `precedence` reads `date:`, `stage_since:` then `updated:` off `rec['meta']`, which carries the
   machine block's keys too (PD16). `pairs` is ranked and uncapped (§1.4): the order is the
   guarantee, not a cut.
6. `conflict_lines(canonical)` — one entry per pair, a block whose first line is
   `- [ ] <a> conflicts <b> — <reason>; keep A · keep B · both · merge (merge keeps <winner>) → answer: ____`
   and whose next three lines are indented six spaces: `A <id> "<statement>" — <source>`, the same
   for `B`, `precedence: <winner> (<why>)`. Statements truncated to 120 characters with `…`; the
   reason phrase as §2.7 prints it (`overlap 0.62`, or ``scope `harvest`, shares
   `harvest.rebase_and_resolve` ``).
7. `CONFLICT_RE` and `CONFLICT_ANSWER_RE` as §2.8 spells them but defined here (PD7), each with
   the comment saying who matches it and why the line decides rather than the answer word.
8. `GraphTests` (§3.1), `ReaderTests` (§3.4), `PairingTests` and `TopTwentyTests` (§3.5) — every
   case those four sections enumerate, one assertion each, including the negatives that are the
   point: the exactly-`0.5` pair that does not pair, the same scope with no shared object, the
   bare word `harvest` that is no named object, the diamond that is no cycle, and the five kinds
   of card outside the live set.
9. `TopTwentyTests`' two records are built as §3.5 describes — the 32-card one from all three body
   shapes of §1.1 with six planted conflicts and nothing else pairing, and the 25-planted one at
   known distinct scores where the first twenty of `pairs()` are the twenty highest in order and
