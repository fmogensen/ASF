# Plan F-0325 — the declared clock becomes the job it was written to be

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0325.md` (approved, landed at
`c84d16927`). Branch: `plan/F-0325`.

**One Task.** The spec's whole change is two symbols in `asf/scheduler.py` (§1, about sixteen lines
with its docstring), one rewritten wave block of `clocks()` (§2, four lines becoming thirteen), one
new `check_wave_clock` in `asf/doctor.py` with two lines at its print site (§3), four comment lines
in `docs/products.example.yaml` (§4), and three test classes. §3 cannot be written before §1 and §2
have **landed** — it calls `scheduler.declares_wave_job` and compares against
`scheduler.WAVE_COMMAND`, and two of its nine acceptance lines read a *converted* clock — so a
split by Story is strictly serial whatever its `writes:` say, buying a second PR and a second review
round and no parallelism at all (**PD2**).

Wave order: **Task 1** — one wave, one Task, `after: none`, starts at once.

Nothing in the spec's `### Out` is touched. `asf/tick/wave_clock.py` is not edited: the locking, the
marker, the private record clone and `ran_recently` keep every rule they have, including the
`note_ran` move B-84831 landed after the spec was written (**PD5**). `clock_of_plist` keeps its
missing wave arm, the upgrade drain keeps not matching `asf wave`, and the wave's event rows keep
being dropped by `wave_clock._Context.event` for a product whose only `wave` carrier is the
converted clock — all three noted in the spec and not fixed here. A clock carrying the `wave` step
under another name (`launch: {steps: [wave]}`) is still built as a tick with the derived job beside
it, which is a different card.

This plan corrects the approved spec in one place, measured, and it is not a widening: **the spec's
§3 as written fails the spec's own acceptance line** `a product declaring no clock named wave gets
no line` — it reports the *derived* wave job as "not the wave job (steps: [])" for every product
that declares no `wave` clock at all (**PD4**). One guard fixes it, and the Task's Steps carry the
corrected function.

2. §1 — `asf/scheduler.py`, after `WAVE_COMMAND` (`:98`). The spec's code, verbatim:

   ```python
   #: the tick step the wave job runs — the step a declared ``wave`` clock carries (F-0325)
   WAVE_STEP = 'wave'


   def declares_wave_job(clock):
       """Whether ``clock`` is the operator's own declaration of the wave job (F-0325): named
       :data:`WAVE_CLOCK`, carrying :data:`WAVE_STEP` and nothing else.

       Such a clock used to be built as a plain tick, so it ran ``asf tick --steps wave`` and took
       the product's one tick lock (:func:`asf.tick.tick.lock_path`) — on a busy product it skipped
       every firing a long tick ran through, and being named ``wave`` it also kept the dedicated job
       from ever being installed beside it. It is rendered as that job instead, at the ``every:`` or
       ``at:`` it declares. ``steps`` is left as declared on purpose: :func:`tick_argv` dispatches on
       ``command`` before it reads ``steps``, and :func:`asf.doctor.check_clock_steps` reads the
       ticked set out of ``steps`` — emptied, it would report the wave step as being on no clock.
       """
       return (clock.name == WAVE_CLOCK and not clock.shadow
               and list(clock.steps or []) == [WAVE_STEP])
   ```

   The `not clock.shadow` arm is what leaves P4's shape a tick, and `== [WAVE_STEP]` is what leaves
   `[wave, prs]` a tick — both of them `D4`'s cases, named to the operator by §3 rather than
   converted.

3. §2 — the wave block of `clocks()` (`:551-554`) becomes, verbatim from the spec:

       if WAVE_CLOCK in declared:

           # cadence it declares, under tick-wave.lock — never as a tick on the product's tick lock

4. §3 — `check_wave_clock` in `asf/doctor.py`, beside `check_clock_steps`. The spec's function with
   **the PD4 guard added** (the two guard lines are marked; everything else is the spec's, including
   the docstring, to which one sentence is added for the guard):

   ```python
   def check_wave_clock(product):
       """One ``NEEDS OPERATOR`` line per wave-clock shape ASF will not convert to the wave job
       (F-0325, :func:`asf.scheduler.declares_wave_job`).

       Two of them. A clock *named* ``wave`` that is not the job holds the label
       ``<prefix>.<product>.wave`` the job would be installed under, so the job is never added
       beside it (:func:`asf.scheduler.clocks`) — a shadow clock, or one carrying steps besides
       ``wave``. And ``clocks.wave: off`` in ``config.yaml`` forbids the job outright, which leaves a
       declared ``wave: {steps: [wave]}`` clock running as a tick on the product's tick lock, the
       very thing it was written to avoid. A product whose clocks do not load has nothing to read:
       the scheduler section reports that.

       Only a clock the product's own file *declares* is read. A product that declares no ``wave``
       clock still has one in the built list — the derived job :func:`asf.scheduler.clocks` appends,
       whose ``steps`` are empty — and reporting that as "not the wave job" would name a clock the
       operator never wrote, on every healthy product.

       The ``off`` arm is read off the built clock rather than by calling
       :func:`asf.tick.wave_clock.off` again: :func:`asf.scheduler.clocks` has already evaluated it,
       and ``env.load_config`` re-reads and re-validates ``config.yaml`` on every call. A clock that
       :func:`asf.scheduler.declares_wave_job` accepts and that still carries no
       :data:`asf.scheduler.WAVE_COMMAND` can only have come through that one guard, so ``command is
       None`` *is* ``off``. This couples the line's wording to there being exactly one reason
       ``clocks()`` declines the conversion; a second reason must add its own arm here.
       """
       try:
           built = scheduler.clocks(product)
       except scheduler.SchedulerError:
           return []
       declared = product._get('clocks') if hasattr(product, '_get') else None   # PD4
       if scheduler.WAVE_CLOCK not in (declared or {}):                          # PD4
           return []                                                             # PD4
       wave = next((c for c in built if c.name == scheduler.WAVE_CLOCK), None)
       if wave is None:
           return []
       path = f'products/{product.name}.yaml'
       if not scheduler.declares_wave_job(wave):
           shape = 'shadow: true' if wave.shadow else f"steps: [{', '.join(wave.steps or [])}]"
           return [f'NEEDS OPERATOR: clock wave in {path} is not the wave job ({shape}) — it holds '
                   f'the label the wave job installs under, so the wave job is never installed '
                   f'beside it; rename the clock']
       if wave.command != scheduler.WAVE_COMMAND:
           return [f'NEEDS OPERATOR: clock wave in {path} runs the wave step as a tick on the '
                   f"product's tick lock, because clocks.wave: off in config.yaml keeps it from "
                   f'running as the wave job — remove clocks.wave: off to give it its own lock']
       return []
   ```

   The guard mirrors `clocks()`' own `WAVE_CLOCK in declared` (`:551`) and reads the product, not
   the config, so it costs nothing. The `hasattr(product, '_get')` form is the one `clocks()` uses
   at `:530` and `:546`. A converted clock still produces no line: `declares_wave_job` is true and
   the clock carries `WAVE_COMMAND`, which is the whole point. Measured over all seven shapes, this
   function returns exactly: nothing for the converted clock, nothing for a product with no declared
   `wave` clock (with `clocks.wave` off or not), nothing for a product with no `wave` step anywhere,
   the shape line for `[wave, prs]` and for `shadow: true`, and the `off` line for a declared
   `wave: {steps: [wave]}` under `clocks.wave: off`.

## What this plan leaves unbuilt, and why

Everything in the spec's `### Out`, and nothing else. `asf/tick/wave_clock.py` is not edited: the
job keeps its lock, its marker, its private record clone and `ran_recently` exactly as they are,
including B-84831's rule that a raising run leaves no marker (PD5). This card moves one clock onto
that job; it does not change the job.

Three consequences of that are named in the spec and stay named rather than fixed.
`scheduler.clock_of_plist` still has no arm for the wave's job, so an installed `asf.<p>.wave` job
reads back as `None`; that path is only reached for an *undeclared* installed job, and this change
makes a declared wave clock more often declared, never less, so no new case reaches it.
`asf.upgrade.TICK_PATTERN` (`asf/upgrade.py:65`) still does not match `asf wave`, so a converted
clock's runs stop being counted by the drain and `upgrade.waiting()` no longer pauses them —
`MOVE_PATTERN` (`:798`) does match it, which is the dedicated job's existing behaviour that this
card makes one more clock share. And the wave's **event** rows are lost for a product whose only
`wave` carrier is the converted clock: `wave_clock._Context.event` is `return None`
(`asf/tick/wave_clock.py:182-183`, PD5), so the `launch`, `capacity`, `triage`, `host_pressure`,
`budget_hold`, `paused` and `on_trunk` rows that product used to write into
`metrics/events/<day>.jsonl` through the tick's own `Context` stop being written, and nothing names
the loss — by `D2` the clock keeps `steps: ['wave']`, so `check_clock_steps` counts the step as
ticked and `check_wave_clock` returns `[]` for exactly that shape. All three are the job's existing
behaviour, shared by one more clock.

A clock carrying the `wave` step under a different name (`launch: {steps: [wave]}`) is not touched:
it is the same tick-lock shape, but the derived job is still installed beside it (P1c), so rows are
still launched and the only cost is a noisy log. Lower severity, different card — and `check_wave_clock`
is keyed on the name `wave`, so it says nothing about such a clock either.

`D4`'s name-keyed guard is kept rather than keyed on `command`: `wave: {steps: [wave, prs]}` is a
real tick that keeps the name, so appending the derived job beside it would build two clocks named
`wave` and render the duplicate label `asf.<p>.wave`, one install overwriting the other. A name
collision cannot be resolved inside `clocks()`, so `D5` names it to the operator instead. `D6` is
kept too: `clocks.wave: off` still wins over a declared `wave` clock, because a clock converted
under `off` would fire every minute to print `wave: clocks.wave is off — nothing to do` — worse
than the tick it replaced.

Two seams this plan found and does not fix. `scheduler.MIN_EVERY_S` is tunable through
`scheduler.min_every_s` while `wave_clock.MIN_EVERY_S` is a constant applied only to
`clocks.wave.every`, so an operator who lowers the floor for every clock can declare a wave clock
below the job's own floor; the job's lock makes the extra firing a no-op, and overriding the
operator's `every:` is what `D3` chose against (PD9). And `TestCheckClockSteps` reads the
operator's real `~/.ASF/config.yaml` because the class isolates no `ASF_HOME`; this card works
around it by patching `wave_clock.off` in every new case (PD7) rather than fixing the fixture,
which would be an edit to a class `D2` exists to keep green.

coverage: 3/3 stories; uncovered: none
