# Plan F-0115 — five Tasks, four waves: the registry, the read-only token, the derived list, the composed file, the row and the offer

Epic: E-0004 — Control plane — the factory's dashboard, served from the record. Spec:
`docs/specs/f-0115.md` (approved). Branch: `plan/F-0115`.

**Five Tasks, four waves.** The spec's §*The design* is almost the split: one new module
(`asf/workers/worker_perms.py`) and one edit each in four existing files. What it does not settle
is the order, and the order is not free — Tasks 3, 4 and 5 all write the new module and its test
file, so their footprints cannot be disjoint and `after:` is the honest answer rather than a wider
wave (PD11). The chain is: the gate's command list becomes a function anyone may read, and — in
the same wave, on a footprint that touches nothing else — `printenv` joins the approvals hook's
read-only register; then the module that derives the allow list from that function; then the file
that merges it over the operator's own and the one line in `spawn` that points `--settings` at it;
then the row that says when a derived rule is denied anyway, the command that prints the list, and
the two documents.

Each Task lands something whole. After Task 1 `harvest.gate_commands(conv, asf_repo, only)` returns
exactly what `product_gate` runs and `product_gate` runs exactly it — a pure extraction, proved by
the 164 existing gate cases staying green. After Task 2 a session's `printenv | grep -iE '…'` is
read by the approvals hook as a search, not as a run of whatever the pattern names. After Task 3
`worker_perms.allow_rules(product)` is the list, with no file written and nothing launched from it.
After Task 4 the card's own defect is closed: a worker session launched by `spawn` carries a rule
for `bash tools/check_conventions.sh`.

**Read PD1 before Task 5** — the spec's §2 module surface omits `check_doctor`, which its own §5
calls. **Read PD2 before Task 5** — registering the command is a three-file edit, not the two the
spec names, and one of the two it names registers nothing. **Read PD5 and PD6 before Task 3** —
they are the two places a naive reading of the design makes every worker launch slower, or makes it
raise where it never did.

Every anchor the spec cites was re-read in this worktree at `cc5e5038c`, four commits past the
spec's own `b21116e00`. **Every precondition still holds and no line number moved**; PD12 carries
the re-read. Two of the spec's own statements are wrong in detail and neither changes any work
(PD4, PD3). Baseline green before any edit, measured here:

- `python3 -m unittest -q tests.test_workers tests.test_approvals tests.test_install` →
  `Ran 440 tests in 105.199s` / `OK (skipped=1)` — P15 to the test, to the count.
- `python3 -m unittest -q tests.test_surface tests.test_doctor` → `Ran 88 tests in 3.407s` / `OK`.
- `python3 -m unittest -q tests.test_harvest` → `Ran 164 tests in 104.189s` / `OK` — the suite that
  is Task 1's whole proof, green before it is asked to prove anything.

The spec's §*Out of scope* binds every Task, and three of its lines are the ones most likely to be
crossed by accident: **no deny rule is written by this card** — F-0062 §2.7 owns those, and

than deleting a rule that does not exist yet; and **the session transcript is not masked** — the
exposure is real, pre-existing, not widened here, and wants its own Bug card.

### Task 1: the commands the gate runs become one function, and `product_gate` is its first reader
stories: S-38350
writes: asf/harvest/harvest.py, tests/test_harvest.py
after: none

The spec's §1. After this Task `harvest.gate_commands(conv, asf_repo, only)` returns `(cmds, env)`
— every command the gate runs for `conv`, in the order it runs them, with the test command's
leading `NAME=value` tokens lifted out — and `product_gate`'s first six lines are the call. Nothing
about what the gate runs changes, and the 164 cases of `tests.test_harvest` are the proof of that.

This is an extraction and must read as one. The bisection path (`only`), the per-command timeout,
the red-module parse, the `keep_red_output` call and the timing line are untouched; the diff in
`product_gate` is six lines out, four lines in.

Read **PD4** before counting call sites — there are two, not the three P3 names.

**Files**

- `asf/harvest/harvest.py`
  - `gate_commands(conv, asf_repo, only=None)` — new, placed directly above `product_gate`
    (`:850`), the spec's §1 snippet byte for byte, docstring included
  - `product_gate` (`:861-870`) — the six lines from `cmds = []` through the `elif asf_repo:`
    become the spec's four: `env = gate_env(tmp)`, `cmds, extra = gate_commands(conv, asf_repo,
    only)`, `env.update(extra)`, `if only: env[ONLY_VAR] = ' '.join(only)`. **No other line of
    this function.**
  - `ASF_GATE_SCRIPTS`' `#:` block (`:708-709`) — one sentence: it is read by the worker allow
    list too (`asf.workers.worker_perms`), so a lint appended here is allowed in every worker
    session with no second edit
- `tests/test_harvest.py` — `class GateCommandsTests`, new.

**Steps**

1. `gate_commands` first, exactly as §1 gives it. Two things in it are load-bearing and easy to
   lose: `extra` is initialised to `{}` at the top, so a `conv` with no `test_command` returns
   `(cmds, {})` rather than an unbound name; and the scripts are appended under `if not only and
   asf_repo`, which is the same condition `product_gate`'s `if only: … elif asf_repo:` reads the
   other way round (P1) — with `only` set the old code took the first branch and never appended,
   and the new code appends nothing for the same reason.
2. `product_gate`'s replacement. `env.update(extra)` moves **out** of the `if conv.test_command:`
   block and runs unconditionally; that is not a behaviour change, because `extra` is empty
   whenever the old code would have skipped the update. `env[ONLY_VAR]` stays in `product_gate`:
   it is an environment the gate sets, not a command the gate runs, and `gate_commands` is the
   registry of commands.
3. `ASF_GATE_SCRIPTS`' sentence. Write it for the next person to append a lint — what else moves
   when they do, which is nothing, which is the point of the card.
4. `GateCommandsTests` — over a `Conventions` built in the test, not a product on disk: the test
   command alone for `asf_repo=False`; the test command then the two `bash tools/<x>.sh` argvs in
   `ASF_GATE_SCRIPTS` order for `asf_repo=True`; **both scripts present, which is the asymmetry
   the card's evidence shows and the one assertion that must not be softened**; a leading
