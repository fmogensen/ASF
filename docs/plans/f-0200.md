# Plan F-0200 — an S1 card stuck on a signature question is not allowed to be quiet

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0200.md` (approved). Branch:
`plan/F-0200`.

Two Tasks, cut so that **the reads land before the line that depends on them**:

1. **the three reads** — `severity_of`, `graded`, `body_signature`, `signed`, the filler chain in
   `process_inbox`, the Bug branch's severity, and `shape.derive`'s one added clause. After this
   Task the card that opened this Feature is *minted* rather than asked: an `S1:` title is a
   severity and a body `Error:` line is a signature. No new output, no new row, nothing louder.
2. **the loud line** — `stuck_s1_lines`, the severity token in `question_lines`, the print in
   `cmd_groom` above `_write_incremental`'s early return, the `Intake` row in `asf status`, and
   the one `NEEDS OPERATOR` family the troubleshooting guide is missing. After this Task a card
   that is *still* stuck says so, every tick, naming its file.

They run **1 → 2**, one after the other. This is not a convenience: Task 2's `stuck_s1_lines`
reads a card's severity through Task 1's `severity_of` (C5 — one definition, every reader on it),
and Task 2's `TwoTicksOfASilentNight` asserts the third run *mints* the card at `severity: S1`
with the body line as its signature, which is Task 1's behaviour. The footprints confirm the
serialisation independently: both Tasks write `asf/groom/inbox.py` and
`tests/test_intake_severity.py`.

**Read PD1, PD3 and PD4 before writing a line.** The spec's design cites two module constants
that do not exist (`SIGNATURE_MAX`, `QUESTION_MAX`) and gives no value for either; one clause of
the spec turns a test module red that none of its fences names; and one tracked document claims a
completeness this change falsifies. All three are named below with the decision made.

**Steps**
