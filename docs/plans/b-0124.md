# B-0124 — plan: status and the tick digest say the record is stale, in words

Item: B-0124 — Status shows a 7-hour-old snapshot as current when every tick fails offline. Epic:
E-0001 — ASF 0.1 — a working factory. Branch: `fix/B-0124`. No spec exists; the Acceptance below
is the record.

## Cause

From 03:00 to 10:20 the factory host had no route out: every tick's record step failed with
"Could not resolve host: github.com", and nothing pushes when a record failure can't reach
origin — so `metrics/ticks` never carried a line about the streak either. `asf status` reads only
`index.json`, which the last successful record left in place, so it printed the same "0 working,
3 dead" snapshot unchanged for 7 hours with no hint beyond "(exit 1)" in the Cron cell.

## Task 1 — a local record-health stamp, read first by status and the tick digest

writes: `asf/tick/record_health.py` `asf/tick/summary.py` `asf/tick/tick.py`
`asf/views/status.py` `tests/test_tick.py`

- Step 1: add `asf/tick/record_health.py` — `path(product)`, a local, never-git-tracked
  `record-health.json` under the product's state dir; `record(product, ok, reason, now)`, writing
  `{ok, ts}` on a landed record step or `{ok: False, ts, since, ticks, reason}` on a failed one,
  extending the previous stamp's `since`/`ticks` streak when it was already failing; and
  `line(product)`, rendering `"STALE since <local HH:MM> — record failed: <reason> (<n>
  ticks)"`, or `None` when the last tick's record step landed (or none has run).
- Step 2: in `asf/tick/tick.py`, call `record_health.record(...)` from `_run_steps` right after
  the `record` step runs, landed or not; reduce a DNS/network git error to the word `"offline"`
  (`_reason()`, checked against `_OFFLINE_MARKERS`) instead of the raw git error text, in both
  `run_record_step` and `run_asf_step`'s exception path.
- Step 3: in `asf/views/status.py`, add `stale_cell(root, product)` — `record_health.line()`
  first; when that says the last tick landed (or none has run on this host), fall back to the
  index's own age against twice the record clock's period (`_record_period_s`, read from
  `scheduler.clocks`, falling back to `DEFAULT_RECORD_CLOCK_S`), for a dead cron rather than an
  offline host. Wire it as the **Stale** row, first in `render()`'s table, no row when neither
  path says the table is stale.
- Step 4: in `asf/tick/summary.py`, `digest()` takes an optional `stale_line` and appends it
  after the step/counter lines when present; `run()` passes `record_health.line(product)`, so
  the per-tick digest (B-0087) carries the same line `asf status` prints.
- Step 5: tests, in `tests/test_tick.py`:
  - `RecordHealthStaleStatusTests.test_a_failed_record_tick_makes_status_print_the_stale_row_with_since_time_and_count`
    — two ticks fail at record with a DNS error; each tick's own output reduces it to `"RECORD
    STALE — offline"`; `status.stale_cell` reads back `"STALE since <since> — record failed:
    offline (2 ticks)"`.
  - `RecordHealthStaleStatusTests.test_a_landed_tick_after_the_streak_clears_the_row` — a landed
    tick after an offline streak clears both `record_health.line()` and `status.stale_cell()`.

## Acceptance

- [x] `asf status`'s first row says the table is stale, with the since-time and the tick count,
      when the last tick failed at record.
- [x] A tick that fails offline reduces its reason to `"offline"` instead of the raw git error,
      in both the tick's own output and the stale row.
- [x] The per-tick digest (B-0087) carries the same stale line `asf status` prints.
- [x] A failed-record tick makes status print the STALE row with the since-time and the count
      (`tests/test_tick.py::RecordHealthStaleStatusTests`).

## Accepted costs

`_OFFLINE_MARKERS` (`asf/tick/tick.py`) is a second, narrower network-failure classifier than
`asf/workers/lifecycle.py`'s `NETWORK_RE` — noted as an I-list follow-up, not blocking. The
`stale_cell` fallback path (index age against twice the record clock's period, for a dead cron
rather than an offline host) has no direct test coverage; `RecordHealthStaleStatusTests` only
exercises the `record_health` stamp path. `tick_line()`'s `metrics/ticks` JSONL entry doesn't
carry `ctx.stale_reason`, so a replayed past tick (`asf watch`) won't show the STALE annotation
once an offline streak's lines do get pushed — only the live per-tick digest carries it.
