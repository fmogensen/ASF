# Plan F-0242 — four files, four Stories, one wave: the diagnosis stops disagreeing with the gate, and the two levers get pulled

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0242.md` (approved). Branch:
`plan/F-0242`.

Four Tasks, one per Story, cut so that **each Task is one file's seam and no two Tasks touch the
same file**:

1. **the diagnosis counts rework** — `diagnose.rank`'s `by_kind` rows gain the flagged repair
   numbers, `causes` gates and speaks on them, `metric` answers a `kind:` cause with the number its
   own threshold compares. After this, `asf scorecard` and `asf release-readiness` give one answer
   about ADR 0003 instead of two.
2. **the pre-review is in every review brief** — a `review_checks_cmd` context key built from the
   branch's own prefix, one block in `review.md` that makes running it the reviewer's last act
   before the verdict, and the golden brief regenerated. This is the one that cuts rework: a
   `BOUNCE` derived after the session ended is a whole round that finds nothing.
3. **the waiver reaches the branch it applies to** — `docs_only_task` admits a direct-lane Feature,
   so a Feature whose declared `writes:` are all docs stops drawing a review row the flag was
   written to waive.
4. **the gate names the lever that is off** — `REPAIR_LEVERS`, `repair_levers`, and one clause on a
   *failing* criterion 2, so the next reader sees what to turn on without reading the spec.

They run **as one wave — all four at once**. Every `after:` is `none` and every `writes:` is
disjoint, measured below (PD1): Task 1 is `asf/scorecard/diagnose.py`, Task 2 is `asf/briefs/`,
Task 3 is `asf/harvest/lane.py`, Task 4 is `asf/release.py`, and no two share a test module either.
There is no landing order to respect because there is no shared symbol: none of the four reads
anything another adds, and `asf/scorecard/score.py` — the one module all four reason about — is
written by none of them. The Feature's own acceptance box 2 needs Tasks 2 and 3 *plus* an operator
act, and that act is a `NEEDS OPERATOR` line, not a Task.

**Read PD2 and PD3 before writing a line of Task 1 or Task 4.** The spec's design is sound and its
preconditions all hold — re-measured here, every one — but two of its snippets cannot be coded as
written: one adds a second call to a function the same function already calls (PD2), and one reads a
name that is not in scope at the point it is written, in a function whose signature twelve tests
drive directly (PD3). Neither changes the design. Both turn into a session debugging the trunk if
they are met for the first time while coding. PD4 through PD7 are four places the spec's prose,
acceptance text or Records table says something the code does not; all four are corrected here
rather than widened.

### Task 1: the diagnosis counts rework, not the planned first review
stories: S-53504
writes: asf/scorecard/diagnose.py, tests/test_scorecard.py
after: none

The spec's §1 in full: `rank`'s `by_kind` rows gain `repair_sessions`, `repair_usd` and
`repair_share`, `causes` gates and speaks on them, and `metric` answers a `kind:` cause with the
number its own threshold compares. When this lands, `asf scorecard` and `asf release-readiness`
give one answer about ADR 0003 instead of two, and a `kind:review` cause becomes a thing an operator
can close by cutting rework rather than by cutting reviews.

Read **PD2** (`rank` already calls `repair_flags` — hoist the one call, do not add a second) before
starting, and read the two measurements above it: the existing `$2.00 of $21.00` assertion survives
because `repair_* == *` for every kind but `review`, and the `precheck` invariant holds because
`repair_flags` never consults `REPAIR_PREFIXES` for a `review`.

**Files**

- `asf/scorecard/diagnose.py` — the hoisted `flags`/`pairs` pair above the per-kind loop (`:176`,
  PD2); the three new keys in the per-kind `setdefault` (`:179-180`) and the two new roundings in
  the loop below it (`:184-187`); the per-Feature pass's own `flags` line and `zip`/`continue`
  replaced by `for s, rep in pairs` (`:226-229`); `metric`'s `kind:` arm (`:253-259`); `causes`'
  `by_kind` loop (`:289-295`)
- `tests/test_scorecard.py` — `DiagnosisCountsReworkTests`, new class

**Steps**

1. Run the whole-set fence first and keep the number. It is `Ran 1104 tests` / `OK (skipped=1)` at
   `3eb5e6e60`; if yours differs, find out why before editing.
2. Hoist the flags (PD2). Above the per-kind loop: `flags = score.repair_flags(facts.sessions)`,
   then `pairs = [(s, f) for s, f in zip(facts.sessions, flags) if score.in_window(s.get('ts'),
   start, end)]`, then `sessions = [s for s, _f in pairs]` so `usd` and `minutes` are summed from
   the same list they always were. Pass `facts.sessions` — the **whole** stream, never `sessions` —
   and put the spec's precondition 2 in a comment on that line: the first review of an item may fall
   before the window, and a windowed stream would count it as the first one inside.
3. The per-kind loop reads `for s, rep in pairs`. Its `setdefault` gains `'repair_sessions': 0` and
   `'repair_usd': 0.0` beside the existing `'repair': score.is_repair(k)`, which **stays** — it is
   the kind-level fact ("could a session of this kind ever be repair") and it is what gates the
   cause. Inside the loop, `if rep:` adds one to `repair_sessions` and the session's `usd` to
   `repair_usd`. The rounding loop below gains `c['repair_share'] = round(c['repair_usd'] / usd, 3)
   if usd else 0.0` **before** `c['usd']` is rounded, and `c['repair_usd'] = round(c['repair_usd'],
   2)`. Order matters: `repair_share` divides by the unrounded `usd` total, as `share` does.
4. Delete the per-Feature pass's `flags = score.repair_flags(facts.sessions)` (`:226`) and turn its
   `for s, rep in zip(facts.sessions, flags):` with the `if not score.in_window(…): continue` two
