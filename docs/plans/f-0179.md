# Plan F-0179 — the freeze before the reader

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0179.md` (approved). Branch:
`plan/F-0179`, cut from `origin/main` at `fac479304`.

**Three Tasks, three waves, strictly sequential — and the order is inverted from the spec's own
section order, on purpose.** The spec's design reads §1 evaluator → §2 parser → §3 backend → §4
doctor → §5 freeze. Landing it in that order would put the tree, for the length of one wave, in a
state strictly *worse* than today's: §1's C3 turns `${{ vars.X || 'heavy' }}` from a guessed `heavy`
into an unresolved row, `runs_on()` does not yet pass any variables (that is §3), and the freeze
that makes an unresolved row safe is not in yet (that is §5) — so `asf ci reconcile --apply` on a
product carrying that expression would compute `heavy` as *not needed by any job* and remove it.
That is the exact irreversible write this whole card exists to prevent, arriving as a side effect of
the fix. PD1 measures it. So the freeze lands **first**, on today's `labels is None`, and everything
after it is safe.

1. **Task 1 — §4 and §5, the freeze and the row that explains it.** `RunsOn` gains `event` and
   `expr`, `parse_runs_on` keeps the raw value on an unresolved token, `unresolved`/`unresolved_rows`
   give the doctor one advisory row per unjudged job, `Step.held` and `plan`'s `frozen` stop every
   removal while one stands, and `cmd_reconcile` says so. `tests/test_ci_pool.py` gains
   `UnresolvedRows` and `UnresolvedFreezesRemovals`. `after: none` — every part of it works against
   the reader that ships today (PD2).
2. **Task 2 — §1 and §2, the evaluator, and §4's one drift change, which may not land apart from
   it.** `resolve_expr`, `event_classes`, `_Unresolved`, `_label_token` without its regex,
   `parse_runs_on(workflow, text, variables=None)` emitting one row per event class — and `drift`'s
   provider-like flag skipping a declared class label, in the same commit, because the resolver is
   what first makes `class-pr-heavy` visible to that flag (PD3). `Expressions` is new,
   `RunsOnParser` is amended, `Drift` grows three tests. `after: Task 1` — `expr`, `event` and the
   freeze are what make an expression this evaluator still refuses safe to refuse.
3. **Task 3 — §3 and §6, the repo's variables and the guide.** `GitHubBackend.variables()`, read
   once per `runs_on()` and passed to every `parse_runs_on`; `BackendReads`; and
   `docs/guide/ci-runner-pool.md` rewritten for the finished behaviour. `after: Task 2` —
   `parse_runs_on` has no `variables=` parameter until Task 2 lands, and the guide describes all
   three Tasks at once.

Wave order: **1**, then **2**, then **3**. One seat per wave. All three write `asf/ci_pool.py` and
`tests/test_ci_pool.py`, so `footprint.first_conflict` queues them whether `after:` says so or not
(PD4) — `after:` states the order honestly rather than leaving it to the queue.

Read **PD5 before writing `variables()`**: the call must be made from `runs_on()` and **not** from
`_workflow_texts()`, and it must return `None` without a `repo_slug` — a shipped test added since
the spec was written counts the calls that walk the workflow files and goes red on the third. Read
**PD6 before writing `_label_token`**: the spec contradicts itself about whether a token may resolve
to more than one label, and the card's own acceptance test needs the answer §2 gives. Read **PD7**
before `parse_runs_on`'s `expr`: the spec's sketch tests `if labels`, and `unresolved` tests
`labels is None` — for `runs-on: []` those two disagree. Read **PD8** for the three places GitHub's
own spelling is wider than the spec's grammar.
