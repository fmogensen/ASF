# B-0125 — plan: a hook that broke says so, and is never read as a refusal

Item: B-0125 — approvals hook errors look like refusals: an intermittent crash refuses ordinary
Bash. Severity S1. Epic: E-0001 — ASF 0.1 — a working factory. Branch: `fix/B-0125`.
Spec: `docs/specs/b-0125.md` — the causes under load the card asks about, and what was measured.

## Cause

`asf hook approvals` fails closed on any internal exception (F-0031 D7): a boundary that opens
when it breaks is not a boundary. But it said so in the language of policy —
`approvals hook failed: <why> — refused` — and a session cannot tell that from a deliberate
refusal. botsleon's B-1372 adjudicator, on 47c3e9d, had a read-only `ls` refused on that path and
the identical retry passed. The session spends the turn writing up a refusal that never happened,
and the hold it records is false.

Fail-closed is right and stays. What was wrong is the wording, and that nothing anywhere carried
the traceback the operator needs to find the real fault.

## Task 1 — an internal failure reports itself as an error, not a refusal

writes: `asf/approvals.py` `tests/test_approvals.py` `docs/plans/f-0031.md` `docs/specs/f-0031.md`

- Step 1: `HOOK_ERROR_LINE` — `approvals hook error: {why}; not a refusal — retry`. Distinct
  from every refusal's wording on purpose. `run_hook`'s `except` prints it instead of the old
  `approvals hook failed: … — refused`, and still returns rc 2: an error is never an allow (D7).
  `why` is `str(e) or type(e).__name__`, so a message-less exception still names its type — the
  idiom `asf/tick/step_wave.py:112` already uses.
- Step 2: `record_hook_error` puts the failure where it can be acted on — the whole traceback in
  the hook's own log (`hook_error_log_path()`, `~/.ASF/logs/approvals-hook.log`), never in the
  session's transcript; one `hook-error` line in the ledger. It never raises: the thing that
  broke is often the state directory itself, and a logger that throws makes one error two.
- Step 3: that ledger line carries no `hold` key, so `_fold` skips it and `open_holds` never sees
  it. The hook broke; the session did nothing wrong; nothing is parked and nothing relaunched.
- Step 4: `_log_traceback` rotates at `HOOK_ERROR_LOG_MAX_BYTES` (4 MiB) to `.1`, one generation,
  as `harvest.keep_red_output` does for the red gate's log. The hook runs on every `Bash`,
  `Write`, `Edit`, `MultiEdit` and `NotebookEdit` call of every session, so a systematic break
  writes a traceback per tool call; uncapped it fills the disk.
- Step 5: `raise_hook_errors(product, out)` — one `approvals hook erroring: N times in <job>`
  line per job with more than one error since the tick last said so, marked announced in the
  ledger the way a hold's is (§4). A single error is the session's own business; it was told to
  retry and did. A run of them is the operator's. Wired into the tick at
  `asf/tick/step_wave.py`.
- Step 6: every policy refusal keeps its exact current wording — `_refusal_lines`,
  `_amendable_refusal_lines`, the operator-config line, the full-suite line, the invalid-matrix
  line. None of them is touched.
- Step 7: F-0031's own Acceptance fence (`docs/plans/f-0031.md`) and §3 test list
  (`docs/specs/f-0031.md`) name `test_classifier_exception_fails_closed`, renamed here; both are
  corrected to the new id, and F-0031's D7 row amended to say what the failure now sounds like.
- Step 8: tests, in `tests/test_approvals.py`.

## Accepted costs

`raise_hook_errors` counts a job's errors over the whole ledger rather than a time window, so two
unrelated errors months apart read as one run of two. The alternative — a window on the `ts`
already recorded — needs a window length nothing else in the ledger has, and the cost of getting
it wrong is one extra tick line. Noted as I-list, not fixed here.

The line is printed before the `hook-errors-announced` marker is appended: if the append fails the
run is announced again next tick. The other order loses the announcement entirely on the same
failure. A repeated line is the cheaper loss for an S1 about things going unsaid.

The causes under load the card asks about are investigated in `docs/specs/b-0125.md` and, on the
measurements there, none of them is fixed here: the first-order cost is the hook's ~1 s import,
which is a change to how the hook is dispatched and belongs to its own card, not to an S1 about
wording.
