# Plan F-0053 — the table is the verdict

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0053.md` (approved). Branch: `plan/F-0053`.

Five Tasks, cut by the module that gains the surface, as the spec's own §2 is cut. Task 1 is the
grammar and the checklist in one pure owner (§2.1), Task 2 the pre-review command (§2.2), Task 3
the reviewer's brief and the skeleton it renders (§2.3), Task 4 the verdict derivation in the one
review reader and the passing checks on every task row (§2.4), Task 5 the round's verdict and the
acceptance tick in ingest (§2.5).

Task 1 is the owner every other Task imports, so nothing starts beside it. Tasks 2 and 4 then run
together — `asf/review_checks.py` + `asf/cli.py` against `asf/evidence/**` — and Tasks 3 and 5 last,
Task 3 because its brief prints the command Task 2 adds, Task 5 because it reads the `checks` key
Task 4 puts on a task row. Tasks 1 and 2 both write `tests/test_reviews.py`; they are already
ordered, so the queue costs nothing.

Wave order: **1 → 2 ‖ 4 → 3 ‖ 5**.

§3.7's gate binds every Task, so every Gate below runs `python3 tools/run_tests.py` and both
checkers beside its own fence.

### Task 1: `asf/reviews.py` — the check-table grammar and the checklist, in one owner
stories: S-19950, S-19951
writes: asf/reviews.py, tests/test_reviews.py
after: none

§2.1: the one thing in the factory that parses a `| check | result | evidence |` table, the one
thing that knows which checks a kind of review must cover, and the one thing that turns rows into a
verdict. Pure, stdlib, no path literal, no product name — a peer of `asf/tokens.py` and
`asf/approvals.py` (D1). Nothing imports it yet; Tasks 2, 3, 4 and 5 are its four callers.

**Files**

- `asf/reviews.py` — the module docstring, `MECHANICAL`/`STANDARD`, `PASS`/`FAIL`/`NA`,
  `APPROVED`/`CHANGES`/`BOUNCE`, `RESULTS`, `HEADERS`, `KINDS`, `Check`, `CHECKLIST`, and
  `cells`, `parse`, `normalize`, `required`, `missing`, `verdict`, `typed_verdict`, `faults`,
  `render_table`, `passed`
- `tests/test_reviews.py` — `TableTests`, `NormalizeTests`, `VerdictTests`

**Steps**

1. The module, with §2.1's docstring byte-for-byte — including "Nothing here opens a file, runs git
   or knows a path", which PD11 keeps true — and §2.1's constants, `Check` namedtuple and
   `CHECKLIST` exactly as the spec's fenced block spells them: two tuples per kind, mechanical
   first, standard second.
2. `cells(line)` — the splitter as `asf/evidence/evidence.py:356` has it: split on `(?<!\\)\|`,
   drop an empty leading and trailing cell, unescape `\|` to a literal pipe, strip each cell. This
   is the copy that becomes the original; Task 4 makes `evidence.cells` delegate to it.
3. `parse(text)` → `([Check, …], [fault, …])`. A table begins at a line whose cells, lower-cased
   and stripped of `*` and backticks, are one of `HEADERS`; the **next** line must be a separator
   (`| --- | --- | --- |`) or no table is found there at all — no rows, no fault. Rows run until
   the first line that does not start with `|`. Blocks number from 1 in order of appearance, so the
   order of the two passes is the order of the file (D3). A row whose cell count is not 3 is a
   fault naming its line, not a row. A result cell not in `RESULTS` is a fault naming its line —
   and a cell still carrying the skeleton (`<pass|fail>`, or anything holding `|` or `<`) is
   reported as **unfilled**, never as a pass. An empty evidence cell makes the row `fail` (D9).
4. `normalize(name)` — lower-case, collapse whitespace, strip backticks, `*`, a leading `-` and
   trailing `.,;:`. The one comparison used for coverage and, in Task 5, for acceptance matching.
5. `required(kind)` → the normalized mechanical names of `CHECKLIST[kind]`, in checklist order and
   none of the standard ones. `missing(checks, required)` → the required names no row covers, in
   checklist order.
6. `verdict(text, required=())` per D4: `''` when no table is present at all; `BOUNCE` when `parse`
   returned a fault or `missing` is non-empty; `CHANGES` when any row is `fail`; else `APPROVED`.
   An `n/a` row is neither a fail nor a missing check. `typed_verdict(text)` → the legacy word, a
   `verdict`-prefixed line preferred, as the shipped readers read it today.
7. `faults(text, required)` → the parse faults in line order, then one
   `required check missing: "<name>"` per missing name. `passed(checks)` → the normalized names of
   every `PASS` row. `render_table(rows)` → `| check | result | evidence |`, the separator, and one
   `| <name> | <pass\|fail> | ` per row — the escaped pipe, so the skeleton re-parses as one cell.
8. `TableTests` per §3.1: one table → three `Check`s with `block == 1`, the `\|`-escaped pipe in a
   check name unescaped, no fault; two tables under two headings → six rows, blocks `1,1,1,2,2,2`,
   file order; `| check | ok | evidence |` parses the same (D2). Then the faults, each naming its
   line number: a row of two cells; a result of `approved`; a result still reading `<pass|fail>`
   asserted as *unfilled* and asserted **not** a pass; a header with no separator under it → no
   table, no rows, no fault. A row with an empty evidence cell parses as `fail`.
   `render_table(required('spec'))` re-parses through `parse` into five rows and no fault.
9. `NormalizeTests` per §3.1: `` `The Gate commands are green.` `` and
   `- the  gate commands are GREEN` fold to the same string; `required('code')` is the six
   mechanical names and none of the standard ones; `missing` returns them in checklist order.
10. `VerdictTests` per §3.2: every mechanical row `pass` → `APPROVED`; one row `fail` → `CHANGES`;
    every row `pass` but one required check absent → `BOUNCE`; an unfilled result cell → `BOUNCE`;
    a table whose rows all read `fail` under a typed `verdict: APPROVED` line → `CHANGES`, the word
    never winning; prose with a verdict word and no table → `''` with `typed_verdict` returning
    `APPROVED` for it; `''` → `''`; `pass` and `n/a` with full coverage → `APPROVED`; a `pass` row
    with an empty evidence cell → `CHANGES`.

### Task 2: `asf review-checks` — the mechanical pre-review, and what it refuses
stories: S-19952
writes: asf/review_checks.py, asf/cli.py, tests/test_reviews.py
after: Task 1

§2.2: the command a review session runs on its own file before it forms an opinion, and the command
anyone can run on any review. It refuses a missing table outright, so nothing written under this
spec can land without one (D4), and `--kind` is required so no session ever checks a spec against
the code checklist (D5). A command, not a session kind (D10) — and a new module rather than a body
inside `cli.py`, which holds none (PD11).

**Files**

- `asf/review_checks.py` — `cmd_review_checks(args, record)`: read `PATH` as given, resolve
  `--card` when present, print, return the exit code
- `asf/cli.py` — the `review-checks` subparser beside `pr-hygiene` (`asf/cli.py:261`), and its
  dispatch arm importing `cmd_review_checks`
- `tests/test_reviews.py` — `PreReviewCommandTests`

**Steps**

1. `asf/review_checks.py`, stdlib plus `asf.reviews`: `cmd_review_checks(args, record)` reads
   `args.path` as given (the session is in its worktree — no product, no git), and on `OSError`
   prints one line to stderr and returns 2, never a traceback.
2. `--card` is a Story or Task id in the record: for `--kind code` its Stories' acceptance lines
   join the required set, so a code review that quietly dropped an acceptance line is a fault (§2.2).
   The lines come from `proves.card_bullets(root, item)` — the one parser (PD8) — normalized through
   `reviews.normalize`; a Task's card contributes the lines of every Story on its `stories:`. A
   `--card` naming nothing in the record is one stderr line and exit 2.
3. Human output is §2.2's three shapes exactly: the `== REVIEW <basename>  kind <k>, <n> checks,
   <m> faults` header, one line per `reviews.faults` entry prefixed `<basename>:<line>: ` (or
   `<basename>: ` for a missing-check line, which has no line), then the derived `verdict: <v>` line.
4. Exit 1 when there is a fault, 0 when there is none — and the green run still prints its verdict
   line, because `CHANGES REQUESTED` is a well-formed review, not a failure of the reviewer (§2.2).
5. `--json` prints `{"path", "kind", "verdict", "faults": [...], "checks": [{"name", "result",
   "evidence", "block", "line"}]}` with `sort_keys=True` — the typed output §2.2 calls the tick's.
6. The subparser: positional `path`, `--kind` with `choices=reviews.KINDS` and `required=True`,
   `--card`, `--json`. The dispatch arm resolves the record the way the record-reading commands do
   (`resolve_record(args, …)`), so `--card` works from a worktree and the no-`--card` form needs
   nothing.
7. `PreReviewCommandTests` per §3.3, through `cli.main` over files written into a temp dir with
   `ASF_HOME` pinned to it — no git, no network: a complete `pass` table with `--kind spec` exits 0
   and prints `verdict: APPROVED`; the same file with one row deleted exits 1 with a
   `required check missing:` line naming it and `verdict: BOUNCE`; nothing but prose and
   `verdict: APPROVED` exits 1 with `no check table` and `verdict: BOUNCE`; a malformed row exits 1
   naming its line number; a complete table with one `fail` exits **0** with
   `verdict: CHANGES REQUESTED`. Then `--kind code --card S-19950` over a fixture record whose Story
   has three acceptance lines requires all three, and a table missing one exits 1 naming that line's
   text. `--json` parses, has sorted keys, and its `checks` length equals the row count. A missing
   path exits 2 with one line and no traceback; `--kind` omitted exits 2.

### Task 4: the one reader derives the verdict from the rows, and every task row carries its checks
stories: S-19954
writes: asf/evidence/review.py, asf/evidence/evidence.py, tests/test_evidence.py, tests/test_review_reader.py, tests/test_pr_hygiene.py
after: Task 1

§2.4: the table decides, and the typed word only answers for a file that carries no table at all
(D4). Wired at the layer that now owns the reading rather than the one §2.4 names (PD4, PD5), with
`BOUNCE` mapped into the live two-value vocabulary so no lane branch is stranded (PD6). And the
second key §1.1 says something must carry: a task row's review currently drops the file name it
read, and ticking an acceptance line needs the path.

**Files**

- `asf/evidence/review.py` — `verdict_of(text)` deriving from the table first, `required=()`; the
  `BOUNCE → CHANGES` map; the docstring's verdict paragraph
- `asf/evidence/evidence.py` — `verdict_of(blob, legacy=True, required=())`; `cells` a one-line
  delegation to `reviews.cells`; `reviews.required(kind)` passed at the spec/plan and task lookups;
  `row["checks"]`
- `tests/test_evidence.py` — `VerdictOfTests` and `ParseRowsTests` kept and extended; the two-branch
  fixture assertions of §3.5
- `tests/test_review_reader.py` — the reader's own table cases
- `tests/test_pr_hygiene.py` — kept green, per PD4

**Steps**

1. `review.verdict_of(text, required=())`: `reviews.verdict(text, required)` first; when it returns
   `''` the present `VERDICT_LINE_RE` reading answers, unchanged. Map the result into the module's
   own vocabulary — `APPROVED → review.APPROVED`, `CHANGES` **and `BOUNCE` → `review.CHANGES`**
   (PD6) — so `VERDICTS` and every caller are untouched. `legacy_verdict_of` keeps its word
   fallback, which is what holds §3.5's `b"changes requested, see below"` case.
2. The module docstring's verdict paragraph gains the table: the rows speak first, the `verdict:`
   line answers only for a file with no table, and a bounce reads as changes. One sentence naming
   `asf.reviews` as the grammar's owner.

### Task 5: ingest sets the round's verdict from the table, and ticks the lines a code review proved
