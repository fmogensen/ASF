# B-0128 — plan: an adjudicator's 'no further sessions' ruling does not stick

Item: B-0128 — An adjudicator's "no further sessions" ruling does not stick: the lane
re-adjudicates the item. Epic: E-0001 — ASF 0.1 — a working factory. Branch: `fix/B-0128`. No
spec exists; the Acceptance below is the record.

## Cause

`correction_rows` (`asf/feeder/rows.py`) sent every held correction at `rounds >=
CORRECTION_ROUNDS` straight to `STALEMATE → ADJUDICATE`, with no memory of an adjudicate session
that already ran and ruled over that same hold. An adjudicate run never touches the branch
(`pending_correction`, `asf/workers/lifecycle.py`, already excludes `kind == 'adjudicate'` runs
from answering a correction, so its own ending does not clear the hold either) — so the very next
tick launched another paid adjudicate session over a head nothing had changed, on a loop with no
exit for any item whose last step is a merge the factory may not make itself.

## Task 1 — a settled ruling holds the lane in WAITS ON merge, not another STALEMATE

writes: `asf/workers/lifecycle.py` `asf/feeder/rows.py` `tests/test_lifecycle.py`
`tests/test_feeder.py`

- Step 1: in `asf/workers/lifecycle.py`, add `settled(path, item, at)` — true once an adjudicate
  run has *finished* (`finished(r)`, not the bare `ended` flag: a crashed, stopped or
  quota-exhausted run delivered no ruling and must not settle the hold forever) with
  `started >= at` over the correction raised at `at`. `corrections()` carries the result as a
  `settled` field per item.
- Step 2: also in `asf/workers/lifecycle.py`, add `settled_prs(path, item, at)` — the PR numbers
  (`#773`, `#775`, ...) the settling run's own REPORT `ruling:` paragraph names
  (`asf.workers.report.ruling`), in the order they first appear. `corrections()` carries these as
  a `prs` field per item — the PR-number half of the card's Want ("`asf next` shows `WAITS ON
  merge: #773, #775`") is in this Task's scope, not a follow-up.
- Step 3: in `asf/feeder/rows.py`'s `correction_rows`, when `rounds >= CORRECTION_ROUNDS` and the
  correction's `settled` is true, emit a `FIX → CORRECT` row with `action = 'WAITS ON merge'`
  (plus `: #<n>, #<n>` when `prs` names any) and `waits_on='merge'` instead of the
  `STALEMATE → ADJUDICATE` row — no launch, so the wave never relaunches a session over a settled
  hold. An unsettled hold at the round cap still gets `STALEMATE → ADJUDICATE`, unchanged.
- Step 4: tests:
  - `tests/test_lifecycle.py:289`,
    `test_b0128_an_adjudicate_run_does_not_answer_the_correction` — an adjudicate run that
    finished over a held correction settles it (`corrections()['settled']` true) without ever
    reading as `CORRECTED`; its ruling's `#773, #775` come back as `corrections()['prs']`.
  - `tests/test_lifecycle.py`,
    `test_b0128_a_crashed_adjudicate_run_delivers_no_ruling_and_does_not_settle` — an adjudicate
    run that ended `crashed` (not `finished`) does not settle the hold and names no PR.
  - `tests/test_feeder.py:688`,
    `test_b0128_a_settled_correction_waits_on_merge_not_another_adjudicate` — a settled
    correction at the round cap yields one `FIX → CORRECT` row, not `STALEMATE → ADJUDICATE`,
    with no launch.
  - `tests/test_feeder.py`, `test_b0128_a_settled_correction_names_the_prs_the_ruling_waits_on`
    and `test_b0128_a_settled_correction_with_no_pr_named_is_the_bare_action` — the row's action
    is `WAITS ON merge: #773, #775` when the ruling named PRs, and the bare `WAITS ON merge`
    when it named none.

## Acceptance

- [x] After an adjudicate ruling settles a held correction, a new review round on the same head
      does not produce `STALEMATE → ADJUDICATE` again
      (`tests/test_lifecycle.py:289`, `tests/test_feeder.py:688`).
- [x] `asf next` names the PR(s) a settled ruling waits on merge of, e.g. `WAITS ON merge: #773,
      #775` (`tests/test_feeder.py`,
      `test_b0128_a_settled_correction_names_the_prs_the_ruling_waits_on`).
- [x] A ruling that never actually finished (crashed, stopped, quota-exhausted) does not settle
      the hold (`tests/test_lifecycle.py`,
      `test_b0128_a_crashed_adjudicate_run_delivers_no_ruling_and_does_not_settle`).

## Accepted costs

The card's other half — the lane leaves `WAITS ON merge` "only when the named PR merges or
closes, or the head moves with new commits" — is not new work here: it rides on
`asf/harvest/lane.py`'s existing PR-CLOSED/merge handling and a new push answering the
correction (`pending_correction`'s later-run check), neither of which this Task changes. Review
round 1 flagged this as untraced end-to-end (its I list); it is read-existing-behaviour, not a
gap this Task opened, and is left for a follow-up look rather than re-proving pre-existing code
under this card.
