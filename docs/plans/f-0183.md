# Plan F-0183 — a runner label is judged against what the job actually runs on

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0183.md` (approved). Branch:
`plan/F-0183`.

Two Tasks, cut on the spec's own two Stories — **the reader learns to ask, then the plan learns to
refuse**:

1. **the value the host actually gives** — `Backend.variables`, `GitHubBackend.variables`,
   `_VARS_REF` and the `vars.` rule in `_label_token`, `parse_runs_on`'s `variables` argument,
   `RunsOn.needs_vars`, and `GitHubBackend.runs_on` resolving through one read whose failure is a
   reason rather than an error. After this, the incident itself is fixed: the variable is set, the
   host answers, `vendor-heavy` resolves, and the plan keeps it.
2. **nothing is removed while one reference is unresolved** — `unresolved_vars`,
   `unresolved_rows`, `Step.held` and its clause, `plan`'s three-way removal split, `drift`'s row
   and its withheld `stranded`, `doctor_rows` passing the reason, and `cmd_reconcile`'s footer.
   This closes the residual case Task 1 leaves open: a variable the host *cannot be asked* about.

They run **1 → 2**, one at a time. The order is forced twice over. By data: Task 2's every branch
reads `RunsOn.needs_vars`, which Task 1 creates — there is no `unresolved_vars` to call before it.
By footprint: both Tasks write `asf/ci_pool.py`, `tests/test_ci_pool.py` and
`docs/guide/ci-runner-pool.md` — the footprints are *identical*, so the queue serialises them
whatever `after:` says, and `after: Task 1` only names the reason.

**Landing Task 1 alone is a strict improvement, and it is not the whole card.** With the variable
readable it fixes the incident outright (PD12). With the variable *un*readable it swaps one wrong
answer for another of the same cost: today `${{ vars.X || 'heavy' }}` is judged as `heavy` and the
live label is removed; after Task 1 it is `labels is None`, the job is dropped from `jobs`, and the
live label is removed *and* the runner is called `stranded` (spec P6, re-measured in PD12). Task 2
is what turns "not judged" into "nothing is removed". Do not stop after Task 1.

**Read PD2 and PD3 before writing a line of Task 1.** The spec's §2 and §3 are written against a
`ci_pool.py` that no longer has that shape: §2's tail unpacks a branch that is still a bare `None`
and raises `TypeError`, and §3 patches a `runs_on()` body that was refactored out from under it.
Both are named below with the current code beside them.

The fences of the spec's `## Acceptance tests` bind every Task, so every Gate and Acceptance block
below carries them.

The spec's `## The design` §§4–5 and the rest of §7, and its second Story. Task 1 taught the reader
to say *I could not resolve this*; this Task is everything that listens. `plan` stops removing what
it cannot judge, `drift` stops calling a runner stranded on a job it could not read, and both name
the workflow, the job, the variable and — when there was one — the reason the variables could not
be read at all.

The two exemptions are the two removals that provably cannot strand a job, and they are not
optional: no `runs-on` may route on a `class-` label (P12), and a reserve's label is the reserve's
to place and the tick rewrites it every cycle (P11). Adds are untouched — a runner missing its role
still gets it and still starts its trial while the hold stands (C6), which is why `apply` needs no
change at all: it writes `s.remove`, and a held label is not in it.

No new flag (C11). The two escape hatches are the operator's and both fix the cause: set the
variable at repository level, or take the expression out of the `runs-on`.

**PD14** (where the rows go in `drift`, and the green summary), **PD4** (the reason string) and
