# Plan F-0033 — Dogfood end to end in CI: the factory's own loop as a test

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0033.md` (approved).
Branch: `plan/F-0033`.

Three Tasks. The spec's footprint is small and lopsided: of the four files it touches, three of
the five goldens and the whole scenario live in **one** file, `tests/test_sample_product.py`. A
cut that ignores that would produce Tasks that cannot run together anyway, so the cut follows the
file boundary rather than pretending to a parallelism the footprint refuses.

- **Task 1 — the walk.** `WholeLoopFromCardToRelease` drives `sample/` through nine ticks, plays
  each session's writes, asserts the stage ladder and the minted Task, and drops the inherited
  `GIT_CONFIG_*` that makes the module unrunnable on an operator's machine. One file.
- **Task 2 — the goldens.** The `normalise` helper and the five fixtures under
  `tests/fixtures/sample_loop/`, with the four golden tests that read them. Same file as Task 1,
  so it waits; it is a second pass over a class that must already exist.
- **Task 3 — the build says *the loop*.** The named CI step and the one line in `sample/README.md`.
  Footprint-disjoint from Task 2, but it names a test class, so it waits for Task 1.

Wave order: **1 → (2 ‖ 3)**.

Task 3 cannot start at once even though its `writes:` intersects nothing: its step runs
`python3 -m unittest -v tests.test_sample_product.WholeLoopFromCardToRelease`, and a CI step
naming a class that does not exist is a red trunk. It needs Task 1's class, not Task 2's goldens —
§3.5, its own acceptance, is a ladder assertion and the ladder is Task 1's. So it waits on Task 1
and runs beside Task 2.

Nothing in this plan changes a production code path. The spec's §1.2 refuses that outright, and
the one environment fix (§2.6) is confined to `FailurePathsBase.setUpClass` — the test's own
environment builder, not `hermetic.build`'s contract.

The change is four lines inside `FailurePathsBase.setUpClass` (`tests/test_sample_product.py:290-310`), the same file and the same method Task 1 already opens, and every scenario in the module — including Task 1's new one — fails at `setUpClass` without it on an operator's machine. Splitting it out would be a Task whose diff cannot be tested apart from Task 1's. |
| PD10 | **The existing CI step already runs the new class; the named step is still not redundant** | `.github/workflows/tests.yml:42-43` runs `python3 -m unittest -v tests.test_sample_product` — the whole module — so `WholeLoopFromCardToRelease` is in CI the moment Task 1 lands, before Task 3 exists. | PD11 | Task 1's fence is §3.1, whose text says "every golden matches" | It passes at Task 1 regardless, because Task 1 adds no golden test — there is nothing to match yet. only checkably so; each was run against the tree before being written down, because each becomes a
literal in a test. PD10 and PD11 are the two places this plan declines to overstate what a Task
buys.

### Task 1: the loop walked — nine ticks, the ladder, and a fixture an operator can run
stories: S-18050, S-18051, S-18052, S-18053, S-18058
writes: tests/test_sample_product.py
after: none

The spec's §2.2, §2.3 and §2.6. One new scenario class that drives `sample/` from its first tick
to a landed Task, playing each session's writes between ticks, and one fix to the shared fixture's
environment without which no scenario in the module runs outside CI.

**Files**

- `tests/test_sample_product.py` — three changes, all additive except the third:
  - `WholeLoopFromCardToRelease(FailurePathsBase)`, a new class after
    `FinishedWithoutPushIsCorrected` (`:467`), with the nine-tick `setUpClass` of §2.2.
  - `EXPECTED_LADDER`, a module-level list beside `RED_TEST` / `GREEN_COUNT` (`:278-281`).
  - `FailurePathsBase.setUpClass` (`:290`): the inherited `GIT_CONFIG_*` dropped from the base
    environment before `hermetic.build` is called (`:305`).

**Steps**

1. **The environment fix first** (§2.6, S-18058), because nothing else in this Task is runnable
   on an operator's machine without it. In `FailurePathsBase.setUpClass`, build the base mapping
   that is handed to `hermetic.build` as a named local, then delete `GIT_CONFIG_COUNT` and every
   key matching `GIT_CONFIG_KEY_*` / `GIT_CONFIG_VALUE_*` from it before the call. `hermetic.py`'s
   `_git_config` *appends* to whatever count it finds (`asf/hermetic.py:38-49`); dropping the
   inherited pairs is what stops an operator's `core.hooksPath` reaching the child `git` and
   making the wave's hook preflight refuse to launch. Do not touch `asf/hermetic.py`.
2. `EXPECTED_LADDER`, copied from the spec's §2.3 exactly:
   `['card', 'card', 'card', 'spec-draft', 'spec-approved', 'spec-approved', 'plan-approved',
   'building 0/1', 'landed']`. PD5 confirms `landed`, not `on-prod`, is the last entry for a
   product with no `deploy_workflow`.
3. A `stage()` classmethod: read `<cls.backlog>/index.json`, return the `stage` of `F-0001`.
   Call it after every `cls.tick()` and append to `cls.ladder`.
4. `setUpClass` walks §2.2's nine ticks. Each is `cls.script(...)` then `cls.tick()` — the base
   class's `tick()` already waits on the background harvest — and between them the test plays the
   session's writes with `cls.session_commits` / `cls.session_pushes` against
   `cls.sessions()[<job>]['worktree']`:
   - ticks 1–2: `fix-bug-b-0001` on `bugfix/B-0001`; the test commits `GREEN_COUNT` to
     `src/count.py` and a passing `tests/test_empty.py`, and pushes. Reuse `GREEN_COUNT`; the test
     it pairs with must be **green**, unlike `HeldThenCorrectedThenLanded`'s `RED_TEST` — this
     scenario is the success path and a held branch here is a failure, not a stage.
   - tick 3: `spec-f-0001` launches once the S1 lane clears; the test writes `specs/f-0001.md` —
     `sample/`'s own `specs_dir`, not `docs/specs` — commits and pushes.
   - tick 5: `plan-f-0001`; the test writes `plans/f-0001.md` carrying **one `### Task 1:` heading
     with a `writes:` line under it** (PD8). Without that line `writes_lines` returns None and the
     minted card has no footprint; without the heading `mint_plan_tasks` prints
     `has no ### Task N: heading — nothing to mint` and the ladder stalls at `plan-approved`.
   - tick 7: the coder. Read the minted Task id out of `index.json` (`type: task`,
     `parent: F-0001`) and build the job key as `f'coder-{tid}'.lower()` (PD6) — never a literal
     id, never a literal job name.
   - tick 9: no session; the tables are read.
5. `test_the_stage_ladder`: `assertEqual(self.ladder, EXPECTED_LADDER)` as a whole list, so a
   stage that repeats or never appears names its own hinge (S-18053).
6. `test_each_stage_launched_the_session_it_should`: the `launched …` line of each tick names
   `fix-bug-b-0001`, `spec-f-0001`, `plan-f-0001` and the coder job, in that order (S-18051).
7. `test_the_plan_minted_the_task_and_the_coder_took_the_code_lane`: exactly one Task child of
   `F-0001` exists, and the branch the wave chose is `feature/<that id>` — `sample/`'s own `code`
   prefix, not the default `worker/` (S-18052).
8. Run the fences. §3.4's second invocation is the one that was red before step 1: run it from a
   shell that has `GIT_CONFIG_COUNT` set, or set one by hand, so the fix is witnessed rather than
   assumed.

### Task 2: the normaliser and the five goldens
stories: S-18054, S-18055, S-18056, S-18057
writes: tests/test_sample_product.py, tests/fixtures/sample_loop/board.md, tests/fixtures/sample_loop/roadmap.md, tests/fixtures/sample_loop/scorecard.md, tests/fixtures/sample_loop/release-bug.md, tests/fixtures/sample_loop/release-task.md
after: Task 1

The spec's §2.1, §2.4 and §2.5. A second pass over the class Task 1 landed: one `normalise`
helper, four golden tests, and the five fixtures they read. This is the half of the card that
says *the stamped tables are asserted against goldens*.

**Files**

- `tests/test_sample_product.py` — the module-level `normalise(text, tmp, day, ids)` of §2.4; a
  `GOLDEN` path constant and an `UPDATE = bool(os.environ.get('ASF_UPDATE_GOLDEN'))` flag, the
  pair `tests/test_briefs.py:41` already established; the following-day rollup in
  `WholeLoopFromCardToRelease.setUpClass` after tick 9; and four tests.
- `tests/fixtures/sample_loop/board.md` — **new**: the `BOARD` table at the end of the loop.
- `tests/fixtures/sample_loop/roadmap.md` — **new**: the `ROADMAP` table.
- `tests/fixtures/sample_loop/scorecard.md` — **new**: `metrics/daily/<day>.md`.
- `tests/fixtures/sample_loop/release-bug.md` — **new**: the release note naming `B-0001`.
- `tests/fixtures/sample_loop/release-task.md` — **new**: the release note the following day's
  rollup cuts, naming the minted Task.

**Steps**

1. `normalise(text, tmp, day, ids)` — §2.4's six replacements, in an order that does not undo
   itself (the temp root before any sha inside a path, the stamp's `HH:MM` before the general ISO
   timestamp): a git sha → `<SHA>`, the temp root → `<TMP>`, today → `<DAY>` and the following day
   → `<DAY+1>`, an ISO timestamp → `<TS>`, the stamp line's `HH:MM` → `<HH:MM>`, the minted Task
   id → `<TASK>`. **Replace, never strip** — a stripped line cannot regress, and the goldens must
   still fail if a table loses its stamp line or grows a column.
2. One `_golden(name, text)` helper: under `ASF_UPDATE_GOLDEN=1` write the normalised text and
   return; otherwise read and `assertEqual`. Regenerating must produce a file identical to the one
   on disk — that is §3.2's whole point, and an un-normalised sha is what makes it fail.
3. `test_board_and_roadmap_match_the_goldens`: run `asf backlog --product sample` and
   `asf roadmap --product sample` through `cls.asf` (`asf/cli.py:146,149`), normalise each, and
   compare against `board.md` and `roadmap.md` (S-18055).
4. `test_scorecard_matches_the_golden`: read `<backlog>/metrics/daily/<day>.md`, which the tick's
   `record` step wrote — `sample/` declares `steps: {daily: off}`, so the `daily` step is not the
   source and must not be invoked (S-18056).
5. The following day's rollup, in `setUpClass` after tick 9, exactly as §2.5 specifies:
   `python3 -m asf.metrics.metrics --root <record> --product sample rollup <day+1>`. Both
   `--root` and `--product` are real arguments of that parser (`asf/metrics/metrics.py:1465-1466`),
   and the cap that makes the second run necessary is `_cut_trunk_release`'s
   `if prev and prev[-1][:10] >= day: return None` (`:1148-1150`) — one release note per day
   (PD12).
6. `test_release_notes_and_their_tags`: both `releases/<day>-<sha7>.md` and
   `releases/<day+1>-<sha7>.md` exist, both match their goldens normalised, and **both tags are
   present in the scenario's bare origin** — a release note whose tag was never pushed is a
   release that did not happen (S-18057).
7. Generate the five fixtures with `ASF_UPDATE_GOLDEN=1`, then read each one before committing:
   a golden holding a raw sha, a timestamp, a temp path or the minted id is a normaliser that is
   not finished (§2.4's last paragraph). Then run §3.2 and require `git diff --exit-code` to be
   clean (S-18054).
