# Plan F-0231 — two Tasks, a strict chain: the operator's verb first, then the lane's own drop

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0231.md` (approved). Branch:
`plan/F-0231`.

**Two Tasks, chained.** The spec's C1 rules both halves in and says *"each is a Story, each ships
and is proved on its own"*. The first half is true on its own. The second is true **given** the
first: `drop_unanswerable_corrections` calls `correction_mod.pending_jobs` (spec `## The design`
§3, line `for job, held in correction_mod.pending_jobs(path, item)`), so the lane's drop cannot be
built, let alone proved, before the module that holds that function exists. The split therefore
holds and the order is forced — not a preference (PD1).

1. **Task 1 — the operator's release.** `asf/workers/correction.py` (new), the two `asf/cli.py`
   lines, the `correction` row in `asf/surface.py` with `tests/test_surface.py`'s 49 → 50, the new
   `tests/test_correction_drop.py` carrying its base class and `DropReleasesEveryHold`, and the
   guide bullet. `after: none` — it starts at once.
2. **Task 2 — the lane's drop.** `health.branch_is_gone`, `step_health.drop_unanswerable_corrections`
   and its call site in `run`, and the two remaining test classes in the file Task 1 created.
   `after: Task 1`.

Wave order: **1**, then **2**. Their `writes:` intersect on `tests/test_correction_drop.py`
deliberately — the `after:` edge already serialises them, so the shared file costs nothing (PD1).

Read **PD4 before moving the call site** — where in `run` the drop goes is load-bearing, and the
reason is the tick's step order, not taste. **PD6 before writing a line of §3** — three tests in
`tests/test_tick_steps.py` are a live regression surface, and one guard in the spec's own body is
what keeps them green. **PD5 before writing `branch_is_gone`'s third question**, and **PD8 before
building the `BranchIsGone` fixture** — the harness the spec points at has no repo.

### Task 1: `asf correction drop <item>` releases every correction the ledger is holding
stories: S-36600
writes: asf/workers/correction.py, asf/cli.py, asf/surface.py, tests/test_surface.py, tests/test_correction_drop.py, docs/guide/operating.md
after: none

The spec's `## The design` §1 in full, its `asf/surface.py` row from `## Records`, and the guide
bullet — nothing else. After this lands, an operator holding a stale correction has a verb: one
call, every hold on the item released oldest first, one appended ledger line each, and the count
printed with whatever is still holding it named.

Three things are load-bearing, each with a precondition behind it. The holds are gathered **once,
before the first append**, and the loop walks that fixed list — not a recompute after each release,
which would make the count the operator is told a moving number. Every appended line carries the
**one** `now` and the **one** `--why` of this call, because `same_head_loop` reads "launches since
the item's latest `unparked`" as a single release (P13) — and that is why a park released here
carries `unparked` as well as `dropped` (C5): without the stamp the next tick recounts the launches
this call released and re-parks the item. And `left` is a **second read of the file** after the last
append (P5, measured: the re-fold really happens), so the report names what the next tick will see
rather than what was predicted.

Read **PD9** before adding any string literal to the new module, **PD10** before touching
`asf/surface.py`, and **PD14** before putting a single `test` method on the base class.

**Files**

- `asf/workers/correction.py` — **new**, the spec's §1 verbatim: the module docstring, the three
  imports (`datetime`, `asf.env`, `asf.workers.lifecycle`, `asf.workers.pool as pool_mod`),
  `pending_jobs`, `cmd_drop` and `register`, with their docstrings. Nothing else in the file.
  It is inside both whole-tree fences (PD9): no `STATE_WORDS` literal, no `end_reason` comparison,
  no branch prefix, document path or item id as a literal.
- `asf/cli.py` — two lines, beside `unpark`'s at `:290-291`, exactly as §1 writes them:
  `from asf.workers.correction import register as register_correction` then
  `register_correction(sub)`. `unpark`'s two lines are not moved or changed.
- `asf/surface.py` — one row in `COMMANDS`,
  `'correction': ('release a correction the ledger is holding', RECORD, None)`, in the table's
  existing order beside the other operator verbs. `VERBS` and `RENAMED` are untouched (PD10).
- `tests/test_surface.py` — the `49` at `:49` becomes `50`. The comment above it keeps saying what
  it says; only the number moves.
- `tests/test_correction_drop.py` — **new**: `class CorrectionDropHome(unittest.TestCase)` carrying

- `docs/guide/operating.md` — one new bullet after the park bullet (`:210-212`), naming

**Steps**

1. **`pending_jobs`** — §1 verbatim. Over `lifecycle.item_runs(path, item)` — the reader
   `correction_of` uses, so the command and the row it clears see the item's runs the same way, and
   a reset item's closed runs drop out for free. One entry per job, the newest `at` winning the
   dedupe, returned `sorted(..., key=lambda jc: ((jc[1].get('at') or ''), jc[0]))`: **oldest
   first**, the job name breaking a tie so the output order is deterministic.
2. **`cmd_drop`** — §1 verbatim, in that order. The `known` gate is the **raw**
