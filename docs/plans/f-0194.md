# Plan F-0194 — the CI the factory owns: the config, one run on a machine, the pass, the seam, the instruments, the page

Epic: E-0003 — ASF 0.3 — autonomous delivery. Spec: `docs/specs/f-0194.md` (approved). Branch:
`plan/F-0194`.

**Six Tasks, five waves.** The spec's own §*The design* is the split, almost: one new module
(`asf/ci_vm.py`) and one edit each in eight existing files, with nothing downstream of the
`(state, detail, checks)` triple learning a new shape. What the spec does not settle is the
*order*, and the order is not free here — every Task writes `asf/ci_vm.py` and
`tests/test_ci_vm.py`, so no two footprints can be disjoint and `after:` is the honest answer
rather than a wider wave (PD14). The chain is: the config a product can hold, then a sha that
actually runs on a machine, then the three ways the pass is reached, then the seam the lane
judges through, then the capacity and the doctor, then the badge and the page.

Each Task lands something whole. After Task 1 a product file can *say* `ci.provider: vm` and be
refused for every way of saying it wrong. After Task 2 a sha runs on an ssh-reachable machine and
comes back with an exit code and forty lines. After Task 4 a vm product's lane judges red and
green with no call to the code host at all.

**Read PD1 and PD2 before writing a line of the judging seam (Task 4).** They are the two places
the spec's own code snippets, taken byte for byte, produce the opposite of what their own prose
says: `trunk_red`'s replacement marks every *concluded* trunk check red, green ones included, and
`red_evidence`'s new clause puts every passing check's log into a correction body. **Read PD3
before Task 4** — it names a helper (`evidence._trunk_shas`) that does not exist in this tree.
**Read PD4 before Task 2** — the store shape the spec's Records section lists cannot express the
one rule C10 says matters more here, not less.

Every anchor the spec cites was re-read in this worktree at `b21116e00`, fourteen commits past
the spec's own `7fbbfdba9`. **Every precondition still holds; four files moved their line
numbers** (`asf/capacity.py`, `asf/ci_pool.py`, `asf/ci_queue.py`, `asf/evidence/evidence.py` —
the five files carrying the load-bearing anchors, `asf/harvest/lane.py`, `asf/env.py`,

| PD1 | **`trunk_red_at`'s docstring and the `trunk_red` snippet that calls it contradict each other, and the docstring's reading marks every green trunk check red** | The spec's §4 surface says `trunk_red_at(product, sha, names)` returns *"``({name: red}, complete)`` … the names of ``names`` with a concluded row here and whether every one of them had one"* — a dict and a bool. The snippet in the same section is `red.update({n: sha for n in found}); left -= set(found) \| complete`, which needs `found` to be an iterable of **red names only** and `complete` to be a **set**. Iterating the documented `{name: red}` dict yields *every concluded name*, so a sha whose `gate` passed and whose `lint` failed would be recorded `{'gate': sha, 'lint': sha}` — the trunk read as red on a check that passed, which holds every branch behind a trunk-red that is not there. And `set(found) \| complete` with a bool `complete` raises `TypeError`. Settled: **`trunk_red_at(product, sha, names) -> (red, concluded)`, two `frozenset`s** — `red` is the subset of `names` whose concluded row at `sha` is red (PD4), `concluded` is the subset with any concluded row at all (red *and* green). The call site is then exactly today's semantics: `red.update({n: sha for n in red_here}); left -= concluded`. `set(red_here) \| concluded` is redundant once `red ⊆ concluded` is the contract, and the contract is the right one — a name is discarded from `left` when its verdict is known, which is what `left.discard(name)` does at `lane.py:3614` today after `done` is non-empty, *before* redness is tested. Note the one asymmetry that must be preserved: today's walk `break`s out entirely when `self._trunk_runs[sha] is None` (the read failed, `:3607`). Under `vm` the store read cannot half-fail — an unreadable store is `(frozenset(), frozenset())` at every sha, the walk runs its five commits finding nothing and returns `{}`, which is "not red", which is what P5's last sentence says unreadable must mean. Do **not** add a `break`. |
| PD2 | **`red_evidence`'s new clause must be guarded by `c.get('name') in red`, and must be placed before the `link`/`_JOB_RE` lines — the spec's snippet is guarded by neither** | The spec's §4 gives `if c.get('log'): out.append(…); continue` and calls it *"one clause at the top of its loop"*. Read as written it emits a log tail for **every** check dict that carries one, and under `vm` every check dict carries one — so a correction raised for a red `gate` would be handed the passing `lint`'s last forty lines too, and a branch red on one job would get a body containing every job's output. `red_evidence`'s own docstring is *"per ``red`` check"*, and today's loop enforces it at `lane.py:3707`: `if c.get('name') not in red or not m: continue`. Settled, the clause is placed as the loop's **first two statements**, before `link = c.get('link') or ''`: `if c.get('name') in red and c.get('log'): out.append(f"\n{c.get('name')}: {c.get('host') or 'vm'}\n" + '\n'.join(c['log'])); continue`. Placement before `link`/`m` is load-bearing and is why the clause cannot simply be appended: a vm check's `link` is `''` (C1's own key list), so `_JOB_RE.search('')` is None and the existing `continue` at `:3707` fires first — a clause added after it is dead code, and a vm product's correction would carry `''`, which is the exact defect C11 says must not be reintroduced by omission. |
| PD3 | **`evidence._trunk_shas(product)` does not exist — the trunk shas `ci_green_runs` hands `green_trunk_shas` come from one bounded `git log`, written in `ci_vm`** | The spec's §4 `ci_green_runs` clause is `return ci_vm.green_trunk_shas(product, _trunk_shas(product), ci_vm.required_names(product))`. `grep -n 'trunk_shas' asf/evidence/evidence.py` is empty in this checkout: there is no such function, and the name is free. The two candidates already in `evidence.py` are both wrong to reach for: `main_commits(product)` (`:1031`) is a full `git log --name-only` over every trunk commit since the record's first, which is a tree walk to answer a question about twenty shas; `ancestry(product, …)` answers containment, not enumeration. Settled: `ci_vm` owns its own reader, `trunk_shas(product, limit=GREEN_TRUNK_LIMIT, run=subprocess.run)` → `git -C <product.repo_dir> rev-list --first-parent -n <limit> origin/<product.main>`, `[]` on any failure, with `GREEN_TRUNK_LIMIT = 20`. Twenty is not arbitrary: it is exactly what today's `ci_green_runs` reads (`gh run list … --limit 20`, `:1006`), so a vm product's prod-deploy candidate window is the same depth as a gh-actions product's and the switch C11 protects stays a config change. `--first-parent` matches `trunk_red`'s own walk (`lane.py:3595`) so both readers of trunk history agree on what "the trunk's commits" are. The `ci_green_runs` clause is then `return ci_vm.green_trunk_shas(product, ci_vm.trunk_shas(product), ci_vm.required_names(product))` and `evidence.py`'s diff is the four lines of the clause and nothing else. |
| PD4 | **The row carries one key the spec's Records list omits — `ever_red` — because C10's B-0129 rule cannot be expressed in one row per (sha, job), and the pass never re-dispatches over a concluded row** | C10 is explicit: *"Keeping the B-0129 rule (a sha with a red attempt is red even if a retry went green) matters more here, not less"*, and `AsChecks`/`VmChecks` bind it (*"a sha with one red attempt stays red beside a green retry"*). The store the spec specifies is `runs[sha][job]` → **one** row, whose keys are `state, host, run_id, pid, branch, attempt, started, ended, exit, log, superseded_by`. A second attempt overwrites the first, so a green retry erases the red it overturned and the fenced assertion cannot even be *constructed* — there is nowhere to put the earlier verdict. Two ways out; the one chosen is the smaller. **Rejected:** making `runs[sha][job]` a list of attempts, which changes `rows_at`'s `{job: row}` contract and with it `checks_at`'s "one check dict per row", `in_flight`'s count and every fixture. **Chosen:** the row gains `ever_red: bool` — set True at conclusion whenever the concluding state is in `RED_STATES = (FAILED, TIMEOUT, CANCELLED)`, never cleared, carried across a re-dispatch at the same sha. `trunk_red_at` reads `row['state'] in RED_STATES or row.get('ever_red')`. It costs one key, no contract moves, and the assertion becomes a two-line fixture. Note what makes this cheap rather than load-bearing: **the pass itself never re-dispatches over a concluded row** — §5 step 4 dispatches *"every job with no row at it"*, so under the pass's own operation `attempt` is always 1 and `ever_red` always equals `state in RED_STATES`. The key exists for the one path that can produce attempt 2 — an operator clearing a row to force a re-run — and it is precisely that path B-0129 is about. `checks_at` does **not** read `ever_red`: a PR's checks are the verdict at the head now, and a re-run that went green is a PR that may merge. Only the trunk walk is sticky, which is the asymmetry B-0129 itself describes. |

### Task 2: a sha runs on an ssh-reachable machine and comes back — the transport, the three remote scripts, the store, and the pass that dispatches, collects, supersedes, times out and prunes
