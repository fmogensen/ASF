# Plan F-0042 — six Tasks: the probe, the command, the operator-owned rule, the day, the doctor, the installer

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0042.md` (approved). Branch:
`plan/F-0042`.

Six Tasks in four waves. The Feature has two independent roots and they are genuinely independent:
the credential probe (`asf/credentials.py`, new) and the `owner:` field on a rule card
(`asf/rules/rules.py`, `asf/tick/file_bugs.py`, `asf/record/new.py`). Neither reads the other's
code, their footprints do not intersect, and either one is useful alone — so they start together.
Everything after them converges: the command needs the probe, the day needs both, the doctor needs
the cache, and the installer needs all of it.

Wave order: (1, 3) → 2 → (4, 5) → 6

| wave | Task | what it is | after |
|---|---|---|---|
| 1 | Task 1 | the probe, its verdict, and `credentials:` in both config files (§2.1, §2.2) | none |
| 1 | Task 3 | `owner:` on a rule card — no Bug, one line a day (§2.7) | none |
| 2 | Task 2 | `asf credentials check` — the cache, the table, `--json`, `--quiet` (§2.3) | Task 1 |
| 3 | Task 4 | the daily part, its events, and no token anywhere (§2.6, §2.4) | Task 2, Task 3 |
| 3 | Task 5 | the doctor's `credentials` row (§2.5) | Task 2 |
| 4 | Task 6 | `asf credentials install` — the card and the script (§2.8) | Task 3, Task 4 |

Tasks 1 and 3 share no path. Tasks 4 and 5 share no path — that is deliberate (PD9), and it is
what makes wave 3 two coders rather than two handoffs. Every other pair that intersects is
ordered by `after:`, never left for the queue.

§3's preamble binds every Task: every block runs from this repo's root, the new module is
stdlib only (`subprocess`, `json`, `datetime`, `shlex`, `re`, `dataclasses`), every test is
hermetic — no network, no real `~/.ASF`, no operator keychain, every fixture pointing `ASF_HOME`
and the product's `state_dir` at a tmpdir, and every probe a fake `run` or a `bash -c` the test
writes itself. No test names a vendor, a worker account or a machine path: a provider is
`provider-a`, an account is `lane-1` (`tools/check_generic.sh`, `tools/forbidden-names.txt`).
Each Task's **Acceptance** carries the §3 fences its Stories name, copied byte for byte, plus the
whole-suite fence, which this product's external CI runs on the pull request and no session runs
on this host (the standing rule).

Stated because a coder looking for a rule dict inside `cmd_check`'s json branch will not find one. |
| PD6 | **The `NEEDS OPERATOR: ` prefix goes on the printed line only; the `line` field stays unprefixed** | `file_bugs.rule_violation_signatures` reads `v['rule']` and `v['line']` and puts the line into a Bug's evidence; `rule_of(line)` splits on the first space. A `line` field beginning `NEEDS OPERATOR:` would make `rule_of` return `NEEDS`, and would put the prefix inside the ledger's stored `lines` and inside `report_operator_rules`' own output, which adds its own prefix — `NEEDS OPERATOR: NEEDS OPERATOR: R-nnnn …`. So the prefix is applied in `cmd_check`'s human branch at print time and nowhere else. |
| PD7 | **The providers are probed in parallel, or the rule check times out before it can report** | `rules.TIMEOUT` is 60 s (`asf/rules/rules.py:28-38`) and `run_check` kills the script at it; `PROBE_TIMEOUT_S` is 20 s. Three providers probed one after another is up to 60 s inside a 60 s budget, four is 80 s — the script is killed, `run_check` returns a *check failure*, and after three runs the operator is raised about a broken check instead of an expired credential. That is the exact inversion D10 exists to prevent, arriving by wall clock. So `check()` probes with a `concurrent.futures.ThreadPoolExecutor`, the same idiom and the same `MAX_WORKERS = 8` bound `rules.run_all` already uses (`:169-183`) — the wait is a subprocess wait, so threads are the right tool — and the worst case is one `PROBE_TIMEOUT_S`, not N of them. D6's cache makes this rare; it does not make it safe, because the one run per hour that does probe is a tick. |
| PD8 | **A `broken` probe is never written into the cache** | D6's second sentence is the load-bearing one: "the window arithmetic is recomputed from the cached expiry each run, so a credential ticking into its last three days is caught without a probe." If a `broken` result overwrote its provider's entry, it would overwrite `expires` with `''` — and D3 makes an empty expiry `unknown`, which *passes*. A provider whose probe breaks for an hour would therefore stop being watched for that hour, and one whose probe breaks the day before it expires would go quiet exactly when the line was due. So `write_cache` keeps the previous entry for any provider whose new result is `broken`; the broken state is reported from this run's results (it is what makes `--quiet` exit 2) and is not remembered. The next run re-probes, because no fresh entry was written — which is also what makes D10's three-runs-in-a-row count advance. |
| PD9 | **The doctor's row reads the cache through a function Task 2 exports, so Task 5 never opens `asf/credentials.py`** | §2.5 says the row is a view: "from the cache (never a fresh probe)". Task 2 therefore exports `read_cache(product)` → `{name: Result}` alongside `cache_path(product)`, and Task 5's `check_credentials` composes it with Task 1's `for_product`, `config_problems`, `verdict` and `days_left` and adds nothing to the module. That keeps Task 5's footprint to `asf/doctor.py` and `tests/test_doctor.py`, which is disjoint from Task 4's, which is why wave 3 is two Tasks and not two waves. §3's requirement that "the row runs no probe (a counting fake `run` stays at zero)" is then structural: the row has no `run` to pass. |
| PD10 | **The once-a-day key is the rule card's own id, and the daily part raises its line through `report_operator_rules` rather than a second copy** | D11 requires one key so the line prints once whichever of the two runs first. But the daily part does not know a rule id — it knows a product and a list of providers, and §2.6 step 4 says only "the shared ledger". Two writers keying differently (`R-nnnn` from the rules row, `'credentials'` from the day) is two lines on every day the daily step runs, which is the duplicate D11 forbids. So: `report_operator_rules(violations, ledger, day, out=print)` is Task 3's, it takes violations in the `--json` shape (`[{rule, line, owner}]`), and Task 4's daily part calls **that function** with a rule id it resolves from the record — the live rule card whose `check:` basename is `credentials.sh` (`credentials.rule_id(root)`), falling back to the literal key `'credentials'` when no such card is installed. One function, one ledger shape, one key. Before the operator installs the card the rules row contributes nothing at all (there is no card to run), so the fallback key can never collide either. |
| PD11 | **An unrecognised `owner:` is reported by `rules.py`, not by `asf check`, and the plan says why** | §2.7 says a bad value is "read as `'factory'` and reported by `asf check`, so a typo never silences a rule". The substance is already delivered by the default: a typo makes the rule factory-owned, so its violation files a Bug exactly as it does today — nothing is silenced, and that is what the sentence is for. The report is visibility, and it has no home in `asf/record/check.py`: there is no rule-card field table there to extend (`enforced:`, `scope:` and `reason:` are not validated there either — `SETTABLE['rule']` in `asf/record/new.py:20` is the only field list, and it gates `asf set`, not the card), so putting the first one there would invent a validator this spec did not ask for and would need its own copy of `OWNERS`. So `cmd_check` prints `R-nnnn owner: 'oprator' is not one of ('factory', 'operator') — read as factory` under the `== RULES` table and `--json` carries `owner_unknown: [{rule, value}]`. Exit code unchanged: a typo is not a violation. `asf/record/check.py` is in no Task's `writes:`. |

### Task 1: the probe, its verdict, and `credentials:` in both config files
stories: S-29550, S-29551
writes: asf/credentials.py, asf/env.py, tests/test_credentials.py, tests/test_env.py
after: none

§2.1 and §2.2. The module and its two data classes, the config readers and their problem lists,
the one function that runs a probe, and the arithmetic that turns a result into a verdict. No CLI,
no cache, no table, no tick wiring — nothing in this Task has a caller outside its own tests, and
that is intentional: it is the surface Tasks 2, 4, 5 and 6 are written against.

**Files**

- `asf/credentials.py` — **new**. Module docstring: what a provider is, that a probe is read-only
  and never prints a token, and that its contract is the rule contract. Then:
  - `PROBE_TIMEOUT_S = 20`, read through a `_timeout()` helper so `$ASF_CREDENTIAL_PROBE_TIMEOUT`
    overrides it, in the shape `asf/rules/rules.py:28-38` already uses (a bad value falls back to
    the default rather than raising at import). `DEFAULT_WINDOW_DAYS = 3`,
    `DEFAULT_PROBE_EVERY = '1h'`, `DETAIL_MAX = 160`.
  - `Provider` and `Result`, frozen dataclasses, exactly the fields §2.1 gives them —
    `Provider(name, probe, renew, account='', window_days=DEFAULT_WINDOW_DAYS)` and
    `Result(provider, state, expires='', detail='', probed_at='')`. `Result.state` is one of
    `'valid' | 'invalid' | 'broken'`; a `STATES` tuple names them so no string is typed twice.
  - `providers(cfg)` → `{name: Provider}` from `cfg`'s `credentials.providers` map, each provider
    taking `window_days` from its own entry else `credentials.window_days` else
    `DEFAULT_WINDOW_DAYS`. A missing or misshapen `credentials:` section is `{}`, never a raise:
    the problem list is where a bad section is reported, and the doctor is what reports it.
  - `probe_every(cfg)` → seconds, from `credentials.probe_every` through `_seconds('<n>s|m|h|d')`;
    an unparseable value falls back to `DEFAULT_PROBE_EVERY` and is named by `config_problems`.
  - `config_problems(cfg)` → `[(dotted key, problem)]`, every problem §2.1 lists: a provider with
    no `probe:`, one with no `renew:`, a `window_days` that is not a positive integer, a
    `probe_every` that is not `<n>s|m|h|d`, an `account:` that `pool.accounts_from_config(cfg)`
    does not name, and a `renew:` that `redact.default_patterns(None)` matches, reported as
    `credentials.providers.<name>.renew: carries a secret-shaped value — put the secret in a file`
    (§2.4's last bullet, byte for byte). Sorted by dotted key, so the doctor's row is stable.
  - `product_problems(value)` → `[(dotted key, problem)]` for a product file's `credentials:`
    value: not a list, an entry that is not a non-empty string, or a duplicate name. `None` is no
    problem — a product that names none is a product with nothing to check.
  - `for_product(product, cfg)` → the `Provider`s the product names, in the product's own order.
    A name `credentials.providers` does not define raises `env.ConfigError` with exactly
    `product.yaml credentials: <name> is not a provider in config.yaml credentials.providers`.
  - `probe_env(provider, cfg, product)` → the environment the probe runs under (D5, PD13). With
    `provider.account`: the account of that name out of `pool.accounts_from_config(cfg)` and a
    synthetic `runtime.Job(product.name, 'credential-probe', product.repo_dir, None, None,
    account=acct, product_auth_env=env.product_auth_env(product))` through `runtime.build_env`.
    Without one: `hermetic.worker_base()`. Either way `GIT_TERMINAL_PROMPT=0` is set last, so a
    credential the session cannot reach fails at once instead of hanging on a prompt.
    `runtime.AuthEnvError` propagates — `run_probe` is what turns it into a `broken` result.
  - `run_probe(provider, env_map, now, run=subprocess.run)` → `Result`. The command is
    `shlex.split(provider.probe)`, run with `env=env_map`, `capture_output=True`, `text=True`,
    `timeout=PROBE_TIMEOUT_S`. rc 0 → `valid`, rc 1 → `invalid`; any other rc, `OSError`,
    `subprocess.TimeoutExpired` or `runtime.AuthEnvError` → `broken`. `probed_at` is `now`
    rendered `%Y-%m-%dT%H:%M:%SZ`.

    `DETAIL_MAX` characters with a trailing `…`; and puts that in `Result.detail`. Nothing else in
    this module, and nothing in any Task below, ever sees the raw streams — they are local
    variables of this function and are not returned, logged, printed or stored. The scrub is
    applied before the truncation, so a secret cut in half is still redacted whole.
  - `_expires(line)` → the expiry parsed out of that same line with
    `^\s*expires[:=]?\s+(never|<ISO-8601>)\s*$`, case-insensitive, re-rendered as an ISO-8601

    scrub, so a probe that prints a token beside its expiry still contributes a timestamp, and the

## What the operator does once the six Tasks have landed

Nothing in this plan writes operator config, and nothing in it signs in for anybody. After Task 6:

1. Add the `credentials:` section of §2.2 to `~/.ASF/config.yaml` — one entry per provider, with
   its read-only `probe:` command and the exact `renew:` command, and `account:` when the
   credential belongs to a worker account rather than to the factory's own environment.
2. Add `credentials: [<provider>…]` to each `~/.ASF/products/<p>.yaml` that needs one.
3. Run `asf credentials install --product <p>` and commit the two files it names — the rule card
   into the record, `rules/credentials.sh` into this repo. Both are in the amendable set, and this
   is the step no session may take.
4. `asf doctor` for the `credentials` row, and `asf credentials check` for the table.

Until step 3 the rules row carries no credentials rule and the daily part keys its line on the
literal `credentials` (PD10) — the day's line still prints, and the tick's `RULES` table is silent
because there is no card to run. Until steps 1 and 2 every part of this Feature is a no-op and
every fence is still green: a product that names no provider has nothing to check.
