# Plan F-0065 — seven Tasks: build the instrument, prove the fence is on, then read it three times

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0065.md` (approved). Branch:
`plan/F-0065`.

Seven Tasks. Two of them land together and the other five are a chain, because a spike's shape is
not the code's shape: the instrument (`probe.sh`, `fixture.sh`, `collect.py`, `settings/*.json`,
`session.sh`) can be built in two parallel pieces, but every measurement after it reads the same
document and each one's result decides whether the next is worth launching.

**The wave order is: wave 1 = Task 1 ∥ Task 2; then 3 → 4 → 5 → 6 → 7.** Task 1 is the probe set
and the fixture product — the instrument's reading end (§2.1, §2.4). Task 2 is the collector and
the settings templates — the instrument's recording end, including the one thing the spec insists
happens before anything else is trusted, reading the harness's own settings surface and refusing a
guessed key (§2.5, §3.10). Task 3 is `session.sh`, which needs both (§2.2). Task 4 is the cheapest
and most decisive measurement, in the order D7 fixes it: is the fence on at all, does it survive
`bypassPermissions`, and does a proxied egress need names `hermetic.WORKER_ALLOW` strips (§3.4,
§3.5, §3.9). Task 5 is the coder's table, the long one. Task 6 is the reviewer's and the prober's.
Task 7 closes the document — three settings blocks, the adoption list, the deletion line, and the
two checks that no account name or machine path reached a tracked file (§2.7, §2.8, §3.7, §3.8).

Tasks 4–7 all write `docs/research/sandboxed-worker-shell.md`, and all four carry
`tools/spike/f-0065/**` besides: a measurement Task that finds the instrument wrong fixes the
instrument in the Task that found it, rather than reporting an `error` row as a finding (§2.1 says
`error` is never read as a finding). Those footprints intersect by construction, so the chain is
declared on `after:` rather than left for the scheduler to discover (PD1).

The spec's §3 fences are copied byte for byte into each Task's **Acceptance**. Three of them launch
real sessions, cost money, and need the account's runtime credential; §4's `NEEDS OPERATOR` is
reproduced at the foot of this plan with a session count, because the count is a plan-level fact
the spec does not carry.

No file under `asf/` or `tests/` changes in any Task (§1.2), so no Task's Gate runs
`python3 tools/run_tests.py`: `tools/run_tests.py` discovers `tests/test_*.py` only
(`tools/run_tests.py:63-72`) and this Feature adds none. Every Task's Gate is its own §3 fence plus
`bash tools/check_generic.sh`, which scans **every tracked file** — including the spike's — against
`tools/forbidden-names.txt`.

| PD4 | **A tracked settings file cannot carry a real path, so `settings/<role>.<variant>.json` is a template and `session.sh` renders it** | Two facts collide. (a) The sandbox's filesystem grants are absolute paths — `<repo>/.git`, `<state>/<product>`, `<home>/.local/bin` (§2.5) — and none of the three is knowable at commit time. (b) `tools/check_generic.sh` delegates to `asf.redact --tree`, which scans **every tracked file** against `tools/forbidden-names.txt`, and that file's patterns include the operator's own account name; a state-dir path under `$HOME` would fail §3.8 on the first run. So the tracked file is a template whose paths are `${REPO}`-shaped placeholders, and `session.sh` expands it into `<state>/spike/f-0065/settings/<role>.<variant>.json` — untracked, real paths, the path actually handed to `--settings`. §2.2's "`--settings settings/<role>.<variant>.json`" names the template, not the argument. The `<…>` slots of §2.5 are a different thing entirely and are still forbidden (D2, §3.10): a placeholder for a *path this host supplies* is legitimate; a placeholder for a *key name nobody read off the harness* is the thing the spike exists not to do. `collect.py --surface` therefore reads keys out of the tracked template and must accept `${…}` in a value while refusing `<…>` in a key. |
| PD5 | **`session.sh` builds its environment through `asf.workers.runtime` and `asf.hermetic`, never by hand** | This is the largest risk in the Feature and the spec does not name it. A session launched by hand in the operator's shell is measured against the *operator's* environment, and every row of every table is then a measurement of something the factory never runs. The worker environment is not a subset of the operator's: `runtime.build_env` (`asf/workers/runtime.py:363-392`) puts the session under its own HOME (`session_home`, `:121`), sets `CLAUDE_CONFIG_DIR` to the account's config dir, filters through `hermetic.build(..., mode='worker')` down to `WORKER_ALLOW` (`asf/hermetic.py:63-66`) plus the job's passthrough, sets `core.hooksPath` from `job.hooks_dir`, and installs git's credential helper for the code host from `GH_TOKEN` (`git_credential_config`, `:344-351`). `session.sh` constructs a `runtime.Job` and calls `runtime.build_env` and `runtime.build_command` (`:98-110`) — imported from the package, not reimplemented — and differs from `Runtime.run` in exactly three declared ways: cwd is the fixture worktree, `--settings` is the rendered leg file (PD4), and the brief on stdin is `roles.block(roles.load(<role>), cap)` plus the tail that runs `probe.sh`. Anything else it copies is a place the measurement can silently diverge from production. Being a shell script (§2.2) does not change this: the environment is produced by a `python3` heredoc inside it, so the file count stays four. |
| PD6 | **The account's own user settings file is a second settings layer, and a leg is void until it is proved clean** | `hooks.install` writes the `approvals` `PreToolUse` entry into every worker account's *user* settings file, product-less and unconditionally (`asf/hooks.py:11-13`, `:317-319`), and `build_env` points `CLAUDE_CONFIG_DIR` at that account's config dir. So every leg the spike launches — including `off` — already has a settings file the spike did not write, merged under its `--settings`. If a sandbox key were ever set there, `off` and `bare` would not differ and D3's whole pair discipline would read green on a fence that was always on. `session.sh` therefore reads `hooks.account_settings_path(account)` before each launch and refuses the leg if it carries any key the surface reading (§3.10) identified as a sandbox key, naming the file. This also settles what `off` *is*: not "no settings file", but "the same file with the sandbox block absent". |
| PD7 | **Under `-p` an invalid settings file is silently ignored, so `session.sh` validates the rendered file itself** | P11 is the reason every row is a pair (D3), but the pair only catches the failure *after* two sessions have been paid for. The rendered leg file is machine-produced from a template, which makes a JSON syntax error unlikely and a *semantic* error — an unrendered `${REPO}`, an empty grant array, a key the surface reading did not list — the realistic one. `session.sh` `json.load`s the rendered file and refuses the launch when any value still matches `${…}` or any top-level key is not in the surface's key list. That is a launch-time refusal costing nothing, in front of a failure mode whose only other detector costs a session. It does not replace the pair: the pair is what proves the harness *honoured* the file, which no amount of local validation can show. |
| PD8 | **`P09` runs the fixture product's test command, not this repository's** | §2.1's `P09` row is "the product's test command", and the spec's own §1.2 forbids any change under `tests/`. Read as this repository's suite it would be `python3 tools/run_tests.py`, ~325 modules and several minutes inside a metered session, measuring nothing the probe is about — the probe wants exec, a `TMPDIR` write, and a git fixture with its own `hooksPath` (§2.1). Stated so a coder neither contorts the spike to satisfy a check that does not apply to it nor commits a machine path to one that does. |

### Task 1: the probe set and the throwaway fixture — fourteen probes, one line each, and the product they run against
stories: S-31350, S-31351
writes: tools/spike/f-0065/probe.sh, tools/spike/f-0065/fixture.sh
after: none

§2.1 and §2.4. The instrument's reading end: a script that asks fourteen questions and prints
fourteen lines, and the throwaway product that gives five of them something to ask. Nothing here
launches a session and nothing here reads a log — the whole Task is provable on the host,
unsandboxed, which is also the control column (§2.1).

**Files**

- `tools/spike/f-0065/probe.sh` — **new**. `probe.sh <role>`: runs that role's probes only, per
  §2.1's `role` column. Each probe prints exactly one line,
  `PROBE <id> <ok|refused|error> <at most one line, no secret value>`, and nothing else on stdout.
  The three verdicts are kept apart deliberately: `refused` is the fence saying no, `error` is the
  probe itself broken (a missing binary, no fixture, no credential), and the two are never
  collapsed. **The script's exit status is always 0** — a probe that aborts the script loses every
  row after it, and a lost row is indistinguishable from a passing one in the log.
  - `P00` (all) — write `$HOME/.f0065-control`, a write outside every grant. The first control.
  - `P01` (all) — a TLS connection to a host no grant names. The second control.
  - `P02` (coder, reviewer) — edit a tracked file in the worktree: a write inside cwd.
  - `P03` (coder, reviewer) — `git commit -s --allow-empty`: a write to
    `<repo>/.git/worktrees/<job>` and `<repo>/.git/objects`, plus exec of the hook directory under
    the state dir (P5, P8). The spec's own prediction is that this is what breaks first.
  - `P04` (coder, reviewer) — `git ls-remote origin` against the **real** product's remote (§2.4):
    DNS, TLS, and a read of `<repo>/.git`.
  - `P05` (coder, reviewer) — `git push --dry-run origin HEAD:refs/heads/<scratch>`: the same plus
    the credential helper's own shell exec reading `$GH_TOKEN`
    (`asf/workers/runtime.py:283-291`, `:344-351`). `--dry-run` negotiates refs and leaves no ref
    behind (D5).
  - `P06` (coder, reviewer) — the code host's API CLI, its rate-limit endpoint: TLS to the API
    domain and a read of the CLI's config under the session HOME (P7).
  - `P07` (all) — the factory CLI, one read-only view: exec of `<home>/.local/bin/asf`, a symlink
    out of the worktree (`asf/workers/runtime.py:250`), and a read of `$ASF_HOME`.
  - `P08` (all) — a `Bash` call the approvals matrix classifies, so the hook writes its ledger row:
    a write under `$ASF_HOME/state/<product>` by a hook, not by the model (`asf/hooks.py:319`,
    `asf/approvals.py:519-524`). §2.1 says why this is the probe with the worst failure mode: the
    hook fails closed, so a refused ledger write can refuse the call that triggered it, and a
    session whose every classified call is refused does nothing and reports nothing.
  - `P09` (coder, reviewer) — the **fixture** product's test command (PD8): exec, a `TMPDIR` write,
    and a git fixture with its own `hooksPath`.
  - `P10` (coder) — dependency installation inside the session: TLS to the package registry, a
    write to the package cache under HOME, a write in the worktree.
  - `P11` (coder) — the headless browser engine: launch, load `about:blank`, print the engine's
    version, exit. Exec from its cache under HOME, its child processes, its own inner sandbox.
  - `P12` (coder) — the development server: bind a loopback port, fetch it in the same session,
    stop it.
  - `P13` (prober) — read the brief from the state dir and write the named side file: a read under
    `<state>/<product>/briefs`, a write at the one path the brief names.
  - No probe prints a token (§4). `P05` and `P06` authenticate through the existing helper and the
    existing environment variable and print only a status; anything a probe's output carries
    towards a file follows the shape of `asf.workers.runtime.mask` (`:354`).
- `tools/spike/f-0065/fixture.sh` — **new**. Builds the fixture product under the state dir and
  outside every repository (§2.4), prints its path, and is idempotent — a second run reuses what is
  there. It creates: a git repository with one commit and an `origin` pointing at a bare repository
  beside it, so `P03`'s commit and a local ref negotiation work with no host involved; a package
  manifest with exactly one dependency, so `P10` fetches from a real registry into a temporary
  cache and installs into no real tree; a one-script development server that binds a loopback port
  and answers one path (`P12`); a headless-browser script (`P11`); and a one-line test command that
  execs, writes under `TMPDIR` and uses the fixture's own `hooksPath` (PD8, `P09`). **The browser
  engine's own download happens here, outside any session** — deliberately, because that is what
  the tick already does for `worktree_setup` (`asf/workers/spawn.py:619-664`, called at `:697`),
  and separating it is what tells the adopting card which half of "dependency installation" needs a
  grant at all (§2.4).

**Steps**

1. `fixture.sh` first: nothing in `probe.sh` can be run until there is a product to run it against.
   Write it to be re-runnable from the start — every leg of every later Task calls it.
2. `probe.sh` next, one probe at a time, each verified on the host before the next is added. The
   invariant to hold while writing: one line per probe, stdout carries nothing else, exit 0 always.
   A probe that needs a credential the host does not have prints `error` with the reason and does
   not abort.
3. Run the whole set for each of the three roles on the host and read every line. On the host,
   unsandboxed, `P00` and `P01` **must** read `ok` — they are the two things a fence turns over, and
   a control that is already `refused` here is a broken probe, not a fence (§3.2).
4. Check the two scripts against `tools/check_generic.sh`: no account name, no machine path, no
   product name. Paths to the state dir and the repository are derived at run time, never written
   in (PD4, PD9).

**Gate**

```bash

for r in coder reviewer prober; do bash tools/spike/f-0065/probe.sh "$r"; done

```


```bash

```

```bash

```

### Task 2: the fence's own settings surface, read off the harness, and the collector that refuses a guessed key
stories: S-31352
writes: tools/spike/f-0065/collect.py, tools/spike/f-0065/settings/**
after: none

§2.5, §3.10, and the whole of `collect.py` (§2.2, §2.3, D12). This is the Task D2 is about: the
sandbox's key names are the spike's **output**, not its input. P12 says this build of the harness
exposes no sandbox flag and this repository holds no example settings file, so every key in every
template below is read off the harness before it is written, and `collect.py --surface` is the
check that none was guessed.

**Files**

- `tools/spike/f-0065/settings/<role>.<variant>.json` — **new**, one per pair leg. The variant
  vocabulary is fixed by §2.2: `off` (no fence — the control column, and the leg that proves the
  probes work), `bare` (the fence on, nothing granted), `grant-<n>` (`bare` plus exactly one
  grant), `mode-bypass` / `mode-default`, `grant-net` / `grant-net-passthrough`. Each file is
  JSONC in §2.5's shape, with two departures from the spec's sketch, both PD4:
  - every **key** is a real key read off the harness — no `<…>` slot survives this Task;
  - every **path value** is a `${REPO}`-, `${STATE}`-, `${HOME}`- or `${TMPDIR}`-shaped placeholder,
    because a tracked file may carry no machine path (`tools/check_generic.sh` scans every tracked
    file). `session.sh` renders these in Task 3.
  - each key carries a `//` comment naming where in the harness it was read from; `--surface`
    prints that provenance, which is what makes §3.10's output a record rather than a list.
  - Each `grant-<n>` leg adds **exactly one** entry over `bare` (§2.5), so the pair that flips a row
    names one grant and not a bundle. The grants the slots call for: the gitdir and object store
    under `<repo>/.git` (P5); `<state>/<product>` for hooks, briefs and the ledger (P8, P13, P14);
    `<home>/.local/bin` for the factory CLI symlink (P7); `$TMPDIR` (P9); the code host, the host's
    API domain and the package registry (P04, P05, P06, P10); loopback (P12).
- `tools/spike/f-0065/collect.py` — **new**, whole. Reads the stream-json logs, pulls the `PROBE`
  lines out of the assistant's own tool results, pairs the legs, and prints markdown. Its modes,
  all of them used by a later Task's fence:
  - `--surface` — one line per key any `settings/*.json` uses, with where in the harness it was
    read from. **Exits 1 while any key is still a `<…>` slot** (§3.10). A `${…}` in a *value* is
    legal and is not a slot (PD4). `--surface --json` emits the same as a dict.
  - `--role <r> [--leg <v>] --require-control` — checks the two control rows **before anything else
    is printed**. `P00 ok` or `P01 ok` in a leg whose settings say the fence is on means the
    settings file was ignored (P11); the collector exits non-zero naming the leg, and no table is
    produced from that run (D4, §2.3).
  - `--pair <leg> <leg> --probe <id>…` — the A/B reading: the probe's verdict in each leg, and for a
    `refused` leg the fence's own reason string, verbatim, capped to one line.
