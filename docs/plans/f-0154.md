# Plan F-0154 — six Tasks, one wave: one workflow's runs, four per-pass snapshots, and the two places the spec's own design costs more than it saves

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0154.md` (approved). Branch:
`plan/F-0154`.

**Six Tasks, one wave.** The spec's five items touch five disjoint parts of the tree and none reads
another's code: the flaky pass, the health pass's `git status`, the record's card parse, the lane's
git facts, and the batched reads. Story 5 is delivered by two Tasks rather than one, because its
three call sites sit in two unrelated modules with two unrelated test modules (PD13). Every
`writes:` set is pairwise disjoint, so nothing queues behind anything, and every Task is
`after: none`.

1. **Task 1 — the flaky pass asks one workflow for its own runs.** `asf/tick/flaky.py`,
   `tests/test_flaky.py`. `after: none`.
2. **Task 2 — one `git status` per worktree per version of that worktree.**
   `asf/workers/lifecycle.py`, `asf/workers/health.py`, `tests/test_lifecycle.py`. `after: none`.
3. **Task 3 — a card is parsed once per version of its text.** `asf/record/core.py`,
   `asf/record/frontmatter.py`, `tests/test_record_cache.py`. `after: none`.
4. **Task 4 — the lane's git facts, keyed on the shas they were read from.** `asf/harvest/lane.py`,
   `tests/test_lane.py`. `after: none`.
5. **Task 5 — the ingest's document lookups become one batch.** `asf/evidence/evidence.py`,
   `asf/record/ingest.py`, `tests/test_evidence.py`. `after: none`.
6. **Task 6 — the plan readers' per-plan reads become one batch each.** `asf/record/plan_order.py`,
   `asf/record/plan_tasks.py`, `tests/test_plan_order.py`, `tests/test_plan_tasks.py`.
   `after: none`.

Wave order: **(1, 2, 3, 4, 5, 6)** — one wave. Verified through the record's own readers:
`asf.tick.migrate.plan_task_records` returns `T1`…`T6` with the titles below, `writes_lines` reads
each `writes:` line back as its path list, pairwise disjoint, and `plan_order.task_order` returns
`{1: [], 2: [], 3: [], 4: [], 5: [], 6: []}` (PD15).

**Two findings change what a Task must build, and both are measured, not argued.**

**Read PD1 before writing a line of Task 5.** D12 as written — warm `DocCarriers` "from the
`links.spec` and `links.plan` of every card in `canonical`" — costs **6.39 s** in one process at
this record's real scale. The whole §5 item is worth about 8 s. Scoped to the paths the code can
actually ask for, the same warm costs **0.73 s**. The literal reading is a pessimization that would
eat the card.

**Read PD2 before touching `asf/workers/health.py` in Task 2.** The spec places the
`WorktreeStatus` "beside the `RemoteHeads` it already builds at `:810`". Seven of the nine `gather`
sites run *before* that line, inside `run_steps` at `:795`. Built where the spec says, the snapshot
serves two call sites out of nine and the Story does not land.

**Read PD5 before writing `frontmatter.clone`** — it is the one place in this card where a cache can
silently change what the record *writes*. **PD7 before `collect`'s window** — the existing fake
carries no `created` key. **PD3 before threading anything into `publish_gap`.**

| PD3 | **`publish_gap` takes the snapshot through the lambda that already wraps it, not through the generator's yielded tuple** | The publish seam is `run_steps([...], lambda *args: publish_gap(*args))` at `health.py:795-796`. The generators yield a 5-tuple `(product, run, ev, reason, alive)` — from the `steps` closure at `:719` and from `republish_steps` at `:529` — and `run_steps` calls `publish(*ask)` (`:488`, `:491`). **Decided:** the lambda becomes `lambda *args: publish_gap(*args, status=status)`. Widening the tuple to six was the alternative and it is the trap: it would touch two yield sites, `run_steps`'s unpacking and every test that `send()`s into the protocol, for nothing. `file_review` (`:363`) and `republish_steps` (`:510`) are called from the `steps` closure directly, so each gains a `status=None` keyword and is passed the closure's snapshot at the call site. |
| PD4 | **The publishes run on three threads, and `_groups` proves no two of them ever share a worktree — the snapshot needs no lock** | `run_steps` uses a `ThreadPoolExecutor` with `PUBLISH_WORKERS = 3` (`health.py:424`, `:468`) and maps `publish` over the asks of different groups at once (`:491`). So `WorktreeStatus.lines` will be entered from three threads. `_groups` (`:427-457`) is a union-find that unions any two runs sharing a **branch**, an **item** or a **worktree** (`lifecycle.path_key(wt)`), and `run_steps` drives the runs of one group strictly one after another. Two asks in flight at the same instant are therefore from different groups, and two runs in different groups share no worktree — which is the same guarantee the function's own docstring states for evidence and publishes. **Decided:** a plain dict, no lock. The worst case if that guarantee were ever broken is two threads computing the same key and one overwriting the other with an equal value — a duplicate `git status`, never a wrong answer, because the key carries the mutation evidence. Do **not** add a `threading.Lock`: it would serialise the publish phase this factory deliberately parallelised. State the reason in the class docstring so the next reader does not add one. |
| PD5 | **`clone` must rebuild the `_Entry` list over the copied containers, because today `e.value is meta[key]` and `render` replays the raw line when the two are equal** | **Measured**, by parsing a card with a nested `links.runs: [1, 2]` and a `tags: [a, b]` and round-tripping it: `entries['links'].value is meta['links']` → **True**; `entries['tags'].value is meta['tags']` → **True**; and after `meta['links']['runs'].append(3)`, `frontmatter.render(meta, body)` reproduces the **original** text byte for byte — the in-place mutation is silently dropped, because `render` compares `current == e.value` (`frontmatter.py:322`) and they are the same object. `parse` makes them the same object deliberately: `entries.append(_Entry('dict', key, subdict, raw)); meta[key] = subdict` (`:263-264`), and the same for `'list'` (`:236`) and `'scalar'` (`:283`). **The hazard:** a `clone` that copies container values into the new dict but shares the cached `entries` breaks that identity. The clone's `meta['links']` and `e.value` become different objects, so an in-place mutation makes them unequal, so `render` renders the key **canonically** instead of replaying its raw line. That is a change to what the record *writes to a card*, introduced by a cache, in the module the groom writes through. **Decided:** `clone` builds a fresh `_Entry` for every entry, whose `value` **is** the copied container it put in the dict — so `e.value is meta[key]` holds in a clone exactly as it holds in a fresh parse, and `render(clone(meta), body)` is byte-identical to `render(parse(text)[0], body)` for a mutated clone as well as an unmutated one. Scalars and `raw`/`kind`/`key` are shared; they are immutable. **Nothing in `asf/` depends on today's drop**, which is what makes this a preservation rather than a choice: no caller mutates a nested container in place (searched across `asf/` for `['meta'][…][…]` and for `.append`/`.update`/`.setdefault` on a meta value — no hit). `migrate.py:428` builds a **new** `merged_links` and rebinds `rec['meta']['links']`; `groom.py:513` and `:557` rebind a top-level key; `ids.py:73`, `new.py:163`, `migrate.py:407` and `:464` reassign `machine_keys`. ### Task 3: a card is parsed once per version of its text, and every caller is still handed its own copy
stories: S-36752
writes: asf/record/core.py, asf/record/frontmatter.py, tests/test_record_cache.py
after: none

The spec's `## The design` §3 in full, and nothing else. After this lands, the record step's

**Read PD5 before writing a line of `clone`.** It is the one place in this card where a cache can
change what the record *writes*. `parse` makes `e.value` and `meta[key]` the **same object** for
every list and dict value (`frontmatter.py:236`, `:263-264`, `:283`), and `render` replays a key's
original raw line when `meta[key] == e.value` (`:322`). A clone that copies the containers into the
dict but shares the cached `entries` breaks that identity, and an in-place nested mutation then
renders canonically where today it renders the original line. `clone` must build **fresh `_Entry`
objects over the copied containers**, so the identity holds in a clone exactly as in a fresh parse.
**PD6** is why that rebuild is one comprehension and not a `deepcopy`.

Two things are load-bearing besides. **The cache is validated by content, not by mtime** (D9):
`load_items` must read the file anyway, because the record it returns carries `text` — with the read
already paid for, content equality has no staleness window at all, and there is nothing for a coarse
filesystem clock or a same-nanosecond rewrite to defeat. `_REGISTRY_CACHE` (`lifecycle.py:305-363`)
already made this choice for this reason and is the shape to copy (P8). **A parse error is not
cached** (§3): a file that fails to parse is reported on every call, as it is now.

stories: S-36753
writes: asf/harvest/lane.py, tests/test_lane.py
after: none

The spec's `## The design` §4 in full, and nothing else. After this lands, the second and later
questions about one branch cost one `rev-parse` each instead of a `diff` (`touched_files`), a `diff`
(`already_on_trunk`) or five processes (`own_commits`).

The whole decision is D11, and it is about invalidation. **The key is the resolved sha of each ref,
so nothing is ever invalidated and nothing has to be.** The lane fetches, rebases, rewrites and
archives branches mid-pass; an `invalidate()` the lane must remember to call after each is a defect
waiting for the one path that forgets. A moved ref is a different key. **A ref that does not
resolve bypasses the cache entirely** and calls through, exactly as today.

**Read PD9 before writing the docstrings.** A cache *miss* costs one process more than today,
because `own_commits` keeps its own `rev-parse --verify` and `touched_files` keeps its own `diff`.
The win is entirely on the repeats — which is what the profile measured: 450 diffs, 270 cat-files
and 225 rev-lists per tick, nearly all of them the same question about the same unmoved branch.
Claim that, not a saving on the first call.

**Files**

- `asf/harvest/lane.py` — beside the three functions: `_FACTS = {}`, `_FACTS_MAX = 512`,
  `_ref_shas(repo, trunk, branch)` returning `(trunk_sha, branch_sha)` in **one** `git rev-parse
  origin/<trunk> origin/<branch>` or None when either ref does not resolve, and `clear_facts()`.
  `touched_files` (`:351-355`), `already_on_trunk` (`:841-858`) and `own_commits` (`:476-517`) keep
  their signatures, their return shapes and their bodies; each resolves the pair first, returns the
  stored answer on a hit, and on a miss does exactly what it does now and stores it.
  `already_on_trunk`'s key carries `item` and the deliverable path as well, because its answer
  depends on them (`deliverable_of`, `:834-839`) — and so does the `files=` it was handed, which is
  what the caller at `:1336-1337` passes. `own_commits` stores the whole `(base, shas, why)`
  triple, **refusals included**: a branch with a merge on it is refused for the same reason every
  time it is asked, until someone rewrites it and the key changes. Nothing else in the module moves

- `tests/test_lane.py` — one new class, `RefShaCache`, over a real fixture repo with `lane.H.sh`
  counted. The cases §3.4 names: `touched_files` twice for one branch runs **one** `diff` and two
  `rev-parse`s and returns equal lists; a new commit pushed to the branch makes a second `diff`

  `already_on_trunk` for the same branch but a different `item` is a separate entry; `own_commits`
  twice runs its five processes once and returns the same triple, refusal included, for a branch
  with a merge on it; and a branch name that does not resolve is answered uncached, with the same
  return value as today, as many times as it is asked. `clear_facts()` empties the store.

**Steps**

1. **`_ref_shas` and the store.** One process for both refs. A non-resolving ref returns None and

2. **`touched_files`.** The smallest of the three; get the key shape and the eviction right here and

3. **`already_on_trunk`.** Its key is wider: the two shas, `item`, the deliverable path, and the

   answers for the same branch (`:846` passes none, `:1337` passes the list it read at `:1336`), so
   they must not share an entry.
4. **`own_commits`.** Store the triple whole, refusals included. Do **not** feed the key's resolved
   sha in as `tip` to save the internal `rev-parse` — PD9, and §3.4's counts assume the internals
   are untouched.
5. **`clear_facts`**, then the new test class. Count with `lane.H.sh`, not by eye. It does not
   subclass another test class (PD12).
6. Run the Gate. `tests.test_lane` **166** plus the cases you added, `tests.test_doc_lane_landing`
   **12** and `tests.test_direct_lane` **27** unchanged — those two are the regression surface for
   the six callers at P9.

**Not in this Task** — every other Task's footprint. `lane.changed_lines` (`:357`),
`lane.item_on_trunk` (`:860`) and `Lane.merges_clean` (`:1461`) — **O3**: they read the same refs
