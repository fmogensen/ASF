# Plan F-0099 — the groom runs on the tick clock

Epic: E-0002 — ASF 0.2 — self-improvement. Spec: `docs/specs/f-0099.md` (approved). Branch: `plan/F-0099`.

Eight Tasks, cut along the spec's own footprint table (§2.10) by the thing that changes: the step
and the clock it runs on (Task 1), the day file (Task 2), the questions in it (Task 3), intake
(Task 4), the adjudicate round (Task 5), the card's own end-to-end test (Task 6), the measure
(Task 7), and the doctor line that says a step is on no clock (Task 8).

The spec was written against a tree that had already moved: the hotfix `1fb04d1` landed a partial
every-tick groom — `step_daily.groom_every_tick`, a `cmd_groom(incremental=True)` path, a
`merge_groom_text`, an `adjudicate_per_day` cap and `groom_state['new']` — and the spec names none
of it. PD4, PD5 and PD6 below are where this plan meets that tree; each says what the hotfix built,
what §2 replaces it with, and which Task does the replacing. No scope is added: every one of them
is a section of the spec, met where it actually lands.

Five of the eight write `asf/groom/groom.py` or `tests/test_groom_every_tick.py`, so they queue.
That is the honest order and also the dependency order — the step must exist before the file it
writes is made additive, and the questions must be asked before a round can be cut over them.

Wave order: **1 ‖ 7 → 2 ‖ 8 → 3 → 4 → 5 → 6**.

§3's rule that the whole suite stays green binds every Task, so every Gate below runs
`python3 tools/run_tests.py` beside its own fence.

**Steps**

1. `cmd_groom`'s apply block gains 2b: today's `groom/<date>.md`, read and applied through
   `apply_groom_answers` exactly as the previous day's is, under the same `args.apply` gate. Both
   are idempotent (spec P3), so applying both every tick costs a re-read and writes nothing twice.
2. `merge_day_file(existing_text, sections)` per §2.4's docstring: answered lines of `existing_text`
   first in their own order; then the question text `existing_text` carries for a question
   `sections` still asks, slot reset to `____`; then `sections`' new questions appended to their
   section. A question nobody answered that `sections` no longer asks is dropped.
3. The token a line is matched by: the item id, the `inbox:<file>` token, or
   `shape.proposal_key(verb, ids, areas)` for a proposal — the key `apply_proposal` already records
   a decline under, so a re-proposed merge is the same question. `_LINE_TOKEN_RE` is extended, not
   replaced.
4. The four states of §2.4's table are read off the answer slot: `→ answer: ____` (open, with or
   without a `(barred: …)` mark) and `(spoken for: …)` are re-derived; anything else is an answer
   and is kept verbatim for the rest of the day. The `(spoken for: …)` and `(barred: …)` marks are
   never kept — they are statements about now (§1.4).
5. The single write path: `render_groom_file` → `merge_day_file` against the file on disk (when one
   exists) → write → `apply_groom_answers` on what was written. `_write_incremental` and the
   `incremental` flag are deleted, and `step_groom.run`'s call becomes §2.1's fence (PD5).
6. `--rebuild`: the merge keeps answered lines verbatim and re-renders every other line from the
   record, dropping the "keep the question text" half of step 2.
7. The digest: `write_digest` renders, strips the stamp line from both sides, compares, and returns
   without touching the file when they match.
8. `ApplyTodayTests` and `MergeDayFileTests` per §3/T4 and §3/T5, including the `filecmp.cmp(...,
   shallow=False)` pair, the third run that appends exactly one line, the closed card that loses
   its open line and keeps its answered one, and `--rebuild`.
