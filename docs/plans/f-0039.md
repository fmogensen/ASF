# Plan F-0039 — the findings go back to the session that wrote the thing

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0039.md` (approved). Branch: `plan/F-0039`.

Seven Tasks, cut along the spec's own §3: one Task per fenced acceptance, because §3 is already
the footprint. The runtime's half (Task 1), the rule (Task 2), the message (Task 3), the wave
(Task 4), the fallback (Task 5), the metric (Task 6) and the surfaces (Task 7).

Every one of §3's fences names a class in **one** file, `tests/test_continuation.py`, byte for
byte. Six of the seven Tasks therefore write that file and queue behind one another (PD11). That
is not an accident of the cut — it is also the dependency order, since the rule cannot be asked
before the id it reads is recorded, and the wave cannot continue before there is a message to
send. The honest wave order is a single file at a time.

Wave order: **1 → 2 → 3 → 4 → 5 → 6 → 7**. By landed-code dependency alone, 5 and 6 need only
Task 4 and 7 needs only Task 3; the shared test file serialises them.

§3.7's `python3 -m unittest discover -s tests -v` binds every Task, so every Gate below runs
`python3 tools/run_tests.py` beside its own fence. §3.7 also names `tools/check_conventions.sh`
for a reason this plan takes seriously (PD3): every path in `asf/workers/continuation.py` comes
off `conventions`, and the module owns exactly one constant, `DEFAULT_HEARTBEAT_MIN`.

| # | Question | Decided |
|---|---|---|
| PD1 | How the work is cut | One Task per fenced acceptance in the spec's §3, in §3's order. Each Task's Gate is its own fence plus the whole suite (`python3 tools/run_tests.py`) and the two check scripts. No Task invents an acceptance the spec does not carry. |
| PD2 | Task card ids | Not minted here. `asf.record.plan_tasks.mint_plan_tasks` turns each `### Task N:` heading of the landed plan into a card with an id from `asf.record.ids.mint_id`, so this plan's headings are the parser's ordinals `1…7`. This session's `BACKLOG_ID_RANGE` (`T:16900-16949`) is therefore unused; no id is invented. |
| PD3 | Which Story is which | The spec's `## Stories` bullets are bare `- S:`; the ids live in its frontmatter (`stories: [S-15350 … S-15356]`). The mapping is positional, first bullet to first id: S-15350 the recorded id, S-15351 the `--resume` command and the seam, S-15352 the rule, S-15353 the message, S-15354 the wave, S-15355 the fallback, S-15356 the metric. |
| PD4 | **`derive_kind('correct-f-0039')` returns `code`, not `other`** | §1.1, §1.4 and §3.6's parenthetical all say a `correct` session derives to `other` today. It does not. `KIND_PREFIXES` (`asf/metrics/metrics.py:40-45`) has no `correct` pattern, `derive_kind` falls through its loop and returns its default, `'code'` (`:165`). So a fixer session is not merely uncounted today — it is counted as a **coder**, inflating the code figure by exactly the number this Feature exists to reduce. | PD5 | **The `sessions` stream schema must gain `resumed`, or every session event raises** | §4 says the stream event carries `resumed` beside `session` and never says the schema gains the key. `metrics._apply` refuses an event with a key the schema does not hold — `raise SchemaError(f"{where}: unknown key(s) …")` (`asf/metrics/metrics.py:143`) — so `session_event` emitting `resumed` without `SCHEMAS['sessions']['resumed'] = (('str', 'null'), None)` would break the rollup for every session, continued or not. Task 6 adds the schema key in the same diff as the field. This implements §4; it widens nothing. A consequence worth stating: the default fills `resumed: null` on every line, so "`resumed` is absent" in §2.7 means falsy, and the `fixers` row counts it that way. |
| PD6 | **A continuation runs on the writer's account, not a fresh pool pick** | `--resume <id>` resolves a transcript, and a transcript lives in the account's own config dir: `runtime.build_env` sets `CLAUDE_CONFIG_DIR` from `Account.config_dir` (`asf/workers/runtime.py:124`) and `hermetic.build` gives the account its own home. A continuation handed a different account would resume nothing. So `continuation.continue_run` does not call `pool.pick_account`: it reads `run['account']` off the writer's ledger line and resolves that name through `pool_mod.Pool.from_config`. This is also what makes §2.5's own sentence true — a continuation takes no pool slot beyond the row's own, because it takes the slot the writer already had. An account that is no longer in `worker_pool.accounts` is one more `(None, why)` from `resumable`: `account <name> no longer in the pool`, and the row falls back in the same tick. |
| PD7 | What the continuation's ledger line carries from the writer, and what is its own | The writer's: `job`, `worktree`, `branch`, `log`, `id_range`, `account`, `product`, and — the whole of acceptance #3 — `session`. Its own: `pid`, `pgid`, `started`, `brief`, `resumed`, `continued: 1`. And `kind` is the **row's** `brief_kind`, not the writer's: §2.7 reads a continuation as "a session of `kind: fix` carrying `resumed`", which for the code lane requires the line to say `kind: correct` so `RECORD_KINDS` can map it. §4's example is the doc lane, where the row kind and the writer's kind are both `spec` and the question does not arise. |
| PD8 | How the worktree is rebased | By calling `spawn.make_worktree(product, run['job'], branch)` — the writer's job name, so it resolves the writer's own worktree — not by a second rebase written into `continuation`. That function is P3's path exactly: an ended run's worktree reused as it stands, rebased onto the fetched trunk, and published by the factory when the rebase moved a branch origin already holds (B-0056). It carries `lifecycle.may_launch` and `hooks.ensure_git_hooks` with it, so a continuation cannot reach a live run's worktree or a repo whose push gate is missing. §2.4's prompt promises the session "your own branch …, rebased onto origin/main before this message"; this is the one function that makes the promise true. |
| PD9 | **What "the runtime declined" can mean for a detached launch** | §2.2 says a `continue_run` returns `None` for "a `Popen` that raises, or a process that exits non-zero before writing an `init` line". Only the first is reachable on the real path: `ClaudeCodeRuntime.run(wait=False)` returns as soon as `detach.spawn` returns (`asf/workers/runtime.py:200`) and cannot know what the child then did. So `ClaudeCodeRuntime.continue_run` returns `None` when the spawn itself raises, and the second clause is reachable under `wait=True` — which is `FakeRuntime`'s path and §3.5's fifth case, where it is asserted. A resumed process that dies before its `init` line is caught on the next tick by health, exactly as a failed launch is, and the correction is still unanswered (P4), so the next tick falls back. Nothing is widened: the seam, the reason string and the fallback are the spec's; only the tick it lands on differs for that one case, and this row is where it is said out loud rather than implied. |
| PD10 | The id range is the writer's, not a new reservation | `spawn.reserve_id_range` is not called by a continuation and `release_id_range` is not called either. The conversation already holds the range it was given, and a second reservation would let one session mint cards from two ranges — which is how two Tasks come to share an id. The ledger line repeats the writer's `id_range` so the run is readable on its own. |
| PD11 | `tests/test_continuation.py` is written by six Tasks | §3's fences name `tests.test_continuation.RuntimeTests`, `.RuleTests`, `.PromptTests`, `.WaveTests`, `.FallbackTests`, `.MetricTests` and `.SurfaceTests` byte for byte, so all seven classes live in one file and every Task that adds one writes it. They queue. No class is added without the code it covers landing in the same diff, and no Task edits another's class. |
| PD12 | **The review path is derived, never written** | §2.4's illustration names `docs/reviews/1-f-0039-review-r1.md`; under the default `review_pattern` (`{reviews_dir}/{n}-{slug}.md`, `asf/conventions.py:52`) with `slug = item_id.lower()` the same file is `docs/reviews/1-f-0039.md`. | PD13 | **Which round `continuation` reads, and why not `collect`'s** | `preamble.collect` points an answer kind at round N and a writer kind at N+1, but `ANSWER_KINDS = ('fixer', 'adjudicate')` (`asf/briefs/preamble.py:136`) — a `spec` row is a writer kind, so `collect` would hand a continued `spec` row round **N+1**, the file nobody has written. `continuation.target` derives N itself from `feeder_rows.review_round(feature)` (`asf/feeder/rows.py:162`, which already returns `(doc, round)` off a `spec-review r2` stage) and `collect` is left untouched — §1.4's ruling, met where it actually lands. |
| PD14 | Task 5 writes only a test | §2.5's fallback is the `if why:` branch of Task 4's diff and lands with it. §3.5 is the card's second acceptance over five separate causes, and giving it its own Task keeps that proof from being marked done by whichever Task happens to land last. Its diff is one file (the precedent is F-0099's Task 6). |
| PD15 | Task 7 carries S-15352 | §3.7's `SurfaceTests` covers `asf brief --continue`, which prints the rule's decision and, when there is none, the rule's reason. That is the operator-facing half of S-15352 — "One rule decides whether a session may be continued, **and names the reason when it may not**" — so the Story is carried by both the Task that builds the rule and the Task that exposes it. ### Task 1: the runtime's own session id, recorded — and a job that carries a `resume`
stories: S-15350, S-15351
writes: asf/workers/runtime.py, asf/workers/health.py, asf/workers/lifecycle.py, tests/test_continuation.py
after: none

§2.1 and §2.2. The id the coding-agent CLI has been writing into every log's `init` line is read
for the first time and recorded on the run beside its `ended` line; `Job` gains a `resume` field,
`build_command` the flag, and `Runtime` the `continue_run` seam that a runtime which cannot
continue declines. No decision is made here and nothing calls `continue_run` yet — this Task is
the half of the spec that is pure mechanism, and everything after it reads what it writes.

**Files**

- `asf/workers/runtime.py` — `init_line(log_path)` and `runtime_session(log_path)` per §2.1's two
  docstrings, the same rewinding scan `read_result` makes (`:147`); `Job.__init__` gains
  `resume=None` (`:30`); `build_command` gains the one clause after `-p --permission-mode`
  (`:77`); `Runtime.continue_run(job)` returning `None` with §2.2's docstring (`:179`);
  `ClaudeCodeRuntime.continue_run` (`:186`); `FakeRuntime`'s `init` line gains
  `session_id: fake:<job>:<n>` (`:236`) and `FakeRuntime.continue_run` (`:214`).
- `asf/workers/health.py:304` — the `update_session` that writes the `ended` line also writes
  `runtime_session=runtime_mod.runtime_session(s.get('log')) or None`, per §2.1's fence.
- `asf/workers/lifecycle.py:82` — `RUN_FIELDS` gains `runtime_session`, `resumed` and
  `continued` (§4): they belong to one run and must never fold into the next (P2).
- `tests/test_continuation.py` — **new**: `RuntimeTests` (§3.1).

**Steps**

1. `init_line(log_path)`: the last run's `system`/`init` record, or `None`. One pass over the
   file, holding the newest `init` seen and discarding it at the next — the shape `read_result`
   already uses, so the two agree on where a run begins (P1). A missing file is `None`, not a
   raise.
2. `runtime_session(log_path)`: `init_line`'s `session_id`, else `''`. The docstring says what
   `ASF_SESSION` is and is not (F-0076, D1): ours, a launch, not a conversation.
3. `Job.resume` defaults to `None`, so every existing construction is unchanged;
   `build_command` emits `['--resume', job.resume]` directly after `-p --permission-mode <m>`
   and before `--add-dir`, so `tests/test_workers.py:104`'s golden stays byte-identical for a
   job with no `resume`.
4. `Runtime.continue_run(job)` returns `None` on the base class — a runtime that cannot continue
   declines, and the caller falls back (§1.2). This is the whole of the remote seam.
5. `ClaudeCodeRuntime.continue_run(job, wait=False)` is `run(job)` with `job.resume` set; a
   `Popen`/`detach.spawn` that raises returns `None`, and under `wait=True` a process that exits
   non-zero having written no `init` line returns `None` too (PD9). It writes no
   `_session_line`: the continued run is the writer's session, and a second `asf` session line
   would claim otherwise.
6. `FakeRuntime.run` writes `'session_id': f'fake:{job.name}:{n}'` into its `init` line, `n`
   counting the runs it has replayed for that job — so every test below exercises the real read
   rather than a stub. `FakeRuntime.continue_run` replays the next scripted step and appends a
   second `init`+`result` pair to the **same** log, and records the call in `calls` as
   `(job, message_text)`. A scripted step carrying `{"decline": true}` returns `None`, which is
   §3.5's fifth case.
7. `health.health` per §2.1's fence — one keyword on the `update_session` already at `:304`, in
   the same pass, so an ended run carries the id from the moment it is ended and no second write
   is needed.
8. `RUN_FIELDS` per §4. `_clean` already drops a run field written as null (`:156`), so a run
   that never recorded an id carries no key rather than a null one.
9. `RuntimeTests` per §3.1: `init_line`/`runtime_session` over a log with one run, with two runs
   (the second `init`'s id wins — P1), with a run that has no `init` line (`''`) and over a
   missing file; `build_command` golden with `resume=None` (asserted byte-identical to
   `tests/test_workers.py`'s list) and with `resume='abc'`; `Runtime().continue_run(job)` is
   `None`; `FakeRuntime.continue_run` appending a second pair to the same log, after which
   `read_result` returns the **second** run's result and `runtime_session` the second run's id;
   `health.health` writing `runtime_session` on the `ended` line; and `lifecycle.fold` **not**
   folding it into the next launch (P2).

```sh
python3 tools/run_tests.py 2>&1 | tail -3
```

### Task 2: the rule — who may be continued, and the reason when they may not
stories: S-15352
writes: asf/workers/continuation.py, tests/test_continuation.py
after: Task 1

§2.3. One module answers *may this row be answered by continuing a session* — one rule, one
reason string, three readers (the wave, `asf brief --continue`, and the tests). It makes exactly
one git call, and it makes no decision the feeder could have made, because the feeder may read
neither the ledger nor git (P5).

**Files**

- `asf/workers/continuation.py` — **new**: the module docstring, `ANSWERING`, `NEVER`,
  `DEFAULT_HEARTBEAT_MIN`, `heartbeat_min`, `writer`, `dead`, `resumable`, `target`. The
  prompt half (§2.4) is Task 3's and the launch half (§2.5) is Task 4's.
- `tests/test_continuation.py` — `RuleTests` (§3.2).

**Steps**

1. The three module constants exactly as §2.3 fences them: `ANSWERING = ('correct', 'spec',
   'plan')`, `NEVER = ('adjudicate', 'review', 'groom', 'reshape', 'rebase', 'close', 'fix-bug',
   'task')`, `DEFAULT_HEARTBEAT_MIN = 6`. These and the module's own name are the only literals
   it owns — every path comes off `conventions` (PD12).
2. `heartbeat_min(product)` reads `stage_limits.heartbeat_min` the way
   `stall.silent_minutes` reads its own (`asf/workers/stall.py:35`): a number is minutes, a
   duration string `<n><s|m|h|d>` is converted, anything else is the default. `stage_limits` is
   a free-form map, so no schema changes (P7).
3. `writer(product, branch)` is `lifecycle.by_branch(sessions_path)[branch]` or `None` — the
   latest run on the branch, whoever holds it now, which for a held `spec/F-0039` corrected on
   `spec/F-0039` is the same run the correction was written on.
4. `dead(run, product, now)` → `(True, 'heartbeat stale (14m > 6m)')` when the run is live (no
   `ended` line) **and** its log's mtime is older than `heartbeat_min`; `(False, '')` otherwise.
   A run that ended is not dead — §1.4's whole point, and without it every doc-lane review would
   fall back and acceptance #1 would be unreachable.
5. `resumable(product, run, now, repo=None)` returns `(session_id, '')` or `(None, why)`, running
   §2.3's tests in the order the docstring lists them, each with its own reason text: `no session
   on <branch>`, `heartbeat stale (Nm > Mm)`, `still running`, `no runtime session id recorded`,
   `worktree reaped`, `another session moved the branch`, `already landed`. One more joins them
   at the end, from PD6: `account <name> no longer in the pool`.
6. `another session moved the branch` is the module's only git call, on the product repo:
   `git log --format=%(trailers:key=ASF-Session,valueonly) origin/<main>..origin/<branch>`. A
   trailer that is neither empty nor this run's own `session` means somebody else has written
   here since (P6), and the writer's memory of the branch is wrong. It runs once per candidate
   row, beside the two `step_wave.repo_facts` already runs.
7. `target(product, row, root, runs=None, now=None)` → `(run, session_id, round, review_path)`
   or `(None, None, 0, why)`. `row.brief_kind` in `NEVER` → `kind <k> never continues`; a
   `spec`/`plan` row whose Feature is not at `<doc>-review rN` → `no review round` (a first
   draft is not an answer, and there is nothing to send). The round is N, off
   `feeder_rows.review_round`, never N+1 (PD13), and the path is
   `conventions.review_path(slug, n)` (PD12).
8. `RuleTests` per §3.2, over a hand-built registry and a temp worktree: each of the reasons in
   turn — no run on the branch; a live run silent 14 minutes against `heartbeat_min: 6`, and the
   same run silent 2 minutes (`still running`); an ended run with no `runtime_session`; an ended
   run whose worktree was removed; an ended run whose branch carries a commit with a different
   `ASF-Session` trailer, over the git fixture (P6); a landed run. Then the one that passes: an
   ended, finished run with its id, its worktree and its own trailers → `(the id, '')`. Then
   `heartbeat_min` as `6`, as `'6m'`, as `'90s'`, as nonsense (→ the default), and unset (→ 6).

**Gate**

```sh
python3 -m unittest -v tests.test_continuation
python3 -m unittest -v tests.test_lifecycle tests.test_gitfixture
python3 tools/run_tests.py 2>&1 | tail -3
bash tools/check_generic.sh && bash tools/check_conventions.sh && python3 -m asf.cli check
```

**Acceptance**


### Task 3: the findings, parsed — and the message that sends nothing the session already holds
stories: S-15353
writes: asf/workers/continuation.py, tests/test_continuation.py
after: Task 2

§2.4. A review file becomes a message: the check table, the verdict and the C/I lists, and not
one line of the brief. The session holds the card, the spec, the plan and its own diff; what it
does not hold is the findings, and a path would only make it read the file again — which is the
cost this Feature exists to remove.

**Files**

- `asf/workers/continuation.py` — `findings(text)` and `prompt(product, run, row, round_n,
  review_path, text)` per §2.4's two docstrings.
- `tests/test_continuation.py` — `PromptTests` (§3.3).

**Steps**

1. `findings(text)` → `{'verdict', 'table', 'criticals', 'improvements', 'missed'}` over the
   shape `asf/briefs/templates/review.md` asks a reviewer for. `verdict` is
   `harvest.pr_hygiene.parse_verdict(text)` — the one parser, never a second one (P8).
2. `table` is the contiguous block of `|` lines under the check header, verbatim, rows and
   separator as written: a reviewer's own evidence column is the finding, and re-rendering it
   would lose the `\|` the template asks for.
3. `criticals` and `improvements` are the `C`/`I` items, each kept **whole** — a C is
   `file:line` plus the exact fix, and half of one is not actionable. A `### Missed in round 1`
   section is read into `missed`.
4. `prompt(...)` renders §2.4's message: the `CORRECTION — round N of the review of <item> is
   in. verdict: <verdict>` head; the three sentences naming the session's own worktree and
   branch and telling it not to re-read what it wrote; the review path; the table; the C list;
   the I list; and the closing instruction — fix every C exactly, apply the I's it agrees with,
   widen nothing, re-run the acceptance tests and the Gate, `git commit -s`, push, finish with
   the typed REPORT, one line per C.
5. A `correct` row whose branch carries no review file sends the same shape with the harvest's
   correction text under `stall.CORRECTION_HEAD` (`asf/workers/stall.py:32`) in place of the
   review block — the red gate's own output is the finding, and `briefs.build.correction_text`
   already puts it under that head for a cold fixer.
6. The whole message is capped at `conventions.preamble_max_lines` (`asf/conventions.py:145`),
   the cap a brief already runs under. The table and the C list are kept whole; the I list is
   trimmed first, worst last.
7. `PromptTests` per §3.3: `findings` over a review file written to `templates/review.md`'s own
   shape — the verdict line, the six-row check table verbatim, three C items and two I items
   kept whole, a `### Missed in round 1` section read into `missed`; over a file with a verdict
   and no table; over one with a table and no verdict (`parse_verdict`'s fallback, P8). Then
   `prompt`: it contains the check table and every C, it names the branch and the review path,
   and it contains **none** of the brief's preamble — asserted by `'Backlog item:' not in text`
   and `TAIL` absent; a `correct` row with no review file carrying the harvest's correction text
   under `CORRECTION_HEAD` instead; the cap trimming the I list before the C list. And `target`
   refusing, by kind: `adjudicate`, `review`, `fix-bug` and `task` each → `kind <k> never
   continues`; a `spec` row on a Feature at stage `card` → `no review round`; a `spec` row at
   `spec-review r2` → round **2** and round 2's review path, not round 3 (§1.4, PD13) —
   asserted against `conv.review_path(slug, 2)`, never a literal (PD12).

### Task 4: the wave continues, then launches — both lanes
stories: S-15354
writes: asf/workers/continuation.py, asf/tick/step_wave.py, tests/test_continuation.py
after: Task 3

§2.5 and §4. The wave asks the rule before it builds a brief; a row that can be continued is sent
its findings and is not launched; a row that cannot is briefed and launched in the **same tick**,
with one line naming why. This is the Feature: the card's first acceptance lands here, and the
fallback branch it shares with Task 5 lands here too.

**Files**

- `asf/workers/continuation.py` — `continue_run(product, row, run, session_id, round_n,
  review_path)` → the ledger record, or `None` when the runtime declined.
- `asf/tick/step_wave.py:171` — `run`'s row loop gains §2.5's block between the held check and
  `_build`, and the `cold` line after `_build`.
- `tests/test_continuation.py` — `WaveTests` (§3.4).

**Steps**

1. `continuation.continue_run` writes the message to
   `<state>/briefs/<writer job>.continue-r<n>.md` — one file per round, kept for the operator
   exactly as a brief is (§4) — through `spawn.write_brief`'s own directory
   (`spawn.briefs_dir`), so the two live side by side.
2. The worktree is `spawn.make_worktree(product, run['job'], branch)` (PD8): the writer's own,
   reused as it stands and rebased onto the fetched trunk, with `may_launch` and the push-gate
   check carried along. A `SpawnError` from it is not a crash — it is the fallback's trigger,
