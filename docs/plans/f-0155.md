# Plan F-0155 — the sha on the line: `freshness` names the commit of every copy, and the guide says what it is for

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0155.md` (approved). Branch: `plan/F-0155`.

Two Tasks, one per Story, cut where the spec's `## The design` is already cut: the module that
gains the surface, and the prose that explains it. Task 1 is `asf/views/freshness.py` — the
docstring that stops promising no git, `head_sha`, the two new `Fresh` fields, and the `@ <sha>`
clause on both paths of `line` — with its fences in a new `tests/test_record_sha.py` (spec D9).
Task 2 is the paragraph in `docs/guide/operating.md` that says what the sha is for, with a prose
assertion in `tests/test_readme.py`.

Wave order: **1 → 2**, and both behind F-0122.

Neither Task starts at once. The spec's **Ordering** section is a hard dependency, not a
preference (PD5): every file below is in the `writes:` of an F-0122 Task that has not landed, and
landing this first would put `@ <sha>` on the nine tables and then silently lose it the moment
F-0122's Task 4 routes them through `freshness.view_record`. Both Tasks therefore carry
`after: F-0122`, and the wave holds each until F-0122 is in a done state.

Task 2 is prose about the exact string Task 1 makes `line` produce, and its example lines are
checked against Task 1's `TheLineNamesTheCommit` rather than retyped — so it waits for Task 1 as
well. The two footprints are otherwise disjoint; the queue costs nothing, because Task 2 is
`after: Task 1` on its own merits.

§Acceptance tests' last fence — the whole suite and both tree fences, as CI runs them — binds both
Tasks, so every Gate below runs it beside its own.

### Task 1: `freshness` names the commit of every copy it names
stories: S-35850
writes: asf/views/freshness.py, tests/test_record_sha.py
after: F-0122

The spec's three `asf/views/freshness.py` design sections, whole: the module docstring stops
promising no git, `head_sha` answers the commit a copy is at, `Fresh` carries one for each copy
the line names, and `line` hangs `@ <sha>` off both paths. Nothing about **which** copy is read
changes — `pick`'s decision is F-0122's and no branch of it reads a sha.

**Files**

- `asf/views/freshness.py` — the module docstring's last paragraph; new `head_sha` and `_at`; two
  new fields on `Fresh`; `pick` filling them; `line` using them
- `tests/test_record_sha.py` — new module: `HeadSha`, `PickCarriesTheCommits`,
  `TheLineNamesTheCommit`, `BothCopiesNamed`, `NoGitNoSha`, `NextNamesBothCopies`

**Steps**

1. The module docstring's last paragraph, replaced by the spec's diff byte for byte
   (`docs/specs/f-0155.md:129-139`). F-0122 ships *"Two file reads, no git, no network"* as a
   contract; this change makes it false, and a module whose docstring forbids what its code does
   is the defect class this factory files Bugs for (spec D8). The replacement says what is true:
   two `index.json` reads decide *which* copy with no git, and naming the copy then costs at most
   two local `rev-parse`, no fetch, with an unreadable sha dropped rather than raised.
2. `head_sha(root)`, new, beside `generated_at`. The docstring is the spec's
   (`docs/specs/f-0155.md:147-158`) — what it is (the commit the copy *is at*, so two copies can
   be named and compared by hand), what it is not (a currency check; it runs no `fetch` and
   decides nothing, `pick` chooses from the two `generated` stamps with no git at all), and the
   list of what answers None. The body is the spec's block **with PD6's correction**:

   ```python
   try:
       out = subprocess.run(['git', '-C', root, 'rev-parse', '--show-toplevel', '--short', 'HEAD'],
                            capture_output=True, text=True, timeout=5)
   except (OSError, subprocess.TimeoutExpired):
       return None
   if out.returncode != 0:
       return None
   lines = out.stdout.strip().splitlines()
   if len(lines) != 2 or os.path.realpath(lines[0]) != os.path.realpath(root):
       return None
   return lines[1].strip() or None
   ```

   One process per copy, so the spec's *at most two `rev-parse` per command* still holds. Add a
   sentence to the docstring naming the case the comparison refuses: `rev-parse` walks **up**, so
   a record root that is not a work tree but sits inside one would otherwise answer the enclosing
   repository's HEAD — a sha that names a commit the record is not at, which is the confusion this
   card exists to end. Cite `cli._checkout_root` as the precedent for the shape.
3. `Fresh` gains two fields, exactly as the spec's diff writes it
   (`docs/specs/f-0155.md:171-181`): `Fresh = collections.namedtuple('Fresh', 'root source
   generated age_s checkout older_s sha checkout_sha')`, with the comment above it extended to say
   that `sha` is the short HEAD of `root`, `checkout_sha` that of `checkout`, and either is None
   when the copy is not a git work tree.
4. `pick` fills them **as its last act**, after it has decided the copy, so no branch of the
   decision can read one: one `head_sha` when it kept the checkout, two when it fell back. Read
   the namedtuple comment's parenthetical the one way that matches the spec's **In** bullet
   (*`checkout_sha` for the operator's own copy, set only when the clone was taken*):
   `checkout_sha` is **None when `source` is `'checkout'`** — in that case the copy read *is* the
   checkout and its sha is already `sha`, so there is no second copy to name. Do not set it to a
   duplicate of `sha`; `line` tests it to decide whether a second clause exists.
5. `_at(path, sha)` — the spec's helper (`docs/specs/f-0155.md:213-215`), one place so the two
   sites cannot drift: `f'{path} @ {sha}' if sha else path`.
6. `line(fresh)` builds both paths through `_at` and changes nothing else — not a word, not an em
   dash, not the `git -C <path> pull`. Its docstring gains the spec's two examples in the summary
   and the spec's added paragraph (`docs/specs/f-0155.md:203-206`): a sha that would not read is
   **dropped**, not guessed, and the two clauses drop **independently** — the clone's sha being
   unreadable does not cost the checkout its own. The `index age unknown` form is F-0122's and is
   untouched except that its path goes through `_at` like the others.
7. `HeadSha` in `tests/test_record_sha.py`: a repo with a commit answers a short hex sha; None for
   a bare non-repo, for a repo with no commit yet, for a missing path, **and for a plain directory
   nested inside a repository** (PD6 — the case that would otherwise answer the enclosing repo's
   sha). And that it runs no network call, asserted by making `subprocess.run` refuse any argv
   carrying `fetch`, `pull`, `ls-remote` or `remote`, as the spec's fence describes.
8. `PickCarriesTheCommits`: both fields are filled, and `pick` decides **nothing** by them — the
   copy chosen is identical with a sha, with no sha, and with a `head_sha` that raises; and
   `checkout_sha` is None when the checkout was kept and set when the clone was taken. The
   raising case is the fence under step 4's ordering: a `head_sha` that blows up must not be able
   to change which copy was picked.
9. `TheLineNamesTheCommit` and `BothCopiesNamed`: `@ <sha>` after the path in the plain case; both
   shas in the fallback case, in the two places the docstring shows; the clause dropped — and
   **only** that clause, every other word unchanged — when a sha is None; and each of the two
   dropped independently (clone sha None with checkout sha set, and the reverse). Pin the expected
   strings whole rather than asserting `assertIn` on a fragment: this line is what an operator
   reads inside a `/asf:*` fence, and Task 2 quotes these exact strings.
10. `NoGitNoSha`: a record root that is not a git work tree still prints the whole line, one clause
    short, and `asf status` and `asf next` both **exit 0** over it. This is the fence under spec
    D6 — an identity clause must never be able to stop a table printing.
11. `NextNamesBothCopies`: the card's own test with the handle it asked for — a fixture with a
    checkout and a clone whose index is newer, `asf next` run over it, and the first line carrying
    the clone's path, the clone's sha, and the checkout's sha and lag. It exercises F-0122's Task 4
    wiring as well as this change, which is one more reason this Task is `after: F-0122`.
12. Write no machine path and no worker account name into either file: the fixtures build their own
    temporary directories, and any illustrative path in a docstring is `/path/to/record` or
    `~/.ASF/state/<product>/record`. `bash tools/check_generic.sh` is in the Gate.
13. Keep the module inside the two whole-tree fences of PD8 without a special case — no state word
    and no `end_reason` (`tests/test_lifecycle.py:730-739`), no product convention in a literal
    (`tools/check_conventions.sh`). Both run in this Task's Gate.

### Task 2: the guide says what the `@ <sha>` is, and what it is not
stories: S-35851
writes: docs/guide/operating.md, tests/test_readme.py
after: Task 1, F-0122

The spec's guide section: the paragraph F-0122's Task 6 leaves where the *pull before you read*
one was gains its last sentences, saying that the sha is an **identity** and not a freshness
check, and how the two shas on a fallback line are read. Prose about the exact string Task 1
makes `line` produce, so it lands after it and quotes it rather than paraphrasing.

**Files**

- `docs/guide/operating.md` — the paragraph F-0122's Task 6 leaves at the opening, gaining the
  spec's four sentences
- `tests/test_readme.py` — new `RecordShaProseTests`

**Steps**

1. Append the spec's diff (`docs/specs/f-0155.md:245-254`) to that paragraph, as a new paragraph
   under it: the `@ 9f8e7d6` after each path is that copy's HEAD; it is an identity, not a
   freshness check; quote it when you report what a table said; when the line names two copies the
   two shas are how far apart they are, and
   `git -C <checkout> log --oneline 9f8e7d6..a1b2c3d` is the difference; a record that is not a git
   work tree simply has no `@` clause.
2. Do not restate what F-0122's Task 6 already wrote there — which copy is read, the age, the
   fast-forward, the `git -C <path> pull` command. This Task adds the identity paragraph and
   nothing else; the surrounding text is F-0122's and stays as that Task left it.
3. Any example sha or `record:` line in the paragraph is the **exact** string `freshness.line`
   produces, checked against Task 1's `TheLineNamesTheCommit` rather than retyped. Illustrative
   paths are `/path/to/record` and `~/.ASF/state/<product>/record` — no worker account name and no
   machine path (spec P14).
4. `RecordShaProseTests` in `tests/test_readme.py`, reading the guide **from the checkout** as
   `ProductResolutionProseTests` and `WorktreeSetupProseTests` already do
   (`tests/test_readme.py:482` and `:507` are the precedent and the shape, including their `_read`
   helper). Each assertion names the clause it is pinning, so a later rewrite is told which
   sentence it broke: the paragraph carries the `@` clause and calls it the copy's HEAD; it says
   *identity* and denies that it is a freshness check; it gives the two-sha `git log --oneline
   <a>..<b>` comparison; and it says a record that is not a git work tree has no `@` clause.
5. `bash tools/check_generic.sh` before the push, over the guide and the test. This is the Task
