# Plan F-0193 — a second reviewer who is the customer, and one gate in both the places the pages got out

Epic: E-0003 — ASF 0.3 — autonomous delivery. Spec: `docs/specs/f-0193.md` (approved). Branch:
`plan/F-0193`.

Six Tasks, one per Story, cut so that **the trunk never carries a gate that can hold a branch no
session can release**. That is the single risk this card runs: every arm of it either blocks a
landing or blocks a deploy, and each one is one line away from blocking it forever.

1. **the vocabulary, and nothing that gates on it** — `asf/enduser.py`'s pure half, the three
   config keys, the doctor rows. No caller: the factory's behaviour is byte for byte what it is
   today when this lands.
2. **the reviewer exists before anybody is sent to it** — `CHECKLIST['enduser']`, the composed
   slug, the brief template. Still no gate: a review kind nothing asks for.
3. **the landing gate, the correction path and the ledger, in one commit** — T4e, T5e, the launch
   row, the BACK that briefs a corrector, and the row the deploy gate later reads. They land
   **together**, deliberately (PD1, PD2): three of the four pieces are separately useless and the
   fourth, alone, is a branch stuck in BACK.
4. **the deploy gate, on the walk the view already does** — `enduser.covered`, the refusal at both
   of `marker_refusal`'s sites, and the first-parent walk lifted into one place.
5. **the two signatures** — `merge_legal_content` and `deploy_legal_content`.
6. **the view says which of them is missing** — the `asf prod` State cell.

They run **1 → 2 → 3 → 4 → 5 → 6**, one at a time. The chain is real for 2→3→4 (each calls code
only its predecessor ships) and is enforced for all six anyway by `tests/test_enduser.py`, which
every Task writes (PD9) — the spec's acceptance fences name nine classes in one module, so one
module it is.

**Read PD1, PD2 and PD3 before writing a line of Task 3, and PD10 before Task 2.** PD1 and PD2 are
two places where following the spec's §3 literally ships a gate that holds a branch and briefs
nobody to answer it. PD3 is a round number read off the wrong review. PD10 is a claim in the
spec's own Acceptance section that is false at this sha.

Every Gate below carries `bash tools/check_generic.sh` and `bash tools/check_conventions.sh`
beside its own commands — the spec's two whole-tree fences bind every Task. Note that
`check_conventions.sh` scans `asf/*.py` **and** `asf/**/*.py` (`tools/check_conventions.sh:105`),
so `asf/enduser.py` is in its scope from Task 1 onward, and it generates a forbidden pattern for
every path-shaped convention default at run time: the new module reads `conv.review_path(...)` and
`env.state_dir(product)` and writes no document path or state path as a literal.

### Task 1: the vocabulary and the three config keys, and nothing that gates on them
stories: S-37750
writes: asf/enduser.py, asf/env.py, asf/conventions.py, asf/doctor.py, docs/products.example.yaml, tests/test_enduser.py
after: none

The spec's `## The design` §1 and the doctor half of §6, and nothing else: a new `asf/enduser.py`
holding the classification and the config readers, `audience:` as a product field,
`customer_content.legal_paths` and `customer_content.enduser` as conventions, and
`enduser.findings(product)` appended to the doctor's existing `customer content` section.

**Nothing the factory does changes when this Task lands.** No lane reads `applies`, no deploy reads
`legal`, no brief reads `audience`. A product that sets all three new keys gets a doctor row and
nothing else. That is the point of cutting it here: the policy's three arms can be pinned one at a
time against a factory whose behaviour is provably identical, and every later Task is wiring.

Glob matching is **borrowed, never reimplemented**: `customer_content.matches(globs, path)`
(`asf/customer_content.py:76`) is the one matching rule in the factory for these paths — a trailing
`/` is a prefix, else `fnmatch` where `*` crosses `/`, and a bare directory matches everything
below it — and `enduser.py` imports it (P1). A second glob rule for the same paths is how
`legal_paths` and `paths` would come to disagree about the same file.

**Files**

- `asf/enduser.py` — new. This Task ships its pure half only: `paths`, `legal_paths`, `audience`,
  `policy`, `applies`, `legal`, `enabled`, `findings`, and `slug` (one line, needed by Task 2 and
  cheaper to write beside the names it composes than to bolt on later). `record`, `rows` and
  `covered` are Tasks 3 and 4's and are not stubbed here — an unimplemented function on the trunk
  is a function somebody calls.
- `asf/env.py` — `PRODUCT_FIELDS['audience'] = _STR` (`:516-521`) and the `audience` property
  beside `app_host`/`customer_paths` (`:813-818`).
- `asf/conventions.py` — the two new keys' shape validation inside the existing
  `customer_content` block (`:509-527`): `legal_paths` through `_path_list_problem` exactly as
  `paths` is, and `enduser` against `REVIEW_POLICIES` (`:202`, already the tuple `('none',
  'required')`) with the same message shape as the review-policy arm at `:622-624`. The `#:`
  comment at `:232-235` gains the two keys.
- `asf/doctor.py` — the `customer content` row (`:954-956`) concatenates `enduser.findings(product)`
  onto `customer_content.findings(product)`. One section, not two (P17).
- `docs/products.example.yaml` — the `audience:` block and the two convention keys, byte for byte
  as the spec's `## Records` writes them.
- `tests/test_enduser.py` — new module: `class Classification`, `class Policy`, `class Doctor`,
  all plain `unittest.TestCase`s and never a subclass of a harness in another module.

**Steps**

1. `paths(conv)` is `customer_content.paths(conv) + legal_paths(conv)`, de-duplicated **in order**
   (`dict.fromkeys`), so a glob listed in both appears once and the list a doctor row prints is
   stable. `legal_paths(conv)` reads the block through `customer_content._block(conv)`'s own
   accessor shape and is `[]` unset.
2. `audience(product)` is `(product.audience or '').strip()` — `''` unset, never `None`, because
   the brief interpolates it and a `None` would render the word `None` as the reviewer's identity.
3. `policy(product)` resolves in the spec's stated order and returns the arm it fired on as well as
   the answer — `('required'|'none', why)` — because `asf doctor` must print which arm decided
   (D2) and deriving that twice is how the doctor and the gate come to disagree. `enabled(product)`
   is `policy(product)[0] == 'required'`.
   1. `conventions.customer_content.enduser` when it is exactly `'none'` or `'required'`;
   2. else `'required'` when `audience(product)` is non-empty **and** `paths(conv)` is non-empty;
   3. else `'none'`.
   A value that is neither word is **not** a third arm: `asf.conventions` already rejects it as a
   shape problem (Step above), and `policy` falls through to arm 2 rather than inventing a meaning.
4. `applies(product, files)` and `legal(product, files)` are `[f for f in files if
   customer_content.matches(<the list>, f)]` — order preserved, so a refusal line names files in
   the order the diff did. `applies` does **not** consult `enabled`: the classification and the
   switch are two questions, and every caller in Tasks 3–6 asks `enabled(product) and
   applies(...)`. Keeping them apart is what lets `Classification` test the globs without a
   product that has turned the gate on.
5. `slug(item)` is `f'{str(item).lower()}-enduser'`. One line, no branch.
6. `findings(product)` returns `[(ok, detail)]` in `customer_content.findings`' shape (`:269-295`),
   with the four rows §6 names: green naming the resolved policy *and its arm*, the glob counts and
   the ledger's row count (`0` until Task 3 writes one, read through a helper that treats an absent
   file as empty — PD14); red for `enduser: required` set explicitly with an empty `audience`; red
   for `legal_paths` set while both legal approval classes resolve to `auto` (this row is written
   now and reads as red only once Task 5 mints the classes — until then the lookup finds no class
   and the row is not emitted, which the `Doctor` test pins so the row cannot silently stay dark);
   amber for a product that deploys with `audience:` set and `customer_content.paths` empty.
7. `Classification` — `applies` and `legal` over the glob forms `matches` supports; a file in
   `legal_paths` and not in `paths` is in `applies` anyway (D6) and `legal(...)` is a subset of
   `applies(...)` for every fixture; a glob listed in both yields one entry in `paths(conv)`, not
   two.
8. `Policy` — the three arms in order, each with the other two arms' inputs present so the order is
   what is being tested: an explicit `enduser: none` beats a set `audience` + non-empty `paths`; an
   explicit `enduser: required` beats an empty `audience` (and the doctor's red row is what catches
   that, not `policy`); derivation fires only with both; an unknown word falls to arm 2. Assert the
   `why` string names the arm.
9. `Doctor` — `audience:` loads as a scalar and its absence is not an error; a `legal_paths` that is
   not a list is a named `conventions` problem; an `enduser:` that is neither word is a named
   `conventions` problem; the four `findings` rows, each asserted by its `ok` value and a
   distinguishing phrase, and `findings` on a product with no `customer_content` at all returns
   what it returns today with nothing appended.
