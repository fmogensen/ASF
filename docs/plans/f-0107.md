# Plan F-0107 — `asf install`: one command from zero to a ticking factory

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0107.md` (approved). Branch: `plan/F-0107`.

Eight Tasks, cut the way the spec's §2 is cut — by the file that gains the surface. Task 1 is the
new module and the half of `asf install` that aborts (§2.2 steps 1–6, §2.3, §2.4); Task 2 is the
half that records and carries on (§2.2 steps 7–12); Task 3 is `asf plugin install` (§2.5); Task 4
is the bootstrap split and the release-tag default (§2.1, D5, D6); Task 5 is `asf uninstall`
(§2.6); Task 6 is `asf upgrade --to` (§2.7); Task 7 is the zero-to-green CI test (D12); Task 8 is
the README and the guide (§2.8).

Three Tasks need nothing landed and start at once — Task 1 (the module), Task 3 (the plugin
action) and Task 6 (`--to`, which touches only `asf/upgrade.py`). Task 2 needs Task 1's step
framework and Task 3's writer, because step 9 calls it. Task 4 needs `asf install` to exist before
the bootstrap can `exec` it. Task 5 needs the module and its registration. Task 7 needs the whole
install path green. Task 8's fenced README line is Task 4's bootstrap signature and its
`upgrading.md` edit names Task 6's flag.

Wave order: **1 ‖ 3 ‖ 6 → 2 ‖ 4 ‖ 5 → 7 ‖ 8**.

Five of the eight write `tests/test_install.py`, because that is where the spec's own fences put
their classes (PD5). Those five queue behind one another whatever their `after:` says; the wave
above is the dependency order, not a promise of concurrency.

§3's last fence — the whole suite as CI runs it — binds every Task, so every Gate below runs
`python3 tools/run_tests.py` beside its own.

### Task 1: `asf/install.py` — the module, the flags, and the six steps that abort
stories: S-32351, S-32352, S-32353, S-32354
writes: asf/install.py, asf/init.py, tests/test_install.py
after: none

§2.2 steps 1–6, §2.3 and §2.4: the new module, the command surface, the step framework every
later Task hangs a step on, and the six steps whose failure ends the run — the host, this `asf`,
the config, the repos, the adopt, the account.

**Files**

- `asf/install.py` — new: `CONFIG_TEMPLATE`, `detect_accounts`, `account_stanza`, the step
  framework (`Step`, `run_steps`, the summary table, the exit status), `cmd_install`, `register`,
  and steps 1–6
- `asf/init.py` — `register_commands` also registers `asf install`
- `tests/test_install.py` — `InstallCommandTests`, `InstallConfigTemplateTests`,
  `InstallAccountsTests`, `InstallStepsTests` (its steps 1–6 methods)

**Steps**

1. The module docstring names what it is and what it is not: it configures, it never installs the
   package (D2), and the bootstrap it is `exec`ed by is named
   `os.path.join('tools', 'install' + '.sh')` (PD15).
2. The step framework: one `Step` record of `(label, fn, abort)`, a runner that prints one line
   per step — `ok` / `wrote …` / `already in place` / `repaired …` / `FAILED … (exit N)` — stops
   on a failed `abort=True` step, records and continues past the rest, and ends with the summary
   table and `0` only when every step passed. This is the shell's own discipline
   (`tools/install.sh:141-147`), moved without change.
3. `register`: `asf install` with `--product` (required), `--repo DIR`, `--repo-url URL`,
   `--record DIR`, `--record-url URL`, `--scheduler {launchd,cron,none}`,
   `--account NAME[:CONFIG_DIR]` (`action='append'`), `--fake-workers`,
   `--console-permissions {user,repo}`, `--allow-checkout`, `--yes`. Added to
   `asf.init.register_commands` beside `upgrade` and `hooks` (PD13).
4. The missing-flag rule, before anything is written: on a tty a missing `--repo`, `--record` or
   `--scheduler` is asked for once each with its default in the prompt; with `--yes`, or off a
   tty, one with no default is one `NEEDS OPERATOR` line and a non-zero exit. `--record` has no
   default unless the product file already carries `backlog_dir` (PD9).
5. Step 1 — the host: `git` on `PATH`, and `gh` unless the product has no PR host. Each missing
   one is a `NEEDS OPERATOR` line naming it; nothing is installed (the spec's Out).
6. Step 2 — this `asf`: print `cli.version_string()`. A checkout or editable install refuses with
   one `NEEDS OPERATOR` line unless `--allow-checkout` is given (D2). A checkout is what
   `cli._checkout_root()` finds.
7. Step 3 — `CONFIG_TEMPLATE`: one `str` with slots for `default_product`, `scheduler.kind`,
   `capacity.total.sessions` and the account block, a header pointing at
   `docs/config.example.yaml` for every key it does not write, and `# TODO` on the three
   `worker_pool.models` ids and nothing else. Written to `env.config_path()` only when absent,
   with `<ASF_HOME>/products/` created beside it; an existing file is never rewritten — the keys
   it lacks are printed as the diff that was not made, the way `cmd_init` prints its product diff
   (`asf/init.py:277-280`).
8. Step 4 — the repos: `--repo-url` / `--record-url` are cloned into `--repo` / `--record` only
   when that directory does not exist. An existing directory is read and never written to.
9. Step 5 — the adopt: `asf init --product <p> [--repo DIR] [--backlog DIR]`, called in-process
   through `init.cmd_init` so its exit status is the step's (D3: one writer for
   `products/<p>.yaml`).
10. Step 6 — the account: `--account NAME[:CONFIG_DIR]` wins; else `detect_accounts(home)` reads
    every directory under `<ASF_HOME>/accounts/` holding the runtime's credential file; else one
    stanza with `auth_env` commented out plus a `NEEDS OPERATOR` line naming `claude setup-token`.
    Each stanza is `name`, `role: local`, `cap: 2`, `config_dir`, `home`. `--fake-workers` writes
    `backend: fake` and no account at all. An account already in `worker_pool.accounts` is left as
    it stands. Nothing reads a credential's contents (D10).
11. `InstallConfigTemplateTests`: the template is written when absent and not when present; the
    diff-not-made is printed for a file missing keys; every top-level and nested key it writes is
    a key `docs/config.example.yaml` documents (read from the file, not a hand-kept list — D4);
    `env.loads` parses what it writes and `env.load_config` accepts it.
12. `InstallAccountsTests`: `--account a`, `--account a:~/dir`, two `--account`s; detection over a
    fixture `<ASF_HOME>/accounts/` with one credentialled and one bare directory; neither, which
    writes one stanza and the `NEEDS OPERATOR` line and still returns 0 for the step;
    `--fake-workers`, which writes `backend: fake` and no stanza; and one assertion that no
    credential file is ever opened.
13. `InstallCommandTests`: the parser carries every flag; `--product` is required; a checkout
    install refuses without `--allow-checkout` and runs with it; the tty prompt asks once per
    missing flag and takes the default on an empty answer; `--yes` off a tty turns a defaultless
    missing flag into a `NEEDS OPERATOR` line and a non-zero exit with nothing written; the
    version line names what `cli.version_string()` returns.
14. `InstallStepsTests`: the framework (abort stops, record-and-continue does not, the summary
    names each failure and the exit status is non-zero), `test_adopt_step` (an existing product
    file is left as is and its diff printed; a missing `backlog_dir` with no `--record` is the
    abort of PD9; a `--record-url` clones only into a directory that does not exist), and the
    steps 1–6 rows. Built on a temp `HOME`/`ASF_HOME` through `asf.hermetic.build`, so the suite
    reads nothing of the operator's home (`tests/test_00_home.py`).

### Task 2: the six steps that record and carry on, and the second run that writes nothing new
stories: S-32355, S-32357
writes: asf/install.py, tests/test_install.py
after: Task 1, Task 3

§2.2 steps 7–12: the hooks, the clocks with their read-back retry, the plugin, the console offer,
the doctor against its pre-existing-RED baseline and the tick dry run. None of them aborts — each
records a failure and lets the rest run, exactly as `tools/install.sh` does today — and a second
run of the same command writes nothing new.

**Files**

- `asf/install.py` — steps 7–12, the baseline doctor reader, the clock read-back retry, the
  plugin-console probe, the tail
- `tests/test_install.py` — `InstallStepsTests`: `test_idempotent_second_run`,
  `test_doctor_and_dry_run_tail`, and the steps 7–12 methods

**Steps**

1. The baseline: the doctor's RED rows are read **before** step 3 writes anything, the way the
   shell reads them before its step 1 (`tools/install.sh:55-75`), and kept for step 11.
2. Step 7 — `asf hooks install --product <p>`, in-process. Idempotent because `hooks.merge`
   merges and keeps every unrelated key (`asf/hooks.py:252-272`).
3. Step 8 — `asf scheduler install --product <p>`, then every declared clock read back through
   `asf scheduler status`; a clock still absent gets **one** retried bootstrap, and one still not
   loaded after it is a `NEEDS OPERATOR` line naming the label and a failed step. This is
   `scheduler_install_verified` (`tools/install.sh:149-171`) in Python, behaviour intact. With
   `--scheduler none` there is nothing to install or read back (PD10).
4. Step 9 — `asf plugin install`, calling Task 3's writer.
5. Step 10 — `asf console-permissions offer --product <p>` printed, or
   `install --product <p> --scope <s>` when `--console-permissions` was given
   (`asf/console_perms.py:154-163`).
6. Step 11 — `asf doctor --product <p>` against step 1's baseline: a RED also in the baseline is
   one `WARN … (not caused by it)` line naming it, a RED that is not fails the step, and a
   non-zero doctor with no RED row read is a failure (the doctor itself broke). The exit status is
   the doctor's own (`asf/doctor.py:1079-1091`).
7. Step 12 — `asf tick --product <p> --dry-run` (`asf/tick/tick.py:344-346`), which works on a
   throwaway copy of the state directory and launches nothing.
8. The tail: the plugin's two console commands with the written path
   (`/plugin marketplace add <ASF_HOME>/plugin`, then `/plugin install asf@asf`) — or, when the
   runtime's own CLI is probed once at run time and offers a non-interactive plugin install, that
   command is run instead and the line says which was used (D8). Then `asf install: done`, or one
   `NEEDS OPERATOR` line per failed step.
9. `test_doctor_and_dry_run_tail`: a pre-existing RED warns and does not fail; a new RED fails and
   is named; a green doctor passes; the dry run is called with `--dry-run` and its exit status is
   the step's; the two `/plugin` lines carry the written path; the probe, when it finds a
   supported command, runs it and says so, and when it does not, prints the operator line.
10. `test_idempotent_second_run`: the whole command run twice over one temp `HOME`/`ASF_HOME` —
    the second run writes no new file, changes no byte of `config.yaml`, `products/<p>.yaml` or
    the generated plugin tree, reports every step as `already in place` or `repaired …`, and exits
    0. Asserted as a tree snapshot (path → sha) taken after each run, not as a printed line.
11. The steps 7–12 methods: each failure is recorded and the following steps still run, the
    summary names them, and the exit status is non-zero; the clock retry is exercised through a
    stubbed `scheduler status` that fails once and passes on the retry, and once that never
    passes.

### Task 3: `asf plugin install` — the marketplace tree from the installed package
stories: S-32356
writes: asf/plugin_build.py, tests/test_plugin.py
after: none

§2.5: a third action beside `build|check` that writes the whole tree under `<ASF_HOME>/plugin`
from the CLI's own parser, reading nothing from a checkout — so a `pipx` install has the `/asf:*`
skills (B-0047).

**Files**

- `asf/plugin_build.py` — `installed_plugin_dir()`, `install(dest, out)`, `install` as a third
  `choices` value, `--dir` documented for it
- `tests/test_plugin.py` — `PluginInstallTests`

**Steps**

1. `installed_plugin_dir()` returns `os.path.join(env.ASF_HOME, 'plugin')` (`asf/env.py:21`) —
   under `<ASF_HOME>`, never the runtime's own configuration directory (PD15, D7).
2. `install(dest=None, out=print)`: `dest or installed_plugin_dir()`, then
   `expected_files(os.path.join(dest, 'plugin'))` written relative to it —
   `.claude-plugin/marketplace.json` at the top, `plugin/.claude-plugin/plugin.json`,
   `plugin/skills/<name>/SKILL.md` per view and dialogue, `plugin/hooks/hooks.json`
   (`asf/plugin_build.py:130-138`). Directories are created; every file is written whether or not
   it differs, so the tree is regenerated byte-identical on a second run.
3. Strays under the destination's `plugin/skills` are **removed**, not merely reported: a skill
