# F-0031 — The approval matrix as code: the plan

Binding: the approved spec `docs/specs/f-0031.md` (§1 decisions D1–D14, §2 the design, §3
acceptance A1–A6, §4 records). This plan adds no scope. Where the spec is silent or wrong for the
build, the ruling is in the decisions block below, not in a Task.

Task ids are not written here: the record mints one Task card per `### Task N:` heading, in
document order (`asf/record/plan_tasks.py`), and the feeder launches them lowest id first.

## Decisions for the build

| # | Question | Ruling | Why |
| --- | --- | --- | --- |
| PD1 | Wave order | Strictly sequential: Task 1 → 2 → 3 → 4 → 5 → 6. Every Task writes `tests/test_approvals.py` (the spec puts every acceptance class in that one file) and all but Task 3 write `asf/approvals.py`, so the feeder's `writes:` gate queues them; each also builds on the one before | The spec's single test file makes the footprints intersect by construction; accepting the queue is cheaper than splitting the tests out, which the spec's commands name by module |
| PD2 | A Task launched before the previous one is on the trunk | Each Task's first step checks that the previous Task's symbols import from `origin/main`; if not, the session prints `NEEDS OPERATOR: <this Task> started before <previous Task> landed — relaunch after harvest` and ends without writing code | The feeder frees a footprint when the session ends, not when harvest lands it; a Task built on a trunk without its base would re-invent it |
| PD3 | P4/P5 (the runtime's hook contract and settings location) | Confirmed in Task 1, step 1, against the installed runtime version, before any hook code is written (the spec's P4 "if it does not hold") — the finding goes in Task 1's commit body | The spec requires it of "the plan's first Task"; Task 1's own code does not depend on it, Tasks 2–3 do |
| PD4 | "the home's runtime settings" for an account without `config_dir` (§2.3, P5) | The account's `home` when set — `asf/workers/runtime.py` `build_env` points `HOME` there — else the operator's home. One function, `hooks.account_settings_path(account)`, in `asf/hooks.py`; `asf/doctor.py` calls it | `tools/forbidden-conventions.txt` forbids the runtime's settings directory in every `asf/**/*.py` except `asf/hooks.py`, the exempt runtime adapter; the path is resolved there once |
| PD5 | `hooks.install` for a product with no `repo_dir` | The approvals entry is installed in the worker accounts regardless; the existing `NEEDS OPERATOR … has no repo_dir` (rc 2) stays, and applies only when a rule declares a hook | §2.3 makes the approvals entry unconditional; the rule hooks' precondition is unchanged |
| PD6 | `tests/test_install.py` `HooksTest` | Task 3 updates it: the `hooks: 0 rules declare a hook` return is gone (§2.3) and the message becomes `hooks: <n> rule hooks in <repo settings>; approvals in <k> worker accounts`. Idempotence is asserted on file content, not on an `already installed` wording | A spec-mandated change breaks those assertions; the file is in Task 3's `writes:` so the diff stays inside its footprint |
| PD7 | The A2 end-to-end block run from inside a factory session | Run it with the session's identity removed: `env -u ASF_JOB -u ASF_PRODUCT bash <file>`, the block saved byte for byte to a scratch file outside the repository. Every unit test passes `environ` to `run_hook` explicitly and every subprocess test builds its own environment | A coder's session carries `ASF_JOB` (P2); the block's "no `ASF_JOB` → rc 0" case would inherit it and fail. Once the hook is installed in the worker accounts, the block's own command text (`git push origin HEAD:main`) would also be refused as a `Bash` call — a file run by path is not |
| PD8 | The record repo's harvest path (`run_harvest`, when `is_record_repo`) | Not gated by the merge classes — the spec places the check in `run_product_harvest` after `commits_name_item`, which that path never reaches | Stated so nobody widens it in review; a follow-up card is the groom's |
| PD9 | `class` as an event field | `ctx.event('held', **{'class': cls, …})` — `class` is a Python keyword and cannot be a keyword argument | §4 fixes the field name |
| PD10 | Story ids | The `stories:` lines carry the spec's S-7450 … S-7456. The brief listed the Feature's Stories as "none yet"; the record keeps only ids it holds (`plan_tasks.stories_of`), so those Stories must be in the record before the Task cards are minted for the lines to count | Ids are never invented here; the spec's are the only ones on the trunk |

**Steps**
1. P4/P5 (PD3). Record `claude --version`, and confirm against that version's hooks
   documentation: a `PreToolUse` command hook receives JSON on stdin with `tool_name`,
   `tool_input`, `cwd`; exit 2 blocks the call and feeds stderr to the model; exit 1 is
   non-blocking; with `CLAUDE_CONFIG_DIR` set, user settings are `<config_dir>/settings.json`,
   else the home directory's. Put the version and the four facts in the commit body. If any does
   not hold, print `NEEDS OPERATOR: F-0031 P4/P5 does not hold on runtime <version> — <which> —
   the spec's D6/D7 need a ruling` and still finish this Task (nothing here depends on it).
2. `asf/approvals.py` §2.1: `LEVELS = ('auto', 'groom', 'human-now')`; the frozen
   `ActionClass(name, covers, default, read_by)`; `CLASSES` — the nine rows of the §2.1 table,
   in its order, with its defaults and `read_by`.
3. `matrix(product)` → `{class: (level, 'yaml'|'default')}` for every class; one
   `env.ConfigError` naming every unknown class and every level not in `LEVELS`.
   `signals(product)` → `{class: {'paths': [...], 'commands': [...]}}` from
   `product.approval_signals`, a `ConfigError` for a class not in the catalogue or a key other
   than `paths`/`commands`.
4. `classify(product, tool_name, tool_input, cwd)` → `[(class, detail)]` in catalogue order, per
   §2.1 "Matching": `Write`/`Edit`/`MultiEdit` read `file_path`, `NotebookEdit`
   `notebook_path`, `Bash` `command`; anything else → `[]`. Paths are made repo-relative
   against `git rev-parse --show-toplevel` in `cwd` (else `cwd`), POSIX-separated; a glob with
   `/` matches the whole path, without one the file name, both `fnmatch.fnmatchcase`. The
   built-in recognisers of the §2.1 table: `touch_production` (a `git push` refspec to
   `product.main` in the `main`, `HEAD:main`, `refs/heads/main` and `<src>:` forms — built from
   the product's `main`, never a literal; `gh workflow run <deploy_sha.workflow>` when set),
   `touch_security` (the path globs plus `hooks.RUNTIME_SETTINGS_GLOBS`; `gh secret`,
   `gh auth`, `git config core.hooksPath`, `--no-verify`), `touch_legal` (file-name globs),
   `new_epic` (a `Write` of a not-yet-existing `epics/*.md` in a repo where
   `harvest.is_record_repo`; `asf new epic`), `file_bug` (`asf new bug`). `approval_signals`
   add to a class; never remove. `detail` is the matched path or the command's first 120
   characters.
5. The ledger (§4, D9, D14): `ledger_path(product)` = `env.state_dir(product)/approvals.jsonl`;
   `refuse(product, item, cls, level, job, tool, detail)` appends the §4 `refused` line with
   `hold = f'{item}/{cls}'` and `ts`; `resolve(product, hold, resolution)` appends `resolved`
   (`resolution` in `granted|done|dropped`, else `ValueError`); `holds(product)` folds the file
   to `{hold: {item, class, level, detail, first, last, count, resolution, announced, closed}}`;
   `open_holds(product)` = holds whose latest `refused` has no later `resolved`, oldest first;
   `is_granted(product, hold)` = its latest `resolved` is `granted`. A malformed line is skipped.
6. `asf/hooks.py`: add `RUNTIME_SETTINGS_GLOBS` (the runtime's project and user settings file
   globs) with a one-line comment; nothing else in this Task.
7. `asf/env.py`: `'approval_signals': _MAP` and a `Product.approval_signals` property beside
   `approvals`. `asf/conventions.py`: the `amendable_paths` field, its docstring line, default `[]`.
8. `docs/products.example.yaml`: replace the `approvals:` block with §2.2's, add the commented
   `approval_signals:` block and `amendable_paths: [rules/*, docs/CONSTITUTION.md]` under
   `conventions:`. `sample/product.yaml`: the same nine `approvals:` lines.
9. `tests/test_approvals.py`: `CatalogueTest` and `MatrixTest` with exactly the method names of
   A1, plus a `LedgerTest` (refuse → open; resolve → closed; a repeat refusal bumps `count`).
