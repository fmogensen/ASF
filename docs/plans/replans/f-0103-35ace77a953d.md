### Task T-0203: the wave writes down what held it, and the tick line carries it
stories: S-57308
writes: asf/tick/step_wave.py, asf/tick/tick.py, asf/metrics/metrics.py, tests/test_tick_steps.py, tests/test_metrics.py
after: none

§2.3: the one fact the wave knows and nothing else does — that it launched nothing, that New
Tasks existed anyway, and which gate held the rows it planned but did not launch. A pure function
for the answer, one key on the tick line, one key in the ticks schema. No printed line changes,
`wave: nothing to launch` included. Re-cut from `0ecf7bb` against RPD2/RPD3: `wave_state` reads
`screen()`'s own per-row verdicts rather than re-walking `planned` by hand.

**Files**

- `asf/tick/step_wave.py` — `GATE_CAP`, `NO_ROW`, `wave_state`; `launch` setting `ctx.wave` once,
  right after `worker_rows` is read off `screened`
- `asf/tick/tick.py` — `Context.__init__` gains `self.wave = {}`; `tick_line` carries `wave=ctx.wave`
- `asf/metrics/metrics.py` — `SCHEMAS['ticks']['wave'] = (('dict',), {})`
- `tests/test_tick_steps.py` — `WaveStateTests`; one case added to the existing `WaveStepTests`
- `tests/test_metrics.py` — `TickWaveSchemaTests`

**Steps**

1. `GATE_CAP = 10` and `NO_ROW = 'no row planned'` at module level in `step_wave.py`, beside the
   other wave-step constants, each with §2.3's doc comment — what the limit is for, not that it
   is a limit.
2. `wave_state(screened, held, items, launching=0)`, pure, returning
   `{'idle': bool, 'new_tasks': int, 'new_task_ids': [...], 'gates': {gate: count}}`:
   - `idle` is `not launching`;
   - `new_tasks` / `new_task_ids` from `items`, per the record's own default (every item whose
     `type` is `task` and whose `state` — defaulting to `New` — is `New`, confirmed at
     `asf/feeder/rows.py:1704`): ids sorted, capped at `GATE_CAP`, the count itself uncapped;
   - a gate per entry of `screened` whose `.starts` is false: `kind == WAITS` → `row.waits_on`,
     else the first word of `row.action` (the guard a future row without `waits_on` set still
     needs); `kind == HELD` → `f'held {held[row.item_id][0]}'` — the class alone, not the level;
     every other kind (`CLOSED`, `HOST`, `NO_SEAT`, `CAPPED`) → the kind string itself
     (`'closed'`, `'host'`, `'no seat'`, `'relaunch cap'`) — counted, not listed;
   - `gates = {NO_ROW: new_tasks}` when `screened` is empty and `new_tasks` is more than 0;
     `{}` when `screened` is empty and `new_tasks` is 0 too.
3. `launch` (`asf/tick/step_wave.py:1124`): right after `worker_rows = [s.wrow for s in
   starting]` (today's `:1205`), one assignment —
   `ctx.wave = wave_state(screened, held, items, launching=len(worker_rows))`. `screened` and
   `items` are already in scope there (`:1201-1202`, `:1135`); `held` is `approvals.raise_holds`'s
   own return, already bound at `:1128`. One assignment covers every return path below it
   (the `host_held` return, the `not worker_rows` return, the final return) because none of them
   change `screened` or `worker_rows` afterward — unlike the stale plan, which asked for the
   assignment "before each return" against a loop that no longer exists. A `launch` that raises
   before reaching this line leaves `ctx.wave` at `Context.__init__`'s `{}` — the safe default in
   both directions (PD15 of the original plan still holds: a crashed wave files no stalled-wave
   Bug and does not silently continue one). `launch_now` (`:1248`, the wave clock's own path,
   outside the product tick and never the writer of a `metrics/ticks` line) is untouched — out of
   this card's footprint, per the spec's own §1.3.
4. `Context.__init__` (`asf/tick/tick.py:219`): `self.wave = {}` beside `self.counts` (`:224`).
5. `tick_line` (`asf/tick/tick.py:907`): `wave=ctx.wave` added to the returned `dict` (`:910`).
   Nothing else on the line moves; `product` and `steps` are already there (landed independently
   of this card since the spec was approved — nothing to widen for them).
6. `SCHEMAS['ticks']` (`asf/metrics/metrics.py:164`) gains `'wave': (('dict',), {})` and only
   that. No new rule in `validate`'s `ticks` branch: a `dict` is all the key promises.
7. `WaveStateTests` per the spec's T5, expressed over `screen()`'s own objects: one
   `Screened(row, row.action, step_wave.WAITS)` whose row's `action` is `'WAITS ON T-0044'` and
   `waits_on` is `'T-0044'`; one the same with `action='ON TRUNK'`, `waits_on='trunk'`; one
   `Screened(row, 'held merge_pr (human-now)', step_wave.HELD)` whose row's `item_id` is a key of
   `held` mapping to `('merge_pr', 'human-now')` — with `launching=0`:
