## Reading the decision

Nothing in the approved spec's §3 or §4 is redesigned here — both land exactly as written. What
moves is *which Task they land in*. Re-reading `asf/tick/step_wave.py`'s `launch` (RD3, RD4) shows
the three checks already run inside **one function, one pass**, today:

1. `plan_order.overlay(items, plan_order.trunk_reader(product))` — the wave's own "defence in
   depth" re-derivation of every open Task's `after:`, called at the **top** of `launch` — already
   runs every tick, before anything else.
2. `gated_plan(...)`, a few lines later, calls into `feeder.rows.task_rows`, which reads that same
   `after:` to decide WAITS vs. launch.
3. §4's new `trunk_preflight` (T-0643's own design) sits further down the same `launch`, between
   the `left_out` loop and `host_hold` (RD3).

So "the one plan preflight, carrying all three checks over the same plan in the same pass" is not
a new module to invent — it already describes `step_wave.launch`'s existing shape, once §3's fix
to `plan_order.derived_after` (the `known` guard: keep, don't drop) and §4's wave-time trunk
recheck both land. The decision's scope is the **Task breakdown**, not the code: build both in one
Task, one coder, one branch, so the plan's `after:`-handling and the wave's trunk recheck are
reviewed and tested together as the one pass they already run in, rather than as two Tasks that
could drift apart or land out of order.

T-0641's own open question — the old plan's PD1, whether §1's predicate safely closes real plan
Tasks — is not reopened here: T-0641 has landed, and a landed Task is kept exactly as it is. Its
ruling, whatever it was, already happened.
