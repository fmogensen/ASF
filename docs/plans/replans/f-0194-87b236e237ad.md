# F-0194 re-cut — the seam, and nothing beside it

The groom's decision on this Feature is five words: **`cut it to the seam`**. The spec
(`docs/specs/f-0194.md`, approved) and the plan (`docs/plans/f-0194.md`) stand; this document
re-cuts the work still to do under them. Nothing has landed — all six Tasks are New — so the cut
is free: no commit is reverted and no branch is recut.

**What the seam is.** The spec names it itself, twice. C1: one method,
`GitHubHost.checks(number, required, head)`, returning today's `(state, detail, checks)` triple,
whose body under `ci.provider: vm` is `ci_vm.checks_at(product, head, required)`. And the design
rule the whole spec follows: *"nothing downstream of the triple learns a new shape. Every new line
of behaviour is on one side of one seam."* The seam is the one place a verdict crosses from *who
ran the tests* into the rules that decide whether a branch lands.

**The rule this cut applies.** Keep what a verdict must pass through for it to be **true** and to
**arrive at all**. Cut everything that only:

- *describes* the machines rather than judging them — `asf capacity`'s ceiling, the in-flight
  count, the five doctor rows (T-0712);
- *re-renders* a verdict the store already holds somewhere else — the commit status posted back to
  the PR host (T-0713), which C16 itself calls *"a write to someone else's system in service of a
  human's convenience"*;
- *stores what no reader of the triple reads* — the artifact collection, `ci.artifacts`,
  `ci.jobs[].artifacts` and the retention prune (cut from T-0709 and T-0708);
- makes the verdict arrive **sooner** rather than at all — the one-minute `ci-vm` clock and its four
  edit points in `asf/scheduler.py` (cut from T-0710).

**Four Tasks, three waves. Two dropped. Nothing added.**

| wave | Task | why it waits |
|---|---|---|
| 1 | T-0708 | nothing — `after: none` |
| 2 | T-0709 | the config the transport and the pass read |
| 3 | T-0710, T-0711 | both need only the store and the pass; their footprints intersect on `asf/harvest/lane.py` and `tests/test_ci_vm.py`, so the queue runs them one after the other in either order (PD14), in non-overlapping regions of that file |

The card's own acceptance — a product *"can switch from github-actions to vm by changing config
alone"* — is true at the end of T-0711, which is the last Task of the cut. It is not true before
it: until the seam lands, a vm product's lane still asks the code host.

## What the cut costs, named rather than discovered later

- **A vm product's CI capacity is not counted.** With T-0712 dropped, `capacity.product_ci` never
  sees `ci.hosts`, so the ceiling falls through to `capacity.ci` or the operator default, and
  `ci_runs_in_flight` still asks `gh run list --workflow <ci.workflow>` — which for a vm product
  reads 0 (no workflow is ever dispatched) or `?` (no workflow named). The factory can therefore
  start more branches than the machines have slots. That is **slower, not wrong**: the surplus
  queues in the pass's own dispatch, and the branches hold at `WAITING_CI` where, per P3 and
  measured again here (`ci_since` has one writer and one reader, `lane.py:4016-4020`, and the
  30-minute `landing_checks_wait_min` escape at `:4095` is reached only when `missing` is
  non-empty, which C4 makes impossible under `vm`), nobody is blamed and nothing is sent back.
- **No doctor row says a host is unreachable, or out of disk, or missing its `repo.git`.** The
  instrument that survives is the lane's own line each tick: `checks pending: <job names>`.
- **The one hazard PD7 found survives inside the seam.** `merge_required` adds
  `deploy_sha.prod.required_jobs` — workflow job names — to a non-docs class's required set, and
  under `vm` no `ci.jobs` entry answers them, so C4 renders each `pending` for ever. The doctor row
  that would have named it is cut; **C4's detail string is now the only instrument**, so T-0711
  keeps *"names no `ci.jobs` job"* in the detail and fences it in its acceptance. An operator
  reading `checks pending: deploy-prod (names no ci.jobs job)` has what they need.
- **No commit status on the PR, and no guide page.** A human looking at the PR sees no ASF verdict;
  the verdict is in `asf ci vm` and in the lane's output. The commented `ci.provider: vm` block in
  `docs/products.example.yaml` moves into T-0708 and is the only written reference this cut leaves.
- **Artifacts are not kept at all.** This is the one place the cut removes something the card's
  *description* asked for (*"Artifacts are kept on the VM, or in a configured store, with a
  retention setting"*). Keeping them without the prune would grow a CI box's disk without bound —
  the F-0178 failure under another name — so it is keep-both or cut-both, and the seam reads
  neither: no consumer of the triple reads an artifact. Cut both. A failed job still leaves its
  bounded 40-line tail in the store (C18), which is what `red_evidence` hands a correction session,
  and the run directory is removed at conclusion so nothing accumulates. A machine-local artifact
  keep is now a card of its own, beside the object store the spec already pushed out.

### Task T-0709: a sha runs on an ssh-reachable machine and comes back — the transport, the three remote scripts, the store, and the pass that dispatches, collects, supersedes and times out
stories: S-37701, S-37703
writes: asf/ci_vm.py, tests/test_ci_vm.py
after: T-0708

The spec's §2, §3 and §5's `vm_pass`, cut to **four steps, not five**: collect, supersede, time
out, dispatch. No artifact move, no prune, no `<root>/artifacts/` directory, no
`find … -mtime +<days>`. The run directory is removed at conclusion, which is what keeps a machine's
disk bounded with nothing to prune.

After this Task `ci_vm.vm_pass` pushes a sha to a machine, runs a command in a disposable worktree,
collects the exit code and forty lines, removes the directory, cancels what a newer push
superseded and fails what ran past its timeout — all under one lock, all behind the dry-run guard,
and none of it wired to anything yet.

The transport and the pass land together because they must: the `OneRun` fixture — this Task's own
acceptance — drives every one of them through `ci_vm.vm_pass`, so a Task that stopped at `push_sha`
would have no way to run its own fences.

Three of the four steps are on the seam, not beside it, and none of them may be cut further:
**collect** is the only thing that ever writes a verdict; **time out** (C7) is what guarantees every
dispatched job reaches a terminal state, because a `running` row is `pending` for ever and holds the
branch; **supersede** (C8) is what keeps the scarce slots pointed at the shas the seam is actually
asked about — without it, a branch that pushes often spends every slot on dead shas and the current
head is never dispatched.

Read **PD4** (the `ever_red` key, and why the pass never re-dispatches over a concluded row),
**PD10** (`vm_pass` has no `Lane`), **PD11** (the lazy `lane` import for `red_log_lines`) and
**PD12** (no `/tmp`, no `mktemp`) before starting.

**Files**

- `asf/ci_vm.py`
  - §2 — `ssh_argv`, `run_ssh`, `push_sha`, and `REMOTE_START`, `REMOTE_POLL`, `REMOTE_CANCEL`
    plus the inlined cleanup script, each a `sh` program with `{}` slots filled by `shlex.quote`
  - §3 — `STORE_FILE`, `RUNNING`/`PASSED`/`FAILED`/`TIMEOUT`/`CANCELLED`, `RED_STATES`, `BUCKETS`,
    `load`, `save`, `rows_at`, `in_flight`
  - PD10 — `heads`, `dispatch_targets`; and PD3's `GREEN_TRUNK_LIMIT` / `trunk_shas`, which land
    here with their siblings (their only caller arrives in T-0711)
  - §5 — `_MUTATING`, `vm_pass` and the four step functions it calls in order (`collect`,
    `supersede`, `time_out`, `dispatch`), and `register(sub)` as part of the module's own surface
    (T-0710 wires it)
- `tests/test_ci_vm.py` — `class FakeSsh` (the fixture) and `class OneRun(FakeSsh)`

**Steps**

1. The fixture first, because every assertion here is about what a real `sh` actually did: a temp
   directory as the "machine", a `sh` script put on `PATH` as `ssh` that strips the flags and the
   target off its own argv and runs the remaining stdin script against that directory, a real git
   repo with one commit, and a real bare repo reached over `file://`. No network, no real ssh, no
   mock of the scripts — `REMOTE_START`, `REMOTE_POLL` and `REMOTE_CANCEL` are executed.
2. `ssh_argv(host, timeout_s)` — the exact flag set and no more (C3): `BatchMode=yes`,
   `StrictHostKeyChecking=accept-new`, `ConnectTimeout=<n>`, the target, `sh -s`. No `-i`, no `-p`,
   no user, no `ProxyJump`: that is the operator's own ssh config, and re-expressing a subset of it
   here is the second configuration language C3 refuses.
3. `run_ssh(host, script, kind='read', timeout_s=None, run=subprocess.run)` — the script on
   **stdin**, never argv. `kind` other than `'read'` is a write: `if kind in _MUTATING and
   mutation_guard.is_active()` prints `would_line('ssh', …)` and returns `(1, '', line)` **before
   any process starts** (C17). Never raises: `OSError` and `TimeoutExpired` are `(124, '', <why>)`.
   `_MUTATING = ('start', 'cancel', 'cleanup')` lives here, not in `mutation_guard` (C17's own
   argument: there is no ssh argv to inspect). `'prune'` is not in it — there is no prune.
4. `push_sha` — `git push --force <ssh://…/repo.git> <sha>:refs/asf/<run_id>` from
   `product.repo_dir` (C5). A write, refused under a dry run through the same guard with the same
   line shape. `(True, '')` / `(False, why)`.
5. The three scripts. `REMOTE_START`: `mkdir -p <root>/runs`, `git init --bare -q <root>/repo.git`
   if absent, `git -C <root>/repo.git worktree add -q --detach <rundir>/src <ref>`, write
   `<rundir>/cmd`, start it **detached in its own process group** with stdout and stderr to
   `<rundir>/log` and the exit code written to `<rundir>/exit` on exit, print the pid.
   `REMOTE_POLL`: one call per host per pass whatever the number of runs, printing
   `<run_id> <exit-or-dash> <pid> <bytes-of-log>` per directory under `<root>/runs`.
   `REMOTE_CANCEL`: `kill -TERM -<pgid>`, a grace, `kill -KILL -<pgid>`, print what it killed.
   Cleanup: `git -C <root>/repo.git worktree remove --force`, `rm -rf` the run directory and the
   pushed ref — and nothing moved anywhere first. **No `timeout(1)` anywhere** (C7) — the pass owns
   the clock. Nothing is written outside `<root>`, and `<root>` holds exactly `repo.git` and `runs/`.
6. The store: `<state_dir>/ci-vm.json`, `{"version": 1, "at": …, "runs": {sha: {job: row}}}`,
   written atomically (`<file>.<pid>` then `os.replace`). The row is the spec's eleven keys plus
   `ever_red` (PD4). `load` never raises — an unreadable or absent file is
   `{'version': 1, 'at': 0, 'runs': {}}`, which is what makes PD13's *"every required name
   pending"* the automatic answer in T-0711.
7. `vm_pass(product, out=print, dry_run=False, now=None, run=subprocess.run, wait_s=0)` — not a vm
   product: `(0, 0)` with no ssh and no git call, checked first. Then the lock
   (`<state_dir>/ci-vm.lock`); another pass holding it is `None`, one line, no work. Then the four
   steps **in order, because each frees what the next needs**: **collect** (one `REMOTE_POLL` per
   host with a `running` row; an `exit` file concludes `passed` on 0 else `failed`; the tail read
   bounded to `RED_LOG_TAIL_BYTES` off the remote, then through `lane.red_log_lines`, then at most
   `RED_LOG_LINES` stored, C18; the run directory removed; `ever_red` set per PD4) → **supersede**
   (one `heads(product)`; a `running` run whose branch's head moved is cancelled, cleaned,
   `superseded_by` the new sha; **a trunk run is never superseded**, C8) → **time out** (`running`
   past `timeout_min` on the pass's own clock: the tail collected *first*, then cancelled, cleaned,
   `timeout`, C7) → **dispatch** (`dispatch_targets(product)` in C9's order — trunk first, then
   branches by name, then jobs in `ci.jobs` declaration order — for every job with no row at the
   sha: a host whose labels satisfy the job's and that has a free slot, `push_sha`, `REMOTE_START`,
   the `running` row). `in_flight` is the dispatcher's own slot counter now that capacity's caller
   is cut.
8. One line per dispatch, conclusion, supersession and timeout, each naming the branch, the sha's
   first nine characters, the job and the host — the spec's §5 grammar:
   `ci vm: <branch> <sha9> gate passed on ci-1 (4m12s)` and
   `ci vm: dispatch worker/T-0700 abc123def gate → ci-1 (slot 2/2)`. One line when no slot or no
   matching host was free, saying which.
9. `register(sub)` — `asf ci vm [--apply] [--dry-run]`: the view without `--apply` (the hosts,
   their slots, what is running and at which sha), the pass with it. T-0710 wires it into the group.
10. `OneRun`'s cases, below.
