`scheme=`. The cause **key is not renamed** — `ci-job:<name>` stays exactly what `metric` and
`verify` read today, which is the whole of the spec's C11: a card already filed against that key is
verified by the same reading, and the count can only go up.

  the two counters (`:212-214`); the `ci-job:` cause's detail line (`:315-316`).

**Steps**

2. Both `setdefault` literals (`:210-211`, the `ci-job:<name>` row, and `:220`, the gate rows) gain
   `'timeouts': 0, 'runner_losses': 0`. The gate loop's own body (`:215-223`) is otherwise
   untouched: a gate is not a job, has no `cause`, and neither counter is ever incremented there —
   which is exactly what keeps `by_ci_job`'s rows one shape.
3. The job counter's body gains `cause = j.get('cause')`, `c['timeouts'] += 1 if cause ==

   today — measured at this head: `facts_fixture`'s one `ci` row (`tests/test_scorecard.py:93`)
   carries job dicts with no `cause` key at all, so `j.get('cause')` is `None` and every existing
   `DiagnoseTests` assertion holds unchanged (confirmed green in RD6).
4. The `ci-job:` cause's detail (`:315-316`) gains `+ (f" {c['timeouts']} ran to their limit." if
   c['timeouts'] else '')` and `+ (f" {c['runner_losses']} lost their runner." if
   c['runner_losses'] else '')` **inside** the positional argument, before the `,` and the
   `scheme=` keyword that follow it at `:317-318`. No key, scope, threshold or unit changes.
5. The new `DiagnoseTests` cases are the Acceptance below. `metric` needs no change at all: it
