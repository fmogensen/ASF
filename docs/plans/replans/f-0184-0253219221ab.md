## The findings, all re-verified in this worktree at `7d2ee49c6`

**R1 — the baseline row never fires as the old plan wrote it, and the obvious repair raises.**
`ci_measure.regressions(readings, base)` reads `baseline[0]` (`ci_measure.py:202`), so its `base`
is the **in-memory** map `{runner: {kind: (p50_s, n)}}` that `baselines()` returns. The old plan's
Task 5 says the row is *"one per `ci_measure.regressions` hit against
`ci_measure.read_baselines(product)`"*, and `read_baselines` returns the **file document** —
`{v, taken, window_days, per: {...}, tier: {...}}` (`:242-275`), whose runners are one level down
under `per` and whose readings are `{'p50_s': …, 'n': …}` dicts, not tuples. Measured, over a
`ci-4`/`gate` reading of 512s against a published 318s baseline:

```
whole doc as base ->  []                      # silent: base.get('ci-4') is None
['per'] as base   ->  KeyError: 0             # {'p50_s': …}[0]
converted         ->  [('ci-4','gate',512.0,318.0)]
```

So the row as planned is silent, and a coder who notices and reaches for `['per']` gets an
exception in a diagnostic command. **Decided:** T-0680 converts, once, at the call:
`{r: {k: (v['p50_s'], v['n']) for k, v in kinds.items()} for r, kinds in
(read_baselines(product).get('per') or {}).items()}`. `ci_measure.py` is **not** edited to meet the
caller — it is another Task's landed footprint, and the conversion is three lines in the reader
that wants it. The converted call reproduces §2.5's example row exactly (512 ÷ 318 = 1.61×).

**R2 — the tiers the slow row names come from the census, through the public reader.**
