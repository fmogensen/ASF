### RD6 — `prefetch` must consume its results, because `RateLimited` is a `BaseException`

`gh_limit.RateLimited` is **`class RateLimited(BaseException)`** (**:40-42**), and its docstring says
why: *"A BaseException on purpose: never caught by an `except Exception` fallback."* The tree holds
that line everywhere — `pr_graph`'s module docstring: *"a rate limit is never absent —
`RateLimited` propagates"*; `evidence.py:89`: *"a rate limit is never 'no PRs' (RateLimited is no
Exception: it leaves)"*.

The spec's `prefetch` swallows *"every exception"* with `contextlib.suppress(Exception)`, which is
already the right instrument — `RateLimited` is not an `Exception` and leaves the callable. But a
`ThreadPoolExecutor` captures whatever leaves a worker **into its Future**, and `pool.map` returns a
lazy generator: a `prefetch` that *"throws every answer away"* by never iterating that generator
would swallow a rate limit after all, by never retrieving it — and the pass would carry on calling
GitHub against a latch that is already tripped.

**Decided:** `prefetch` discards *values*, never *results*. It consumes the map fully (`for _ in
pool.map(...)` or `list(...)`) inside the `with` block, so an ordinary failure stays suppressed per
call and a `RateLimited` from `gh_limit.guard` leaves `prefetch` and the pass with it. This is
stated in `prefetch`'s docstring beside *"never load-bearing"*, because the two sound contradictory
and are not: a broken read is the pass's to make again, a tripped latch is nobody's to make at all.
