# B-82658 — plan: check_cancelled judges the newest check per name, not a stale rerun twin

Item: B-82658 — Watchdog: a required check cancelled or timed out past 10 min — #1233@4a831f9c8.
Severity S2. Epic: E-0001 — ASF 0.1 — a working factory. Branch: `fix/B-82658`.
Spec: `docs/specs/b-82658.md` — the cause, the evidence on the card, and why this is the same
shape of bug `asf/harvest/lane.py`'s `latest_checks()` already fixed for `pr_checks()`.

## Cause

A rerun leaves the pre-rerun `CANCELLED`/`TIMED_OUT` check-run entry in the PR's
`statusCheckRollup` forever, alongside the rerun's own later entry of the same name.
`check_cancelled` scanned the whole rollup, so a required check already fixed by its one rerun
kept breaching for ever.

## Task 1 — check_cancelled judges only the newest entry per check name

writes: `asf/dwell.py` `tests/test_dwell.py`

- Step 1: in `asf/dwell.py`, add `_latest_by_name(checks)` — `checks`, reduced to one entry per
  `name`: the newest by `completedAt` (a check still running has no `completedAt` and counts as
  the newest), the list's order kept. The same dedup `asf/harvest/lane.py`'s `latest_checks()`
  already applies to `pr_checks()`'s identical stale-twin problem.
- Step 2: in `check_cancelled`, call `checks = _latest_by_name(checks)` right after `checks` is
  built and the draft/empty-checks guard, before the "something still runs" scan and the
  `CANCELLED`/`TIMED_OUT` scan — so a stale pre-rerun entry is never judged beside its own
  rerun's later result.
- Step 3: test, in `tests/test_dwell.py`
  (`CancelledCheckTests.test_a_stale_cancelled_check_shadowed_by_its_own_rerun_is_not_a_breach`):
  a PR whose rollup carries a `CANCELLED` `"tests"` entry 30 minutes old beside a `SUCCESS`
  `"tests"` entry 5 minutes old yields no `check_cancelled` finding.

## Accepted costs

`_latest_by_name` breaks an exact `completedAt` tie by keeping whichever of the two same-named
entries sorts later in the input list (`>=`), not necessarily the true latest. Not observed in
the evidence for this item and not covered by a test either way; flagged non-blocking (I1) by
review round 1. Worth a secondary tiebreak (e.g. the run id out of `detailsUrl`) if it's ever seen
in practice — not fixed here.
