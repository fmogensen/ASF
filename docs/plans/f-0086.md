# Plan F-0086 — The groom proposes merges, splits and batches — shape decides delivery speed

Epic: E-0001 — ASF 0.1 — a working factory. Spec: `docs/specs/f-0086.md` (approved). Branch: `plan/F-0086`.

Four Tasks. Three of them are disjoint and run together; the fourth writes `asf/groom/groom.py`
after the first does, because it depends on the first — the ingest fix has to be on the trunk
before a merge is allowed to mark a Task `removed`.

## Decisions

| # | Question | Decided |
|---|---|---|
| P1 | How the work is cut | By module: record (`asf/record`), feeder (`asf/feeder`), briefs (`asf/briefs`), groom (`asf/groom` + `asf/conventions.py`). The spec's design section is already written per module, and each module has its own test file, so a Task's gate is its own. |
| P2 | Proposals and apply in one Task | Yes. S-7900…S-7903 all write `asf/groom/shape.py`, `asf/groom/groom.py` and `tests/test_groom_shape.py`; the spec's fenced acceptance for the proposal Stories reads the *rendered groom file*, so the section wiring in `groom.py` cannot be deferred to the apply Task. Splitting them would produce exactly the shape the spec's D2 merges back: overlapping Tasks the feeder serialises anyway, at the cost of a second session and a second gate. |
| P3 | Task 2 queues on Task 1 | Deliberate, not an accident. Both write `asf/groom/groom.py`, and the spec's Preconditions say merging *depends* on S-7906 ("a merged-away Task would then stay `New` forever"). Task 1 lands the ingest and coverage fix including `groom_stories_without_tasks`; Task 2 then adds the four sections and the apply on top. |
| P4 | Task card ids | Not minted here. `asf.record.plan_tasks.mint_plan_tasks` turns each `### Task N:` heading of the landed plan into a card with an id from `asf.record.ids.mint_id` (`asf/record/plan_tasks.py:60-80`), so this plan's headings are the parser's ordinals `1…4` as in `tests/test_plan_tasks.py:18`. The session's `BACKLOG_ID_RANGE` (`T:8700-8749`) is therefore unused by this plan; no id is invented. |
| P5 | How capacity and the two conventions reach the sections (spec is silent) | `build_groom_sections(canonical, derived, date)` gains three keyword arguments with defaults — `capacity=DEFAULT_CAPACITY`, `area_depth=DEFAULT_AREA_DEPTH`, `batch_max_globs=DEFAULT_BATCH_MAX_GLOBS` — and `cmd_groom` fills them: capacity from `asf.tick.step_wave.capacity()` (imported inside the function, so `asf.groom` keeps its import out of `asf.tick`), the two conventions from `env.load_product(args.product).conventions`, guarded by `except env.ConfigError` exactly as `default_bug_epic` is today (`asf/groom/groom.py:284-289`). Defaults keep every existing caller working. |
| P6 | `derived` at apply time (spec is silent) | D8 re-checks readiness when an answer is applied, and `shape.ready_tasks` needs `derived` for the parent chain — but `cmd_groom` computes `derived` only *after* the inbox pass (`asf/groom/groom.py:302`). So `apply_groom_answers` gains `derived=None` and computes `compute_derived(canonical)` itself when it is not given. The post-inbox recompute stays as it is: the sections must see cards the inbox just minted. |
| P7 | `KIND_ORDER` and the new row kind | `KIND_ORDER[RESHAPE] = 3` **and** the fallback in `candidates`' sort key becomes `KIND_ORDER.get(r.kind, 4)` (`asf/feeder/rows.py:353`). Today every kind not in the table sorts at 3; leaving the fallback at 3 would tie `RESHAPE` with `PLAN → CODE` and let a lower-id new Task sort first, which is not "before new work within a Feature". Bumping the fallback moves all unlisted kinds together, so no existing relative order changes. |
| P8 | The capacity-1 feeder test | `tiers.select` shows a non-launching row only while a slot is free (`asf/feeder/tiers.py:34-37`), so with capacity 1 a `WAITS ON` row emitted after the `RESHAPE` row took the slot falls outside the cut. `test_reshape_row_takes_a_slot_and_waits_take_none` therefore asserts presence against `rows.candidates()` and the slot arithmetic against `rows.plan_rows()`. No change to `tiers.py`: the cut's behaviour is not this Feature's business. |
| P9 | `tests/test_conventions.py` | Not in any Task's `writes:`. It asserts no field list (checked), and the spec asks for no conventions test — the two new fields are covered by the shape tests that read them. |

Nothing here widens the spec. Where the spec's design left a signature or a sort key unstated, the
decision above names it; where the spec states behaviour, the Task copies it.

### Task 2: the groom proposes merges, batches and splits, and applies the answers
stories: S-7900, S-7901, S-7902, S-7903
writes: asf/groom/shape.py, asf/groom/groom.py, asf/conventions.py, docs/products.example.yaml, tests/test_groom_shape.py

The Feature's body: a new pure module that reads shape off the index and three sections of
answerable lines, plus the apply that turns `yes`/`no` into typed fields. Runs after Task 1 (P3);
its branch is cut from a trunk that already carries the removed-Task fixes.

**Files**

- `asf/groom/shape.py` — new. `area_of`, `areas`, `ready_tasks`, `merge_proposals`,
  `batch_proposals`, `split_proposals`, `proposal_key`, and the `Proposal(verb, ids, areas, why)`
  record, exactly the surface the spec's design lists.
- `asf/groom/groom.py` — `GROOM_SECTIONS`, `build_groom_sections`, `PROPOSAL_RE`,
  `apply_groom_answers`, `apply_proposal`, `merge_tasks`, `cmd_groom`'s summary line.
- `asf/conventions.py` — `DEFAULT_AREA_DEPTH = 2`, `DEFAULT_BATCH_MAX_GLOBS = 2` beside their
  neighbours (`asf/conventions.py:39-58`), each with its one-line doc comment, and the two fields on
  `Conventions` (`asf/conventions.py:74-88`).
- `docs/products.example.yaml` — both keys under `conventions:`, commented out, at their defaults.
- `tests/test_groom_shape.py` — new: `AreaTest`, `MergeProposalTest`, `BatchProposalTest`,
  `SplitProposalTest`, `ApplyTest`.

**Steps**

1. `shape.area_of(glob, depth)` per the spec's D5: the glob's `footprint._literal_head`, minus its
   last path component unless the glob ends in `/`, cut to the first `depth` segments; a root file
   is `.`. `areas(writes, depth)` returns `{area: [globs]}` in first-seen order.
2. `shape.ready_tasks(canonical, derived)`: `type: task`, `is_open`, machine `state: New`, not
   `blocked`; its Feature (parent chain or `feature:`, as `feeder.rows._task_feature` resolves it)
   decided, open, at `plan-approved` or `building …`; no `reshape:`; and, when it has a
   `split_from:`, also `decided: true`. Sorted by (Feature rank, Task rank, id).
3. `merge_proposals` (D2): the overlap graph over one Feature's ready Tasks, using
   `asf.feeder.footprint.overlaps` — never a second overlap test. One `Proposal` per connected
   component of size ≥ 2; `ids` ordered by `(rank, id)`, so `ids[0]` is the survivor (D7). The `why`
   names the first overlapping pair.
4. `batch_proposals` (D3): per Feature, `units` = ready Tasks with each pending merge counted as one.
   When `units > capacity` and at least two Tasks have `len(writes) <= batch_max_globs`, batch the
   `max(2, units - capacity + 1)` smallest, ordered `(len(writes), rank, id)`.
5. `split_proposals` (D4): a ready Task whose globs fall in two or more areas, where at least one
   area overlaps a holder (an `Active` Task, or a ready Task of *another* Feature — splits compare
   across Features) and at least one overlaps none. The `why` names each held area with its holder,
   then the free areas.
6. `proposal_key(verb, ids, areas=())` → `<verb> <sorted ids>`, or `split <id> <areas>`. Every
   proposal builder drops a proposal whose key is already in any named Task's `reshape_declined`
   (D11).
7. `groom.GROOM_SECTIONS` gains, after `Stories without Tasks after plan-approved`:
   `('Merges proposed', 'merge')`, `('Batches proposed', 'batch')`, `('Splits proposed', 'split')`,
   `('Split parts to confirm', 'split_parts')`. `build_groom_sections` computes all four and takes
   the three new keyword arguments of P5; `cmd_groom` fills them. Render each line as
   `- [ ] <id> <verb> <ids> — <why> → answer: ____`, matching the spec's four worked examples
   byte for byte in shape; `(none)` when empty, like every other section.
8. `PROPOSAL_RE = ^- \[[ xX]\]\s+(?P<id>[A-Z]-\d{4})\s+(?P<verb>merge|batch|split)\s+(?P<rest>.*?)\s+—`.
   `apply_groom_answers` tries it before `ANSWER_LINE_RE`; a match goes to `apply_proposal` and never
   reaches `_parse_answer`, so `no` on a proposal line can never write `removed` (D6). The
   `controller:` prefix keeps its attribution-only meaning. `apply_groom_answers` gains `derived=None`
   (P6).
9. `apply_proposal(root, canonical, verb, ids, areas, answer, date, who)`:
   - `yes` + `merge`/`batch` → `merge_tasks`: re-check every id is still ready (D8) and, if one is
     not, print `groom: <verb> <ids> skipped — <id> is <why>` and write nothing; otherwise write on
     the survivor `writes` and `stories` (ordered unions) and `merged` (the others, appended), and
     on each other Task `removed: merged into <survivor> (groom <date>)`.
   - `yes` + `split` → re-check ready, then `reshape: split <a> | <b> (groom <date>)`. No `decided`
     field is written.
   - `no`/`close` → append `proposal_key(...)` to `reshape_declined` on each named Task.
   - Blank, `____`, or a field already at its target value → nothing, which is what keeps `--apply`
     idempotent (`asf/groom/groom.py:88-90`).
   One History line per card per applied answer, through `append_history_lines`:
   `- <date> groom: merged T-b into T-a (operator)`,
   `- <date> groom: removed → merged into T-a (operator)`,
   `- <date> groom: reshape → split <areas> (operator)`,
   `- <date> groom: merge declined (operator)`.
10. `cmd_groom`'s summary counts the four new sections the way it counts the others (the existing
    `counts` comprehension already iterates `GROOM_SECTIONS`, so this follows from step 7).
11. The two conventions and their commented-out lines in `docs/products.example.yaml`.
12. `tests/test_groom_shape.py` with `tests/test_groom.py`'s `make_repo` / `write_item` / `run`
    helpers, and a temp `config.yaml` carrying `feeder: {capacity: 4}` for `BatchProposalTest`.

### Task 3: the feeder holds a reshaped Task and launches one reshape session

## Waves

- **Wave 1** — Task 1 (`asf/record` + the one `groom.py` coverage line), Task 3 (`asf/feeder`),
  Task 4 (`asf/briefs`). Pairwise disjoint `writes:`, so the feeder launches all three together.
  Task 3 emits rows with `brief_kind='reshape'` before Task 4 lands the template; nothing validates
  a kind at row time (`normalize_kind` runs when a brief is built), so neither gate depends on the
  other.
- **Wave 2** — Task 2. Its `writes:` meets Task 1's on `asf/groom/groom.py`, so the footprint gate
  holds it until Task 1 is done — which is what this Feature wants anyway (P3).

coverage: 7/7 stories; uncovered: none
